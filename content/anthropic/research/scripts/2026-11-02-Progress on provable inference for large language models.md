Progress on provable inference for large language models，中文可以译成，大语言模型可证明推理的进展。这篇文章发表于二〇二六年十一月二日，距离今天十一月八日，只有六天。

欢迎收听 Claude FM。今天我们聊一个听上去很像密码学支线任务，实际上却直接关系到模型调用可信度的问题。你花钱调用的那个模型，真的就是给你生成回答的模型吗？

你可能会说，我看回答质量就知道了。便宜模型写不出这么好的代码，或者某个模型的语气，我已经很熟悉了。但这些判断都不是严格证据。小模型偶尔也能发挥出色，大模型也会犯低级错误。更重要的是，中间服务完全可能只在部分请求上替换模型，让你很难靠体感发现。

这篇文章想做的，就是把这件事从凭感觉判断，变成可以检查的数学声明。它介绍了一个叫 FlashProve 的研究原型。模型服务商给出回答的同时，还能提供一份密码学证明，让拿不到权重、也买不起整套推理设备的用户，验证这次计算确实对应指定的模型。

但先把最重要的边界放在前面。这不是证明答案正确，不是证明模型没有幻觉，更不是证明模型安全。它要证明的是，这个回答与事先承诺的那套模型计算相匹配。身份证是真的，不代表持证人说的每句话都是真的。这条区别，会贯穿我们今天的讨论。

先回到实际工作中的信任链。假设你的应用通过一家模型聚合平台调用上游服务。你选了高能力模型，平台收取相应费用。但在拥堵时段，它可能偷偷切到更便宜的模型。返回结构、模型名称、计费字段，都可以维持原样。你看到的只是服务商关于自己行为的一份说明。

传统数字签名能解决一部分问题。它能证明某段数据由持有某把密钥的一方签发，而且签发后没有被修改。但是，签名本身并不能证明签发之前发生了什么。服务商完全可以给另一套模型的回答签名。你验证了签名，依然没有验证实际执行的模型。

另一个办法是自己重跑。拿到权重，准备同样的输入，再算一遍，看看结果是否一致。可是前沿模型往往不公开权重。即使权重公开了，运行成本也很高。更何况，用户原本就是因为没有相应资源，才购买推理服务。为了验一次货，再建一家同样的工厂，这显然不合理。

可证明推理要填补的，就是这个空缺。它把昂贵的计算和相对便宜的检查分开。服务商承担生成证明的主要成本，用户只需要检查一个远小于完整计算过程的证明文件。不必拿到模型参数，也不必重新运行整个模型。

文章采用的工具，叫零知识简洁知识论证，英文缩写通常写作 zkSNARK。你不需要记住这串字母，可以先把它理解成一种带隐私保护的计算收据。收据不只是写着我算过了，而是能让验证程序检查，所声称的计算是否符合约定。

这里有两个关键性质。一个是简洁，验证比重新执行原始计算便宜得多。另一个是零知识，证明本身不会额外泄露模型权重或者内部计算轨迹。当然，模型回答本身已经透露的信息，不会被魔法般消除。零知识说的是，证明不会在这个基础上再多泄露。

这项研究选择的是纯软件密码学路线，不是主要依靠可信执行环境。可信执行环境可以理解为硬件提供的隔离保险箱，由芯片和相关机制为内部执行背书。它和密码学证明不是谁彻底替代谁，而是建立在不同信任假设上，可以互相补充。

密码学路线的吸引力是，即便执行环境不值得信任，只要密码学假设和验证链成立，攻击者也不能轻易为错误计算伪造有效证明。但请注意，这句话不意味着服务器不会被攻破，更不意味着权重不会被偷。它限制的是攻击者拿错误计算冒充约定计算的能力。

那 FlashProve 具体怎样工作？我们从两个阶段来理解。第一步发生在离线阶段，模型提供者对权重生成一个承诺。你可以把它想成先封存一份配方，再公开一个能够锁定这份配方的凭据。之后不能随意换配方，却声称自己用的还是原来那份。

这个比喻有个需要修正的地方。它不是把权重简单做一个公开摘要就万事大吉。这里的承诺要和后续证明协议配合，同时满足绑定权重和隐藏权重的要求。用户拿到的是用来固定模型身份的密码学对象，而不是能还原参数的压缩包。

第二步是在线阶段。针对给定的提示词和待核验的输出 token，也就是模型处理文本的基本单位，服务商生成证明。验证方拿着权重承诺、输入、输出和证明，检查这组数据是否符合约定模型的执行结果。

这里还有一层经常被忽略的信任。如果你只知道某个承诺，却不知道它对应谁，那你最多证明自己始终在使用同一个未知模型。要证明它是你买的那个模型，还需要通过可信渠道，把承诺与模型名称、版本和获准使用的身份对应起来。我个人认为，这会是工程接入时必须认真管理的元数据。

想象一家餐厅。后厨不愿公开秘方，顾客也不可能进去重做一道菜。现在餐厅先锁定秘方，再提供一种能验证烹饪计算的收据。顾客能够检查，这道菜是不是按约定配方执行出来的。但是，这份收据不会自动告诉你，秘方是否健康，或者菜是否符合你的口味。

对应到协议，文章强调四种性质。诚实计算生成的证明应该被接受，这是完备性。错误声明很难混过验证，这是可靠性，也就是通常说的健全性。证明不额外泄露秘密，这是零知识。证明相对小、验证相对便宜，这是简洁性。

不要把可靠性理解成毫无前提的绝对不可能。密码学通常是在明确计算假设下，把成功伪造的概率压到可以忽略。它更接近工程上有清楚条件的安全保证，而不是一句不需要解释的绝对安全。

接下来是最吸引眼球的性能结果。文章测试的模型是 Llama 四 Maverick，一个总参数量约四千亿的混合专家模型。混合专家，英文叫 MoE，意思是模型内部有多个专家子网络，每个 token 只调用其中一部分，而不是让全部参数都参与计算。

这款模型每个 token 实际使用的参数，大约是一百七十亿。FlashProve 的重要设计，就是让证明工作量跟真正参与运算的专家成比例，而不是跟四千亿总参数成比例。你可以想象一家拥有几百位医生的医院，今天一次会诊只请了其中几位。核验会诊过程，不必让全院医生重新报到。

但它又必须隐藏这次到底请了谁。文章声称，证明不会泄露每层选择了哪些专家。这就比单纯把未使用参数跳过去更复杂。它既要利用稀疏执行节约计算，又不能通过证明内容直接暴露内部选择。

第二个关键优化，是事后证明和批处理。模型先完成文本，证明器再读取已经完成的内容，以类似预填充的方式并行处理。预填充可以理解为，给定一段已经存在的文本，一次性计算这段上下文，而不是像实时聊天那样，一个字接一个字等待生成。

为什么这能提速？生成时，后一个 token 往往要等前一个出来，存在串行依赖。但文字已经确定以后，很多计算就可以组织成更适合并行硬件的形式。文章还把多个请求放在一起证明，让权重承诺的相关操作按批次承担，而不是每个请求都重复付费。

第三个优化，是把系统放进单张显卡。注意，这不是说四千亿参数都塞进了显存。测试使用的是四比特量化权重，量化模型仍然大约占二百三十二吉字节。它把各层权重切分成片段，放在主机内存里，再分段传入显卡进行证明。

所以这里的单卡配置，还配有大约二百九十吉字节主机内存，以及二十四个处理器核心。显卡是八十吉字节显存的 H一百。我个人认为，单卡这个标签很容易让人联想到普通开发机，但它实际表达的是降低对多卡系统的依赖，而不是把整体硬件要求降到了笔记本级别。

在这套配置上，离线承诺阶段每个模型大约运行三十九分钟。这份承诺也不是永远有效。出于协议中的技术原因，它大约可以支持一千六百万次请求，之后需要重新承诺。生产系统如果采用这个方案，就需要管理承诺的有效范围和轮换，而不能把它当作永久不变的模型编号。

在线测试把二十四个请求组成一批，每个请求对应一千零二十四个 token 的窗口。整批证明大约花二百二十三秒，折算得到每秒一百一十个 token 的证明处理速度。每个请求对应的证明文件约十八点七八兆字节，也就是文章概括的十九兆字节。

这里必须慢一点。每秒一百一十个 token，不等于用户能以这个速度收到带证明的实时回答。它是特定批处理和上下文条件下的证明吞吐。原文还说明，每份证明检查一个 token 的选择。因此，不能直接把这个数字理解成，每秒给一百一十个新生成的回答 token 提供完整端到端认证。

如果你在做性能评审，要追问清楚分母到底是什么。统计的是上下文里参与计算的位置，还是新增输出的位置？证明覆盖一个选择，还是整段生成过程？批处理带来了多少摊销？这不是吹毛求疵，而是决定业务成本能否算对的关键。

验证端不需要显卡，只需要权重承诺和证明文件。承诺下载量大约六点五兆字节。在二十四线程处理器上，检查一份证明大约十七秒；单线程大约二十一秒，统计包括离线阶段的相关检查。对于四千亿参数模型，这确实比重新执行轻得多，但也不是点击一下就瞬间完成。

再看和普通推理的对比。作者用常见开源推理引擎 vLLM，在八张 H一百上运行同一模型的八位浮点版本，再按显卡时间进行比较。证明处理同样一批请求，大约需要普通推理七十二倍的显卡时间。在测试的更高负载下，这个比例接近九十四倍。

因此，文章说的大约七十到九十五倍，是有具体实验口径的。证明侧使用四比特权重和整数运算，对照侧是八位浮点版本。这不是同一份实现只打开一个证明开关的对照实验，更不是所有模型和服务负载下都成立的固定税率。

即便如此，这个进展仍然值得重视。过去一些系统证明很小的模型，都需要长时间计算。文章列出的同模型先前方案 VerInf，报告处理一千个 token 需要十四点三小时，证明文件约九十三点六吉字节，验证几乎要一天。但它使用不同硬件，不能直接把两个时间相除当作严格的算法加速比。

更稳妥的结论是，这个方向正在从难以使用，走向可以认真做试点。文章也列举了商业团队的进展，不过部分对应实现尚未开源。因此，这次发布的价值不只是一个性能数字，还包括其他人可以拿来检查、复现和改进的实现与材料。

底层密码学怎么做到这些？文章没有在博客里展开完整协议，我们也不假装能用一个比喻替代技术报告。它采用一种成熟路线，先构建交互式预言机证明，再借助哈希函数，把它转成可分发、可验证的密码学证明。

直觉上，你可以把前一层理解为，把庞大计算组织成一种适合严格抽查的数学结构。这里的抽查不是随便看几行日志，而是通过编码理论和复杂性理论，让错误计算难以同时满足所有检查关系。系统还结合了带线性约束的编码接近性测试和查找论证等工具。

我们不必记住这些名称，但要知道，FlashProve 不是靠让另一个模型判断回答像不像来验真。它验证的是数学关系。文章称，这套基于哈希的构造还能提供后量子安全性质。不过具体保证仍要放回所使用的密码学假设和协议分析中理解。

说到这里，真正棘手的问题出现了。负责检查的代码本身，谁来检查？如果验证器写错，攻击者可能提交一份实际上无效、但能钻实现漏洞的证明。你原本想摆脱对服务商的信任，结果只是把信任转移到了另一段程序。

这也是文章另一条主线，形式化验证。作者使用 Lean，一种可以编写数学定义并让机器检查证明的工具，描述协议及其安全性质。他们特别提到，Claude 参与了优化，并找到了应用现有密码学工具的新方法，但大型复杂系统里的优化决策往往不容易评估。

所以，与其因为代码是人工写的或者模型写的，就直接决定信不信，不如把关键声明写成机器能检查的形式。这里的目标包括完备性、可靠性和零知识。相关分析处在随机预言机模型里，可以把它理解为，对哈希函数行为采用的一种理想化数学建模方式。

但形式化验证不是盖上一个章，整套软件就自动安全。文章非常明确地指出两个缺口。首先，你证明的命题，必须真的是你想要的命题。假设团队本来想证明所有关键步骤都经过核验，却不小心把定义写得过弱，机器仍然可能正确地证明一个没有实际价值的结论。

因此，人仍然要审计顶层声明。作者提供了交互式可视化工具，帮助审阅这些定理。我个人认为，这特别像需求评审与单元测试的关系。测试再严谨，也不能自动修复需求写错的问题。形式化工具加强的是逻辑检查，不替你决定业务上到底该承诺什么。

第二个缺口，是实际运行的代码是否符合形式化协议。作者提供了两个验证器。一个是运行较快的 C加加实现，另一个是较慢、但有形式化正确性连接的 Lean 实现。后者被证明，只会接受安全定理所定义的验证器会接受的东西。

快版本没有同等级的形式保证。它在作者的测试中，与 Lean 验证器对所有测试证明给出了相同结果。但测试一致不等于所有输入都一致。这一点很重要，不能把提供了形式化证明，简化成生产使用的快速代码已经全部证明正确。

不同安全性质，审计重点也不同。要防止假证明蒙混过关，关键是验证器，因为证明器本来就可以不可信。要保证不泄露权重，关键却是证明器。一个有问题的证明生成程序，完全可能把秘密塞进不该出现的地方，即使验证端没有漏洞。

作者没有提供便于实际运行的 Lean 证明器来解决后者，因为生成证明太昂贵。他们期待模型提供者通过充分的人工或智能体安全审计，检查实现与形式协议的一致性。所以，对外购买模型服务的人，和持有私有权重的服务商，关注的风险并不完全一样。

再来看最容易被宏大叙事盖过去的限制。当前证明针对的，是一个精确的整数模型，而且使用贪心解码。贪心解码就是每一步选择模型当前评分最高的那个 token，不进行随机采样。它不是对所有常见生成设置的通用保证。

日常聊天里，你可能调整温度，希望回答更有变化。实际服务还可能使用浮点运算，不同硬件和计算顺序也会引入差异。即便大家口头上都说运行的是同一个模型，只要某一步输出选择发生变化，就不再完全匹配这里证明的整数贪心计算。

原文说，整数版本与浮点推理通常预期差异较小，也做过经验测试，但这不覆盖对抗性设计的提示词。换句话说，普通测试里经常接近，不代表攻击者刻意寻找差异时也一样。我个人认为，对高风险系统，这是必须单独验证的行为等价问题，不能靠模型名称一致来跳过。

另外，当前上下文最多一千零二十四个 token。对很多真实工程任务，这相当短。一个稍复杂的代码文件，或者几轮包含工具结果的对话，就可能超过窗口。不能把长对话随手切成很多短段，再宣布原来的长上下文行为也得到了证明，因为模型看见的信息已经变了。

系统也不隐藏架构。它隐藏权重、中间值和专家选择，但混合专家的结构本身不是秘密。文章提出，未来可以设想连架构和执行代码一起承诺的系统，但那不是这次已经实现的能力。对把架构也视为商业机密的提供者，这仍然是限制。

还有侧信道。证明内容不泄露秘密，不代表观察证明生成耗时、资源消耗等外部现象，也绝对得不到信息。本文把这类攻击放在范围之外。因此，零知识是对特定对象和模型的严格声明，不是对整个线上服务所有可观察行为的隐身承诺。

现在把这些放回实际工作。假如你负责一家公司的模型网关，我个人建议先做离线审计试点，而不是承诺所有聊天请求实时附带完整证明。挑一类短输入、允许延迟、价值较高的任务，固定模型版本、整数执行规则和解码方式，把证明作为事后可核验的审计材料。

比如一个内部评测集，你担心评测时使用的模型与正式声称的模型不一致。可以先设计能够被当前协议完整覆盖的测试请求，并保存承诺、输入、输出、证明和验证结果。这里最重要的不是把几个文件丢进对象存储，而是让它们有明确的绑定关系和版本记录。

如果验证失败，不要立刻得出服务商作弊的结论。也可能是输入规范不同、输出经过了后处理、整数模型与浮点服务不一致，或者证明文件损坏。我个人建议把密码学验证失败与业务判责分开，先保留证据，再沿着执行配置和数据链路排查。

如果验证通过，也别自动把答案标成事实正确。假如模型在代码审计中漏掉一个漏洞，有效证明只能说明指定模型执行了指定检查，并给出这个结果。文章讨论的失败证明设想，也是证明某个模型投入约定数量的 token 后没有取得某种结果，而不是证明世界上不存在漏洞。

安全团队也可以考虑另一种用法，要求推理服务器为结果提供绑定授权权重的证明。这样，攻击者即使控制了服务进程，也不能随意换成另一个模型，还继续拿有效证明冒充原模型。但这不会阻止所有攻击。授权模型本身产生危险内容，或者输出之后的外围系统被攻击，都不在这份证明自动解决的范围内。

而且，FlashProve 当前是事后证明。你可能已经收到了回答，过一段时间才知道它是否通过检查。对于自动付款、执行命令、修改生产配置这样的动作，晚到的保证可能已经来不及。我个人认为，可以把未验证输出先隔离，待通过后再进入高风险流程，但这种设计会直接引入等待时间。

若只证明一部分流量，也要诚实描述覆盖范围。被验证的请求可信，不等于其余所有请求都因此获得相同保证。如何选样、攻击者是否知道抽样规则、抽样结果如何用于审计，都是额外的系统设计问题，不能把密码学可靠性直接移植成全流量可靠性。

监管场景同样如此。文章设想，通过推理证明，让提供者证明一定时期确实执行了声称的模型推理。这可能帮助核实部分算力使用承诺，也可能帮助检查是否提供了获准模型。但证明这些推理发生了，不等于证明没有同时进行秘密训练。

这是一个很值得记住的逻辑边界。证明做了某件事，通常不等于证明没有做另一件事。如果想对整体算力用途作判断，还需要覆盖率、计量以及其他约束。我个人认为，这类工具最好的定位，是可信治理证据链中的一个组件，而不是一把解决所有监管难题的钥匙。

对于想动手的工程师，这次发布包括技术报告、协议说明、证明器、两个验证器，以及 Lean 证明和可视化材料，代码与相关文档采用 Apache 二点零许可证。第一步可以先围绕验证器理解数据格式和信任边界，再评估有没有资源运行完整证明流程，不必一开始就追求最大的模型。

我个人会优先检查三个问题。我们到底要认证什么声明？它能否在当前整数模型、短上下文和贪心解码条件下成立？为此付出的证明计算、传输和等待成本，是否低于这份保证带来的价值？如果这三个问题答不清楚，接入再漂亮，也容易变成昂贵的安全装饰。

最后再把主线收回来。FlashProve 的进展，是让隐藏权重的大模型推理，能够附上一份外部可检查的数学证据，同时把成本推进到值得实际试验的范围。

我个人认为，它最重要的变化，是把相信服务商确实这么算了，往我能核验这个具体声明推进了一步。但身份真实不等于答案真实，局部证明不等于全系统安全，理解这两条边界，才算真正理解了可证明推理。
