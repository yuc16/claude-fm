Claude can design electronic prototypes from start to finish，中文可以译为，Claude 能够从头到尾设计电子产品原型。这篇文章发表于二〇二六年十一月九日，今天是二〇二六年十一月十五日，距离发表只有六天。欢迎来到 Claude FM，今天我们聊的不是让人工智能画一张看上去很专业的电路图，而是让它把设计推进到真正能拿在手里、接上电、运行起来的电子样机。

先把最重要的边界放在前面。这里的从头到尾，不是说 Claude 自己操作机器焊接，也不是说它已经交付了经过认证、可以大规模上市的商品。文章展示的是，Claude 负责设计、编写固件、准备制造文件，并指导人类工程师组装和运行。三个原型都能工作，而且电路没有经过额外修补。但长期可靠性、商业认证，以及量产能力，仍然没有得到验证。

为什么这件事值得软件工程师听？因为它把一个我们很熟悉的问题，搬到了容错率更低的世界。写软件时，一个函数看起来正确，不代表整个系统能上线。做硬件也是一样，芯片选得对，不代表板子布得下；板子布得下，不代表外壳装得进去；装得进去，也不代表声音、电源和无线连接都能正常工作。真正难的，是让这些条件同时成立。

文章来自 Anthropic，他们与一家设计和制造电路板的公司 Diode Computers 合作。大约一年多以前，双方就开始测试 Claude 的电子设计能力。当时的任务还比较基础，比如读芯片的数据手册，判断一颗芯片要正常工作，需要哪些配套零件。那时的模型不能可靠地完成电路板布局，也很难保证设计出来的各个部分能够配合。

到了这次实验，他们使用 Claude Fable 五点二，要求它设计三个设备。一个是连接电脑的会议免提电话，一个是语音助手中枢，还有一个是手持电子宠物。这三个任务的意义，不在于产品类别有多新，而在于它们必须同时面对电路、机械结构、嵌入式软件，以及制造条件。它们是跨领域的组合题，而不是单一知识点的问答题。

以免提电话为例，最初的要求相当简洁。做一个圆饼状设备，通过 USB C 连接电脑，里面有麦克风和扬声器，支持蓝牙，并且使用电路板天线。这里的 USB 是通用串行总线，大家每天给设备接线时都会碰到。原文并没有描述一份事无巨细的工程任务书，而是说，在很少提示的情况下，Claude 自己把这个需求展开成了具体工作。

它写产品规格，画原理图，选择元件在印刷电路板上的位置，然后安排元件之间的铜连接，设计可以三维打印的外壳，编写固件，最后准备零件清单。印刷电路板，也就是常说的 PCB，可以理解为零件的承载平台，加上预先铺好的电气道路。固件则是运行在设备内部、直接控制硬件的软件。设计完成以后，Diode 按照 Claude 的指导组装电路板、运行固件，做出了真正工作的设备。

这台免提电话在使用数周以后仍然能工作，另外两个设备也保持正常。不过，三个成功案例不能自动变成对所有电子设计任务的保证。我们接下来更值得追问的是，它究竟在哪些环节表现出了进步，这些进步又为什么能把原来卡住的工作往前推进。

文章认为，最显著的差别是几何推理。听到几何，你可能想到中学里的三角形和圆，但电路板上的几何问题更像是在一个很小的城市里，同时安排住宅、道路、供电和交通规则。芯片不是随便放在哪里都行，连接器也不是朝哪个方向都一样。有些配套零件需要靠近它服务的芯片，有些线路必须避开干扰，还有些线路的长度和相互间距需要受到控制。

早期模型的问题就出在这里。它可能知道某颗芯片需要一个配套元件，却把这个元件放得太远。也可能把接口摆在一个电气上能连接、机械上却不方便使用的位置。这很像一个只理解软件模块依赖、不理解部署环境的程序员，把所有服务都接通了，却忘了服务之间还有延迟、带宽和故障域的问题。

新版模型的做法更有工程上的优先级。它不是看到哪两个点就先连哪两个点，而是先处理高速信号、大电流，以及对噪声比较敏感的连接。我们可以把这理解成先修高速公路和主干供电，再安排普通街道。因为主干线路的条件最苛刻，如果先让次要连接占满空间，最后就可能没有办法给关键连接留出合适的路径。

语音助手中枢就是一个具体例子。Claude 先处理 USB 和以太网连接。这些连接涉及成对工作的铜走线，信号沿着两条细长的铜路径传播。模型会一对一对地安排，控制同一对走线的长度和间距，还会加入小幅弯折的调谐形状，用绕一点路的方式补足长度，让信号到达时间更接近。

你可以想象两个人需要并排走到终点。一个人走得太短，一个人绕得太远，即使最终都到了，也可能错过配合的时机。这里的类比并不能代替真实的信号分析，但能帮助我们理解，为什么电路连接不只是连上就算完成。文章还提到，Claude 调整了电源部分的元件布局，以提高效率。也就是说，它考虑的不只是连接关系，还有这些连接在空间里的具体实现。

为了不只靠三个演示说话，研究团队还提供了基准测试。Diode 的内部测试叫 PCB Gym，会把现有电路板的布局拿掉，再考察模型放置元件和重新布线的能力。Fable 五点二得到百分之六十九，Fable 五得到百分之二十五。另一个公开测试叫 BenchCAD 二点一，要求模型根据工程图和渲染图重建三维零件、装配体和电路板，新模型得分是百分之八十三点五，接近前代 Fable 五点一的两倍。

这里要特别留意两个比较对象。前一个测试对比的是 Fable 五，后一个对比的是 Fable 五点一，不能把它们混成同一组升级数字。也不能把百分之六十九理解成，随便给它一块商业电路板就有百分之六十九的概率直接成功。原文提供的是特定基准里的分数，它能支持能力进步这个判断，但不能直接换算成所有真实项目的交付概率。

除了空间安排，第二个关键变化是，模型愿意主动推翻自己的局部设计。文章里有一句话特别有工程味道。过去一年，Diode 用早期模型做过很多完成了百分之九十五、却仍然不能用的板子。对于软件从业者，这个状态应该不陌生。界面做完了，接口也有了，只有最后一个核心依赖接不上，整个系统就没法交付。

硬件布线里的最后一点，尤其不能简单按工作量理解。如果剩下的连接被前面的布局堵死，那不是再努力画几条线就能解决，而是可能要退回去移动元件、改变信号分配，甚至重做一片区域。百分之九十五完成度，可能只是一个看起来很接近终点的死胡同。旧模型的问题，就是不太会主动承认自己走进了死胡同。

这次免提电话使用四层铜的电路板。Claude 在设计过程中，重新分配了两颗芯片上部分信号对应的引脚，让触摸控制区域下面的走线能够留在同一层，而且不彼此交叉。之后电路板背面又太拥挤，它进一步交换了可以互换的引脚信号，重新安排了板子的一整个角落，而不是不断增加线路在不同铜层之间的跳转。

这里有一个容易忽略的前提。不是所有引脚都可以随意互换，原文说的是能够互换的那些引脚。真正有效的调整，是在器件允许的范围内重新分配功能，而不是为了让图更漂亮，就改掉芯片本身的电气约束。对于工程师来说，这种能力的价值在于，模型能把芯片配置和物理布线放在一起考虑，而不把它们当成互不相关的两个任务。

语音助手中枢的例子更直接。Claude 发现铜线纠缠到难以目视追踪，于是判断，应该把这部分走线删除，重新开始。文章说，它进行了数十次删除和重新布线，直到得到可行的安排。我个人认为，这比一次画出漂亮线路更值得关注。真实工程不是永远不犯错，而是能不能识别错误的结构，愿不愿意付出返工成本，把系统带回可解的状态。

当然，返工次数多本身不是好事。它也可能意味着低效。这里真正有价值的是，返工最终收敛到了可制造、可运行的结果。如果未来把这种能力接入工作流，我们不应该只奖励它持续产出文件，还要记录每次改动的理由、解决了哪个约束，以及是否引入新的问题。否则，自动返工也可能退化成自动来回折腾。这是我的实践建议，不是文章已经验证的结论。

第三个变化，是它不只使用工具，还会根据任务调整工具。先说查资料。芯片的数据手册，是厂家对引脚、电气条件和工作模式的正式说明。对于电子设计来说，它更像接口契约，而不是可以凭印象略过的帮助文档。文章里的 Claude 在遇到依赖具体器件细节的问题时，经常会去查对应的数据手册。

比如，有人问手持电子宠物在不装电池的情况下能不能运行。Claude 读了充电芯片的手册后，判断可以用 USB 供电，但充电指示灯可能闪烁，因为充电器会反复给代替电池位置的小电容充电。这不是仅凭设备能不能亮起来给出的二元回答，它进一步推演了某个工作状态下可能出现的现象。

这对软件工程师的启发很直接。一个硬件模块的名字，和它完整的行为契约，是两回事。就像某个接口叫保存，并不代表它返回成功时数据已经永久落盘。模型如果只凭熟悉的名词补全答案，很容易忽略边界条件。查手册的价值，就是把推理重新锚定到具体器件，而不是停留在一般常识。

更有意思的是布线工具。Diode 给 Claude 提供的软件，可以调用 KiCad 内置的布线器。KiCad 是常见的电路板设计软件，而这里的布线器可以在模型选择的两个点之间安排一条线路。但语音助手中枢有一个一百引脚的连接器，相关长线路如果逐条处理，就需要大量细碎操作。

于是 Claude 判断，这种交互方式不够高效，自己写了一个布线算法。它把板子划分成网格，在网格里搜索每条线路能够通过的路径。大约半小时后，这个工具就能用大约一秒钟布好一条长线。之后它发现一条音频时钟线靠以太网线路太近，又修改算法，让敏感线路周围留出更多空间。

我们不要把这理解成，它用半小时替代了一套成熟的专业设计软件。原文展示的是，它针对眼前任务补了一个更合适的工具，解决特定长线路的安排问题。这里最值得软件工程师关注的，是任务分解方式发生了变化。模型不再只想，我下一步应该点哪里，而是会想，重复点击这么多次，是不是应该先写一段程序。

我个人认为，这就是软件能力向其他工程领域渗透的一条重要路径。不是要求一个模型把所有专业动作都靠语言逐条完成，而是允许它把重复工作变成算法，再用专业约束修正算法。与此同时，生成工具也需要检查。算法找得到路径，不代表路径满足全部电气要求，工具输出仍然需要回到设计规则和工程验证里。

第四个重点，是跨领域约束。很多演示看起来很惊艳，是因为它只展示了一个领域内部的结果。比如电路图没有明显问题，或者外壳渲染得很漂亮。但产品失败，经常发生在两个领域交接的地方。电路工程师觉得没问题，机械工程师也觉得没问题，最后却发现板子放不进盒子，或者设备装起来以后声音不对。

文章中，Claude 为每个设备的外壳写了检查代码，确认电路板的三维模型放进去后，元件之间不会发生碰撞。不过，它发现免提电话还有更细的问题。最终摆放位置虽然可能合适，安装过程却不一定可行。如果把板子垂直放进外壳，静音开关会撞到后壁。解决方法是安装时把板子倾斜大约二十五度，再放入对应位置。

Claude 在三维模型里检查了这个过程，并把步骤加进装配说明。这说明什么？静态的装配结果，和到达这个结果的运动路径，是两种不同的问题。就像一个数据库最终状态符合约束，不代表迁移过程中每一步都不会锁死服务。硬件也有自己的迁移路径，装得下和装得进去，中间就隔着这样一个现实细节。

语音助手中枢的外壳还牵涉声学。麦克风通常需要一个让外部声音进入的小通道。Claude 计算出，如果这个通道长二十五毫米，共振频率会接近三点四千赫兹，落在语音频段内。它的判断是，这对语音助手来说仍然能用，但不是理想状态。于是它提出做成后高前低的楔形外壳，把相关通道缩短到大约十毫米。

按照文章给出的计算，这样可以把共振频率抬到约八点九千赫兹，接近语音所用范围的边缘。这里我们要区分预测和测量。原文展示的是设计时的计算与调整，并没有因此宣布完成了全面的声学实测。我个人认为，最有意义的不是某个频率数字，而是模型发现外壳的几何长度会影响声音，随后愿意改变外观结构，而不是只在软件里补救。

免提电话还有一个跨领域例子。设备有一圈发光二极管，也就是常说的 LED 灯。Claude 编写固件，让声音越大，灯光就越暗，目的是不超过它给电路板设定的电流上限。灯和扬声器在功能上不同，但它们共享供电预算。模型在这里把电源约束转化成了软件控制策略。

这就像一个后端系统同时跑在线请求和批处理任务。总资源有限，就要让不同负载协调，而不是各自按最大需求争抢。不过这个类比也提醒我们，协调策略是否合适，要看产品需求。灯光变暗能不能接受，声音是否始终优先，都应该让人类明确。文章说明 Claude 做了这个设计，但没有说这种取舍适合所有设备。

接下来是最现实的一关，工厂能不能做。电子设计里，图画得通只是起点，制造还会受到最小间距、保护层形状，以及元件供应情况的约束。文章提到两类检查，一类是面向制造的设计检查，简称 DFM，把电路板几何形状与工厂能力对照。另一类是采购检查，确认分销商有没有所需零件。

Claude 自己执行检查，并把结果分成必须修复的问题，以及可以忽略的提示。语音助手中枢有六处细长的阻焊层被标为太薄，无法制造。阻焊层就是电路板表面的保护涂层。它没有因此把元件全部挪动，而是扩大阻焊开口，修复了这些几何问题。这是一个改动范围比较克制的处理方式。

另一个提示涉及两处地之间的连接。这里的地，可以理解为电流共同的返回路径。自动检查器没有识别出这是一处刻意设计的连接，于是把它报成错误。Claude 判断这不会影响性能，保留了设计。这个例子说明，检查器发出提示，不代表所有提示都必须机械消除，工程判断仍然存在。

但我也要补一句个人建议。不能因为文章里有一次正确忽略告警，就让模型在项目里随意清空告警。更稳妥的方式是要求它给出忽略理由、对应依据和影响范围，再由工程师复核。自动检查和模型解释都不是最终真理。尤其当两者意见相反时，分歧本身就是一个值得保留的审核点。

最终，Diode 直接根据 Claude 的设计文件制造了三块板，没有为了调整制造问题来回沟通。团队对此感到意外，因为现实里往往需要多轮修改。但这里的结论仍然要放在合适的位置。这说明这些原型的设计文件顺利通过了当次制造流程，不代表它们已经完成了面向大规模生产的成本、良率和供应链优化。

如果你现在就在做嵌入式、机器人，或者某种带传感器的小设备，应该怎么借鉴？我个人建议，不要一开始就把整个产品扔给模型，要求它全权交付。更实际的入口，是挑一个边界清楚、风险可控、结果能够独立核对的子任务，例如整理某颗芯片的供电要求，核对接口定义，或者检查外壳与电路板的空间关系。

给任务时，要把约束一起交出去。不要只说帮我做一个语音设备，还要说明供电来源、可接受的尺寸、需要哪些接口，以及现成制造条件。文章中的简短提示展示了模型的主动展开能力，但实际团队不应该把需求缺失当成理想工作方式。能明确的条件越早明确，模型后面因为错误假设而返工的机会通常就越少。

再往前走，可以让它先交付中间产物，而不是直接交最终文件。比如先解释功能如何拆分，哪些接口最敏感，哪些决定会影响后面的结构设计。然后再审原理图和布局，最后检查制造资料。这样的阶段性审核，不是退回全手工，而是把人的注意力集中到高影响决策上。我个人认为，这比只看最终样机有没有亮灯，更容易发现系统性风险。

对于软件团队，另一个可马上借鉴的点，是把模型的工程活动留下可追踪记录。它为什么换引脚，为什么删除原来的线路，为什么忽略检查提示，都应该能回溯。我们熟悉的版本控制、变更说明和自动检查，可以成为连接软件工作习惯与硬件设计过程的桥梁。但这里要强调，这是一种工作流建议，并不是原文已经展示了一套完整的审计系统。

还要特别防范一种错觉，就是模型解释得越顺，工程结果就越可信。比如它说两条线长度已经匹配，我们仍然要看实际设计数据。它说外壳没有碰撞，要检查模型尺寸和装配方式。它说某个零件有库存，也要注意采购时点。文字层面的自洽，不能代替设计文件、制造约束和实际测量之间的一致。

这也把我们带回文章最明确的局限。三个设备都是原型，还没有完成电气验证、天线调试、热测试和认证，也不是按量产要求设计的。能连接蓝牙，不等于天线性能在各种使用姿态下都合格。连续用了几周没坏，也不等于已经证明长期可靠。这些不是否定演示，而是区分工程阶段所必需的常识。

此外，Claude 没有连接测试仪器，也没有直接连接制造和装配设备。真正动手制造和测试的，仍然是 Diode 的工程师。所以这次工作不能被描述成一个完全脱离人的自动工厂。更准确的理解是，模型承担了跨度很大的数字设计和推理工作，人类负责把这些设计带进物理世界，并确认原型能运行。

原文最后提出，下一步要研究更密、更快、更复杂的电路板，也要看模型能不能做仿真，并且从成品设备的测量中学习。这一点很关键。当前展示的主线，是从需求走向设计，再走向原型。下一步如果能把真实测量重新带回设计，就有机会形成更完整的闭环。但那是计划中的方向，不是这篇文章已经交出的结果。

文章也提到，其他模型在这个领域同样有进展，OpenAI 最近介绍过用模型设计手持设备的工作。因此，不必把这看成某一个模型独有的魔法。我个人更关心的趋势是，人工智能开始处理那些必须同时尊重逻辑、空间和制造条件的任务，软件生成能力也开始成为它解决物理工程问题的一种工具。

最后用三句话收个尾。这篇文章真正展示的，不只是 Claude 会画电路，而是它开始能在布局、返工、工具使用和制造约束之间持续协调，把设计推进到可工作的样机。我个人认为，它最有价值的角色不是替工程师宣布产品合格，而是更快地探索方案、暴露约束，并把更多想法送到值得认真测试的阶段。样机能工作是一道重要门槛，但从样机走向可信赖的产品，测量、验证和人的责任仍然不能省。
