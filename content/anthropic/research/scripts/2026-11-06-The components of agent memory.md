## Script

The components of agent memory，中文可以译为，智能体记忆的组成部分。这篇文章发表于二〇二六年十一月六日，来自 Anthropic 的研究栏目。今天是二〇二六年十一月八日，所以我们聊的是两天前刚发表的一篇研究。

欢迎来到 Claude FM。我想先问你一个问题。如果你做的人工智能助手，每次都能翻出以前的聊天记录，却还是反复犯同一种错，你会觉得它有记忆吗？从存储系统的角度看，有。从一个真正能积累经验的同事的角度看，好像还差得很远。

这篇文章就在拆解这个差距。它不只是讨论应该把数据放进文件夹，还是放进数据库，而是追问，智能体怎么判断什么值得记，怎么把一次失败变成下次有用的规则，以及写错了的记忆，要由谁来纠正。

这里的 agent，也就是智能体，指的是能够调用工具、执行任务，并持续推进目标的模型系统。文章提出的一个重要思路，是让智能体在工作间隙整理自己的经历。作者把这个过程叫 dreaming，中文可以说做梦。当然，不是说模型有了梦境，而是利用后台计算，重新阅读日志，修订笔记，建立知识之间的联系。

作者开头引用了哲学家克尔凯郭尔的一句话。生命只能向后理解，却必须向前生活。记忆系统也有这个矛盾。当你正在做事的时候，你并不知道今天哪个小细节，会成为明天解决问题的关键。等你终于知道什么重要，那个细节可能已经被你忽略了。

人脑给了作者一个类比。我们经历事情时，海马体参与快速形成记忆；到了睡眠或者安静休息时，近期经历会被重放，其中一部分逐渐整合进长期知识。文章也提到，Letta 和加州大学伯克利分校的研究者提出过睡眠时间计算，让模型在交互间隙重新组织已有上下文。

这里要注意，这只是功能上的类比，不是证明模型和大脑以同样的机制工作。对软件工程师来说，你可以把它理解成前台请求和后台维护的分工。前台先把事情办完，后台再做复盘、合并和校验。问题在于，后台到底应该产出什么，才不会只是多制造一堆文本。

我们先把文章所说的记忆定义清楚。它指 Claude 从用户交互和任务经历中获得、跨会话保留，并且以后能够重新读取的知识。这里不包括修改模型权重，也就是训练得到的内部参数；不包括只在当前对话中生效的上下文学习；也不包括为了继续长对话，把旧消息压缩成摘要的上下文压缩。

这个区别很重要。当前窗口里记得住，和下周开一个新会话还能用，是两件事。把历史消息概括一下，和提炼出一条经过验证的工作规则，也不是一回事。文章真正关心的是，经历如何变成可以复用的外部知识，而不只是让对话继续下去。

作者给出的第一个关键判断是，记忆有时是一种预测。你写下一条规则，实际是在预测，这个规律将来还会有用。你保存一个已经核实的事实，也是在预测，未来某次任务值得直接使用它，而不是再花时间查一遍。

想象你刚接手一个老项目，发现测试环境的某个配置开关，名字和实际含义正好相反。你当然可以把整个排障过程保存下来，但下一位同事更需要的，可能只有三样东西：这个开关实际控制什么，你怎么验证的，以及在哪个版本里成立。记忆的价值不在记录了多少经历，而在减少多少重复摸索。

文章用持续学习基准的一点零版本做实验，其中一个任务要求 Claude 查询数据库，连续回答问题。每次回答以后，系统告诉它正确答案，它可以写下记忆。下一个问题从全新会话开始，唯一能够延续的，是一个持久化的记忆目录。

这个设置把问题分得很清楚。模型不能依靠前一个会话还留在窗口里的信息，只能依靠自己主动保存的东西。理想情况下，它会形成一个学习闭环：答错以后记录失败，提出原因假设，验证假设，再把得到的规律用于下一题。

不同模型的表现差别很明显。Sonnet 四点六能提出为什么答错的猜测，但目录里散落着不少未经验证的猜测。Opus 四点七开始把内容整理成一个参考文档，并区分哪些事实已经检查，哪些还没确认。Sonnet 五会在评分器确认后标记答案，答错时写下修正。

到了 Opus 五，作者观察到更完整的闭环。它的大多数条目包含规则，说明为什么知道规则成立，保留之前问题的答案，还会提醒后续使用者注意已经踩过的坑。后来的 Opus 五点五和 Sonnet 五点五也能完成这样的闭环，有记忆时的成绩与 Opus 五大致相当，而无记忆时的基础表现略高。

这里最值得带走的，不是模型名字的排序，而是知识状态的变化。一个猜测如果被写成肯定句，再在未来被当成事实使用，记忆就会把不确定性藏起来。原来只是一次可能的解释，经过保存和重读，居然变成了系统的默认常识。

我个人认为，工程上很值得把事实、假设和建议分开。比如一次接口故障之后，不要只写，请求失败是因为限流。应该说明，这是日志已经证实的原因，还是目前最合理的猜测。若做过验证，也要保留验证条件。否则所谓长期学习，可能只是长期累积误判。

第二个关键问题，是到底什么值得记。文章让 Claude 玩宝可梦红版，观察它在长任务中怎么组织记忆。每次运行开始，模型都有一个可以读取和写入的记忆文件夹。作者比较了 Sonnet 三点七和 Fable 五各一次运行，在大约一万步时的表现。

Sonnet 三点七的做法接近，既然不知道以后需要什么，那就什么都记。打一场战斗，建个文件；捡到一个物品，再建个文件；遇到一个非玩家角色，也保存一下。最后它写了四百一十三个记忆文件，分散在二百二十五个文件夹里，拿到一枚徽章。

Fable 五则只有两个文件夹中的九个文件，再加一个顶层全局文件，却拿到了四枚徽章。这里不能简单说，文件越少成绩越好，因为比较的是不同模型，而且是各一次运行。但作者观察到的行为差异，非常值得工程团队警惕。

宝可梦里的状态不停变化。你站在哪里、身上有多少钱，下一步就可能不同，而且屏幕本身通常就能告诉你。把这些东西反复存进长期记忆，不仅重复，还会过期。于是智能体以后必须花力气判断，眼前看到的状态和笔记里的状态，究竟哪个才是真的。

Sonnet 三点七就在整理记忆这件事上越陷越深。大约一万步时，它开始建立第四套所谓主记忆目录。接下来的十七步里，它创建六个文件，删除九个文件，却没有在游戏里采取任何行动。你本来雇它来通关，它却忙着给自己的资料室搬家。

Fable 五更多保存游戏不会直接告诉它的东西，比如策略、路线计划，以及它从尝试中总结出来的规则。全局文件像一个仪表盘，写着当前目标、挑战道馆的计划，以及使用记忆的原则。其他文件再分别处理路线和游戏策略。

文章给了一个很生动的例子。连续七个精灵球都没抓到鲤鱼王以后，模型写下，如果连续三个以上失败，就改变按键时机，在菜单步骤之间增加等待，因为做出这个调整以后捕捉成功了。

不过我们也要保留判断。这个例子展示的是模型保存了什么，并不等于作者已经严格证明，改变等待时机就是成功的因果原因。一次成功之后提炼出的经验，仍然可能需要更多检验。前面说的学习闭环，在这里同样重要，不能因为笔记写得像规则，就默认它是真的。

Opus 五点五采取了类似的精简策略，持续维护当前目标和下一步的小型笔记，最后通关。我个人认为，这给工作流一个很好的提示：稳定可查询的状态交给系统，难以重新获得的经验交给记忆。数据库能实时告诉你的，不一定需要模型再抄一遍。

那是不是应该给模型列一套非常细的记忆规范？文章的发现有点反直觉。作者认为，告诉 Claude 记忆是干什么用的，通常有帮助；但过于具体地规定怎么用，可能限制更强模型的判断。

在数据库任务里，只告诉模型有一个记忆目录，就足以让 Opus 四点七和 Opus 五明显受益。研究者也分别测试了一些具体规则。比如要求只记录失败，结果两个模型从记忆中获得的提升都大幅缩水。

原因并不难理解。失败当然值得复盘，但成功也可能提供关键证据。你第一次确认一个特殊查询方式是对的，或者终于弄清一个字段的含义，这些信息未必来自失败。只准记录失败，相当于把学习材料人为砍掉了一半。

不过旧一些的模型又是另一种情况。Sonnet 四点六经常不读记忆，也不验证自己的解释。明确提醒它回答前读取文件，并且测试假设，基准得分几乎翻倍。Sonnet 五则在没有专门提醒时，十次里大约九次会先读记忆，而四点六不到一半。

所以我个人认为，记忆提示词也要根据模型能力做实验。不能因为一个模型需要逐步提醒，就把所有模型都放进同样的流程。也不能因为新模型表现更好，就删掉所有约束。真正该比较的是，约束有没有改善任务结果，而不是提示词看起来够不够专业。

接下来进入文章最有辨识度的部分，后台做梦。前面谈的都是工作时写什么，但工作中的判断可能从一开始就错了。错误笔记被保存下来以后，会影响后面的行动，后面的行动又可能被解释成支持原来判断的证据。

文章仍然用宝可梦举例。游戏里的月见山，入口在地图西边，出口在东边。入口附近有一处单向台阶，走下去就会掉回之前的路线，不能直接爬回来。Claude 用山口附近的宝可梦中心作为地标，所以它认为这个建筑在哪一边，会直接影响路线选择。

有一次，它错误地记下，宝可梦中心在山的东边。离开中心时，它宣布月见山已经在身后，又把笔记更新成月见山完成。实际上它根本没有穿过山。随后它走下台阶，回到了旧路线，而导航工具没有明确展示这次掉落。

于是它又解释说，自己只是向西走过头了，仍然以为此前就在正确的一侧。这是一个典型的错误认知模型。真正需要修正的是我对地图的理解，而它只是在错误理解里重新规划动作。路线算得再勤快，也绕不出前提的错误。

研究者把含有错误位置的记忆目录交给做梦流程，让 Claude 对照原始会话记录检查。模型发现笔记写错了，修正之后，它直接回到月见山，最终到达华蓝市。没有修正的那次运行，则三次掉回旧路线，最后也没有到达目标城市。

这里的核心不是让模型多想一遍，而是让它拿笔记和原始证据对照。如果只是把错误摘要再总结一次，很可能得到一份更简洁、更自信的错误。做梦有效，需要有可追溯的材料，让系统能发现，自己后来写下的说法，与当时实际发生的事情不一致。

放到开发场景里，假设助手记下某服务不支持批量接口。后来每次都用循环逐条调用，既慢又容易限流。后台复盘如果能回看接口文档和调用记录，也许会发现，当时只是权限没开，而不是接口不存在。需要更新的是长期规则，而不是继续优化循环。

做梦还可以做另一件事，就是建立新的知识表示。文章重点讨论 wiki，也就是由 Claude 撰写、维护并相互链接的知识页面。你可以把它想成一张导航地图，告诉模型某个主题有哪些事实，相关问题应该去哪里找，而不是把所有文档重新复制一遍。

作者使用了 Stainless 的内部文档。这家公司是 Anthropic 在当年五月收购的软件公司。语料大约三十五万个文件，总计约四亿两千万 token。token 是模型处理文本时使用的基本单位，这个量级已经远远不是把资料一次塞进对话窗口就能解决的。

研究者设置了二十五个问题，并让 Opus 五在最多一百二十八轮会话中探索文档，创建和修正链接页面，合并重复内容，再对照来源核实说法。各轮通过共享日志协调，在之前工作的基础上继续积累。

随着做梦会话从两轮增加到一百二十八轮，只使用维基回答时，满足评分标准的比例从百分之十三提高到百分之四十八。注意，这不是说二十五题里答对了百分之四十八，而是按照评估标准计分的结果。原文中的不同指标，不能随手混成一个准确率。

更值得注意的是，维基和搜索一起用，效果最好。只用搜索工具时，综合得分是百分之五十三。随着维基成长，搜索加维基的得分从百分之五十四提高到百分之六十一。而且每个问题还能节省大约两万个 token。

这说明维基更像熟悉公司的老同事，而不是替代原始资料的万能答案库。老同事知道该查哪个系统、哪份文档，也知道几个不同名字其实在说同一件事。但真要确认具体条款，还是应该打开原文。地图提供方向，搜索提供证据，两者承担不同的职责。

当然，不是每个任务都值得建地图。文章还测试了并购文件和 Harvey 的法律基准。有一组二十四个并购问题，其中超过一半需要跨文档整合，很多还需要判断或者计算。在这些题上，使用维基得分百分之八十七，只用搜索是百分之七十三。

你可以想象，问题如果是这次交易涉及哪些付款安排，它可能散落在主合同、补充协议和附件里。事先建立关联，确实能帮助回答。但如果问题只是某一份合同的通知期限是多少，直接搜索原文，可能就已经足够。

作者也遇到了维基越写越大，最后比原始文档还大的情况。这就像做了一张和真实国土一样大的地图，细节全有了，抽象却消失了。维基的维护成本照付，但没有显著降低理解成本。记忆系统不能只评估内容有没有覆盖，还要评估有没有减少后续工作。

另一个关键设计，是记忆的层级。有些内容可以通过搜索找到，有些内容应该放到每次会话开始就能看到的顶层。文章把这种预先加载叫上下文注入，意思是在模型开始工作前，主动把某些记忆放进它的输入。

这样做有明显好处。模型不需要先想到应该搜索什么，才能知道某个坑的存在。但代价也直接。注入内容占用窗口，错误记忆会跟着进入每个新会话，而且加载进去不代表一定遵守。文章提到，指令文件越长，遵循程度还可能下降。

因此，顶层应该小，更多承担索引作用。文章介绍，Claude Code 的自动记忆不会把全部内容载入每个会话，而是只加载主记忆文件开头两百行或者二十五千字节范围内的内容。这一层主要告诉 Claude，它知道什么，以及细节存在哪里。

我个人认为，可以把它类比成团队入职手册的首页。首页不应该塞满所有事故复盘，而应该告诉你项目怎么启动，哪些原则不能违反，遇到哪类问题去查哪里。若每个历史细节都被提升成最高优先级提醒，真正重要的提醒反而会被淹没。

文章还有一个很工程化的案例，说明做梦不是把文件整理漂亮就够了，必须围绕任务目标组织信息。一个模拟公司收购的法律任务，重点是准确描述合同条款。最初模型建立维基时，多个智能体同时往一张共享的条款表里写内容。

结果既有摘要不准确，也有并发覆盖，导致关键事实丢失。基于这个维基生成的法律简报，只包含五十七个事实中的四十一个，大约百分之七十二。这里的问题不只是模型理解能力，也是数据结构和写入方式不合适。

后来研究者让 Claude 反思失败，提出新的构建指令，再重新建立维基。改进之后，每份合同有自己的页面，由单个智能体负责，条款逐字引用，而不是共同压缩进一张表。基于改进后维基生成的简报，能够满足全部评分标准。

这不是说所有任务都应该逐字摘抄。合同的具体措辞本身就是关键事实，过度概括会损失法律意义。换成项目背景介绍，长篇照抄可能毫无必要。记忆应该保留什么粒度，取决于后续任务需要做什么，不能用一种摘要模板通吃。

后台整理也能修补跨会话留下的空洞。比如某次会话先写下一个页面链接，准备以后补内容，下一次却用了另一个名字建页。文章里有一轮做梦发现九条指向不存在页面的链接，把它们改指向同一文档的现有页面，又补了三个新页面，其中包括索引。

这些修复听起来不惊艳，却非常实用。知识系统越大，链接失效、重复页面、名称不一致就越像技术债。单次任务里的模型未必看得到全局，后台流程却能跨越多次会话，检查这些局部合理、合起来混乱的问题。

如果你现在就要给团队搭一个类似系统，我个人建议先从一个很窄的工作流开始，比如代码库维护助手。先不要追求一个永远懂你的超级记忆，而是明确希望它减少哪种重复劳动，是重复查启动方式，还是重复踩测试环境的坑。

原始任务记录和提炼出来的记忆，最好分开保留。前者提供证据，后者方便使用。一条重要规则应当能回到来源，看得到适用条件和验证过程。尤其当记忆会影响部署、权限或者数据操作时，不能只留下结论，不留下理由。

你可以先让前台助手保存少量高价值信息，比如用户明确要求长期记住的偏好，已经验证的特殊操作，以及任务中断后的下一步。那些每次调用工具都能重新得到的实时状态，不必不加区分地升级成长久知识。

后台整理也不必一开始就持续运转。可以在一个任务结束后，检查新增笔记是否与日志一致，是否存在重复，旧规则有没有被新证据推翻。原文也明确说了，持续检查所有记忆未必现实，做梦需要计算资源，频率和重点都仍是开放问题。

我个人认为，优先复查经常被读取、最近发生变化，或者一旦出错代价很高的记忆，会比机械地全库扫描更容易落地。不过这是工程上的推演，不是文章已经验证的最优方案。你还得记录整理消耗，以及它实际避免了多少后续错误。

评估时，也别只问模型记没记住。应该让它在新会话里完成真实任务，比较没有记忆、只有原始记录搜索，以及搜索加整理后记忆的效果。除了完成质量，还要看读取了多少材料，花了多少时间，是否引用过期事实，能不能找到原始依据。

还有一种值得专门测试的情况，是故意放入一条已经失效的记忆。比如项目过去使用某种测试命令，后来迁移了。看助手能否根据新的仓库配置纠正旧笔记，而不是把旧经验当作比当前事实更高的权威。真正可靠的记忆，不仅要会保留，也要会撤回。

最后别忽视权限。我个人认为，后台做梦仍然是数据处理流程，不能因为发生在用户看不见的地方，就绕过原来的访问边界。一个人能在某次会话里看到的材料，不代表提炼之后就可以进入所有人的共享记忆。整理知识时，也必须保留知识的使用边界。

回到这篇文章，作者没有给出唯一正确的记忆架构。现场记笔记能立即帮助后续行动，却会打断当前任务；后台整理能看得更全面，却需要额外计算，结果也未必立刻可用。维基能提升跨文档理解，但还得维护，也可能积累新的错误。

所以我的总结是，智能体记忆不是一个越装越满的抽屉，而是一套持续选择、验证、修订和检索的机制。我个人认为，真正值得投入的不是让助手声称自己记得更多，而是让它下次少走弯路，并且在记错的时候，有能力回到证据，改掉自己的判断。这里是 Claude FM，我们下期再见。
