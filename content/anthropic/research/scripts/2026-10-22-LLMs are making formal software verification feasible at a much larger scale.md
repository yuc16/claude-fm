今天我们解读的文章，英文标题是 LLMs are making formal software verification feasible at a much larger scale，中文可以译为，大语言模型正在让更大规模的软件形式化验证成为现实。这篇文章发表于二〇二六年十月二十二日，今天是二〇二六年十月二十五日，是一项刚刚公布的研究。

欢迎收听 Claude FM。我想先请你回忆一下，上一次给一个底层库升级版本，你为什么相信它可以上线？可能因为单元测试全绿，可能因为连续跑了几天模糊测试，也可能因为它已经被很多公司用了很多年。但这些理由都不能直接回答一个问题：有没有某种输入，仍然能让它出错？

这篇文章讨论的，就是怎样把“目前没有发现问题”，往“在明确范围内，可以证明不存在某类问题”推进一步。Anthropic 与 Theorem 合作，让 Claude 为真实开源软件生成形式化证明。最值得关注的，不只是证明数量，而是他们尝试把现成测试、现有二进制和自动证明，连接成一条工程流水线。

先把最容易误读的地方说清楚。文章没有证明一百多个开源库从此完全没有漏洞，也没有证明任意部署环境都安全。它证明的是，在限定的机器模型、运行条件、输入大小和测试入口下，某些指定错误不会发生。我们今天要听懂的，既包括这个进展为什么重要，也包括这句话里的每一个限制为什么不能省。

背景其实很直观。软件防守过去很大程度依赖一种成本不对称：找漏洞很费人，所以测试、审计和及时修补，能让攻击成本保持在一定水平。但文章指出，大模型越来越擅长寻找漏洞，还能把看起来不严重的问题串成攻击链。于是，过去“已经测得够多了”的安全余量，可能正在缩水。

文章举出 Linux 内核，说明成熟并不等于没有漏洞。它部署广、测试多，仍然会不断暴露问题。这里真正值得工程师思考的，不是哪一个项目特别差，而是传统测试的逻辑边界：无论你跑过多少次，通常只能说明那些被执行过的情况没有暴露问题，不能自然推导出所有情况都正确。

你可以把测试想象成检查一座仓库。你打开一万个箱子，没发现危险品，这提供了很有价值的证据。但形式化验证想做的是另一件事：根据仓库的结构、箱子的来源和明确规则，推导出整个限定范围内都不可能出现某类危险。两者不是谁替代谁，而是在回答不同的问题。

形式化验证的基本方法，是把程序和运行环境变成数学对象，再证明程序满足某份规格。这里的规格，就是对“什么算正确”的精确定义。比如，读取一个数组时，访问位置必须落在合法范围里。又比如，压缩再解压之后，输出必须等于原始输入。没有规格，所谓正确就没有明确对象。

困难也恰好在这里。写出完整规格已经不容易，写证明更难。原文提到，开发 seL4 操作系统内核花了大约两个人年，而形式化验证花了二十个人年。人年说的是总工作量，不一定是同一个人连续干二十年。这个量级说明，过去这类保证往往只适合极其关键的系统。

而普通工程团队面对的是另一幅场景：代码很大，历史很长，依赖很多，文档还不一定跟得上。你让大家先写一套完整数学规格，再把多年积累的代码全部证明一遍，项目很可能还没开始就被成本挡住。文章的突破口，就是不先追求完整描述软件的所有功能，而是从已有测试提炼可证明的目标。

我们来看模糊测试，也就是 fuzzing。开发者提供一个入口，让测试引擎不断塞入半随机、经过变异的输入。如果程序崩溃，或者某个断言失败，就把对应输入留下来。它非常适合解析器、解码器、压缩库这类输入结构复杂、边界条件特别多的软件。

但模糊测试像不断试钥匙。它可以很聪明，根据覆盖情况调整方向，也能一天试很多很多次，可它终究是在尝试具体输入。输入越长，可能组合越多。有些问题不是再多跑几个小时就容易碰到，而是触发条件本身跟常用的搜索策略不合拍。

研究团队换了一个问法。既然开发者已经写好了测试入口，也已经规定出错时应该崩溃，那么能不能把“这个入口对于范围内的所有输入都不会崩溃”，直接变成一个数学命题？这样，已有测试就不只是采样工具，也成了规格的来源。

这里有一个特别重要的区别。它不是把以前跑过的一批测试结果包装成证明，而是把测试程序本身纳入证明对象。原来是给这个入口喂一个输入，看看会不会失败；现在是针对所有满足条件的输入，证明这个入口都不会触发规定的失败。两者的量词，从“这些”，变成了“所有”。

研究采用的输入范围，是小于六十四兆字节。你可能会问，为什么还要设上限？因为证明必须有清楚边界。现实计算机本来就有有限内存和资源，证明也不是对一个无限能力、无限输入的抽象程序随便许愿。边界不让结果失去价值，隐藏边界才会。

研究使用了谷歌 OSS-Fuzz 项目中的大量测试入口。这是一个持续为开源项目运行模糊测试的平台，里面已经积累了开发者认为值得检查的行为。团队还利用 AddressSanitizer，中文通常叫地址消毒器，简称 ASan。它会给程序加入检查，让某些非法内存访问转化为可观察的错误。

于是，“程序不崩溃”并不只是看进程有没有突然退出。它还可以覆盖这些插桩检查发现的内存问题，以及开发者写下的断言。但要记住，ASan 不是所有内存错误的万能探测器。因此，证明不会触发它的检查，不等于证明任何定义下的内存安全问题都不存在。

更有意思的是，团队不是只在源代码层面做证明，而是针对编译后的 RISC-V 指令。RISC-V 是一种处理器指令集。换句话说，他们面对的是程序真正被编译成的机器指令，再用这些指令和 Linux 进程的形式语义，建立数学上的执行模型。

为什么这值得注意？假设你证明了一段高级语言代码的某个性质，最后部署出去的却是编译产物，中间还隔着编译器和链接过程。在二进制层面证明，可以直接围绕那个产物讨论行为。不过，这不代表所有信任都消失了，而是信任重点转移到了指令和操作系统模型是否准确。

这里的形式语义，你可以理解为一份足够精确的机器说明书。一条指令怎样改变寄存器，怎样读写内存，某个系统交互允许返回什么结果，都要有定义。证明要成立，就需要在这本说明书允许的行为中，排除目标错误，而不是只模拟一条顺利执行的路径。

具体成果是，在几周时间里，Claude 修复发现的问题之后，为一百二十三个开源库的二百三十九个入口完成了证明。证明覆盖的是指定条件下的正常退出，不触发所覆盖的内存安全检查，也不发生断言失败。研究还考虑了模型允许的操作系统响应和内存布局，而不只是固定的一次运行。

这些证明采用 Rocq，一种形式化证明系统。总规模大约是一亿八千万行证明代码。典型证明约六十万行，而对应二进制的指令数量，中位数约一万八千条。听到这个比例，你就能理解为什么传统上很难靠专家手工铺开：一个并不夸张的程序，也可能需要非常庞大的论证。

但这里不要把证明代码行数当作准确率指标，也别把它理解成模型说了六十万行话，所以更可信。关键是，这些内容要交给独立的证明检查器验收。Claude 负责构造证明，检查器负责检查证明是否符合逻辑规则，并且确实推出目标命题。

这和让模型审查自己的回答，有本质区别。模型可以写错、猜错、走弯路，但错误证明不能仅凭语言流畅就过关。就像一个学生可以写很长的数学解答，最后仍然必须每一步成立。我们不需要相信学生永远不会犯错，需要相信验算机制能拒绝不成立的推导。

当然，验算机制也不是脱离现实的神谕。文章明确指出，开发者仍然需要信任三个方面：处理器和 Linux 进程的形式模型，最终被证明的准确命题，以及 Rocq 证明检查器本身。模型生成的一亿多行证明，原则上不需要逐行人工审阅，但这三个根基不能因此被忽略。

这里可以用地图来理解。你可以严格证明，在地图标出的道路上，所有路线都不会经过某片危险区域。但如果地图漏了一座桥，或者把道路方向标反，推导再严谨也不保证现实里的车一定安全。形式化验证消除的是特定模型中的不确定性，不会自动消除模型与现实之间的差距。

接下来，文章最有工程味道的一点，是证明失败也能产生价值。Claude 尝试建立证明时，会遇到无法继续的地方。失败不必然等于发现漏洞，也可能是证明策略不够好，或者缺少辅助结论。但如果障碍对应一条真实可执行的错误路径，它就变成了漏洞线索。

研究允许 Claude 在发现问题后修改代码，再根据修改后的程序重新生成规格，继续证明。这个过程像修桥时做承重推演：发现某根梁撑不住，不是只把报告标红，而是修改结构，再重新检查。最终证明针对的是修补后的那个版本，而不是自动替原来的版本背书。

文章报告，这些验证尝试发现了数百个问题，其中一些非常不符合普通模糊测试的搜索习惯。比如，一个解压实现中的计数器下溢，会进一步导致越界写入，但需要大约二十兆字节、具有罕见特定结构的输入。很多模糊测试偏向小输入，常见上限是一兆字节，这类条件就不容易碰上。

另一个图像解码器的越界读取，需要六十四兆字节输入，以及超过两吉字节的内存。还有问题依赖对同一文件的两个句柄，按照特定顺序调用。你看，这些并不只是“某个字节等于某个值”，还可能涉及大规模结构、资源状态和跨调用关系。

文章还提到，Claude 重新发现了 libexpat 中一个需要深度嵌套输入才能触发的已知漏洞。这里应该区分首次发现和重新发现，不能把所有案例都算成全新的安全成果。不过，它说明证明导向的分析，确实能走到普通测试较难覆盖的角落。

更有意思的是，Claude 在证明内存相关性质时，还注意到某个限制文件加载范围的功能并不总被执行。这是逻辑问题，不一定造成崩溃。它提醒我们，目标之外的发现也可能有价值，但这些顺带发现，不能反过来被说成目标之外的行为已经全部得到证明。

你可能会问，不崩溃这个目标，是不是太弱？对一个返回错误答案但很稳定的程序，确实不够。可文章指出，许多测试会把更高层的性质编码成断言。只要性质不成立，断言就失败。那么，证明断言永远不失败，就能得到比“不越界”更强的保证。

比如压缩库，可以检查先压缩再解压，结果是否等于原始输入。如果入口确实对范围内所有输入都执行这项检查，而证明排除了断言失败，那么得到的就是这项往返性质。注意，它依然不是说压缩率最优、速度最快，也不是覆盖了所有调用方式，而是精确证明那条被写进测试的关系。

同样思路还能用于重复操作结果不变，两个实现输出一致，或者运算满足某条代数规律。我个人认为，这对工程团队特别实用，因为很多人觉得自己不会写形式规格，但其实已经在属性测试里表达了不少规格。缺的可能不是从零发明规则，而是把规则写得更清楚，并接上合适的证明工具。

文章里还有一个很能说明证明深度的案例。为完成 cpp-httplib 的相关证明，Claude 必须排除标准库集合析构时递归过深导致栈溢出的可能。要做到这一点，就得证明底层红黑树的平衡机制确实让树高保持在对数级别，而不是退化成一条长链。

想象你在搬走一棵树，每拆掉一个节点，都要先处理它的子树。如果树像一根很长的竹竿，递归层数就可能很深；如果树保持平衡，高度增长会慢得多。这个例子说明，一个看似简单的安全目标，可能迫使证明穿透标准库，处理真正的算法性质，而且发生在机器码层面。

研究也没有把形式化验证限定为这一条路线。他们让 Claude 根据定义 zlib 文件格式的技术规范编写形式规格，再证明 Linux 内核中的对应实现满足规格。这次使用的是编译为 x86 的二进制，以及由 Claude 生成、经过大量测试的指令集形式语义。

这里既有进展，也有新的审查重点。进展是可以从格式标准走到实际二进制，讨论端到端的正确性。审查重点是，自动生成而且测试充分的机器语义，仍然需要认真核验；测试过模型，不等于模型已经获得不容置疑的正确性。文章也没有把这些可信基础从限制里删掉。

团队把类似方法用于另外大约六个常用库，发现了一些边界情形中的小问题，原文称这些问题不可利用，正在向上游提交。作者的判断很克制：这些久经测试的代码，实际上已经相当接近正确，而形式化方法有机会把剩下的细小缝隙找出来，并提供更完整的保证。

另一个实验，是让 Claude 用 Rust 开发支持 Python 较大子集的解释器，并使用面向 Rust 的验证工具 Verus，证明它符合一篇学术论文描述的 CPython 语义。随后又运行超过一百七十万个随机生成的 Python 程序，观测到百分之九十九点九五的行为一致。

这个数字不能听成“形式化证明只有百分之九十九点九五可靠”。证明面对的是指定语义，随机测试比较的是实际行为，二者是不同层次的证据。剩余差异在原文中被描述为已知的边界情况。对我们来说，重点是，即使有证明，继续做现实对照测试仍然很有必要。

文章还提到，对关键应用进行简单安全性质的验证尝试，发现了潜伏十多年的逻辑问题；验证一个广泛使用的 PDF 阅读器时，一周发现的安全问题数量，相当于通常一年报告的数量。这些结果支持的，是“尝试证明也能帮助找漏洞”，而不是所有此类软件都已经完成验证。

讲到这里，我们必须问钱的问题。既然能生成一亿多行证明，是不是以后直接让模型一直跑就行？原文明确说，某些证明可能消耗数亿个 token。token 可以理解为模型处理文本时使用的计量单位。如此大的消耗，意味着成本效率不是锦上添花，而是能不能推广的核心约束。

研究提供了两个改善方向。第一个是模型进步。团队从真实代码中构造了三十六个小型验证任务，在证明其中一半任务的比较中，Opus 五点五相对 Opus 五，所需 token 大约减少百分之四十。这个结论针对特定任务集，不能直接等同于所有大型项目成本都下降四成。

第二个方向是复用。证明并不是每次从最底层开始重写。你证明过一条关于内存操作的结论，或者某段初始化代码的行为，后续可以在满足条件时继续使用。它很像软件依赖，只不过被依赖的不只是函数实现，还有已经检查过的逻辑结论。

在共享证明工作区的实验中，自动执行任务的智能体，也就是 agent，可以参考彼此的证明。相比各自独立工作，所需 token 减少了百分之十七，还有一些原本单独失败的任务因此成功。研究观察到，运行时初始化和 ASan 相关代码，在不同程序中会带来大量共同的证明工作。

这意味着规模化并不必然等于成本线性增长。假设很多项目都依赖同一个基础组件，那么围绕它建立的证明资产，可能被反复利用。文章提到 Lean 数学库 Mathlib 的积累方式，就是新证明建立在已有证明之上。不过，软件场景里能否复用，仍然取决于版本、接口、前提和实际构建是否匹配。

我个人认为，这里的长期价值甚至不只是“模型比人便宜”。它更像把过去散落在专家脑子里的论证，变成可以检查、检索和组合的工程资产。但文章没有给出完整的商业成本表，所以现在还不能据此断言，普通团队已经能以固定低价验证任意大型系统。

那如果你是一个工程团队负责人，明天到底能做什么？我建议先别把目标设成证明整个服务绝对安全，而是挑一个边界清晰、风险明确的组件。比如处理外部输入的文件解析器，或者一个已经有良好属性测试的编解码模块。这是实践建议，不是原文报告过的统一落地流程。

第一件实际工作，是把你想防的错误写成一句足够具体的话。不要只说“这个库安全”，而要说清楚，哪个入口，在什么长度的输入上，不能发生哪种错误。如果关心业务正确性，就把对应关系写出来，比如序列化再反序列化是否保留数据，而不只检查程序是否退出。

接着检查测试入口有没有真的触达目标行为。假设解析器看到不认识的头部就立即返回，那么一个只喂错误头部的入口，即使容易证明，也可能没有覆盖复杂解析逻辑。同样，证明空操作永远不出错并不难，但这不等于证明你真正依赖的功能没有问题。

然后把环境假设放到台面上。文章主实验是单线程、静态链接、固定内存预算的 RISC-V 程序，使用 Linux 模型，链接 musl 标准库。而你的服务可能跑在 ARM 或 x86 上，使用 glibc、动态链接，还有多个线程。这些差别不是部署细节，而是决定证明能否直接适用的条件。

因此，一次负责任的试点，应该把被证明的源码版本、构建产物、编译条件、机器模型和定理陈述放在一起保存。我个人建议，把它当成一种需要版本管理的安全资产。否则过几个月只剩一句“这个模块以前证明过”，却不知道对应哪个二进制，工程价值会迅速缩水。

还有一个特别值得防的坑，是为了让证明通过，悄悄削弱规格。比如本来要证明所有合法输入都能正确处理，后来改成遇到复杂输入就提前返回错误。对于某些安全目标，这也许是合理修补；但对于功能要求，它可能是退化。检查器能验证命题成立，不能替产品决定这个命题是否值得。

所以在允许模型自动修复代码时，人的审查重点应该发生变化。不是去逐行读几十万行证明，而是认真看补丁有没有改变外部行为，有没有绕过断言，有没有缩小本来应该支持的输入范围。证明的机械正确性和修复的业务合理性，是两份不同的责任。

证明失败时也不要急着宣布发现漏洞。你可以要求系统尽量给出可复现输入、明确执行路径，或者说明缺少哪条辅助结论。一个无法完成的证明，可能暴露真实错误，也可能只说明当前方法还不够强。把失败原因分类，会比只追求通过率更有助于积累经验。

同时，不要因为某个入口证明通过，就关掉整个项目的模糊测试。原文说的是，在同样范围和模型内，那个入口已经没有对应崩溃可供继续寻找。现实里的其他架构、其他入口、更大的输入，以及没有被模型描述的行为，仍然需要测试。证明和测试应该分工，而不是争一个谁取代谁的位置。

尤其要注意调用者。一个库内部的特定测试入口安全，不代表业务代码可以任意传参数、任意复用对象，或者违反资源生命周期。文章明确指出，调用者误用库仍然可能导致调用者一侧的内存破坏。要补上这层保证，需要明确公开接口的使用条件，并让调用者遵守这些条件。

你可以把它理解为插座和电器的关系。证明某个插座在规定电压和接线方式下安全，不等于随便接什么线路都安全。软件里的这些接线条件，就是参数范围、对象状态、所有权和调用顺序。对工程师来说，把这些条件显式化，本身就可能改善接口设计和代码审查。

在团队选题上，我个人更看好从关键依赖开始，而不是只验证自己写得最顺手的小函数。因为基础库往往被很多系统共同使用，一份高质量证明可能沿着依赖关系产生放大价值。文章也提出类似方向，并提到合作方探索验证更大软件生态的路线，但那是路线图，不能当作已经完成的成果。

最后，还要把证明检查基础设施当成高价值组件来维护。这个方案并没有让信任归零，而是把信任集中到更小、更稳定的部分。相比人工检查海量应用代码，持续审查检查器、机器模型和命题，可能更可行。但“更可行”不等于可以不审查，更不等于模型生成的东西天然可靠。

原文已经宣布公开一部分证明和相关语义，供外部检查与复用，并说明不会公开可能暴露尚未修复漏洞的证明。合作方也提供帮助开发者开始验证的 Claude 技能。对想尝试的团队，我建议先看这些材料能否匹配你的目标环境，再决定投入，而不是只根据新闻里的规模数字立项。

把今天的内容收束起来，大模型带来的变化，不是让一句“相信我，这段代码没问题”更有说服力，而是让生成可由外部工具检查的数学证明，开始具有更大规模的工程可能。我个人认为，真正值得期待的未来，是每一份安全保证都能回答四个问题：证明了什么，针对哪个产物，在什么条件下，以及还有什么没有证明。
