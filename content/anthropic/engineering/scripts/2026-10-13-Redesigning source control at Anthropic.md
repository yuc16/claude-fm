今天我们要聊的文章，标题是 Redesigning source control at Anthropic，中文可以翻译成，在 Anthropic 重新设计源代码版本控制。这篇文章发表于二〇二六年十月十三日，并在十月十五日补充了相关先行项目的介绍。今天是二〇二六年十月十八日，我们聊的是一篇刚发表不久的工程实践。

欢迎收听 Claude FM。我想先请你想象一个场景。你的团队终于解决了写代码太慢的问题，智能体可以自己实现功能、优化程序、反复运行研究实验。但紧接着，大家开始排队等拉代码、等测试、等合并。程序员没闲着，机器也没闲着，可交付就是越来越堵。

这篇文章讨论的，就是这种看起来有点反直觉的局面。代码生产能力提升以后，原来被我们当成背景设施的版本控制，突然成了生产线最窄的地方。Anthropic 的做法不是继续给 Git 加机器，而是重新审视假设，做了一个叫 Scion 的内部版本控制系统。

先把尺度摆出来。文章说，二〇二六年五月，他们每天平均合入大约两千五百次代码变更。到了九月，这个数字超过三万。几个月时间，增长超过一个数量级。作者还判断，每消除一个瓶颈，原来被压住的代码生产需求就会释放，继续推高系统负载。

不过，别急着把这个故事理解成所有公司都该抛弃 Git。作者反复强调，他们的工作负载很特殊，内部使用 Claude 的强度也很特殊。这里的 Claude 是 Anthropic 的人工智能助手。这篇文章更值得听的地方，是当使用者从人变成大量自动化程序，基础设施应该怎样重新划分职责。

我们先看看他们究竟被什么卡住了。Anthropic 使用 monorepo，也就是把很多项目放在同一个大代码仓库里。这个仓库仅主分支的历史数据就接近一百吉字节，压缩过的工作副本也超过二十五吉字节。大仓库本身不稀奇，真正惊人的是读取频率。

他们每天仅用于 CI，也就是持续集成的代码检出，就有大约两千五百万次。还没算开发环境、智能体沙箱和研究任务。所谓检出，就是把某个版本的代码准备到任务能使用的地方。如果每次都天真地搬一份完整数据，文章估算每天会产生超过六百拍字节的 Git 流量。

这就像一家工厂，每个工位开工前都要求运来一整座仓库的物料，哪怕实际只用其中一盒螺丝。单个工位看，流程非常完整；工位变成几千万个，完整就变成浪费。这里要优化的，不只是传输快不快，而是任务究竟需不需要拿到这么多东西。

Git 为什么容易走到这一步？因为它本来就是一个分布式版本控制系统。理想情况下，每个克隆都是能够独立工作的仓库。你离线也能查历史、比较差异、定位某一行由谁修改，还可以切换版本。这些能力非常宝贵，也是 Git 成为行业标准的重要原因。

但 Anthropic 发现，自己实际使用 Git 的方式已经很集中式了。大家认可一个权威仓库，大量客户端是始终在线的任务和智能体。也就是说，他们为了获得几乎用不到的离线自治能力，不断支付复制数据和维护本地仓库的成本。这是需求和架构假设之间的错位。

当然，他们不是没试过常见优化。浅克隆可以少拿历史，稀疏检出可以少拿目录，还有延迟获取对象的机制。他们也用内部镜像，以及存放在对象存储里的仓库快照。高峰时，内部 Git 镜像达到数百个。这些办法确实争取到了时间。

问题是，主分支前进得太快，快照刷新完没多久，又落后了一大截。客户端拿到快照之后，还得追赶新增历史。同时，仓库只拿了一部分，查询差异和逐行归属这些依赖历史的操作，就需要更加小心地维护。省下来的传输，可能又变成维护复杂度。

于是，他们换了一个问题。不是怎样把完整仓库更快地复制到每台机器，而是，如果绝大多数客户端一直在线，为什么不能让服务端回答问题，让客户端只拿完成任务真正需要的数据？我个人认为，这个提问比后面任何单项优化都重要。

Scion 的第一个核心变化，就是客户端和服务端不再对称。Git 的客户端很强，理论上也能承担服务端角色。Scion 则把历史查询、逐行归属、创建提交、合并和变基等操作集中到服务端。客户端主要负责本地缓存、文件落盘、监听文件变化，以及提供好用的交互。

你可以把它理解成，从每个员工都保管全套档案，变成由档案中心提供专业查询服务。员工手边只放正在处理的材料。代价也很明确，档案中心得可靠，网络得可用。它不是白捡的性能，而是用更强的在线依赖，换取更低的本地成本。

更进一步，客户端使用的源代码查询能力，也都通过 API，也就是程序接口，向其他系统开放。一个任务如果只想知道两个提交的共同祖先，或者某一行最后由谁修改，就直接问服务端，不必先准备一个本地仓库，再启动 Git 执行命令。

这个改变对自动化很有价值。比如一个自动回退系统，要判断哪些提交受到了影响；一个二分排查系统，要沿历史寻找引入故障的变更。它们需要的是版本关系，不一定需要源文件。文章说，没有这种低成本的程序化查询，一些内部工具很难在他们的规模下实用。

这里可以停下来想想自己的流水线。一个检查任务克隆仓库，只为了列出修改过的文件；另一个任务又克隆一次，只为了确认提交关系。我们经常把完整工具链当成获取一个答案的前置条件。Scion 的启发，是把答案变成服务，而不是把整套数据库交给提问者。

第二个核心变化，是如何记录提交。在 Scion 里，基本工作单元叫 changeset，也就是变更集。它是预写日志中的一条记录，保存大多数你熟悉的提交信息。但和 Git 提交指向一棵目录树不同，它直接记录相对第一个父提交，哪些文件发生了变化。

文件内容另外放在对象存储里，经过压缩，用基于内容的地址引用。你可以把变更集想象成一张修改清单，上面写着哪些路径更新了，以及新内容去哪里取。这里记录的是增量，不是每次都为整个大仓库重新整理一遍全部状态。

为什么强调第一个父提交？因为合并提交可能有多个父提交，总得选一个作为描述变化的基准。文章说明，这带有设计取舍的性质。在他们采用主干开发的单仓库环境里，人们主要关心主线上的历史和逐行归属，所以这种表示方式符合实际需求。

增量表示背后的目标是，一次小修改的成本，应该主要取决于修改本身有多大，而不是仓库有多大。如果只改了一个配置文件，却触发对整个仓库的大量处理，仓库越大，每次微小操作就越贵。智能体可以高频提交，这种固定负担会迅速放大。

Scion 的提交、变基和合并都在服务端完成，所以也没有传统意义上提交以后再推送的步骤。文章说，接收变更集不需要接收 Git 那样的对象打包文件，也不需要为这条路径进行加锁或跨服务器协调。这里说的是这条数据写入路径，不等于整个系统完全没有协调。

他们尤其警惕另一种东西，叫引用，也就是指向提交的名字，比如分支和标签。名字会移动，多台服务器就需要对它当前指向哪里达成一致。Scion 仍然支持引用，但尽量不让创建和获取提交依赖它，把移动引用与生成变更集分开。

文章提到，更新引用是对 Spanner 中单行数据执行比较并交换。Spanner 是他们使用的数据库。你可以把这个操作理解成，只有当前位置仍然等于我预期的位置，才把它改到新位置。关键不是某个术语，而是把必须协调的可变状态压到很小。

不过，只记录修改清单，会马上遇到一个问题。假设我要查一个文件过去改过多少次，难道每次都从现在往前翻日志？要查某一行的作者，又怎么办？增量写入很便宜，不代表所有读取天然也便宜。这就引出 Scion 很重要的一层，派生数据。

派生数据，就是能够从原始变更集计算出来的辅助结构。例如文件路径历史、逐行归属，以及帮助查提交关系的跳表。跳表可以粗略理解成，给一条很长的历史道路修一些跨越多个路口的快速通道，避免查询时只能一步一步往前走。

这些结构通过同一套机制生成。某个变更集的派生结果，可以从父提交的相应结果递归计算出来。这样，新需求来了，可以增加一种索引；访问频繁的结果提前算，冷门结果等有人问再算。原始事实和查询加速结构，不必绑死成一种格式。

更重要的是，客户端看不到这些内部结构。服务端今天增加复制检测索引，明天优化按路径搜索的索引，不需要让所有客户端跟着升级。我个人认为，这也是服务化的重要收益，把内部表示的变化留在服务内部，而不是传播到每台开发机和每个任务里。

文章也很坦率地交代了技术来源。大规模单仓库并不是他们第一个研究的问题，谷歌的 Piper 和 Meta 的 Sapling 都提供了先例。尤其是 Sapling 的服务端 Mononoke，以及它采用的 Bonsai 数据模型，开创了 Scion 所使用的许多技术。

所以这里不是一个凭空发明、推翻前人的故事。更准确的理解是，新的工作负载让过去少数超大组织才需要的设计，提前进入了更多人的视野。Anthropic 把这些经验与自身智能体密集使用的环境结合，做出了一个高度定制的系统。

接下来是第三个核心变化，也是性能数字最亮眼的部分：别围绕传输完整仓库设计协议，而是围绕获取不可变对象设计协议。Scion 客户端从根目录树开始，检查本地缺哪些目录对象，递归请求，然后再请求缺失的文件内容对象。

这里的沟通方式，不是先详细告诉服务器我已经有什么，让服务器为我计算一份定制大礼包，而是客户端直接说，我要这个对象、那个对象。每个对象一旦存储就不再改变，任何持有它的缓存都可以回答，不必反复向上游确认是否过期。

可以把它类比成点菜。原来是你把冰箱里所有食材报给餐厅，请餐厅推算你还缺什么。现在是你自己看冰箱，直接下单缺少的东西。服务器少做个性化计算，缓存也更容易复用。尤其当大量任务使用相近版本时，大家要的对象会高度重合。

这种方式还天然支持中断后继续。没有一个必须一次传完的数吉字节打包响应，已经拿到的对象可以保留，缺什么再补什么。稀疏检出也不必另开一套复杂流程，不需要的目录就不请求。虚拟化检出则进一步做到，文件真正被访问时才把内容准备出来。

注意，这里有两个层次。稀疏检出是先圈定我要哪些目录；虚拟化检出是即使目录属于范围之内，也可以等到真正读文件时再拿内容。共同原则都是，不要因为未来可能需要，就现在把整个世界搬过来。对短命的自动化任务，这一点尤其重要。

他们在实际机器上又加了一层共享。客户端通过本地套接字，连接同一节点上的 scion-daemon，也就是节点级守护进程。多个任务使用同一个对象缓存，而不是各自在自己的临时环境里重复存储。守护进程还会从定期刷新的快照启动。

想象一台机器连续运行几十个测试任务，它们大部分代码完全一样。如果每个任务都重新拉一次，你是在为隔离付出重复传输的成本。共享不可变对象，则可以让不同任务复用底层数据，同时各自保留需要的工作目录。这里共享的是内容，不是随意共享可写状态。

节点守护进程再连接本地区域的 scion-cache 缓存服务器。缓存直接从内存流式发送对象，而且使用守护进程可以消费的磁盘格式，不必临时为客户端重新压缩或计算差量。区域缓存没有的对象，再向权威服务端请求，后者去数据库或云存储读取。

客户端、节点守护进程、区域缓存和权威服务之间，相关协议使用相同的 RPC，也就是远程过程调用接口。从接口角度看，各层有很强的可替换性。不过他们没有因此允许随意跨层访问，而是严格执行分层，目的是隔离故障影响。

为什么这很关键？假设区域缓存突然出问题，所有节点都绕过它，直接请求权威服务。平时被缓存挡住的洪水，会瞬间冲到最上游，把局部故障变成全局故障。接口可以通用，流量路径却必须受控。这是缓存架构里很容易被低估的工程约束。

文章给出的结果是，各层缓存命中率都超过百分之九十九。与之前的 Git 镜像基础设施相比，Scion 在处理器和内存需求上的占用缩小到约二百分之一。持续集成和研究任务检出代码，从分钟级变为秒级，速度提高了约两个数量级。

仅持续集成，就获得了百分之二十五的处理器容量收益。这里别把不同指标混为一谈。二百分之一说的是特定基础设施的处理器和内存占用，百分之二十五说的是持续集成容量收益，不能理解成公司所有计算成本都下降了同样比例。文章也没有提供供所有组织套用的通用基准。

讲完架构，我们再看人是怎么把它做出来的。七个人，五个月，除了 Scion，还做了叫 Antique 的代码评审工具、代码搜索、身份与访问管理，以及另外一批相关系统，并完成单仓库迁移。同时，日常代码合入量还在快速增长。

Claude 在这里既是压力来源，也是建设工具。文章提到，在内部获得 Claude Mythos Preview 和 Claude Tag 之后，需求与开发速度同时上升。它举了一个很具体的例子：团队曾手写 Git 到 Scion 的导入流水线原型，后来让早期内部模型重写。

作者说，没有进一步指示，模型生成的版本内存占用减少到原来的二十分之一，速度提高到四倍，并保留了导入顺序和数据结构里的隐含约束。这是团队报告的一次具体经历，不应该直接推导成任何代码交给模型重写，都能获得同样的结果。

更值得我们关注的是，工程师到底在负责什么。文章说，参与项目的工程师都认为 Claude 比自己更擅长写代码，但他们仍然需要理解系统之间的关系、明确设计权衡，并且经常对模型说不。实现某个局部功能，和守住整体系统边界，是两种不同能力。

一个例子是，系统想知道某次变更什么时候合入主分支。有些实现会暴力扫描提交日志。但正确答案应该向代码评审工具查询。扫描也许能在小样本上跑通，却违背了规模要求。模型完成了表面的任务，工程师必须指出，它选错了事实来源和成本模型。

另一个例子来自对抗式评审，也就是主动寻找问题的审查方式。这种方法很有用，但也可能过度防御。文章提到，有评审对内部服务提出过多假设性担忧，导致模型堆出过量校验和复杂性。工程师的价值，也包括判断哪些担忧值得解决，哪些只是让系统更难维护。

团队仍然审查每一项变更，但关注点转向变更意图，而不是逐行通读。我个人认为，普通团队不能把这句话理解成可以跳过代码细节。更合理的借鉴是，先确认目的、约束、复杂度和失败方式，再决定哪些部分需要深入检查，不能只看代码写得漂不漂亮。

在测试上，他们利用模型生成能力，为遇到的非简单基础设施交互和版本控制交互构建隔离模拟，还做了模糊测试和复杂的限流。文章也提到，模型发现过祖先关系查询没有利用某个索引的问题。这里的收益不只是多产代码，还包括把以前排不上日程的验证补起来。

安全方面，Scion 支持仓库级和目录级的细粒度权限，保护敏感代码。评审工具还可以表达更复杂的审批语义，比如区分只改注释和修改敏感逻辑。这个区别很重要，代码量增长以后，如果仍然对所有变更施加完全相同的人工检查，人的注意力会很快耗尽。

运维上，他们还给不同组件安排专注观察的 Claude，称为超级粉丝。这些助手能读取遥测数据和日志，持续盯着某个组件找异常。同时，传统告警仍然保留。作者认为，这些助手可以发现一些细微或新型问题，不只是检查指标有没有越过预设阈值。

我个人认为，这种做法值得试，但观察权限和操作权限应该分开考虑。发现异常、解释证据，与自动修改生产系统，并不是同一件事。原文介绍的是监测实践，没有给出一套可以直接照搬的自动处置规范，听众落地时需要自己补足这部分边界。

最后一个很有冲击力的问题，是合并队列还应该长什么样。过去，我们常希望测试通过的提交就是即将合入的提交，最好再锁住队列，保证主分支状态可控。可如果测试还在跑，已经有几百甚至几千个变更合入，这个等待与验证模型就越来越吃力。

文章说，他们没能有效复现行业常见的全局仓库锁方案，因此把更多投入放在合并后、部署前的自动测试。这意味着并发变更可能冲突，他们依靠 Claude 快速修复。我个人认为，这不是在主张取消验证，而是在把验证重新安排到符合吞吐量的位置。

但这也不是普通业务系统可以直接照搬的答案。修复快，不等于损失一定小。如果合并之后立刻影响资金、用户数据或者外部接口，那么隔离、回退和部署边界都需要单独设计。文章没有展开这些具体流程，我们不能替它补出一套万能安全保证。

那么，如果你所在团队每天只有几十次或几百次提交，明天能做什么？我个人建议，先不要讨论重写版本控制。先测一条真实流水线，从任务创建到真正开始业务计算，中间有多少时间花在准备仓库、下载历史、展开文件和执行仓库维护上。

然后给任务分类。有的只需要提交关系，有的只需要文件列表，有的需要少数目录，真正需要完整工作副本的是哪些？这一步很朴素，却能防止一个常见误判，把某类任务的特殊需求，变成所有任务共同承担的成本。先减少不必要的工作，再优化必要的工作。

接着可以挑一个查询型任务做实验。比如把获取变更文件列表，改成调用已有代码托管平台的接口，而不是完整克隆。这里要检查接口语义、权限和限流，确认它回答的确实是你想问的问题。不要只比较一次请求有多快，还要看整体稳定性和维护成本。

如果主要成本来自重复下载，可以评估节点共享缓存或区域缓存，但要格外注意缓存的内容是否不可变、不同租户能否互相看到不该看的数据，以及故障时会不会集体回源。Scion 的启发不是缓存越多越好，而是内容寻址、共享复用和故障隔离需要一起设计。

如果主要问题是大仓库，也可以继续改善 Git 的浅克隆、稀疏检出和按需获取，而不是立刻换系统。作者最后也明确建议，让 Git 服务端提供更完整的查询接口，改善协议以及各种局部获取能力之间的组合。客户端和服务端，不必永远采用完全对称的架构。

还有一件很实际的事，是为模型写清楚不可违反的约束。比如历史查询不能线性扫描主分支，创建一次小变更不能处理全仓数据，区域缓存故障不能击穿权威服务。这些约束最好能被测试和指标检查。我个人认为，智能体越擅长补实现，这份约束清单就越值得认真维护。

至于是否迁移到全新的版本控制，必须把周边系统一起算进去。Scion 与 Git 差异很大，迁移涉及评审、搜索和持续集成，不是换一个命令行工具那么简单。作者也明确说，它不是通用 Git 替代品，内部可投入的模型资源更不能代表普通企业的经济条件。

回到今天这篇文章，我个人认为，最有价值的不是两百倍或者五个月这些醒目的数字，而是他们不断追问，哪些成本来自真正的需求，哪些只是来自继承下来的假设。当代码生产速度改变，值得重审的不只是写代码的方法，也包括查询、传输、验证和协作的边界。

Scion 给出的答案，是让服务端承担更多计算，让客户端少拿数据，让共享内容尽量不可变，再由工程师守住系统约束。对大多数团队来说，不必立刻重造 Git，但可以从明天开始，检查自己的自动化任务，到底是在完成工作，还是在反复搬运一座根本用不完的仓库。
