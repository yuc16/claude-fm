## Shownotes

Anthropic 在九月十七日给 Claude Projects 做了一次彻底改版：它不再是一个装文件的文件夹，而是一个由 coordinator 指挥、多个 thread 并行执行的工作系统。你只需要说清目标，拆解、分工、并行、审查、汇总全部交给 Claude，而且它在你关掉电脑之后还在跑。

本期我们把这篇五分钟的产品文章拆成二十五分钟来讲透，重点回答一个问题：当 AI 不只是写代码，而是开始管理一堆 AI 写代码的工作时，我们工程师的位置应该放到哪里。

本期要点：
- Projects 的本质变化是从静态上下文容器变成动态编排系统，coordinator 负责拆解和调度，thread 负责执行
- 每个 thread 是一个独立的 Claude Code 云端会话，有自己的分支和仓库副本，多个 thread 改到同一块代码会以合并冲突的形式暴露
- 共享记忆让不同 thread 之间不再需要人工搬上下文，甚至能记住你的沟通偏好，但也带来记忆污染和漂移的风险
- 并行会更快触及用量上限，好在可以给 coordinator 和 worker 分别配置模型和投入程度来做成本分层
- 发布节奏：先 Pro 和 Max 的部分用户，再扩到全部 Claude Code 用户，Team 和 Enterprise 排在后面，现有 project 不受影响
- 真正的瓶颈会从「能不能做」变成「你能审查多少」，这道天花板值得每个团队提前想清楚

## Script

欢迎收听 Claude FM，我是你的主播。今天我们要解读一篇非常新鲜的文章，标题是 Projects redesigned: from folder to conversation，中文可以翻译成「Projects 重新设计：从文件夹到对话」，发表时间是二〇二六年九月十七日。今天是九月二十号，也就是说这篇文章只发表了三天，属于刚刚出炉的一手消息，不存在时效性的问题，我们现在讲它反而是最新鲜的时候。

这是 Anthropic 官方博客上的一篇产品更新，全文只有五分钟的阅读量，但信息密度非常高。我自己读第一遍的时候觉得它像一篇普通的发布公告，读第二遍的时候意识到它其实在讲一件挺大的事情。它讲的不是 Claude 变聪明了多少，而是我们使用 Claude Code 的方式要怎么变。这件事会直接影响你接下来几个月的日常开发节奏，所以值得我们用一整期节目把它彻底拆开。

先把结论摆到最前面。过去我们在 Claude Code 里做一件稍微复杂的事情，是谁在当项目经理？是我们自己。你开一个会话做前端，开一个会话做后端，再开一个会话写测试，然后你要自己记住哪个会话做到哪一步了，自己把上下文在几个会话之间搬来搬去，最后还要自己把结果拼起来，看看能不能合到一起。这篇文章要解决的问题就是这件事：Anthropic 把 project 这个容器重新设计了一遍，让它从一个装文件的文件夹，变成一个会自己协调工作的对话。你只要描述你想达成什么目标，剩下的拆解、分工、并行、审查、汇总，Claude 来管。你负责的是随时介入，随时调整方向。

如果你最近正在用 Claude Code 做多仓库、长周期的活，或者你在团队里负责推动 AI 编码工具的落地，那这期节目你应该会很有收获。我会先讲清楚它到底变了什么，然后拆开它的架构，讲 coordinator 和 thread 这套设计，再讲共享记忆和 library 这两个很关键但容易被忽略的部分，最后落到实践上，讲讲哪些场景值得马上试，哪些坑必须提前避开。

我们先回到背景。为什么会有这篇文章？我们回想一下过去一年多，用 AI 写代码的真实体验到底是什么样的。单次对话能解决的问题，其实早就解决了。写一个函数、修一个 bug、解释一段代码、帮你把一段报错看明白，这些事情都很顺，你几乎已经形成肌肉记忆了。但真实的工程任务，几乎从来不是单次对话能解决的。一次依赖大版本升级要改几十个文件，一次接口废弃要动三个仓库，一次性能优化要先测量、再改、再验证、再准备回滚方案。这类任务有几个共同特征：它比一次回复要长，它不止一个部分，而且这些部分之间还有依赖关系。

在这些任务上，我们现在的主流做法是什么？是把大任务切成小任务，一个一个丢给 AI，人类在中间做调度。你自己心里有一张甘特图，你知道 A 会话做完要把结果贴给 B 会话，你知道 C 会话的改动不能和 D 会话撞车。说得夸张一点，你变成了一个 AI 团队的项目经理，同时你还是这个团队里唯一的集成工程师。这件事的成本其实非常高，高在你自己的注意力被切碎了，高在每一次交接都要重新解释一遍上下文，也高在你一旦离开电脑去开会，整条流水线就停在那里，等你回来手动踢一脚。

文章里有一句话我印象特别深，它说：管理一次构建过程中的多个会话，过去需要你把工作拆开，在一次次交接之间来回周旋，再把结果缝回去。现在，在一个 Claude Code 的 project 里，你描述需要完成什么，Claude 来管理工作。这句话就是整篇文章的题眼。它要解决的不是 AI 能不能写代码，而是谁来协调这一堆 AI 写出来的代码。这是一个层次的转变，从单点能力转向工作流编排。我个人的判断是，这个转变的意义，可能比模型能力再提升一代还要大，因为它改变的是你一天的时间怎么被使用。

那么，从文件夹到对话，到底变了什么？我得先说说以前的 project 是什么样子。如果你用过 Claude 的 projects，你对它的印象大概是一个文件夹，或者更准确地说，是一个知识容器。你把项目说明文档、代码规范、参考资料丢进去，然后在这个 project 里开对话，对话就会自动带上这些背景信息。它的核心价值在于让 AI 记住背景，但工作怎么拆、几个对话怎么配合，还是你自己的事情。它本质上是一个静态的上下文包。

这次重新设计之后，project 变成了一个有目标、有执行体、有协调者的运行时。文章的原话是：project 里面有 threads，它们负责干活；还有一个 coordinator，它负责指挥。这个结构非常像一个小型的工程组织。你给一个目标，coordinator 把它拆成工作项，分给若干个 thread，每个 thread 独立去执行，coordinator 盯着进度、检查产出，最后把结果汇总给你。

文章用了一个我很喜欢的比喻，它说你可以像给一位幕僚长做简报那样，在 project 里给 Claude 交代任务。幕僚长这个角色很有意思，他不是替你干活的人，他是替你组织干活的人。你告诉他，我们这个季度要把结账流程的延迟降下来，他会去判断这需要几个人、分几条线、谁先谁后、什么时候回来找你确认。这就是 coordinator 的定位。你要练的能力，也从写指令变成了做简报。

你可能会问，这跟我以前开三个会话分别做三件事，有什么本质区别？我的理解是三点。第一，以前是我拆任务，现在是 Claude 拆任务，而且它拆完会给你看它建议先做什么。文章里说，当你启动一个 project，选好目标和仓库或者上下文之后，Claude 会先建议它马上可以接手的工作。这个动作很关键，它把冷启动这件事也接管了，你不用自己在那里想第一步该干嘛。

第二，以前每个会话是孤立的，现在它们共享同一个项目上下文和同一份记忆。这个我们后面会重点讲，我认为它是这次改版里最有想象力的部分。

第三，以前协调成本落在你身上，现在协调成本落在 coordinator 身上，而你可以只在关键节点介入。文章说，你既可以在项目主聊天里监控和引导整体进度，也可以钻进某一个具体的 thread 里去看细节、去调整方向。这个两个粒度的设计我觉得非常实用，因为大部分时候你只想看大盘，但偶尔你就是想盯住某一个具体的改动，这两件事不应该被迫用同一个界面来做。

接下来我们把架构拆细一点，因为这篇文章虽然短，技术细节给得挺扎实。先看一个 thread 到底是什么。文章说得很明确：每一个 thread，本质上就是一个 Claude Code 的云端会话，它在自己的分支上、在自己的仓库副本上工作。这句话里有三个信息，我们一个一个说。第一，它是云端会话，不是你本地的进程，所以你把电脑盖上它还在跑。这一点文章在开头就强调了，说你可以随时从手机上调整方向，离开电脑之后它继续工作。第二，它有自己的分支，也就是说每个 thread 的改动是隔离的，不会互相覆盖。第三，它有自己的仓库副本，这意味着它可以在不影响别人的前提下随便改、随便跑测试。

这就带来一个很自然的疑问：如果两个 thread 改了同一块代码怎么办？文章的回答非常坦诚，甚至有点可爱。它说，coordinator 会让工作保持有序，但是如果真的有多个 thread 动到了同一份代码，重叠的部分会被当作合并冲突来解决，就像任何一个普通的 PR 一样。这里说的 PR，就是 pull request，合并请求。这句话我认为是整篇文章里最诚实的一句。它没有说我们有一个魔法可以自动解决冲突，它说的是：并行就是并行，冲突就是冲突，我们用工程界已经成熟的机制来处理它。我个人非常欣赏这种诚实，因为它直接告诉你，并行不是免费的，它会给你带来和人类团队并行开发一模一样的后果。你以前怎么管人类的并行开发，以后就要怎么管 AI 的并行开发。

还有一个细节值得注意：thread 还可以继续往下拆。文章说，每个 thread 在需要的时候，可以用 subagents、循环和 workflow 把分配给它的工作再切成更小的块，这样大的任务能更快完成。所以这里其实是一个多层的委派结构：coordinator 分给 thread，thread 再分给 subagent。这个设计有点像公司的组织架构，一个项目负责人下面带几个小组长，小组长下面再带人。为什么要这样设计？因为一个会话的上下文窗口是有限的，把大任务切成小任务，可以让每个执行单元都待在自己最舒服的上下文长度里工作，不用担心信息被挤掉。这个思路其实和我们人类做软件工程是一模一样的，你为什么要把一个巨大的模块拆成几个小模块，因为一个脑子装不下那么多东西。

我再举两个文章里的例子，这样你能具体感受到它在解决什么问题。第一个例子是性能优化。假设你要降低应用的结账流程延迟，具体指标是 p 七五延迟，也就是第七十五百分位的延迟。你把这个目标配到 project 里，然后让 Claude 去做三件事：给每个接口做性能剖析、测试各种优化方案、并行地在不同的 thread 里开 PR。注意这里的顺序感和并行感，剖析是要先做的，测试是可以并行的，开 PR 也是可以并行的。你自己做这件事的时候，可能是先剖析，然后一个一个方案去试，一天试一个，一个星期就过去了。而在这里，多个优化方案可以同时被验证，你第二天早上回来的时候，可能已经有三份带数据的对比摆在面前。

第二个例子更复杂一点，也更接近真实的大工程。你把你公司的 API 仓库、Web 仓库、移动端仓库都连上，然后设定一个目标：废弃掉第一版的旧接口。Claude 会怎么做？它为每个仓库创建一个 thread，让这些 thread 分头去迁移调用方、跑测试、开 PR，最后告诉你哪个 PR 需要先合并。这个例子里最值钱的是最后一句，它告诉你哪个需要先合并。因为跨仓库的改动是有顺序的，API 改了 Web 必须跟着改，Web 改完了移动端才能发版。这个依赖顺序，过去是记在某个资深工程师脑子里的，现在 Claude 会把它算出来并主动告诉你。你想想这意味着什么，意味着团队里那个最懂全局的人的脑子里的一部分东西，被外化出来了。

你可能会问，这种并行到底能省多少时间？我觉得要分两种情况看。如果你的任务是三个真正独立的模块，那并行几乎是线性的收益，三个 thread 就是三倍速。但如果你的任务本质上是一条链，每一步都严格依赖上一步，那并行帮不了你太多，coordinator 的价值主要在于它不会忘记下一步，不会因为你去开了一个两小时的会就卡在那里。这也是我想提醒的一点：这套东西不是万能加速器，它加速的是可以并行的那部分工作，以及不需要你亲自盯着才能推进的那部分工作。后者的价值其实更大，因为它把等待时间变成了可以被利用的时间。

接下来讲我觉得这篇文章里最有想象力的一部分：共享记忆。文章说，随着时间推移，Claude 会学到更多关于这个项目的细节，并且把这些细节应用到它的工作里。每一个 thread 现在都会向一份共享的记忆里写东西，也会从这份共享的记忆里读东西，这就减少了复杂 prompt engineering 的必要。这句话值得掰开讲。什么叫减少 prompt engineering？就是说你不需要每次开新会话都写一大段背景说明，因为背景已经在记忆里了，而且是所有 thread 共享的同一个背景。

文章给了几个非常具体的例子，我很喜欢这几个例子，因为它们特别有工程现场的味道。第一个，Claude 能记住发布日期被改到了周五。第二个，它能记住当初为什么要砍掉导出功能。第三个，它能记住在动计费服务之前要先跟谁确认。你看这三个例子其实是有层次的：第一个是事实，第二个是决策的原因，第三个是流程和人际约束。尤其是第三个，这通常是最难传递的团队知识，因为它既不在代码里，也不在文档里，它只在老员工的脑子里，而且往往是踩过坑之后才形成的。

然后是工作风格。文章说 Claude 也会记住你的工作和沟通风格。你可以要求它调整多久向你汇报一次、多久开一个新的 thread、每次更新写得多详细。这一条我觉得对个人体验的影响非常大，因为不同人对被打扰的容忍度完全不同。有的人希望每完成一个小步骤就被告知一次，有的人只想知道最后结果。以前你要在每一个新会话里重复交代这些偏好，现在它可以被记住、被复用。这听起来是小事，但你一天开十个会话，这就是一天的十次重复。

我用一个类比来说明共享记忆的价值。它就像是给你的项目配了一位一直在场的资深同事，这位同事读过所有的会议纪要，知道所有的历史决策，而且他会在你需要的时候，主动把这些信息递给你。更妙的是，这份记忆是自动生长的，每开一个新 thread，都是对新知识的一次补充。这个类比的反面也很清楚，如果这位资深同事记错了某件事，而且所有人都相信他，那错误就会跟着扩散。

所以作为工程从业者，我们要对记忆保持一点警惕。下面这几点是我个人的看法，不是文章里的内容。第一是记忆污染。如果某一次对话里产生了一个错误的结论，比如说这个函数已经废弃了，而这个结论被写进了共享记忆，那它可能会影响后续所有从这个记忆里读信息的 thread。这是一个典型的错误放大机制，一次小错，被并行地复制了十次。第二是记忆漂移，随着时间的推移，早期的记忆可能会过时，但是没人去清理它，它就一直挂在那里，越来越像一条没人敢删的祖传配置。第三是团队场景下的边界问题，共享记忆里可能包含敏感信息，比如计费服务的处理流程，这在多人共享一个 project 的时候，需要更谨慎的权限设计。所以我的建议是，等你真正开始重度使用的时候，要像维护文档一样定期回看和清理这些记忆，把它当成一个有生命周期的资产，而不是一劳永逸的设置。

再讲一个很容易被忽略的部分：library，也就是库。文章说，除了记忆之外，project 现在还包含一个 library，它会收集你添加的文件，以及 Claude 产出的 artifacts，也就是产物。这样做的好处是更容易找到相关的材料，也更容易让新的工作建立在过去的基础上。

这个功能听起来平淡，但我认为它是长期项目的关键。你想，一个长跑项目里，最容易丢失的东西是什么？不是代码，代码在仓库里跑不掉。是那些中间产物：一次性能剖析的报告，一次架构讨论的结论，一份迁移进度的清单。这些东西过去散落在无数个对话历史里，你几乎不可能再找回来，只能凭记忆重新问一遍。有了 library，它们被集中在一个地方，可以被后续的工作直接引用。我特别喜欢文章里那句让新的工作建立在过去的基础上，它本质上是在做一次性的知识沉淀，把一次性的对话变成可复用的资产。这跟我们做工程时讲究的可复用性是同一个道理。

讲到这里我们停一下，把已经讲的东西串一遍，因为这篇文章的结构其实是一条完整的链。project 提供一个目标和环境，coordinator 负责拆解和调度，thread 负责执行，subagent 负责进一步细分，共享记忆负责信息的纵向积累，library 负责产物的横向沉淀，而你在最上面负责方向和审查。这是一个相当完整的编排体系。它不是简单地把模型能力往上堆，而是围绕长任务这个场景重新组织了工作方式。文章里有一句话概括得很好：projects 是为长时间运行的工作或者 agentic workflow 也就是智能体工作流设计的，也就是那些比一次回复更长、而且不止一个部分的工作。

接下来讲三件非常实际的事情：用量、配置，还有发布节奏。先说用量，这是你一定会撞上的问题。文章说得很直接：project 可以同时跑好几个 thread，而每一个 thread 都是一个完整的 Claude Code 会话，所以 project 会更快触及用量上限。这句话翻译过来就是：能力越强，消耗越快。并行是要花 token 的，而且不是线性地花，因为每个 thread 都带着自己完整的一套上下文。

文章给的解法是，你可以查看针对 project 的用量，并且可以分别为 coordinator 聊天和 worker thread 选择模型和 effort level，也就是投入程度。这个设计很重要，它意味着你可以做一个成本分层：让 coordinator 用更强的模型来做拆解和审查，因为它的调用次数少但每次都很关键；让那些相对机械的 thread 用更经济的选择，因为它们的工作量大但难度低。这是一个非常务实的成本控制手段。我个人建议你一开始就把这个分层规划好，而不是等到额度用完了才想起来。

再说配置。文章提到，你启动 project 的时候要选一个目标和仓库或者上下文，然后可以配置这个 project 的云端环境、连接器、插件、指令和模型。这里我特别想强调云端环境这几个字，因为它决定了 thread 能不能真的跑起来。一个 thread 要在云端跑测试、开 PR，那它必须有一个能装依赖、能跑命令、能访问你需要的东西的环境。这件事在真实项目里往往比模型能力更麻烦，因为你的项目可能有私有的依赖、特殊的构建步骤、需要内部镜像的包管理。所以我的建议是，如果你们团队要试这套东西，第一步不是急着接一个大目标，而是先把云端环境这件事搞通，让一个最简单的 thread 能成功跑完一条从改代码到开 PR 的完整链路。这条链路打通了，后面所有的事情才有意义；打不通，再好的编排能力也落不了地。

然后是发布节奏，这块信息我们要说得准确一点。文章说，从九月十七号开始，更新后的 projects 以 beta 的形式提供给一部分 Claude Pro 和 Max 订阅者，条件是这些用户要在 Claude Code 里使用云端会话，并且在网页版和桌面端上没有任何现有的 project。接下来一周，他们会把权限扩大到这两个套餐下更多的 Claude Code 用户。再之后是全量的 Claude 套餐，以及 Team 和 Enterprise 套餐。如果你用的是 Pro 或者 Max，但目前还没有权限，可以加入 waitlist，也就是等候名单。另外，Pro 和 Max 上已有的 project 会照常工作，不会被打断进行中工作。Anthropic 会随着这个功能扩展到聊天和 Cowork，再逐步升级它们。

最后是一个预告，也可能会是很多人最关心的一条。文章说 thread 目前跑在云端，而在你的机器上运行、和你的本地工具和代码在一起、并且在你自己的网络里，这件事很快就要来了。这个方向我特别关注，因为对不少团队来说，这是一个绕不开的前提条件：只有代码不出内网，很多项目才谈得上真正落地。当然，文章只说了很快，没有给具体时间，我们也不要过度解读。但方向是清楚的，云端负责长任务和并行，本地负责合规和深入集成，这两条路最终会汇到一起。

好，讲完了文章的内容，我们进入我觉得最有价值的部分：这对你的实际工作意味着什么，以及你该怎么上手。我准备了八件事，我们一件一件说。

第一件事，先判断你手上的工作里，哪些属于长任务。文章给了两个标准：比一次回复长，而且不止一个部分。按这个标准去筛，你会发现很多任务其实不符合。比如帮我写一个正则，这是短任务，用普通对话就好，没必要上 project，上了反而是浪费。但如果任务是，把我们的日志系统从旧方案迁移到新方案，那它完全符合标准：它要改配置、要改代码、要改文档、要做灰度、要准备回滚方案，而且这些部分之间还有先后关系。我的建议是，你先从手上正在做的事里挑一两个候选，用这两个标准过一遍，不要一上来就把所有工作都往 project 里搬。原因很简单，project 的启动和配置是有成本的，你要选目标、连仓库、配环境、写约束，这些成本在长任务里可以摊薄，在短任务里就是纯粹的浪费。

第二件事，学会把目标写清楚，而不是写成一串指令。这一点我要多说几句，因为它决定了整套系统的效果上限。你给的是一个目标，不是一串步骤。这两者的区别是：指令是你要怎么做，目标是你要达成什么。比如，在三个仓库里把第一版接口的调用方全部迁移到第二版，这是一个目标，它说清楚了终局状态，但没有规定路径。而你先改 A 文件，再改 B 文件，然后跑这个命令，这是一串指令，它是你替 coordinator 做了它的工作。既然你请了一位幕僚长，你就应该给他目标和约束，让他去设计路径。那约束要写什么？我建议至少写清楚三件事。第一，哪些范围是允许动的，哪些是不能碰的，比如不要改数据库 schema，不要动权限模块。第二，验收标准是什么，比如测试必须全绿、构建必须通过、性能不能退化。第三，什么情况下必须先来问你，比如涉及线上配置变更、涉及数据迁移、涉及对外接口的破坏性修改。这三件事写清楚了，你后面会省掉大量来回确认的时间，而且 coordinator 拆任务的时候也会有明确的边界感。

第三件事，关于并行的使用策略，一定要正视合并冲突这件事。文章里那句多个 thread 改同一块代码会变成合并冲突的细节，值得你认真对待。这意味着并行是有成本的，而这个成本最终会在你这里变现。所以一个很实用的原则是：尽量按工作边界来切分并行，而不是按任务类型来切分。什么叫按工作边界切？就是让每个 thread 主要待在自己的一亩三分地里，比如一个 thread 负责 API 仓库，一个负责 Web 仓库，一个负责移动端。这样它们之间的交集天然就小，冲突自然就少。反过来，如果你让三个 thread 同时去优化同一个模块的性能，那它们大概率会踩到彼此的代码，最后你要花更多时间去处理冲突，可能比串行做还慢。文章里那个性能优化的例子其实是很聪明的，因为它让并行发生在不同的优化方案之间，如果这些方案改动的是不同的代码路径，冲突就很小。但你如果理解成三个 thread 都去改同一个热点函数，那就等着解决冲突吧。这个区别，我觉得是这套系统上手时最容易踩的一个坑。

第四件事，认真对待共享记忆，把它当成一个需要维护的东西，而不是一个自动生效的开关。我前面说过记忆污染的风险，这里给几条具体的操作建议。一是关键结论要在主聊天里确认一次，不要让它只是某个 thread 里的一句顺口说法，因为一句顺口说法被记下来，第二天可能就被另一个 thread 当成事实了。二是定期回看记忆里有什么，尤其是那些涉及流程和权限的条目，因为它们最容易被过时的信息污染，也最容易被误导后人。三是在团队场景下想清楚谁能往记忆里写东西，因为这本质上是在改项目的事实来源，这个权限不应该所有人都默认拥有。还有一个更微妙的点：文章说 Claude 也会记住你的沟通风格，这是一把双刃剑。好处是它越来越合你的脾气，坏处是如果你某天突然想要更详细的过程输出，而它已经习惯了只给你一句话总结，你就得显式地去改这个偏好。所以风格偏好最好在项目开始时就有意识地设定一次，而不是任由它在早期几次对话里被随机固化下来，因为一旦固化，改起来比设起来麻烦。

第五件事，成本和用量的规划，要有意识地做，而不是被动地被限制。我前面提到要让 coordinator 和 worker 用不同的模型和投入程度，这里再补充两个策略。一个是控制并发的数量，不是所有任务都需要开五个 thread，有时候两个刚刚好。并行的收益是递减的，开到五个之后的协调成本可能超过你节省的时间。另一个是控制碎片化的程度，thread 越多，协调开销越大，不只是钱的开销，还有你自己审查的开销。这里我要说一个可能有点反直觉的观察：这套系统把你的瓶颈从能不能做，变成了你能审查多少。并行度提高之后，所有的产出最终都要经过你的眼睛，所以你真实的吞吐量上限，其实是你每天能认真 review 多少个变更。这是一个很值得反复提醒自己的事实，因为很多团队一开始会兴奋地提高并行度，然后发现自己被淹没在待审查的变更里，最后为了跟上进度，只好放松审查标准，而这一步一旦迈出去，整套系统的价值就开始下降了。

第六件事，也是最重要的一件：不要放弃审查这个环节。文章里说 coordinator 会 review 每个 thread 的输出，也会组装最终结果，但这不等于你可以不看。我个人的观点是，至少在早期，每一个 PR 你都要按对待一个陌生同事提交的代码那样去审。原因有两个。一是这套系统会产生很多你意料之外的改动，尤其是在跨仓库迁移的时候，它可能会在一些边缘调用点上做出你从来没想过的处理方式，而这些边缘调用点恰恰是最容易出线上问题的地方。二是审查的过程本身就是你校准系统行为的过程，你只有看了产出，才知道该往共享记忆里补什么规则、该往指令里加什么约束。如果你把审查完全交出去，那这套系统会以你察觉不到的速度漂移，等你发现的时候，可能已经在几个方向上偏离了你原本的意图。

第七件事，团队视角。文章提到 Team 和 Enterprise 套餐会在这波之后跟上，也提到 connector 和 plugin 这类配置。对团队来说，真正需要提前想清楚的往往不是工具怎么用，而是治理问题：谁有权开 project，谁有权连仓库，哪些仓库根本不允许连，共享记忆里允许出现什么级别的信息，以及最关键的，谁对最终合并进主干这件事负责。这篇文章描述的是一个 AI 团队，但责任是不能被委派的，代码也不会因为是谁写的而改变它的质量要求。所以我建议团队在试用阶段就定几条简单的规则，比如所有 project 产出的 PR 必须有人类 reviewer，比如涉及支付和权限的模块不允许自动合并，比如跨仓库的迁移必须有明确的合入顺序记录。规则不用多，但要有，而且要写下来，因为口头约定在并行的工作流里特别容易失效。

第八件事，给你一条渐进的上手路径。如果你现在就有权限，我建议第一步是拿一个自己非常熟悉的仓库，做一个小而完整的目标，比如把某个测试覆盖率不到一半的模块补到八成，并且让持续集成全绿。这个目标的好处是它有明确的验收标准、天然可以并行、而且风险很低，即使出问题你也能一眼看出来。第二步，挑一个跨两个仓库的中等任务，感受一下多 thread 协作和依赖顺序的通知机制，重点体会它在告诉你哪个先合并的时候，判断是不是符合你的预期。第三步，才去考虑那种真正跨三个仓库、涉及线上变更的大迁移，并且在那个时候，把前面说的约束、审查规则、成本分层都提前准备好。这三步走下来，你会对这套系统能做什么、不能做什么，有一个非常具体的判断，而不是停在文章描述的想象里。

最后我想讲讲我对中国工程师群体的一点现实提醒。这套东西目前的门槛不只是模型能力，还有几个很务实的前提：你需要能用上 Claude Code 的云端会话，你需要有一个能跑起来你项目的云端环境，而且像我前面说的，跨地域访问和代码出网的合规问题，是必须提前解决的，不能等到项目做到一半才发现走不通。文章里说本地运行很快就要来了，对很多人来说，这才是真正的解锁时刻，因为那意味着你的代码可以待在本地，而编排仍然可以在云端或者混合模式里发生。在这个时间点之前，我的建议是先把怎么用 project 的思路练起来，比如怎么把一个模糊需求写成目标和约束，怎么判断一个任务适不适合并行，怎么给自己的审查能力设一个上限。这个思路本身不依赖任何工具，你今天就可以在自己手动开多个会话的时候用起来。

好，我们来总结一下。这篇文章讲的是 Claude Projects 的一次重新设计，核心变化是从一个静态的文件夹，变成一个以目标为起点、由 coordinator 和 thread 组成的动态工作系统。你给目标，它负责界定范围、委派工作、协调并行、审查产出、组装结果；每个 thread 是一个完整的云端会话，在自己的分支和仓库副本上工作；共享记忆让每个 thread 都能读到项目积累下来的知识，也把你的沟通偏好记下来；library 负责沉淀文件和产物。代价是用量消耗更快，而且并行的冲突会真实地以合并冲突的形式回到你面前。

我个人对这次改版的评价是：它是一个方向上的信号，而不是一次功能的堆叠。过去一年我们讨论 AI 编程，话题大多是模型能写多好的代码。而这次改版把话题推到了下一层：当模型可以写出足够好的代码之后，瓶颈就变成了谁来管理和协调这些工作。Anthropic 给出的答案是，把协调本身也交给模型，人的位置往上移一层，去定目标、定约束、做审查。这个方向对不对，我觉得还需要时间来验证，但有一件事是可以确定的：你从今天开始就可以练习的，是把自己的工作写成目标加约束的形式，并且认真对待我能审查多少这个真实的天花板。
