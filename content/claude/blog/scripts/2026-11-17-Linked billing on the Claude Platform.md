## Shownotes

Anthropic 在 Claude 平台上推出关联计费 beta，第三方平台可以让客户把 Claude 用量直接记到自己组织的账上，全程不交换 API key。这期节目我们把这件事拆开讲：它到底解决了什么老问题，安全边界画在哪里，平台方和采购方分别该怎么用。

本期要点：
- API key 共享的三个老痛点：泄露面、无法细粒度限额、撤销即全断
- 关联计费的核心机制：授权一次、账单直达客户组织、密钥不出门
- 一个必须注意的取舍：请求跑在平台组织里，客户侧的 IP 白名单、加密密钥、数据保留策略不生效
- 平台侧收益：免建计量与开票、按客户看用量、可按请求选择谁付费
- 近二十家平台首批支持，覆盖项目管理、部署、数据库、费用管理、终端、安全自动化
- 实操建议：月度限额不是熔断器，agent 场景还要配单任务硬约束

## Script

欢迎收听 Claude FM。今天这期节目，我们聊一篇刚刚出炉的文章，标题是 Linked billing on the Claude Platform，中文我把它翻成“Claude 平台上的关联计费”。文章发表于二〇二六年十一月十七日，距离今天十一月二十二日只有五天，可以说是热气腾腾。目前这个能力还处在 beta 阶段，也就是公开测试阶段，功能已经可用，但接口和细节还可能调整。

为什么我觉得它值得你在通勤路上听完整整二十五分钟？因为它讨论的不是模型能力，不是又一个跑分榜单，而是一个非常土、非常工程、但又极其要命的问题：第三方平台想帮客户调用 Claude，账单到底怎么走，密钥到底要不要交出去。这个问题听起来像财务问题，实际上是安全问题，是采购流程问题，也是每一个做 SaaS 的团队都躲不开的基础设施问题。如果你正在做一个 agent 平台，也就是那种能自主调用工具完成任务的智能体平台，或者你所在的公司正在同时用五六个 AI 工具，这一期大概率能帮你省下一些踩坑的时间。

我们先把这个问题的来龙去脉讲清楚。

假设你是一家做 coding agent 的公司，产品是一个能自动读代码、改代码、跑测试、提交变更的智能体，底层模型用的是 Claude。你的客户是各种规模的企业，他们自己也在用 Claude，甚至已经和 Anthropic 签了年度承诺消费额度。现在客户跑来跟你说，我想用你们的产品，但我不想为模型单独再走一遍采购，我能不能直接消耗我自己在 Anthropic 那边的额度？

在关联计费出现之前，这件事的标准做法叫 BYOK，bring your own key，自带密钥。客户在 Anthropic 控制台里创建一个 API key，也就是接口密钥，本质上就是一串密码，然后把这串 key 复制粘贴到你平台的后台设置里。你的平台拿着这串 key 去调 Claude，Anthropic 把账记到客户头上。流程能跑通，但问题一大堆。

第一个问题是泄露面。API key 一旦离开客户的组织，就多了一个需要被保管的秘密。你的平台得把它存进数据库，得加密，得定期轮换，还得防止它从日志里、从代码仓库的提交历史里、从某个客服工单的截图里漏出去。我见过太多团队，密钥就明文躺在配置文件里，或者在调试日志里被打出来，一存就是两年。你说这是谁的错？其实是流程设计的错，因为只要密钥需要在两个组织之间传递，泄露就只是时间问题。

第二个问题是控制粒度。客户把 key 交出去之后，基本就瞎了。他不知道这串 key 到底被调用了多少次、花了多少钱、用了哪些模型，也没法给某一个平台单独设一个额度上限。他想管，只能靠平台自觉。

第三个问题是撤销成本。客户一旦怀疑某个平台有问题，想撤销，只能把 key 整个删掉。删完之后，所有用这串 key 的地方一起断掉，可能连带把其他正常业务也停了。所以现实中很多客户干脆就不撤，宁可留着风险。

这是一个在 SaaS 世界里存在了十几年的老问题。你想想 OAuth 出现之前，第三方应用要访问你的账号，怎么办？你得把用户名密码直接给它。OAuth 出现之后，你跳到一个授权页面，点一下同意，第三方拿到的是一个有范围、有有效期、随时可以撤销的令牌，密码本身从来不出门。关联计费想做的，就是 API 计费领域的 OAuth 化。这个类比你记住，后面所有的设计细节都能对上。

还得说说二〇二六年这个时间点的行业状态。过去两年，agent 类工具的调用量在指数级膨胀。以前一个 SaaS 接模型，可能就是一个聊天框，一天几千次调用。现在一个 coding agent，一个任务跑下来可能就是几十万 token，一个工作流自动化平台，一个客户可能同时跑上百条流水线。token 是计费单位，你可以粗略理解成模型处理的文本量。调用量上来了，成本就从“可以忽略”变成“财务部门要开会讨论”的级别。企业一边特别想用这些 agent 工具，一边又怕失控，怕某个月账单突然翻十倍，怕 IT 部门根本不知道公司里有多少人在偷偷接 AI 工具。这就是关联计费诞生的土壤。

理解了背景，我们再来看 Anthropic 给出的方案。

核心机制其实很简单：客户不再把 API key 交给平台，而是把自己的 Claude 平台组织，也就是 organization，关联到平台上。关联之后，平台发出去的请求会带上这个关联关系的标识，Anthropic 直接把用量记到客户的组织账上。整个过程里，API key 一次都没有离开过客户自己的组织。

我们把关联的动作拆开走一遍，你就明白它有多轻。客户在平台的产品界面里点“关联 Claude”，页面跳转到 Anthropic 托管的审批页，客户确认这个平台要访问什么、准备给它设多少月度上限，然后点同意。跳回平台，关联建立。平台这边的代码改动其实很小：以前是从数据库里读客户的 key，拼到请求头里；现在换成读一个关联标识，拼进去。就这么点差别，但背后的安全模型完全变了。平台不再持有任何客户的秘密，它持有的只是一个“这个客户授权过我”的凭证，而且这个凭证随时可能被客户作废。

你可能会问，这个关联动作是谁来批准的？文章写得很清楚，需要客户组织里拥有所有者、管理员或者账单角色的人，在 Anthropic 托管的审批页面点确认。这个设计挺关键。因为关联计费意味着动用公司的真金白银，如果任何一个普通成员都能随手把一个外部平台绑到公司账上，那财务和 IT 部门会疯掉。所以它把授权收拢到了有财务权限的角色手里，同时又保证一次批准对整个组织生效。不管你是三个人的小团队还是三千人的大公司，流程是一样的。这一点我觉得挺聪明，很多产品在小团队和大团队之间会做两套流程，结果两边都不好用。

关联建立之后，客户能做的事情有几件。他可以从已有的 Anthropic 承诺额度里扣，也可以按量付费。承诺额度这个东西，你可以理解成公司年初和 Anthropic 谈好的一个年度消费包，先承诺一个量，换一个更优的单价，然后慢慢消耗。关联计费让这些额度可以直接在第三方工具里消耗，不用重新走一遍采购。他还可以为每一个关联的平台单独设一个月度支出上限，也可以设一个对所有平台生效的默认上限。他可以在控制台里看到每个平台分别花了多少钱。他随时可以解绑，而且是在控制台里直接操作，不需要求平台配合，也不需要等工单回复。

平台这边呢，也有对应的收益。

最直接的一条是，它不需要自己建计量和开票系统。用量计量指的是统计每个客户调了多少次、用了多少 token、用了哪些模型，按什么规则折算成钱；开票结算指的是生成账单、收款、对账、处理退款和税务。这两套东西听起来不复杂，真做起来是几个月的工作量，而且是个无底洞。你得处理不同国家的税，得处理信用卡拒付，得处理客户说“这个月账单不对”的扯皮，还得给财务做月结报表。关联计费把审批流和计费都托管在 Anthropic 这边，平台只要接进去就行。对于一个小团队来说，这相当于把一整个计费中台外包出去了。

第二条是，平台能看到每个关联客户的用量。在控制台里能看，也可以通过用量与成本分析接口，也就是 Usage and Cost Analytics API，用程序拉数据。这一点对做产品很重要。你可以基于这个数据做自己的用量看板，让客户在你这儿就能看到自己花了多少；你可以做容量规划，提前知道哪个大客户这个月用量要爆；你可以做客户成功，发现某个客户用量突然掉了一半，赶紧去问问是不是出问题了。

第三条，也是我觉得最灵活的一点，平台可以按请求决定谁来付钱。也就是说，同一家平台，可以一部分调用算平台的账，一部分调用算客户的账。这个能力打开了很多产品设计的空间，我们多推演几个场景。

场景一，免费增值模式。一个工作流自动化平台，免费版让用户试用，模型调用由平台自己承担，成本可控，因为免费版有限制；用户升级到付费版，引导他关联自己的 Claude 组织，之后的调用直接记在他账上。这样平台不再承担模型成本，毛利结构一下子就变了。以前平台最怕的就是重度用户，用得越多平台亏得越多；现在重度用户越多，平台收入越高，因为模型成本转移出去了。

场景二，功能分层。同一个产品里，基础功能比如文本摘要、分类打标，调用量小，平台买单，作为产品体验的一部分；那些特别耗 token 的高级功能，比如让 agent 自己规划任务、自己写代码、自己跑几十轮迭代，就让客户关联自己的账来付。这样定价可以做得非常细，客户也能清楚地知道钱花在哪儿。

场景三，混合模式。企业客户签的是年度合同，合同里包含一定额度的平台服务费，超出部分转嫁到客户自己的 Claude 组织。财务上很清楚，平台也不用垫资。

你注意，这三种模式在 BYOK 时代都很难做，因为那时候要么客户给 key，要么平台全包，中间没有灰度。现在可以按请求粒度切，产品设计的自由度大了很多。

好，讲到这里，方案看起来很美。但文章里有一句话，我认为是整篇最重要的，也是最容易被忽略的，我们得单独拿出来说。这句话是：请求在平台的组织里运行，所以客户组织里的设置，比如 IP 白名单也就是访问来源限制、加密密钥、数据保留策略，都不适用。

这句话什么意思？我们拆开看。虽然账单记在客户头上，但请求实际上是在平台的组织里发出去的。这就好比，你用公司的信用卡副卡在某个商店消费，钱是从你公司账上扣的，但这次购物的会员积分、退货政策、售后，都归那个商店和你这张副卡的关系管，不归你公司管。对应到技术层面，客户在自己组织里配置的那些安全策略，对平台发起的请求是不生效的。

这个取舍非常值得琢磨。为什么这么设计？因为从请求的归属来看，它确实是平台在服务它的客户，平台是请求的发起方，客户的 Claude 组织只是付钱的那一方。如果让客户的 IP 白名单、加密密钥、数据保留策略强行作用到平台的请求上，技术上很难做，而且会带来一堆边界情况。比如客户的加密密钥在客户自己的云环境里，平台的服务器根本访问不到，怎么加密？所以 Anthropic 选择了一个清晰的边界：钱走客户，请求的安全边界走平台。

我个人认为这是合理的工程取舍，但对企业采购来说，这是一个必须在合同和评估阶段问清楚的点。你可以想象几个场景。

第一个场景，一家金融公司，合规要求所有调用 Claude 的数据必须按照自己的数据保留策略处理，必须走自己的加密密钥。这时候关联计费就不满足要求，因为它绕过了这些设置。这家公司如果还想用那个平台，可能就得换一种方式，比如继续用 BYOK，或者干脆要求平台提供私有化部署。

第二个场景，一家医疗公司，数据特别敏感，所有请求必须经过自己的出口 IP 审计。关联计费下，请求从平台的 IP 发出去，这条审计链就断了。

第三个场景，一家普通的互联网公司，只是想让费用归集到自己账上、想有个统一的支出上限、想让财务能看到每个工具的消耗，对请求层面的安全策略没那么敏感。那关联计费就是完全够用的，而且体验比 BYOK 好太多。

所以我的建议是，把关联计费理解成“账单层面的关联”，而不是“安全层面的托管”。这两件事不要混为一谈。你在评估的时候，要把“钱怎么走”和“数据怎么走”分成两个问题来问，别被一个“安全”的大词糊弄过去。

接下来我们看看生态。文章列了一长串已经支持关联计费的平台，我念几个你可能熟悉的：Linear，做项目管理的，也做云端 coding agent；Ramp，做企业费用管理的；Railway，做应用部署的；Asana，做工作管理的；ClickHouse，做数据库的；Warp，做终端的；Tines，做安全自动化的；还有 Harness、Gumloop、Niteshift、OpenArt、Omni、Mintlify、Kilo Code、Factory、Higgsfield AI、Major、Runlayer、Tessera 等等，加起来接近二十家。

这个名单本身就说明了一些事情。它不是一两个尝鲜的小工具，而是覆盖了项目管理、应用部署、数据库、企业费用管理、终端、安全自动化、创意生成这些企业软件的核心品类。换句话说，Anthropic 不是在做一个小功能，它是在铺一层基础设施。

你再看文章里那些合作方的证言，关键词反复出现。不用再分享 API key，少一个攻击面，一次关联就能用，月度支出上限，开户流程更简单。Linear 那边的说法很直接，手动复制 API key 本身就是不安全的，现在管理员点一下就能把承诺额度用在 Linear 的云端 coding agent 上。Tines 强调的是 IT 和安全团队需要的可见性和控制。Niteshift 提到随着 agent 用量在规模和范围上增长，客户越来越同时关注成本控制和安全。Railway 说的是让开发者专注在构建和部署上，而不是手动管理 API key。这些说法拼在一起，其实描绘出了二〇二六年这个时间点的真实状态：agent 类工具的调用量在快速膨胀，企业一边想用，一边又怕失控，而“不用交密钥”这件事，已经成了能否进入企业采购清单的门槛之一。

那具体怎么上手？文章给了两条路径。平台方这边，在 Claude 平台的控制台里创建一个应用，然后按照文档里的步骤接入。客户这边，从任何一个支持关联计费的平台发起关联，用有所有者、管理员或账单角色的账号批准，然后设限额。想找哪些平台支持，可以去 Claude 应用市场里看。

好，理论讲完了，我们来聊点实际的。这部分可能是对你日常工作最有用的。

如果你是一个平台方，一个 SaaS 团队，正在纠结要不要接关联计费，我给你一个判断框架。先问自己三个问题。第一个，你的客户里有多少比例已经在用 Claude，并且有企业级的采购关系？比例越高，这个功能的价值越大，因为你能直接吃到他们已有的承诺额度。第二个，你的销售在成单过程中，有多少次卡在安全审查或者 API key 管理这一关？如果你每个季度都要填一堆安全问卷，回答“我们如何存储客户密钥”这种问题，那关联计费能帮你省掉一大块销售摩擦。第三个，你自己维护计量和开票系统，一年要花多少工程人力？如果这三个问题的答案都指向“不少”，那这件事的投入产出比大概率是正的。

接入的时候有几个坑要提前想好。

第一个坑是“谁付费”的逻辑。因为它是按请求决定的，你得在代码里明确每一个请求走哪条账。我建议一开始不要做太复杂的规则，先从“整个工作区一个策略”开始，跑通了再细化到按功能、按实例。因为一旦规则复杂，出问题的时候你会很难排查：客户说我没花这么多钱，你一看日志，发现三个月前的一个配置把某类请求路由错了。这种 bug 特别隐蔽，因为请求是成功的，只是账单记错了人。

第二个坑是安全策略的责任转移。前面说了，客户组织的 IP 白名单、加密密钥、数据保留策略对你不生效，那这些责任就落在你身上了。你得自己评估：我这个平台处理的是什么数据，需不需要额外的隔离，日志里会不会留下敏感内容，数据在模型侧留多久。很多团队容易忽略这一点，觉得“反正账单是客户的，合规也是客户的事”。不是的，请求从你的组织发出去，你就得对你的组织负责。

第三个坑是客户体验。关联流程跳转到 Anthropic 的页面，这是托管的好处，但也意味着你对这段体验的控制力有限。你需要在产品里做好引导：告诉客户为什么要关联，关联之后会发生什么，限额怎么设比较合理，如果客户公司的审批人不是他本人，怎么把链接转给财务。这些细节不做，转化率会掉得很厉害。

如果你是一个客户方，一个正在采购 AI 工具的企业，我建议你把关联计费加进你的采购清单，并且问供应商几个具体问题。

第一个问题，这个平台是不是支持关联计费，如果不支持，它是怎么拿到我们的 key 的，key 存在哪里，多久轮换一次，离职员工能不能带走。

第二个问题，关联之后，我们的数据保留策略和加密要求还能不能满足，如果不能，平台的合规资质是什么，有没有第三方审计报告。

第三个问题，月度支出上限能不能设，超限之后是拒绝请求还是只发告警，谁来收这个告警。

第四个问题，解绑的流程是什么，解绑之后历史用量数据还能不能查到，能不能导出。

第五个问题，也是最容易被忽略的，谁能批准关联。你最好在内部明确一个流程：哪些角色有权限批准，批准之前要不要走一次安全评审，关联之后多久复核一次。

这里我要特别提醒一点，关于支出上限。文章说的是月度限额，这意味着它不是一个实时的熔断机制。你可以想象一个场景：一个 agent 陷入了循环调用，十分钟烧掉了一大笔钱，但你的月度限额还有富余，它不会拦你。所以在 agent 类工具上，光靠月度限额是不够的，你还需要平台侧提供单次任务的最大步数、最大 token 数、最大并发这类硬性约束。这是我个人认为在实际使用中最容易出事的地方。月度限额管的是“这个月总量别太离谱”，管不了“这一分钟别失控”。两套机制得配着用。

还有一个运维层面的小变化。以前你用 API key 的时候，可以在 Anthropic 控制台里按 key 统计用量，一个 key 对应一个系统，账很好算。换成关联计费之后，你的支出会分散在多个平台上，每个平台有自己的一套调用逻辑、自己的重试策略、自己的缓存策略。所以你需要定期做支出归因的审计，看看钱到底花在哪儿了，哪些平台的用量在异常增长。文章提到控制台能看到每个关联平台的支出，平台侧也能通过接口拉数据，这两边的数据最好定期对一对。如果对不上，说明中间有一层的计量口径不一致，得赶紧查。

再往深一层想，关联计费其实改变了企业内部的 AI 治理方式。以前是“谁申请 key 谁负责”，散落在各个团队，IT 根本看不到全貌，这就是典型的影子 IT。现在只要走关联流程，账单就集中在一个组织下，财务和 IT 能看到全貌，能设上限，能随时掐断。这种集中化对合规部门来说是好事，但对一线团队来说可能是摩擦：以前自己申请个 key 十分钟搞定，现在要走审批，要等财务。所以推行的时候，你得把审批流程设计得足够轻，比如小额自动通过、大额才升级，不然大家又会绕回去偷偷用。

最后我们往大了看一点。这篇发布本身不炫技，没有新模型，没有新能力，就是一个计费和授权机制的调整。但我个人认为它的意义不小。它标志着 AI API 的商业化，正在从“卖 token”往“卖可治理的 token”演进。企业客户要的从来不只是便宜，他们要的是能审计、能限额、能撤销、能归因。关联计费把这些东西补齐了。

而且这个模式有很强的外溢可能。你想想云厂商的应用市场，早就有类似的私有报价和合并计费，客户在用第三方软件时，账单直接进云厂商的统一账单。这让我想到 Stripe 早年做的平台分账，也是把“谁收钱、谁付钱、怎么分”抽象成一层基础设施。如果关联计费在 Claude 平台上跑通了，其他模型厂商大概率会跟进，甚至可能出现跨模型厂商的通用关联标准。到那个时候，“把你的组织关联一下”可能会变成接入任何 AI 工具的标准动作，就像今天你用任何网站都习惯点“使用某个账号登录”一样。到那时候，回头再看今天这篇 beta 公告，可能会觉得它是一个分水岭。

当然，现在还是 beta，生态还在长，那个“客户组织设置不适用”的限制也还在，接入的文档和工具链肯定还会迭代。但方向是清楚的。

总结一下今天这期。Anthropic 在 Claude 平台上推出了关联计费的 beta，让第三方平台可以在不接触客户 API key 的前提下，把 Claude 的用量直接计费到客户自己的组织上。它用一次授权、一个上限、一个随时可撤销的关联，替代了过去复制粘贴密钥的做法。对平台方来说，省掉了计量和开票的重建，还拿到了按客户看用量和按请求分账的能力；对客户来说，拿到了可见性和控制权；代价是请求层面的安全策略由平台负责，而不是客户。我的点评是：这是一个典型的、不性感但很值钱的基础设施发布。它不会上头条，但它会实打实地改变很多团队的集成方式和采购流程。如果你在做 agent 平台，或者在企业里管 AI 采购，值得花半小时把文档读一遍，然后问自己一个问题：我们现在还在传密钥吗？
