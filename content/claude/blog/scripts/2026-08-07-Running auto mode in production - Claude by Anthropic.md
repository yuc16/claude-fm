## Script

今天我们要聊的文章是 Running auto mode in production，中文可以翻译成，在生产环境中运行自动模式。这篇文章发表于二〇二六年八月七日。今天是二〇二六年八月九日，也就是说它几乎是刚刚发布的一篇文章，非常贴近当下 Claude Code 和 AI 编程工具的最新演进。

这期为什么值得听？因为它不只是介绍一个新功能，而是在回答一个越来越现实的问题。过去我们讨论 coding agent，也就是能帮你读代码、改代码、跑命令、调用工具的编程智能体，常常停留在演示和个人效率层面。可一旦进入公司生产环境，问题马上变了。不是它能不能写代码，而是它能不能安全地写代码。不是它能不能跑命令，而是它跑命令时会不会删错东西、越过边界、被 prompt injection 也就是提示词注入带偏。Anthropic 这篇文章用 Nuro、Gusto 和 Garner Health 三家公司的实际做法，展示了一个很关键的方向，怎样让 agent 跑得更久、更快，但又不是完全放飞。

先说文章的核心背景。Claude Code 里的 auto mode，现在已经是默认设置。auto mode 可以翻译成自动模式。以前，agent 想执行每一个命令，系统都要问你要不要批准。比如它想看一个文件，你点批准。它想跑测试，你点批准。它想改一个配置，你再点批准。这种方式的好处很明显，人始终在环路里，human in the loop，每一步都有人看着。但坏处也很明显，随着任务变长，或者你同时开好几个会话，审批本身就变成了瓶颈。

你可以想象一个很常见的工作日场景。你让 Claude Code 帮你重构一个模块，它要先搜索代码，再读文档，再跑测试，再改文件，再跑 lint，再修错误。如果每一步都弹一个确认，你刚开始还认真看，十分钟之后就开始机械地点 approve。再过一会儿，你可能连它到底要执行什么都懒得看了。这个时候，所谓人工审批，在形式上还存在，但实际安全价值已经下降了。这就是文章里说的 permission fatigue，权限疲劳。

另一条路是什么？直接跳过权限检查。很多开发者为了快，会选择 bypass permissions，也就是绕过权限审批，让 agent 直接执行。这样确实流畅，尤其是你希望它连续工作半小时、一小时，甚至放在那里过夜。但风险也跟着来了。prompt injection 可能让模型去做和你原始意图不一致的事。scope drift，也就是范围漂移，可能让任务从修一个测试慢慢滑向修改生产配置。还有最极端但并非不可想象的情况，误删生产资源，或者对线上 API 发出不该发的请求。

auto mode 试图补上的，就是速度和安全之间的这条缝。它不是让所有命令都自动通过，也不是让人一条条审批，而是在中间放了一个 classifier，中文可以叫分类器。每当 agent 想执行一个动作，分类器会评估这个动作看起来是不是有潜在危害。如果看起来安全，它就放行。如果看起来危险，或者和用户原本请求不对齐，它就阻止，要求停下来。

文章给了两个很有信息量的结果。第一，在 Anthropic 的内部评估里，这个分类器抓到的危险动作，比开发者手动点击权限提示时抓到的还多。这个说法很有意思，因为它不是简单说机器比人聪明，而是在说，当审批变成高频、重复、疲劳的动作时，人类的注意力会被消耗掉。第二，auto mode 经过了第三方 red-teaming，也就是第三方红队测试，表现仍然保持住了。第三，因为会话中断更少，在所有 Claude Code 使用中，Claude 在两次中断之间工作的时长，是之前默认模式下的九倍。

九倍这个数字很关键。它意味着 auto mode 的价值不只是少点几个按钮，而是改变了工作流的形态。如果 agent 只能连续工作三分钟，你会把它当成一个辅助工具。如果它能连续工作半小时、一晚上，你就会开始把一些原来必须人盯着推进的工作，交给它做阶段性推进。文章后面三家公司案例，其实都是围绕这个变化展开的。

我们先看 Nuro。Nuro 是一家做 physical AI 的公司，文章里说它在开发通用的四级自动驾驶技术。四级自动驾驶意味着在特定条件和区域内，车辆可以不需要人类驾驶员接管。这样的公司对代码安全、测试、评估和生产环境的要求都很高。Nuro 在二〇二五年末开始采用 Claude Code，到二〇二六年三月，Claude Code 已经成为公司内部最受欢迎的 agentic coding tool，也就是智能体式编程工具。

有意思的是，在 auto mode 正式推出之前，Nuro 的员工软件工程师 Kai Zhou 已经在内部做了一个类似的原型。他写了一个 hook，也就是挂钩机制，把每一个待执行动作发送给一个小模型。这个小模型会自动批准大约百分之九十的常规操作，把敏感操作转到 Slack 里，让真人审查。你看，这个原型几乎就是 auto mode 的企业版雏形。它说明这个需求不是 Anthropic 凭空想出来的，而是工程团队真的已经被权限提示折磨到要自己造轮子。

Kai 当时面对的矛盾非常典型。工程师不想一直坐在那里点批准。可从公司安全和法律的角度，完全跳过权限审批又太危险，不能正式批准。auto mode 发布以后，他就把自己的副项目搁置了。现在，他说自己写的所有代码都用 auto mode。他不想坐在那里一直点 approve。大多数时候，他会同时打开三到四个 auto mode 会话，只在需要的时候回来检查。

这句话背后有一个新的工程工作方式。过去你可能一次只和一个工具互动，像开一辆手动挡车，手一直放在挡杆上。现在更像同时派出三到四个初级工程师，每个人负责一个小方向，你不盯着他们敲每一行，而是在关键节点审查结果。这个变化对资深工程师尤其明显。资深工程师真正稀缺的是判断力，不是按确认键的时间。auto mode 的目标，就是把人的注意力从低价值审批里释放出来，转移到结果、方向和边界上。

但 Nuro 并不是完全无约束地使用 auto mode。文章说得很清楚，Kai 在涉及其他团队的工作上，会切回 interactive mode，也就是交互模式。比如 Claude Code 代表他去 review 一个 Pull Request，也就是审查合并请求时，他会在发出去之前逐条确认。这里的边界非常重要。你让 agent 在自己的工作区里读代码、跑测试、改草稿，风险是一类。你让 agent 代表你对别人说话、对别人的代码给评价、影响其他团队协作，风险又是另一类。后者牵涉信任、沟通和组织上下文，不能简单用自动化吞掉。

Nuro 还大量使用 skills。skills 可以理解成给 Claude Code 配置的标准化能力、流程或者任务技能。同时，工程师会在设置里直接拒绝最危险的命令，比如 recursive deletes，也就是递归删除。递归删除之所以危险，是因为它可能从一个目录一路删下去，删到不可恢复。auto mode 的分类器不是在真空里做判断，而是在这些护栏里面做判断。先有明确禁止项，再有分类器判断灰色区域，这才是比较成熟的用法。

Nuro 案例里最值得展开的，是 auto mode 解锁了长时间运行的研究 agent。Kai 的团队用 auto mode 支撑一种能持续运行的研究型 agent，去 hill-climb 自动驾驶栈背后的评估指标。hill-climb 可以理解成爬山式优化，也就是不断尝试小改动，看指标有没有变好，变好就继续朝这个方向走，变差就回退或换方向。这类任务非常适合 agent，因为它有一个清晰、可测量的信号。比如评估套件标记出一些 false negatives，也就是假阴性，系统本该发现却没发现的问题。agent 可以研究这些案例，写一个方案，跑实验，根据结果继续迭代。

这和很多没有明确评估标准的工作不同。比如让 agent 帮你设计一个全新产品架构，它很难自己判断优劣，因为判断依赖业务、团队和长期演进。但如果任务是降低某个二进制文件的内存占用，或者提升某个评测指标，那就不一样了。指标本身会告诉 agent，它是在进步还是退步。文章提到，Nuro 另一个团队就把这种方法用在缩小某个特定 binary，也就是二进制文件的内存占用上。

Kai 举了一个例子，他晚上十点启动了一个 agent，它一直跑到早上五点，早上给了他三个 Pull Request。他说这很令人印象深刻，只有 auto mode 才能支持这种工作负载。这句话我个人认为是整篇文章最重要的信号之一。它说明 auto mode 的真正价值，不只是白天少打断你，而是让 agent 能进入异步工作。人下班了，评估还在跑，实验还在迭代，第二天早上你面对的不是一堆空白任务，而是三个可以 review 的候选结果。

当然，我们也要冷静一点。原文没有说这三个 Pull Request 都可以直接合并，也没有说它们一定正确。它只说 agent 产出了三个 PR。真正进入生产，还需要人类审查、测试、合规流程和团队约定。但即便如此，这已经改变了工程吞吐的节奏。以前夜里机器可以跑 CI，可以跑批处理；现在夜里 agent 也可以做一部分探索性工程工作。

第二个案例是 Gusto。Gusto 是一家服务中小企业的技术公司。它采用 auto mode 的起点，是主动的安全升级。Gusto 的 AI Dev Tools 团队成员 Martin Emde 观察到，权限疲劳拖慢了团队。auto mode 让他们在不牺牲控制和安全的情况下保持速度。随着工程组织采用 auto mode，整体权限负担明显下降。

Martin 从十二月以来启动了两千四百二十五个 Claude Code 会话，并把 auto mode 作为日常主力模式。这个数字说明他不是偶尔试一下，而是在高频使用。文章提到，过去跨仓库工作经常卡在文件夹访问审批上，现在可以不中断地跑下去。还有一些无人值守任务，比如从 GitHub、Slack 和 Jira 汇总每日笔记，也可以自己运行。这里你可以看到 auto mode 不只用于写代码，也用于工程信息整理。现代软件工程的上下文分散在代码仓库、聊天记录、工单系统、文档系统里，agent 如果每跨一个工具就要等你点一次，它的价值会被切碎。

Gusto 自己分析了从二〇二六年五月中旬以来的会话记录，大约百分之十的 session transcripts，也就是会话转录记录，包含一次 auto mode denial，也就是自动模式拒绝。这是一个很重要的细节。它说明分类器不是摆设，不是所有东西都无脑放行。它确实在某些时刻介入，阻止了动作。同时这个比例也没有高到让正常任务无法推进。Martin 的评价是，auto mode 给了他们速度和控制之间更安全的平衡。他们去掉了重复提示，提高了生产力，同时没有牺牲安全。他们能看到 auto mode 在正确的时候阻止，所以更有信心快速前进。

Gusto 还有另一个角度，来自 AIT Cloud Engineering 团队的 Chad Kunsman。他的工作不是 Nuro 那种过夜长跑，而是很多二十分钟左右的短任务。比如 endpoint investigations，端点调查；log audits，日志审计；connector management，连接器管理；还有通过一组 MCP servers 做文档摄取。MCP 是 Model Context Protocol，可以理解成让模型连接外部工具、数据源和系统的一套协议。对云工程团队来说，这些任务经常需要查不同系统、拉日志、看配置、整理结论。

Chad 的需求不是让 agent 跑更久，而是想要 bypass permissions 那种顺滑的速度，但不想承受坏 prompt 或 prompt injection 溜进去的暴露面。他说，考虑到 auto mode 对 prompt injection 的保护，以及它会检查正在做的事是否和你要求的事一致，它比 bypass permissions 更好，也比权限提示快得多。这个评价代表了很多企业工程师的真实心态。他们不是不在乎安全，而是不想为了安全牺牲到工具不可用。真正好用的安全机制，应该是在绝大多数正常路径上不挡路，在危险边界前才出声。

Chad 还说，分类器少数几次介入时，判断是准确的。它停下来的时候解释了为什么。它发现任务正在偏离他最初的请求，所以检查了一下，并不是毫无根据。这一点很关键。安全系统如果只会说不，开发者很快会想办法绕开它。安全系统如果能解释为什么停，开发者才会建立信任。比如你让 agent 查日志，但它突然要对 live API 发 POST 请求，这时候系统停下来并说这已经超出原始调查范围，你大概率会觉得合理。相反，如果你只是让它读一个本地文件，它也一直拒绝，你就会关掉它。

不过，Chad 对最敏感的工作仍然会退出 auto mode。当一个会话已经深入生产基础设施，比如 Terraform、AWS，或者对 live APIs 发直接 POST 请求时，他会切换到 accept edits，也就是只接受编辑的模式，并手动验证每一个工具调用。他说，你必须权衡节省的时间，和它可能合理犯错的地方，以及这个错误会有多灾难。最终，发生了什么，你仍然要负责。

这句话我建议每个用 coding agent 的工程师都记住。auto mode 不是责任转移器。它最多是一个更聪明的默认安全层。尤其在生产基础设施上，错误成本可能极高。Terraform apply 到错的环境，AWS 权限改错，对线上 API 发错请求，这些事情不是回滚一个本地文件那么简单。你可以让 agent 帮你生成计划、解释 diff、检查配置，但到真正会改变线上状态的那一步，人类责任不能消失。

Gusto 的使用也不是只靠 auto mode 一层。文章说，他们把 MCP 流量通过一个受治理的 proxy layer，也就是代理层来路由。这个代理层有 tool guards，工具护栏，还有 prompt inspection，提示词检查。也就是说，在 auto mode 介入之前，agent 拿到的工具权限已经被收窄了。它不是拥有无限钥匙的万能代理，而是在限定范围内行动。这个叫 defense in depth，纵深防御。一层失效，还有下一层。一层负责权限范围，一层负责提示词检查，一层负责动作分类，一层负责人类审查。

第三个案例是 Garner Health。Garner Health 是一家医疗科技公司。今年二月，他们把 Claude Code 推给了全公司五百五十名员工，覆盖所有职能。文章说，这个工具连接到了所有核心系统，包括 Salesforce、Zendesk 和 Snowflake。员工被鼓励每周花大约两小时，自动化自己工作中最重复的部分。

这个规模和前两个案例又不一样。Nuro 更偏高复杂度工程研究，Gusto 更偏工程组织和云工程安全，Garner Health 则把 Claude Code 推到了全员级别。五百五十个人，每个人都可以连接核心系统，这意味着权限管理和流程标准化的压力会非常大。尤其医疗科技公司还天然涉及敏感数据、合规和业务流程。原文没有展开医疗合规细节，所以我们不额外发挥。但仅从工具接入 Salesforce、Zendesk、Snowflake 这些系统看，它显然不只是本地写代码。

在 auto mode 之前，这种规模会带来大量开销。Garner 的平台工程经理 Evan Magnussen 说，权限管理是一种乏味循环。你要手工维护已批准命令列表，还要看着带管道的命令被拒绝。这里的 piped commands，也就是带管道的命令，在命令行里很常见。比如一个命令输出接到另一个命令输入，用来搜索、过滤、转换。对开发者来说这是正常操作，但对静态审批列表来说，它可能看起来复杂、不好判断，于是容易被拒。结果就是正常工作流被安全机制打断。

现在，Evan 和大多数同事在每个会话中都使用 auto mode。从研究代码库，到通过 MCP 管理外部集成，auto mode 都在使用。他说，他们为整个工程组织建立了一个标准化的软件开发生命周期，而这基本上只有 auto mode 才能实现。员工把它看成肩上的重量被卸下来了，不再需要盯着 agent 好几个小时。

Garner 的这个软件开发生命周期，是通过一组标准化 skills 插件来运行的。一个 agent 接到任务后，会先探索它能访问到的上下文，把上下文文件提交到仓库，然后进行 Evan 所说的 antagonistic research。这个词可以翻译成对抗性研究，意思是让 agent 主动压力测试自己的假设，不是只找支持自己方案的证据，而是寻找反例、边界条件和可能失败的地方。之后它才进入实现阶段。只有当它需要自己找不到的上下文时，才暂停给人类。

这套流程很值得工程团队借鉴。很多人用 agent 的方式是直接说，帮我实现这个功能。模型会很快开始改代码，但它可能没有理解足够上下文，也没有验证自己的假设。Garner 的流程更像是把人类资深工程师的工作习惯模板化。先研究上下文，再沉淀上下文，再挑战假设，再实现。auto mode 的作用，是让这些研究阶段可以连续进行。如果每读一个文件、每跑一个查询、每整理一个上下文都要你批准，对抗性研究就很难跑起来。

Evan 说，分类器开箱即用需要很少调优。他做的一个调整和 Nuro 的 Kai 很像，就是配置 auto mode 不要批准会和其他人沟通的动作，比如发送 Slack 消息或邮件。他个人不喜欢 Claude 在与别人沟通时直接代表他行动。这个边界再次出现，说明在真实组织里，沟通动作和代码动作是不一样的。代码动作可以通过 diff、测试、审查来回看。沟通动作一旦发出，就进入了人际和组织系统，可能造成误解、承诺或者不该公开的信息流动。

文章还提到，负责核心知识产权的团队，一开始对跳过权限最怀疑。后来他们学会调整分类器的 injected prompts，也就是注入给分类器的提示，让它对自己的工作更宽松或更严格。这里不要误解成随便改安全策略，而是说不同团队风险画像不同。做内部工具、做文档整理、做核心 IP、做生产基础设施，应该有不同的默认边界。好的 auto mode 落地，不是一个全公司统一的开关，而是在标准化基础上允许合理调节。

Evan 给其他企业的建议是，应该积极拥抱，但要构建正确控制，这样才能赋能工程师，同时确保安全部署。他说，如果只是告诉所有人去构建自己的工作流，而没有 telemetry，也就是遥测数据，那会非常危险。因为他们有遥测，因为他们建立了相对标准化的工作流，所以更有信心。telemetry 在这里不是一个可有可无的管理报表，而是企业级 agent 落地的基础设施。你需要知道 agent 调用了哪些工具，在哪些地方被拒绝，哪些工作流最常见，哪些权限最敏感，哪里可能出现异常。

把三个案例放在一起看，文章其实给了一个比较完整的生产落地图谱。Nuro 展示的是长时间自主迭代，前提是任务有清晰评估指标和强护栏。Gusto 展示的是日常工程和云工程里的速度安全平衡，前提是 MCP 代理、工具护栏和人工接管。Garner 展示的是全组织规模化 adoption，前提是标准化生命周期、skills、遥测和沟通边界。它们共同说明，auto mode 本身很重要，但真正让它可用的，是围绕它的一整套工程治理。

那对我们这些中国的软件工程师和 AI 从业者意味着什么？我觉得第一件事，是重新定义什么任务适合交给 auto mode。最适合的任务，通常有三个特征。目标明确，边界清楚，反馈可验证。比如跑测试并修复失败，整理代码库上下文，生成迁移草案，扫描日志并总结异常，优化某个有指标的性能问题，或者把多个系统里的信息汇总成日报。这类任务里，agent 可以自己走很多步，而你可以在结果层面审查。

不太适合完全自动放行的任务，也很明显。任何会改变生产基础设施的操作，任何会对真实用户或外部系统产生不可逆影响的操作，任何代表你向其他人发送信息的操作，任何涉及高敏感数据和合规边界的操作，都应该有更强的人类确认。这里不是说 agent 不能参与，而是说它应该更多做准备工作。比如它可以分析 Terraform plan，可以解释 AWS IAM 权限变化，可以草拟邮件，可以生成 API 请求示例，但最后的 apply、send、POST，最好由人确认。

第二件事，是不要把 auto mode 理解成一个孤立功能。如果你在公司里推广类似能力，不能只说大家打开自动模式吧。你需要先定义权限层级。哪些目录可以读写，哪些命令永远拒绝，哪些工具只读，哪些工具可写，哪些环境是 sandbox，哪些环境是 production。你还需要定义工作流模板。比如新需求先研究上下文，再写计划，再实现，再跑测试，再生成 PR 描述。这样 agent 的自由不是无边界自由，而是在轨道上跑。

第三件事，是为 agent 设计评估信号。Nuro 的例子非常值得借鉴。agent 最能发挥作用的地方，不是你说一句做得更好，它就知道什么叫更好，而是你给它一个可以反复测量的目标。单元测试通过率、benchmark 数字、内存占用、构建时间、错误日志数量、某类告警命中率，这些都可以成为 agent 迭代的反馈。如果你来做一个夜间 agent，不妨先问自己，明天早上我怎么判断它做得好不好？如果答案只是凭感觉，那它可能不适合无人值守长跑。如果答案是看这几个指标和这几组测试，那就更适合。

第四件事，是要重视拒绝日志。Gusto 看到大约百分之十的会话记录里有 auto mode 拒绝，这给了他们信心。很多团队上安全系统，只关注拦了多少危险动作，却不分析误拦和漏拦，也不把这些数据反馈给工作流设计。真正成熟的做法，是看拒绝发生在哪里。是不是某类正常命令经常被误判？是不是某些团队总在触碰危险边界？是不是某个 MCP 工具权限给得太大？这些问题只有有遥测才能回答。

第五件事，是把沟通边界单独拿出来设计。Nuro 和 Garner 都提到，不希望 Claude 自动代表自己与其他人互动。这个点非常接地气。我们平时可能容易把发 Slack、发邮件、评论 PR 看成小事，但在组织里，这些动作带有身份和责任。一个 PR review 评论可能影响同事判断，一个邮件可能构成承诺，一个工单回复可能影响客户体验。所以我个人认为，企业默认策略应该是，agent 可以草拟沟通内容，可以总结上下文，可以建议回复，但发送前必须人类确认，至少在大多数场景下应该如此。

第六件事，是对个人开发者也有启发。即便你不是企业平台负责人，只是在自己的项目里用 Claude Code，你也可以借鉴这些原则。把高风险命令加入拒绝列表。生产密钥和生产环境不要暴露给默认 agent 会话。把任务拆成有清晰结束条件的小块。让 agent 先写计划，再改代码。长时间运行前，给它测试命令和评价标准。早上回来不要直接合并它的结果，而是像 review 一个同事的 PR 一样，看 diff、跑测试、问为什么。

这里还要强调一个容易被忽视的点，auto mode 把人从频繁审批里解放出来，但并不意味着人就不需要参与。人的参与方式从过程审批转向系统设计和关键审查。你不再是每一步的门卫，而是路线设计者、护栏设计者和最终责任人。这对工程师能力要求其实更高。你要知道哪些命令危险，哪些指标可靠，哪些工具权限该收窄，哪些结果需要复核。不会设计边界的人，用自动模式反而更容易出问题。

我个人认为，这篇文章最有价值的地方，是它把 agent 生产化从功能讨论带到了组织工作流讨论。很多 AI 编程工具的宣传会强调快，强调能省多少时间。但真正进入生产，快只是第一层。更难的是，如何让一个会行动的模型在公司系统里可控地行动。auto mode 的分类器是一个关键组件，但 Nuro、Gusto、Garner 的案例反复说明，分类器必须和 skills、权限设置、MCP 代理、遥测、人工边界、标准化流程一起工作。

当然，我们也要注意原文的边界。文章来自 Anthropic 自己的博客，选择的也是成功客户案例。它展示了 auto mode 的优点和实践方式，但没有给出完整失败案例，也没有展开分类器的具体技术细节，比如模型结构、训练数据、误判率分布、红队测试方法。这些不是这篇五分钟博客的重点。所以我们在吸收时，应该把它当成生产实践信号，而不是一份完整安全白皮书。

如果你所在团队正在评估 coding agent，我建议可以从一个低风险但有价值的试点开始。比如代码库研究助手、测试失败修复助手、文档同步助手、日志摘要助手。先把工具权限收窄，只给必要访问。再定义标准 workflow，要求 agent 输出计划、证据和结果。然后开启类似 auto mode 的机制，观察它在哪些地方被拒绝，哪些地方节省时间。最后再逐步扩展到更复杂的工程任务。不要一上来就让它碰生产基础设施，也不要完全禁止它行动。最好的路线，是让它在安全沙盒里跑出真实价值，再把边界一圈圈设计清楚。

今天这篇 Running auto mode in production 传递的核心信息，可以用一句话概括，生产环境里的 agent，不应该在手动审批和完全放飞之间二选一。auto mode 试图提供第三条路，用分类器减少无效打断，用护栏挡住危险动作，让工程师把注意力放在判断和结果上。

我的点评是，二〇二六年的 AI 编程工具竞争，已经从谁更会补全代码，进入到谁更能安全地接入真实工作流。auto mode 这样的设计，表面是一个默认设置变化，背后其实是 agent 从玩具走向生产系统的一个标志。对我们来说，真正要学的不是简单打开某个开关，而是学会为会行动的 AI 设计边界、反馈和责任链。
