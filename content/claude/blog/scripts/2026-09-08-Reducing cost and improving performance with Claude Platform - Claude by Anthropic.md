## Script

欢迎收听 Claude FM，我是你的主播。今天这期节目，我们要读的是 Anthropic 官方博客在二〇二六年九月八日发表的一篇文章，英文标题是 Reducing cost and improving performance with Claude Platform，直译过来就是《用 Claude Platform 降低开销、提升性能》。今天是九月十三号，这篇文章离我们才过去五天，可以说是非常新鲜的一手实践指南，时效性没有任何问题。

为什么要专门花二十多分钟讲这一篇？因为它回答的是一个几乎所有把 Claude 接进生产环境的团队都会撞上的问题：成本和效果，到底是不是只能二选一。这篇文章给的答案很明确，不是。它说，很多应用完全可以在不牺牲性能的前提下把账单砍下来，而且幅度不小。文章里给了四个公开基准测试的结果，成本分别下降了百分之五十二到百分之七十三，其中一个甚至把每张工单的成本压到了原来的五分之一，准确率还涨了。

那靠什么做到？文章归纳出三个杠杆。第一，把提示缓存的命中率拉满。第二，在升级到前沿模型的时候，把提示词里的反模式清掉。第三，把 effort，也就是模型的工作投入度，校准到任务本身的需要。这三个杠杆听起来都挺朴素，但每一个背后都有一大堆容易踩的坑。文章还把这三套经验固化成了 claude-api 技能包里的三个命令，让你可以在 Claude Code 里直接对自己的项目跑一遍成本体检、提示词审计和参数搜索。

所以这期节目我想按这个顺序跟你聊。先讲清楚提示缓存到底省的是哪一笔钱、为什么它那么容易失效，然后讲六种提示词反模式的具体形态和它们造成的真实损失，接着讲 effort 校准的两条曲线和两种典型误判，最后讲这三个命令分别什么时候用、四个基准上的实测数字说明了什么。听完之后，你应该能拿着自己的项目去跑一遍完整的成本审计。

先说背景。在工程直觉里，性能和成本常常被当成一对反比关系：想省钱，就得接受差一点的结果；想要好结果，就得多花钱。这个直觉在很多场景下是对的，比如你换一个更小的模型，或者把推理步数砍一半，效果通常确实会掉。但 Anthropic 这篇文章想说的是，这个直觉最容易掩盖掉一大类本来可以白捡的节省，也就是那些纯粹因为配置不当而白白烧掉的钱。

要理解这一点，得先搞清楚 Claude 处理一个请求到底在哪些环节花钱。文章讲得很直白：在 Claude 生成回答之前，它会先把你的提示处理成一个内部的工作状态，这一步叫 prefill，中文可以叫预填充。预填充是处理输入这件事里最贵的部分，因为你把成百上千甚至上百万个 token 一次性喂进去，模型要一个 token 一个 token 地算过去，把每个位置上的注意力状态算出来。这个过程算完之后，模型才开始真正往外吐字，也就是生成阶段。

那提示缓存做的事情是什么呢？它把预填充算出来的那份内部状态存下来。这份状态在技术上叫 KV 缓存，也就是键值缓存，你可以理解成模型读你的提示时留下的那份笔记。当一个新的请求以完全相同的前缀开始时，Claude 不需要重新算一遍这份笔记，直接把它读回来就行。读笔记当然比重新做一遍笔记便宜得多，缓存读取只按完整输入价格的一小部分计费。

这里打个比方。预填充就像做菜之前的备料，洗菜、切菜、调料配好、摆盘摆到位。真正下锅炒的那两分钟其实很快，但前面备料要花掉大把时间。提示缓存就是把这套备好的料封进冰箱。下一道菜如果用的料完全一样，直接从冰箱拿出来就能下锅。但冰箱有它的规矩，这个比方正好能对应上文章列出的三条限制。

第一条，缓存是钉死在某个具体模型上的。你给 Claude 三点五存的那份笔记，Claude 四点八读不了。这就像冰箱里那盒料只能配那个灶台的火候，换个灶台就不认了。

第二条，缓存读取必须在整个提示跨度上做到字节级完全相同。注意是字节级，不是"意思差不多"。多一个空格、少一个换行、系统提示里一个词从大写改小写，整个前缀就废了。这一点我觉得是所有人第一次用缓存时最容易栽跟头的地方。

第三条，缓存有存活时间，英文缩写 TTL。五分钟的缓存是从请求开始那一刻算起的，不是从请求结束算起。这个细节非常关键，后面讲 agent 的时候我们会回来说。

搞清这三条限制之后，文章给了一串非常具体的操作建议，我把它们分成两组讲。第一组是防止你把缓存弄坏的五个动作，第二组是主动管理缓存的八条经验。

先说防止弄坏的五个动作。第一个，不要在对话中途去改 effort 或者思考设置。原因很有意思：这些设置会被渲染成提示的一部分，而且位置在你的内容前面，所以它们本身就在缓存前缀里面。你中途把 effort 从高调成低，等于把前缀改了，缓存全废。不过文章特别点了一句，在 Claude Opus 五和 Fable 五点一这两个模型上，你已经可以中途更新 effort 而不破坏缓存了。这是个新能力，如果你还在用老模型，这条依然是硬约束。

第二个，把易变的值从前缀里挪出去。最典型的例子就是系统提示里写了一个动态时间戳，或者一个每次请求都会变的会话 ID。你的本意可能只是打个日志方便排查，但只要它出现在前缀里，每一次调用前缀都不一样，缓存命中率就是零。我见过不少团队在这里吃亏，查了半天以为自己缓存开关没打开，其实是被自己埋的一个时间戳毁掉了。

第三个，避免工具定义会自我重排序。用 Claude 的 Messages API 的时候，提示是按固定顺序拼装的，工具定义渲染在最上面。所以工具定义只要有一丁点变化，哪怕只是顺序变了，缓存立刻碎。如果你是从某个无序的字典结构里遍历生成工具定义，那不同语言的哈希顺序可能都不一样，缓存就永远命不中。这时候要做的就是把工具定义排成稳定的顺序，或者干脆序列化成一份固定的文本。

第四个，fork 对话的时候要小心。子代理和分支只有在三种条件同时满足时才共享父级的缓存：fork 出来的前缀字节完全相同、跑在同一个模型上、用同样的 effort。少任何一个，子代理就是从零开始付全额的输入费。这里很容易出现的误区是，你以为子代理继承了上下文就等于继承了缓存，其实不是，缓存认的是字节和模型，不是逻辑上的父子关系。

第五个，避免同步的工具调用，以及会活过缓存存活期的子代理。这条是实战里最贵的坑。设想一个场景：你的主 agent 发起一轮请求，缓存写好了，然后它阻塞在一个要跑八分钟的工具调用上，比如跑一个大数据查询，或者等一个子代理把代码重构完。等结果回来准备发下一轮请求的时候，五分钟的缓存早就过期了。这时候会发生什么？下一轮必须把整个缓存重写一遍，而重写缓存的价格是正常输入的一点二五倍，如果你开的是一小时缓存，那是两倍。也就是说，你不但没省下钱，还比不用缓存更贵。

这个机制我觉得特别值得记住，因为它违反直觉。缓存不是"有总比没有好"，配置错了的缓存是负收益。所以文章给的建议是，如果你知道某些工具调用会长时间阻塞，就考虑给前缀设一个一小时的存活期，宁可单价高一点，也别让它反复过期重写。

好，接下来是第二组，主动管理缓存的八条经验。

第一条，认真监控命中率。Claude Console 里提供了提示缓存的诊断功能，包括告诉你为什么会未命中。如果命中率突然掉了，缓存诊断的接口会直接告诉你两个请求是在哪个位置分叉的。我觉得这个功能对排查问题特别有用，因为缓存失效往往是无声的，你的请求照样成功，只是账单悄悄变贵了。

第二条，把很少用的工具延迟加载。做法是：所有工具还是照常声明，但把那些少用的标记成 defer loading，它们就不会进入缓存前缀，只有等 Claude 通过工具搜索真的去查它们的时候，才被追加进对话。这样一来，你既保留了工具的可发现性，又保住了缓存的稳定性。这个设计思路我觉得挺巧妙，本质上是把"工具全集"拆成了"高频常驻"加"低频按需"两层。

第三条，把系统提示的更新以消息的形式追加。Claude Platform 允许你在对话中途把一条系统指令当成普通消息加进去，而不是去编辑原来那条系统提示。编辑系统提示等于改前缀，缓存全废；追加一条消息则是在前缀后面加东西，前缀本身没变，缓存保得住。

第四条，请求的布局要让稳定的部分保持稳定。静态的上下文，也就是工具定义和系统提示，放在最前面，不断增长的对话放在它们后面。这样对话越长，能命中的前缀就越长。反过来的布局，比如把对话放前面、把系统提示放后面，那就等于每次都在动前缀，缓存直接作废。

第五条，把模型或 effort 的改动安排到缓存本来就要破的时候。什么意思呢？有些操作本身就会重写大部分缓存，比如压缩，它会重写整个对话历史。既然这次你已经在为缓存未命中付钱了，那这就是切换模型或者调整 effort 的好时机，反正钱已经花了，不如把该改的一次改完。

第六条，随着对话增长移动缓存断点。Claude Platform 支持设置自动缓存，把断点自动应用在最后一个可缓存的块上。手动管断点很累，自动模式省心不少。

第七条，预热缓存。这个技巧很实用：发一个 max tokens 设为零、同时带显式缓存断点的请求。它会把提示处理一遍并写进缓存，但什么都不生成。你可以在会话一开始就跑一次，比如用户正在输入第一句话的时候。等第一个真实请求到达，它命中的就是一个热缓存，首字延迟会明显改善。

第八条，也是最后一条，不要超过缓存的存活期。这一条其实是把前面那个坑再强调一遍：五分钟的 TTL 从请求开始算，如果 agent 阻塞在超过五分钟的工具调用或者子代理上，父级的缓存会在结果回来之前就过期。遇到这种情况，要么缩短工具调用，要么给前缀设一小时的 TTL。

好，缓存放一边，我们来讲第二个杠杆，提示词反模式。

文章开头有一句话我觉得很精准：提示词会积累各种用来"打补丁"的指令，这些补丁是针对当初那个模型的弱点写的。而模型在快速迭代，补丁却留在原地，于是这些指令就会和最新模型的能力发生错位。错位的后果是双重的：既拖累了模型的发挥，又悄悄地推高了成本。

文章列了六种最常见的反模式，我一个一个讲，因为它们特别具体，你大概率能在自己的项目里找到至少两三条。

第一种，验证仪式。典型写法是"再检查一遍你的工作"，或者"回答之前验证两次"。这类指令在早期模型上确实有用，因为那时候模型的自我校验能力弱。但前沿模型会字面理解这些话，它真的会去执行一遍所谓的"二次验证"，于是白白多烧一堆 token。而且更麻烦的是，它往往会重复调用同一个工具，比如重新查一遍订单，因为指令让它"验证两次"。

第二种，彻底性和强调增强器。比如"尽可能彻底"、"关键：你必须永远……"这种全大写的强调。在前沿模型上，这类词的效果不是让它更准确，而是让它更啰嗦、做更多不必要的工具调用。文章里的原话是 leads to verbosity and extra tool calls。我个人认为这里有个心理陷阱：我们写提示词的时候，总觉得语气越强效果越好，但模型能力的提升恰恰让"喊话"变成了噪声。

第三种，强制流程和草稿纸脚手架。典型的就是"一步一步在草稿纸上思考"这种固定步骤，或者给一个推理模板。对前沿模型来说，这些是它不需要的仪式。更糟的是，这种脚手架会和模型原生的推理能力叠在一起，变成两层推理，多花没必要的 token。你可以理解成：模型本来已经有内建的思考过程了，你又在外面套了一层"请先写草稿"，于是它要先把思考写出来，再基于这份写出来的东西再想一遍。

第四种，过时的示例。也就是 few shot 的样例，是照着老模型的失败模式调出来的。这些例子会教会前沿模型去模仿一长串推理链，即使面对那些根本不需要推理链的简单请求。这就好比你在教一个已经会微积分的人做加法，还非要他写出每一步的推导。

第五种，矛盾的规则。前沿模型在指令遵循上强了很多，所以矛盾的指令反而会被更字面地执行，结果是性能下降。文章举的例子特别典型："必须在政策范围内退款"和"未经升级绝不许退款"这两条放在一起。老模型可能会自己糊弄过去，前沿模型会认真对待这个矛盾，然后卡住。

第六种，过时的配置。比如给老一代 Claude 写的手动思考预算设置，在升级到前沿模型的时候，Claude Platform 可能会直接拒绝这个配置。这类问题的表现不是变慢，而是请求报错，属于比较容易被发现的。

好，讲完六种反模式，文章给了一个实验，我觉得这是全文最有说服力的部分之一。他们做了一次从 Opus 四点八到 Opus 五点 的模型迁移，用的是客户支持这个基准测试。做法是：从一个干净的提示词出发，一次只植入一种反模式，一共六种，包括一个已经废弃的思考设置、一对互相矛盾的退款规则、一个手写草稿纸、一句"验证两次"、一句"尽可能彻底"，还有一个强制的六步流程。这样就得到了六个"遗留提示词"。

然后他们拿这六个提示词分别跑三种配置：第一种，原样跑在 Opus 四点八 上；第二种，只改模型 ID，跑在 Opus 五点 上；第三种，跑在 Opus 五点 上，但每个提示词先用 claude-api 的 prompt-audit 命令清一遍反模式。

结果是这样的。在 Opus 五点 上，"验证两次"这种验证仪式会重复查订单，白白烧 token；"尽可能彻底"这种强调词则变成了几十次不必要的知识库搜索。而跑过 prompt-audit 之后，六个提示词平均下来，成本下降了百分之十四点六，准确率反而上升了百分之五点三。

准确率为什么会上涨？文章给了三个具体原因，我觉得每个都值得琢磨。第一，那个废弃的思考设置会让 API 直接拒绝每一个路由请求，也就是说这些请求根本就没跑成功。第二，那对矛盾的退款规则让 Opus 五点 在四个本该退款的工单上扣着不办，反而去问客户确认，这个行为其实是过度谨慎导致的错误。第三，手写草稿纸和 Opus 五点 内置的思考撞车了，在三个工单上，模型把工具调用写在了自己的推理过程里，然后就再也没有真的执行出去。

第三点特别有意思，它是一个非常隐蔽的失败模式：模型看起来"想"了要调用工具，但因为脚手架的存在，这个调用停留在了思考里，没有被真正执行。表面上你不会报错，只是结果不对。我觉得这正好说明，提示词里那些看起来无害的"流程指引"，实际上可能改变模型的执行路径，而且是以一种你很难察觉的方式。

接下来我们讲第三个杠杆，effort 校准。这一部分我觉得是最有"认知升级"价值的。

先定义一下。文章说，effort 是在告诉 Claude"该多用力"。低 effort 的时候，Claude 通常会更快得出结论。高 effort 的时候，Claude 会思考、验证、探索替代方案，然后才回答。这个参数本质上控制的是模型在回答前愿意投入多少推理算力。

然后文章给了两条真实的成本性能曲线，我觉得都很值得看。

第一条是 Claude Fable 五 在 FrontierCode Diamond 上的表现。这个基准是取最难的那五十道题。在低 effort 下，它的得分是百分之十一点五，每个任务花五点三五美元。在最高 effort 下，得分是百分之三十点九，每个任务花十九美元。换句话说，把 effort 拉满，分数涨了大约二点七倍，也就是提升了十九个百分点，但成本涨了大约三点五倍。

第二条是 Claude Fable 五点一 在 Humanity's Last Exam 上、不使用工具的表现。这条曲线很有意思，前面很陡，最后一步却是收益递减的。在低 effort 下，它拿大约百分之五十三，每题大约零点三美元；在最高 effort 下，拿大约百分之六十一，每题大约二点二三美元。关键是最后那一步，从次高档提到满档，只多加了大约零点五分，成本却多了百分之四十六。而且这个提升幅度落在了基准测试本身跑与跑之间的噪声范围里，也就是说，你多付了钱，却没有测到任何真实的提升。

我个人认为这个例子是整篇文章最值钱的洞察之一。它说明 effort 不是越高越好，而是存在一个明确的拐点，过了拐点之后你就是在给噪声付钱。

文章接着讲了两种方向的误校准，都是很常见的错误。

第一个方向，假设越高越好。高 effort 会导致"想太多"，也就是模型花在思考上的时间超过了这个任务本身值得的量。这不只是增加成本和延迟，文章明确说了，它还可能让回答质量下降。原因也好理解：思考只有在还有证据可找的时候才有帮助。如果所有证据都找完了，你再让它继续斟酌，它就只能在几个等价选项之间来回摇摆，反而可能选错。

第二个方向，偏向低 effort。设得太低，模型会在证据还不够的时候就停下来。它做的工具调用更少，所以它可能看完第一条搜索结果就回答了，而不是看到第三条。它在困难步骤上想得更少，跳过了它本来会自己跑的那次检查。最后的表现是：答案看起来是完整的，但它建立在一个不完整的信息基础上。我认为这个描述很精准，因为低 effort 的失败往往不是"答得很烂"，而是"答得挺像样，但其实是错的"，这种错误在生产环境里最难抓。

那怎么校准？文章给了两个方法。

第一个方法，用更低的 effort 去测更强的模型。文章的原话是：一个强模型在低 effort 下，可能比一个弱模型拼命干还便宜。举的例子是 CursorBench 三点二，Claude Fable 五点一 在低 effort 下追平了 Fable 五 在高 effort 下的表现，而成本只有三分之一。这个新模型为什么便宜，有两个原因：一是低 effort 下它每个任务做的工作本来就少，二是 Fable 五点一 的缓存读取价格是每一百万 token 零点二五美元，而 Fable 五 是一美元。文章还补了一句：即使按 Fable 五 的价格算，Fable 五点一 在低 effort 下也能便宜大约百分之四十。

这个结论我觉得对做架构选型的人特别有指导意义。过去我们的默认思路是"任务难就换大模型、上高配置"，但这条曲线告诉你，更划算的做法可能是"用最新一代的模型，但把 effort 开低"。新一代模型的单位 token 效率更高，价格也可能更低，所以它的低配档位往往能吃掉上一代的高配档位。

第二个方法，理解你的任务形状。做法是在一系列 effort 档位上测量你应用的表现，画出你那个具体任务的成本性能曲线。文章给了一个判断标准：在一个还没有饱和的评估上，如果性能成本曲线在各 effort 档位之间是平的，那就说明这个任务不受思考算力的约束，提高 effort 没有任何好处。这个判断我觉得非常实用，因为它给了你一个明确的停止信号。

讲到这里，文章开始介绍三个工具命令。第一个是 prompt-audit，当你迁移到前沿模型、想检查现有提示词的时候用它。它会扫描你工作目录里的提示词、技能和工具描述，包括调用 Claude API 的应用代码，也包括 Claude Code 自己的配置，比如 CLAUDE.md 或者各种技能文件，然后把常见的反模式清掉。

第二个是 hillclimb，用一个评估集做成本性能的迭代搜索。它会把你给的评估集拆成训练集和测试集，提出配置变更建议，并且会去读训练集里失败的样例，据此修复它发现的问题。

文章给了一次 hillclimb 的完整实战，我觉得这段特别值得完整讲一遍，因为它展示了搜索的节奏。

起点是 Opus 四点八 跑在它的默认值上，也就是高 effort。搜索器第一步尝试的是 Opus 五点 加低 effort，同时跑 prompt-audit 把那些强制工具调用的仪式、草稿纸步骤和矛盾规则清掉。这一步就把 Opus 四点八 的基线给超了，训练集准确率达到百分之九十八点九，每张工单成本降到二点六美分。

第二步，它降到 Sonnet 五点 加低 effort，成本更低了，只要一美分一张工单，但准确率掉到了百分之八十八点九。注意，这里它没有直接放弃，而是去读那些失败了的训练工单，从里面看出问题在哪，然后往提示词里补了两样东西：一组路由规则，以及一个退款上限的交叉引用。补完之后，Sonnet 五点在同样成本下回到了百分之九十八点九。

最后，在这批搜索从来没见过的十四个留出工单上，最终的配置拿到了百分之九十点五，而最初的配置是百分之七十八点六，成本大约是原来的五分之一。

我觉得这个例子的价值在于它展示了一个完整闭环：不是换个模型就完事，而是降配、观察失败、从失败里读出缺失的规则、补进提示词、再验证。准确率和成本在这里不是二选一，而是同一个动作的两个结果。

第三个命令是 cost-optimize，用来做整体成本审计。它的第一步是搞清楚你的 token 到底花在哪里。它有三种取数方式：如果你有 Claude Admin API 的密钥，就从组织的用量和成本报告里读；如果你的应用记录了每次 API 响应里的 usage 对象，就从那里读；如果两个都没有，它就去读你构建请求的代码，然后估算。

拿到数据之后，它会按优先级排序各种节省手段：先看提示缓存，然后是精简每个请求携带的内容，这里就包含了一次 prompt-audit，接着是给输出加上边界，最后是把不需要人盯着的工作走批处理。如果你额外提供了一份评估集，它还会进一步算出在不同 effort 和不同模型选择下的成本和性能。

文章在四个公开基准上跑了这个命令，我快速过一下结果。

第一个，LegalBench，成本降低约百分之五十八。cost-optimize 提出的方案是：把跨任务共享的前缀缓存起来、设置低 effort、把任务走批处理 API。思考 token 从十万二千七百七十九个降到八千二百八十四个，通过率在噪声范围内，成本降了大约百分之五十八。

第二个，tau2-bench 的零售场景，成本降低约百分之七十三。做法是实施提示缓存并显式放置缓存断点，通过率保持平稳，支出降了百分之七十三。这个数字我觉得很震撼，一个纯粹的缓存配置动作就能省掉将近四分之三。

第三个，OfficeQA Pro，成本降低约百分之五十二。加上了批处理和文档缓存，成本从一百三十六点二美元降到六十四点八七美元。

第四个，SWE-bench Verified，成本降低约百分之五十五。这个案例里，cost-optimize 发现默认配置其实已经缓存正确了，所以省下来的钱来自另外两个动作：把 effort 设成中等，以及把 agent 的输出限制到几句话。结果是每个任务的中位步数从二十九步降到十七步，提示 token 从七千五百二十万降到三千三百七十万。

好，讲完三个工具，我们来聊对听众的实际工作意味着什么，也就是怎么上手、怎么用、要避什么坑。

我先给一个我认为最合理的落地顺序。第一步，如果你最近刚做过模型升级，先跑 prompt-audit。它的门槛最低，风险也最小，因为清掉的都是那些你早就不需要的补丁。而且实验数据告诉我们它不是零和：成本降百分之十四点六的同时准确率涨百分之五点三。这一步的直接收益往往比你想象的大，因为反模式是长期积累出来的，很多人根本不知道自己的提示词里已经堆了这么多层。

第二步，检查你的缓存配置。我建议你重点看三件事。一是你的系统提示里有没有动态内容，尤其是时间戳、请求 ID、用户 ID 这类。二是你的工具定义是不是稳定顺序。三是你的 agent 里有没有超过五分钟的阻塞调用。这三条查完，你的缓存命中率通常会有明显变化。记得去 Claude Console 看缓存诊断，别靠猜。

第三步，用 hillclimb 做参数搜索，前提是你得有一份评估集。如果你现在还没有评估集，我个人认为这是你最该先补的东西。因为文章里所有省钱的操作，最后都要靠评估来验证"我确实没有牺牲性能"。没有评估，你就不敢把 effort 调低，也不敢换小模型，所有节省都只能停在纸面上。

第四步，如果要做全面审计，用 cost-optimize。它会给出一份优先级列表，你可以按投入产出比一项一项落地。

然后我想说几个要避开的坑。

第一个坑，把缓存当成免费的午餐。文章讲得很清楚，缓存写入是要钱的，一点二五倍，一小时缓存是两倍。所以如果一段前缀你只用一次，缓存反而更贵。缓存的前提是复用，用得越频繁越划算。

第二个坑，改 effort 不检查缓存。除了 Opus 五和 Fable 五点一，其他模型上中途改 effort 会破缓存。如果你的应用里有动态调节 effort 的逻辑，这一点务必确认清楚。

第三个坑，把提示词当成只增不减的仓库。文章里那句"提示词会积累各种打补丁的指令"特别值得记住。每次模型升级，都应该重新审视一遍你的提示词，问自己：这条指令是在补哪个旧模型的短板？新模型还需要它吗？很多时候答案是不需要了。

第四个坑，在同一个模型上死磕 effort。文章给的洞见是，跨模型的成本性能结构可能比 effort 的调节空间更大。一个新一代模型的低 effort，可能同时赢过上一代的高 effort 在成本和效果两个维度上。所以每次有新模型出来，值得重新跑一遍搜索，而不是在旧模型上继续微调。

第五个坑，也是我觉得最隐蔽的一个，是那些"看起来完整"的答案。低 effort 和过时脚手架都可能让模型给出一个看起来没问题、实际建立在部分信息上的结果。这类问题的对策只有一个，就是你得有一个能测出问题的评估集，而且要定期看失败的样例，就像 hillclimb 做的那样。我个人认为，读失败样例这个动作，是这篇文章里所有技巧中门槛最低、收益最高的一个。

最后我来总结一下全篇。

这篇文章的核心主张是：性能和成本在很多情况下不是取舍关系，而是配置问题。它给出三个杠杆。第一，把提示缓存用对，注意它绑定模型、要求字节精确、有存活时间这三个约束，同时用监控、延迟加载工具、断点自动移动、缓存预热这些手段主动管理它。第二，清理提示词里针对旧模型写的反模式，验证仪式、强调增强器、强制流程、过时示例、矛盾规则、过时配置这六类，清掉它们既省钱又提准确率，实验数据是成本降百分之十四点六、准确率涨百分之五点三。第三，把 effort 校准到任务，别默认越高越好，也别一味图便宜，而是用更强模型加更低 effort 的组合去替换弱模型加高 effort，并且在评估曲线上找到那个拐点。

我个人认为这篇文章最有价值的地方，不是它给了几个具体技巧，而是它把"降本"这件事从一种牺牲叙事，变成了一种可测量、可搜索、可验证的工程流程。prompt-audit 负责清理历史包袱，hillclimb 负责在成本性能空间里做搜索，cost-optimize 负责做全局审计，这三个命令合起来，其实是在说：你不该靠感觉来调这些参数，你该靠评估数据。

如果这期节目只能让你带走一句话，我希望是这一句：先去跑一遍 prompt-audit，再去看看你的缓存诊断，然后给你自己搭一个哪怕很小的评估集。这三步做完，你大概率会发现，账单上有一大块钱，本来就不该花。我们下期再见。
