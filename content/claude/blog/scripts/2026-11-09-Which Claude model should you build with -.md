欢迎收听 Claude FM。今天这篇文章值得听，不是因为它给模型排了一张座次表，而是因为它把一个工程问题讲得很具体。你到底应该给什么任务配什么模型，什么时候增加思考时间，什么时候换模型，以及为什么看起来更复杂的多模型系统，最后反而可能更贵。

如果你正在维护一个编码助手，或者准备把智能体接进业务流程，这些问题都会变成真实账单。所谓智能体，也就是能持续调用工具、根据结果推进工作的 agent。它不是回答一次就结束，而是可能读文件、执行测试、修改代码，再根据报错继续行动。模型选择的影响，会在这个循环里不断放大。

先把文章的背景交代清楚。它描述的 Claude 通用可用产品线，有 Haiku 五点五、Sonnet 五点五、Opus 五点五，以及 Fable 五点二。另外还有面向网络安全和生命科学研究的 Mythos 五点二，但需要通过验证项目获得访问，不属于这里日常选型的主要范围。

文章面对的行业状态，是模型已经不只有能力档位，还叠加了推理强度、缓存、工具调用、子智能体和执行模式。同一个模型，你让它快速处理，和让它反复检查，成本与效果可能差很多。于是，选型号已经不是单独一道题，而是系统配置的一部分。

作者给出的起点很明确。大多数编码和知识工作，先用 Opus 五点五，推理强度设为 medium，也就是中等。这也是文章所说的 Claude Code 默认选择。这里不是说它每项任务都最划算，而是当你还不了解任务难度时，它是能力和成本之间比较稳妥的出发点。

围绕这个起点，任务边界清楚、难度较低，就往 Sonnet 五点五移动。分类、路由、标签、字段提取这些简单但量大的工作，再往 Haiku 五点五移动。遇到最难的技术项目，或者 Opus 在 high，也就是高推理强度下仍然做不好，再考虑 Fable 五点二。

但你千万别把它理解成，看见需求文档就用 Sonnet，看见复杂描述就用 Fable。文章特别提醒，规格明确，不代表任务简单。比如数据库迁移，验收条件可以写得很清楚，但历史兼容、线上流量、数据一致性，依然可能让它成为高难度工作。

我个人认为，这里最好区分两个维度。一个是目标清不清楚，另一个是实现过程难不难。把页面上的按钮换个颜色，目标明确，过程也简单。把支付系统迁移到新账本，目标同样明确，可过程可能横跨多个服务，不能因为有文档就自动降档。

如果你做的是日常调试、跨多个代码变更的功能开发，文章建议从 Opus 中等强度开始，必要时再提高。范围明确的修复和功能迭代，可以从 Sonnet 中等强度开始。聊天和交互式应用，则适合先试 Sonnet 的低强度或中等强度，因为用户正在等，延迟本身就是体验的一部分。

普通文档、幻灯片、电子表格，也可以从 Sonnet 开始。但复杂财务模型，或者需要综合大量来源的文档，作者建议起步用 Opus。大量截图和图像驱动的电脑操作，也推荐 Opus，因为这种工作往往不是看懂一张图，而是连续很多轮观察和行动。

至于大型重构、重大迁移、架构规划，以及带领很多子智能体，文章更倾向于 Fable。深度研究、科学和定量分析，也在这个范围。不过这里的推荐是起始配置，不是质量保证。原文并没有说，只要切到更大的模型，你的迁移方案就自动正确。

接下来我们讲最容易误判的一件事，价格。这里会出现 token，可以理解成模型处理文本时使用的计量单位，它并不直接等于一个汉字。文章给出的都是接口标价，以每百万 token 计算，而且输入和输出分别收费。

Sonnet 五点五的输入是两美元，输出十美元。Opus 五点五分别是四美元和二十美元。Fable 五点二分别是八美元和四十美元。也就是说，按普通输入输出单价看，Sonnet 是 Opus 的一半，Opus 又是 Fable 的一半。

Haiku 要多看一道条件。提示长度不超过十万 token 时，输入是零点一美元，输出零点五美元。超过十万以后，分别变成零点五美元和二点五美元，是原来费率的五倍。注意，这是跨过提示长度门槛后的档位变化，不能一直拿短提示价格估算长文档工作。

听到这里，你可能会想，那只要能用 Haiku，就尽量用 Haiku。问题是，单价衡量的是模型读写的价格，不是完成工作的价格。一个便宜模型如果要尝试很多轮，还不断把主流程带偏，最终任务成本可能并不便宜。

文章用两个测试说明，这种关系甚至会反过来。在 Terminal Bench 三点零上，上一代 Fable 五点一使用最高强度，得分百分之五十八。Opus 五点五使用高强度，得分百分之五十八点九，使用的 token 只有前者一半。这里比较的 Fable 是五点一，不要和当前五点二混在一起。

另一个是 FrontierCode 二点零。Fable 五点二高强度，和 Opus 五点五最高强度，得分分别约为百分之四十五点三、百分之四十五点五，接近打平，但 Fable 每个任务的成本大约只有一半。所以，更贵的模型，确实可能更便宜地完成某些难题。

这些数字不意味着你应该把所有请求切到 Fable。它们说明的是，当你不断给较小模型追加思考预算时，应该停下来问一句，现在是不是换模型更划算？文章建议，Opus 超过高强度之前，先测一下较低强度的 Fable，而不是沿着同一条路无限加码。

还有一个很实用的提醒，评估成本时别只看普通任务。原文提到，一个二十道题的搜索测试里，两道题贡献了百分之四十三的支出。假设你的产品每天处理一千个请求，大多数几秒完成，少数却来回搜索几十轮，那些少数请求就可能决定你的利润空间。

我个人认为，这跟线上服务治理很像。平均响应时间很好看，不代表长尾没有问题。模型账单也有长尾，你应该知道最贵的请求为什么贵，是材料太多，工具一直失败，还是模型始终找不到结束条件。只优化平均输入长度，未必能碰到真正的成本中心。

再往下，文章提出一个比换模型更细的旋钮，就是 effort，推理强度。你可以把它理解成允许模型投入多少思考和检查。但它不是知识充值，也不是能力下载。让一个模型思考更久，不能凭空获得它本来没有的技能。

提高强度，通常有助于需要长时间推理、更多工具调用或自我检查的工作，同时也会增加等待时间。文章给了 Opus 在 SWE bench Pro 上的一组对照。中等强度比高强度低大约二点五个百分点，成本大约是高强度的百分之七十。

低强度大约少八个百分点，成本大约只有三分之一。再从高强度提高到额外高强度，分数大约增加一点四个百分点，但成本达到高强度的二点五倍。这不是一条均匀上升的直线，越到后面，额外效果可能越贵。

把它放到工作里想。你让模型给内部日志加一个筛选条件，愿不愿意为了很小的成功率提升，多花一倍以上成本，还多等一段时间？可能不愿意。但如果在改一个高风险的结算逻辑，你可能会接受。前提是你真的测过，而不是把高强度当成安全感按钮。

这里还有默认值的坑。Sonnet 在接口上的默认强度是高，在 Claude Code 中是中等。Fable 也有类似差异，接口默认高，Claude Code 中默认中等。所以你说我们都用了默认配置，可能根本不是同一组实验。做比较时，要记录实际模型和实际强度。

不过文章建议的第一步，甚至不是提高强度，而是先给模型验证自己的办法。测试、构建，或者一个能调用目标接口的脚本，都比空泛地说请认真检查更有用。原因很简单，认真是一种要求，测试结果才是反馈。

比如你让模型修复一个日期解析问题，只告诉它用户说时区不对，它只能从代码里猜。你如果给出失败样例、预期时间和可运行测试，它就可以提出修改、执行测试，再根据结果修正。这里增加的不是模型体量，而是任务闭环的信息质量。

原文给出的顺序是，先检查能不能自我验证，再把强度提高一级，之后才升级模型，并从比原来更低的强度试起。这条顺序很值得写进团队操作习惯。否则大家一遇到失败就升级模型，可能只是在用更贵的推理补一个缺失的测试脚本。

如果结果能自动检查，还可以先低强度执行，只把失败任务交给高强度重跑。文章在同一个 SWE bench Pro 子集上的实验显示，这种做法通过约百分之九十七的任务，每个任务约零点一七美元。全部使用高强度，通过率约百分之九十五点三，每个任务约零点二九美元。

这里我想强调实验边界。这是文章提供的特定子集结果，不是所有任务都会获得同样收益。而且分流成立的前提是，你能识别失败。测试没覆盖的逻辑错误，不会因为测试通过就消失。对于没有可靠验收器的开放式报告，低强度失败再升级，往往没这么容易实现。

如果你需要的是同等能力下更快响应，Opus 和 Fable 还有付费快速模式。那是用更高价格购买输出速度，不是降低推理要求。文章也提到新一代模型可能更快，但我们做产品时仍要区分生成速度和完整任务耗时，后者还包括工具等待、重试和验证。

说到长任务，就要聊上下文。文章里的四个模型，都有一百万 token 的上下文窗口，最大输出都是十二万八千 token。上下文窗口，可以理解成一次工作时能摆在桌面上的资料容量。桌子大，是能放下更多东西，不代表每次都应该把仓库搬上来。

因为对话每进行一轮，上下文都要再次提交。长流程中，大部分重复输入可以按缓存读取计费，确实会便宜不少，但不是免费。Opus 每百万 token 缓存读取零点二美元，Sonnet 零点一美元，Fable 也是零点二美元。

这就出现一个有意思的变化。Fable 普通输入输出是 Opus 的两倍，但缓存读取价格相同。因此，在缓存占比很高的长任务里，它们的整体成本差距会缩小。真正拉开差距的是没有缓存的输入和新生成的输出，不能把整张账单直接乘二。

文章举例，Opus 读取十五万 token 的缓存，一轮大约三美分。两万 token 则大约零点四美分。一次看着很小，但如果一个流程跑很多轮，又有很多并发任务，这些重复读取就会累积。所以主模型越贵，越应该保护它的上下文，让它主要接触决策需要的信息。

我的理解是，别让架构负责人每天把所有原始日志重新读一遍。可以让较便宜的助手先整理出失败位置、关键错误和证据，再让主模型决定下一步。但摘要不能只给结论，最好保留定位依据，否则主模型没办法核查，也就容易被错误摘要带着走。

切换模型也有隐藏成本。文章明确说，提示缓存属于写入它的模型。你换到另一个模型，不能指望直接继承原模型的缓存优惠，新模型的第一轮会对整段会话支付缓存写入成本。

因此，不要为了省单价，在同一段很长的历史里来回切换。Claude Code 可以先压缩上下文，再换模型。自己写接口应用，可以用简短的工作摘要开启新模型会话。摘要里说明目标、已完成事项、证据位置、未解决问题，而不是机械转发全部历史。

还有一种比账单更隐蔽的损失，叫推理过程丢失。文章说，不同模型能读取的历史思考块并不相同。大体上，向下切换不会继承上层模型的思考，但也不是所有向上切换都天然兼容。

具体到这代产品，Opus 可以读取 Sonnet 和 Haiku 的思考块，Sonnet 可以读取 Haiku 的，Fable 五点二可以读取这三者的。但从 Fable 五点二切换到其他通用可用模型，它的思考会被丢弃。接口可能仍然成功，新的模型却已经失去那段推理。

所以，不能用请求没报错证明交接完整。我个人建议把模型交接看成工程交接，明确写下已经验证了什么、还在怀疑什么，以及下一步为什么这么做。不要假定换班的人看到了上一位同事脑子里的全部过程。

再来说多模型协作。文章区分了几种模式，最实用的是子智能体。子智能体有自己的上下文窗口，做完独立小任务，再把摘要交给主模型。它消耗多少 token，就按它自己使用的模型收费。

文章举的例子是日志阅读助手。你可以让 Haiku 读取测试输出，逐项报告失败文件、测试名称和第一条错误，不允许编辑文件。这个任务边界很窄，结果容易核查，正适合便宜模型。主模型继续负责代码修改和判断。

这不是简单的把脏活累活全扔出去，而是按错误代价分工。找错一个文件，一般容易发现；误判一次权限模型，可能把整个实现带偏。但即便是搜索错误，也不是零成本，主模型可能打开错误文件，继续浪费上下文和时间。所以子任务仍然需要清晰的输出契约。

还有一个配置细节值得注意。文章说，当前 Claude Code 内置的 Explore 探索子智能体，已经不是永远跑在 Haiku 上，而是跟随会话模型，接口场景还有相应上限。想让探索保持便宜，需要自己显式配置，而不是凭过去的印象估算费用。

模型别名也不一定跨平台一致。文章里，Anthropic 接口上的 haiku 别名已经指向五点五，并要求相应的新版本 Claude Code。但在部分其他云平台上，仍然指向四点五。你配置文件写的是同一个词，实际运行的可能是不同一代模型。

另一种是先规划、再执行。Claude Code 的 opusplan 别名，会让 Opus 制订计划，再由 Sonnet 执行。听起来很合理，但作者提醒，这和文章建议的分工方向不同。文章更倾向于让主模型保留代码修改，把容易检查的边缘工作交给小模型。到底哪种好，要在自己任务上测。

还有顾问工具，目前是测试阶段。它让便宜一些的执行模型干活，遇到困难再咨询更强的顾问模型。这里最大的限制是，执行者得先意识到自己需要帮助，而且真的发起咨询。低强度时，它可能更少求助。系统里有专家，不等于专家参与了关键决策。

文章对这种模式相当谨慎。成本指南里列出的四种配对，没有一种明确胜过单独执行模型。有一组内部编码测试，Opus 高强度配 Fable 五点一顾问，分数约百分之九十点一，比单独 Opus 高一点七个百分点，但费用约为二点一倍，收益接近多次运行波动的边缘。

因此，我个人认为，顾问架构不要先拿来做技术展示，再倒推业务价值。先看咨询率，看看咨询发生在哪类失败之前，有没有真的改变结果。否则你增加的是系统复杂度和账单，不一定增加有效能力。

再大一层，是多个工作者并行处理超出一个上下文的大任务。文章给出内部缺陷搜索实验，代码总量约两千二百万 token。Opus 带领 Sonnet 工作者，最多同时二十五个，效果与单独 Opus 默认强度相近，成本低约三分之一。

它适合能拆分、能并行、最后能合并的工作。比如不同模块各自检查，再集中审查候选问题。但如果是一条紧密依赖的操作链，后一步必须等待前一步，或者任务本来就放得进一个上下文，规划、派发和合并反而可能更贵。多个智能体，不是多开几个线程就一定加速。

接下来聊接口工程。这篇文章很有价值的一点，是没有把模型切换写成改一个名字那么简单。所有当前模型都支持工具和图像输入，但请求限制不同。你如果真的做动态路由，应该先把这些差异收敛掉。

比如 Fable 五点二保留思考时，如果你修改了思考块之前的系统提示、工具定义或者早期消息，接口可能返回四百错误，除非明确选择丢弃受影响的思考。自己拼装历史的应用，尤其要注意只追加、不随意改写。使用文章列出的官方代理工具链，则不需要自己处理同样的改动。

再比如 Opus 和 Fable 的思考始终开启，不能发送关闭思考的请求。Sonnet 默认思考，也支持只在工具调用之间思考的模式。Haiku 在高强度及以下可以关闭。读取响应时，要按内容块类型处理，不能假定第一块一定是给用户看的正文。

强制工具调用也有兼容性差异。文章说，Sonnet、Opus 和 Fable 不接受某些强制指定工具的设置，会报四百错误。建议采用自动工具选择，配合严格的工具定义，再在提示里明确什么时候调用。不要以为旧模型接受的请求，新模型也一定接受。

从 Haiku 四点五迁移到五点五，还要把旧的思考预算参数换成推理强度，去掉不被支持的非默认采样设置，并让消息以用户轮次结束。电脑操作工具也有指定版本限制。这些细节最好变成接口契约测试，而不是上线后靠用户报错发现。

文章还提醒安全回退。某些被安全分类器标记的网络安全或生物学请求，在 Claude Code 里可能改由旧模型重跑，记录会说明实际使用了哪个模型。因此，你分析效果和成本时，也要记录真正执行的模型，不能只看最初请求的型号。

如果一个系统要支持多个模型，原文建议按最严格的共同约束构建请求。历史只追加，工具使用自动选择并严格定义，内容按类型解析，提示和工具描述写得足够准确。路由规则如果很简单，比如日志归 Haiku、主流程归 Opus，就让代码选择，不要再请一个模型来猜。

最后，把这些建议收敛成你下周就能做的实验。我个人建议，先不要重构整个智能体框架，先从真实积压任务里抽样。既要有普通修复，也要有跨模块修改和曾经失败的难题。每个任务提前写清验收方式，避免看见答案以后再调整标准。

能用测试验收的，就保存测试结果。数据提取任务可以核对字段和行数。文档任务则需要事先明确必须覆盖的事实和人工审查规则。不同任务允许不同验收方式，但不能只有模型自称完成。否则你比较的只是表达自信程度，不是工作结果。

然后为候选模型选两到三个推理强度，各自在独立会话里运行，避免共享缓存影响对比。从每次响应的用量信息记录成本，并累计工具调用、失败尝试和最终交付。除了钱，我个人建议也记录完成时间与人工介入，因为便宜但需要人持续救场的配置，未必适合生产。

把结果画成效果和支出的关系图。文章提出一个很好的标准，多模型组合只有在超过所有单模型方案时，才值得保留。如果一个复杂路由系统，只是打平一个简单模型配置，你就需要认真问，维护它的价值在哪里。

还可以专门做一次长尾复盘。把最贵的一批任务拿出来，看它们是否集中在长上下文、无效搜索、反复重试或者错误的任务拆分。别急着统一降模型。有时删掉重复材料，补一个验证脚本，比更换整套模型架构有效得多。这是我的实践推演，不是原文额外报告的实验结果。

选出暂时胜出的方案后，文章建议先在部分真实流量上影子运行，再正式切换。也就是让新方案处理同样的输入，但先不直接影响用户结果，观察真实分布里有没有评测集没覆盖的问题。模型别名、平台版本、缓存状态和实际回退，都应该一起留档。

今天这篇文章的核心，不是记住哪一个型号永远最好，而是把单价、推理强度、验证能力和协作方式，统一放到完成一个可靠任务的成本里比较。我个人认为，最值得带走的顺序是，先让结果可验证，再调整思考投入，最后才升级模型和架构。真正成熟的模型选型，不是把最强模型放到所有地方，而是知道每一份额外成本，究竟买到了什么。
