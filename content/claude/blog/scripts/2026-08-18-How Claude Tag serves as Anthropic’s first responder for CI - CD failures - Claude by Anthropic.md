文章开头讲了一个很工程师的场景。Anthropic 的一位持续集成团队工程师晚上十点值班，同事在 Slack 上找他，说一个新服务大概有四十四个测试没有触发。放在过去，他就得停下手里的事，打开电脑，叹口气，然后开始一小时左右的调查和修复流程。这个画面很多听众应该很熟。你可能刚准备睡，或者刚把孩子哄好，或者只是想看个电影，结果手机一震，CI 出问题了。麻烦还不一定是大事故，但你必须先判断它到底是不是大事故。

但这一次，他的工作流变了。他把 Claude 拉进来，问它看到了什么。Claude 查出来，这些测试是在当天早上某个 feature flag，也就是功能开关打开之后消失的，而且回滚这个开关是安全的。于是工程师让同事回滚。三分钟后，Claude 又在 Slack 上提醒他，确认跳过测试的规则确实被移除了，错误率也回到了基线水平。你看，这里 Claude 做的不是炫技式的代码生成，而是一个很朴素但非常有价值的动作，先查证据，给假设，建议低风险动作，然后继续验证结果。

文章说，过去几个月里，Claude Tag 已经在 Anthropic 内部担任 CI 和 CD 故障的 on-call 第一响应者。on-call 可以理解为值班响应，尤其是线上系统和研发基础设施出问题时，第一个需要被叫起来的人。所谓第一响应者，并不是说 Claude 完全取代工程师，而是说每次事故发生后，它会立刻进场，先读上下文、看告警、查指标、翻日志、写第一份态势报告。原文给了一个非常关键的数字，最近有态势报告的事故里，第一份报告都是 Claude 写的，通常在十五分钟内发布第一轮分析。

我们先把背景拉开一点。CI 和 CD，也就是持续集成和持续交付，是现代软件团队的血管。开发者写代码、提 PR、跑测试、进合并队列、触发构建、部署到环境，这一串看起来平常，实际上任何一个环节堵住都会影响整个组织的交付速度。尤其在 AI 编程工具普及之后，代码产出速度提高了，PR 数量变多了，构建和测试压力也随之变大。Anthropic 在文末提到，他们的软件工程师平均每个季度交付的代码量，已经是二〇二一年到二〇二五年期间的八倍。这个数字很惊人，也解释了为什么他们会说，如果进入 agentic coding，也就是智能体辅助编码的阶段，那么 CI 也必须进入 agentic CI，也就是智能体辅助的持续集成。

传统值班的问题在哪里呢？第一是检测很难。人类很难提前设计出完美的规则和阈值。比如你给某个服务设置错误率超过百分之二就报警，听起来合理，但如果这个服务刚上线，没有足够流量，你根本不知道百分之二是不是正常波动。再比如某个测试套件偶尔慢十分钟，是不是事故？某个队列积压翻倍，是不是事故？如果规则太宽，就会漏报；如果规则太窄，就会把值班工程师淹没在噪音里。第二是告警疲劳。每一条告警都要看、要判断、要排除，人的注意力是会耗尽的。很多真正的事故不是没人报警，而是报警太多，大家开始默认它不重要。

Anthropic 的思路是，让 Claude 先站在这个入口处。文章给出了他们这套 on-call agent 的四个核心要素。一个是记忆，它要记得事故里已经做过什么，不要每轮对话都从零开始。一个是连接和访问权限，它要能调查、理解，必要时也能采取行动。一个是调度，它要知道什么时候回来继续检查，什么时候生成交接报告。还有一个是指令，它要知道遇到不同类型的事该怎么做，哪些可以等到早上，哪些必须立刻叫醒人类。你会发现，这四个词其实很像一个真实值班工程师的能力模型。一个人值班，不只是聪明就行，他还得知道系统历史，有账号权限，能按时巡检，熟悉团队流程。

这里的主角叫 Claude Tag。你可以把它理解成 Claude 在 Slack 工作区里的一个可被提及、可加入频道、可读取上下文的协作入口。Anthropic 把 Claude Tag 放进了 on-call Slack 频道，让它保留频道里的记忆，也让团队在事故过程中可以逐轮给它指令。Claude 还会实时响应 on-call 频道和其他相关频道里的事件。文章里有一个有意思的细节，例行任务也可以在频道里用自然语言安排，比如每周一美国东部时间早上九点运行 CI 交接。也就是说，它不只是聊天机器人，它有一点像住在团队 Slack 里的值班助理。

当然，光住在 Slack 里不够。Claude Tag 有自己的服务账号，并且能访问 Anthropic CI 工程师需要的一些工具，比如 Datadog、Grafana 这些监控和可观测性工具。管理员会一次性给频道配置好这些访问权限。除了 on-call 频道，他们还会让 Claude 关注其他相关频道，只要这些频道里也有 Claude Tag。这样 Claude 可以获得额外上下文，比如服务告警、配置变更、PR 更新。你可以想象一下，如果一个人排查事故，常常要在五六个系统之间来回切。告警在一个频道，部署通知在另一个频道，PR 讨论在 GitHub，指标在 Grafana，日志在日志系统，集群状态在 Kubernetes。Claude 的价值之一，就是把这些分散的信息拉到同一条调查链路里。

长期指令则放在 markdown 文件里，文章把它们称为 skills，也就是技能。这些文件提交在 GitHub 仓库里，团队成员可以像改代码一样一起迭代它们，也能审查历史变更。里面会包括路由指令、政策、事故经验教训等。这里有两个文件特别关键，一个是 oncall.md，它像值班总手册，告诉 Claude 什么情况要升级，什么情况可以记录，什么流程要遵守。另一个是 lessons.md，它像一本不断增长的事故笔记，记录每次事故发生了什么，根因是什么，修复方式是什么，还有下次要记住的坑。这个设计很重要，因为很多 AI 应用失败不是模型不够强，而是组织知识没有结构化地喂给它。

文章还提到，他们把这套方案整理成了一个通用的 on-call setup kit，也就是值班配置工具包，可以把团队自己的事故历史转化成分诊剧本，最后得到一个只读的 Claude，放在事故频道里做诊断、升级和学习。这里要注意，原文说这套初始搭建花的是几个小时，不是几天。但这并不意味着所有团队都能半天建出 Anthropic 同款效果。它的前提是你有 Claude Team 或 Claude Enterprise 计划，组织 owner 能把 Claude 通过 Claude Tag 加进 on-call Slack 频道，还要帮忙连接合适的工具、GitHub 仓库，并配置 Claude Code Remote。换句话说，这不是一个随便复制 prompt 就能跑的玩具，它需要组织级权限、工具连接和流程共识。

接下来我们看事故流程的第一步，检测。文章说，Claude 不只是改变事故响应，也改变事故检测。对于新服务，Anthropic 会让 Claude 分析前几天的数据和进来的告警，建议增加哪些规则，或者微调那些过宽、过窄的规则。这件事听起来简单，其实很实用。很多团队上线一个新服务时，监控阈值都是拍脑袋定的。QPS 多少算异常，延迟多高算异常，错误率连续多久算异常，通常要等被打疼几次才知道。Claude 可以先看数据分布和告警情况，给出更贴近实际的建议，至少帮你减少明显不合理的阈值。

然后是告警过滤。Claude 会监控每个告警频道里的相关告警，并按照 oncall.md 里的标准判断，这个告警能不能等到早上，还是必须现在 page on-call，也就是呼叫值班人员。原文举了一个规则例子。如果错误率超过百分之二并持续超过五分钟，而且当前不是已知部署窗口，就呼叫值班；否则，把它写入 lessons.md。这个例子很能说明 Anthropic 的态度。告警判断本身仍然可以是确定性的，规则很清楚，阈值、持续时间、部署窗口都有条件。但是否升级到事故、如何补充上下文、如何解释，里面又有 agentic 的路径，也就是智能体根据上下文进行判断和行动。

除了自动告警，Claude on-call 还有另外两个触发入口。一个是 CI 团队成员直接在 on-call 频道里报告问题，就像开头那个四十四个测试没有触发的例子。另一个是公司任何人可以通过内部页面打开一个事故，如果被标记为 CI 基础设施事故，那么系统会为这个事故创建一个 Slack 频道，然后 on-call Claude 会接手关注。这里的设计很像现代事故管理的标准流程。你既要有机器触发，也要允许人类报告。因为很多问题最早不是监控发现的，而是某个开发者说，咦，我的 PR 怎么一直卡着。

真正节省时间的部分在调查。原文给了两个数字，Claude 在事故打开后，发布第一份基于证据的分析的中位数是十四分钟；最快的情况下，它在第一份报告里四分钟就指出了根因。这里我们要小心，不要把它理解成所有事故四分钟搞定。文章说的是最快情况下，而且是第一份报告里命名根因。但即便是十四分钟的中位数，也已经很有意义。很多团队的事故前十五分钟都在问，谁在线，谁知道这个系统，最近有人发版吗，有没有 dashboard，日志去哪看。Claude 如果能在这十五分钟里先把证据链铺出来，值班工程师的压力会明显降低。

它是怎么调查的呢？Claude Tag 会启动一个动态工作流，其中有一个 orchestration agent，也就是编排智能体，再拉起多个 executor subagents，也就是执行子智能体。编排智能体负责拆任务、汇总结果、写成 coherent SITREP，也就是连贯的态势报告。执行子智能体则分别调查每个依赖和事实来源。Anthropic 这里列出的来源包括 Grafana、日志存储、PagerDuty、GitHub、Kubernetes 和 Slack 事故频道，这些都通过 MCP Connectors 连接起来。MCP 可以理解为模型上下文协议相关的连接器，让 Claude 能用统一方式访问外部工具。

这个并行调查非常关键。人类排查事故时，常常是串行的。先看 dashboard，发现错误率上升，再去查日志，看到某个错误码，再去 GitHub 看最近合并，再去 Slack 问是不是有人改配置，再回 Grafana 看时间线。每一步都要切换上下文。Claude 可以让不同执行者同时追多条线索。一个去查指标，一个去查日志，一个看最近 PR，一个看部署窗口，一个看 Kubernetes 状态。最后由编排者把结果合成一份态势报告。原文说这有助于降低 MTTR，也就是 mean time to resolution，平均修复时间。对工程组织来说，MTTR 降低往往比完全避免事故更现实，因为复杂系统不可能永远不坏，但可以让它坏得更短、更可控。

不过，Claude 不是盲搜。文章特别强调，编排者和执行者会被 investigation skill，也就是调查技能引导。对于每类 bug，会有更详细的参考 markdown 文件。作者举了一个例子，针对 shadow divergence bugs，也就是影子系统或影子执行结果出现分歧的 bug，他们有一个六百一十七行的调查技能，编码了作者在典型调查中会执行的每一步。这个技能是怎么来的呢？作者在一次事故中和 Claude 一轮一轮排障，事后让 Claude 根据这次经验生成了文件。这个做法对我们很有启发。不要幻想第一天就写出完美手册。更自然的方式是，让 AI 陪你排一次真实事故，然后把这次排查路径沉淀成下一次可复用的 playbook。

lessons.md 也参与排障。文章说这是一个持续日志，记录他们解决过的每一次事故，包括发生了什么、根因、修复方式、值得记住的坑。Claude 会自动往里面追加内容。每次新的调查开始时，Claude 会先读它，所以第一轮假设会从最近发生过的事情出发。如果同样模式出现足够多次，他们就把它提升进正式的调查技能里。这里很像一个团队从经验到制度的过程。偶发一次的坑先写进经验本，反复出现的模式再变成标准流程。很多公司事故复盘写得很漂亮，但写完就放在文档系统里吃灰。Anthropic 的做法是让 Claude 每次调查前都读这些经验，这样复盘才真的参与下一次响应。

原文里作者最喜欢的一条 lessons.md，是 Claude 写给他的。作者曾经在检查指标之前，根据一个配置文件做了假设。后来 lessons.md 里写下了一句话，我翻译一下，先查询数据，再提出理论。配置告诉你什么可能出错，指标告诉你什么真的出错了。这句话我个人非常喜欢。工程排障里最常见的错误之一，就是看到一个可疑配置，脑子里立刻开始讲故事。但系统真实发生了什么，必须用指标、日志、时间线来确认。AI 如果只是帮你更快地编故事，那很危险；但如果它被训练成先找证据再给假设，那它就更像一个靠谱的同事。

当然，文章也很诚实地说，即使有这些工具和上下文，Claude 也不总是第一次就对。人类直觉和经验仍然重要。Claude Tag 支持团队以 multi-player mode，也就是多人协作模式来排障。任何人都可以实时引导调查，或者加入一个新的假设。这个点非常关键。Anthropic 描述的不是一个无人的值班系统，而是一个人机协作的值班频道。Claude 先做繁琐的信息收集和初步综合，人类再用经验判断它有没有漏掉隐含前提。你可以把它想象成事故现场来了一个非常勤快的初级工程师，能够同时打开十个系统查资料，而且写报告很快，但最后拍板的人仍然是资深工程师。

那 Claude 能不能修呢？文章的回答是，这要看团队如何设置边界。在 Anthropic 这个团队里，大多数部署都在 feature flag 后面。作者另外创建了一个 Claude Code 里的 agent，用的是作者自己的权限，可以围绕这些 feature flag 做渐进式部署。rollout 的第一阶段通常是让 Claude 管理 canary traffic，也就是金丝雀流量，监控问题，并自动把某个功能开关向上或向下调整。这里原文没有展开，作者说这可以单独写一篇文章。所以我们也不要脑补太多，只要抓住原则，它不是直接冲到生产环境随便改，而是在功能开关和金丝雀流量这种相对可控的机制里动作。

除了 feature flag，Claude Tag 还帮他们处理几类修复路径。比如告诉团队是否需要 drain 或 cordon Kubernetes 集群的某些部分。drain 可以理解为把节点上的工作负载排空，cordon 是把节点标记为不再调度新工作负载。再比如在需求突增时，Claude 会给出如何扩容部分基础设施的指令。文章说这种情况少见，但当 Claude 能准确返回缓解措施时非常有用。最常见的修复形式，则是 Claude 生成一个 PR，由 on-call 人员审查、合并，然后部署，以快速解决问题。注意这里仍然有人类 review、merge 和 deploy。原文强调他们质量门槛没有降低，每个 PR 都有明确的人类 owner，每个变更都需要批准才能合并，每个变更都经过同一套 CI gates。

修复之后，Claude 会用调查时用过的许多 MCP Connectors 和工具来验证修复是否按预期生效。比如回到监控看错误率是否回基线，检查测试跳过规则是否移除，确认部署状态是否正常。按照 oncall.md 里的长期指令，它还会把 post-mortem，也就是事后复盘，写入 lessons.md，并为交接态势报告提供内容。这个闭环非常重要。很多自动化只做到发现问题，或者只做到生成修复建议，但没有把验证和学习纳入流程。Anthropic 这篇文章的核心价值，恰恰在于它把检测、分诊、调查、修复建议、验证、复盘、交接都串起来了。

为了跨多个事故沟通全局状态，他们还做了一个叫 ci-weather 的 agent。这个名字很形象，像天气预报。它会汇总每个事故 Slack 频道、构建指标、合并队列统计、部署延迟等信息，然后在一个公司任何人都能看的公共频道里，发布 newsroom-style report，也就是新闻播报风格的状态报告。这样工程师想知道现在要不要暂缓合并，或者想问 CI 到底哪里不对，就不用一直 ping CI 团队，而是去看那个公共频道。对大组织来说，这种事故沟通本身就很耗时。很多时候值班人员不是在修系统，而是在反复回答相同问题，当前影响面是什么，预计什么时候恢复，我的 PR 要不要等。

文章也很诚实地补了一句，他们需要多次迭代报告格式。Claude 可以一次性生成一个产出状态报告的 skill，但让报告真正可读，靠的是团队特定的品味。原文说，这是人类沟通，不是管道工程。我个人认为这句话特别值得所有做 AI 内部工具的人记住。把数据拼出来不难，把它写成别人愿意读、读完知道该怎么办的信息，才是难点。不同团队对风险等级、语气、细节粒度的偏好都不一样。有的公司喜欢极简红黄绿状态，有的公司需要详细时间线，有的团队希望少用模糊词，有的团队更看重行动建议。这些都需要人类和 Claude 一起调。

除了 ci-weather，Claude 还会生成每日和每周总结，帮助团队交接。文章里说，他们希望每周一给人类产出 handoff reports，也就是交接报告，让团队成员可以从别人停下的地方继续。值班交接也是非常真实的痛点。很多事故不是一次性解决，而是有尾巴。某个临时缓解已经做了，但根因修复还没合并；某个指标恢复了，但还要观察二十四小时；某个告警被静音了，但要记得恢复。如果这些细节只在某个人脑子里，下一班接手就会很危险。Claude 的长期频道记忆和总结能力，在这里就特别适合承担整理工作。

现在我们把这篇文章的主线压缩一下。Anthropic 面对的问题不是单一 CI 故障，而是工程交付速度变快以后，研发基础设施的值班压力也快速上升。单靠人类 on-call，很容易陷入告警疲劳、夜间打扰、重复沟通和经验无法沉淀。Claude Tag 作为第一响应者，提供的是一个围绕 Slack 的事故协作层。它有记忆，有工具权限，有定时任务，有版本化的长期指令，能读事故历史，能并行调查多个事实来源，能写第一份态势报告，能在安全边界内提出或辅助修复，最后还能复盘和交接。

对我们这些软件工程师和 AI 从业者来说，这篇文章最实际的启发是什么？我个人认为，不要一上来就问，能不能让 AI 自动修生产。这个问题太大，也太容易引起组织阻力。更好的起点是，让 AI 做只读的第一响应者。你先把它放进事故频道，让它能读告警、读监控、读日志、读 GitHub、读部署通知，但不允许它写生产系统。它的任务是第一时间回答几个问题，发生了什么，影响范围是什么，最近有什么变化，最可能的根因有哪些，需要现在叫醒谁，哪些证据支持这个判断。光做到这一步，很多团队就已经能节省大量时间。

如果你真的要在自己的团队里落地，可以从三个文件开始。第一个是 oncall.md，写清楚升级规则、告警标准、服务负责人、常见系统入口、绝对不能做的事。比如什么条件下必须 page，人类审批前不能改哪些配置，哪些告警可以记录到早上处理。第二个是 investigation skills，按 bug 类型写排障路径。比如测试突然不跑、合并队列积压、构建缓存失效、某类 runner 容量不足、Kubernetes 节点异常。每一类都不需要一开始写得很完美，你可以先把资深工程师平时会查的 dashboard、日志查询方向、最近变更检查顺序写进去。第三个是 lessons.md，把每次事故复盘变成下一次 Claude 必读的记忆。

权限是第一个大坑。文章里的 Claude 有服务账号，连接了多个工具，但这背后一定有管理员配置和权限边界。你不能随便把一个全权限机器人放进生产环境，然后说它很聪明。实践上，我建议先读权限，再小范围写权限，再对写操作加人工审批。比如最早阶段只允许它读指标和日志。第二阶段允许它创建 GitHub issue 或草拟 PR。第三阶段才考虑在 feature flag、canary、扩容建议这些可控场景里让它参与动作。即便如此，也要有审计日志，有明确 owner，有回滚方案。Anthropic 的文章也没有说他们放弃人类审批，恰恰相反，他们强调每个 PR 仍然有人类 owner 和审批。

第二个坑是，不要把所有判断都交给大模型自由发挥。原文有一句非常关键，alerting process 是 deterministic，而 on-call escalation 有 deterministic 和 agentic 两种路径。翻成大白话就是，底层告警规则要尽量确定，什么时候错误率超过阈值，什么时候不在部署窗口，这些条件不能全靠模型即兴判断。但在理解上下文、综合多源证据、提出假设、决定是否需要更高等级响应时，可以让 agent 发挥。这个边界很重要。AI 运维不是把监控规则扔掉，而是在监控规则之上加一个会读上下文、会写报告、会追线索的层。

第三个坑是，事故经验必须被结构化。很多团队已经有事故复盘，但格式五花八门。有人写长篇故事，有人只写几行结论，有人把根因和修复混在一起。Claude 要想真正利用这些经验，最好让每次复盘都包含固定字段。发生了什么，用户或开发者影响是什么，开始时间和恢复时间是什么，根因是什么，缓解措施是什么，永久修复是什么，下次排查应该先看哪里，哪些假设被证明是错的。原文里 lessons.md 的价值就在这里，它不是给领导看的汇报材料，而是给下一次排障读的操作记忆。

第四个坑是，报告可读性需要调。Claude 写出来的状态报告，第一次可能很像流水账，要么太长，要么太自信，要么把关键行动埋在后面。你需要像 Anthropic 调 ci-weather 一样，多次调整团队喜欢的格式。比如开头先说当前状态，是否影响合并，是否建议暂停发版，下一次更新时间是什么。然后再说证据、假设、已采取动作、待办事项。对通勤路上的你来说，可以把它理解成一个事故版的产品化工作。不是有数据就完事，而是要让读者在三十秒内知道自己该不该行动。

我还想补充一个个人观察。Claude Tag 这类系统最先改变的，可能不是最难的根因分析，而是最烦的协作成本。比如夜里十点有人问，四十四个测试为什么没跑。真正耗人的不是每次都需要天才级推理，而是你要重新打开电脑，收集上下文，确认是不是 feature flag，确认能不能回滚，回滚后再看指标。Claude 把这些小而杂的动作串起来，就会明显改善值班体验。文章作者也说，Claude 吸收了他工作里乏味的部分、下班后的打扰和事故沟通，让他能把精力放在真正能提升系统可靠性的中长期架构改造上。

当然，我们也要保持清醒。这篇文章来自 Anthropic 自己，讲的是他们内部用 Claude 的经验。它没有提供一个严格的对照实验，也没有说所有团队都能得到同样的十五分钟态势报告。它也没有展开自动 rollout agent 的具体安全机制。所以我们不能把它当成行业通用基准，只能把它当成一个先进团队的实践样本。忠于原文地说，文章最硬的事实是，他们内部最近几个月用 Claude Tag 做 CI 事故第一响应，Claude 通常在十五分钟内给出第一分析，最快四分钟在第一报告里指出根因，并且这套系统围绕 Slack、工具连接、技能文档和事故经验闭环运转。

如果你是平台工程团队、DevOps 团队、SRE 团队，或者负责公司内部 CI 基础设施，我建议你听完这期之后可以做一个很小的试点。选一个低风险系统，整理最近十次事故，写一个最小 oncall.md，把常用 dashboard、日志入口、GitHub 仓库、部署通知频道接进去，让 Claude 或类似 agent 先做只读分诊。然后找一次演练，让它根据历史事故生成第一份态势报告。你不需要一开始就自动扩容、自动回滚、自动发 PR。先验证它能不能比新人更快地整理上下文，比资深工程师更不怕重复，比值班人员更稳定地写交接。

如果你是普通业务工程师，这篇文章也和你有关。未来你可能会越来越少地在群里问，CI 是不是挂了，我的 PR 为什么卡住了。你会去看一个公共的 CI 天气频道，那里告诉你当前合并队列是否健康，构建延迟是否升高，有没有建议暂缓合并。你也可能在事故频道里看到 Claude 先贴出时间线，说最近某个 feature flag 打开后，某类测试跳过规则变化，建议负责人确认是否回滚。这个体验会改变工程组织的信息流。以前信息在少数平台工程师脑子里，现在它会被持续整理成可读、可检索、可复用的状态。

收尾来看，这篇文章真正讲的不是 Claude 有多神，而是 Anthropic 把 AI 放进了一个非常具体、边界清晰、价值密度很高的工程流程里。CI 和 CD 故障响应天然有大量重复调查、大量跨工具上下文、大量固定流程，也天然需要人类最终判断，这正好适合 agent 先做第一响应。我个人认为，这代表了企业 AI 落地的一个重要方向，不是让模型凭空当专家，而是让它进入团队已有的 Slack、GitHub、监控、复盘和审批流程，把组织记忆和工具链连接起来。最后用一句话总结，agentic coding 带来了更多更快的代码，而 agentic CI 的任务，就是让这条交付流水线在更高速度下依然可观察、可恢复、可交接。
