## Script

今天我们要聊的文章，标题是 How ABC Legal turned every employee into a builder with Claude Managed Agents，中文可以翻译成，ABC Legal 如何用 Claude Managed Agents 让每个员工都变成构建者。这篇文章发表于二〇二六年八月十七日，距离今天二〇二六年八月二十三日只有六天，所以它非常新，基本反映的是当下企业级 AI agent，也就是 AI 智能体，从试点走向规模化运营的最新阶段。

这篇文章值得听，不是因为它展示了某个特别魔法的模型能力，而是因为它讲了一个更现实、更重要的问题：当一个公司里很多人都开始用 AI 自动化自己的工作之后，CTO 到底应该怎么管？如果每个人都在自己的电脑上写脚本、跑定时任务、让 Claude 帮忙处理文件，那短期看很兴奋，长期看就会变成影子 IT。你不知道谁建了什么，不知道昨晚有没有跑，不知道花了多少钱，也不知道出了问题怎么回滚。而 ABC Legal 这个案例，刚好给了一个很清楚的答案：把 agent 当成公司软件资产来管理。

先介绍一下背景。ABC Legal 是一家美国的法律文件递送公司，做的是法律流程服务里非常具体、也非常重运营的事情，比如法院文件送达、电子立案、出庭律师协调等等。听起来不像一家典型 AI 公司，但这恰恰是重点。AI agent 真正能改变的，往往不是那些原本就高度自动化的软件公司，而是这种业务流程复杂、人工判断很多、文档和表单特别多的运营型组织。它们每天有大量重复但又不能完全粗暴自动化的工作，比如查法院规则、核对案件状态、整理客户要的记录、给律师发邮件确认可用时间、处理汇款邮件、分析广告投放建议。

文章里说，ABC Legal 的 CTO Brandon Fuller 今年早些时候给公司一千一百名员工推出了 Claude Enterprise。Claude Enterprise 可以理解成面向企业使用的 Claude 版本，提供更适合公司协作、权限和数据治理的环境。推出之后，公司内部发生了一个很典型的现象：员工并没有等技术团队下指令，反而自己开始动手做自动化。服务送达团队、电子立案团队、出庭律师运营团队，还有市场、合规、财务等部门，都开始用连接器和工具把那些长期吃掉一天时间的任务自动化掉。

从一个 CTO 的角度看，这当然是好消息。说明工具易用，说明需求真实，说明业务人员能感受到价值。但是 Brandon Fuller 很快看到另一个问题：这些早期 agent 住在哪里？很多时候，它们就住在构建者自己的电脑上，以个人桌面上的定时任务形式运行。你可以想象一下，一个员工做了一个每天晚上拉报表、发邮件的自动化，效果很好，但这个人休假了，电脑关机了，密码过期了，任务失败了，没人知道。再或者，另一个部门做了一个类似 agent，却用了更贵的模型，每次跑都消耗大量 token，也没人看见。这种状态不能支撑企业级规模化。

于是文章的核心登场了，Claude Managed Agents。这里的 Managed Agents 可以理解为受管智能体，也就是由 Anthropic 托管运行环境的 agent 平台。它把 agent 从某个人的笔记本电脑里搬到云端，让它们有统一的部署结构、共享工作空间、统一审计和计费界面，并且可以一直在线运行。对 CTO 来说，这意味着你终于能看到公司里到底有哪些 agent，谁是负责人，运行了多少次，成本是多少，出错了没有，以及上一次改动是谁批准的。

截至二〇二六年七月，ABC Legal 已经用 Managed Agents 跑了五十多个生产 agent，一些 agent 覆盖的人类任务成本在还没有重度优化前，就下降到最多约百分之五十。同时，公司里大约三百一十名员工，横跨各个部门，已经在日常工作中使用 Claude。这个数字很有意思，因为它不是说一千一百人全部变成 AI 专家，而是说明 AI 的实际渗透是通过具体工作流扩散的。先是少数人构建，再带动更多人使用，再通过平台治理把它变成组织能力。

Fuller 做的第一件关键事情，是把每个 agent 都定义成代码。这里的代码，不是说每个业务人员都要写复杂程序，而是把 agent 所需要的一切都变成结构化文本，放进代码仓库里。他的理解很直接：agent 本质上就是一个 prompt，也就是提示词，加上一组配置。只要是文本，就可以放进 repository，也就是代码仓库，让全公司看得见、评审得了、改得动、回滚得回去。

具体来说，一个 agent 的系统 prompt、工具列表、运行时间表、凭证配置、记忆设置，都写在配置文件里，和公司的软件代码放在同样的 Git 流程中。Git 是软件工程里常用的版本控制系统，pull request，通常简称 PR，则是把改动提交给别人审查和批准的流程。ABC Legal 的做法是，任何 agent 都不能在没有 PR 审批的情况下改变。这样，每个 agent 天然拥有版本历史、代码审查、回滚能力和审计轨迹。

这一点我个人认为是整篇文章里最值得软件工程师注意的地方。过去很多人做 AI 应用，会把 prompt 当成某种临时文案，放在数据库里、后台配置页里，甚至写在某个人的笔记里。但当 prompt 决定了一个 agent 怎么判断、怎么调用工具、怎么影响业务结果时，它其实就是业务逻辑。既然是业务逻辑，就应该有版本、有 diff、有评审、有回滚。否则你今天改了一句话，明天业务指标变了，你都不知道原因在哪里。

为了让这件事真的能推广，Fuller 花了一周时间做了一个 starter kit，也就是入门模板包。他做了两类模板，分别放在专门的 Git 仓库里。一类是事件驱动 agent，也就是某件事情一发生就启动，比如新任务来了，或者法院返回了某个文件。另一类是定时 agent，也就是按照小时、每天、每周这样的时间表运行。每个 agent 都有一个标准文件夹结构，里面包含 JSON 配置文件、Markdown 格式的系统提示词、部署脚本和运维说明。这里 JSON 和 Markdown 都只是常见的文本格式，重点不是格式本身，而是它们能被版本管理，能被审查，也能被 Claude Code 帮忙生成。

Claude Code 是 Anthropic 面向开发和代码协作的工具。ABC Legal 的构建者不需要手写软件，他们做的是复制模板，告诉 Claude Code 这个 agent 应该完成什么工作，然后让 Claude Code 生成需要的配置、提示词、凭证存储和记忆设置。主分支合并之后，agent 会自动部署。换句话说，业务人员负责描述任务和业务规则，平台负责运行，Git 流程负责治理，Claude Code 负责把描述转成可部署的结构化文本。

为了证明非工程师也能做到，Fuller 找来了公司一个十五人的 steering committee，也就是指导委员会。这个委员会来自财务、市场、运营和开发相关部门，但文章特别强调，他们不是软件开发者。Fuller 让他们克隆仓库，用 Claude Code 构建 Managed Agents。听到这里，你可能会笑，因为让非工程师克隆仓库、提交 PR，本身就不是一件特别简单的事。Fuller 也提到，他甚至要先解释 PR 是什么。有些非工程师以为 PR 是 personal record，也就是跑步最快纪录的那种 PR。结果过了一段时间，他们已经会做 pull request，并且互相发送审查请求。

这段很真实。企业 AI 落地常常不是卡在模型不会，而是卡在组织协作方式。对工程师来说，Git、分支、PR、审查、合并，已经像呼吸一样自然。对业务人员来说，这是一整套新语言。但 ABC Legal 的经验说明，只要模板足够清晰，任务足够具体，平台把运行时复杂度隐藏掉，业务人员是可以学会这种工作方式的。文章说，在一周内，这十五名员工都做出了能工作的 agent。然后他们回到自己的团队，继续培训其他人。大约一个月后，ABC Legal 就有五十多个 agent 在运行。

这些 agent 不是泛泛而谈的聊天机器人，而是每个都有名字、负责人和单一任务。文章举了很多例子，我们挑几个看看它们到底在干什么。一个是 AI Code Reviewer，也就是 AI 代码审查员。它会审查四个代码库里的每个 pull request，进行多模型分析，帮助发现安全漏洞、性能回退和误提交的凭证。工程师现在会等它审查完再合并。这个例子比较贴近软件团队，但它在 ABC Legal 的 agent 版图里只是其中一类。

更业务化的例子是 EvidenceChain Delivery Agent。ABC Legal 有一个自有网站 EvidenceChain.com，法院、原告和被告可以在上面查看某次现场送达的记录，包括送达人是谁、什么时候尝试送达、以及送达文件的照片。有一个客户希望持续获取其中一些特定记录。以前这是一位客户经理每周手工做的事情。现在 agent 每天拉取符合条件的数据库报表，再用 Managed Agent 内置的浏览器取回每个 PDF，然后把文件发送到客户的 FTP 服务器。文章里说，设置这个 agent 的客户经理此前从来没有做过自动化，只是把需求描述给 Claude Code，大约一小时就建好了。

这个例子非常关键，因为它说明 agent 的价值不一定是替代一个完整岗位，而是接管某个稳定、重复、可描述的流程。一个人每周做一次，可能看起来不值得工程团队排期。但如果业务人员自己能用模板和 Claude Code 做出来，它就值得自动化了。企业里大量被忽略的效率损耗，恰恰就藏在这些小流程里。

再看电子立案拒绝诊断 agent。法院拒绝某个立案后，这个 agent 会自动触发，读取任务详情，检查法院规则，并在大约一分钟内把诊断发到 Slack。Slack 是团队协作和即时消息工具。过去这类工作可能会消耗员工一天里的数小时，因为你要看拒绝原因、查规则、对照案件信息，再判断下一步该怎么办。agent 不是简单总结文本，而是在特定上下文里做诊断建议。

还有一个任务验证 agent，会检查每个新进任务是否和法院信息一致。它会用浏览器访问法院网站，确认听证会或案件是否正确提交，是否真的会在指定日期发生，然后根据发现调整任务，并标记司法辖区、法院和诉讼时效相关时间范围。这里我们可以看到企业 agent 的一个典型形态：它不是只在一个数据库里读写，而是要跨系统工作，访问内部平台、外部网站、规则文档和协作工具。传统自动化当然也能做，但需要工程师写很多脆弱脚本。现在 agent 把自然语言理解、网页操作和工具调用结合起来，让这类流程更容易启动。

文章还提到 Attorney Coverage Agent，也就是律师覆盖协调 agent。它会联系律师网络，确认听证会是否有人能覆盖，检查可用性，发送邮件，并读取律师回复里的可用时间和价格，最后让协调员确认。财务部门有 AR remittance agent，也就是应收账款汇款处理 agent，会解析汇款邮件，生成 NetSuite 的付款应用文件，并发到 Slack 让人一键批准，然后再导入。市场部门有 Google Ads 分析 agent，每周给渠道负责人发建议。运营部门有一个叫 Charvis 的 review agent，会检查已经完成的送达任务，目前和合规团队判断一致的比例约为百分之九十八。还有 Service Overdue Nudger，负责处理一线运营积压里最重复的第一轮提醒工作，为人工审批起草分层的每日外联消息。

你会发现，这些 agent 有一个共同点：它们一开始都没有被设计成完全无人监管。ABC Legal 的 agent 多数是在人的监督下工作，把它做了什么、建议什么发到 Slack。人可以在消息线程里回复，也可以用 emoji 表情反应。很多公司做到这里就停了，把 Slack 当成通知中心。但 Fuller 看到，这些回复和表情其实是训练信号，或者更准确地说，是反馈信号。员工点了赞，说明建议可能对；员工回复说不对，说明这里有错误；某个 emoji 被用来标记误路由，说明路由规则需要修改。如果这些信号只留在聊天记录里，就浪费了。

于是 ABC Legal 对需要评分反馈的 agent 采用了三角色架构。注意，不是所有 agent 都需要这个架构。文章说，大多数 agent 是单任务执行器，输出没人评分，自己独立工作即可。但对那些能收集人类反馈的 agent，他们会让三个独立 agent 共享同一个工作空间、环境和凭证库，但在不同时间运行。第一个叫 Initial Agent，也就是初始执行 agent，负责真正干活，通常在任务进入或文档返回时实时运行，并记录每一步的审计轨迹。第二个叫 Harvester，也就是收割 agent，每小时或每天运行，去 Slack 收集人类反馈，把线程回复和 emoji 反应转成带标签的数据点。第三个叫 Tuner，也就是调优 agent，每周运行，从全局看这些反馈，然后提出对 prompt 或配置的修改。关键是，它不直接改模型权重，也不自动上线，只起草一个 pull request，由人审查并合并。

这个设计特别适合企业环境。因为很多人一听到 agent 自我改进，就会担心失控，好像系统今天收到几个差评，明天就自己改规则上线了。ABC Legal 的做法是，反馈可以自动收集，修改建议可以自动生成，但上线仍然走 PR。人类审查是最后一道门。这样既保留了学习闭环，又保留了治理边界。

文章里还有一个很有意思的例子，叫 deliveries as code，可以理解成把配送或工作路由规则当成代码。这个系统最早来自 ABC Legal 的姐妹公司 Docketly，Docketly 大约五十人，围绕 deliveries 来组织工作。每个 delivery 都有自己的路由和处理规则。它们大约一百四十五套规则，不是放在管理后台的数据库记录里，而是每套规则都是 Git 里的一个 YAML 文件。YAML 也是常见配置文本格式。所以调优一个 delivery，就等于编辑一个文件，然后发起 pull request。

这个闭环由四个 agent 组成。一个 agent 每周把判断结果发到 Slack。Harvester 把人类反馈里的表情和回复转成标签。Tuner 根据这些标签对 YAML 规则发起 PR。第四个 agent 则把已经合并的配置推到生产数据库。请注意，第四个 agent 只执行人类已经审查批准的内容。实践中，如果有人用 emoji 标记某个 delivery 被错误路由，那么一周内，这个反馈就可能变成对应路由规则的一次合并修改。整个循环里唯一的人工步骤，就是审查。

这里我个人认为有一个很大的启发：很多业务系统之所以难以被 AI 改进，是因为业务规则藏在数据库、后台表单、员工脑子和历史习惯里。LLM 是文本引擎，如果你把规则变成文本，放进仓库，它就能读、能比较、能建议修改。Fuller 的一句话很有代表性：代码只是结构化文本，LLM 是文本引擎。你的业务越能转成仓库里的文本，agent 给你的杠杆就越大。这个观点听起来简单，但落地范围很广。它不仅适用于传统软件代码，也适用于 prompt、schema、派单规则、通知模板、业务配置。

那为什么 Fuller 最后选择 Claude Managed Agents 作为组织里的 agent harness，也就是智能体运行和治理框架？文章说他评估了多个框架，标准很具体：平台要有版本控制、可观测会话、工作空间计费、模型选择、记忆原语、MCP 接线能力，最重要的是，不需要自己照看基础设施。MCP 是 Model Context Protocol，可以理解成让模型连接外部工具、数据和系统的一套协议或接口方式。对企业来说，agent 真正有用，往往取决于它能否安全连接内部平台、报表系统、Slack、项目管理系统和凭证库。

Managed Agents 的责任边界也很清楚。Anthropic 的托管基础设施负责让 agent 跑起来的部分，包括执行循环、会话、记忆、控制台和模型。ABC Legal 自己负责 prompt、工具列表、触发逻辑、审计轨迹，以及结果反馈闭环。这种分工对企业 CTO 很重要，因为你不希望团队为了每个小 agent 去维护队列、调度器、会话存储、重试机制和监控面板。你希望业务逻辑在自己手里，运行复杂度交给平台。

在规模化之后，有几个能力变得特别重要。版本控制让每次 push 都生成新的 agent 版本，并支持容易回滚。模型灵活性让团队可以根据任务选择模型。多数 agent 默认用 Claude Sonnet，高吞吐、快速任务可以用 Claude Haiku，需要更深推理且成本值得时再用 Claude Opus。换模型只是一行配置变更。MCP 和凭证库让 agent 能连接 ABC Legal 自己的平台，文章说内部有超过一百个工具可用，也能连接 Metabase 做报表，连接 Slack 做人在回路交互，连接 Atlassian 做项目管理。定时部署则通过 Bitbucket Pipelines 和 cron 调度来跑，利用已有的仓库访问、密钥和计费能力。

说到成本，文章并没有把 AI 描述成免费午餐。ABC Legal 跟踪每一美元 AI 支出，并按供应商、工具、团队和使用场景拆分。春天 agent 大规模上线时，支出上升；到了七月，使用量继续增长，但支出开始下降，原因是他们开始做效率优化。一些 agent 覆盖的任务成本下降到约百分之五十，同时三百一十名员工在各部门使用 Claude。

ABC Legal 的成本策略也很清楚：把花费推向垂直的、运营型工具和 agent，因为这些地方的回报更可测量；同时保持横向聊天和头脑风暴类用法的广泛性，但控制成本。换句话说，公司不是禁止大家聊天式使用 AI，而是对于真正大规模消耗资源的地方，要问清楚价值在哪里。一个 agent 如果每天运行上千次，就必须证明它节省了多少小时、多少钱，错误率如何，是否优于人工。

文章提到他们跟踪一个 efficiency ratio，也就是效率比。这个指标衡量 agent 交付的价值和运行成本之间的关系。每个 Managed Agent 每次运行时，都会把自己的价值以小时和美元的形式回报到数据仓库。agent 的经济曲线通常像 J 曲线，刚开始可能是亏的，因为它还新，可能使用更大的模型，prompt 也不够精简，token 消耗较高。随着团队写 eval，也就是评测集，改用更便宜更快的模型，削减 token，agent 才逐渐转正。这里的重点是，AI 自动化不是上线那天就胜利，而是一个持续工程优化过程。

他们的自动化升级路径也很稳。多数 agent 一开始都有人在回路里，也就是 human in the loop。agent 先看任务或工单，提出建议，让人审核后再行动。这个建议要么存到工单里，以横幅形式出现在员工工作流中，让人接受或拒绝；要么发到 Slack 频道，让人在消息线程里回复。这些接受、拒绝、回复和表情，慢慢形成一个好判断和坏判断的数据集，再喂给 harvester 和 tuner 闭环。等 agent 在某个具体任务上证明自己和人类一样好，甚至更好，才进入自动化模式，自主行动。即使进入自动化模式，它仍然留在同一套测量框架里，以便观察性能是否漂移。

这部分对听众里的工程师和 AI 从业者很实际。很多团队做 agent 的时候，容易一上来就追求全自动，认为不能自动执行就不算智能体。但在企业环境里，信任是赚来的，不是宣布出来的。ABC Legal 的原则是，每个 agent 都先提出建议，证明自己稳定和人类一致之后，才获得独立行动权。这个思路其实和自动驾驶很像，先辅助驾驶，再限定场景自动驾驶，最后才扩大范围。你不会因为一次 demo 成功，就让系统立刻接管所有路况。

Fuller 总结的几个工作原则也很值得记。把一切都看作代码，是第一条。越多业务能变成仓库里的结构化文本，agent 就越能发挥作用。用 PR 作为控制面，是另一条。如果你想让 agent 参与某个决策，就尽量把这个决策做成 pull request。因为 Git 天然提供逐行评论、审批流程和不可变审计轨迹，它既适合 AI 审查，也适合人类审查。投入反馈闭环也是关键，Slack 回复和 emoji 不是热闹，它们可以变成结构化信号，推动 prompt 和配置改进，而且不需要重新训练模型。

还有两条很现实。跳过本地定时任务这个绕路。ABC Legal 早期花了时间做桌面定时任务和本地例程，部分原因是 Managed Agents 当时刚推出 beta。Fuller 现在的建议是，直接上 Managed Agents 这类受管平台。另一个是，真正的障碍可能不是 AI，而是 Git。让业务人员熟悉克隆仓库、提交 PR、理解审查流程，是实际门槛。文章说这件事确实可行，而且进展很快，但仍然是一个真实障碍。Fuller 也希望未来工具能把这层体验做得更容易。

最后一条原则特别容易被忽略：不是每个任务都值得做 agent。成本是真实存在的，所以每个团队都要从价值除以成本的角度思考。可做不等于该做。适合 agent 的任务通常有几个特征：流程稳定，输入输出可描述，判断标准能被人类反馈，系统连接可控，错误影响可承受，节省的时间或创造的收益能量化。如果一个任务一年只发生两次，规则每次都变，错误代价又很高，那也许写个操作手册比做 agent 更合适。

那这篇文章对我们实际工作意味着什么？如果你在一个软件团队，正在考虑企业内部 agent，我建议不要从大而全的超级助手开始，而是先选一个窄任务。比如 PR 审查里检查凭证泄露和性能风险，客服工单里做初步分类，财务邮件里抽取结构化信息，运营后台里查某个外部网站并给出建议。任务越窄，越容易评估，也越容易积累信任。然后从第一天就给它 owner，也就是负责人，给它版本，给它运行日志，给它成本标签。不要让 agent 变成没人负责的自动化幽灵。

如果你在平台团队或架构团队，ABC Legal 的实践给你的启发是，把 agent 平台当作内部开发平台来设计。业务人员不应该直接面对复杂 SDK、密钥、调度器和日志系统。他们应该面对模板、示例、自然语言描述和清晰的审批流程。工程团队要做的是铺路，不是替每个部门写所有 agent。你可以提供事件驱动模板、定时模板、Slack 反馈模板、凭证接入规范、评测规范和成本仪表盘。这样业务团队的创造力才不会被开发排期卡死。

如果你是业务侧或产品经理，也可以从这篇文章里学到一种表达需求的方式。不要只说，我想要一个 AI 助手。你要说，当某个事件发生时，agent 应该读取哪些信息，查哪些规则，调用哪些系统，输出什么建议，谁来审批，审批结果怎么记录，什么时候允许自动执行。这样的需求非常适合 Claude Code 之类工具转成配置和 prompt，也更适合工程团队评审。

落地时也有几个坑要避。第一个坑是没有审计。agent 一旦能调用工具，就必须记录它看了什么、做了什么、为什么这样建议。第二个坑是没有成本归因。只看总账单没有意义，你要能知道哪个团队、哪个 agent、哪个用例在花钱。第三个坑是没有负反馈。很多团队只收集成功案例，不收集拒绝和错误，最后 agent 永远无法系统改进。第四个坑是 prompt 私有化。某个人本地调了一个很好的 prompt，但没有进仓库，没有版本，别人无法复用，也无法审查。第五个坑是过早自动化。先让 agent 推荐，再让人批准，等数据证明它可靠，再逐步放权，这会慢一点，但更适合长期运行。

文章结尾说，ABC Legal 的 agent fleet，也就是智能体舰队，还在继续增长。正在进行的项目包括服务照片审查 agent、PagerDuty 分诊 agent、每日 KPI 摘要，以及在现有 agent 上扩大 Tuner 闭环。他们也在寻找更多 X as code 的候选对象，比如通知模板、事件路由规则、派单逻辑，把这些东西迁移到仓库里，让 agent 能读取、推理并提出改进。Fuller 的愿景是，让 AI 支持一个能够自我运行的业务，而员工可以腾出来负责掌舵。

我个人认为，这篇文章的价值在于，它把企业 agent 从玩具阶段拉回了软件工程和运营治理。真正厉害的不是五十多个 agent 这个数字，而是每个 agent 都有版本、负责人、成本、反馈和审批边界。对今天的 AI 团队来说，模型能力当然重要，但决定 agent 能不能在公司里长期活下来的，往往是这些朴素的工程原则。

用一句话总结，ABC Legal 的经验不是让所有员工都变成程序员，而是让所有员工都能用受管、可审查、可度量的方式，把自己最懂的业务流程变成可运行的 agent。对正在通勤路上听节目的你来说，回到公司可以先问一个问题：我们团队里，有没有一个每周重复、规则明确、人工还要花时间判断的小流程，值得先把它变成一个有人监督的 agent？如果有，这可能就是你们企业 AI 落地最好的起点。
