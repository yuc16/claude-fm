## Shownotes

Anthropic 在九月二十四日发布了一篇不长的博客，但它讲的不是新模型有多强，而是当编码会话越来越长、上下文越来越重之后，成本结构发生了什么变化。文章第一次公开了 Claude Code 从三月到九月的使用数据，并解释了 Opus 五点五 在定价、模型行为和 Claude Code 运行框架三个层面做了什么，让长会话变得更便宜。

本期要点：
- 开发者的每个 prompt 让 Claude 工作的时间变成了三点三倍，模型调用多出四成，人工打断减少了六成八
- 每次请求携带的上下文增长了二点六倍，输入和输出的 token 比例从一百八十九比一涨到三百二十四比一
- Opus 五点五 把输入输出 token 价格降了两成，把缓存读取价格降了六成，典型负载整体成本低约四成
- 缓存未命中的输入减少了超过一半，因为 Claude Code 修掉了很多会意外打破缓存的小动作
- 模型完成同一任务需要的轮次更少，而少一轮比拼一个缓存更省钱
- 三个可以立刻上手的习惯：会话开始就选定模型、离开前先压缩上下文、长会话设置一小时缓存

## Script

你好，这里是 Claude FM，我是你的主播。今天我们要聊的这篇文章，标题是 Coding sessions are longer and use more context. Claude Opus 5.5 is built with that in mind. 翻成中文大概是这样：编码会话正在变得更长，用到的上下文也更多，而 Claude Opus 五点五 正是带着这个前提被设计和定价的。文章发表在二〇二六年九月二十四日，距离今天只过去三天，来源是 Anthropic 的官方博客，官方标注的阅读时间是五分钟。

我特别想推荐这一期的原因，是它跟我们平时听到的模型发布文章完全不一样。它通篇几乎没有在讲跑分、讲能力榜单，而是在讲一件更朴素、也更贴近你钱包的事情：你每天在 Claude Code 里敲的那些指令，现在到底在花多少钱，钱花在哪里，以及为什么过去六个月里，账单的结构悄悄变了。

如果你每天的工作里有一多半时间是开着 Claude Code，让它读代码、改代码、跑测试、查文档，那这期内容跟你的关系，可能比任何一个新模型的发布公告都要直接。因为我们今天讨论的不是能力上限，而是成本曲线。而成本曲线这个东西，一旦你不理解它背后的机制，你会在月底看到一个自己完全无法解释的数字。

我们先把背景铺一铺。过去一年半，行业里对 AI 编程的讨论，经历了一次非常明显的重心转移。最早的时候，大家关心的是：模型能不能写对这段代码。后来是：模型能不能一次写对一个完整的函数。再后来是：模型能不能自己完成一个任务，甚至一个完整的功能。到了二〇二六年这个时间点，很多团队已经不太问这些问题了，因为答案是能，至少对相当一部分任务来说是能。

于是讨论就自然滑到了下一个问题：能是能，但是贵不贵、稳不稳、快不快。

这里有个关键的技术前提，需要先交代清楚。现在主流的模型服务，基本都是按 token 计费的。token 你可以粗略理解成文字被切成的小碎片，中文大概一个字到两个字对应一个 token，英文大概四个字符左右对应一个 token。你发给模型的每一段内容，都会被算成输入 token；模型吐出来的每一个字，都算输出 token。而在做编程任务的时候，输入 token 通常是压倒性的大头，因为模型需要读你的代码文件、读报错信息、读文档、读之前的对话历史。

Anthropic 这篇文章里给了一个非常说明问题的数字：输入和输出 token 的比例，从六个月前的一百八十九比一，变成了现在的三百二十四比一。也就是说，模型每吐出一个 token 的答案，背后要读三百多个 token 的材料。这个比例本身就是整个成本问题的核心。

所以这篇文章要解决的本质问题是：既然开发者使用模型的方式，已经从短平快的问答，变成了长时间、高上下文的重型任务，那么定价模型、模型的运行方式、以及工具本身的实现，都应该跟着变。文章把它拆成了三条线来看：第一是计价方式的变化，第二是模型行为的变化，第三是 Claude Code 这个运行框架本身的变化。我们一条一条讲。

先说最有意思的一部分，也是这篇文章独有的部分，就是那批使用数据。Anthropic 拉了从二〇二六年三月到九月，整整六个月里，开发者在 Claude Code 里的聚合使用数据。他们发现了一个很有代表性的现象：每个会话里的提示词数量基本没变，也就是说，大家开口的次数还是一样的，但每次开口之后发生的事情，完全不一样了。

具体来说，Claude 在每一个提示词上工作的时间，变成了原来的三点三倍。对应的，每个提示词触发的模型调用次数，多了百分之四十以上。而与此同时，人的打断减少了百分之六十八。

这三个数字放在一起，画面感就出来了。以前你用 Claude Code，大概是这样的节奏：你说一句，它回一句，你看一眼，发现方向不对，赶紧打断，重新说。像一个新手司机，你坐在副驾上，脚一直悬在刹车上。现在的情况是，你说一句，它开始自己琢磨，自己读文件，自己调工具，自己验证，中间不怎么需要你插手，你甚至可以趁这个时间去泡杯咖啡。

第二个变化是工具的接入方式。数据显示，开发者把工具服务器连上的概率，大约变成了两倍，使用 skill 也就是技能包的概率也明显上升，而把文本直接粘贴进提示词的概率，下降了大约三分之一。

这两件事其实是同一件事的两面。粘贴文本，意味着你手动帮模型找上下文，你从某个文档、某个网页、某个聊天窗口里复制一段东西，塞给它。而连接工具服务器、使用技能包，意味着你把取上下文的这个动作，交给了模型自己去做，它需要什么就自己去拿。

换句话说，开发者正在从喂饭模式，切换到放养模式。以前是模型等着你把材料准备好，现在是你给它一个方向和一个工具箱，它自己去翻箱倒柜。

第三个变化，也是最直接跟钱有关的一个：每次请求携带的上下文，增长了二点六倍。六个月，涨了将近两倍。原因也不难理解，会话变长了，模型读的东西变多了，工具调用链条变长了，历史记录变厚了，这些全部都会累加到每一次请求里。

你要知道，一次请求携带的上下文，不是只付一次钱。模型每往前推进一步，都要把前面所有的上下文重新过一遍。所以上下文长度和成本之间，不是线性关系，而是接近平方的关系。二点六倍的上下文增长，如果你什么都不做，账单可能不止涨二点六倍。

这就引出了文章里最核心的一句话，我把它翻译一下：对于这类会话，上下文工程带来的经济影响是被放大的。说白了就是，你怎么管理上下文，现在不只是影响模型答得好不好，而是直接影响你花多少钱。

打个比方。以前的编程助手像点外卖，你点一份，付一份的钱，送过来吃完就结束了。现在的编程助手更像是请了一个团队进场施工，工人在你家里待得越久，翻的抽屉越多，重新读图纸的次数越多，费用就越高。而且这个团队有个特点：他们每换一个工序，都要把之前看过的所有图纸重新看一遍。所以你给的图纸越多、越乱、越不必要，成本就越吓人。

如果你来设计这个产品，你会怎么办？我猜大多数人第一反应是降价。降价当然要做，但只降价是笨办法，因为降价是线性的，而上下文增长带来的成本是超线性的。真正聪明的做法是让那些重复读的部分便宜下来，也就是缓存。这就说到了文章的第二部分。

Opus 五点五 在定价上做了两个动作。第一，对于按 token 计费用的用户，输入和输出的价格都降了百分之二十。这是基础降价，你听得懂，也猜得到。第二个动作才是重点：缓存读取的价格降了百分之六十。

为什么缓存读取的降价这么关键？因为缓存读取，构成了智能体任务和编程任务成本的绝大部分。你想想刚才那个比例，输入是输出的三百多倍，而在输入里面，又有很大一部分是重复的、之前已经读过的内容。如果每次重复读都要按原价付钱，那成本就会像滚雪球一样失控。把缓存读取打到四折，等于直接砍掉了成本结构里最大的一块。

这里还有一层时间上的巧合，或者说，是设计上的呼应。因为每次请求的上下文在这半年里涨了二点六倍，同样的降价幅度，放在今天能省下的钱，比放在六个月前要多得多。原因很简单，今天的账单里，重复读取的上下文占比更高了，而降价正好打在这个占比最高的部分上。

文章还给了一个横向对比：在发表这篇文章的时候，Opus 五点五 上读取一个缓存 token 的价格，是同类竞争模型的五分之一，而性能还更好。这个说法的口径需要你自己拿去验证，因为各家对缓存的定义和计费周期都不太一样，但方向上至少说明，Anthropic 是铁了心要把长会话的价格打下来。

为了让你彻底理解缓存这件事为什么这么要命，我用一个生活里的例子把它讲透。缓存的工作原理，是前缀匹配。也就是说，模型会把你这次请求的内容，跟上次的内容从头开始一个字一个字地比对，只要开头有一大段完全一样，这一段就可以直接从缓存里读，价格便宜很多。但只要中间有一个字变了，从这个字往后的所有内容，就不能用缓存了，全部要按新输入的价格重新算。

你可以把它想象成一份很厚的合唱谱。整个合唱团已经排练过前一百页了，如果这次要练的还是那一百页，大家直接开口就行。但如果你在第一页中间插进去一句新的歌词，那从第一页开始，所有人手里的谱子都失效了，后面所有页都得重新发、重新对。更糟糕的情况是，很多人习惯在对话的第一句就塞一大堆系统提示和工具定义，那么你后面每一次小小的改动，都可能让整份谱子白练。

理解了这一点，你就能理解文章里那个反直觉的数据了。按道理说，会话变长了，上下文变复杂了，缓存未命中的情况应该变多才对。但实际情况恰恰相反：没有命中缓存的输入，减少了超过百分之五十。

为什么？因为 Claude Code 在过去半年里，做了一堆专门用来保护缓存的小修小补。文章举了两类例子。一类是比较小的、日常的小伤口，比如你刷新了一下登录状态，结果发现整个缓存被重置了。这种体验以前是有的，现在被修掉了。

另一类是更大的动作。比如你在对话进行到一半的时候，临时插进去一段新的指令；比如你让工具按需加载，而不是一开始就全部塞进上下文。这些操作以前都会直接打穿缓存，现在被处理得更温和了。

还有一个我觉得很聪明的改动：对于 Opus 五点五 和 Fable 五点一 这样的新模型，你现在可以在会话进行中调整努力等级，也就是让模型想得深一点或者浅一点，而不会重置缓存。这一点非常实用，因为一个长会话里，任务难度是起伏的，前面可能需要它深度推理，后面可能就是一些机械的整理工作。以前你为了省事只能从头到尾用同一个档位，现在可以随时调，而不用付出缓存清零的代价。

另外两个改动是给长会话和委派场景准备的。第一，使用 API 密钥或者通过云服务商接入的开发者，现在可以设置一小时的缓存存活时间。这个能力订阅用户本来就有，现在开放给了按量付费的人。缓存活得越久，你中间去开个会、喝杯水回来，之前读过的内容还在，不用重新付钱。

第二，分叉出来的子智能体，会从父级的缓存开始工作，而不是把同一份上下文重新读一遍、重新付一次钱。你想，一个复杂任务分出去五个子智能体，每个子智能体都要重新读一遍项目结构、读一遍规范文档，那成本是乘以五的。现在它们可以共享父级的缓存起点，这笔省下来的是实打实的。

讲到这里，我插一句自己的观察。我个人认为，这篇文章最值得记住的其实不是那百分之四十的价格下降，而是一个观念上的转变：缓存命中率，正在变成跟响应速度、准确率并列的核心工程指标。以前我们说一个系统快不快，看延迟；说一个模型准不准，看评测。以后你可能还要问一句：我这个月花了这么多钱，到底有多少打在了缓存上？这个比例，某种程度上代表了你的工作方式有多健康。

接下来我们讲第三个层面，模型行为的变化。Opus 五点五 完成同样的任务，需要的轮次更少。轮次这个词很重要，我解释一下：一次轮次，就是模型跟外部世界交互一个来回，它想一下，调一个工具，看结果，再想一下。省下一个轮次，意味着整个循环不用再走一遍。

文章引用了 Zeta Labs 的实测结果。在它们的场景里，Opus 五点五 相比 Opus 五，每个任务用到的轮次和工具调用都更少，但成本几乎只有一半，更惊人的是，它们最难的那批任务，完成的数量变成了两倍。

这个结果里其实藏着两个独立的收益。一个是单价降了，同样的工作量花更少的钱；另一个是效率提高了，同样的任务用的步数更少。而这两个收益是相乘的，不是相加的。单价降两成，再叠上轮次减少，最后的账单差距就会非常可观。

不过文章很诚实，它没有把这个结论吹成普遍规律。它引用了 Addy 写的一篇分析，原话大意是：在一个范围界定得很清楚的任务上，两个模型完成的轮次差不多，你省下来的就只是价格本身那点钱；真正的差距会出现在开放式任务上，因为在这种任务里，模型可能花很多轮在错误的方向上打转。所以没有哪个单一数字对所有的代码库都成立，你要自己去测。

这段话我觉得是整篇文章里最有价值的一段，因为它把话说得很克制。它其实在告诉你：不要因为看到别人说省了一半，就无脑切过去，你的任务结构决定了你能省多少。

为什么开放式任务更容易省下轮次？我的理解是这样的。一个范围明确的任务，比如把某个函数的参数校验补上，路径几乎是唯一的，模型聪明一点笨一点，最多也就是多绕一步，差距不大。但开放式任务是另一回事，比如让模型去排查一个线上偶发问题，它面前有几十条可能的线索。一个弱一点的模型可能会沿着错误的线索一路挖下去，挖了二十轮才发现方向错了，然后从头再来。而一个强一点的模型可能第三轮就意识到这条路不对，及时掉头。

这里的关键洞察是：少一个轮次，比省一个缓存 token 还要值钱。为什么？因为一个轮次意味着一次完整的模型调用，而一次模型调用要重新读一遍前面所有的上下文。所以省一轮，不只是省了那一轮的钱，还省了它本来会往上下文里增加的内容，以及后续所有轮次重复读这些内容的成本。这是一笔复利。

文章还顺手提了一个跟钱无关、但对体验影响很大的数据：Opus 五点五 的输出生成速度，比 Opus 五 快了百分之三十以上。它不会提高缓存命中率，也不会减少 token 用量，但它意味着你在长时间无人值守的任务上等待的时间更短了。这一点对那种你挂上去就去开会、回来看结果的场景来说，是很实在的改善。

我还想多说一句。当模型开始长时间不被打断地工作时，延迟本身的性质也变了。以前延迟是你敲完一句话，盯着屏幕等它出第一个字，三秒都觉得长。现在延迟是一个任务跑四十分钟还是跑三十分钟，中间你根本不在看。这两种延迟对心理的影响完全不同。前者是打断你，后者只是决定了你什么时候能拿到结果。所以对无人值守的长任务来说，吞吐比首字延迟重要得多。

好，铺垫到这里，我们进入最实用的部分：这对你的实际工作意味着什么，你能上手做什么。

文章里有一句话我很喜欢，它说随着智能体编程逐渐成熟，组织正在从要求开发者不惜成本地扩展，转向要求开发者高效地扩展。这句话背后是一个很真实的组织行为变化。早期大家的 KPI 是，你用 AI 写了多少代码；现在的 KPI 变成了，你用 AI 花多少钱、交付了多少东西。这个转变意味着，成本意识会慢慢变成每个开发者而不是财务部门的事情。

那具体怎么做？文章给了三个动作，我把它们展开讲，并且补充一些我自己会加进去的。

第一个动作，在会话开始的时候就把模型选好，不要中途切换。这一点听起来很小，但它直接关系到缓存。因为不同模型之间的缓存是不通用的，你在会话中间从便宜模型切到 Opus 五点五，或者反过来，基本上等于把之前攒下来的那点缓存优势全部清零，后面所有内容都要按新输入的价格重算。所以一个实用的习惯是：会话开始前先判断这个任务的难度和长度，一次选定，从头跑到尾。如果一个任务确实跨越了不同难度阶段，那就考虑拆成两个会话，而不是在同一个会话里换模型。

第二个动作，在你离开之前压缩上下文，而不是回来之后再压。Claude Code 里有个压缩上下文的能力，它会把你之前的长对话总结成一段更短的内容，从而把上下文缩短。这个动作的时机很关键。如果你先离开，让会话在那里挂着，甚至继续跑，中间产生的所有内容都会累积在上下文里，之后每次调用都要把这些内容重新读一遍。而如果你在离开前先压缩，那么整个无人值守期间，模型带着的是精简版的上下文，每一次调用的成本都会低很多。这个顺序的差别，在长会话里是成倍的。

第三个动作，如果你是走 API 密钥或者云服务商接入的，给长会话设置一小时的缓存存活时间。默认的缓存存活时间通常更短，你花在开会、看文档、甚至排队买咖啡上的那几分钟，就足以让缓存过期，回来之后第一次调用全部按新输入算钱。设置成一小时，成本其实很低，但对长会话来说收益很明显。

文章还建议你跑一下 usage 命令，看看自己的用量里有多少是缓存读取。这一步我觉得是整个流程里最应该马上做的。因为你如果不看这个数字，你就不可能在脑子里形成正确的成本直觉。你可能会以为自己的瓶颈是输出太贵，结果一看，输出占比很少，全是输入和缓存。你可能会以为自己的会话很短不用管，结果一看，某几个开放式的长会话吃掉了大部分额度。

所以我建议你今天就做一个动作：找出你过去一周最贵的那个会话，看看它的 token 结构。是输入多还是输出多？是缓存读取多还是未命中多？这个小小的复盘，往往比看十篇文章更有用。

接下来我想多聊几个文章没有明说，但从它给的机制里可以推出来的实践建议，这部分属于我的延伸，不是原文观点，你可以挑着听。

第一，控制粘贴。数据说粘贴文本的比例下降了三分之一，这是个好趋势。因为粘贴进来的内容，通常带着大量无关的格式、重复的说明、甚至乱码，它不但贵，还会稀释模型的注意力。更好的做法是把这些内容放进一个文件里，让模型自己去读，或者接一个工具让它按需取。文件还有一个好处，就是它可以被缓存，而随手的粘贴往往每次都不一样，缓存不命中。

第二，固定会话的前半部分。既然缓存是前缀匹配，那么你放在会话最前面的内容，只要不变，就可以一直享受便宜的价格。反过来说，你要尽量避免在开头放那种每次都变的东西，比如当前时间戳、随机的会话 ID、动态生成的临时说明。这些东西会让你的前缀每次都不一样，缓存形同虚设。很多团队在做系统集成的时候会掉进这个坑，一个动态字段就能把缓存收益全部吃掉。

第三，警惕那些看起来无害的小操作。文章专门提到刷新登录曾经是打破缓存的元凶之一，这说明破坏缓存的操作往往不是你在写代码，而是环境层面的一些自动行为。所以如果你在自建工具链，检查一下有没有什么环节会在会话中途悄悄改变请求的前缀，比如注入调试信息、切换功能开关、重新加载配置。这些动作在你的日志里可能就是一行，但账单上是很痛的一笔。

第四，关于子智能体，既然是分叉出去的时候从父缓存开始，那么合理的做法是让子任务尽可能早地分叉，而不是等父会话跑到很后面再分叉。因为越晚分叉，父级积累的上下文越多，子智能体要继承的缓存前缀就越长，虽然读缓存便宜，但总归是有成本的。更重要的其实是另一件事：不要让五个子智能体做几乎一样的事。分叉能省的是重复读上下文的钱，省不了重复劳动的钱。

第五，关于什么时候不该用 Opus 五点五。文章引用 Addy 的那句话已经给了答案：如果是范围明确、路径单一、机械化的短任务，两个模型的轮次差不多，你得到的就只是价格优惠。在这种情况下，如果你的任务是海量的、重复的，比如批量改格式、批量加注释、批量做简单重构，那么用一个更小、更便宜的模型可能是更理性的选择，哪怕它偶尔需要多绕一步。而 Opus 五点五 的价值最大化场景，是那种开放式、需要探索、可能走弯路、上下文很厚的任务。把这些任务交给它，把简单任务交给便宜模型，这是我认为最合理的一种分层策略。

第六，学会测量你自己的基线。文章反复强调没有单一数字适用于所有代码库。这句话的实际操作含义是：你需要在自己真实的仓库上跑一次对照。挑三到五个有代表性的任务，一个明确型的，一个开放型的，一个长会话型的，分别用两个模型跑一遍，记录轮次、工具调用次数和花费。这个实验可能花你一个下午，但它给你的判断力，会持续好几个月。而且这件事最好不要只做一次，因为模型和工具都在快速迭代，三个月后你原来的结论可能已经过时了。

第七，团队层面的规范。如果你是团队里的技术负责人，我建议你考虑把几件事写进团队约定：会话开始前确定模型档次、长会话离开前执行压缩、把常用的项目说明和规范做成固定文件而不是每次手打、定期看用量里的缓存占比。这些约定看起来琐碎，但它们的作用是把成本控制从个人习惯变成团队肌肉记忆。而且它们对新人尤其有价值，因为新人往往最容易把一大堆上下文塞进去，然后抱怨模型又慢又贵。

我也想诚实地说一说这篇文章的局限。它的数据是聚合数据，是从整体行为上看的趋势，不代表每一个人的情况。它的成本对比也有很强的场景依赖，尤其是那句典型工作负载降低约百分之四十，典型这两个字是关键。你自己的工作负载越偏向长上下文和智能体循环，这个数字对你越有利；如果你的用法主要是短问答，那你感受到的可能就是输入输出那百分之二十的降价，仅此而已。另外，文章里关于竞争对手价格的对比，是一个截至发表日的快照，这种对比过期得很快，你要当成一个参考而不是定论。这些都是我自己读的时候注意到的边界条件。

最后，我们把整篇文章串一遍。Anthropic 观察到，过去六个月里，开发者的用法变了：每次提示词让模型工作的时间变成三点三倍，模型调用多四成，人工打断少六成八，上下文每请求涨二点六倍，输入输出比涨到三百二十四比一。在这个前提下，Opus 五点五 做了三件事：把输入输出降价两成、把缓存读取降价六成，这是价格；让模型用更少的轮次完成同样的任务、输出更快，这是行为；修掉一堆会打破缓存的操作、支持一小时缓存、让子智能体继承父缓存，这是工具框架。三者叠加，长会话的成本曲线才被真正压下来。而你要做的事情很朴素：看清自己的用量结构，然后保护好缓存命中率。

我个人的点评是这样。这篇文章表面上是一篇定价说明，骨子里其实是一份成本工程的方法论。它传递出的信号是，Anthropic 认为未来的竞争力，不只在于模型多聪明，还在于它能多便宜、多稳定地跑完一个四十分钟的开放式任务。对我们这些每天用它写代码的人来说，这里面最值得内化的一点是：在智能体时代，上下文不再是免费的背景，它是一种需要被经营的成本。你每一次往会话里塞东西，都是在往账本上写字。想清楚这一点，你的工作方式会跟现在很不一样。
