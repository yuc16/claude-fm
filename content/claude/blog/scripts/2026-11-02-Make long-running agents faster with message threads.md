Make long-running agents faster with message threads，中文可以翻译为，用消息线程让长时间运行的智能体更快。这篇文章发表于二〇二六年十一月二日，今天是二〇二六年十一月八日，距离发表只有六天。欢迎收听 Claude FM，今天我们聊一个标题听上去有点像接口小更新，但对智能体工程相当实际的话题。

假设你正在通勤，手机上收到通知，说你的编程智能体还在处理昨晚提交的任务。它已经读了几十个文件，执行了好多轮测试，也修改过几次方案。你可能会想，它怎么越来越慢了？是不是模型推理越来越复杂？是不是工具执行太久？这些都有可能，但今天这篇文章提醒我们，还有一个很朴素的原因：它每次请求模型，可能都在重新搬运之前的全部聊天记录。

这里的 agent，也就是智能体，指的是能够围绕目标，多轮调用模型、使用工具，再根据结果继续行动的程序。它不是问一句答一句就结束，而是会不断循环。循环次数一多，工程系统里那些单次看起来不起眼的开销，就会变成很明显的等待。

Anthropic 这次推出的 message threads，也就是消息线程，解决的正是其中一块。它不是让模型突然学会更快思考，也不是把长历史自动压缩成短摘要，而是让客户端不要每一轮都把相同的历史重新发过去。今天我们会把这个机制讲透，也把它不能解决什么讲清楚，尤其是一个特别容易误解的地方：请求变小了，不代表模型读到的上下文变少，更不代表 token 用量随之下降。

先把背景铺开。按照原文描述，一个编程智能体在一场会话里，可能会向模型发起几百次请求。每次请求，都重新发送此前的每条消息和每份工具结果。这里的 Messages API，就是应用程序调用 Claude 消息能力的接口。你可以把它理解成客户端和模型服务之间的一份通信约定。

在这种调用方式下，模型要继续工作，客户端就得把它需要的对话背景带过去。刚开始没什么压力，只有用户任务和几段回复。后来工具返回了文件内容、测试结果、终端输出，模型又提出修改方案，再调用工具验证。消息越来越多，下一轮请求就越来越大。

我们做一个纯粹用来解释的假设。你让智能体修复支付服务里的一个并发问题。第一轮，它只知道你的需求。第二轮，它看过项目目录。再往后，它看到了订单状态机、数据库访问代码、测试用例和失败日志。到了第二十轮，真正新增的信息，也许只是一段新的测试输出，但请求里仍然要带着前面累积的所有材料。

这像什么呢？像你和同事一起排查故障，每次轮到你说话，你都先把会议开始以来的录音完整重放一遍，然后才补一句，刚才那个测试还是没过。会议内容当然没有丢失，但信息交接的方式很费时间。尤其当记录越来越长，你不是在增加新信息，而是在重复运送旧信息。

原文特别提到，当会话达到几十万 token 的规模，重新发送全部内容，就会增加 Claude 开始响应之前的时间。token 可以理解成模型处理文本等内容时使用的计量单位，它不是严格对应一个汉字，也不是严格对应一个英文单词。这里我们只需要记住，token 数越大，代表会话携带的内容规模越大。

所以这篇文章的切入点很明确：当智能体已经需要带着大量上下文工作时，能不能不改变它看到的内容，只改变这些内容在客户端与服务端之间的交接方式？消息线程给出的答案，就是第一次发送完整对话，后续只发送新增部分。

具体来说，开发者在 Messages API 的请求里加入 thread 参数，也就是线程参数。第一次请求包含完整会话，并启动一个线程。之后的请求，只需要包含新增消息，以及上一次响应的标识。服务端利用这个关联信息，把新内容接到原有对话上。

注意这里的上一次响应标识。它不是一句随口说的，我接着刚才聊。对程序来说，需要一个明确的关联凭据，告诉服务端，这些新增消息应当接在哪次响应之后。你可以把它理解成接力赛里的交接位置：不是重新跑完前面所有路程，而是从上一个已经确认的位置继续。

我们还是沿用支付服务的例子。第一次请求，你把任务说明和已有背景发过去。模型要求查看两个文件，工具执行后得到结果。下一次调用时，客户端不必重新附上最初的任务和已经发送过的全部消息，只需要把这次新增的工具结果发过去，并关联上一轮响应。

再下一轮，模型提出修改，工具返回修改完成和测试结果。客户端继续发送新出现的消息。这样一来，网络上传输的每个请求，不再随着完整会话历史一起膨胀，而是主要围绕这一轮真正新增的内容。

这里有个容易忽视的细节：新增内容不一定很短。如果一次工具调用返回了一大批文档，或者很多图片相关内容，那么这一轮请求仍然可能很大。消息线程消除的是重复发送已有历史的需要，不是给所有新增数据施加一个神奇的体积上限。

我个人认为，理解这个机制，最好把完整上下文和本轮上传内容拆成两个概念。以前，两者经常被绑在一起。为了让模型看到完整上下文，你每次都要上传完整上下文。现在，服务端临时保留线程，两者可以分开：模型仍然看到完整背景，客户端只上传差量。

这有点像你去医院复诊。如果医院已经暂存了上一轮检查资料，你这次只需要补交新报告，而不是把所有资料重新复印一遍。但医生看病时，仍然可能需要结合旧报告做判断。少交一次复印件，不等于医生只看最新那张纸。这正好引出全文最重要的边界。

原文明确说，虽然使用消息线程后，每个请求会更小，但 Claude 每一轮仍然读取完整会话，因此 token 用量保持不变。也就是说，它优化的是交接方式，不是删减模型的阅读材料。

你可能会问，我明明只上传了一小段，为什么还是按完整上下文来理解用量？因为上传了多少，与模型实际处理了多少，不是同一件事。服务端把此前保存的历史接回来以后，模型面对的仍然是完整对话。不能因为你没有重新传输那部分数据，就当它在本轮不存在。

所以，如果你正在做成本优化，要特别小心。原文没有承诺使用消息线程会降低 token 费用，也没有提供新的优惠价格。它明确说明，标准 Claude token 费率和现有速率限制依然适用。这意味着，不能把这个功能写进预算方案，然后默认长会话的模型费用会跟着请求体积一起下降。

假如你的系统真正的问题，是每一轮都带着太多无关历史，那么消息线程并没有替你判断哪些信息可以丢掉。你仍然可能需要另外设计上下文整理策略。不过那是我对工程实践的延伸，不是这篇文章介绍的新能力。文章本身的承诺比较克制：减少重复传输，让长会话更快开始响应。

接下来我们说性能数字。原文给出的结果是，对大多数 Claude Code 用户默认开启消息线程后，在五十万到一百万 token 的请求中，首 token 延迟的中位数大约下降百分之三十五。

这里的 Claude Code，是 Anthropic 的编程智能体产品。首 token 延迟，英文缩写是 TTFT，意思是从发起请求到收到第一个输出 token 所经历的时间。对于用户来说，它很接近那种直观感受：我已经把任务交出去了，界面什么时候终于开始有动静？

这个指标很重要，但也很容易被说过头。首 token 更早出现，不等于整段答案生成时间下降同样比例，更不等于整个智能体完成任务的时间下降同样比例。智能体还可能要等待测试、编译、浏览器操作，或者外部系统返回结果。这些时间不能因为消息线程开启，就自动一起缩短。

我们用一个假设数字帮助理解，不是原文实测。假设某类请求原来要等十秒才开始输出，如果下降百分之三十五，就相当于缩短到大约六点五秒。但如果这一轮后面还有一分钟的工具执行，整轮任务耗时就不会因此减少百分之三十五。你改善的是其中一个阶段，不是所有阶段。

另外，中位数也不是每次都能保证的降幅。中位数反映一组观测里居中的表现，不代表所有请求，也不代表最慢的那一小部分请求。原文没有给出完整的延迟分布，没有提供不同网络环境、不同上下文长度下的详细对比。我们可以认可这个结果的参考价值，但不能替它补出没有公布的数据。

还要注意样本条件。文章说的是五十万到一百万 token 的请求，不是说任何长度的对话都能获得同样收益。如果你只发几百字的问题，历史本来就很少，可省去的重复传输自然也有限。原文的判断是，智能体携带的上下文越多，消息线程越有机会降低首 token 延迟。

这其实提供了一个很实用的选型方向。不要先问这个功能是不是很新，而要先问，你的系统有没有很长的会话历史，有没有频繁连续的调用，有没有明显的响应启动等待。如果这三个条件同时存在，它就值得认真评估。

再来看服务端到底保存什么，以及保存多久。原文说，在两次请求之间，线程保存在内存里，经过加密，不写入磁盘。这是理解它的另一个关键点：它不是把你的对话变成一份长期存在的数据库记录，而是在活跃调用之间提供临时状态。

线程会在最后一次请求过去五分钟后过期。过期以后，客户端需要重新发送完整会话，启动一个新线程。请注意，这里是距离最后一次请求五分钟，不是线程创建五分钟后一定消失。它围绕的是会话是否仍然活跃。

我们拿日常开发来推演一下。智能体刚读完文件，十几秒后就要继续调用模型，那么这个节奏很适合消息线程。它不断产生新消息，又不断回来继续。反过来，如果模型给出一个方案，必须等你午休回来批准，间隔已经超过五分钟，那么原来的线程就会过期，后续要重新发送完整对话。

还有一种容易碰到的情况，是工具本身运行很久。比如一次复杂测试，或者一个等待外部任务完成的流程。如果两次模型请求之间的间隔超过五分钟，按原文描述，线程也会过期。这不是模型忘了你的业务目标，而是服务端那份临时线程状态已经结束了生命周期。

所以，消息线程最适合活跃会话，而不是任何形式的长期任务。长期运行和持续活跃不是同一个概念。有的任务持续两小时，但每隔几十秒就有模型调用。有的任务持续两天，却只在早晚各请求一次。它们在业务上都算长任务，对这项机制的适配程度却很不一样。

我个人认为，五分钟过期机制给开发者最大的提醒是，不要把消息线程当成唯一的会话存储。你的客户端仍然需要有能力重建完整会话。否则线程一过期，你就只剩下最新那段工具结果，却不知道前面的任务、约束和决策是什么。

你可以把服务端线程想成办公桌上正在使用的一叠材料，而客户端保留的完整记录像你的档案。桌上的材料让当前工作衔接得更快，但桌面清理之后，你必须能从档案里重新拿出来。临时状态是加速路径，不能变成无法恢复的单点依赖。

这里我们不需要凭空假设具体的错误码，也不需要编造接口的重试细节。文章没有展开这些。真正接入时，应当根据对应平台的文档确认线程失效如何反馈，以及客户端如何恢复。原文能确定的是，过期后要重发完整会话，建立新线程。

同样，内存中加密、不写入磁盘，是这篇文章明确描述的线程保存方式。但不能把这句话扩大成对整个平台所有日志、所有数据处理环节的全面声明。如果你所在团队有合规要求，仍然需要核对适用的服务条款和数据政策。我个人认为，安全评审最忌讳把一个组件的性质，推导成整个系统的性质。

接下来，我们看看三类最值得关注的场景。第一类是长时间运行的编程智能体，这也是文章最直接的例子。它的特点是，历史长，工具结果多，而且调用往往密集。一个错误修复任务可能经历阅读代码、提出假设、修改、执行测试、根据失败结果再修改，几轮下来，早期材料一直被反复携带。

如果你来做这样的系统，可以先观察每轮请求里真正新增的内容占多少。假如大部分都是旧历史，说明重复传输比较突出。消息线程就有机会让每一轮的交接更轻。但如果你的主要等待来自构建系统，或者测试环境排队，那么它可能改善交互手感，却不一定改变交付任务的主要瓶颈。

第二类是 computer use agents，也就是通过计算机界面执行操作的智能体。原文把它列为适用场景。为了帮助理解，我们可以想象一个操作网页后台的流程：模型观察页面，决定下一步操作，工具执行后，再把新页面信息交回来。这个例子是解释性的，不是文章提供的具体案例。

这种系统常常依赖连续的观察与行动。用户体验不仅取决于最终是否完成，还取决于每一步之间有没有长时间停顿。如果上下文已经很大，每一步又都重复发送历史，就像人在操作界面时，每点一下按钮之前都要先重新翻阅操作录像。消息线程能减少的，是这个反复搬运的部分。

但它不会让网页本身加载更快，也不会保证页面元素一定被正确识别，更不会改善模型操作策略的正确率。我们要把速度问题和能力问题分开。这个边界在实际评审时非常重要，否则一个传输优化，很容易被宣传成智能体全面升级。

第三类是文档和图片较多的工作流。原文强调，在这些场景里，请求可以变小。比如你已经提交一批材料，后续不断围绕它追问，或者智能体持续对比不同材料。这时，旧材料不必随着每轮新问题重新上传，而是在有效线程内被继续关联。

不过，请求变小依然不能推导出模型不再阅读那些文档。我们前面说过，完整会话仍然会被读取。如果你的目标是降低大量材料带来的上下文消耗，需要另行考虑信息筛选和任务拆分。消息线程与这些方法解决的问题不同，不能互相替代。

说到这里，你可能已经准备去改自己的调用封装了。我们把实践路线再讲具体一点，但下面这些是我个人的工程建议，不是原文给出的标准接入步骤。第一件事，不是急着把所有历史字段删掉，而是先理清你现有系统的会话状态放在哪里。

一个成熟的调用链，可能同时存在用户消息、模型回复、工具调用结果，以及应用自己维护的任务状态。你得知道哪些内容已经发过，哪些内容是本轮新增，上一轮响应标识又存在哪里。如果这些概念本来就混在一起，接入线程之后，只会更难排查到底是少发了消息，还是接错了上下文。

比较稳妥的思路，是让业务侧始终有一份可恢复的完整历史，再由请求构造层决定，这一次发送完整内容，还是发送新增内容。这样，功能上的会话记录与传输上的优化可以分开。即使线程过期，你也不需要从零猜测过去发生了什么。

第二件事，是特别关注轮次之间的关联。原文要求后续请求携带上一条响应的标识，所以你要明确，本轮到底在接哪次响应。尤其当应用允许用户同时追加需求，或者工具结果异步返回时，不要想当然地认为它们一定形成一条简单直线。

文章没有介绍并发分支如何管理，所以我们不能宣称它支持某种特定的分叉合并方式。我个人的建议是，先在顺序清晰的调用链上验证，再根据正式文档设计更复杂的并发逻辑。把已知简单路径做好，比靠猜测拼接状态更可靠。

第三件事，是认真做性能测量。既然它主要优化首 token 延迟，就不要只盯着任务总耗时，也不要只看请求体积。你可以分别记录会话规模、发送的数据量、从请求发出到首个输出的等待，以及整轮完成所需时间，再把工具执行时间单独看。

这样你才能回答一个真正有用的问题：用户感觉更快，到底是因为模型更早开始回应，还是因为这一轮测试恰好跑得更快？如果把所有时间混成一个数字，即使上线后表现变化，也很难知道是不是消息线程带来的。

测试时，还应该覆盖不同长度和不同节奏。短会话、长会话，连续密集调用、间隔超过五分钟后的恢复，都值得分别验证。这些是基于原文机制推导出的测试建议，不是文章公布的测试结果。尤其是过期后的第一轮，它要重新发送完整历史，不能期待仍然保持差量请求的体积。

还有一个实际问题，是如何选择上线范围。我个人会优先挑上下文长、调用频繁、用户又对等待敏感的任务试点，而不是一上来覆盖所有功能。这样收益更容易观察，出了问题也更容易定位。对于短小的单轮问答，它并不是天然最优先的优化项。

我们再说几个容易踩的认知坑。一个是把消息线程当作长期记忆。它有五分钟的过期机制，定位是活跃会话的临时衔接，不是让智能体永久记住用户。另一个是把它当作摘要压缩。它没有声称替你提炼重点，模型仍然读取完整会话。

还有一个是以为请求变小，就能绕开既有速率限制。文章明确说，现有速率限制继续适用，所以不要用网络传输量的下降，去推导模型服务的配额一定增加。它没有给出这样的承诺。

再有，就是把百分之三十五当成面向任何业务的服务保证。原文给的是特定上下文范围内，首 token 延迟中位数的大约改善。你的网络、请求结构、会话长度、调用节奏，都可能与它不同。最合理的使用方式，是把这个数字看成值得做实验的依据，而不是直接填进对客户的承诺里。

在平台可用性上，原文说，消息线程目前处于公开测试阶段。除了原生 Claude Platform，也就是 Claude 平台，还覆盖了 AWS 上的 Claude Platform、Microsoft Foundry 中的 Claude，以及 Google Cloud 上由 Anthropic 管理的 Claude Models。具体如何开始，文章指向相应文档，没有在正文展开全部接口细节。

这意味着，对于中国软件工程师和 AI 从业者来说，今天最值得带走的未必是马上复制一段调用，而是先识别自己架构里的重复搬运。你用什么平台是一回事，能不能分清业务历史、临时状态与模型输入，是更基础的一回事。

我个人认为，这篇很短的文章，体现了智能体工程一个值得重视的方向。系统性能不只取决于模型有多强，也取决于模型周围的协作方式是否合理。当一个智能体开始连续工作几百轮，原先为了简单而采用的重复发送，就可能成为越来越明显的摩擦。

但优化也要有边界意识。我们希望更快，不代表应该忽略恢复路径；我们希望少传数据，不代表就能宣称少用 token；我们看到一个漂亮的延迟数字，也不代表可以跳过自己的测量。把收益和约束一起理解，才算真正理解了一项工程能力。

最后用三句话收尾。消息线程的核心，是第一次发送完整会话，后续在有效线程内只发送新增消息，让长上下文智能体减少重复搬运，更早开始响应。它不减少模型读取的完整上下文，也不改变原文所说的 token 用量，而五分钟过期意味着客户端仍要具备完整恢复能力。我个人认为，最值得学的不是一个新参数，而是这种优化思路：先找到系统究竟在重复做什么，再决定把那份重复从哪里拿掉。
