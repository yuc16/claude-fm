How Datadog built a “universal machine tool” for Claude Code，中文我把它翻译成，Datadog 如何为 Claude Code 打造一台通用机床。这篇文章发表于二〇二六年七月二十一日。今天是二〇二六年七月二十六日，所以这是一篇非常新的文章，基本就是在我们现在这个 AI 编程工具进入工程主流程的时间点，讲一个大型工程团队怎样把 Claude Code，也就是 Anthropic 面向开发者的 AI 编程工具，用到生产系统里，并且进一步思考，光让 AI 写代码还不够，真正难的是怎样让它写出来的东西可验证、可复用、可上线。

这篇文章值得听，是因为它没有停留在那种很常见的演示层面，比如让模型写一个小网页，修一个简单 bug，或者生成一段脚本。Datadog 是一家做云监控和可观测性的公司，它自己的系统规模很大，可靠性要求很高。文章说，Datadog 的所有工程师都在用 AI 编程工具写生产代码，其中 Claude Code 至少驱动了三分之二的相关工作。这个信息很关键，因为它意味着我们讨论的不是一个小团队的尝鲜，而是一个成熟工程组织在生产环境里遇到的新问题。

这篇文章的中心人物是 Datadog 工程副总裁 Sesh Nalla。文章围绕他和团队做的几个项目展开，最后落到一个叫 Temper 的系统。Temper 被他们描述成 agentic systems，也就是智能体系统的一种 universal machine tool，通用机床。agent 在这里指的不是传统监控里的代理程序，而是能自己规划步骤、调用工具、读写代码、迭代完成任务的 AI 智能体。所谓机床，是工业制造里那些夹具、量具、铣床、数控机床之类的东西。它们不直接等于飞机发动机，但没有它们，你很难稳定地生产精密零件，也就很难制造复杂机器。Datadog 的类比是，如果 AI 智能体要参与构建大型软件系统，那软件工程也需要类似的机床，让产出变得精确、可重复、可检查、可替换。

我们先把背景摆清楚。过去工程师写代码，所谓进入心流，大概是一条很直接的链路。你理解问题，写代码，跑测试，做代码评审，发布，上线之后观察，再修。这个过程当然也复杂，但核心关系很清楚，就是人的意图直接变成代码。现在有了 Claude Code 这样的工具，抽象层级突然变了。Sesh 在文章里有一句话很形象，他说，你不再是在写代码，你是在塑造工作。你要决定智能体应该看到什么，它能用什么工具，什么叫成功，失败应该怎样被检测出来。就像每个工程师突然在管理链条里升了三级，但他们当初选择当工程师，并不是为了当经理。

这个比喻很有意思。我们平时说 AI 编程提升效率，听起来好像只是从手写代码变成让模型替你敲键盘。但 Datadog 的经验说明，当智能体会做更多事情之后，工程师的工作重心会从实现细节转向任务设计、上下文管理、工具边界、验收标准和风险控制。你可能不是少干活了，而是换了一种更像技术负责人或者系统设计者的活。尤其当一次 Claude Managed Agents，也就是由 Claude 托管和持续运行的智能体会话，可以跑很久，甚至跑几天时，问题就更明显了。每个智能体可能会发明自己的小工具、胶水代码和约定。它们变得更有用，但也更容易制造一堆临时产物。人类工程师就需要在智能体执行和原本面向人类设计的开发工具之间，不断做桥接。

Datadog 在文章里把他们用 Claude Code 的场景分成了几类。最小的一类是 targeted changes，也就是目标明确的改动，比如一堆难缠的 bug 修复、性能优化，以及对接已有服务的桥接代码。再往上是 large refactors，大规模重构。原文举了两个例子，一个是在三天内重构一个自定义 protobuf 解析器，另一个是在不到三个月的时间里，把一个指标控制系统从 FoundationDB 改写到 Postgres。再往上，是替换系统的大块组件，比如新的分片算法和自动扩缩容重新设计。最高的一层，是构建整个系统，比如用 Postgres 替换 MongoDB，自带云控制平面，以及从零开始建设数据摄取管道。

你会发现，这个光谱很像很多公司引入 AI 编程的路线。刚开始我们敢让它修小 bug，因为验证简单，错了影响也相对有限。然后我们发现它能理解项目结构，就让它做重构。再后来，它可以做架构层面的替换，甚至从零写一个系统。但任务越大，生成就越复杂；越靠近生产核心，验证就越模糊。你怎么证明它做的是你想要的？你怎么确认它在边界条件下不会出事故？你怎么把一次成功会话里的经验，变成下一次也能可靠复用的工程资产？这就是文章真正要解决的问题。

在 Datadog 的叙事里，通往 Temper 的路，不是突然来的，而是经过了三个项目。第一个叫 Courier，是他们在二〇二四年引入的一个分布式队列系统。这个系统完全手工从零构建，花了一年。Sesh 说，难点不在于构建各个部件，而在于让部件之间的交互可以被观察、测试和验证。所以他们在容易出错、代价高、难以逆转的地方，提高了严谨程度，使用了形式化建模和模拟。

这点对软件工程师很熟悉。分布式队列表面看就是生产者、消费者、确认、重试、顺序、幂等这些概念。但真正难的不是写出一个能在本机跑通的队列，而是在网络抖动、节点崩溃、消息重复、时钟差异、部分失败这些情况下，还能知道系统会发生什么。Courier 的经验告诉 Datadog，复杂系统的成本，更多在交互和验证，而不是某个函数的实现。

第二个项目叫 BitsEvolve，是二〇二五年九月他们构建的一个闭环进化优化框架。原文描述得很有科幻感：一组模型组成一个 council，也就是委员会，生成多个代码变体。然后通过一连串基准测试、测试套件和生产可观测性数据，决定哪些变体可以留下来。Sesh 说，这是他第一次看到，软件的一部分可以像活的生物一样被培育，通过变异、反馈和适应来成长。

这个想法和传统软件开发很不一样。传统上我们把代码看成工程制品，人写设计，人写实现，人做评审。BitsEvolve 更像是把某个优化问题交给一套环境，让模型不断提出候选方案，再由环境筛选。比如你想优化某段性能敏感代码，模型可以生成十几个不同实现，基准测试淘汰慢的，单元测试淘汰错的，生产可观测性淘汰有副作用的。听起来很强，但文章也指出了瓶颈：进化只会适应它所处的环境。换句话说，反馈回路有多可靠，进化结果才有多可靠。如果你的测试不覆盖关键场景，模型可能会演化出只会钻测试空子的代码；如果可观测性指标不准确，它就会朝错误方向优化。

第三个项目叫 Helix，是一个可与 Kafka 相比的流式服务。文章说，Claude Code 在一个人类工程师指挥下完成了大部分构建工作。Sesh 的描述很直接，他说他们难以置信的是，几天时间里就有了一个功能完整、可与 Kafka 相比的系统。他们开始做 shadowing，也就是影子流量或影子运行，观察到它有机会便宜两倍到五倍。

但这里有一个非常重要的转折。构建很快，不等于上线很快。把 Helix 推到生产环境，需要更多里程。运行加固不是一个人、也不是几天就能完成的，它需要随着时间积累，团队协作，到文章发布时仍然在 rollout，也就是逐步推出过程中。Sesh 说，瓶颈又移动了。智能体可以构建系统的大块部分，但人类仍然要协调，把这些工作通过为人类设计的工具和机制推到生产。

这句话其实戳中了很多团队现在的真实感受。AI 写代码的速度起来之后，原本看似慢的环节全暴露出来了。代码评审慢，测试环境慢，部署审批慢，权限申请慢，风险评估慢，文档同步慢。过去这些慢，被写代码本身的慢掩盖了。现在生成速度突然提升，整个软件交付链路的瓶颈就开始往验证、治理和上线迁移。Datadog 因此需要一种方式，让智能体能在经过验证、由策略驱动的运行时环境里，构建自己的工具。这就是 Temper 出场的背景。

Temper 的核心反转非常关键。传统思路是给智能体一个代码库，让它直接产出应用代码，然后人类和 CI，也就是持续集成系统，再去检查它。Temper 反过来，不让智能体直接把最终应用代码当作主要产物，而是让智能体产出 specification，也就是规格说明。然后一个 deterministic kernel，确定性内核，读取这些规格，做多层验证，最后部署这个规格所描述的运行系统。

这个设计的妙处在于，规格既是被证明的 artifact，也就是制品，又是被执行的 artifact。文章强调，这样就不会出现已验证的东西和正在运行的东西之间发生漂移。我们可以用一个很朴素的例子理解。假设你让智能体写一个订单状态流转服务。传统方式下，它可能在路由里写一点状态判断，在数据库约束里写一点，在后台任务里写一点，在文档里再写一点。你测试时验证了某些路径，但上线后真正执行的是散落在代码里的控制逻辑。Temper 想要的是，让智能体先明确写出状态、转移、前置条件和安全属性，再由内核把它变成可运行系统。验证对象和执行对象是一体的，至少在控制逻辑这个层面，不是口头说一套、代码跑另一套。

Sesh 用机床类比来说明这个变化。他说，智能体不需要每次为局部需求发明一堆断开的工具。它产生的是对意图和问题域的精确描述。就像你给数控机床一个螺纹规格，它会非常可重复地加工出来。你不是每次临场发挥用手磨一个螺丝，而是把规格交给机床。只有这样，才可能组装飞机、发动机和更复杂的东西。对应到软件，智能体可以先用 Temper 或类似机制，把某个东西做出来，再把它转成可重复、可检查、可复用的部件。这样你才有可能围绕代码库建设一个软件工厂。

原文说，每个 capability，也就是能力，在 Temper 里由三份 contract，契约来描述。第一份是 behavior，行为契约，包括状态、状态转移、前置条件，以及必须保持的安全属性。第二份是 data contract，数据契约，包括实体类型、属性、以及每种类型支持的动作，并以机器可解析的形式发布，这样智能体不需要读人类文档，也能发现完整 API。第三份是 authorization，授权契约，采用 default-deny，也就是默认拒绝，基于 scope，也就是权限范围来批准。被拒绝的请求会记录成待处理决策，人类可以批准，并热加载到策略引擎里。

这三份契约放在一起，其实就是把很多团队平时散落的知识显式化。状态在哪里？通常在代码里。数据模型在哪里？可能在 ORM、数据库 schema、接口文档和注释里。权限在哪里？可能在中间件、业务判断和运维手册里。Temper 要做的是，把这些东西整理成智能体和内核都能理解的规格。尤其是默认拒绝这点，我个人认为非常重要。AI 智能体做工具时，如果默认允许，很容易因为上下文理解错误而越权操作。默认拒绝意味着系统先保护边界，把例外变成可审查、可批准、可热加载的策略变化。

接下来是验证。文章说，每个规格在内核加载之前，必须经过四个独立层次的分析。第一层是 symbolic reasoning，符号推理，用来证明每个 guard，也就是状态转移的保护条件，是可满足的，并且每个 invariant，也就是不变量，是归纳成立的。听起来抽象，换成白话，就是系统要确认你写的规则不是自相矛盾的，也要确认关键安全性质在每一步之后都还成立。比如一个任务不能同时处于已删除和运行中，或者一笔资源不能被两个租户同时独占。不是只看当前状态没问题，而是看所有合法转移之后是否仍然没问题。

第二层是 exhaustive state exploration，穷尽式状态探索。它会访问每个可达状态。这里的关键词是可达，不是理论上随便组合出来的所有状态，而是从初始状态出发，通过合法动作能够到达的状态。对小规格来说，这很有价值，因为很多 bug 只在某个罕见状态组合里出现。人写测试通常会覆盖主路径和几个边界路径，但状态空间一复杂，漏掉的情况非常多。穷尽探索就像把迷宫里所有能走到的房间都走一遍，检查有没有死路、矛盾或违反规则的地方。

第三层是 deterministic simulation，确定性模拟。它运行真实生产代码路径，并且使用 seeded fault injection，也就是带种子的故障注入。故障包括丢包、延迟、重排序、崩溃等等。带种子的意思是，同一个 seed，同一个随机种子，可以精确复现同样的失败。这对工程调试太重要了。大家都遇到过那种 CI 偶现失败，重跑就好了，没人知道为什么。确定性模拟的目标是，把混乱环境变成可重复实验。你可以说，给我再来一次第三百二十七号故障场景，我要看这个状态转移为什么坏了。

第四层是 randomized property testing，随机化属性测试。系统会运行大约一千条伪随机动作序列，并且在发现违规时，把失败缩小到最小反例。这个 shrink，也就是收缩反例的能力，在属性测试里非常关键。因为如果系统只是告诉你，一千步之后坏了，你可能根本不知道哪一步导致问题。收缩之后，它会尽量找出一个最短、最简单的动作序列，能稳定触发同样的违反。这样工程师或者智能体才能修。文章还说，在一个小规格上，整个验证级联远低于一秒就能跑完。这个性能信息说明，Datadog 不是把 Temper 当成一套遥远的形式化研究工具，而是希望它能进入日常迭代循环。

这就回到文章标题里的通用机床。机床的价值不只是快，而是把生产从手工艺推向工业化。手工艺也可以造出很精美的东西，但质量依赖师傅，过程难以复制，零件不一定互换。工业化的突破是零件可组合、可检查、可替换。对于 AI 编程来说，单次让 Claude Code 做成一件事，像是一个高水平师傅临场发挥。Temper 想做的是，把临场发挥沉淀成规格、验证和运行时，让产出成为能在团队之间、会话之间复用的部件。

文章还引用了 Simon Willison 推广的 dark factory，黑灯工厂这个说法。它指的是一种软件流程，智能体在虚拟工厂车间里持续工作，人类不必一直在旁边盯着。在 Helix 的黑灯工厂里，Temper 扮演三个角色。它是 agent control plane，也就是智能体控制平面，管理会话、角色、工作队列和生命周期。它也是 tool-builder layer，工具构建层，让智能体用一些小型 Temper 应用去桥接软件开发生命周期里的工具，比如 Git、CI 和部署。它还是 Helix control API，也就是围绕数据平面的生命周期控制接口，用来驱动工作负载。

这三个角色放在一起，你会发现 Temper 不是一个单点工具，而更像一种把智能体纳入工程组织的基础设施。过去我们会给人类工程师提供脚手架、内部平台、审批系统、部署系统和运维控制台。现在如果智能体也要成为生产力的一部分，它同样需要控制平面，需要工具构建层，需要安全的 API 表面。否则每个智能体都会临时写脚本，临时调接口，临时修状态。短期看好像效率高，长期看就是不可治理的自动化碎片。

Sesh 还有一个观察，说 Temper 最令人惊讶的地方，是它开始显得比智能体基础设施更通用。他说很多软件眯着眼看，其实就是围绕数据库 API 的控制逻辑：状态、围绕变更的策略、生命周期转移、外部系统集成。如果软件具有这种形状，Temper 就可能在某种意义上是通用的。这个判断很值得我们停一下。很多业务系统看起来千差万别，订单、工单、实例、部署、账单、任务、告警、审批，但抽象之后确实都是实体在状态之间流转，每个动作有前置条件，每个转移有权限，每个生命周期阶段有副作用和外部集成。

Sesh 用 CRUD 应用举例。CRUD 就是创建、读取、更新、删除。Claude Code 很擅长用 TypeScript 或 Python 写一个 CRUD 应用。但是在普通 CRUD 应用里，控制逻辑往往分散在路由、数据库约束、服务代码、后台任务和文档里。也许测试覆盖率不错，但系统真正的 operational mode，也就是运行模式，通常表现为一个状态机，却隐含在代码库里。Temper 让这个状态机显式化。智能体产生的是精确描述，而不是任意代码。编译步骤在大语言模型之外完成，就像你把 Rust 代码交给 Rust 编译器一样。状态转移表是数据，而不是藏在 service methods，也就是服务方法里的意大利面式控制流。智能体可以在安全约束下动态修改它，并且热加载，而不必走完整 CI 流程。

这里我个人认为有一个很大的启发。过去很多团队做低代码、工作流引擎、状态机平台，也想把业务控制逻辑显式化，但经常失败在两个地方。一个是表达能力不够，业务稍微复杂一点就绕回代码。另一个是维护成本太高，人类不愿意把每个规则都写成严谨规格。AI 智能体出现后，情况变了。人类不一定要手写所有规格，智能体可以从需求、代码和上下文里帮助生成规格，再由确定性内核验证和执行。也就是说，过去形式化和显式建模太贵，现在 AI 可能把这个成本打下来。这正是文章后面提到的，高可靠软件，比如航空和金融系统，几十年来一直用类似小制品、高保证的方式构建，但对通用软件来说，人力成本太高，直到智能体进入图景。

当然，我们也要注意，原文并没有说 Temper 已经解决了所有软件工程问题。它描述的是 Datadog 的尝试，是一个 constrained framework，受约束的框架，用来把一次性的智能体工具转成安全、可复用、能跨会话和团队累积的组件。它不是说从明天开始，所有应用都应该抛弃传统代码库，全部改成规格驱动。更准确地说，Temper 把一个明确的方向摆出来：当 AI 写代码越来越强，最值得投资的可能不是让它更自由，而是给它更好的轨道、更明确的契约和更硬的验证机制。

那对我们这些在通勤路上听节目的软件工程师和 AI 从业者，具体有什么意义？我觉得可以分三层来看。第一层，最容易落地的是改变你使用 Claude Code 或其他 AI 编程工具的方式。不要只说，帮我实现这个功能。你可以让它先输出状态机、边界条件、数据契约、权限规则和失败场景。哪怕你没有 Temper，也可以把这些规格作为代码评审和测试生成的输入。比如做一个部署任务系统，你先让模型列出任务从待创建、排队中、运行中、成功、失败、取消中、已取消这些状态怎么流转，哪些动作在哪些状态允许，哪些转移必须幂等，哪些状态不能回退。这样后面生成代码时，模型更不容易把控制流写散。

第二层，是把验证从样例测试往属性测试和故障注入推进一点。文章里那四层验证，不是每个团队都能一下做到，但思想可以借。你可以问自己，系统最重要的不变量是什么。比如余额不能为负，任务不能同时被两个 worker 持有，同一个部署不能同时有两个 active rollout，删除租户之后不能再产生新数据写入。然后让 AI 帮你写围绕这些不变量的测试，尤其是随机动作序列测试。对于分布式系统，可以加入可复现的故障场景。重点不是追求形式化完美，而是把验证对象从几个 happy path，扩展到状态空间和失败空间。

第三层，是重新设计给智能体使用的内部工具。很多公司现在只是把原本给人用的命令行、控制台、文档和权限系统开放给 AI。这样做能跑，但不一定安全，也不一定可持续。Datadog 的经验提示我们，给智能体的工具最好小、明确、可解析、默认拒绝、可审计。工具返回的信息要适合机器读，而不只是给人看的长文本。权限失败不要只是报错，而要变成可记录、可审批、可热加载的策略决策。这样智能体不会为了绕过限制去写越来越多胶水代码，人类也更容易知道它卡在哪里。

如果你是一个平台工程团队，文章里最值得借鉴的也许是 control plane 这个视角。以后你管理的对象不只是服务、集群、数据库和部署流水线，还包括 AI 会话、任务队列、角色、工具权限和生命周期。一个长时间运行的智能体，本质上也需要可观测性。它在做什么任务，读了哪些上下文，调用了哪些工具，失败在哪里，是否产生了可复用制品，是否越权尝试过操作，这些都应该进入平台视野。Datadog 是可观测性公司，所以他们天然会从这个角度看问题。对普通团队来说，也可以从最小可行的审计日志和任务状态跟踪开始。

如果你是业务工程师，最直接的实践是把隐式状态机显式写出来。很多事故不是算法不会写，而是状态没想清楚。比如退款流程里，已退款、退款中、退款失败、部分退款、人工介入这些状态，如果散落在代码里，很容易出现重复退款或者卡单。再比如云资源生命周期，创建中、可用、更新中、删除中、删除失败，每个状态允许什么操作，后台任务失败后是否能重试，用户取消时如何处理，如果不显式建模，AI 生成代码时也会继承你的混乱。让 AI 帮你提炼状态机，反过来会逼你发现业务规则里的空洞。

如果你是 AI 工程方向的人，Temper 代表了一种很重要的系统边界划分。大语言模型负责理解意图、提出规格、迭代修正，但编译、验证、执行不放在模型黑箱里，而交给确定性系统。这个边界很像编程语言里的编译器。我们不会因为程序员很聪明，就不需要编译器和类型检查。同样，我们也不应该因为 Claude 很强，就让它直接绕过验证。越强的生成能力，越需要更强的约束和检查。这个思想可能会成为未来几年 AI 原生工程平台的主线之一。

这里也有一些坑要避。第一个坑，是把规格当文档，而不是当可执行制品。很多团队写了很多设计文档，但上线代码和文档慢慢漂移。Temper 的关键恰恰是规格既被验证又被执行。如果你只是让 AI 生成一份漂亮文档，然后代码仍然随意写，收益会大打折扣。第二个坑，是把工具越做越大。给智能体一个超级万能工具，短期方便，长期难以授权、难以审计、难以复用。文章里的机床类比提醒我们，部件应该小到能装进脑子里。小制品更容易验证，也更容易组合。第三个坑，是忽略人的审批体验。默认拒绝如果没有顺畅的待决策记录和热加载机制，会变成到处卡住的官僚流程。安全和效率必须一起设计。

还有一个现实问题是，很多团队会问，我没有 Datadog 那样的规模，也没有资源做 Temper，这和我有什么关系？我个人认为，关系很大，因为这里讲的是瓶颈迁移。今天你可能还在让 AI 修小 bug，但一旦团队接受度提高，智能体能做的事情会迅速扩大。到那时，你会遇到同样的问题：生成不缺，缺的是验证；单次成功不缺，缺的是可重复；临时脚本不缺，缺的是可治理的工具。越早把状态、数据、权限和不变量显式化，越容易在 AI 编程时代接住产能提升。

文章最后把软件工业化和生物进化两个比喻合在一起。工业革命之所以可能，是因为机床让零件可组合、可检查、可替换，我们才能制造越来越大的复杂机器。Sesh 说，如果智能体可以在这种纪律下，在软件工厂里自主构建软件，也许我们不需要停在黑灯工厂。用这种方式构建的软件，开始像一种可以通过反馈、选择和适应来培养和进化的有机体。

这个结尾有点浪漫，但不是空泛的浪漫。Datadog 前面讲的 Courier、BitsEvolve、Helix、Temper，实际上是从手工构建，到进化优化，到智能体大规模构建，再到规格和内核约束的路线。它告诉我们，AI 编程的下一阶段可能不是更炫的补全，而是更严肃的工程化。谁能把智能体的创造力装进可验证、可审计、可复用的生产系统，谁就更有可能真的把 AI 变成软件交付的工业能力。

最后总结一下。Anthropic 这篇文章讲的不是 Claude Code 又能写多少代码，而是 Datadog 在生产实践中发现，AI 生成速度越快，验证和控制就越重要。Temper 的核心思路是让智能体写规格，由确定性内核验证并执行，把隐式控制逻辑变成显式状态机和契约。我个人认为，这篇文章最值得带走的一句话是，未来优秀工程师不只是会让 AI 写代码，还要会给 AI 建机床。只有这样，我们才不是在堆更多临时代码，而是在建设真正能持续运转的软件工厂。
