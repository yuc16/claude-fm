## Script

欢迎收听 Claude FM。今天我们要拆的这篇文章，标题是 Claude Tag now supports personal connectors in channels，翻成中文，大致是《Claude Tag 现在支持在频道里使用个人连接器》。它发表在二〇二六年九月二十四日，也就是三天前，非常新鲜，所以我们不用担心时效性的问题。

先说为什么我觉得它值得占用你二十多分钟的通勤时间。表面上看，这就是一条产品更新公告，某个功能上线了，支持了一个新场景。但你如果做过企业级 AI 的落地，你会知道，真正卡住项目往前走的，往往不是模型能力不够，而是权限这一关过不去。AI 要替你去拿数据，它到底是以谁的身份去拿？是频道这个集体的身份，还是你个人的身份？这个问题看起来只是实现细节，实际上它决定了一个功能能不能通过安全评审，能不能在一个组织里被大规模铺开。

这篇文章给出的，就是 Anthropic 对这个问题的一个回答。而且这个回答相当有讲究，它不是简单地把权限开大一点，而是引入了一条新的边界线。我们今天就来仔细看看这条线划在哪里，为什么这么划，以及划完之后，你手里的活儿会发生什么变化。

文章本身非常短，官方标注的阅读时间只有五分钟。但短不代表浅，它每一句话背后基本上都对应着一个可以展开的设计决策。所以我会花比较多的时间，把这些决策一个一个拆开讲。中间我也会讲一些我个人的理解和推演，哪些是原文说的，哪些是我自己的看法，我会明确地区分开。

先把背景铺一下。Claude Tag 目前还是 beta 状态，它做的事情很直观：让你把 Claude 加进一个 Slack 频道，让它和你的团队一起干活。你在频道里艾特它，它就能看到频道里的上下文，回答问题、做总结、帮忙查东西、协助推进任务。

但 Claude 光靠聊天记录是干不了实事的。它需要连接到外部的工具和数据源，才能真正帮上忙。这些连接，文章里叫 connector，连接器。你可以把它理解成一根根管道，把 Claude 接到你的日历、你的云盘、你的客户关系管理系统、你的代码仓库、你的预发布环境等等。没有连接器，Claude 就只能纸上谈兵；有了连接器，它才能读到真实的数据，做出真实的动作。

问题就出在，这些管道的权限，应该挂在谁身上。

在这篇文章发布之前，Claude 在频道里只能使用管理员挂到频道上的那些连接器。注意这个措辞，是管理员挂到频道上，也就是说，权限的主体是频道，不是人。管理员决定这个频道能连哪些工具，然后频道里的每一个人，只要向 Claude 提问，就都有可能通过 Claude 去使用这些连接器背后的权限。

那管理员是怎么应对的呢？文章里有一句话特别关键。我原样翻译一下：大多数组织是故意把这份清单保持得很短的，因为他们希望访问权限跟着人走，而不是跟着频道走。

这句话值得反复咀嚼。它说的其实是一个很朴素的安全直觉：频道是一个公共场所，成员是流动的，权限挂在频道上，就意味着权限会随着成员的进出而扩散或者遗留下来。今天来了一个实习生，他加入频道的那一刻，就自动获得了这个频道所有连接器背后的数据访问能力。这显然不是管理员想要的。

我们可以打个比方。假设你们公司有一个公共会议室，会议室里放着一台公用电脑。因为所有人都会用这台电脑，所以它上面绝对不能存只有财务能看的东西，也不能登录某个人的私人邮箱。公用设备的权限，必须按照最不信任的那个使用者来设定。频道连接器就是这台公用电脑。

再换一个工程师更熟悉的类比。频道连接器很像一个服务账号，或者叫 service account。它是一个不属于任何具体个人的身份，权限是管理员预先配好的，它的行为不区分是谁触发的。你在云平台上给一条持续集成流水线配的那个机器人账号，就是这个东西。所有人都能触发这条流水线，流水线做的事都记在这个机器人账号名下。这种设计的好处是稳定、可预测、不依赖某个具体的人；坏处是它的权限边界必须画得非常保守，因为你没法针对谁在用它做细粒度的区分。

于是我们就撞上了一个死结。团队想在频道里让 Claude 帮忙处理那些真正有价值的事情，但真正有价值的事情，数据往往躺在只有特定的人才能打开的地方。你的日历上什么时候有空，只有你自己知道；你手上那几个客户账号，只有你是负责人；那份还在起草阶段的方案文档，只有你和另外两三个人有权限。这些东西，管理员是不可能大方地挂到频道连接器上的，因为一挂上去，全频道都能通过 Claude 看到。

这就是老状态的尴尬。能力最强的场景，恰恰是权限上最不可能开的口子。文章里有一句话把这个尴尬说得很透，我翻译一下：人们在频道里需要的大部分东西，其实都锁在他们自己的登录之后。

那这次的新能力是怎么解决这个问题的呢？简单说就是：现在 Claude 可以在频道里，针对你发出的请求，使用你自己的连接器。别人用不了你的，而且你能控制输出怎么呈现。

这句话在原文里出现了两遍，一字不差地重复了一遍，可见这是全文的核心句。这里面有三层意思，我们一层一层来。

第一层，触发条件是"你发出的请求"。不是任何人的请求，是你自己的。这意味着 Claude 在做这件事的时候，执行身份是提问者本人，而不是频道。这是一个根本性的转变。权限不再挂在频道上，而是挂在你身上，只不过这一次使用的动作，是 Claude 帮你完成的。

第二层，前提是"你已经在你的 Claude 账号里连过这个工具"。也就是说，这根管道是之前就存在的，是你个人在私信场景下已经授权过的。现在它延伸到了频道里。权限本身没有被放大。你本来就能看的东西，你在私信里本来就能让 Claude 看的东西，现在你在频道里也能让 Claude 看了。这一点非常重要，因为它意味着这项新能力在理论上不会引入新的权限暴露面。你不是获得了一个新权限，你是把你已有的权限，在另一个场景里用了一次。

第三层，"你能控制输出怎么呈现"。这句话听起来轻描淡写，其实是整个设计里最要紧的一环。因为个人连接器保护的是输入端，它管不住输出端。你把私密数据交给 Claude 处理，Claude 处理完了，如果它直接把结果发到频道里，那频道里的所有人就都看到了。所以必须有第二道闸门，专门管"发不发出去"这件事。

我们可以用一个生活场景来理解这个"输入私密、输出公开"的结构。想象你在一个全员会议上，你低头用手机查了一下自己的银行账户余额，然后你抬起头，把那个数字念给全场听。查的动作是私密的，但念出来的那一刻，它就不再私密了。个人连接器管的是低头查手机这个动作，但它管不了你要不要念出来。念不念，是你的事，也是这第二道闸门要处理的事。

文章里把这个闸门做成了两种模式。一种是 review mode，审核模式，每条 Claude 的回复你都可以先看一眼，确认了再让它发出去。另一种是 auto mode，自动模式，Claude 直接把回复发到频道，除非它判断内容里有敏感信息、需要你审核。这两种模式你可以随时切换。另外文章提到，在企业版计划上，管理员可以要求所有人必须使用审核模式。这一条是给合规敏感的组织准备的，我们后面会再展开。

好，抽象的东西讲完了，我们来看文章给的那个具体例子。这个例子很简短，但信息量非常大，我打算像看比赛回放一样，一帧一帧地拆。

场景是这样的。有一个频道叫 checkout-migration，也就是结账流程迁移，这个频道接了 GitHub 连接器。频道里有个人叫 Priya。她在频道里问 Claude：帮我把我的 Google Drive 文档《结账迁移第三季度》和我们已经上线的东西做个对比，看看还有什么没做完。

我们先看这个请求的结构。它其实混合了两个数据源。一个是"我们已经上线的东西"，这是团队的共享信息，躺在 GitHub 里，通过频道的 GitHub 连接器就能读到。另一个是"我的 Google Drive 文档"，这是一份只有 Priya 自己能打开的文档，频道连接器碰不到它。

Claude 的处理分两半。第一半，它通过频道的 GitHub 连接器去读已合并的拉取请求，也就是已经合进主干的那些改动。这是频道身份在干活。第二半，它通过 Priya 自己的 Google Drive 连接器去读那份文档。这是个人身份在干活。

文章专门说了一句：以前，Claude 会停在这里。也就是说，在旧的能力下，Claude 读完 GitHub 那部分之后就没法往下走了，因为它看不到那份只有 Priya 能打开的文档。你可能会想，那让管理员把 Priya 的 Google Drive 也挂到频道连接器上不就行了？不行，而且这正是问题的核心。一旦挂上去，频道里的任何人都可以问 Claude"帮我读一下 Priya 的结账迁移文档"，然后读到里面的内容。管理员不会为了一个场景开这么大的口子。

现在的情况是，Claude 通过 Priya 的个人连接器读到了那份文档，而且文章强调，这件事是"和频道的工作分开的"，原文用的是 separately from the channel's work。这个分开是两层意义上的分开。一层是数据通路的分开，两条路各走各的。另一层是审计意义上的分开，后面会讲。

然后 Claude 发了一条帖子，说明什么已经上线了、什么还没做完。

接下来是输出的部分，也是我觉得最值得琢磨的部分。Priya 判断她那份计划不敏感，所以用了 auto mode，让 Claude 在发之前自己先筛查一遍这个对比结果。文章的说法是：Claude 会筛查这个对比，然后再发帖。如果要换一份她自己更想先过目的文档，她可以切到 review mode，先看到回复，再让频道看到。

这里有三个细节我想单独拎出来。

第一个细节，这个"敏感不敏感"的判断，是模型做的。它不是一串写死的规则，也不是数据防泄漏系统里那种确定性的策略引擎。它是 Claude 自己在读到内容之后，判断这内容适不适合直接发到频道。这意味着它有一定的概率性，不是一个百分之百可靠的闸门。原文没有讨论它的准确率，我个人认为，把它当成一道软性的提醒是合适的，把它当成合规上的硬控制是不合适的。真正敏感的场景，应该用 review 模式，让人的眼睛来过一遍。文章也说了，企业版可以让管理员强制所有人走审核模式，这个设计我觉得就是冲着这个不确定性去的。

第二个细节，切换模式这件事的粒度。文章的描述让你感觉，模式是跟着具体场景走的，至少是跟着请求走的。Priya 觉得这份不敏感，就用自动；换一份她想先看的，就切审核。这说明它不是一次性的全局设置，而是可以在具体场景里灵活选的。这种灵活度对日常使用很重要，因为如果每次都要人审，效率会掉得很厉害，大家就会开始绕开这个工具。设计上给一个自动的口子，反而能让审核这个安全阀门在真正需要的时候被认真使用。

第三个细节，也是最容易被忽略的：Claude 发到频道里的东西，频道里的每个人都能看到。文章后面专门有一句：Claude 发的任何内容，频道里的所有人都可见。这句话看似是废话，但它是整个功能使用中最容易踩的坑。很多人会把"我用了个人连接器"误解成"我这件事是私密的"。不是的。个人连接器保护的是读取那一端，也就是别人不能用你的连接器去读你的数据。但它完全不保护写入那一端，也就是你让 Claude 基于这些数据产出的内容，一旦发到频道，就是公开的。

打个比方，这就像你有一把只有你能开的保险箱。你能把里面的东西拿出来，这是你的特权。但你拿出来之后贴在公告栏上，那就是另一回事了。特权在保险箱，不在公告栏。

接下来讲审计，这部分对工程师来说可能是最有共鸣的。

文章说，Claude 通过你的连接器做的所有事情，都会出现在那个工具自己的日志里，挂在你的账号下面，就像你今天用私信时一样。而频道自己的工作，留在频道的服务账号下面，也就是你的安全团队已经在关注的那个账号。

这句话翻译成工程师的语言就是：日志归属是分开的。你在 GitHub 上让 Claude 读了一个仓库，GitHub 的审计日志里记的是你的名字，不是某个机器人。你在云盘上让 Claude 读了一份文档，云盘那边记的也是你。频道自己发起的那些操作，记在机器人的名字下。

这个设计的好处是显而易见的。事后追溯的时候，你能清楚地分辨出：哪些操作是某个具体的人借道 Claude 做的，哪些是频道作为一个整体做的事。如果某一个操作出了问题，责任链是清楚的。做过审计的人都知道，最怕的就是所有操作都记在一个共享账号下面，出了事谁也说不清是谁干的。

我自己觉得，这一点是这项功能在企业里能不能被接受的关键。很多安全团队反对 AI 助手接入内部系统，理由不是 AI 不可信，而是 AI 做的事情记不清楚是谁做的、为什么做、什么时候做的。一旦 AI 的操作能够准确地归属到触发它的那个人身上，并且这个人自己的权限边界没有被突破，那么风险模型就从"一个权限巨大的黑箱"变成了"一群很好理解的、权限受限的代理操作"。后者的可解释性和可审计性，是前者完全没法比的。

文章还提到一点：你随时可以断开一个连接器。你决定 Claude 能够到什么，也决定频道能看到什么，这和你今天在私信里使用连接器的逻辑是一样的。这个随时可撤的能力很重要，它意味着个人连接器的授权是动态的、可撤销的，而不是一次授权就永久开着。

然后我们来看管理员这一侧。文章说，个人连接器给管理员提供了更多的治理选项，主要有三种做法。

第一种，提供一套共享的工具，挂在一个 agent 身份下。这个 agent 身份你可以理解成给 AI 准备的一个专用账号，它不属于任何具体的人，权限由管理员统一配置。频道需要依赖的公共能力，都走这条路。

第二种，让频道成员只用个人连接器。这个做法听起来很激进，但它的逻辑很清晰：我不再在频道级别配置任何权限，所有访问都依赖每个人自己已经有的、基于角色的访问控制。也就是说，你本来有什么权限，你就能通过 Claude 用什么权限，一点不多一点不少。这套做法的好处是权限模型极度简单，管理员不需要再单独维护一套 AI 专用的权限体系，直接复用现有的账号体系就行。

第三种，逐个工具地决定。这个工具走共享，那个工具走个人，具体问题具体分析。这是最灵活但也最考验治理能力的做法，因为它需要管理员对每个工具的用途和风险都有清楚的认识。

这三种做法没有绝对的好坏，取决于组织的成熟度和具体场景。但我个人认为，这篇文章最有价值的地方，不是给出了这三种选项，而是它承认了这件事本身没有一个标准答案，必须把决策权留给组织。不同公司对同一个工具的敏感度判断可能天差地别，一个工具在 A 公司是公共信息，在 B 公司就是核心资产。让管理员按自己的实际情况来定，这是对的。

推出节奏方面，文章说个人连接器现在正在 Team 计划上逐步推送，Enterprise 计划会随后跟上。

接下来这一段，我认为是全文最实用的部分，也是最容易被忽略的部分。文章很明确地划了一条边界：个人连接器不能无人值守地运行。

原文的说法是：定时任务，以及任何 Claude 自己发起的事情，用的都是管理员挂在频道上的连接器。那些需要无人值守执行的动作，或者整个频道都依赖的动作，应该使用共享连接器。

为什么要有这条边界？我觉得逻辑很清楚。个人连接器这套安全模型，整个是建立在"有一个具体的人在触发、在决策、在负责"这个前提上的。是 Priya 在提问，是 Priya 判断这份文档敏不敏感，是 Priya 决定用自动还是审核。人是这个模型里的锚点。一旦把锚点拿掉，让它定时跑、让它自己发起动作，那这个模型就散了。没有人触发，就没有归责的对象；没有人审核，就没有第二道闸门。

文章举了一个很具体的对照例子来解释这件事。假设你想把 Claude 加进值班频道，帮忙做持续集成的分诊和响应。这个场景需要 Claude 能够识别问题、甚至帮助修复问题，而且是在工作时间之外。这个时候你就需要配置共享连接器，连到你的运行手册、监控工具、部署历史。这样一来，Claude 在半夜三点也能干活，因为共享连接器是不依赖某个具体的人在场的，它挂的是频道的服务账号，全天候可用。如果你指望的是某个工程师的个人连接器，那到了凌晨三点，那个人在睡觉，这条路就断了。

这个例子其实是在告诉读者：判断一个场景该用个人连接器还是共享连接器，有一个很简洁的判据，就是这个动作发生的时候，有没有一个具体的人在场，并且愿意为它的结果负责。有人在场的、需要用到只有他能看的数据的，用个人连接器。没人在场的、整个频道都要依赖的，用共享连接器。

文章还给了另一个方向的例子，讲的是什么样的频道适合完全依赖个人连接器。答案是：高度被监督的工作。它举的例子是协作起草一份 RFP 响应。RFP 是投标书或者方案书这一类文件，起草的时候经常需要从定价数据或者其他敏感来源拉信息，而这些数据并没有配置给整个频道。这种场景就很适合用个人连接器，因为它是少数几个人在一起协作、每一步都有人在看着的工作。

但这里文章又强调了一遍那句关键的提醒：Claude 发的任何东西，频道里的每一个人都能看到。这句话在这个例子里再次出现，是有意为之的。它是在提醒你，即便这个频道里只有三五个高度信任的人，你发出去的内容仍然是频道级别的可见性。这是使用个人连接器时最需要养成的条件反射：在按下发送之前，先问自己一遍，这段话让频道里的所有人看到，可以吗？

最后还有一个很小的细节，但我觉得挺人性化的。文章说，不需要安装任何东西。当你的某个请求需要用到你的某个连接器时，Claude 第一次会问你一下，然后就这次对话的线程里使用它。这个第一次会问你的做法，就是我们熟悉的授权确认流程。你装一个新应用时看到的那种"是否允许访问你的日历"的弹窗，逻辑是一样的。让你在第一次使用的时候明确地知道发生了什么，而不是默默地在后台操作。这个仪式感本身是有价值的。

好，原文的内容我们基本拆完了。接下来是这部分我特别想聊的，就是这件事对你的实际工作意味着什么。我按不同的角色来分，你可以对号入座，也可以都听一遍，因为很多判断是共通的。

如果你是一个普通工程师，日常就在团队的 Slack 频道里干活，那么明天上班你可能可以做这么几件事。

第一，回顾一下你自己的 Claude 账号里连了哪些连接器。这项新能力的前提是你已经连接过。你如果从来没连过，那这个功能对你就是空的。挑几个你日常最常用的、又在频道协作里真的会用到的，比如你的日历、你的云盘、你的项目管理工具，先把管道铺好。

第二，从审核模式开始，不要一上来就用自动。理由很简单，你需要先建立对它的直觉。让它先跑几条，你在发出去之前看一眼，你会很快明白它的输出风格是什么样的、什么内容它会判断为敏感、什么内容它觉得可以直接发。跑顺了之后再慢慢切到自动，这个顺序比较安全。

第三，养成一个习惯：在让 Claude 读你自己的私密数据之前，先想清楚你接下来要用这个结果干什么。如果只是自己看，那你甚至不需要在频道里问，私信里问就行了。如果你是要把结论发到频道，那你得先接受一件事：这个结论是公开的。

第四，注意你提问的措辞。在这个功能里，Claude 需要判断哪些数据该从频道的共享连接器拿、哪些该从你的个人连接器拿。你如果把问题问得含糊，它可能会尝试用错管道，或者干脆告诉你它拿不到。像 Priya 那样把两个数据源都说清楚，是一个很好的习惯。你说清楚哪些是团队共享的东西，哪些是你自己的文档，Claude 就能更准确地选择路径。

如果你是一个团队的负责人，或者平台、IT 一侧的管理员，这件事对你的要求就更结构性一些。

我建议你做的第一件事，是把现有的频道连接器清单拿出来，按"这个动作需不需要有人在现场"重新分一遍类。需要无人值守的，比如监控告警、定时巡检、值班响应，这些必须走共享连接器，因为个人连接器根本跑不了定时任务。这是一条硬性的技术边界，不是风格选择。

第二件事，考虑你在"逐个工具决定"这个选项上要投入多少精力。文章给了三种治理路线，其中最灵活也最难的是逐个工具地判断。好处是精细，坏处是维护成本高，而且需要有人对每个工具的敏感度有持续的理解。如果你的组织还没有这个精力，那么退一步，"让成员只用个人连接器、完全依赖现有的基于角色的访问控制"是一个很干净的起点，因为它避免了维护一套平行的 AI 专属权限体系。

第三件事，把日志归属这件事同步给你的安全或者合规同事。很多时候，安全团队的反对不是因为功能本身，而是因为他们不知道出了事该怎么查。这篇功能说明里明确讲了日志的分野：个人操作记在个人账号下，频道操作记在服务账号下。把这个说清楚，可能比讲十个功能亮点都管用。

如果你关注的是安全或者合规，我个人觉得有几个点需要特别留心。

一个是自动模式的敏感判断是模型做的，不是规则做的。这意味着它有可能漏判，也有可能有误判。在需要留痕的场景里，把它当辅助，别当控制。企业版支持强制所有人使用审核模式，这个开关的存在本身就说明了官方对这个不确定性的态度。

另一个是幽灵依赖的问题。当越来越多的人用个人的连接器去支撑频道里的协作，就有可能出现这种情况：某个流程实际上默默依赖着某个人的个人连接器，但没有任何人意识到这一点。这个人一旦休假、离职，或者哪天顺手把自己的连接器断开了，那个流程就会在某一天毫无征兆地失效，而且失效的原因还很难查，因为日志分散在好几个工具里。共享连接器不会有这个问题，因为它的归属是明确的、组织级的。所以我的建议是，凡是频道里被反复使用、已经有依赖性质的东西，都应该尽快迁移到共享连接器上，个人连接器只用来做那些一次性的、探索性的、明确属于某个人的事。

再有一个是关于可见性的教育。技术上的闸门只能管到发不发，但发出去之后怎么用，是人的问题。团队需要有一个共识：在这个频道里，Claude 发出来的东西就是公开的。这句话应该像"点回复全部之前先想想"一样，成为一个条件反射。

还有一个坑是很多人会忽略的：个人连接器的可用性，取决于那个人的账号状态。如果一个人离职了，账号被停用了，那么所有依赖他个人连接器的协作方式都会失效。这不是一个能被技术解决的复杂问题，它就是一个组织问题。所以在设计频道工作流的时候，你要主动问一句：如果这个人明天不在了，这套东西还能跑吗？

讲到这里，我想往后退一步，聊一点更宏观的东西，也算是我个人的观察。

这篇文章表面上讲的是一个小功能，但它处理的是企业 AI 落地里一个非常典型的张力：AI 助手到底是"一个人"，还是"一个系统"？

如果你把它当人看，那它的权限应该跟着使用者走，谁问的就用谁的权限，结果也归到谁的名下。这就是个人连接器的逻辑。如果你把它当系统看，那它应该有自己的身份、自己的权限、自己的日志，所有人共用一套。这就是共享连接器的逻辑。

而这篇功能说明给出的答案很有意思：两个都是，看场景。同一个 Claude，在同一个频道里，处理同一个提问，可能会同时用到个人身份和系统身份。Priya 那个例子就是活生生的示范：GitHub 那半边用的是频道的身份，Google Drive 那半边用的是她自己的身份，两边的日志分开记。这不是一个妥协出来的中间态，这是一个经过设计的、有意为之的混合。

我个人认为，这种双身份的架构，很可能就是接下来一段时间里企业级 AI 助手的标准形态。因为现实世界里的权限本来就是这样的。你在公司里既是一个拥有个人权限的个体，也是某个团队、某个系统的一部分。AI 要真正融进工作流，就必须能够同时扮演这两种角色，而不是被硬塞进其中一种。

最后总结一下这篇文章讲了什么。Claude Tag 现在允许你在 Slack 频道里使用你自己的个人连接器，来响应你自己的请求，别人用不了，你能控制输出怎么发。它的前提是你已经连过这个工具，它的边界是只在你触发的时候生效，不会在无人值守的场景里跑。它把日志分得很清楚，个人操作记在个人账上，频道操作记在服务账号上。它给管理员留了三种治理路线，也给企业版留了强制审核的开关。

我的一点点评是这样的。这个功能的设计里，我最欣赏的是它对输出端的诚实。它没有假装个人连接器能让你在频道里拥有一个私密空间，而是反复强调：Claude 发出来的东西，所有人都看得到。这种不粉饰的态度，反而让整套机制变得可信。因为一个安全设计最怕的不是限制多，而是使用者对它的边界有错误的理解。

对听众来说，我的建议就一句话：先去把管道的方向想清楚，再决定要不要用。你要的是"我能读到别人读不到的数据"，那这个功能给你；你要的是"我在频道里的对话不被别人看到"，那这个功能给不了你，你也不该指望任何一个频道里的 AI 助手能给你。搞清这两个诉求的区别，你就不会踩坑了。
