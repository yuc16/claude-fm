今天我们聊的文章标题是 How the product designer who built Claude Design uses it to explore ideas before building them，中文可以译作，打造 Claude Design 的产品设计师，是怎样用它在动手构建之前探索想法的。这篇文章发表于二〇二六年七月二十四日，也就是两天前，来自 Anthropic 的官方博客，作者是 Anthropic 的产品设计师 Nate Parrott。

这期值得听的原因很直接。它不是一篇发布会式的功能介绍，也不是那种泛泛而谈的 AI 改变设计流程。它更像是一位一线产品设计师的工作复盘，讲他为什么需要 Claude Design，怎么把它从一个内部小工具做出来，又怎么在每天的设计、沟通、原型和团队对齐里使用它。对于正在做软件产品的工程师、产品经理、设计师，尤其是已经在用 Claude Code 或类似 AI 编程工具的人，这篇文章给了一个很有价值的观察，AI 不只是帮你更快写代码，它也在把团队形成共识的时间往前压缩。

我们先把背景铺一下。二〇二五年秋天，Nate 是 Claude Code for VS Code 这个项目上唯一的产品设计师。他和两位工程师一起，试图把原来运行在终端里的 Claude Code，重新想象成一个终端之外、更友好的图形界面。这里的 Claude Code，大家可以理解成 Anthropic 面向编码场景的 AI 工具，而 VS Code 则是很多工程师每天都在用的编辑器。他们在九月底发布了测试版，十一月 Opus 四点五到来之后，Claude Code 团队开始非常快地发布新功能。

问题就出在这里。工程师借助 Claude Code 的能力，产出速度明显提高，功能推进得更快更猛。但 Nate 作为唯一的产品设计师，仍然是按照过去熟悉的节奏在交付设计。你可以想象一个产品团队里，工程侧像是突然换上了涡轮发动机，设计侧却还在用原来的手动挡。不是设计师不努力，而是原有工具链的摩擦还在那里。一个界面改动，要想清楚流程，要画不同状态，要做可点击原型，要和工程师解释细节，要和团队讨论方向。工程师速度上来了，设计如果还用完全传统的方法，很容易变成瓶颈。

Nate 一开始的尝试其实很自然。因为 Claude Code 原本运行在终端里，终端里的一切都是文本，所以他也把问题当作文本来处理。他把 Claude Code 的输出复制到 Claude 里，加上一些截图，然后问，嘿，我们想加这么一个功能，你来设计一下。结果并不好。这个失败很重要，因为它说明了一个很多团队都会碰到的问题，单纯把设计需求丢给语言模型，并不等于它就能产出有用的设计。设计不是只读一段需求说明，然后凭空给你画一个屏幕。它需要上下文，需要品牌规范，需要已有产品的形态，需要交互状态，需要团队心照不宣的取舍。

后来 Nate 花了大概一个月，把这件事当成副项目来琢磨。他最终发现了一个关键点，Claude 很擅长 HTML。我们平时提到 HTML，往往想到网站页面，想到前端的结构标记。但 Nate 的理解更进一步，HTML 其实是一种丰富的、互动的视觉媒介。你能在幻灯片里做的东西，能在视频文件里呈现的东西，能在 PDF 里排版的东西，很多都可以用网页的方式表达出来。网页不只是网页，它可以是演示文稿，可以是交互原型，可以是动画，可以是一个小工具，也可以是一份会动的备忘录。

于是他让 Claude 生成 HTML，并且给它做了一个分屏界面。左边是聊天，你和 Claude 说要什么。右边是输出，你马上看到它生成的视觉结果。这个形式听起来非常简单，但它把语言模型的优势和视觉反馈连接起来了。原来你跟模型说，请帮我设计这个功能，模型返回一段描述，你还得靠脑补。现在它直接给你一个可看的、可点的、可分享的东西。这个转变很像从读菜谱变成现场试吃。你不再只是讨论这个菜应该咸一点还是甜一点，而是尝一口之后说，这里再加一点酸味，那边火候再轻一点。

不过，光有 HTML 还不够。产品设计不是在空白画布上随便画一个漂亮页面。真正困难的地方在于，它要符合产品和品牌。一个 Anthropic 的页面为什么看起来像 Anthropic，一个 Claude 的产品界面为什么让人觉得是 Claude，这里面有字体、颜色、资产、排版、按钮风格，还有更抽象的原则。Nate 接下来做的事，就是把 Anthropic 品牌的精髓提炼成 prompts，也就是提示词。他把这些字体、颜色、素材和产品原则放进工具的上下文里。这样当他输入自己的需求时，输出结果天然就会遵守 Anthropic 的品牌指南。

这个细节对我们做软件的人非常有启发。很多人试用 AI 设计时，会觉得它第一次出来的东西有点像样，但放进自己产品里就很怪。原因往往不是模型完全不会设计，而是你没有把产品的设计语言喂给它。就像你让一个新同事第一天就做一个核心页面，却不给他任何 Figma 文件、组件库、品牌手册、已有页面截图，只给一句话说，做得高级一点。那他大概率会做出一个看起来像模板网站的东西。Claude Design 的早期价值，就来自把这些上下文装进来，让模型不是在真空里发挥，而是在你的产品语境里协作。

Nate 把这些东西做成一个小型内部原型，分享给团队。结果产品设计师马上用起来，尤其是拿它做交互原型。在传统设计工具里做一个可点击原型，通常需要把每一个屏幕的每一种状态都 mock 出来，也就是先画出来，再手动把按钮和跳转连起来。比如你要演示一个设置向导，第一步输入信息，第二步选择权限，第三步确认，第四步出现错误状态，第五步成功返回首页。传统做法是画很多张画布，然后一个一个接线。Claude Design 的方式更像是，你把素材给 Claude，然后说，让它跑起来。它交付的每个 artifact，也就是生成物，都有一个链接，可以像分享文档一样分享出去。

这里我们要停一下，理解 Claude Design 和传统设计工具的差别。它不是简单把 Figma 的画布换成 AI，也不是把设计师变成一句提示词工程师。它更像是把早期想法的表达成本降得非常低。过去你脑子里有一个方案，想让同事理解，可能要画半天。现在你可以在会议中间，让 Claude 帮你生成一个足够像样的可视化版本。这个版本不一定是最终设计，但它能让讨论从抽象语言变成具体对象。团队不再争论，我理解的这个功能是不是你说的那个功能，而是指着同一个东西说，这里不对，那里可以保留。

文章里有一个很有意思的转折。Nate 第一次真正意识到 Claude Design 有多有吸引力，是在 Anthropic Labs 团队一次 offsite，也就是线下团队活动里的 idea pitch session，想法提案环节。现场每个人都用它快速拼出幻灯片，有些人甚至是在会议中途、轮到自己发言之前才开始做。这个场景特别生动。以前做汇报，幻灯片往往是会前好几天就开始准备。现在人们在讨论过程中就能把想法整理成可展示的视觉材料。那场会让 Labs 团队决定投入人力，于是 Claude Design 从一个副项目，变成了真正的项目。

也正是在这个阶段，团队不再把 Claude Design 描述成一个产品 mockup 工具。它变成了一个用于生产各种视觉沟通材料的工具。文章提到的类型包括幻灯片、落地页、可以打印成 PDF 的 one pager，也就是一页纸说明，邮件、动画、社交媒体视觉素材。Nate 的说法是，它比产品设计高一层，他把它看成一种和 Claude 协作完成视觉内容的方式，而这些视觉内容最主要的任务是沟通和构思。

这个表述非常关键。我们平时说设计，常常马上想到 UI 设计，按钮在哪里，字号多大，卡片阴影多深。但在产品团队里，更大量的视觉工作其实发生在决策之前。你要说服团队为什么这个方向值得做，要把一个复杂系统讲给客户或老板，要比较几个方案，要让工程师理解一个交互想法，要让销售团队拿着一页纸去解释新功能。这些都不是最终产品界面，却都需要视觉表达。Claude Design 瞄准的正是这类工作，早期、快速、可分享、用于沟通。

随着模型的视觉能力变强，Claude Design 能做的事情范围和质量也会提高。文章里提到，最新的 Opus 级模型 Claude Opus 五，比之前的 Opus 模型更擅长阅读图表、图示和截图。因此，当它和 Claude Design 结合时，在生成可以拿去演示的幻灯片和备忘录方面会更强。这里背后的逻辑很清楚。视觉沟通不仅是生成视觉，也包括理解已有视觉材料。你给它一个截图，它要知道界面里有哪些区域。你给它一张图表，它要读懂趋势。你给它一个架构图，它要理解节点之间的关系。模型看懂得越好，设计输出就越不容易变成漂亮但空洞的壳。

当然，Nate 也很明确地说了 Claude Design 不是什么。首先，它没有图像模型，也不是为图像生成打造的。所以它不适合 logo 设计。虽然这并没有阻止一些人尝试让它做 logo，但更好的做法是，把你已经有的 logo 和品牌资产带进来。也就是说，不要把它当成从零生成品牌视觉的魔法机器，而要把它当成一个会使用你已有资产、帮你排列组合、生成选项和起点的协作者。

这个边界非常实用。现在很多 AI 工具的宣传都容易让人以为，一切都可以从一句话开始。但在真实工作里，从零开始未必是优势。你所在的公司已经有品牌规范，产品已经有组件，用户已经熟悉某些交互。Claude Design 的价值不是推翻这些，而是在这些约束里帮你快速探索。它会产生多个选项和起点，你再选择其中好的部分，或者把多个版本组合起来。这个流程更接近一个有耐心的设计搭档，而不是一次性给你最终答案的设计神谕。

第二个边界是，如果你要发布生产软件，还是应该使用 Claude Code。Claude Code 是用来编码的，Claude Design 负责设计工作的其他部分，比如早期构思、协作，或者在任何人真正承诺开工之前，先争取大家对某个方向的认可。文章还提到两者可以往返协作。你可以把在 Claude Code 里开始的原型同步到 Claude Design，在画布上迭代和编辑。也可以把 Claude Design 里已经准备好构建的原型交给 Claude Code 去实现。

这段话其实点出了未来软件开发流程的一个变化。随着模型越来越会构建生产软件，真正决定成败的工作，会越来越前移。以前很多团队的瓶颈在实现，想法有了但做不出来，或者做得太慢。现在实现成本下降，瓶颈就会变成想法是否足够好，团队是否对齐，用户反馈是否来得足够早。如果十个功能都能比较快做出来，那更重要的问题就不是谁敲代码更快，而是我们到底该做哪一个，为什么做，做成什么样才是对的。

Nate 接着分享了他自己每天怎么用 Claude Design。他说自己会把它用于 bread and butter design work，也就是日常基础设计工作。比如为早期想法做线框图，或者一次生成十五个流程版本，拿去向同事收集反馈。这里的十五个版本不是说每一个都要精雕细琢，而是把探索的宽度打开。传统设计里，设计师也会做多方案，但每多一个方案都有手工成本。AI 把这个成本降下来之后，团队可以更早看到更多可能性。

他举的例子很有意思。第一个是 Claude Design 的 intro animation，也就是用户注册 Claude Design 时播放的介绍动画。这个动画就是用 Claude Design 自己做出来的，但不是直接让它吐出成品动画。Nate 说自己不是动画师，所以他先让 Claude Design 为自己构建了一个定制的视频编辑器，然后用这个编辑器做动画。这个例子非常能体现 HTML 作为媒介的力量。工具不只是产出一个东西，它还能先产出一个新的小工具，让你用这个小工具继续创作。

第二个例子是一个地铁到站时间应用，带有可调节的动画控制，用来调运动效果的物理参数。大家如果做过前端动画会知道，动效的手感很难靠一句话说清楚。是快进慢出，还是有一点弹性，是像纸片滑动，还是像真实物体带惯性。用滑块调参数，比反复对模型说再自然一点、再轻一点，要高效得多。Claude Design 在这里不只是做界面，也帮助设计师做出可以调试体验的环境。

第三个例子是类似 Instagram 的颜色控制。Nate 不是用语言描述颜色，而是让 Claude 做滑块和预设，让他可以调整一个应用的配色方案。这个细节也很现实。很多视觉选择很难用文字准确表达。你说蓝色更柔和一点，模型未必知道你想要的是饱和度下降，亮度提高，还是色相偏青。可如果给你滑块，你就能像调照片一样直接试。

第四个例子是 Claude Design 自己的重设计。Nate 和两位队友 Helen、Andrew，在 Claude Design 里面一起 riff，也就是即兴发散，探索编辑器的新设计。他明确说不会照原样发布，但这是他们探索产品未来形态的方法。这个说法我很喜欢，因为它把 AI 生成物放在正确位置上。它不是最终交付物，而是思考材料。就像白板上的草图不会直接上线，但它能让团队共同看到某个方向。

文章后半部分是非常实用的最佳实践。第一条是，提示之前先思考。Nate 说，要得到最符合愿景的输出，最好也最高效的方式，就是一开始就告诉 Claude 你需要什么。他会花很多时间在设计前写 prompt。有时他在 Claude Design 里用语音按钮口述，有时坐在沙发上用手机备忘录打字，有时散步时录语音，之后把转写文本贴进去。无论你喜欢哪种沟通方式，关键是在离开电脑的时候先想清楚你要什么，这样坐下来时 Claude 才能执行你的具体愿景。

这对工程师也很适用。很多人抱怨 AI 给的结果不稳定，其实有时候是我们自己没有把问题想清楚。你让模型帮你设计一个设置页面，但你没说用户是谁，核心任务是什么，应该突出哪一个操作，已有产品是什么风格，哪些信息必须出现，哪些可以省略。模型当然只能用自己偏好的套路填空。Nate 的建议不是把 prompt 写得花哨，而是把思考前置。好的 prompt 本质上是一份简短但清晰的设计 brief，设计简报。

第二条是，告诉 Claude 它应该长什么样。如果不加引导，Claude 会选择它偏爱的某种审美。Nate 说你可能已经能认出来那些风格。避免这个问题的方法，是明确字体和颜色，或者提供 moodboard，也就是情绪板，放一些作为灵感参考的图片。你也可以让 Claude 先头脑风暴字体和颜色搭配，然后来回讨论，直到某一组搭配感觉对了。

这里我个人认为，对国内团队尤其重要。很多 AI 生成界面会有一种国际 SaaS 模板感，白底、大圆角、渐变、卡片、轻阴影，看上去都还不错，但很难和具体业务贴合。如果你做的是开发者工具，它的气质可能要克制、密集、可扫描。如果你做的是企业管理系统，它可能要强调稳定、信息密度和权限层级。如果你做的是消费者应用，它的视觉情绪又完全不同。所以不要只说做得现代一点，要具体说你想要的字体气质、颜色范围、参考对象和情绪。

第三条是，把重复工作变成设计系统。你可以上传品牌文件和资产，比如 logo、幻灯片、截图、字体规范，以及任何你会重复使用的东西，Claude 会分析它们并生成一个设计系统。这样之后每个 artifact 都从你的选择开始，而不是从空白开始。这个流程和软件工程里的抽象复用很像。我们写代码不会每次从零写按钮、表单、弹窗，而是有组件库。设计工作也一样。AI 如果每次都从空白开始，就会不断发散。设计系统相当于给它一个轨道，让速度变快的同时不至于跑偏。

第四条是，让它给十个选项，然后 remix，也就是混合重组。Nate 的原话意思是，大多数不会好，这没关系，一两个会好。然后你可以说，我喜欢 B 选项，也喜欢 D 选项的一点点，请给我五个把它们揉在一起的新版本。这个方法很值得练习。和 AI 协作时，不要期待一次命中。更有效的方式是先发散，再收敛，再局部重组。就像你和一个设计实习生共创，第一轮先让他多拿些方向出来，你圈出有意思的部分，再让他沿着这些部分继续推。

第五条是，描述不出来就画。假如你脑子里有一个布局，但找不到合适的语言，那就画在纸上，拍照上传。这个建议看似简单，却很重要。很多空间关系用语言说非常费劲。比如左上角要有一个窄的状态面板，中间是三列任务卡片，右边是一条可以收起的详情栏，底部还有一个跨列的时间轴。你说半天，模型可能理解错。手绘草图哪怕很丑，也能传达结构。AI 的强项是从模糊输入里补全细节，不一定需要你画得像专业线框图。

第六条是，指着说。与其写一大段文字说明你指的是哪个元素，不如点中它，然后说话。前提是你的设备开启了听写，然后选择 comment，也就是评论，点进评论框。你的话会像打字一样出现在评论框里。这其实是在把人类最自然的协作方式搬进工具。现实里我们和同事看一个设计稿，不会说，从左上角算起第三个容器里的第二行文字下方的按钮。我们会指着屏幕说，这个，往下一点。Claude Design 如果能支持这种点选加语音，就能减少很多沟通成本。

第七条是，当保真度不重要时，先做线框图。要求生成 wireframe，也就是线框图，会快很多，也能让 Claude 把注意力放在设计的高层结构，而不是视觉细节上。这非常适合快速尝试不同想法。很多团队容易太早陷入颜色、圆角、图标这些细枝末节。其实在早期，更重要的是信息架构对不对，用户流程顺不顺，关键操作有没有被放在正确位置。线框图就像建筑的平面草图，先判断房间怎么连，再讨论墙面刷什么颜色。

第八条是，最后一公里手动做。Nate 建议，对于最终的小调整，比如重新排列、删除、编辑文字、调整大小、改颜色，使用直接编辑工具，而不是继续 prompt。直接编辑不消耗 token，也就是模型上下文和计算资源，而且尺寸和对齐这类小事，本来就更适合靠眼睛判断。这个建议很务实。AI 协作不是所有事情都要通过自然语言完成。你明明可以拖一下解决，就不要写一段话让模型猜。好的工作流一定是人和模型各做擅长的部分。

第九条是，给 Claude 真实上下文。如果你是在为一个已有应用或网站设计功能，可以连接 GitHub。Claude 会获取你的组件和已有屏幕，并以它们为起点。经过几次尝试，它可以以很高的保真度重建你已有的设计。文章还提到，Web search，也就是网页搜索，以及 MCP 连接也可以在 Claude Design 中使用，只要你的设计依赖外部信息。这里的 MCP 可以理解为模型上下文协议，用来把外部工具和数据源接入模型工作流。

对工程团队来说，这一点可能是最接近生产力提升的。真实设计从来不在孤岛里发生。你要改一个支付页面，就要知道已有组件长什么样，错误状态怎么展示，后端有哪些字段，文案风格是什么，竞品怎么做，用户反馈里抱怨什么。连接真实上下文之后，Claude Design 才不是生成一个看起来漂亮但无法落地的平行宇宙版本，而是沿着你当前产品继续长出来的分支。

第十条是，继续和 Claude 并行工作。你不必等 Claude 完成一个结果再继续提新修改或新任务。你可以一次排队多个消息，也可以在它还处理上一轮时继续说。这反映的是另一种协作节奏。我们过去使用工具，通常是发出一个命令，等待完成，再做下一步。和 AI 协作时，更像是跟一个动作很快但还需要方向的伙伴一起工作。你可以边看边补充，边发现问题边交代后续。这样会减少等待感，也更接近真实的设计讨论。

文章最后引用了 Bret Victor 的一个演讲，叫 Stop Drawing Dead Fish，中文可以理解成，停止画死鱼。简介里有一句话，所有我们画出来的东西，默认都应该是活的。Nate 鼓励设计师，无论是在 Claude Design 里，还是在任何工具里，都思考怎么让作品活起来。他最喜欢的 Claude Design 作品，是那些无法塞进既有分类的东西。比如带交互模拟的文档，会和你说话的幻灯片，本身也是视频的图示，既是设计也是自己编辑器的设计。

这段其实把全文的精神抬高了一层。为什么 HTML 是一个很重要的媒介？因为它不只是静态画布，它能响应、能计算、能动、能被点击、能嵌入数据。过去很多设计交付物像是死鱼，一张张静态图，能看但不会动。真实软件却是活的，它有状态、有时间、有反馈、有输入输出。Claude Design 让设计师更容易用代码，特别是 HTML，去创作这些活的东西。不是要求每个设计师都成为前端工程师，而是让他们能借助模型进入一个原本门槛较高的表达媒介。

我个人认为，这对工程师也有一个反向启发。很多工程师习惯于先把东西做出来，再让别人看。因为写代码本来就是我们的强项。但如果早期视觉和交互原型变得非常便宜，我们就不必每次都用生产代码来验证想法。你可以先用 Claude Design 做一个假但可点的版本，和产品、设计、销售、客户成功甚至真实用户聊一轮。等方向基本对齐，再进入 Claude Code 或其他工程实现工具。这样减少的不是代码量本身，而是返工量。

当然，也要避免几个坑。第一个坑是把 Claude Design 当成最终裁判。AI 生成的多个方案只是候选，不代表它知道你的业务目标。最终判断仍然要回到用户任务、商业目标、技术约束和品牌一致性。第二个坑是过度追求视觉精致。早期原型越精致，越容易让团队误以为方向已经定了，反而不敢提出结构性问题。如果你想讨论流程，就用线框图。如果你想讨论品牌情绪，再提升保真度。第三个坑是不给上下文。没有上下文的 AI 输出，短期好看，长期会让产品风格碎片化。

如果你明天就想把这套思路用到工作里，可以从一个很小的场景开始。比如你正在设计一个新功能，不要先打开传统设计工具画最终稿，而是先写一段设计 brief。说明用户是谁，场景是什么，成功结果是什么，必须出现哪些信息，已有产品风格是什么，你想避免什么。然后让 Claude Design 或类似工具生成三个低保真流程。拿给同事看时，不要问好不好看，而是问，你能不能看懂用户下一步要做什么，哪个地方让你困惑，哪个方案最符合我们要解决的问题。

第二步，把团队常用资产整理出来。把 logo、组件截图、已有页面、字体和颜色规范、过去的幻灯片模板放在一起，让模型先学习你的语言。这个动作很像给新人办入职。不要让每次设计讨论都从解释公司长什么样开始。尤其是工程团队，如果你们有前端组件库，有 Storybook，有设计 token，有 GitHub 仓库，那这些都是非常有价值的上下文。把它们接入之后，AI 才更可能沿着你的系统设计，而不是自己发明一套。

第三步，改变评审方式。传统评审常常是一两个高保真方案摆上来，大家围着细节挑毛病。使用 Claude Design 这类工具之后，可以把评审前移成探索会。会前每个人都可以快速生成几页视觉材料，会议里不急着定稿，而是把不同方案的优点拆出来，像 Nate 说的那样，把 B 的结构和 D 的视觉情绪揉在一起，再让模型继续生成变体。这样评审不再只是批改作业，而是真正的共同构思。

第四步，保留手工判断。越是 AI 能快速生成，越要让人类判断变得清晰。你要知道什么叫好。是更符合品牌，还是更能降低用户认知负担，是更容易实现，还是更能帮助销售讲清价值。如果团队没有标准，AI 会制造更多选择，反而让人更焦虑。Claude Design 能帮你摆出十条路，但不能替你决定公司该往哪走。

最后我们回到文章本身。Nate 说，Claude Design 之所以形成现在的样子，是因为 Anthropic 内部的人不断发现他原本没有计划到的用法。它现在已经以测试版形式提供给 Claude Pro、Max、Team 和 Enterprise 计划用户。文章的结束语是，希望大家试试看，并把它带到他们还没有想到的地方。

总结一下，这篇文章讲的不是一个单点功能，而是一种新的设计工作流。Claude Design 把 HTML 变成设计师和模型共同使用的视觉媒介，让早期想法可以更快变成可看、可点、可分享的东西。它的边界也很清楚，不负责生产级编码，不擅长从零生成 logo，最后的细节仍然需要人手工把关。

我个人认为，它最重要的意义，是让软件团队在写代码之前，更早、更低成本地看见想法。未来 AI 编程越来越强时，真正稀缺的可能不是把功能做出来的能力，而是提出好方向、让团队对齐、在想法还便宜的时候收集反馈的能力。Claude Design 正是在这个位置上，补上了从想法到共识之间的那块画布。
