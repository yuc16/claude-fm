英文标题是 How Warp builds self-improving agents on Claude，中文可以翻译成 Warp 如何基于 Claude 构建自我改进的智能体。这篇文章发表于二〇二六年八月二十六日。今天是二〇二六年八月三十日，所以这是一篇非常新的文章，基本上就在我们这一周的技术语境里。它来自 Anthropic 的 Claude 博客，讲的是 Warp 这个 AI 终端和 agentic development environment，也就是智能体化开发环境，怎样在 Claude Platform 上做出一种很简单，但非常有工程味道的自我改进 agent 模式。

这期值得听，是因为它不只是讲一个产品案例，也不只是说我们用了 Claude，效果很好。它真正讨论的是一个大家在做 agent 时都会撞上的问题：agent 第一次看起来很聪明，但用久了之后，它犯的那些小错、重复错、领域知识错，会不会自动变少？如果不会，那这个 agent 很快就会从助手变成噪音源。Warp 的做法很有意思，它没有把重点放在无限调 prompt，也没有说必须训练一个新模型，而是把人类反馈变成一条可持续的工程闭环，让 agent 的知识像代码一样被修改、审查、合并，然后在下一次运行里生效。

我们先把背景讲清楚。现在很多团队做 agent，最容易从一个 prompt 开始。比如你要一个代码审查 agent，就写一段指令，告诉它检查重复代码、注意性能问题、指出潜在 bug、遵守团队风格。第一次跑出来可能还不错，十条评论里面有八条是对的。听起来八十分已经可以上线了，对吧？但在真实产品里，八十分经常是不够的。因为剩下那二十分错误，不是安静地待在那里，而是会直接打断人的工作流。

想象一下你在早高峰地铁上看同事的 PR，也就是代码合并请求。旁边有一个 agent 给你留了五条评论，其中三条有价值，一条可有可无，一条完全误解了你们团队的命名习惯。你第一次会觉得还行，毕竟省了点时间。第二次它又犯同样的错，你会皱眉。第三次你发现自己每次都要解释同一个约定，甚至要在评审里告诉别人忽略这个 agent 的建议。这个时候，agent 不再是生产力工具，而是制造背景噪音的工具。

原文说 Warp 就是在内部代码审查 agent 上遇到了这个问题。Warp 是一个面向开发者的 AI 驱动终端和智能体开发环境，它构建在 Claude Platform 上。他们的团队一开始让内部的代码审查 agent 帮工程师看代码，但工程师反馈说，这个 agent 会给出没有帮助的评论，输出质量也不稳定。这里的重点不是 agent 完全不能用，而是它经常差一点。差一点在 demo 里可以接受，在真实团队协作里就很烦。

Warp 一开始也用了很多团队会用的临时办法。比如看到某次代码审查失败了，就手动改 prompt，把那条失败经验写进去。这样当然会让下一次输出更可用一点。再比如改进 AGENTS 点 md 这类上下文文件，让 agent 多知道一些项目约定。这个也有帮助。但原文强调，这些都不是完整解法，因为它们不规模化。你不能指望每一次低质量输出之后，都有人专门去整理经验、重写 prompt、维护上下文。更麻烦的是，这类修改往往会越堆越长，最后 prompt 变成一锅粥，既难读，也难判断哪条指令真的还有效。

Warp 最后意识到，真正的问题在于反馈会消失。一个 agent 无论是做代码审查、写规格文档，还是给 issue 做分诊，它和用户的交互通常都发生在一个会话里。会话结束之后，用户对它说的那句这个建议不对，或者这里应该打某个标签，或者这个评论很有用，往往就不再进入下次运行。也就是说，最有价值的领域知识，明明已经由人类在工作中表达出来了，却没有沉淀进 agent 的长期记忆里。

这就像带新人。新人第一次写代码 review，不知道团队约定，你告诉他这里我们全局变量有特定命名方式。第二天他记住了，第三天做得更好，这叫学习。但如果这个新人每天早上都会失忆，每天都从同一个初始说明书开始工作，那你会崩溃。很多 agent 的真实状态就是这样。它可能有很强的推理能力，但缺少一个把团队反馈积累起来的机制。

Warp 的解法叫基于 Agent Skills 的框架。这里的 skill 可以理解成技能文件，或者文件化的知识编码。它不是把所有知识直接塞进原始 prompt，而是用普通文件保存 agent 执行任务所需的原则、领域知识、资源引用和操作指引。agent 做事的时候可以读取这些 skill，就像一个工程师做任务时查团队规范、查设计文档、查脚本一样。

这篇文章最核心的模式其实非常简单：一个内层 base skill，一个外层 improver skill，中间夹着人类反馈。base skill 可以翻译成基础技能，它负责具体任务本身，里面放的是功能领域知识和执行指令。比如代码审查 agent 的 base skill 会说明什么样的问题值得评论、项目里有哪些命名约定、哪些类型的建议要避免、审查时要关注哪些风险。当一个 PR 被打开，代码 agent 就拿着这个 base skill 和当前代码上下文，生成审查意见。

中间这一层是人类反馈。原文特别强调，人类反馈是自我改进循环的关键组成部分。对于代码审查来说，最简单的反馈可以是点赞，表示这条评论有用。但越具体越好。Warp 创始人 Zach Lloyd 在文中举了例子。人可以说，这是一条好的、有用的评论。也可以说得更具体，比如你建议重命名这个变量，但我们代码库的约定是，这种全局变量要用某一种命名上下文。后面这种反馈的价值就大得多，因为它不仅告诉 agent 你错了，还告诉它下一次怎样做才对。

外层 improver skill 可以理解成改进技能，或者观察者 agent 的技能。它不是每次任务都跑，而是按计划运行。比如每天一次、每隔一段时间一次，具体文章没有限定。它会拉取一段时间内积累的人类反馈，把 agent 当时提出的建议和人类后来的回应放在一起比较，然后提出一个很小、很聚焦的 base skill 修改。注意这里的关键词是小而聚焦。它不是看见几条反馈就大改整个系统，而是尽量捕捉一个明确的规律，改动一小段技能文件。

为什么这个模式在工程上很舒服？因为 skills 是普通文件。普通文件就意味着 agent 非常擅长读写它们，也意味着人类可以像审查代码一样审查这些修改。外层 improver skill 提出的更新可以走正常的 PR 和 code review 工作流。有人看，有人批准，有人合并。合并之后，下一次内层 base skill 运行时，就自动继承了这次改进。

这点很重要。很多人听到自我改进 agent，会本能地担心：是不是 agent 自己改自己，然后越改越偏，最后没人知道发生了什么？Warp 这里的答案不是完全放手，而是把改进变成可审查的文件变更。agent 可以提出修改，但人类决定是否合并。它把学习速度和治理机制结合起来了。这跟软件工程里的持续集成很像。你可以自动跑测试、自动生成修复建议，但进入主分支之前，仍然需要团队认可。

原文说，Warp 现在已经把这种模式用于整个开源仓库，包括分别用于写规格、代码审查和 issue 分诊的 agent。每类 agent 都有自己的自我改进循环。也就是说，这不是只适用于代码审查的一个小技巧，而是一个可复用的模式：任何反复处理相似任务、并且能从人类反馈中学习的 agent，都可以这么设计。

我们再细看这套方法为什么有效。它首先解决的是上下文位置的问题。传统 prompt 调优经常把所有东西塞进 prompt。规则、例子、例外、团队偏好、历史失败案例，全部塞进去。结果就是 prompt 越来越长，模型每次都要消化一大坨东西，而且很多信息在当前任务里未必相关。skill 文件的思路更像工程文档。知识不一定都出现在原始 prompt 里，但 agent 可以在做事过程中查到它。这样既避免 prompt 失控，也让知识结构更清楚。

第二，它解决的是反馈生命周期的问题。普通会话里的反馈是短命的。你在 issue 下留了一句评论，下一轮 agent 不一定知道。Warp 的 improver skill 会专门去收集这些反馈，把它们转成技能文件里的长期知识。这样反馈就不只是纠错，而是训练组织能力。今天一个维护者解释了一个标签的含义，明天所有类似 issue 的分诊都可能变得更准。

第三，它解决的是人机协作边界的问题。人类不需要学习一个额外系统来反馈 agent。文章里提到，反馈应该发生在人们已经工作的地方。比如直接在 PR 或 issue 里评论，而不是再打开一个表单、再提交一次评分。Zach Lloyd 说，低摩擦才能让信号持续流动。如果你让反馈太麻烦，你就拿不到反馈，也就无法改进 skill。这句话对很多内部 AI 工具都很扎心。我们经常设计了一个看起来完整的反馈按钮，但没人点，因为它不在工作流里，或者点了之后还要解释太多。

Warp 文章后半部分给了一些写自我改进 skills 的经验，我把它们用更口语的方式拆一下。首先是写原则，不要写死规则。Zach 的说法是，要像指导一个聪明人那样写 skill，而不是像给计算机编程那样写。比如你可以写，注意重复代码。这个原则给了 agent 一个方向，它会结合上下文判断哪里算重复、哪里只是必要的相似。相反，如果你试图列出所有变量命名规则、所有函数形态、所有边界条件，最后可能既写不全，又限制了模型的泛化能力。

这里有一个很实用的类比。你带一个资深新同事，通常不会说如果变量长度超过十二个字符并且出现在第三层目录就怎样怎样。你会说，我们这个项目里更在意可读性，遇到重复业务逻辑要优先建议抽象，但不要为了抽象牺牲局部清晰度。这种话不是形式化规则，却能帮助聪明人做判断。大模型恰好也是更擅长理解这种带有目的和取舍的指令。

接着是解释为什么。不要只告诉 agent 做什么，还要告诉它为什么这么做。原因很简单，why 可以让 agent 在没见过的新场景里推理。如果你只说某个标签应该加在某类 issue 上，它可能机械套用。如果你解释这个标签的目的是让贡献者知道可以开始写产品和技术规格，即使具体界面方案还没定，它就更可能在新的 issue 上做出正确判断。原文后面的案例正好就是这个。

再来是让反馈容易给。这个原则看起来简单，但它往往决定系统能不能跑起来。对于开发团队，最自然的反馈位置就是 PR 评论、issue 评论、代码审查回复。你不应该要求工程师审查完 agent 的评论之后，再去另一个仪表盘打分。因为真实工作里，大家忙的时候会跳过所有额外步骤。自我改进系统最需要的是持续信号，不是一次性高质量调研。低摩擦的反馈入口，才是循环能转起来的前提。

还有一个建议是保持 skills 小，并且使用渐进披露。渐进披露就是不要一次把所有东西倒进上下文里。一个好的 skill 文件不应该特别巨大，而应该引用资源文件和脚本。agent 需要的时候再查，不需要的时候就不占上下文。对工程师来说，这其实很像模块化。你不会把整个代码库复制进一个文件，你会用清晰的文件结构、脚本和文档组织知识。skills 也一样。

原文还说，反馈质量大于数量，但数量也有帮助。一个资深工程师给出少量非常具体的领域反馈，可能比很多随手点赞点踩更有价值。因为二元反馈只能告诉你好或者不好，却很难告诉你为什么不好。Zach 说，如果反馈来自了解领域知识的人，而且非常详细，就算样本量相对小，也能得到很好的信号。当然，如果高质量信号的语料更大，效果会更好。Warp 在自己的开源仓库里有很多贡献者，也会做大量代码审查，所以它们能积累相当多的反馈。

最后一个经验是，要多花力气写 improver skill。因为 improver skill 是观察者，是把反馈转成技能更新的那一层。原文说，除去具体领域知识的部分，改进机制本身相当可复用。代码审查 agent 的 improver skill，和其他 agent 的 improver skill，差别没有那么大。换句话说，一旦你把观察反馈、提炼规律、生成小修改、写清楚变更理由这套能力做好，它可以迁移到很多任务上。今天用在代码审查，明天可以用在客服回复、测试用例生成、告警分诊、需求澄清。

文章里最具体的案例，是 Warp 的 issue triage agent，也就是 issue 分诊智能体。我们把这个流程完整走一遍，因为它特别适合理解这套架构。场景是，只要有人在 GitHub 上提交一个新 issue，就触发一个 GitHub Action。GitHub Action 可以理解成 GitHub 里的自动化工作流。它会启动一个 agent，分析这个 issue 的复杂度和可行性，给它分配标签，并建议一个修复方向。

这个分诊 agent 运行时依赖一个内层 skill 文件。这个文件里保存了领域知识，比如每个标签是什么意思，分诊前应该怎样研究代码库，什么时候该判断为简单问题，什么时候该认为需要更详细设计。这里的关键是，标签不是随便贴的。开源仓库里标签会影响贡献者如何参与，也会影响维护者如何排优先级。如果 agent 少贴一个重要标签，后面的协作就可能慢下来。

原文中的样例 issue 里，第一阶段的内层 skill 做得还不错，但漏掉了一个标签，叫 ready to spec。这个标签表示贡献者可以开始围绕这个 issue 编写产品规格和技术规格。也就是说，这个问题已经足够真实、足够明确，可以进入规格设计阶段，哪怕具体的 UI 或 UX 形态还没有完全确定。Warp 的一位维护者发现了这个缺口，于是直接在 issue 里留下反馈。更重要的是，他不仅说漏了这个标签，还解释了他期待什么，以及为什么期待这样做。

这句为什么，是后续自我改进的燃料。如果反馈只是打一个差评，improver skill 最多知道这次不好，却不知道应该改哪里。如果维护者说，这个 issue 描述了一个真实问题，虽然界面方案未定，但已经可以开始写规格，所以应该打 ready to spec 标签，那么 agent 就能提炼出一个可复用原则。下次遇到类似 issue，它不必看到完全一样的文字，也能判断这种状态应该贴这个标签。

接下来，外层 improver skill 在 Warp 的 agent 编排平台 Oz 里运行，作为一个定时的 update triage agent。Oz 在这里的角色可以理解成调度和编排 agent 的平台。这个 improver agent 会认证到 GitHub，然后运行 skill 里附带的一个 Python 脚本。这个脚本会拉取最近带有反馈的 issues，把它们汇总成一个 JSON 文件，再让 agent 读回上下文里。JSON 是一种常见的数据交换格式，用来结构化保存这些反馈信息。

文章特别提到，把脚本打包在 skill 里本身就是一个最佳实践。因为 skill 不一定只是一段说明文字，它还可以引用资源文件和脚本。这样 agent 不需要每次运行都临时写新代码来拉数据，而是复用一段稳定脚本。这个细节很工程。很多 agent 系统一开始喜欢让模型现场生成脚本、现场调用工具，短期看很灵活，长期看容易不稳定。把固定动作沉淀成脚本，把判断和提炼交给模型，是更可靠的分工。

拿到这些反馈之后，improver agent 会识别维护者评论里的具体信号，然后提出最小修改。原文说，它打开了一个 PR，修改内层 triage skill，让它在 issue 描述了真实问题时，即使具体 UI 或 UX 形态尚未定义，也要应用 ready to spec 标签。注意这个改动很小，但它捕捉到了维护者反馈的核心。它没有把整个标签体系重写，也没有引入一大堆不相干规则。

然后这个 PR 会带着描述进入正常代码审查流程。描述里会解释，是什么反馈信号触发了这次变更，修改了什么。人类维护者审查、批准、合并。合并之后，下一次 triage skill 运行，就继承了这个新知识。最后这一步人类确认，关闭了整个闭环，也确保真正改变系统行为的仍然是人，而不是 agent 单方面决定。

我个人认为，这个案例最值得工程团队学习的，不是 ready to spec 这个标签本身，而是它把学习行为产品化了。很多团队说我们要让 agent 学习团队偏好，但落地时往往变成两种极端。一种是完全人工维护 prompt，累且不可持续。另一种是让 agent 自动记忆一切，风险又太高。Warp 这里给出的中间道路是，agent 负责观察和提出改进，人类负责批准和合并，知识以文件形式沉淀。这很符合现有软件工程文化。

那对我们听众的实际工作意味着什么？如果你在公司里做代码相关 agent，我建议你先不要急着做一个很复杂的长期记忆系统。你可以从一个最小闭环开始。先把 agent 任务定义清楚，比如只做代码审查，或者只做 issue 分诊，或者只做需求文档初稿。然后给它一个 base skill，把团队的核心原则写进去。不要写成上百条僵硬规则，而是写成一个聪明新人能理解的工作指南，包括做什么、为什么做、什么情况下不要做。

接着，你要找到反馈自然发生的位置。如果是代码审查，那就是 PR 评论和评论回复。如果是 issue 分诊，那就是 issue 下面维护者的补充说明。如果是需求文档 agent，那可能是产品经理在文档里的修改意见。关键是不要让用户离开工作现场。你可以约定一些轻量格式，比如当人类想给 agent 反馈时，在评论里明确指出这条建议有用，或者这条建议不符合某个团队约定。格式可以简单，但最好能让后续收集更容易。

然后设置一个 improver agent，定期收集这些反馈。它不需要每分钟跑。很多团队一开始每天一次，甚至每周几次就够了。它的任务不是重新完成业务工作，而是做复盘。它要看 agent 当时做了什么，人类后来怎么评价，里面有没有可以沉淀成 skill 的规律。最好的输出不是一个含糊总结，而是一个可审查的小改动。比如在 skill 文件里加一句原则，改一个标签定义，补一段反例说明，或者引用一个脚本资源。

这里要避的一个坑，是让 improver 一次改太多。人类审查 skill 更新时，最怕看到一大段泛泛而谈的新增内容。比如请更准确地理解用户需求，请更认真地检查边界情况，这种话听起来对，但没什么信息量。更好的改法是，遇到描述了真实用户问题但方案尚未确定的 issue 时，如果贡献者已经可以开始写产品和技术规格，就标记为 ready to spec。具体、可验证、和反馈直接相关，这样才容易合并，也容易判断后续有没有效果。

另一个坑，是把 skills 写成法律条文。模型不是传统规则引擎。你当然可以有硬性规定，比如某个安全检查必须执行，但大多数领域知识更适合写成原则加理由。比如不要只说禁止评论变量命名。你可以说，除非命名会导致误解或违反项目中已有约定，否则不要对局部变量命名提出风格化评论，因为这类评论会制造噪音，降低开发者对 agent 的信任。你看，这里面有行为、有条件、有原因，agent 更容易泛化。

还有一个现实问题是，如何衡量这个闭环有没有用。原文没有展开指标系统，所以我不能说 Warp 具体用了哪些量化指标。但从工程实践看，我个人认为你至少可以观察几个朴素信号。比如人类采纳 agent 评论的比例有没有上升，维护者纠正相同错误的频率有没有下降，agent 产生的 PR 或标签变更被回滚的次数有没有减少，团队成员主观上是否觉得它更像助手而不是噪音。这些不一定要一开始就做成复杂仪表盘，但要有意识地看。

安全和治理也不能忽略。自我改进听起来很诱人，但如果没有审查，就可能把一次错误反馈变成长期错误知识。Warp 的做法里，人类合并是一个关键护栏。尤其在企业环境里，你可能还要区分哪些 skill 可以自动更新，哪些必须资深工程师批准，哪些涉及安全、合规或架构决策的内容不能由 agent 直接改。简单说，反馈可以自动收集，建议可以自动生成，但知识进入主干，最好有明确责任人。

对 AI 从业者来说，这篇文章也提醒我们，agent 能力的提升不总是来自模型本身升级。Claude 的能力当然是基础，但 Warp 这个案例里真正起作用的，是围绕模型的工作流设计。你把反馈放在哪里，把知识存在哪里，改动如何审查，下一次如何继承，这些都是系统工程。很多时候，模型已经足够聪明，问题在于组织没有给它一个稳定学习的轨道。

我也很喜欢原文里关于 simplicity，也就是简单性的强调。Zach Lloyd 说，这个框架其实很简单：有一个领域特定的 base skill，然后有一个 improver skill 去改进它。这个简单性正是方法的美。复杂 agent 系统很容易让人陷入工具调用、记忆库、向量检索、多 agent 协调的细节里。但 Warp 展示的是，先把最基本的循环跑通。人类反馈，提炼改动，文件化知识，审查合并，再次运行。这个循环一旦稳定，才值得继续加复杂能力。

如果你现在就想在团队里试一下，我会建议从低风险、高频率、反馈明确的任务开始。代码审查里的风格和项目约定、issue 标签分配、需求文档的结构检查，都很适合。不要一上来就让 agent 决定重大架构，或者自动改生产系统配置。先找一个人类本来就会频繁纠正的小任务，让 agent 学会少犯重复错误。这样改进效果容易感知，风险也可控。

最后我们回到文章的主旨。Warp 基于 Claude 构建自我改进 agents 的核心，不是神秘算法，而是把短暂的人类反馈变成长期的技能文件更新。内层 skill 做任务，外层 skill 看反馈并提出小修改，人类通过正常 PR 流程把关。这个模式让 agent 从一次性助手，逐渐变成能在组织里积累经验的系统。

我个人认为，这篇文章最有价值的一句话可以概括为：不要只问 agent 这次能不能答对，要问它下次能不能因为这次的反馈答得更好。对于软件团队来说，这正是从 demo 走向生产的分水岭。Claude 提供了推理能力，而像 Warp 这样的工程闭环，决定了这种能力能不能在真实协作中持续复利。
