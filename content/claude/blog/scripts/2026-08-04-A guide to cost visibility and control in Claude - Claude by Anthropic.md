## Script

今天我们聊的文章是 A guide to cost visibility and control in Claude，我把它翻译成中文叫做 Claude 成本可见性与控制指南。这篇文章发表于二〇二六年八月四日，也就是五天前，放在今天二〇二六年八月九日来看，它是一篇非常新的产品和实践指南。它不是那种发布新模型、刷新基准分数的文章，而是更偏企业落地，讲一个很现实的问题：当 Claude 已经进入公司内部、进入软件产品、进入自动化流程之后，费用到底怎么看，怎么管，怎么花得值。

这期值得听，是因为很多团队在引入大模型的时候，一开始最兴奋的是能力，能写代码，能分析文档，能做客服，能帮销售写方案，能帮法务读合同。但过了试点阶段，财务、IT、研发负责人很快会问一个问题：这个东西到底花了多少钱？更关键的是，这些钱到底换来了什么？如果你在公司里负责 AI 平台、工程效率、IT 管理，或者正在把 Claude API 接进自己的产品，这篇短文其实是在给你一套成本治理的思路。它不只是说少用一点模型就省钱，而是说要把成本、能力、任务难度和组织管理串起来看。

文章开头就说，企业使用 Claude 的方式很多。有的公司是把 Claude 推给几千名员工，让大家在日常工作里使用。有的创业公司或者单个团队，是基于 Claude Platform，也就是 Claude 平台，用 API 做自己的应用。不管是哪一种，成本都重要。这句话听起来很普通，但背后是一个行业阶段的变化。早些年很多公司试用大模型，更多像创新项目，预算来自实验池，大家关心的是有没有惊艳效果。到了现在，AI 工具已经从试验台走进生产环境，进入了采购、合规、预算、审计、成本中心这些传统企业流程。这个时候，AI 不再只是技术团队的玩具，而是企业经营的一部分。

Anthropic 在这篇文章里给出的核心建议，是不要只把 token 消耗当作衡量价值的主要指标，而是要看 cost per outcome，也就是每个结果的成本。token 可以理解成模型处理文本时的最小计量单位，中文里大致可以理解为一段文字被切碎之后的片段。很多开发者天然会盯着 token，因为 API 账单通常就是按输入和输出 token 来计费。但文章提醒我们，真正值得比较的不是某个任务用了多少 token，而是完成一个业务结果要付出多少成本。

我们可以用一个很简单的例子来理解。假设公司要处理一批客户投诉邮件。方案一是让人工客服一封一封看，分类、提炼问题、写回复建议。方案二是用 Claude 先做分类和摘要，再由人复核。你如果只看 token，可能会发现这一批邮件跑下来用了很多 token，账单不低。但如果人工原来要花三个人两天，现在一个人半天就能处理完，而且回复质量更稳定，那从业务结果来看，这笔钱可能很划算。反过来，如果你只是用最强模型把一堆格式非常固定的报表转成 JSON，虽然效果也许不错，但任务本身并不需要复杂推理，那你可能是在为用不到的能力付费。

文章建议企业问两个问题。一个是，如果没有 AI，这件事本来要花多少成本？这里的成本不只是现金，还包括人力、时间，甚至包括原来根本不会尝试做这件事的机会成本。另一个是，模型完成的是一个困难的、需要判断和推理的任务，还是只是规模很大但本身很简单的任务。第一个问题高度依赖企业自己的业务，任何供应商都没法替你准确衡量。第二个问题则可以通过模型选择来解决，也就是把合适的模型放到合适的工作上。

这点非常关键。很多团队在做大模型应用的时候，容易走两个极端。一个极端是所有任务都用最强模型，觉得这样最保险。另一个极端是为了省钱，尽量全部用便宜模型。Anthropic 在文章里明确说，这两种都可能不经济。把不够强的模型派去做复杂推理，表面上单次调用便宜，但它可能会因为做不好而反复重试，消耗更多 token，还需要更多人工修正，最后总成本反而更高。把前沿模型放到基础文档处理上，则是在为任务根本用不到的高级能力买单。

如果你是工程负责人，可以把这件事想象成团队排班。你不会让公司里最资深的架构师每天专门做会议纪要整理，也不会让刚入职的实习生独立负责核心交易系统的架构决策。不是因为某个人好或者不好，而是因为任务对能力的要求不同。模型也是一样。成本治理的第一步，不是粗暴地说少用，而是让每一级能力有自己的位置。

文章接着介绍 Claude 的模型家族。按照原文，Fable 面向最困难的问题。Opus 适合长周期任务和编码。Sonnet 适合日常工作和分析。Haiku 适合高频、大规模、例行任务。这里我们不用纠结每个名字背后的技术细节，可以先把它看成一个能力和成本的梯度。越靠近前沿模型，推理、规划、复杂判断能力越强，但成本也更高。越轻量的模型，适合吞吐量大、结构明确、重复性强的场景。

文章还提到两个很重要的机制，一个叫 effort controls，可以翻译成思考强度控制。它的意思是，对同一个模型，你可以调高或调低模型在解决问题时投入的思考量。另一个叫 advisor tool，也就是顾问工具。它允许较小模型在遇到难点时，去请教一个前沿模型，而不是从头到尾都用最贵的模型跑完整个任务。

这两个机制其实代表了成本优化的一个新方向。过去我们常说模型路由，也就是根据任务把请求发给不同模型。但如果任务本身不是均匀难度呢？比如一个代码审查任务，大部分文件只是普通风格问题，轻量模型就能看出来。但其中某一个模块涉及并发、权限和数据一致性，确实需要更强模型判断。这个时候，如果全程都用前沿模型，贵。如果全程都用小模型，关键问题可能漏掉。更合理的方式是，大部分时间让小模型做基础工作，遇到关键判断点再请更强模型出手。advisor strategy，顾问策略，讲的就是这种思路。

文章给了一个保险公司的例子。一个保险公司可以让前沿模型帮助理赔员评估复杂的商业索赔，同时让 Haiku 给相关文档打标签、分流、整理。你可以想象整个流程：客户提交了很多材料，保单、发票、事故说明、历史往来邮件、现场照片说明。最开始的工作是把这些资料按类型分好，识别哪些是合同条款，哪些是损失证明，哪些需要补充信息。这些工作量大，但判断边界相对明确，轻量模型就可以做。到了真正评估复杂商业索赔的时候，需要理解合同条款、风险责任、异常情况和金额影响，这时前沿模型的价值才体现出来。这样一来，成本不是平均撒出去，而是集中花在最需要判断力的环节。

接下来，文章把场景分成两类。Claude 可能作为员工直接使用的产品，也可能作为应用背后的 API。前者的控制权主要在 IT 管理员，也就是 admin 手里。后者的控制权主要在工程师手里，因为他们负责怎么调用 API、怎么设计工作流、怎么把模型接进产品。文章也指出，大多数大客户两种方式都会用。比如一家公司既给员工买了 Claude Enterprise，让产品经理、运营、法务、销售都能用；同时研发团队又通过 Claude Platform 在客服系统、内部知识库、代码工具里集成 Claude。

这一区分很重要，因为成本治理的抓手完全不一样。员工直接使用产品时，管理员关心的是哪些部门能用、哪些人能用、默认用什么模型、每个人最多能花多少。API 场景下，工程团队关心的是请求怎么拆分、能不能缓存 prompt，能不能批处理，生产环境和测试环境怎么分账，任务什么时候用小模型，什么时候升级到大模型。很多公司成本失控，就是因为只看到账单总额，却没有把使用方式拆开看。

我们先看 Claude Enterprise 里的成本控制。文章建议一般按顺序来做，因为在看到一个月真实用量之前，很难设置合理的限制。这个建议非常实在。很多公司一上来就想设预算上限，比如每个人每月不能超过多少，每个部门不能超过多少。但如果你完全不知道真实使用模式，这个上限不是太松就是太紧。太松没有治理效果，太紧则会让真正有价值的团队用不了，反而阻碍 adoption，也就是采用。

文章提到的第一个企业控制手段是 access gating，可以翻译成访问门控。管理员可以决定哪些组、哪些自定义角色能够使用 Claude Code、Claude Cowork 这样的产品，而不是全公司一键全开。文章建议先从一个团队开始，观察结果，然后按部门逐步扩展。

这个做法很像灰度发布。软件工程师对灰度应该很熟悉。你不会在新功能还没有监控的时候一次性推给所有用户，而是先给一小部分用户，看看错误率、性能、反馈，再扩大比例。企业 AI 工具的推出也应该这样。先让一个研发团队使用 Claude Code，观察他们的代码生成、代码审查、调试辅助场景，看他们到底每天用多少、在哪些任务上最有价值、有没有安全或者合规问题。然后再推广到更多研发组，甚至推广到产品、运营和数据团队。这样成本增长是可观察的，而不是突然有一天财务告诉你账单爆了。

第二个控制手段是 model controls，也就是模型控制。文章说它有两个层级。一个是 entitlements，可以理解成模型使用权限，决定一个团队能访问哪些模型。另一个是 defaults，也就是默认设置，决定新对话默认从哪个模型开始。管理员可以让做最困难工作的团队获得最强模型的权限，同时让其他人默认使用 Sonnet。

这里的默认值非常有意思。在企业工具里，默认值往往比制度更有力量。你可以允许大家切换到更强模型，但如果默认就是最强模型，大多数人会一直用最强模型，哪怕只是改一封邮件。相反，如果默认是一个适合日常工作的模型，大多数普通任务就会自然落在合理成本区间。只有当用户明确知道自己需要更强推理时，才切换上去。对于管理员来说，这比天天教育员工省钱更有效。

当然，这里也不能简单地把权限收得太死。原文的态度不是剥夺能力，而是匹配任务。比如安全团队做事件分析、法务团队处理复杂合同、研发团队做大型重构，这些场景可能确实需要更强模型。如果你为了省钱把他们都限制在较弱模型上，他们可能会花更多时间修正结果，或者干脆不用 AI，最后组织收益下降。所以模型权限应该和工作类型绑定，而不是和行政级别简单绑定。谁的任务更难，谁就应该更容易拿到强模型。

第三个控制手段是 hard spend caps，硬性花费上限。它可以给整个组织、单个用户或者一个组设置使用天花板。如果是给组设置，每个成员都会获得这个限制。文章特别说，上限会立即生效。它也建议等你知道完整组织的基线之后再设置。所谓基线，就是一个月左右真实使用之后，你大概知道正常情况下各部门、各用户、各产品线会花多少。

硬性上限的好处是明确，它能防止意外失控。比如某个用户开启了大量对话，或者某个团队突然把工具用在一个超大规模任务上，账单不会无限增长。但硬性上限也有风险。它可能在关键时刻把真正重要的工作卡住。所以实践上，我个人认为，硬性上限更适合作为安全护栏，而不是主要治理手段。主要治理还是应该靠模型匹配、默认值、流程设计和可观测性。上限是刹车，不是方向盘。

文章还提到，管理员可以自动化审核花费上限提高请求，识别接近花费上限的成员，发现使用量快速变化的成员。这个点虽然篇幅不长，但非常贴近企业管理。因为一旦 AI 使用规模扩大，手动审批会变成瓶颈。比如某个团队这个月因为上线项目，需要临时提高 Claude Code 的使用上限。如果每次都要发邮件给 IT、等经理签字、再人工调整，体验会很差。但如果系统能自动根据角色、历史使用、预算归属来审批一部分请求，管理员只处理异常情况，治理效率就高很多。

识别接近上限的成员也很有价值。它不一定意味着这个人浪费，也可能意味着这个人找到了高价值用法。比如某个工程师用 Claude 辅助迁移老代码，使用量很高，但产出也很高。管理员看到他接近上限，应该进一步了解，而不是简单地拦掉。相反，如果某个成员使用量突然快速变化，可能是项目需求，也可能是误用，甚至可能是自动化脚本配置错误。能早发现，就能早处理。

说到这里，就自然进入文章的另一个重点：可观测性。成本控制的前提是看得见使用情况。文章说，使用数据可以在 admin dashboard，也就是管理员仪表盘里查看，可以发送到企业自己的系统，也可以直接向 Claude 提问。它列出三个功能，usage analytics，用量分析，Analytics API，分析接口，以及 analysis with analytics chat，用分析聊天来分析数据。

原文对前两个功能没有展开太多，只是点名。但从管理员视角看，用量分析通常就是看谁在用、哪个团队在用、用量随时间怎么变化、花费集中在哪些地方。Analytics API 则意味着你可以把这些数据接入自己的系统，比如数据仓库、成本看板、FinOps 平台、内部审批流程。FinOps 是云成本管理里常见的说法，强调工程、财务和业务一起管理技术成本。AI 成本越来越像云成本，也需要类似方法。

最有趣的是 analytics chat，也就是用自然语言直接问使用数据。文章举了两个例子。你可以问，这个月谁是最高花费者？也可以问，这个季度哪个团队的使用增长最快？不用拉完整报表。这个功能体现了一个很实际的趋势：管理 AI 的工具本身也会被 AI 化。过去管理员要导出 CSV，写 SQL，做透视表，再发给领导。现在可以直接问一个问题，让系统基于使用数据回答。当然，真正落地时，企业还要关心权限、数据口径、审计记录。但作为交互方式，它确实降低了成本分析门槛。

如果你在公司负责 AI 平台，我建议你把这些可观测能力分成三层来看。最底层是账单层，你至少要知道总花费、按时间的趋势、按组织和用户的分布。中间层是行为层，你要知道大家用的是什么模型、什么产品、什么类型的任务，是否集中在少数人和少数团队。最高层是价值层，你要把使用量和业务结果关联起来，比如代码交付速度、客服处理时长、知识检索成功率、文档处理吞吐量。文章强调 cost per outcome，其实就是提醒你不能停在账单层。

接下来文章转向 Claude Platform，也就是开发者基于 Claude API 构建应用的场景。它说 Claude Console 为组织和开发者提供控制。Workspaces 可以按产品、团队或者环境分隔 API 使用，并且在成本和用量报告里有自己的行。Workspace 可以理解成工作空间。这个设计对工程团队非常重要，因为 API 费用如果都混在一个总账里，后面很难追责和优化。

想象一下，你们公司有三个应用都在调用 Claude。一个是内部客服助手，一个是代码审查工具，一个是销售知识库问答。如果全部共用一个 API 项目，月底只看到总账单上涨，你很难知道是谁贡献了增长。是客服请求变多了，还是代码审查 prompt 太长，还是销售问答用了不合适的模型？如果用 Workspaces 分开，每个产品、团队、环境都有独立报表，你就可以像管理云资源一样管理 AI 成本。生产环境和测试环境也应该分开，否则测试脚本一跑，生产成本看板就被污染了。

文章列出 Claude Platform 上几个有用的成本杠杆。第一个是 prompt caching，也就是 prompt 缓存。原文没有详细展开，但它点名为成本杠杆。一般来说，缓存的思想很容易理解：如果很多请求里有一大段相同的上下文，比如公司政策、产品说明、代码库摘要、长文档前半部分，那么系统可以复用已处理的部分，避免每次都完整重新计算。对于长上下文应用，这往往非常关键。

举个场景。你做一个内部知识库助手，每个用户的问题都要带上一大段制度文档。如果每次提问都把同样的制度全文重新送进模型，成本会很高，延迟也可能增加。prompt caching 的价值就在于，相同前缀或者稳定上下文可以被缓存起来，后续请求只为变化部分付出更多计算。文章没有给具体折扣数字，所以我们不在这里编数字。但从工程原则看，缓存几乎总是降低重复计算成本的第一工具。

第二个杠杆是 batch processing，批处理。它适合不需要实时返回的任务。比如你要给一百万条历史客服记录打标签，要给大量商品描述生成摘要，要离线处理文档归档。这类任务不是用户坐在屏幕前等答案，而是可以排队慢慢跑。批处理通常可以让系统更高效地调度资源。对开发者来说，关键是区分在线任务和离线任务。在线对话、实时客服、代码编辑器里的补全，用户等着结果，需要低延迟。离线标注、报表生成、历史数据清洗，可以放进批处理管道。不要把所有任务都当实时任务做，那样既贵又难扩展。

第三个是 effort parameter，也就是思考强度参数。前面我们在企业产品里讲过 effort controls，在 API 场景下，它变成开发者可以调的参数。它允许你根据任务难度控制模型投入多少推理努力。一个常见误区是，所有请求都用最高思考强度。这样当然可能提高复杂任务的质量，但对于简单任务就浪费了。比如判断一封邮件是不是垃圾邮件，或者从固定格式文本里抽取日期，没必要让模型长时间思考。相反，如果你让模型做复杂架构权衡、法律条款分析、调试隐蔽并发问题，就应该给它更多思考空间。

第四个是 advisor strategy，顾问策略。文章对它给了比较明确的描述：让较小模型，比如 Sonnet，在关键时刻调用前沿模型，比如在工作交付之前进行评估。大部分任务跑在较小模型上，只在需要应用更大模型判断力的地方付费。这个策略对工程设计很有启发。你可以把它做成流水线。前面几步由便宜模型完成草稿、提取、分类、初步判断。到了最后一步，强模型做审核、打分、发现风险，或者只处理小模型标记为不确定的样本。这样你不是简单降低模型等级，而是把强模型当成稀缺专家使用。

这里我个人认为，advisor strategy 会成为很多企业 AI 应用的标准模式。因为真实业务任务往往不是单次问答，而是多步骤流程。比如合同审查，第一步解析合同结构，第二步抽取关键条款，第三步和公司标准条款库比较，第四步识别高风险条款，第五步生成修改建议。并不是每一步都需要最强模型。解析结构和抽取字段可以用较小模型，风险判断和修改建议可能需要更强模型。如果你能把流程拆清楚，成本就会下降，质量还可能上升，因为每个环节的职责更明确。

文章还说，这些功能一起使用，可以在不动预算线的情况下，常规性地大幅降低生产工作负载的成本。注意原文没有给具体百分比，所以我们不要说能省多少多少。但它的意思很清楚：很多成本优化不是靠砍预算，而是靠工程设计。缓存减少重复计算，批处理提高吞吐效率，effort 参数避免过度思考，advisor 策略把强模型用在刀刃上，Workspaces 帮你看清成本归属。这些组合起来，往往比单纯要求团队少用更有效。

对中国的软件工程师和 AI 从业者来说，这篇文章的实践价值很直接。如果你在公司推动 Claude 或其他大模型平台落地，我建议从三个问题开始。你们的 AI 使用，是员工工具为主，还是 API 应用为主，还是两者都有？你们现在能不能按团队、项目、环境看到花费？你们有没有把任务按难度分层，而不是默认全用同一个模型？

如果答案是看不清，第一步不是优化 prompt，而是建立可观测性。至少要把成本按组织、应用、环境拆开。研发测试和生产要分开，内部工具和客户功能要分开，不同团队的试点要分开。否则你会陷入一种很常见的状态：大家都觉得 AI 有用，但没人说得清到底哪里花钱，哪里产生价值。到预算评审时，就很容易被一刀切。

如果答案是模型使用混乱，第二步是做任务分层。你可以把任务粗略分成例行高频任务、日常分析任务、长周期复杂任务和最高难度判断任务。例行高频任务，比如分类、标签、格式转换、简单抽取，优先考虑 Haiku 这样的轻量模型。日常分析、总结、一般写作、常规问答，可以考虑 Sonnet。长周期编码、复杂项目规划，可以考虑 Opus。最困难、最需要高质量判断的问题，再考虑 Fable 这样的最强模型。这里不是让你机械套名字，而是建立能力和任务匹配的意识。

如果你负责员工使用的 Claude Enterprise，访问门控和默认模型很重要。不要一开始全公司全功能开放。先选一个有明确场景、有负责人、有反馈机制的团队。比如一个后端平台组，用 Claude Code 做代码理解和迁移；或者一个运营分析组，用 Claude 做报表解读和文档生成。跑一个月，记录使用量、典型案例、节省时间、出现的问题。然后决定是否扩大。默认模型可以设置在日常够用的档位，把更强模型权限给确实需要的团队。这样既不会过度压制创新，也不会让成本在看不见的地方扩散。

如果你负责 API 应用，实践重点更偏工程化。每个应用建立单独 Workspace 或类似的成本归属单元。每条请求记录模型、输入输出规模、延迟、任务类型、是否命中缓存、是否经过强模型审核。对于长上下文场景，尽早评估 prompt caching。对于离线任务，尽量走 batch processing。对于复杂流程，把任务拆成多步，不要把所有上下文和所有要求塞进一次超大调用里。该小模型先做的就小模型先做，该强模型复核的就强模型复核。

这里有一个常见坑，叫只优化单次调用价格，不优化整体流程。有的团队看到 Haiku 便宜，就想把所有任务都切过去。结果复杂任务质量下降，人工返工增加，用户不信任系统，最后还要重试多次。另一些团队则相反，为了追求稳定，所有任务都用最强模型，结果简单任务成本过高，规模一大就不可持续。正确的思路是端到端衡量。一个流程从输入到最终可用结果，中间总共花了多少模型成本、多少人工时间、多少重试、多少延迟，最终质量如何。文章开头说 cost per outcome，其实就是这个意思。

另一个坑是过早设置硬上限。很多管理者一看到 AI 账单，就想马上给每个人封顶。但如果没有基线，你可能会限制住最积极、最能产出价值的人。更好的做法是先观察一个完整周期，找到正常范围，再设置提醒和软性阈值，最后设置硬性上限。硬上限要配合申请提高额度的流程，而且这个流程最好自动化一部分。比如超过上限前提醒用户和主管，说明当前花费用在哪里，如果是项目需要，可以申请临时提高。如果只是异常增长，管理员可以介入排查。

还有一个坑是只看最高花费者。文章里 analytics chat 的例子问谁是本月最高花费者，这当然有用，但不要把它等同于谁在浪费。最高花费者可能是最有价值用户。你更应该追问，他做了什么任务，节省了多少时间，产出了什么结果，能不能把他的用法推广给别人。同样，使用量增长最快的团队也不一定有问题，可能是他们刚刚找到了适合 AI 的场景。成本治理不是打压使用，而是让高价值使用增长，让低价值使用减少。

我个人认为，这篇文章最值得借鉴的一点，是它把 AI 成本从技术指标拉回到业务结果。token 是必要的计费单位，但不是价值单位。企业真正关心的不是消耗了多少 token，而是客户问题是不是更快解决，代码是不是更快交付，员工是不是少做重复劳动，原来无法处理的大量信息现在是不是可以处理。只有把这些结果和成本放在一起看，AI 预算才有讨论基础。

当然，文章本身是一篇五分钟的官方博客，所以它没有深入展开每个工具的配置细节，也没有给出具体案例数据。比如 prompt caching 能省多少、batch processing 的具体使用限制、effort 参数如何调优、advisor strategy 怎么实现路由逻辑，这些都需要开发者去文档和实际产品里验证。我们在解读时要注意这一点，不要把文章没有说的东西当成官方承诺。它提供的是框架和方向，而不是完整实施手册。

如果把全篇浓缩成一句话，我会说，Claude 的企业成本管理不是简单限额，而是先看清用量，再匹配模型，再用工程手段优化流程，最后用预算上限做护栏。对于正在把大模型推向组织内部和生产系统的团队，这个顺序非常重要。先可见，再控制；先理解价值，再谈节省。

最后做个小结。Anthropic 这篇 A guide to cost visibility and control in Claude，重点讲了企业如何用 Claude Enterprise 和 Claude Platform 里的控制能力管理成本。它强调 cost per outcome，强调模型要匹配任务，强调管理员和工程师分别有不同抓手。我的点评是，这说明大模型竞争已经不只是模型能力竞争，也进入了企业治理和成本工程阶段。谁能让 AI 既有用、又可控、还算得清账，谁才更可能真正进入长期生产环境。
