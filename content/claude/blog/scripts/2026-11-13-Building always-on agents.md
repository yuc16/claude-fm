## Script

Building always-on agents，中文可以翻译成构建始终在线的智能体。这篇文章发表于二〇二六年十一月十三日，距离今天十一月十五日只有两天。欢迎收听 Claude FM，我是你今天的主播。这一期，我们不聊怎么让模型回答得更漂亮，而是聊怎么让它在你不盯着屏幕的时候，持续替你把事情往前推进。

想象一下，你让一个助手跟进线上故障。它查完日志，发现还需要另一位同事确认，于是发出询问。你关掉页面去开会。两个小时后，同事回复了，它继续排查。到了晚上，它发现风险已经解除，只给你发来一条简短结论。这里真正困难的，不是某一句话怎么生成，而是谁记得这件事还没结束，谁接住后来到达的消息，谁判断下一步能不能自己做。

这就是文章要解决的问题。这里的 agent，也就是智能体，不再只是等你提问的聊天窗口，而是一个有状态、能主动行动的系统。有状态，意味着不同时间的工作之间能够接续。主动，意味着没有新的用户指令，它也可能根据约定的时间或者外部事件开始工作。不过，主动不等于随意行动，文章后半段很大一部分，恰恰是在讨论怎样把主动性关进可靠的工程边界。

先交代一下文章所处的背景。作者说，过去几个月，始终在线的智能体重新受到关注，主要原因是模型能力进步，让这种产品更实际了。一方面，模型判断用户意图、识别什么时候应该回来询问的能力更可靠。另一方面，智能的使用成本在下降，尤其对执行跨度比较长的任务，经济性改善得更明显。

原文给了一个具体数字。在一项长程编程基准上，Opus 五点五每解决一个任务的成本，比 Opus 五低了百分之七十八；而典型工作负载的降幅是百分之四十。注意，这说的是某项基准里的单位成功任务成本，不是所有应用的调用价格都下降了百分之七十八。文章也没有展开这项基准的完整实验设置，所以我们应该把它当成背景证据，而不是可以直接套进预算表的承诺。

我个人认为，这个背景很关键。当一次任务只能执行几步时，大家更关注模型当场说了什么。当任务能够跨越几个小时，甚至不断延续，问题就变成了系统怎么管理时间、状态、权限和人的注意力。模型能力是发动机，但发动机更强，不代表你可以省掉变速箱、刹车和仪表盘。这篇文章的价值，就是把周围这些容易被忽略的部件拆开讲清楚。

它的第一个提醒有点反直觉。始终在线的智能体，其实并不是一直醒着。始终在线描述的是用户体验，而不是计算过程。它大多数时间都在休眠，等到有事情发生才醒来，完成一段工作，保存结果，再回去休眠。你可以把它理解成一个可靠的值班同事，而不是一个二十四小时不停自言自语的人。

这里要区分两个词。run，我们叫一次运行，是从接到事件到完成这一段工作的过程。session，我们叫会话，是消息和工具调用的记录。一次会话可以跨越多次运行。比如助手先问你能不能执行某个操作，这是一次运行。你第二天批准，它接着做，是另一次运行，但仍然可以恢复到原来那段会话。

这个区别听起来像术语，实际决定了系统怎么设计。如果你把一次运行、一次会话和一个后台进程混成同一件事，就很容易让程序一直挂在那里等回复。可用户可能明天才回答，进程中间可能重启，机器也可能被回收。文章的思路是，让执行资源可以释放，让需要延续的信息留下来。人可以晚点回来，系统不必一直占着工位等他。

为了做到这一点，文章列出五个基础部件，事件收件箱、定时器、记忆、权限和发件箱。我们先沿着一个事件进入系统的方向看。普通聊天助手通常由用户消息触发，但常驻智能体还会接收外部系统通知、计划任务和后台作业的结果。比如代码仓库推来一个变更通知，或者工单系统告诉你，一个阻塞任务终于有人回复了。

最直接的写法，是每个事件来源都直接调用智能体。但这样很快就会遇到并发问题。假设同一个工单，在几秒内连续发生状态变更和评论更新，两边各启动一次运行。两个助手都读到旧状态，都觉得自己应该通知用户，或者分别写入不同的进度。最后不一定是模型判断错了，而是两个正确的局部判断互相打架。

文章给出的解决方法，是先放进一个持久化的事件收件箱。最简单的实现其实很朴素，一张数据库表，一个负责接收事件并写表的接口，再加一个读取待处理事件的后台工作进程。这里的持久化很重要，它意味着进程挂了，事情还在。系统真正承认的事实，是表里有哪些事件，而不是某个进程内存里觉得自己收到了什么。

每个事件要有处理状态，也可以根据来源提供的唯一标识去重。原文建议从每个用户一个收件箱开始，有更高并行需求再细分。这个建议不是说所有用户共用一条串行队列，而是先明确每个用户内部的处理边界。同一个人的助手不要同时自相矛盾，不同用户之间仍然可以各自工作。

事件入口还应该尽快确认收到。因为有些 webhook，也就是外部系统主动推送的通知，如果迟迟拿不到响应，就会认为投递失败，再发一遍。入口可以做轻量检查，但更深入的核验，比如检查提示注入，应该放到运行阶段。提示注入，说白了就是外部内容试图冒充指令，诱导模型偏离原来的任务。尽快接收，不代表跳过后续安全判断。

工作进程被唤醒以后，应该重新去收件箱读取最新待处理事件，而不是只相信唤醒它时附带的那一点信息。这让收件箱成为事实来源。如果工作做到一半崩溃，新进程还能看到没有完成的事件，重新接手。同一个收件箱同时只应该有一个活跃工作进程，这样可以避免重复执行和互相覆盖。

这里我要补充一个工程上的推演，不是文章直接给出的保证。事件可以重试，并不意味着外部动作天然不会重复。比如邮件已经发出，但完成状态还没来得及写回，进程就挂了，重试时仍可能再发一次。所以如果你准备让助手创建工单、发送通知或者触发部署，最好另外考虑幂等机制。收件箱解决的是事件不轻易丢失，不能自动解决所有副作用的一致性。

运行过程中又来了新事件，怎么办？文章没有强推一种答案。你可以留到下一次运行，可以合并进当前运行，也可以中断后重启。选择取决于场景。如果用户连续补充三句话，合并处理通常更自然。如果用户突然说先别发出去，那它可能比普通的新评论更紧急。我个人认为，这里需要产品语义，而不仅仅是一个通用队列算法。

文章还建议批量处理积压事件。你应该遇到过这种聊天习惯，先发一句帮我看看，再发一段日志，最后补一句这是测试环境。如果每条消息都启动一次完整运行，助手可能连着回答三遍，还在第一遍里误判环境。把已经到达的一组消息一起交给它，不光省成本，也更接近人类实际理解一段交流的方式。

有了收件箱，系统能回应外部变化，但真正的主动性，还需要定时器。文章把定时器分成两类，一类是跟进，一类是周期计划。跟进是助手给自己设的一个未来检查点，比如明天下午看看对方有没有回复。周期计划则是固定节奏的任务，比如每天早上整理一次项目动态。前者通常执行一次，后者需要不断计算下一次时间。

定时器应该有自己的持久化存储，不要把尚未到期的任务全部塞进事件收件箱。收件箱只装现在已经可以处理的事件。你可以把定时器想成日历，把收件箱想成今天桌上的待办。明年才发生的事，没必要每天躺在桌面上，和眼前真正要做的事情混在一起。

调度器负责定期扫描那些已经到期的记录。遇到一次性的跟进，就把它标记为完成。遇到周期任务，就把下次到期时间往后更新。然后，它往收件箱加入一个事件，并唤醒工作进程。注意，定时器本身并不绕过收件箱直接启动模型。不管是用户来信还是时间到了，最后都从同一个入口进入运行周期。

这个统一入口的好处，是你不用为定时任务再造一套并发和恢复逻辑。假设早上的项目简报定时器触发时，恰好用户发来一句今天只看支付模块，两个事件可以在同一套处理机制里被理解。原文说，调度器可以自己写，也可以使用持久化执行引擎。关键不是框架名字，而是到期这件事不能只寄托在某台机器临时挂着的计时器上。

接下来是记忆。很多人一听长期智能体，就想到把全部聊天记录塞回上下文。但原文给出的原则更克制，记忆应该主要保存智能体无法重新查到的东西。如果信息已经存在其他系统里，比如问题追踪平台，就保存一个指针，而不是再复制一份事实。否则，原系统已经更新，你的记忆还停在昨天，助手反而被自己保存的旧资料误导。

这就像一个接班工程师的工作笔记。笔记里最值得写的，不是把整套监控指标抄下来，而是目前怀疑哪条链路、谁确认过什么、还有哪件事没有结论。实时状态去监控系统查，工单详情去工单系统查，笔记负责保存那些不容易从结构化系统里重新拼出来的上下文。这样记忆更短，也更有价值。

文章把记忆分成几种。首先是用户指令，例如未经允许不要对外发消息，或者每天只在工作时间汇总。这类内容应该独立保存，而且每次运行开始都加载。原因很简单，用户不可能每次都在旁边重新强调边界。一个助手如果记得你喜欢短回答，却忘了你不允许自动修改生产环境，那不是记忆能力强，而是记错了优先级。

然后是用户笔记，也就是对用户角色、偏好以及纠正意见的记录。一开始可以只有一个文件，增长以后再拆成多个小文件。每次运行先加载索引，需要细节时再读取对应内容。这个设计很像一本有目录的手册，不是每次查一个电话号码，都要先把整本书从头读完。索引解决可发现性，按需读取控制上下文开销。

还有一类是过去已经发给用户的消息。它的用途不是重新保存全部聊天，而是帮助助手知道自己已经说过什么。你昨天提醒过一次某个问题，今天如果没有新进展，就不应该换个说法再提醒一遍。可以单独保存相关记录，也可以由工作进程加载最近几条对话。这种看似不起眼的记忆，直接影响用户会不会觉得助手啰嗦。

最后是任务进度。每个仍在进行的任务，都应该留下做过什么、还剩什么的进度记录。之后的新运行读到这些信息，就能从上次停下的地方继续。比如排查故障时，已经排除了数据库连接数，正在等待缓存节点的指标。这些调查路径如果没保存，下一次醒来就可能从头再查，把成本和等待时间都重新付一遍。

这些记忆必须落在能活过工作进程的存储里。原文提到，Claude Code 的自动记忆，以及 Messages API 的记忆工具，使用文件目录的形式组织内容。对于常驻智能体，这些目录应映射到数据库或者对象存储这样的持久化设施。文件是组织方式，不代表你可以把唯一一份记忆留在随时会销毁的临时容器里。

文章还提到 dreaming，可以理解为离线整理记忆。它会回顾过去的会话，替换过时条目，发现跨越多次运行才看得出来的模式。这里不是说系统真的在做梦，而是把工作当时的记录和事后的整理分开。我个人认为，可以把它想成值班交接之后再整理交接手册，但整理过程本身也需要验证，不能让推测悄悄升级成用户明确表达过的事实。

记忆还要和上下文窗口区分开。每次开始工作，智能体都要加载系统提示、工具定义和一部分记忆，这些构成固定开销。新会话再加上触发事件，旧会话则还会带回之前的消息和工具调用。文章建议保持初始上下文精简，并利用 prompt caching，也就是提示缓存，降低重复输入的成本。

如果会话太长，可以压缩早期消息，也可以开启新会话，但两种方法都会丢失细节。所以，重要信息应该在工作过程中及时保存到记忆，而不是等到上下文快满了，才临时抢救。这有点像电脑内存和硬盘的区别。你不能因为某个内容还在当前屏幕上，就以为它已经稳稳地保存了下来。

再往下，是整套架构风险最高的部分，权限。因为智能体拿着用户的访问能力，却可能在用户不在场时执行操作。文章把每次工具调用的结果概括成三种选择，自己继续，直接阻止，或者等待批准。这里的目标不是让所有事都免审批，也不是每一步都弹窗，而是按动作的风险，划出不同的自主边界。

首先是凭据怎么放。文章推荐把真正的密码或者访问令牌放在智能体环境之外的代理中。智能体发出不带凭据的请求，由代理注入真实凭据再转发。这样至少在架构上，不需要让模型工作的环境直接持有全部敏感信息。就像你允许助理向公司采购系统提交申请，不等于要把管理员密码贴在它的工作台上。

但我要强调，这是减少凭据暴露面的办法，不等于请求本身就安全了。一个没有看到令牌的智能体，仍然可能请求执行不合适的动作。所以代理后面该有哪些权限边界，仍然需要认真设计。这个提醒是我的工程判断，原文在这里主要介绍凭据代理模式，并没有声称单靠它就能解决全部安全问题。

文章接着提到 Claude Code 的自动模式，用分类器审查风险较高的动作，识别危险行为并阻止，让 Claude 寻找更安全的方案。但对于最重要的决策，仍然需要用户审查。这一点值得反复记住，判断力提升，不意味着责任边界消失。尤其是删除数据、对外承诺或者改变关键系统状态这类操作，自主程度不应该只由模型的自信语气决定。

最实用的机制，是延迟工具调用。假设助手已经把修复方案准备好了，但部署需要你批准。它不必一直运行着等待，而是在工具调用进行到一半时保存会话，结束本次运行，再把审批请求展示给你。原文举的方式包括通过 MCP Apps 构建交互卡片，你可以把它理解成一个带操作入口的审批界面。

你点击同意以后，这个回答作为新事件进入收件箱，触发下一次运行，恢复原来的会话并继续那个等待中的调用。在你没有回答的时候，工作进程还可以处理其他事件。等待的是某项动作，不是把整个助手冻结。这就像工作流系统里的人工审批节点，只不过前后的任务理解和执行，由智能体参与完成。

如果你来做一个研发助手，这个能力会很有用。它可以先读日志、整理证据、草拟修复建议，在需要写入敏感系统时暂停。你晚些时候批准，不影响它同时处理另一个只读查询。不过我个人建议，实际落地时还要检查批准是否已经过期。昨晚认可的操作，今天环境变了，未必还适合原样执行。这个时效检查是实践补充，不是原文提供的完整方案。

最后一个部件，是发件箱。普通聊天里，助手经常一边工作一边输出，用户可以看到过程。常驻智能体大部分工作发生在后台，用户更需要结果和少量必要说明，而不是每次查询、每次重试都收到一条动态。所以一次运行结束，并不必然意味着发消息。它也可以安静结束，或者发出一个需要批准或澄清的请求。

文章在这里很务实，不要求所有项目一开始就建正式发件箱。如果一个发送工具能直接把结果交给用户，已经够用，就不必增加一层。只有当你希望控制发送节奏，或者希望发送出错以后能够恢复，独立的发件箱才更有必要。它通常也是一张表，加上一个分发服务，读取待发送消息，决定发什么，再完成投递。

这里的分离很有意义。工作完成和消息送达不是同一件事。助手可能已经完成调查，但通知渠道临时不可用。如果没有独立记录，你可能只能重跑整个任务，才能重新得到那条消息。有了发件箱，就可以把业务执行和消息投递分开恢复。不过具体怎么保证投递一致性，文章没有深入展开，工程上仍需要自己设计。

比可靠送达更微妙的，是到底应该发多少。消息太多，用户会把通知关掉。消息太少，又可能错过真正需要介入的变化。文章建议建立 evals，也就是评估，寻找两者的平衡，而且最好一开始安静一些，再逐步赢得用户更多注意力。我个人非常赞同。主动助手最稀缺的资源，往往不是调用额度，而是用户愿意再看你一眼的耐心。

怎么把这个建议落地？下面是我的实践推演。你可以拿历史事件回放，看看哪些变化值得立即通知，哪些应该汇总，哪些根本不必出现。不要只问消息说得对不对，还要问现在发有用吗，之前说过吗，用户能采取行动吗。比如监控指标短暂波动又自行恢复，和持续恶化需要负责人处理，虽然都是真实事件，但对注意力的要求完全不同。

把这些部件串起来，一次完整循环就很清楚了。外部通知、用户回复或者到期定时器，把事件送入收件箱。工作进程领取事件，选择开启新会话还是恢复旧会话。智能体读入必要记忆，在权限范围内调用工具，保存新的发现和任务进度。如果需要，登记下一次跟进时间。最后决定发送结果、保持安静，或者暂停某项动作等待用户输入。

下一次醒来，可能是定时器到了，也可能是用户回复了。每一次运行都可以很短，但循环能够长期延续。这就是始终在线的来源，不是一个永远不会退出的模型请求，而是一套知道什么时候继续工作的系统。你会发现，文章没有给出神奇的新推理算法，真正的重点是把已有的智能体循环，嵌入可靠的生命周期管理。

如果你准备在团队里试做，我个人建议从一个窄场景开始，例如跟进内部工单，而不是直接打造全能数字员工。先只接一个事件来源，允许读取工单和整理摘要，不允许自动修改关键状态。先验证它能不能跨越进程重启接续工作，能不能在连续收到几条消息时只回应一次，再谈更复杂的自主执行。

接着，为用户规则、任务进度和已发送消息准备最小的持久化记录。增加一个一次性跟进定时器，让它在约定时间重新检查工单。需要敏感操作时，就走保存会话、等待批准、收到事件后恢复的路径。你不必一次集齐所有复杂设施，但每增加一种能力，都应该知道相应的失败以后，系统靠什么继续。

测试时也别只看顺利路径。我个人会故意让同一个事件重复到达，让工作进程在中途退出，让用户隔很久才批准，让投递渠道临时失败，再观察是否重复操作、丢失进度或者反复打扰。这样的测试没有炫目的演示效果，却决定了助手能不能从一次演示，变成真的可以托付日常工作的产品。

最后提醒一句，原文是一篇架构指南，不是一份完整的生产系统规范。事务边界、租约、重试策略、审批失效和权限细分，都还需要结合业务补齐。它给我们的不是复制即用的万能模板，而是一张足够清楚的地图，让你知道长期自主工作背后，哪些责任必须有人承担，不能全部交给一句系统提示。

总结一下，始终在线的智能体，本质上是事件驱动、状态持久化、权限受控的一组短暂运行，而不是一个永不停止的聊天窗口。我个人认为，它最重要的成熟标志，不是可以自己做多少事，而是知道什么时候该醒来，什么时候该停下，以及什么时候值得打扰你。这里是 Claude FM，我们下期再见。
