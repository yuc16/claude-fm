这篇文章来自 Anthropic 的博客，是他们关于 human-agent teams，也就是人和智能代理组成团队这一系列的第二篇。第一篇讲的是 Anthropic 自己在多人 AI 协作方面学到的东西，这一篇则把视角转向 Slack。Slack 很有意思，因为它在 AI 真正火起来之前，就已经在思考一个老问题：公司里每天产生那么多聊天、讨论、决策、争论、草稿、会议纪要，这些东西到底能不能变成组织知识？如果能，为什么过去这么多年大家还是觉得找不到信息，还在反复问同样的问题？

文章采访的对象是 Jaime DeLanghe，她是 Slack 的首席产品官。她二〇一七年加入 Slack，最早做的是搜索和机器学习，目标就是把工作场景里的对话变成机构知识。这个出发点对我们软件工程师和 AI 从业者很熟悉，因为几乎每家公司都说自己有知识库，但真正到排查线上问题、接手老项目、理解历史决策的时候，大家还是会去问人，去翻聊天记录，去找那个可能已经离职的同事。知识确实存在，但它经常以一种很难被消费的形态存在。

这篇文章值得听，不是因为它发布了一个新模型，或者讲了一个复杂算法，而是因为它回答了一个更现实的问题：当 agent 真的进入组织协作工具之后，我们应该怎样改变工作方式？很多团队现在已经接入了 Claude、Slack AI、企业搜索、会议总结工具，也可能在内部做各种机器人。但如果只是把过去的流程搬进 AI，让 agent 帮你更快地写消息、更快地整理文档，那只是加速原来的低效。Slack 在这篇文章里强调的是，我们可能要重新设计工作流，尤其是重新设计对话、上下文、决策和行动之间的关系。

先看背景。Slack 从诞生开始，就有一个很强的产品信念：工作应该尽量发生在公开频道里，而不是散落在每个人的私信、邮件和本地文档里。为什么？因为公开频道会产生共享上下文。一个新人加入团队时，不应该面对一个空邮箱和一堆口口相传的潜规则，而应该可以进入历史频道，看到事情是怎么一步步发生的。一个工程师接手服务时，不应该只看到最后的架构图，还应该能看到当初为什么做这个取舍，为什么没有选另一个方案，哪些限制当时很重要，哪些限制现在可能已经不存在了。

听起来很美好，但 Jaime 在文章里讲得很坦诚。她说，Slack 早期有很多研究论文都显示，实际上，对话并不会自动变成知识。你希望它会，但现实往往只是，那里挂着一大堆东西，人们还是不得不重复自己。这个判断很关键。过去十年，很多协作软件都暗含一个假设：只要沟通都在线上，只要所有内容都可搜索，组织知识自然就会积累起来。可实际情况是，搜索只能帮你找到记录，不能帮你理解记录。聊天记录里有噪声，有玩笑，有中途改变的方向，有过期的信息，有只对当时参与者有意义的省略表达。对人来说，把这些工作过程的废气重新提炼成知识，成本太高了。

文章里用了一个词，exhaust，可以理解成工作过程中排出来的尾气。人协作的时候会产生大量副产品，会议、消息、评论、状态更新、临时结论。过去大家希望这些尾气会自然沉淀成组织知识，但最后发现，人类没法规模化处理它。现在，Slack 的判断是，这正是 agent 的工作。agent 在这里我先翻译成智能代理，指的是能基于上下文执行任务、生成结果、持续协助人的 AI 系统，而不只是你问一句它答一句的聊天机器人。

这里的第一层变化，是从找记录变成问原因。过去你在 Slack 里搜索，可能会搜某个关键词，比如“为什么弃用方案 A”，然后你会得到几十条消息，你再一条一条读。Jaime 的建议是，不要只问“当时决定了什么”，而要让 agent 重建“为什么做这个决定，以及从那以后上下文发生了什么变化”。这听起来是一个小改动，但对工程团队很重要。

举个例子，你们团队两年前决定不用某个数据库，理由可能是当时的托管版本不成熟、缺少某些索引能力、团队没有运维经验。两年后，如果有人再问“我们为什么不用它”，传统知识库可能只会告诉你“当时决定不用”。但一个有足够上下文的 agent 可以把聊天记录、设计文档、会议纪要和后续事故复盘串起来，告诉你：当时主要担忧是写入延迟和备份恢复能力，后来供应商在去年推出了新版本，团队也通过另一个项目积累了相关经验，所以原来的反对理由有一部分已经减弱，但数据迁移成本和一致性模型仍然是风险。你看，这就不是简单检索了，而是把历史决策重新放到今天的语境里解释。

第二层变化，是扩大上下文的表面积。文章提到，Slack 和 Claude 这样的工具正在把会议、邮件、日历和文档仓库连接起来。连接得越多，团队重复自己的次数就越少。这个观点对做企业 AI 的人尤其重要。我们经常会把 agent 效果不好归因于模型不够强，prompt 没写好，或者工作流设计不细。但在企业场景里，很多时候根本问题是上下文不完整。一个 agent 如果只看得到 Slack 频道，看不到会议记录，它就不知道某个决策其实已经在会上改过。它如果看不到日历，就不知道你下午要和客户开会。它如果看不到文档仓库，就不知道最新的方案已经不在聊天里，而在一个设计文档里。

所以，Slack 的方向不是把 agent 做成一个孤立的聊天入口，而是让它生活在团队的工作环境里。对工程师来说，这有点像你写一个服务，不只是实现一个函数，而是要接入日志、监控、配置、权限、告警和数据源。agent 的智能不是只来自模型本身，也来自它能读到什么、被允许做什么、以及它的输出会流向哪里。

接下来文章讲到人和 agent 团队的核心节奏。它不是人发一个问题，agent 回一个答案这么简单，而是一轮又一轮的交接。由 Claude in Slack 驱动的 agent 负责生产性工作，比如起草、总结、监控、准备材料，然后把结果交给人。人负责审核、判断、做决定、重新指示方向，再把下一步交还给 agent 执行。你可以把它想象成一个产品经理、工程师和运营之间的协作，只不过其中一些成员是 agent。agent 不应该替代所有判断，而是把大量准备工作和整理工作先做掉，让人把注意力放在优先级、取舍和责任上。

文章用了 Jaime 自己周一早上的例子。她说，周一早上，她已经收到了 agent 为她生成的每日简报。等着她审阅的，还有上一周产品工作坊的回顾，其中标出了需要升级处理的问题；一份关于全网 AI 发展的报告；当天会议的准备材料；还有一份她之前交给 agent 重写的过期个人简介。每一个循环的末尾，都是人来审阅，并基于 agent 的行动做决定。

这个例子非常具体，也很能说明 agent 的价值边界。你想象一下你自己的周一。你可能要看上周团队进展、线上问题、客户反馈、待办事项、今天的会议、行业新闻，还要补几份文档。这里面很多事并不需要你从零开始做，但如果没人准备，你就得自己在碎片时间里翻。agent 的角色就是把这些散落信息先变成可审阅的材料。它不是替你当负责人，而是替你铺好桌面，把要看的文件摊开，把异常标红，把明显的重复工作做掉。

文章还提到一个很实用的小设计：轻量信号要变成可行动的触发。在 Jaime 的频道里，一个 emoji 反应就可以把某个事项加入列表，然后 agent 接手任务。这个细节看似小，但对工作流很重要。我们平时推进自动化，经常失败在入口太重。你让团队成员每次都填一个表单，写完整需求，选择分类，再点提交，大家很快就不用了。但如果一个表情、一次标记、一个简短回复就能触发 agent，那它就更接近真实工作流。对 Slack 这样的协作工具来说，用户已经在频道里看消息、讨论问题、表达反应，agent 最好顺着这个自然动作接住任务，而不是要求人跳到另一个系统里。

不过，当你开始和一组专业 agent 一起工作时，会有一种不适应。因为很多人的心智模型还停留在一对一聊天机器人。打开一个窗口，问一句，得到一句。这种模式适合个人问答，但不太适合团队协作。Jaime 的做法更社会化，她说自己喜欢把 agent 想成同事。这个比喻非常有用。

如果 agent 是同事，那它就应该有角色和职责。一个人类同事不会什么都做，或者说如果一个人什么都说自己能做，你反而不知道该找他干什么。一个 agent 也一样。文章里说，agent 应该有清晰的目标和关注领域。如果 agent 的价值是被强制规定的，而不是使用者清楚感受到和理解的，那么大家很难记住这个东西到底是干什么的。换句话说，别指望靠一个公告让所有人使用某个 agent。真正有效的 agent，应该让人一用就知道，哦，这个东西就是帮我拉上周指标到状态更新里，或者就是帮我提交帮助台工单，或者就是每天早上帮我准备客户会议。

这对我们做内部平台或者 AI 工具的人有直接启发。很多公司现在会搞一堆 agent，名字很酷，功能描述很长，但用户不知道什么时候该用谁。结果最后大家还是回到通用聊天框。文章的建议是，对于常规、事务性的任务，可以交给一个通用 agent，而不是要求大家记住很多专用工具。比如提交帮助台工单、把上周指标拉进状态更新，这些任务不需要一个名字很复杂的系统。反过来，如果某个 agent 的用途连使用者都说不清，那可能就该退休了。这个“退休”意识很重要。内部工具最怕只增不减，最后变成另一个信息迷宫。

再往下，文章回到 Slack 最核心的产品哲学：默认公开频道。Jaime 说，从早期开始，Slack 就建议频道默认公开，因为你是在建立共享理解，为接下来所有工作建立共享上下文。她建议，除非有明确理由需要隔离上下文和知识，否则频道就保持公开。agent 能够访问的信息越多，它作为团队成员就越有效。

这里可能会让一些听众皱眉。公开频道当然好，但公司里有很多敏感事情，绩效、薪酬、客户合同、法律风险、未发布的财务信息，这些不能随便公开。文章并不是说所有东西都要公开，它强调的是，真正敏感的内容应该被隔离，但日常业务工作应该尽量在开放空间里进行。更有意思的是，文章指出，很多工作退回私信，并不是因为保密，而是因为人们不舒服，不想让别人看到自己半成品的思考。比如一个粗糙草稿、一个还没想清楚的问题、一段不成熟的推理。Jaime 的观点是，团队需要有心理安全感，让人可以相信同事会善意对待这些半成品。她还说，信任是通过给予信任获得的。

这段对 agent 尤其重要。因为 agent 读的就是团队读到的东西。一个私密频道，对汇报它的每个 agent 来说都是盲点。你把关键讨论放在私信里，agent 之后做总结、做风险扫描、做会议准备，就会漏掉这些内容。过去，私信带来的问题主要是新人看不到历史，团队重复沟通。现在又多了一层，agent 也看不到历史。上下文被切碎，智能就会打折。

我个人认为，这里是企业落地 agent 最容易被低估的部分。大家会花很多时间讨论模型选择、权限架构、提示词模板，却不愿意讨论组织文化。可是 agent 的效果和组织文化高度相关。如果一个团队习惯把真实讨论藏在小群和私信里，只把已经包装好的结论放到公共频道，那么 agent 学到的就只是表面叙事。它看不到争议，看不到权衡，看不到为什么一个方案被放弃。最后它生成的知识也会很漂亮，但不一定真实有用。相反，如果团队愿意把大部分日常工作留在公开频道，哪怕里面有草稿和困惑，agent 才可能把工作过程转化为可复用知识。

文章还讲了推广新工作方式的方法。最快学习一种新工作方式的办法，是看同事怎么做。Jaime 在 Salesforce 看到一个例子，员工在一个全公司频道里分享技巧、调试经验和工作流小窍门，频道叫 How I Slackbot。按照她的说法，这个频道有几千名成员，而且默认公开。在这样的频道里，一个来自销售流程的小技巧，可能最后重塑一个工程流程。

这个例子非常真实。很多时候，AI 工具的最佳用法不是从产品说明书里来的，而是从同事的偷懒技巧里来的。一个销售同事发现可以让 agent 根据客户邮件生成下一步行动，一个客服同事发现可以让 agent 把重复投诉归类，一个工程师看到了，可能就会想到让 agent 根据错误日志和工单生成排查清单。跨职能传播的不是工具本身，而是“原来还可以这么用”的想象力。

Slack 内部推广产品经理使用 Claude 的过程也很有意思。文章说，那是一个几乎完全自组织的过程。一个产品经理找开发者体验负责人帮自己配置起来，然后写了一个 Slack canvas，也就是一种共享画布，说明自己做了什么、怎么做的。其他产品经理开始复制这个格式。团队自己组织工作坊，甚至建立自己的 Git 仓库。你看，这不是一个自上而下的强制培训，而是一个可复制样板扩散出去的过程。

对工程组织来说，这个启发很直接。如果你想推广 agent，不要只发一封邮件说“我们已经购买了 Claude，请大家使用”。更有效的做法是建立一个公开的展示频道，让大家分享自己真实的工作流，尤其是失败和调试过程。比如“我用 agent 做发布前检查，它漏掉了数据库迁移，所以我后来加了哪些上下文”，“我让 agent 写事故复盘初稿，它第一次太像模板，后来我让它引用具体时间线和监控指标”，“我用 agent 整理客户反馈，结果分类太粗，于是我改成先让它抽取原话再聚类”。这些小故事比宏大的 AI 战略更能推动采用。

然后文章进入一个更难的问题：怎么衡量生产力。Jaime 说，她从 Slack 早期就一直在思考这个问题。我们想让人发送更多消息吗？也许不是。发送更多消息不一定意味着他们从 Slack 获得更多价值。更多消息可能意味着大家找不到需要的东西，或者第一次没能把意思说清楚。

这个类比放到 AI 上也成立。现在很多团队会看 token 使用量。token 是大模型处理文本的基本计量单位，使用量能说明系统在被调用，也能说明费用和容量情况。但文章说，token 使用量只能告诉你灯亮着，也就是有人在用，但这还不够。使用量是脉搏检查，不是价值证明。你看到一个团队每天调用十万次 agent，不能自动得出结论说他们生产力提高了。也可能是因为 agent 输出质量差，大家反复重试；也可能是因为流程设计不好，把简单事情复杂化；还可能是大家在新鲜感阶段玩得多，但没有改变关键业务结果。

Jaime 说，对于这么复杂的事情，简单指标无法完成任务。要把工具使用和更好的业务结果连接起来，仍然需要很多信念上的跳跃，没有一个仪表盘或者使用统计能替你证明。这个说法很诚实，也可能让一些管理者不太舒服。因为大家都希望有一个简单数字，比如每人每天节省多少分钟，需求交付速度提升多少，会议减少多少。但组织知识和协作质量本来就很难测。你怎么衡量一个新人因为 agent 总结历史而少问了五个问题？你怎么衡量一个错误决策因为 agent 找出了三年前类似失败案例而被避免？这些价值真实存在，但不一定会立刻出现在一个干净的报表里。

我个人认为，比较务实的做法是把定量和定性结合。定量上看使用是否持续、哪些任务被反复使用、人工修改率大概怎样、响应时间和成本是否可控。定性上要听团队讲故事：哪些工作过去很痛，现在变轻了；哪些决策因为上下文更完整而更快；哪些 agent 大家已经自然依赖，哪些只是被迫打开。文章没有展开这套评估框架，但它提醒我们，不要把使用量误认为价值。

最后，Jaime 给组织实施人类 agent 团队的最大建议，是重新想象每一个工作流。她说，我们必须弄清楚怎样改变工作方式，而不只是更快地做同一种工作，而且这会是一项团队运动。这个观点可以说是全文的落点。agent 的意义不是让你把原来十分钟的会议总结压缩到一分钟，虽然这也有价值。更大的意义是，当准备、总结、监控、检索、起草这些生产性动作成本大幅下降后，团队的协作方式本身应该改变。

比如过去你不开一个同步会，就没人有时间整理信息。现在 agent 可以在会前准备背景、会中抓取行动项、会后总结分歧和决策。那会议就可以更少地用于信息传递，更多地用于判断和取舍。过去一个设计文档写完之后就躺在仓库里，很少有人回头看。现在 agent 可以在新需求出现时主动找出相关历史文档和决策。那文档就不只是归档，而是会重新参与工作。过去你接手一个项目，靠问人补上下文。现在如果频道公开、文档连通、agent 有权限，你可以让 agent 给你生成一份“这个项目从哪里来、现在卡在哪里、谁做过哪些关键决定”的入门材料。那 onboarding，也就是新人上手，就不再完全依赖师傅带徒弟。

对正在听节目的工程师和 AI 从业者来说，最实际的问题是：明天能怎么做？如果你在一个团队里想尝试，不要一上来做全公司大平台。文章最后的建议是，尽快开始，但从小处开始。把一组人带进一个共享频道，接入 Claude，给他们同一套资源，然后让他们工作。如果 Slack 的经验有参考价值，他们做出来的东西会自己扩散。

我建议你可以从一个具体频道开始，比如一个产品研发小组频道，或者一个值班和事故响应频道。先挑三类任务。第一类是每日或每周简报，让 agent 总结过去一天的关键变化、阻塞、风险和待决问题。第二类是会议准备，让 agent 根据频道讨论、文档和日历，为每个会议准备背景、待确认事项和建议议题。第三类是决策追踪，让 agent 不只记录“决定了什么”，还要整理“为什么决定、反对意见是什么、哪些前提未来需要复查”。这三类任务都符合文章里说的模式：agent 做准备和整理，人做审核和判断。

如果你负责内部 AI 平台，还要特别注意权限和边界。文章强调公共频道，但不是鼓励越权访问。agent 能读什么，应该和团队能读什么一致。敏感信息要隔离，尤其是人事、法务、财务和客户保密内容。与此同时，也要警惕因为过度保守导致 agent 什么都看不到。一个没有上下文的 agent，会变成一个看似聪明但经常胡猜的助手。比较好的设计是，把日常业务尽量放在公开或团队可见空间，把真正敏感的内容明确分区，让人知道哪里适合开放协作，哪里必须严格控制。

还要避开一个坑，就是让 agent 的输出直接变成事实。文章反复强调，每个循环末尾是人来审阅和决策。特别是在工程场景里，agent 总结事故原因、生成迁移步骤、整理客户影响范围，都可能出错。你可以让它做初稿，让它把证据列出来，让它指出不确定之处，但最终负责的人必须审核。把 agent 当同事，不等于把它当负责人。一个初级同事写的发布方案，你也会 code review，也会让资深工程师把关。agent 也一样。

另一个坑，是把 agent 设计成太万能。很多团队会想做一个“公司万能助手”，既能查制度，又能写代码，又能订会议室，又能分析销售数据。结果用户不知道它擅长什么，也不知道什么时候该信它。文章里“像同事一样”的比喻可以帮我们校准。你可以有一个通用事务 agent，处理重复和低风险任务；也可以有几个专业 agent，围绕产品反馈、工程值班、客户会议、市场情报等场景。但每个 agent 都要能用一句话说清楚价值。如果说不清，就不要硬推。

还有一个很实用的推广方式，是建立一个内部“我是怎么用 agent 的”频道。不要只发成功案例，也鼓励分享调试过程。比如某个后端工程师分享，他让 Claude 在 Slack 里每天检查值班频道，把超过两小时没更新的事件标出来。另一个前端工程师看到后，可能会把这个模式改造成设计评审跟踪。一个产品经理分享，她让 agent 根据一周用户反馈生成主题和原话摘录，客服团队可能就拿去做投诉分类。文章里 Salesforce 的 How I Slackbot 频道说明，真正有生命力的采用，往往来自这种公开模仿和改造。

如果你是团队管理者，最好也调整一下自己对产出的期待。不要问“用了 AI 之后大家发了多少消息、调用了多少 token”。这些数字可以看，但只能当体温计。更应该问的是：团队是不是少重复解释同样背景了？新人是不是更快理解历史？决策是不是更容易回溯原因？会议是不是更少用于同步信息，更多用于做判断？那些过去没人愿意做的总结和准备，现在是不是有了稳定机制？这些问题虽然不如仪表盘漂亮，但更接近 agent 对协作的真实价值。

我个人还想补一句，Slack 这篇文章有一个隐含前提：对话本身很重要，但对话必须被组织。过去我们常说“文档是知识”，后来又说“代码是文档”，Slack 的观点更进一步，工作对话也是知识的原材料。可是原材料不是成品。没有 agent 的时代，人类很难把这些原材料持续加工成可复用知识。现在 agent 给了我们一个机会，但前提是你要让原材料可见、可访问、可追溯，并且在人类判断的监督下被加工。

所以回到全文，Anthropic 这篇访谈真正想传达的，不是 Slack 有了几个很酷的机器人，而是企业 AI 的落地可能会从个人助手走向团队成员。agent 的价值不只在于回答问题，而在于参与工作循环：准备、总结、监控、起草、交接，然后由人审核、决定、重新指挥。这个循环跑得越自然，agent 越像团队的一部分，而不是一个额外工具。

最后用两三句话收尾。Slack 的经验告诉我们，工作中的对话过去没有自动变成知识，不是因为对话没价值，而是因为人类没有足够能力持续整理它。agent 让这个老愿景重新变得可行，但它需要公开上下文、清晰职责、轻量触发、人工审核和组织层面的学习机制。我个人认为，这篇文章最值得中国工程团队带走的一句话是：不要只用 AI 更快地做旧流程，而要从一个小频道开始，重新设计人和 agent 怎么一起工作。
