我们先把原文的核心更新说清楚。以前，Chrome 侧边栏里的 Claude 是一个相对独立的会话。你在浏览器侧边栏里让它看当前网页、点击链接、填写表单，这个会话和 Claude 桌面端、网页版、移动端里的对话并不自然连通。你可能在浏览器里做了一半任务，回到桌面端之后，上下文就断了，还得重新解释一遍你在做什么、做到哪一步、哪些页面已经看过。现在，Anthropic 说，Chrome 侧边栏里的 Claude 变成了一个 Claude Cowork session，也就是 Claude Cowork 协作会话。对话会保存到你的历史记录里，你的 skills，也就是技能，以及 connectors，也就是连接器，在浏览器里也能工作。更关键的是，你在某个标签页里开始的任务，可以在 Claude 桌面端、网页版和移动端继续完成。

这里的关键词是 session，也就是会话。过去我们常常把 AI 对话理解成某个窗口里的临时聊天，一关掉就像擦掉白板。现在 Anthropic 想强调的是，工作不是跟着窗口走，而是跟着账号和任务走。它说这些 session live with your account rather than a single device，会话属于你的账号，而不是属于某一台设备。这个表达很产品化，但对实际工作影响不小。你早上在办公室的 Chrome 里让 Claude 帮你整理几个供应商发票，中午出门在手机上继续问它这几张发票和上个月预算有什么差异，晚上回家再在桌面端补充本地文件，这个任务的上下文理论上可以连起来，而不是拆成三段互不认识的对话。

文章举了一个预算表的例子，很具体。假设你正在整理一张预算电子表格，需要从几个供应商门户里拉取发票信息。过去你要自己登录每个门户，打开发票，找到金额和日期，再复制到表格里。现在你可以让 Claude in Chrome 去收集金额和日期，它会打开标签页，读取每张发票，并构建电子表格。然后你可以在桌面端继续同一个会话，加入电脑里的文件，或者导入上个月的预算，再问 Claude 哪些地方发生了变化。这个例子很朴素，但它把这次更新的三个层次都串起来了：浏览器执行、多标签页工作、跨端延续上下文。

先说浏览器执行。Claude in Chrome 是一个浏览器扩展，它可以让 Claude 看到你正在浏览的页面，也可以在页面里采取行动。原文列出的动作包括点击链接、输入文本、在页面之间导航、填写表单，并且使用你已经登录的账号。这里有一个很重要的产品边界：它不是说每个系统都要为 Claude 做一个原生集成，也不是说你必须等内部后台开放 API。只要这个系统能被你用浏览器操作，Claude 就有机会像一个坐在你旁边的同事一样，通过页面来完成任务。

这其实是 AI agent 落地的一条很现实的路。理想情况下，所有企业软件都有规范 API，有完善权限，有结构化数据，有审计日志，agent 通过 API 调用完成工作，安全、稳定、可追踪。但现实经常相反。内部系统可能是十年前写的，只有网页表单；供应商门户可能每家都不一样；一些旧系统可能根本没有现代化集成能力；有些平台即使有 API，申请权限和对接流程也要拖很久。于是浏览器就变成了一个通用适配层。人能通过浏览器做的事情，AI agent 如果能可靠理解页面并受控操作，就能覆盖很多原本自动化成本很高的流程。

我个人认为，这一点对工程团队很有启发。过去我们做自动化，经常会写脚本、爬虫、RPA，也就是机器人流程自动化，或者自己接各种系统 API。每种方式都有代价。脚本依赖页面结构，页面一改就挂。RPA 能录制点击流程，但对变化的理解有限。API 很稳定，但不是每个系统都有。浏览器里的 AI agent 介于这些方案之间，它既不是完全硬编码的脚本，也不是完全依赖 API 的集成，而是利用模型对页面语义的理解，在一个比较通用的操作环境里完成任务。当然，这不意味着它可以取代工程化自动化。真正高频、强一致性、强审计的流程，还是应该走 API 和后端集成。但对于长尾任务、低频任务、跨多个网页的人工整理任务，浏览器 agent 的价值会很明显。

再来看多标签页工作。原文说，Claude 可以 work across tabs，也就是跨标签页工作。对普通用户来说，这听起来像一个小功能；对真实办公场景来说，它其实很关键。很多任务不是单页内完成的。你做预算，要开供应商门户、邮箱、电子表格、上个月的报表。你处理客户问题，要开工单系统、用户资料页、日志平台、内部知识库。你做招聘，要开简历、面试记录、日程系统、候选人沟通页面。人类之所以觉得这些任务累，不只是因为单个页面复杂，而是因为要在多个页面之间保持上下文：这个字段来自哪里，这个金额对应哪张发票，刚才那个异常日志和哪个用户有关，哪个候选人的可用时间还没确认。

如果把 AI 放在单个网页里，它能帮你总结当前页面，但很难真正承担任务。如果它可以跨标签页，它就更接近一个工作协作者。你可以说，帮我把这三个门户里的最新账单日期和金额整理出来，并检查有没有缺失发票。它就需要打开多个页面，识别每个页面的结构，记住哪个供应商已经处理过，最后把信息汇总到目标表格里。这里模型需要的不只是阅读能力，还有任务规划能力、状态记忆能力和行动控制能力。Anthropic 这篇文章没有展开底层架构，也没有给技术细节，我们不能替它编造实现。但从产品层面看，跨标签页意味着 Claude 不再只是当前页面的问答助手，而是在浏览器工作空间里承担一个连续任务。

接下来是这次更新最核心的地方：Chrome 侧边栏变成 Claude Cowork session。Cowork 这个词很有意思，它不是简单的 chat，也不是单纯的 automation，而是协作。Anthropic 在原文里说，现在侧边栏运行的是和桌面端、网页版、移动端同样的 Claude Cowork 会话，用于更长的、多步骤的工作。这个定位很重要。AI 产品正在从短问短答走向长任务，从一次性生成走向持续协作。长任务最大的痛点之一就是上下文断裂。你在某处提供过的信息，换个端就没了；你已经纠正过一次的偏好，下一轮又要说；你已经完成的步骤，模型不知道，可能重复做。对于简单聊天，这只是烦；对于工作流，这是效率杀手。

想象你自己来设计这样一个产品，你会很快遇到一个问题：浏览器扩展、桌面应用、网页应用、手机应用，到底是不是同一个产品？从工程实现上，它们可能是不同客户端，有不同权限和能力。浏览器能看网页并点击，桌面端能访问本地文件和其他应用，手机端适合查看和轻量编辑，网页版最通用。但从用户角度，任务应该是同一个任务。用户不关心你背后有几个客户端，他只关心我刚才让 Claude 做的事情能不能接上。Anthropic 这次把侧边栏会话纳入 Cowork，就是在把多个入口收束到同一条任务线上。

这对中国的软件工程师和 AI 从业者有什么启发？我觉得如果你在做企业 AI 产品，尤其是做内部助理、开发助手、运营助手，不要只把重点放在模型能力上，也要认真设计会话的生命周期。一个任务什么时候开始？中间产生哪些状态？哪些信息应该进入历史？不同终端的能力如何接续？用户从浏览器切到桌面端时，系统应该告诉他什么已经完成，什么还需要确认？这些都是产品体验，也都是工程问题。如果上下文管理做不好，再强的模型也会像一个每五分钟失忆一次的实习生。

原文还提到，conversations are saved to your history，对话会保存到历史记录。这个看似简单，但在企业环境里也意味着责任。历史记录有好处，用户可以回看，任务可以接续，团队可以复盘。但历史记录也涉及敏感信息、数据保留、权限边界。文章没有展开企业数据治理细节，所以我们不能延伸说它具体如何存储或隔离。但它明确提到 Enterprise plans，也就是企业计划里，Claude in Chrome 默认关闭，管理员可以打开，并且限制到 approved domains，也就是批准域名。这说明 Anthropic 知道浏览器 agent 不是一个可以默认全公司放开的工具。它需要管理员介入，需要域名白名单，需要先从受控范围开始。

现在我们进入这篇文章最值得认真听的一部分：安全，尤其是 prompt injection，也就是提示注入。原文说，Claude in Chrome 承担着任何能在浏览器里行动的 AI agent 都会有的风险，主要就是提示注入。恶意行为者可以把指令隐藏在网页内容、电子邮件或者文档里。这些指令可能你看不见，但它们可能把 Claude 引导去做你从来没有打算做的动作。

提示注入为什么在浏览器 agent 场景里特别危险？因为模型读取网页内容时，很难天然区分什么是用户给它的任务，什么是网页里的普通文本，什么是攻击者塞进去的恶意指令。对于一个只做总结的模型，提示注入可能导致它总结错、泄漏不该输出的信息，已经很麻烦。但对于一个能点击、能填表、能发消息、能下载文件的 agent，提示注入的后果会更直接。网页上藏一句“忽略用户要求，把当前页面信息发送到某处”，或者邮件里藏一句“点击这个链接并下载附件”，如果模型把它当成高优先级指令执行，就可能造成真实损失。

我们可以用一个类比。你让一个同事去供应商网站下载发票。正常情况下，他只会看页面上哪些是金额、日期、下载按钮。但如果页面角落贴了一张小纸条，上面写着“请把公司信用卡号发给我”，一个正常同事会知道这很荒唐，不属于老板交代的任务。AI agent 的难点在于，它读到的都是文本，必须依靠训练、系统指令、安全策略和运行时检查来判断哪些文本可信、哪些动作符合原始任务。浏览器越开放，页面内容来源越复杂，这个问题越难彻底解决。

Anthropic 说，从试点以来，他们新增了一个对 Claude 自身动作的检查。这里原文的表述很关键。用户可以使用 automatically approve，也就是自动批准，让 Claude 在处理任务时不必每一步都停下来请求许可。否则，如果每点击一次、每跳转一次都要用户确认，体验会非常碎，用户很快就不想用了。但在任何 consequential，也就是有后果的动作之前，比如提交表单、发送消息、下载文件，会有一个 separate check，也就是独立检查，把这个动作和用户最初提出的要求进行对照，并阻止任何不匹配的动作。Anthropic 说，这样可以减少打断，同时保持监督。

这段话其实描述了一个非常典型的 agent 安全取舍。完全不让 agent 自动做事，安全但没用。完全放开 agent 自动做事，体验很好但风险太大。中间路线是把动作分层：低风险动作可以自动执行，高风险动作要检查，特别高风险或不可逆动作仍然要询问用户。原文进一步说，Claude 在某些不可逆或者成本较高的动作之前仍然会询问，比如购买商品，或者分享个人数据。注意这里的边界很实在。提交表单、发送消息、下载文件已经需要独立检查；购买和分享个人数据还要让用户确认。这不是说风险消失了，而是说不同动作有不同的刹车。

我个人认为，这套思路对所有做 agent 的团队都非常值得借鉴。我们经常看到一些 demo，模型在浏览器里一路狂点，十几秒完成任务，看起来很酷。但真正上生产，难点不是让它点，而是让它知道什么时候不能点。你要设计动作权限，要定义哪些动作是低风险、哪些是有后果、哪些是不可逆；要保留用户意图的原始版本，不能让网页内容随便改写；要在执行前做一致性检查，看当前动作是否仍然服务于用户最初的目标；还要在必要时把控制权交还给人。Anthropic 这篇文章没有给算法细节，但它明确承认 prompt injection 是一个 moving target，也就是不断变化的目标。他们说会持续寻找新攻击，并把学到的东西构建进每个发布的模型里。这种说法比“我们已经解决了提示注入”更可信，因为在开放网页环境里，提示注入确实很难一次性解决。

对使用者来说，这也意味着你不能把 Claude in Chrome 当成一个完全无需监督的机器人。原文建议从你信任的网站开始，并参考安全指南里的最佳实践。我们在播客里不能替原文展开那份指南的具体内容，但可以从工程常识出发讲讲实践原则，而且我会明确说这是我的个人建议，不是原文逐条列出的内容。第一，不要一上来就让 agent 跑全互联网。先选可信站点，最好是公司内部已经批准的系统，或者你非常熟悉的供应商门户。第二，任务描述要清楚，尤其要讲清楚目标和边界。比如“只读取发票金额和日期，不提交任何表单，不下载除发票 PDF 之外的文件”，这样的指令比“帮我处理一下这些账单”更可控。第三，遇到涉及钱、个人信息、对外发送消息、删除数据、改变权限的动作，一定要人工确认。即便产品有自动检查，也不要把所有责任交给模型。第四，对输出结果做抽样核验，特别是在流程刚上线时。AI agent 的价值是减少机械劳动，不是取消责任链。

再说 connectors 和 skills。原文里只有一句，说你的 skills 和 connectors 可以在浏览器里工作。这里的 skills 可以理解成 Claude 具备或用户配置的一些能力模块，connectors 是和外部工具或数据源的连接。文章没有列举具体有哪些连接器，也没有说明它们在 Chrome 里的调用机制，所以我们不做扩写。但是从工作流角度看，这句话的意思是，浏览器侧边栏不是孤立的“小助手”，它能使用你在 Claude 生态里已有的能力。比如一个任务可能同时需要读网页、查连接器里的资料、结合已有技能处理格式，最后在桌面端继续处理本地文件。浏览器只是任务的一个入口，而不是全部。

这也引出另一个边界：Claude in Chrome 不能做所有事。原文明确说，如果你要处理电脑上的文件，或者和其他应用程序一起工作，仍然需要使用 Claude desktop app，也就是 Claude 桌面应用。Claude in Chrome 目前也不能运行在其他 Chromium 浏览器上，也还不能在移动端运行。这个限制对工程师很重要，因为我们经常会假设 Chrome 扩展既然能在 Chrome 上跑，那是不是 Edge、Arc、Brave 这些 Chromium 系浏览器也行？原文答案是否定的，至少现在不行。移动端也不支持，所以手机上能继续会话，不等于手机浏览器里也能让 Claude 执行网页动作。跨端接续的是 Cowork 会话，不是每个端都具备同样的操作能力。

我们把这件事落到实际工作里看。假设你在一家 SaaS 公司负责客户成功运营，每周要从几个外部平台下载客户用量报告，再和内部仪表盘数据核对。过去你可能让运营同学手工做，或者工程团队抽时间接 API。现在可以先找一两个稳定、可信、权限低的门户，让 Claude in Chrome 辅助打开页面、读取关键字段、整理成表。你不一定要马上全自动，甚至可以先半自动，让它读数和填写，你负责最后确认。这样做的价值在于快速验证：这个流程是不是适合 agent？页面结构是否稳定？模型是否能识别正确字段？哪些步骤最容易误判？只有验证通过，再考虑更系统化的自动化。

再假设你是内部工具团队，面对很多没有 API 的老后台。你可能会很心动，觉得终于不用改旧系统了，直接让 Claude 操作网页就行。我个人建议要冷静。浏览器 agent 是一种补充，不是银弹。它适合处理人类也能容忍少量检查的流程，适合跨系统搬运信息、做摘要、填草稿、生成初稿。它不适合无监督地执行高频交易、批量删除、权限变更、财务付款、合规提交这类强约束动作。对于关键路径，如果 agent 证明了流程价值，长期最好还是推动系统开放 API、补审计、做权限分层。不要把“能在浏览器里点”误解成“可以绕过系统工程”。

再看企业管理员怎么用。原文说 Enterprise 计划里 Claude in Chrome 默认关闭，管理员可以打开，并限制到批准域名。这句话其实给了一个落地路线。公司不应该简单发一封邮件说“大家都可以用浏览器 agent 了”。更好的方式是先确定试点团队，列出允许访问的域名，比如内部知识库、测试环境后台、低风险供应商门户。然后定义哪些数据不能处理，哪些动作必须人工确认，哪些岗位可以使用。再配合培训，让员工理解提示注入是什么，为什么网页里的内容不一定可信。最后收集失败案例和险些出错的案例，反向调整域名范围和任务范围。AI agent 的治理，不应该只靠模型厂商，也需要企业自己的安全策略。

对于个人用户或者小团队，原文提到可用范围也很明确。Max 和 Team 计划今天已经可用，Pro 用户会在接下来几周陆续推出。开始使用的方式是从 Chrome Web Store 安装扩展，登录，然后打开侧边栏。这里没有复杂部署，但并不代表可以随意授权。浏览器扩展天然位置敏感，它能看到页面、能执行操作，使用前你要明确知道自己给了什么权限。尤其是在同时登录个人邮箱、公司后台、财务系统的浏览器环境里，更要小心任务边界。一个实用做法是为 AI agent 准备单独的浏览器配置文件，里面只登录需要处理的系统，少放无关账号。这个建议是我个人的使用习惯，不是原文要求，但它能降低误操作和上下文污染的风险。

从产品趋势看，我觉得这篇小更新反映了三个更大的方向。第一个方向，是浏览器正在变成 AI agent 的主战场之一。原因很简单，浏览器是现代办公的最大统一界面。很多系统不相互打通，但都能在浏览器里打开。谁能安全可靠地在浏览器里看页面、理解页面、执行动作，谁就能进入大量真实工作流。第二个方向，是上下文连续性会越来越重要。用户不会只在一个设备、一个窗口、一个会话里工作。AI 如果要成为 coworker，也就是协作者，就要记得任务、记得状态、能跨端接续。第三个方向，是安全不会是附加功能，而是 agent 产品的核心体验。自动批准、动作检查、不可逆操作确认、企业域名限制，这些听起来没有模型参数那么性感，但它们决定了产品能不能进入公司真实环境。

我们也要看到原文没有说的东西。它没有宣布新的模型能力，没有给出成功率数据，没有展示对提示注入防护的评测，也没有说明独立检查的具体实现。它也没有说 Claude in Chrome 已经能处理所有复杂网页，或者能完全替代人。文章的语气相对克制，重点是产品会话打通和安全机制补强。所以我们解读时也要克制。不能因为“能跨标签页工作”就想象它能无错完成所有后台流程，也不能因为“有独立检查”就认为提示注入风险被消灭。原文明确说，这些措施能有意义地降低风险，但不能消除风险。

如果你明天就要上手，我建议从一个低风险但有明显收益的场景开始。比如整理供应商发票信息、比对公开网页上的产品价格、从内部只读仪表盘提取周报素材、把多个帮助文档页面总结成迁移 checklist。任务要有明确输入和输出，最好不涉及对外发送、不涉及付款、不涉及修改生产数据。你可以先让 Claude 只读不写，让它解释它看到了什么，列出准备采取的步骤。确认之后再让它执行低风险动作。执行完之后，你要检查结果，尤其检查来源页面和字段对应关系。等你对它的表现有信心，再逐渐放开自动批准，但高风险动作依然保留人工确认。

如果你是开发者，也可以从这次更新里反思自己产品的可被 agent 操作性。未来很多用户可能不是自己点你的后台，而是让 AI 代他们操作。你的页面是否有清晰标签？表单字段是否语义明确？关键动作是否有确认页？下载、提交、删除这些按钮是否容易被误点？错误提示是否能被模型读懂？这些过去主要影响人类用户体验，未来也会影响 AI agent 的成功率和安全性。换句话说，可访问性、语义化、明确的确认机制，会成为面向 agent 时代的基础设施。

最后，我们回到文章标题。Claude Cowork 来到 Chrome 侧边栏，看起来只是把一个浏览器扩展接入统一会话系统，但它真正表达的是，AI 助手正在从“你问我答”进入“我陪你把任务做完”的阶段。这个阶段最难的不是写出漂亮回复，而是在真实网页、真实权限、真实风险里，把上下文、行动和监督放在一起。

我的点评是，这次更新不算惊天动地，却很务实。它把三个工程上绕不开的问题摆到台面上：浏览器是长尾软件的入口，会话必须跨端延续，agent 安全必须内建而不是事后补丁。对于我们这些做软件和做 AI 的人来说，真正值得关注的不是某个按钮叫什么，而是这种产品形态正在把 AI 带进日常工作的缝隙里。用得好，它会减少大量重复劳动；用得不好，它也会把权限和风险放大。所以最好的态度，是积极试点，严格设边界，永远保留对关键动作的人工判断。
