## Script

今天我们要聊的文章，标题是 The new rules of context engineering for Claude 5 generation models，我把它翻译成，Claude 五代模型的上下文工程新规则。这篇文章发表于二零二六年七月二十四日，也就是两天前，今天是二零二六年七月二十六日，所以这是一篇非常新的文章，基本上反映的是 Anthropic 对 Claude Opus 五和 Claude Fable 五这一代模型的最新实践总结。

这篇文章特别值得软件工程师和 AI 从业者听，因为它讲的不是一个很炫的新功能，也不是某个模型榜单又涨了几分，而是一个更贴近日常开发的问题。我们到底应该怎样给 AI 编程助手准备上下文。换句话说，当你在用 Claude Code，或者你自己在公司里做一个 agent，也就是智能体系统的时候，你应该把多少规则、多少说明、多少团队习惯、多少项目背景塞给模型。过去很多人的直觉是，越详细越好，越安全越好，越多例子越好。但 Anthropic 这篇文章给出的结论有点反直觉。他们说，对于最新一代 Claude 模型，他们把 Claude Code 的 system prompt，也就是系统提示词，删掉了超过百分之八十，在编码评测上却没有看到可测量的损失。

这句话如果你做过 agent，一定会觉得很有冲击力。因为很多团队现在的提示词工程，实际已经变成了提示词考古。某一年为了避免模型误删文件，加了一条强规则。某一次模型乱写注释，又加了一条禁止注释。某个客户抱怨输出风格不对，又加了一段风格要求。最后 system prompt 越来越像一个公司内部制度汇编，里面有很多条款单独看都有道理，但放在一起就会互相打架。模型每次响应前，都要先在这些规则之间做法律解释。Anthropic 这篇文章的核心观点就是，到了 Claude 五代模型，很多过去必要的护栏，正在变成束缚。上下文工程的新方向，不是把模型管得更死，而是给模型更清晰的环境、更好的工具接口、更合适的参考材料，然后让它运用判断力。

我们先把背景说清楚。很多人平时说 prompt，指的是你在对话框里敲的那句话，比如帮我修这个 bug，或者给这个函数加单元测试。但文章开头就提醒我们，当你给 Claude 发一条消息时，你写的 prompt 只是它拿到的上下文里很小的一部分。真正进入模型视野的，还有 system prompt，Skills，也就是技能说明，CLAUDE.md 文件，memory，也就是记忆，以及其他来源。Anthropic 把这一整套东西叫做 context engineering，中文可以叫上下文工程。

为什么要单独强调上下文工程。因为 prompt 通常是一次性的、具体的，它可以非常针对当前任务。但上下文是横跨很多请求反复使用的，它不能太具体。你不知道用户下一句会问什么，也不知道 agent 下一步会遇到什么代码结构。于是问题来了，你怎么写一套通用的背景、规则和指导，让 Claude 在各种请求里都能受益，而不是被误导。

这件事的难点，会随着模型能力变化而变化。老模型不够稳的时候，你可能必须写很多强约束。比如不准删除文件，不准随便改配置，不准写太长的文档，不准生成中间规划文件。这样做的目的是避免最坏情况。可是当模型变聪明以后，同样的强约束就可能让它在本来应该灵活处理的地方变得僵硬。Anthropic 说，他们最近明显感受到，对最新一代 Claude 模型的 prompting 方式发生了大跳跃。对 Claude Opus 五和 Claude Fable 五这样的模型，他们删除了 Claude Code 系统提示词超过八成，而且编码评测没有可测量的退化。

这里我个人认为，最重要的不是百分之八十这个数字本身，而是它背后的工程信号。模型能力提升以后，最佳实践不是简单地继承过去的提示词资产，而是要重新审计。你原来写进去的每一条规则，可能曾经是修复一个问题的补丁，但今天它可能已经成了技术债。就像一个老项目里有很多兼容代码，早年是为了支持旧浏览器，后来浏览器升级了，你还继续保留那些 hack，就会让主逻辑越来越难维护。提示词和上下文也是一样。

文章把这个过程叫做 unhobbling Claude，可以理解为给 Claude 松绑。Anthropic 发现，他们以前在 Claude Code 的 system prompt、CLAUDE.md 文件和 skills 里，都对 Claude 约束得太多了。内部使用记录里经常出现这样的情况。同一个请求里，系统提示词说，按情况保留文档。另一个 skill 又说，不要添加注释。用户自己的请求可能又说，这里要解释清楚。结果 Claude 面对的是几个互相冲突的信息源。通常它能够理解用户真实意图，最后也能做对，但它必须额外思考这些重叠和冲突的指令，才能决定怎么做。这会增加认知负担，也可能降低输出质量。

这对我们很有启发。很多公司在引入 AI coding agent 的时候，会把各种规范都写进一个长文档。比如代码风格、提交规范、测试规范、安全规范、数据库变更规范、前端组件规范，甚至还有沟通语气规范。每条都来自一个真实痛点。但一旦这些规范过长、过细、互相重复，模型就会像一个刚入职的新同事，拿着五份互相矛盾的 onboarding 文档，不知道到底该听哪一份。人类工程师遇到这种情况会去问同事，或者凭经验判断。新一代 Claude 也越来越能判断，所以文章建议我们，不要把所有判断都替模型预先写死。

第一个变化，是从给 Claude 规则，转向让 Claude 使用判断力。文章举了一个很具体的例子。早期 Claude Code 的系统提示词里曾经说，在代码里默认不写注释。绝不要写多段 docstring，也不要写多行注释块，最多一条短注释。除非用户要求，不要创建规划、决策、分析文档，要基于对话上下文工作，而不是创建中间文件。

如果你过去用过 AI 写代码，这类规则听起来很熟悉。因为老模型确实喜欢啰嗦。你让它修一个小 bug，它可能在代码里加一堆解释性注释，甚至创建一个 plan.md，写一篇执行计划。更糟糕的是，它写的注释有时还不准确，反而污染代码。所以早期加上不写注释这种强规则，是一个合理权衡。宁可少写，也不要乱写。

但问题在于，这条规则并不总是正确。很多复杂代码确实需要多行注释。有些团队有自己的文档风格，有些公共 API 需要详细 docstring，有些算法实现没有解释就很难维护。如果系统层面死规定不写多行注释，模型就会在这些场景里做错。Anthropic 说，更新后的提示词不再用这种绝对禁令，而是改成一句更抽象、更依赖判断的话。写出的代码要读起来像周围的代码，匹配它的注释密度、命名方式和惯用写法。

这句话非常值得品味。它不是说永远不要注释，也不是说必须注释，而是把判断依据交给周围代码。对于软件工程师来说，这其实更符合真实工作方式。你加入一个代码库，不会先问全世界最佳实践是什么，而是先看这个仓库怎么写。周围文件如果几乎不写注释，你突然加一大段注释就很突兀。周围文件如果每个 public method 都有 docstring，你新写的函数也应该保持一致。这叫局部一致性。新模型能够读懂这种上下文，所以提示词就可以从命令式规则，转为原则式指导。

你可以把这个变化应用到自己的项目里。假设你现在 CLAUDE.md 里写着，不要使用 any，不要写 class component，不要直接访问数据库，不要修改 migration，不要生成 mock 数据。你可以逐条问自己，这些是永远成立的硬约束，还是大多数时候成立的偏好。如果是偏好，就尽量改成更有判断空间的表达。比如，优先遵循当前模块的类型风格，除非用户明确要求，否则不要引入新的抽象。再比如，数据库访问要跟随现有 repository 层模式，不要绕过已有封装。这样的表达比简单禁止更有用，因为它告诉 Claude 应该参考什么，而不是只告诉它不能做什么。

第二个变化，是从给 Claude 例子，转向设计接口。文章说，过去工具使用的头号规则，是给 Claude 例子，告诉它这个工具该怎么用。比如你有一个内部工具，就在提示词里写三四个调用示例。对于老模型，这很有效，因为它们需要通过例子模仿格式。但对最新模型，Anthropic 发现，给例子反而可能把模型限制在某个探索空间里。模型会过度模仿例子，以为只有这些用法是合理的，而忽略工具本身更丰富的能力。

新方向是，不要过度依赖示例，而要认真设计工具、脚本和文件的接口。也就是说，Claude 能看到哪些参数，这些参数表达力够不够，工具描述是否清楚，参数名是否自解释，状态枚举是否传达了使用方式。文章举了 Todo 工具的例子。只要把 status 设计成 pending、in_progress 和 completed 这样的枚举，Claude 就能理解任务有待处理、进行中、已完成几个状态。再加上一条说明，保持一个任务处于 in_progress，就能定义你希望的行为。

这个观点对做 agent 的团队特别重要。很多人会把模型调不好的原因归结为 prompt 不够长，其实可能是工具接口太糟糕。比如你给模型一个叫 run 的工具，参数是一个字符串 command，模型当然很难知道什么时候该用、怎么用、危险在哪里。你如果把工具拆成 read_file、search_code、run_tests、create_todo、update_todo，参数写得清楚，模型就容易得多。再进一步，如果 run_tests 有 target、timeout、allow_network 这些参数，模型能理解边界。好的工具接口，就像好的 API 设计，不需要用一堆文档解释，也能让调用者自然走向正确路径。

这里有个类比。你让一个新同事使用公司内部平台，如果平台按钮叫操作一、操作二、执行，旁边再给他一份二十页说明书，他还是容易误操作。反过来，如果按钮叫创建分支、运行单测、发起代码审查、回滚部署，页面还清楚显示危险操作需要确认，那说明书可以短很多。对 Claude 也是一样。与其在 system prompt 里塞很多工具使用例子，不如把工具本身设计得更语义化、更安全、更符合任务流程。

第三个变化，是从所有内容都放在前面，转向 progressive disclosure，也就是渐进式披露，或者说按需加载。早期 Claude Code 主要面向编码，所以系统提示词里包含了很多关于代码审查和验证的详细信息。这些信息不是每次都需要，但一旦需要就很关键。以前的做法是先全塞进去，保证模型随时能看到。但这样会占用上下文窗口，也会让模型在不相关任务中被干扰。

现在 Claude Code 已经更擅长在正确时间加载正确上下文。Anthropic 把验证和代码审查相关内容移动到了各自的 skills 里，Claude Code 可以选择性调用。文章还说，渐进式披露不只适用于 skills，也适用于 tools。有些工具是 deferred loading，也就是延迟加载。agent 必须先通过 ToolSearch 搜索到完整定义，才能使用这些工具。这样系统可以拥有更多工具，比如 Task 工具，但它们在不需要时不会占用上下文。

这其实是上下文工程里非常核心的一条。上下文窗口再大，也不是垃圾桶。你把所有东西都放进去，会产生两个问题。第一是成本和速度问题，token 越多越贵，响应越慢。第二是注意力问题，模型虽然能看见很多内容，但不代表每一条都能被同等重视。无关信息越多，冲突概率越高，模型越容易在噪声里迷路。

我们可以把它想成工程师的工作台。你修一个小 bug，不需要把公司所有架构文档、历史设计决策、所有事故复盘都摊在桌上。你需要的是当前文件、相关测试、附近调用链。如果修到数据库迁移，再打开迁移规范。如果要做安全敏感改动，再查看安全 checklist。这就是渐进式披露。对 agent 来说，CLAUDE.md 不应该变成一个中央百科全书，而应该像一个目录，告诉 Claude 去哪里找对应知识。

文章特别提醒，过去有个常见神话，认为 CLAUDE.md 和 Skill.md 应该成为所有已知实践的中心仓库，因为不写进去 Claude 就找不到。Anthropic 的新建议是，考虑构建一棵文件树，让不同文件在正确时间被加载。比如你的仓库根目录 CLAUDE.md 只写项目是什么、最容易踩的坑、有哪些可用技能。具体的验证流程放到 verification skill。前端设计规范放到 frontend skill。数据库迁移注意事项放到 migration skill。模型只有在需要时才加载相关内容。这比把所有规范平铺在一个巨大 markdown 里更健康。

第四个变化，是从重复自己，转向简单的工具描述。文章说，早期 Claude 模型有时需要重复指令，或者更容易听上下文窗口末尾的指令，而不是开头的指令。因此系统提示词里会在主提示词中提到工具，在工具描述里又重复一遍工具使用说明。现在他们发现，可以删掉这些重复例子，把工具使用说明放在工具描述里，而不是 system prompt 里反复强调。

这点听起来很小，但在真实系统里非常关键。重复是提示词腐化的开始。第一次重复，是为了保险。第二次重复，是因为某次模型没听。第三次重复，是另一个团队不知道前面已经写过，又加了一段。过几个月以后，同一个原则在不同地方有三个版本，措辞还不完全一样。模型看到后不知道哪个优先。人类维护者也不知道改哪里。

更好的做法，是让信息有唯一归属。工具怎么用，就写在工具描述里。产品角色是什么，就写在 system prompt 里。仓库特殊坑点，就写在 CLAUDE.md 里。团队某个工作流，就写在 skill 里。这样上下文结构清楚，也方便审计。如果有一天你发现模型对 run_tests 用法不对，你就去改 run_tests 的描述，而不是在 system prompt、CLAUDE.md 和 skill 里各加一句提醒。

第五个变化，是从把记忆放进 CLAUDE.md，转向自动记忆。文章说，过去他们鼓励用户把东西保存到 Claude 的 memory，甚至可以用井号快捷键自动写入 CLAUDE.md。现在 Claude 会自动保存与工作和用户相关的记忆。这里我们要注意，文章没有展开自动记忆的具体实现，也没有说所有信息都应该让模型自动记。所以我们不要过度解读。但方向很明确，CLAUDE.md 不再需要承担那么多记忆职责。它应该更像仓库级别的轻量指南，而不是长期记忆数据库。

对团队来说，这意味着你要区分几类信息。第一类是仓库事实，比如这个项目是做支付网关的，类型定义集中在一个文件里，测试要用某个命令跑。这适合写在 CLAUDE.md。第二类是个人偏好，比如我喜欢先看 diff 再改代码，我倾向于简洁回答，这适合 memory。第三类是临时任务上下文，比如这次要把某个 API 从旧版本迁移到新版本，这适合当前对话或计划引用。不要把所有东西都塞进同一个文件，否则几年后它会变成没人敢删的杂物间。

第六个变化，是从简单 spec，转向 rich references，也就是更丰富的参考材料。文章说，在 plan mode，也就是计划模式里，Claude Code 过去很依赖 markdown 计划文件。把计划保存成文件，方便 Claude 需要时引用。类似地，很多最佳实践建议把 specs，也就是规格说明，放在代码库里，让 Claude 在长项目中参考。这仍然有用，但 Anthropic 发现，Claude 越来越能处理复杂参考。你不一定只能给简单 markdown 文件，也可以给它 HTML artifacts。artifacts 是 Claude 的一个功能，可以创建更丰富的产物。你还可以给代码形式的参考。一个 spec 也可以是详细测试套件，或者另一个代码库里的函数，Claude 可以把它移植过来。

这点我觉得非常有现实意义。我们经常把需求写成自然语言，觉得写得越详细越好。但对模型来说，高保真的参考未必是文字说明。比如你要实现一个前端页面，一段 HTML mockup 通常比一张截图或者一段描述更好。因为 HTML 结构明确，样式层级清楚，模型能直接读懂。如果你要定义一个 API 行为，一组测试用例可能比一页需求文档更精确。测试会告诉模型，输入是什么，输出应该是什么，边界情况是什么。如果你要迁移某个算法，一个已有代码实现可能是最好的 spec，因为代码本身就是精确语言。

文章还提到 rubrics，也就是评分标准或评价量表，也是一种参考。rubrics 可以让 Claude 在某个领域尝试验证你的品味，比如什么算好的 API 设计。它可以使用动态工作流，启动 verifier agents，也就是验证智能体，用这些 rubrics 来检查结果。这说明 Anthropic 对 agent 的想象不只是单个模型一次性回答，而是让模型围绕参考材料、评价标准和验证流程组织工作。

这里要强调忠于原文的一点。文章没有给出 rubrics 的具体例子和实现细节，只是说它们是 references 的一种形式，可以帮助 Claude 验证特定领域的品味。所以我们在实践里可以理解为，如果你的团队对好代码、好 API、好设计有一些可表达的评判标准，不要只把它们当成口头经验，可以整理成 Claude 能引用的参考。比如一个 API rubric 可能会关注命名是否一致、错误返回是否可预测、分页方式是否符合已有接口、权限边界是否清晰。模型在生成和审查 API 时，就可以用这套标准自查。

说完这些变化，文章进入到怎么应用到自己的上下文。它把上下文拆成几个层次。首先是 system prompt。system prompt 强烈绑定产品上下文。它告诉 Claude 正在什么产品里运行，正在做什么。对于 Claude Code 用户来说，你通常不会修改这个系统提示词。但如果你在构建自己的 agent harness，也就是智能体运行框架，这里就应该花很多时间。

这句话很重要。system prompt 不是团队规范的垃圾桶，而是产品身份和任务边界的根。你的 agent 是代码助手、客服助手、数据分析助手，还是运维助手。它能不能执行命令，能不能发起外部请求，面对不确定性应该问用户还是自己探索。哪些行为属于危险操作，需要确认。它的角色和基本行为应该在 system prompt 里定义。但具体项目里的小习惯，不应该全塞进去。

然后是 CLAUDE.md。Anthropic 的建议是保持轻量，简短描述 repo 是做什么的，但把大部分 token 花在代码库里的 gotchas，也就是坑点上。比如你的代码组织方式很特殊，所有类型定义都放在一个巨大的单体文件里，别处不要放类型。这种信息模型单靠浏览文件系统可能不容易猜到，就值得写。相反，避免陈述显而易见的东西，也就是 Claude 通过看文件系统或代码库就能知道的事情。

这个建议非常实用。很多 CLAUDE.md 里会写，本项目使用 TypeScript，使用 React，测试位于 tests 目录，源代码位于 src 目录。可是这些信息模型看一眼 package 文件和目录结构就知道了。你把 token 花在这些地方，价值很低。真正值得写的是那些违反直觉、隐藏在团队习惯里的东西。比如，不要直接编辑生成文件，源头在 schema 目录。比如，前端组件看起来可以复用，但这个目录只给管理后台用。比如，某个旧模块名字叫 v2，其实它服务的是 v3 API。比如，测试命令有两个，快速单测和集成测试，不要默认跑最慢的一套。这些才是 AI 容易踩坑、人类新人也容易踩坑的地方。

文章还建议在 CLAUDE.md 里大量使用渐进式披露。如果你有几条独特的验证指令，不要把完整流程塞在 CLAUDE.md，可以创建一个 verification skill，然后在 CLAUDE.md 中引用它。也就是说，根文件像路标，不像百科。它告诉 Claude，遇到验证任务时去看验证技能，遇到发布流程时去看发布技能，遇到设计系统时去看设计技能。

接下来是 Skills。文章把 skills 定义成轻量指南，用来让 Claude 在需要时找到信息。不要把它们做得过度约束，除非是在非常重要的领域。对于很长的 skills，要尽量使用渐进式披露，把它拆成很多文件。最好的 skills，是编码你、你的团队或你的产品特有的观点、知识和最佳实践。

这里我想多讲几句。Skill 不是一本通用教科书。你不需要写，如何写好单元测试，如何设计 REST API，如何进行代码审查。这些通用知识模型本来就知道。你要写的是，咱们团队如何写单元测试，咱们这个服务为什么不用某种常见模式，咱们 API 错误码历史上有哪些兼容要求，咱们代码审查最看重什么。换句话说，skill 的价值在于本地知识和团队品味，而不是百科知识。

比如你在一个金融系统团队，可能有一个 payment verification skill，里面不是泛泛地说支付要安全，而是写清楚，本仓库里金额永远用整数分表示，禁止浮点；时区统一使用 UTC，但对账导出要按业务地区转换；退款状态有历史兼容，不能只看一个字段；任何涉及幂等键的改动必须增加重复请求测试。这样的 skill 对 Claude 非常有帮助，因为它把隐性经验显性化了。

再往下是 References，也就是参考。文章说，你可以通过提及文件的方式把文件作为 references 包含进来。references 允许 Claude 引用关于当前计划的深入信息。它可以是 spec 文件、mockup，甚至是整个代码库。一般来说，你应该偏好代码形式的文件，因为代码用一种 Claude 很熟悉的语言提供了清晰、高保真的指令。文章举例说，一个设计的 HTML mockup，通常会比设计描述或截图产生更好的结果。

这背后的原则是，高保真输入优于低保真描述。你让 Claude 实现一个按钮组件，如果只说要现代、简洁、有科技感，那它只能猜。如果给它 Figma 截图，它能看个大概，但很多结构细节还是要推断。如果给它 HTML 和 CSS mockup，它就能直接映射到实现。你让它修 bug，如果只说用户登录偶尔失败，它要猜很多。如果给它失败测试、日志片段和相关调用链，它就能更快定位。上下文工程不是写更多自然语言，而是给模型更接近真实问题形态的证据。

最后，文章给出一个总建议，try simplifying，试着简化。Anthropic 说，在 system prompt、skills 和 CLAUDE.md 文件中，你可能需要像他们一样做简化。他们推出了一个新命令叫 claude doctor，可以帮助自动完成这件事。在 Claude Code 里可以使用 doctor 命令来调整 skills 和 CLAUDE.md 文件的大小。文章还提到，如果想了解更高级模型的 prompting，可以看 Fable field guide。这里我们不展开，因为原文只是顺带提到。

现在我们把这些内容落到实际工作里。假设你是一个后端工程师，团队准备让 Claude Code 深度参与日常开发。你第一步不应该是开一个大文档，把公司所有规范粘进去。更好的做法是先盘点现有上下文。你的 system prompt 是否承载了太多项目细节。CLAUDE.md 是否超过几千行，里面有没有大量显而易见的信息。skills 是否像法律条文一样过度约束。工具描述是否重复、冲突、过期。references 是否还停留在自然语言需求，而不是测试、mockup、代码样例。

然后你可以做一次瘦身。对每条规则问三个问题。它现在还必要吗。它是否永远成立。它应该放在这里吗。比如，不要写注释，可能应该删掉，改成匹配周围代码注释密度。比如，提交前必须运行所有测试，这可能太重，应该改成根据改动范围选择相关测试，并在不确定时说明未验证部分。比如，禁止修改某目录，如果那个目录是生成目录，这可能是硬约束，应该保留，但最好说明源文件在哪里。比如，前端样式必须使用某设计系统，这不是一句禁止就够了，最好提供对应组件参考和示例页面。

再看工具。很多团队给 agent 的工具接口，其实是从人类脚本直接搬过来的。比如一个内部脚本有十几个 flag，命名历史包袱很重，错误输出也不清楚。你把它暴露给 Claude，再写三页 prompt 教它怎么用，效果未必好。更好的方式是给 agent 包一层更清晰的工具接口。让参数更语义化，让危险操作显式，让返回结果结构化。比如 search_code 返回文件路径、行号、匹配上下文，而不是一整段 grep 输出。run_tests 返回通过数、失败数、失败测试名、关键错误，而不是一屏日志。create_pull_request 明确需要 title、summary、test_plan，而不是让模型拼命令行。这样你会发现，prompt 可以短很多，稳定性却更高。

再看渐进式披露。你可以把团队知识按使用场景拆开。根 CLAUDE.md 只写项目目的、快速启动、关键坑点和技能索引。verification skill 写怎么验证改动，包括不同语言、不同模块、不同测试层级。database skill 写迁移和数据兼容。frontend skill 写设计系统和可访问性要求。release skill 写发版流程。security skill 写敏感操作和禁止事项。每个 skill 自己也不要写成巨石文档，而是继续拆文件。Claude 需要时加载，平时不占上下文。

这里有个常见坑要避开。简化不等于什么都不写。文章不是说新模型已经强到不需要上下文，而是说上下文要更像环境和参考，而不是枷锁。该写的坑点一定要写，该做的安全边界一定要做，该提供的工具描述一定要清楚。如果你的 agent 能删除生产数据，那就不能只相信模型判断力，必须在工具层做权限和确认。如果你的代码库有非常特殊的兼容规则，也不能指望模型自己猜出来。所谓让 Claude 使用判断力，是在提供清晰边界和高质量参考之后，让它在局部选择上判断，而不是把风险控制全部交给模型。

还有一个坑，是把旧提示词直接迁移到新模型。很多团队升级模型时，只改模型名，不改上下文。这可能会错过新模型的能力红利。老提示词里的重复、强约束和例子，可能会压制新模型。升级到 Claude 五代这类模型后，你应该安排一次 context review，就像升级数据库或框架后做配置审计一样。看看哪些 workaround 可以删除，哪些示例可以改成接口描述，哪些长文档可以拆成按需加载，哪些自然语言 spec 可以替换成测试或代码参考。

如果你是做 AI platform 的工程师，我个人认为这篇文章还有一个更大的启发。未来 agent 系统的竞争，不只是模型谁更强，也是谁的上下文架构更干净。一个好的 agent harness，会有清晰的上下文分层。系统提示词定义产品身份和安全边界。工具接口承载可操作能力。skills 承载团队知识和工作流。memory 承载长期个性化信息。references 承载当前任务的高保真材料。验证器和 rubrics 承载质量标准。每一层都有自己的职责，不互相污染。这就像软件架构里的分层设计，越到系统变复杂时越重要。

对个人开发者来说，也可以从很小的动作开始。今天下班前，你可以打开自己项目里的 CLAUDE.md，删掉那些模型看目录就能知道的废话。把绝对化的规则改成基于周围代码和团队惯例的原则。把最常用的验证步骤拆成一个单独 skill。下次让 Claude 做前端页面时，试着给 HTML mockup，而不是只给一句描述。让 Claude 修 bug 时，尽量给失败测试和日志，而不是只说有问题。你会慢慢感受到，好的上下文不是更多文字，而是更少噪声、更高信号。

我们最后收个尾。Anthropic 这篇文章的核心信息很清楚，Claude 五代模型时代，上下文工程要从堆规则、堆例子、堆文档，转向简化、接口设计、按需加载和高保真参考。他们自己最有力的证据，就是为 Claude Code 删除超过八成系统提示词，却没有在编码评测中看到可测量损失。

我个人认为，这篇文章其实是在提醒我们，AI 工程正在从 prompt 小技巧，走向真正的软件架构问题。你不是在哄模型听话，而是在设计一个信息环境，让一个越来越有判断力的模型能高效工作。对于软件工程师来说，这正好是我们熟悉的领域。少一点神秘主义，多一点接口设计、模块边界和持续重构，这可能就是新一代 context engineering 的基本功。
