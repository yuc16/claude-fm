今天我们要聊的文章，标题是 How Rakuten builds agents overnight with Claude Fable five，Claude by Anthropic，中文可以翻译成，乐天如何用 Claude Fable 五在一夜之间构建智能体。这篇文章发表于二〇二六年七月二十日，也就是距离今天二〇二六年七月二十六日只有六天，所以它非常新，基本可以看作是 Anthropic 在当前这一轮前沿模型竞争里，拿出来展示企业级 agent 落地能力的一篇案例文章。

为什么这篇值得你在通勤路上听完？因为它讲的不是一个很泛泛的，某某公司用了 AI 提效多少的故事。它真正有价值的地方在于，Rakuten，也就是我们中文里常说的日本乐天，正在把 Claude 放进软件开发、产品、销售、市场、财务这些不同业务职能里，而且文章重点强调了一个变化，过去你把一个 agent，也就是智能体，交给它一个长任务，中间很可能要不断看着它，提醒它，纠正它。但 Claude Fable 五让 Rakuten 的 AI 负责人感到不一样的地方，是它可以在更长时间里自己检查自己，自己发现错误方向，然后在负责人睡觉的时候把任务继续往前推进。

先把主角交代一下。文章里的受访者叫 Yusuke Kaji，他是 Rakuten 的 AI for Business 总经理。他对自己工作的描述很有意思，说他的任务是找到具有变革性的创新种子，然后把这些种子在公司里规模化。这里的“种子”不是一个漂亮 demo，而是能够真的进入业务流程，进入生产环境，影响很多人的工作方式的东西。Claude 就是其中一颗种子。

从二〇二五年三月开始，Rakuten 就开始使用 Claude。文章里提到三个方向。一个是用 Claude Code 加速软件开发。Claude Code 可以理解成 Anthropic 面向开发者的编程智能工具，不只是补全几行代码，而是能理解项目上下文，修改文件，协助完成工程任务。第二个方向，是在不同业务职能里搭建 agent。第三个方向，是用 Claude 为数百万客户提供 AI 功能。也就是说，这不是一个单点试用，而是从内部工程效率，到公司业务流程，再到面向终端用户的产品能力，比较完整地铺开。

Kaji 说，Rakuten 选择和 Anthropic 合作，是因为看中了 Anthropic 的企业级关注点、领导力和产品品味。这里的产品品味这个词，后面还会反复出现。它不是一个很硬的 benchmark 分数，而是说模型做事情的时候，是否能理解什么叫“像我们团队会做出的判断”。比如一封销售邮件该不该更克制一点，一个产品方案该不该多考虑合规风险，一段代码的抽象层次是否过度设计，这些事情没有标准答案，但有团队偏好，有组织文化，有长期积累出来的判断方式。Rakuten 很看重这一点。

文章一开始还提到，Kaji 见证了 Anthropic 近十来次模型发布。在这个过程中，他能交给 agent 的工作范围不断扩大。最早，是用 Claude Code 帮助发布生产软件。后来，是为公司不同团队搭建定制的 Claude Managed Agents，也就是 Claude 托管智能体。他把测试新模型比喻成开始一场新的任务，或者说新的冒险。他还用了一个很有意思的说法，说好的领导会给团队成员准备有挑战性的目标，而他们也会为新的 Claude 准备有挑战性的任务。也许 Claude 也在推动他们自己伸展能力边界。

这个说法其实很能说明当下企业使用前沿模型的状态。我们过去测试模型，经常是问它一道题，跑一个 benchmark，看看它能不能过。现在更像是把它放进一个真实组织的真实任务里，看看它能不能扛住复杂上下文、工具调用、多人协作、长时间运行和模糊判断。对于软件工程师来说，这个差别非常大。写一个 demo agent，半小时跑通一个流程，不难。难的是让它在公司真实系统里跑几个小时甚至一整天，中间不跑偏，不破坏已有流程，不浪费太多成本，最后交出来的东西还真的能用。

Rakuten 自己把这场改造叫 AI-nization，可以翻译成 AI 化。文章里说，这是他们公司范围内的努力，要把 AI 注入到为客户、业务伙伴和员工所做的一切事情里。注意，这个表达有点激进，不是“我们有一些 AI 项目”，而是“公司要围绕 AI 重塑自己”。当 Claude Managed Agents 到来时，Rakuten 在一周之内，就把 agent 部署到了产品、销售、市场和财务等团队里，并且接入了 Slack、Microsoft Teams，以及公司自己的任务系统。

这段信息很关键。因为很多人谈 agent，脑子里想的是一个独立聊天窗口，像一个更聪明的对话机器人。但企业里的 agent 真正要有价值，必须进入现有工作流。员工不会为了 AI 另开一套宇宙。他们每天就在 Slack 里沟通，在 Teams 里开会，在 Jira 或内部任务系统里接需求、改状态、追进度。agent 如果不能接入这些系统，它就像一个很聪明但坐在门外的人，只能听你转述。接入之后，它才开始像一个系统的一部分，能读上下文，能参与任务流转，能在合适的地方推动事情。

Kaji 说，以前构建 agent 的约束是谁会写代码。也就是说，只有懂技术的人才能把一个业务流程变成自动化 agent。现在约束变了，变成谁理解业务问题。这个变化对组织很大。你可以把它想象成公司里有很多隐藏人才，可能是销售运营、财务分析、市场项目经理，过去他们有很强的业务直觉，但没有能力把想法变成软件。现在，如果 agent 能够承载上下文和品味，这些人就能把自己的业务理解直接放大。Kaji 的说法是，让隐藏人才释放潜力，并且把潜力放大一百倍。

这里我个人认为，文章有一个很重要但没有展开太多的点，就是 AI 正在改变“谁能创造软件化流程”。过去软件工程团队是组织里把想法转成系统的主要入口。业务团队提出需求，产品经理翻译，工程师实现，排期上线。这个链条最大的成本不是写代码本身，而是沟通、等待、理解偏差和优先级竞争。Kaji 说现代公司被设计成尽量降低沟通成本，而像 Claude Code 这样的 agent，可以在我们和它一起工作时，进一步降低新创新的成本，让一个想法更快从脑子里变成生产系统。

不过文章马上提醒我们，agent 跑得越快，新的瓶颈就越明显。Rakuten 的 agent 在各个领域关闭问题的速度大约快了十倍。这里的 close issues 可以理解为处理任务、解决问题、关闭工单或事项。但与此同时，组织接下来的任务数量也在不断增加。你加更多 agent，并不会自动增加人类判断力。agent 越快，整个组织的进展就越依赖某个人能不能完成最后闭环，能不能判断这个结果是否接受，能不能决定下一步。

这其实非常真实。我们在工程团队里也会遇到类似问题。以前瓶颈是没人写代码，现在 AI 帮你把代码写出来，瓶颈可能变成没人 review。以前瓶颈是没人整理需求，现在 AI 帮你整理了十份方案，瓶颈变成没人拍板。以前瓶颈是没人做数据分析，现在 AI 一晚上跑出二十个分析角度，瓶颈变成负责人不知道哪个角度值得变成行动。文章里说得很直接，增加 agent 不等于增加 judgment，也就是判断力。这句话我建议所有想在公司大规模部署 agent 的团队都记住。

接下来文章进入最核心的部分，为什么 Claude Fable 五让 Rakuten 觉得不一样。对大多数构建者来说，长时间运行 agent 最难的不是让它调用工具，也不是让它读几个文档。难点是如何在最少监督下，让它有足够高的成功概率。你可以把工具接好，把上下文喂给它，把权限配置好，但 Kaji 的经验是，总会有一个上限，超过某个时长之后，agent 就需要人类介入验证它有没有跑偏。

在 Claude Fable 五之前，把一个 agent 放出去做一个多小时任务，而且没有人盯着，是一种赌博。Kaji 的说法很直白，如果 agent 第一步选对了路，后面一切都好。但如果它第一步方向错了，它可能会花大量时间修正路径，甚至根本到不了终点。对于一个计划运行五小时或者一整天的任务来说，早期一个错误假设，就可能烧掉整个运行过程。唯一能及时发现的办法，是人类中途检查。

这听起来像什么？像我们写一个长脚本跑批任务。如果一开始配置文件路径错了，或者数据分区选错了，程序可能很认真地跑几个小时，最后产出一堆没用结果。传统程序至少会有类型检查、单元测试、日志告警。但 agent 的问题更复杂，因为它的“错误路径”不一定是报错。它可能看起来每一步都合理，只是最初理解错了目标。比如你让它“分析本季度日本市场增长放缓的原因”，它一开始把范围理解成全球市场，后面所有搜索、汇总、报告都围绕全球市场展开。五小时后你拿到一份精致但不对题的报告。

文章把这种失败模式总结为缺少 self-verification，也就是自我验证。任何模型都可能第一步走错。问题在于，早期模型不会在执行过程中持续检查自己的工作，所以一开始的偏航没有被发现。偏差会在长任务里不断累积，几个小时后产出一个次优甚至无用的结果。这个观察很重要，因为它告诉我们，长时间 agent 的关键能力不是单步聪明，而是过程中能不能不断问自己，我现在做的事情还符合原始目标吗？我的假设还成立吗？任务状态是不是已经变化了？

根据 Kaji 的说法，Claude Fable 五改变了 days-long agentic runs，也就是跨天级智能体运行的计算方式，因为它会在执行过程中更频繁地检查自己的工作，比之前任何模型都频繁。他说，他们测试 Fable，很喜欢它的自我反思和自我验证能力。相比以前的模型，它会在凌晨两点或三点，在他指出之前，就理解自己的错误，这样他就可以睡觉。

这句话当然有一点案例文章的表达色彩，但背后的含义非常明确。一个企业负责人愿不愿意把 agent 放出去跑一夜，取决于他第二天早上面对结果时，会不会大概率被迫重来。如果每次早上醒来都要发现 agent 半夜跑偏了，那它不是助手，是制造返工的机器。Claude Fable 五让 Kaji 感到变化的地方，是它中途会自己发现问题，这降低了长任务无人值守的心理成本和管理成本。

文章总结了 Claude Fable 五和前代模型相比的三个行为差异。我们不用像读白皮书一样逐条念，但可以把它们拆开讲透。第一个，是它会重新检查自己的假设。当任务状态在中途变化时，Fable 五会注意到，并在基于错误假设行动之前纠正自己，而不是一路走到黑，几个小时后才发现走错。这个能力对企业任务非常关键，因为企业环境不是静态题目。任务优先级会变，数据会更新，某个依赖系统会失败，某个同事会在 Slack 里补充新约束。如果 agent 不能处理变化，它只能做封闭环境里的自动化。

举个工程场景。你让 agent 修一个线上 bug，它一开始判断问题来自前端缓存，于是准备修改前端逻辑。但跑测试和查日志的过程中，它发现后端某个接口返回字段在灰度环境里不一致。一个弱一点的 agent 可能会继续沿着前端缓存方向修补，因为最早计划就是这样。一个更强的 agent 应该停下来问，最初假设还成立吗？如果根因其实在接口契约，那我是不是应该回到问题本身，重新选择路径？文章说 Fable 五在这类事情上有更强表现。

第二个行为，是它会在每一步回到 first principles，也就是第一性原理。这里不要把第一性原理理解得太玄，它在实际工作里就是回到原始意图。用户到底想要什么？这个任务的成功标准是什么？现在这个动作是否服务于目标？Kaji 说，以前当一次运行开始走错方向时，需要他自己进行这种纠偏。现在 Fable 五会在没有被明确要求的情况下，重新对照原始意图。

对于软件工程师来说，这像是一个高级同事在做需求时，不只是机械执行 ticket，而是不断确认“我们真正要解决的问题是什么”。比如需求写的是“把报表导出速度优化百分之五十”，一个机械执行者可能直接去优化 SQL。一个懂第一性原理的人会问，用户抱怨的是等待时间，还是导出后人工处理成本？如果大多数用户只需要最近七天数据，默认全量导出才是问题；如果瓶颈在权限校验，优化 SQL 没用。agent 能回到原始意图，意味着它更像一个能承担结果的人，而不是只执行步骤的脚本。

第三个行为，是它匹配团队的 taste，也就是品味。Kaji 为这个现象起了一个词，叫 taste alignment，中文可以说品味对齐。他说，即使只给很少指导，Fable 五在模糊判断上的选择也和他们团队更一致。并且他认为，Fable 的品味对齐比 Anthropic 以前的模型，以及他们用过的其他模型都更顺滑。

品味对齐这个词很值得琢磨。我们平时讲模型对齐，常常想到安全对齐、价值观对齐、遵循指令。但企业里还有一种更细的对齐，叫工作品味。比如你的团队偏好简单可维护的方案，而不是炫技。你的产品文案偏好克制可信，而不是夸张营销。你的财务报告偏好保守假设，而不是乐观预测。你的代码 review 偏好小步提交，而不是一次大改。很多时候你无法把这些偏好完全写成规则，但老员工知道，新人需要时间学习。如果 agent 能更快学会这种 taste，它的输出就更少需要重写。

这三个能力加在一起，改变了 Kaji 能委派给 agent 的工作单位。文章里有一句很关键的话，Fable 之前，他们必须把工作拆成定义明确的小块，让 agent 去执行。现在，他可以交给它一个完整任务，并且同时跑好几个。Claude Fable 五改变的是中间过程。它会在每一步反思，抓住早期错误假设，并且自己回到第一性原理，重新导航到正确结果，不需要人在旁边一直掌舵。

这里的变化不只是“模型更聪明”。它改变了管理 agent 的方式。过去你像管理一个实习生，必须把任务拆得很细，“先做甲，再做乙，做完给我看，不要自己决定”。现在更像管理一个可信的中级成员，你可以说“请把这个问题解决到可以进入评审的程度”，中间允许它自己选择路线。当然，文章没有说它已经等同于人类员工，也没有说可以完全放弃审查。它说的是，因为模型能在中途自我纠正，sign-off，也就是最后签核，第一次变得更可行。Kaji 委派的单位，从任务本身转向了 decision，也就是决策。

这句话有一点抽象，我们拆一下。所谓从任务转向决策，不是说人类不做决策，而是说 agent 可以把很多执行和中途路径选择包进去，最后把需要人类判断的关键点呈现出来。以前你可能要审批每个小步骤，现在你更关注几个真正需要人类负责的判断，比如要不要采用这个方案，要不要发给客户，要不要改变业务规则。这样人类注意力就从过程控制，转向结果和关键决策。

文章还提到，Rakuten 的 agent 带有 memory，也就是记忆。Kaji 说，他们带记忆的 agent 会记得过去会话中哪里出了错，并且避免重复那些错误。这一点和前面的自我验证、品味对齐是连在一起的。如果一个 agent 每次运行都像失忆一样，它就很难形成组织经验。你今天纠正它一次，它明天又犯同样错误，这会让人很沮丧。记忆让 agent 有机会积累“这个团队不喜欢什么”“这个系统有哪些坑”“上次这个假设为什么错了”。

不过我个人认为，企业在引入记忆时也要非常谨慎。文章没有展开治理细节，所以这里是我的评论，不是原文结论。记忆很有价值，但也会带来权限、隐私、过期信息和错误经验固化的问题。一个 agent 记住了过去的错误，当然很好；但如果它记住了不该跨团队传播的信息，或者把某次特殊情况当成永久规则，就会产生新风险。所以实践里要考虑记忆边界、可审计性、可删除性，以及哪些内容应该成为团队知识，哪些只适合会话临时上下文。

文章说，结果是任务的绝对数量持续上升，但真正需要人类处理的任务保持在一个可聚焦的水平。不必在中途跳进去掌舵，是 Kaji 认为最大的生产力收益。它让团队把时间花在只有人应该做的决策上，也让一个 AI-native，也就是 AI 原生的组织继续加速，而不是卡在人类不断纠偏的瓶颈上。

说到这里，我们也要看成本。文章有一节叫平衡成本和效率。Kaji 很直接地说，前沿能力有前沿价格，成本决定了他能多广泛地部署。作为大企业，他们要平衡智能和成本。他们团队会同时衡量 task completion ratio，也就是任务完成率，和 cost per task，也就是单任务成本。然后把那些额外能力会改变结果的工作交给 Fable 五，把剩下的工作交给更小的模型。

这对工程团队很实用。很多公司一上来就纠结，要不要所有任务都用最强模型。其实 Rakuten 的做法更像是一个模型路由策略。不是“最强模型永远最好”，而是“某个任务是否值得为更强能力付费”。如果只是整理会议纪要、改格式、做简单分类，小模型可能足够。如果是跨多个系统、长时间运行、需要自我验证、需要模糊判断的任务，Fable 五这种更强模型就可能通过减少错误路径、减少返工、减少人工看护，把总成本降下来。

Kaji 认为，Fable 五在成本账上有两个优势。一个是它用更少 token 和更少错误路径完成更多事情。token 可以理解成模型处理文本的基本计费单位，中文里常翻译成词元。更少 token 不只是少说废话，也意味着规划和执行更有效率。另一个优势，是它需要更少 hand-holding，也就是更少手把手看护。一个模型单次调用贵，但如果它少跑弯路，少需要人半夜起来检查，少造成返工，总账可能反而更划算。

我个人认为，这里给我们一个很好的评估框架。不要只看每百万 token 多少钱，也不要只看一次回答多快。对于 agent，尤其是长时间 agent，你应该看端到端成本。包括模型调用成本、工具调用成本、人类监督成本、返工成本、失败带来的机会成本，以及最重要的，结果能不能进入真实业务流程。如果一个便宜模型跑了五小时，最后因为早期假设错了全部重来，那它并不便宜。如果一个贵模型在中途发现问题并纠正，最后让负责人早上只需要做最终判断，它可能更便宜。

文章最后谈到下一步。Kaji 现在测试的前沿，不是单个 agent 的速度，而是让 agent 协调人。Claude Code 已经加速了他和同事的工作，但任何组织最难的部分，是人和人之间的 alignment，也就是对齐。一个人的上下文和品味，怎样传递给另一个人？很多 nuance，也就是细微差别，会在团队成员之间丢失。他正在探索一种更像经理的 agent，能够协调或组织，保留那些通常在沟通中丢掉的细节。

这个方向非常有意思，也可能比“写代码更快”影响更大。因为组织里很多损耗来自人和人之间的信息不对称。产品说了一个需求，工程理解成另一个版本。销售听到客户反馈，传到研发时变成一句模糊描述。管理者脑子里有优先级，但没有及时同步给执行团队。一个能够持有上下文、理解团队品味、协调多人工作的 agent，可能不只是生产工具，而是组织操作系统的一部分。

但 Kaji 也明确说，他们不把 AI agent 看作未来同事或竞争者。他们认为 agent 是围绕在我们身边的系统。这句话和很多“AI 员工”叙事不太一样。它强调 agent 不是简单替代某个工位的人，而是嵌入组织流程、放大人的能力、降低创新成本的系统层能力。我个人更认同这个表述。因为如果你把 agent 当成一个虚拟员工，你会自然去问它能不能完全替代某个岗位。但如果你把它当成组织周围的新系统，你会问，哪些流程可以重新设计，哪些判断应该留给人，哪些重复沟通可以被吸收，哪些上下文可以被持续保留。

文章里还有一句 Anthropic 自己经常提的建议，Kaji 也拿来要求 Anthropic，那就是应该为三到六个月后会出现的模型构建，而不是只为眼前这个模型构建。这个建议对开发者尤其重要。因为如果你只根据当前模型的能力设计系统，你可能会过度补丁化，写很多复杂 prompt、很多硬编码限制、很多 workaround。等模型能力提升后，这些补丁反而变成负担。反过来，如果你相信模型很快会更会规划、更会自检、更会调用工具，你的系统架构就应该给它留出空间，比如更清晰的工具接口，更好的权限边界，更可观察的运行日志，更标准的任务评价机制。

Kaji 最后说，他认为社会还没有找到 Claude Fable 五的 model-task fit，也就是模型和任务之间的最佳匹配。但它已经很突出，像是跨过了一条线，走进了我们的世界。这句话听起来有点文学化，但可以理解成，Fable 五的能力已经不只是实验室里多答对几道题，而是开始改变企业可以放心委派给 agent 的任务边界。

那对正在听节目的你，实际工作里可以怎么用这篇文章？如果你是软件工程师，最直接的启发是，不要再只把 AI 当成代码补全器。你可以开始设计长任务 agent 的工作流。比如让它处理一个中等复杂度的 bug，从阅读 issue、定位相关代码、提出假设、跑测试、修改实现、生成说明，到准备 review 材料。但你要特别关注中间的自检点。你可以要求它在关键步骤主动复核原始目标，记录当前假设，说明证据来自哪里，并在发现矛盾时回退。这不是为了形式好看，而是为了避免五小时后产出一个精致的错误结果。

如果你是技术负责人，可以从小范围开始做模型路由。不要把所有任务都扔给最强模型，也不要因为成本就只用小模型。你可以把任务按风险和复杂度分层。低风险、短上下文、标准答案明确的任务，用便宜模型。高风险、长上下文、需要跨工具、需要自我验证、需要团队品味的任务，用更强模型。然后像 Rakuten 一样，不只看调用成本，而是看任务完成率和单任务成本。这个单任务成本最好包含人工 review 和返工时间，否则你很容易被表面便宜误导。

如果你在业务团队，文章给你的启发是，你可能不必等工程团队排期，才能把一个业务想法变成可运行的流程。当然这不是说绕过工程治理，而是说业务专家的价值会更直接地被放大。你最需要培养的，可能不是写代码能力，而是把业务问题表达清楚的能力。目标是什么，边界是什么，哪些判断必须保守，哪些地方可以尝试，什么结果算成功，什么结果必须升级给人。这些表达越清楚，agent 越能成为你的杠杆。

如果你在做平台或内部工具，我建议重点关注四件事。第一是上下文接入，agent 必须能在权限允许范围内看到任务系统、文档、代码库、沟通记录。第二是工具边界，能读什么、能改什么、能发什么，必须清晰可控。第三是可观察性，长时间运行过程中，每个关键假设、每次工具调用、每次自我纠偏，都要能被追踪。第四是人工闭环，不要假设 agent 能消灭审批，恰恰相反，你要把人类判断放在最关键的位置，让人从盯过程转向做决策。

也要避几个坑。第一个坑，是把 agent 当成魔法，直接给一个模糊目标就让它跑一夜。文章里强调的是 Fable 五更会自我验证，不是说目标可以随便写。第二个坑，是只追求自动化比例。自动化越高，如果判断闭环跟不上，组织可能只是更快地产生待审核事项。第三个坑，是忽视品味对齐。很多团队以为只要答案正确就行，但真实工作里，输出风格、风险偏好、抽象层次、沟通方式都会影响采纳率。第四个坑，是忘记成本。前沿模型要用在能改变结果的地方，而不是用来做所有简单杂活。

还有一个更深的启发，给所有 AI 从业者。过去我们做 agent，常常把重点放在规划能力和工具调用上。文章提醒我们，下一阶段的关键可能是 self-verification，自我验证，taste alignment，品味对齐，以及 memory，记忆。规划让 agent 知道下一步做什么，自我验证让它知道自己有没有走偏，品味对齐让它知道怎样的结果才像这个团队会接受的结果，记忆让它不要反复犯同样错误。这四件事合起来，才更接近一个能长期嵌入组织的系统。

当然，我们也要保持一点冷静。这篇文章是 Anthropic 官方博客里的客户案例，天然会强调 Claude Fable 五的亮点，不会展开失败率、具体评测方法、部署治理细节，也没有给出完整的量化实验数据。比如十倍更快关闭问题，是跨领域总体描述，具体任务类型、基线和统计口径文章没有细说。所以我们不能把它当成严格论文来读。但作为一篇企业落地案例，它提供的信号很清楚，企业开始把关注点从“模型单次回答好不好”转向“agent 能不能长时间、自我纠偏、低看护地完成真实工作”。

总结一下，Rakuten 的案例告诉我们，Claude Fable 五最重要的变化，不只是更快，也不只是更强，而是让长时间无人值守的 agent 更可信。它会重新检查假设，回到原始意图，贴近团队品味，并且通过记忆避免重复错误。对企业来说，这会把瓶颈从写代码、做执行，进一步推向判断、签核和组织协调。

我个人认为，这篇文章真正值得记住的一句话是，增加 agent 不等于增加判断力。未来几个月，很多团队会发现 AI 能把任务生产得非常快，但真正拉开差距的，是谁能设计好人和 agent 的协作边界，谁能把人类判断放到最关键的位置，谁能为三到六个月后的模型提前搭好系统。今天这期 Claude FM，就聊到这里。
