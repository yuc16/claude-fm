## Script

The AI-Native SDLC playbook，中文可以翻译成，AI 原生软件开发生命周期实战手册。这篇文章发表于二〇二六年八月二十一日。今天是二〇二六年八月二十三日，所以这是一篇非常新的文章，几乎就是 Anthropic 在当前这个阶段，对 Claude Code 以及 agentic AI，也就是能自主执行任务的智能体式 AI，如何进入企业研发流程，给出的一份操作指南。

这期为什么值得听？因为过去一年，很多工程团队已经体验到一个明显变化，写代码本身越来越不像过去那样是最慢、最贵、最不确定的环节了。一个工程师带着 Claude Code，可以在一天里推进过去需要几天甚至一两周的代码改动。但问题也随之出现，代码快了，需求还慢，评审还慢，安全审批还慢，发布流程还慢。结果就是，我们给发动机换了涡轮增压，却还在用老式马车的刹车和转向系统。Anthropic 这篇文章要解决的，正是这个错配。

先说背景。SDLC 是 software development lifecycle，软件开发生命周期。传统上，它大概包括规划、设计、构建、测试、部署和维护这几个阶段。产品经理写需求，架构师做设计，工程师写代码，测试或者质量团队验证，发布团队上线，运维团队监控。每个阶段之间靠文档、工单、审批和交接来流转。这套流程的好处是责任清楚，控制点明确，尤其适合大公司、金融、保险、医疗这些强监管环境。问题在于，它诞生时默认了一件事，写代码是最耗时的事情。

所以你会看到很多仪式，比如产品需求文档，估时会议，架构评审，安全评审，发布委员会。它们原本的目的，是在漫长的开发周期里强制大家对齐。因为一个需求一旦进入开发，可能要持续几周、几个月甚至几个季度，中间改方向代价很高。可是到了 Claude Code 这类工具成熟之后，构建阶段突然被压缩了。如果一个 agent 可以在短时间内生成大段改动，还能跑测试、修 lint、补文档，那么老流程里那些等待审批、排队 review、人工逐行检查的环节，就会变成新的瓶颈。

原文说，当代码不再是瓶颈，三件事会变成现实。第一，瓶颈会移动到构建阶段的左边和右边，也就是规划、评审、测试和部署。这些环节还在用人的速度运行。第二，控制措施开始和现实脱节。以前逐行 review 是合理的，因为每一行都是人写出来的，变更量也比较有限。现在如果大部分 diff，也就是代码差异，都是 agent 生成的，你仍然要求人逐行看完，那就很难跟上。第三，治理成本上升。因为异常情况仍然要走会议、委员会、周会或者月会。AI 让产出频率上来了，但组织的治理节奏没有变。

文章举了一个安全评审的例子。安全团队的人数通常是按照人类工程师的产出规模配置的。如果 agent 把代码产出放大了几倍，安全队列就会堆积。要么代码排队等审，吞掉 AI 带来的效率收益；要么代码在审查不足的情况下上线，这对受监管企业来说又不可接受。所以 Anthropic 的观点很明确，既然实现阶段已经被 AI 改造了，那么整个软件开发生命周期也需要被同等程度地改造。

这篇文章的核心概念叫 AI 原生 SDLC。它不是说把传统流程一脚踢开，也不是说让 AI 自己决定一切。它强调的是，把旧流程里的控制目标保留下来，但是用新的执行方式来实现。传统 SDLC 像一条直线，需求传给设计，设计传给开发，开发传给测试，测试传给发布。AI 原生 SDLC 更像一个循环，每个阶段都有 AI 嵌入，每个阶段结束时都写下一个明确产物，提交到版本控制里，然后下一个阶段读取这个产物继续工作。

这就是原文反复强调的一个词，committed artifact，可以理解成，已经提交到版本控制的阶段产物。早期阶段主要是 markdown 文件，也就是文本文件，因为产品负责人和 agent 都能读，也都能对它采取行动。比如 intent 点 md，记录意图；spec 点 md，记录需求和设计规格；plan 点 md，记录实施计划。到了构建之后，产物就变成代码、测试、PR、评审发现和事故记录。整条提交链本身就是审计轨迹。谁提出了什么，agent 生成了什么，谁批准了什么，都在 git 历史里。

这个思路很关键。过去很多企业的流程控制依赖人记得做什么，依赖工单状态，依赖会议纪要，依赖某个人在群里说一句可以。AI 原生流程要做的是，把这些中间态变成机器和人都能读取的文件，并且进入版本控制。这样 agent 不需要每次都从零开始问你上下文，人也不需要靠记忆追溯过程。每个阶段读上一个阶段的产物，写下自己的产物，下一阶段再继续。

但原文也不断提醒，人类仍然对所有需要判断的决策负责。AI 原生不是无人负责。它改变的是人类注意力的位置。以前人要亲手启动每个阶段，亲手写大部分文档，亲手看大部分细节。现在人更像站在几个关键闸口，审阅 agent 标出来的风险、决定是否推进、批准高风险动作。换句话说，人类从流水线工人，变成了调度员、审计员和最终责任人。

我们先来看规划阶段。传统流程里，如果一个业务同学有想法，他可能要先写一段描述，再找产品经理沟通，产品经理再帮他整理成需求。这个过程经常卡在表达和排期上。Anthropic 建议让任何想法先进入一个统一的 intent 点 md。这个文件就是意图文档，描述问题是什么，谁受影响，期望结果是什么，有哪些约束，还有哪些开放问题。

比如文章里的例子，是保险理赔状态自助查询。问题是客户总打电话问理赔进展，客服人员三分之一通话时间都花在只回答状态的问题上。期望结果是客户可以在门户里看到理赔状态、下一步和预计日期。受影响的用户和系统包括理赔处理人员、门户团队和理赔核心 API。约束是门户会话里不能新增个人敏感信息，只能使用现有认证。开放问题是第三方查勘员是否也需要访问。

注意这里的变化。这个意图文档不要求提出想法的人懂 git，也不要求他会写正式需求。他可以用自己的话跟 Claude 头脑风暴。Claude 像一个业务分析师一样追问范围、用户、限制和成功标准，然后按照组织模板生成 intent 点 md。提出者再纠正 Claude 理解错的地方，最后通过连接器把文档提交到共享仓库。产品负责人看到后做接受或拒绝的决定，这个决定也通过 merge 或关闭 review 记录下来。

这对企业很有价值。因为很多需求在早期是散落在聊天记录、会议纪要和个人脑子里的。AI 原生流程要求它们尽早变成一个结构化、可读、可审计的文件。更重要的是，一旦产品负责人接受这个 intent 点 md，它就可以触发下一步，而不是等某个人手动把信息复制到另一个系统。

接下来是设计阶段。原文说，产品负责人批准 intent 点 md 之后，Claude 会读取它，并根据组织的品牌、安全、合规和用户体验技能，生成 spec 点 md。这里的 spec 是 requirements and design spec，也就是需求和设计规格。产品负责人要审这个规格，但不必亲手从零写它。目标是产出一个工程团队可以用来规划的规格，同时把风险点提前标出来。

这个地方很像我们今天很多团队想做但做不顺的事情。比如一个前端需求，过去可能是产品写文档，设计师画图，工程师看半天仍然发现边界条件不清楚。文章描述的路径是，intent 点 md 被接受后，产品负责人可以用 Claude Design 的 beta 版本从意图生成 mock，也就是界面原型，迭代之后导出给 Claude Code 去构建。这里原文没有展开 Claude Design 的细节，只是把它作为前端场景下的典型例子。

真正重要的是，组织的 policy，也就是政策和规范，在 spec 写作时就被读取和应用，而不是几周后在评审里才被发现。比如安全政策说不能暴露某些个人信息，品牌规范说某类提示语要用固定语气，用户体验标准说错误状态必须可恢复。Claude 在写 spec 点 md 时就会应用这些约束。如果不同政策之间冲突，它要明确标出 concern，也就是关注点或者风险点。产品负责人先和对应政策负责人解决这些问题，再让工程团队看到规格。

这其实是把很多晚期返工提前了。你可以想象，如果一个 API 的数据字段设计到上线前才被安全团队发现会泄露个人信息，那代价很大。可是如果在 spec 阶段 Claude 就根据组织技能发现，某个字段不能出现在门户 session 里，那只需要改文档和设计，成本非常低。原文还强调，生成 spec 的 prompt，使用的技能版本，以及最终 spec，都应该进入版本控制。这样以后审计时可以看到，当时 agent 是根据哪些规则生成的规格，人又是如何批准的。

然后进入构建阶段。这里是很多工程师最熟悉的部分，也是 Claude Code 发力最大的地方。但文章的重点不是“让 Claude 直接写代码”，而是先用 plan mode，也就是计划模式。工程师把已经批准的 intent 点 md 和 spec 点 md 给 Claude，让它生成实施计划。这个计划要说明哪些文件会变，工作顺序是什么，用什么测试证明改动正确。工程师要反复追问，哪些地方可能被破坏，哪一步风险最高，有没有其他方案被放弃了。直到一个没有看过对话的工程师，只凭这个计划也能实现改动。

计划被接受后，提交为 plan 点 md。这个文件加入审计轨迹。后续 PR 评审会检查实际 diff 是否符合计划。如果实现过程中偏离计划，也要在同一个提交里更新 plan 点 md。文章甚至建议可以用 hook，也就是钩子，来强制计划和代码保持同步。这里的思想很像建筑施工。以前我们担心 AI 边写边改，越写越偏。plan mode 等于是先让它画施工图，人批准之后，才让它动工。

原文还提到 auto mode，也就是自动模式。工程师批准计划并充分迭代后，Claude 可以在不逐个编辑请求人工确认的情况下应用改动。随着后面的护栏成熟，比如调好的 CLAUDE 点 md、编码组织政策的 skills、阻止危险行为的 hooks、以及 Claude 可以自己运行的测试套件，auto accept，也就是自动接受，会成为常规工作的默认方式。但前提很明确，规格要紧，影响范围要小，代码已经有测试覆盖。

这里有一个很重要的转变。过去工程师可能盯着 agent 每一步怎么改文件，像看实习生敲键盘。未来更合理的方式，是让 agent 在更长的自主会话里完成工作，然后工程师审阅产物。也就是从 review actions，审动作，转向 review artifacts，审产物。对工程师来说，这意味着你的技能重心会往需求澄清、计划审查、风险识别、测试设计和最终判断迁移。

要让 Claude 真正理解一个代码库，文章强调了一个文件，CLAUDE 点 md。它给 Claude 提供一个新同事第一天入职需要知道的上下文，包括约定、命令、架构，以及团队最常见的错误。过去这些知识散落在老员工脑子里、wiki 里、README 里、群聊里。现在把其中 agent 必须知道的部分写进仓库根目录的 CLAUDE 点 md，并且像代码一样 review。

原文建议先在仓库里运行 init，让 Claude 根据代码库生成一个初版，然后删到只剩新同事第一天真正需要的内容。保留构建、测试、lint 命令，保留重要约定，保留 Claude 经常犯错的地方。比如支付服务里，Money 一律用 BigDecimal，不能用 double；每个 endpoint 都需要集成测试；不要升级依赖版本，因为平台团队负责；旧的 v 一包已经冻结，改动要放到 v 二包。文章给了一个很实用的规则，如果 Claude 同一个错误犯了两次，就把纠正写进 CLAUDE 点 md。并且保持在一页以内，因为 Claude 每次会话开始都会读它，过期内容只会浪费上下文。

除了 CLAUDE 点 md，文章还讲了 skills，也就是技能。技能是把组织知识操作化的一种方式。什么时候写 skill？原文给的经验法则是，如果某类制度知识必须被一致应用，就写成 skill。比如安全标准、API 设计约定、品牌规则。不要把属于具体仓库上下文的东西写成 skill，那些更适合放进 CLAUDE 点 md 或 prompt。

一个 skill 通常是一个文件夹，里面有 SKILL 点 md，前面的元信息说明何时触发，正文说明要做什么。比如 secure API review，安全 API 审查技能，可以规定每个外部 endpoint 必须有网关 JWT，不能有匿名路由，输入要按 OpenAPI schema 校验并拒绝未知字段，改变状态的 endpoint 要发审计事件，标记为个人信息的字段不能出现在日志和错误消息里。政策变更时，修改 skill，并由政策负责人签字批准。工程师下次会话自动拿到新版本。

但 Anthropic 很清醒地说，skill 是 advisory control，建议性控制。它会让 Claude 更可能在写代码时应用政策，但不能强制合规。如果一条政策必须永远成立，就需要 deterministic，也就是确定性的机制，比如 hook 阻止动作，或者 PR 阶段重新检查。文章的表述很漂亮，skill 让违规变少，hook 让违规接近不可能。

hook 是构建阶段和发布阶段都很关键的护栏。Claude 在实现时最常做的是编辑文件和执行 shell 命令，所以 hook 可以在这些动作前后运行。它可以阻止编辑受保护路径，比如生成代码或冻结包；可以在文件编辑后自动跑 formatter 和 linter，避免风格漂移；可以检查 diff 里有没有凭证。文章强调，构建阶段的 hook 要快，而且范围要小，最好只针对变更文件。完整测试套件这类重检查，更适合在提交或 PR 阶段跑。

这里还有一个细节，值得团队设计流程时注意。如果一个 hook 需要询问人类审批，它最好放在部署阶段的门禁里，而不是构建阶段。因为构建阶段的人工审批会把人重新放回所有并行会话的关键路径，直接抵消自动化的收益。也就是说，构建阶段尽量用自动 allow 或 block，发布阶段再用需要人批准的 ask。

文章接着讲并行。一个工程师可以驱动多个工作流。parallel session，也就是并行会话，是另一个完整 Claude Code 实例，在自己的 git worktree 里做独立任务。worktree 可以理解成同一个仓库的不同检出，分别在不同分支上，避免多个 session 撞同一个文件。subagent，也就是子智能体，则是在一个会话内部运行的有范围助手，有自己的上下文窗口和工具限制，适合重复任务，比如验证应用行为、简化代码、研究代码库。

原文建议，两三个并行 session 是一个合理起点。真正的上限不是机器能跑几个，而是一个人能认真 review 几个流。这个判断很实在。很多团队试 AI 工具时会兴奋地开十个任务，最后变成十堆没人敢合的代码。并行的核心不是“让 AI 忙起来”，而是让工程师作为驾驶员同时推动几条独立路线，但仍能看清每条路线的风险。

每个会话都要有自我验证的方法。原文强调，不管是测试、构建，还是截图 diff，都要给 Claude 一个检查自己工作的方式。一个 session 应该先检查自己的工作并修正错误，再交给工程师。对于 bug fix，文章建议先让 Claude 写一个失败测试来复现 bug，运行并确认失败原因符合预期，然后提交这个测试。之后再让 Claude 修改代码让测试通过，并且用 hook 阻止它在修复任务中编辑测试文件。这样，修复前已经存在、agent 又不能篡改的测试，才是 bug 消失的证据。

对于 UI 工作，闭环可以是视觉检查。给 Claude 浏览器或者截图工具，给它 mock，让它实现、截图、比较、调整。两三轮很正常，并且每轮结果应该变好。这里我个人认为，是很多前端团队马上可以落地的点。你不一定要一上来做全生命周期自动化，但你可以先把“完成”的定义改掉。不是 Claude 说写完了就完了，而是它必须跑指定测试，贴出健康输出，或者拿截图和设计稿对比。

再往测试治理走，文章提出 evals，也就是评估集。它把 evals 称为 AI 原生的阶段门禁 QA。传统 QA 会在阶段之间做检查，而在 AI 原生流程里，当你换了模型、改了 prompt、改了 CLAUDE 点 md、skills 或 hooks，就需要一套 eval 来验证 agent 仍然能按同样标准工作。

原文建议平台工程师收集最近真实工作的二十到五十个任务，每个任务都有期望或已经接受的结果。把每个任务写成 eval，包括 prompt 和可接受标准，比如测试通过、lint 干净、行为不变、政策符合。eval 套件在 CI 里非交互运行，可以按计划运行，也可以在 agent 配置变化时运行。配置变化要像代码变化一样接受回归测试。如果一个 skill 的修改让通过率下降，就要在合并前 review。每个生产事故也应该变成一个 eval，作为回归测试留在套件里。

这个观点对平台团队非常重要。很多团队现在评估 AI 编码工具，只看主观感受，某次 demo 很惊艳，就推广；某次翻车很严重，就禁用。Anthropic 的建议是，既然 agent 配置会影响代码产出，那它就应该像代码一样被测试。模型升级不是无风险升级，prompt 改写也不是文案调整，它们都可能改变 agent 行为。evals 就是给这些变化装上回归测试。

部署阶段，文章讲了两个部分，PR review 和 CI CD。Claude 既可以给 review，也可以接收 review。它可以根据组织政策审查进来的 PR，也可以处理自己 PR 上的 review comment。这样工程师可以把注意力更多放在行为、意图和风险上。注意，不是让 Claude approve PR。原文明确说，职责分离要保留。写代码的 agent 没有办法批准代码，最终批准仍然来自人类 code owner，并通过 branch protection，也就是分支保护，强制执行。

为了让 AI review 稳定，技术负责人可以在仓库根目录写 REVIEW 点 md，定义评审政策。比如分成 bug 与逻辑错误、安全和漏洞、合规三个 pass。合规要检查变更是否符合 spec 点 md、plan 点 md 和设计原则。REVIEW 点 md 还要定义什么算 Important，什么只是 Nit。Important 应该保留给会破坏行为、泄露数据或违反政策的问题。风格和命名最多算 Nit，而且可以限制每次最多报告五个 Nit，避免 AI review 变成噪音制造机。生成文件和 CI 已经强制的东西也应该排除。

当 reviewer 或作者在评论里 tag Claude，Claude 可以处理评论并推送修复。PR 线程记录了请求和变更。对于 Claude 自己开的 PR，团队甚至可以做一个自定义命令，让 Claude 反复扫描未解决评论和失败检查，修复并推送，直到 PR 变绿，只等 code owner 批准。review 发现还会反馈回 CLAUDE 点 md。同样的错误第二次被 review 抓到，就把纠正写进 CLAUDE 点 md。这样从下一次 PR 开始，错误会更早被避免。

发布门禁则更强调 hook。构建阶段的 hook 主要是自动 allow 或 block。发布阶段的 hook 可以 ask，也就是暂停动作，等待指定人员批准。工程领导、变更管理和合规团队要列出必须保留的人类审批门，比如变更管理签字、发布授权、受保护路径编辑。平台工程师把每个门禁表达成 hook。团队 hook 可以放在仓库配置里，不能妥协的 hook 要放进平台或 IT 管理的设置里，个人工程师不能关掉。block 必须解释原因，并告诉 Claude 去哪里拿批准。

CI CD 里运行 Claude，要从只读判断步骤开始。比如构建失败时，让 Claude 读日志，判断最可能原因，说明是 flaky 还是 real，也就是偶发还是实际失败，并写三行摘要给 PR。然后再增加受现有门禁保护的写操作，比如修 lint、更新生成文档、处理 review comment。只要 agent 写东西，就通过 PR 进入分支保护，不能直接推 main。

原文对安全执行环境也很重视。agent job 要在容器里运行，有网络策略，使用短期、范围受限的 token，默认没有生产凭证。部署能力通过 MCP 暴露。MCP 可以理解成模型上下文协议，让外部工具以受控方式接入模型。部署、状态查询、回滚都变成按环境授权的工具，而不是给 agent 一个带生产凭证的 shell。开发环境可以让 agent 自由部署，生产环境则让 agent 准备发布，由 release manager 授权，hook 强制生产门禁。回滚路径必须反复演练，最好是一条 agent 可以运行、且在 staging 经常练习的命令。

最后是维护阶段，也是文章最有想象力的部分。前面几个阶段虽然都有 Claude，但通常还需要人启动。维护阶段转向 headless，也就是无头自动运行，用 Claude 来闭环。比如一个持续运行的监控 agent，看到 bug ticket 或指标异常后，创建 intent 点 md，然后流经需求、计划、构建、测试和评审阶段。当然，中间不是完全放飞。每个阶段之间有独立信心门，可能是确定性检查，也可能是对抗性 reviewing agent，用来决定继续推进还是升级给人。

文章用控制带 breach，也就是指标突破控制区间，来说明这个模式。服务负责人或平台工程师先选一个稳定指标，比如 CI 测试失败率、发布后五百错误率、PR 周期时间。检测脚本完全确定性，不用模型，通常用滚动窗口里的均值和标准差，加上类似 Western Electric 的规则，既捕捉突刺，也捕捉慢漂移。响应层级写在版本控制配置里。一倍标准差只记录，两倍标准差让 Claude 只读诊断，三倍标准差时 Claude 可以行动，但只能开 PR 进入 review gate，或者触发预先批准的 runbook，比如回滚部署。

这里的边界非常重要。检测用确定性脚本，不让模型决定有没有异常。模型负责诊断、整理 intent、提出修复方案。权限由配置和 managed settings 控制，不能随意访问生产。调用、发现和 triage 决策都有时间戳记录。服务负责人或 on-call 工程师负责分流，决定现在修、排期修，还是 dismiss。被 dismiss 的结果反过来调控制带，减少噪音。修复上线后，再把事故写成 eval，防止未来回归。

原文给了几个例子。如果 CI 测试失败率突破三倍标准差，agent 可以隔离 flaky test 或打开 revert PR，最终由 review gate 决定。如果发布后五百错误率突破三倍标准差，而且窗口里有一次部署，agent 可以触发已有回滚 pipeline。如果 PR 周期时间出现漂移，agent 可以给工程领导写报告。这说明闭环不只适用于线上事故，也适用于研发过程指标。

文章还提到 Claude Tag，目前在 Slack 里是 public beta。它让 Claude 以自己的身份成为工作沟通频道成员。比如晚上十点事故频道里有人发紧急修复请求，Claude 可以成为第一响应者。频道里的对话和组织知识都留在原处，任何成员都可以引导它、让它验证假设、探索选项。通过 MCP，Claude 可以验证指标是否回到 baseline，并在 thread 里确认，还可以把 postmortem，也就是事后复盘，写到版本控制的 lessons 文件里，供未来调查读取。它也可以在 ticket 或频道里被 tag，处理小而明确的修复，或者把更大的工作写成 intent 点 md，重新喂进第一阶段。

讲到这里，我们可以把这篇文章的主线收束一下。Anthropic 并不是在说，未来研发流程里人不重要了。恰恰相反，它认为人类判断要更清晰地留在关键点上。AI 原生 SDLC 的核心，是把每个阶段的输入输出标准化、版本化、可审计化，把重复劳动和交接摩擦交给 agent，把确定性政策交给 hook 和 CI，把模型行为变化交给 eval，把发布和高风险决策交给人。

对正在听节目的工程师和 AI 从业者，我觉得最实际的落地顺序可以很朴素。不要一开始就追求全自动闭环。先选一个仓库，写好 CLAUDE 点 md，把 build、test、lint 命令整理成 Claude 能运行也能判断结果的形式。再把一个反复踩坑的团队约定写进去，比如不要改生成文件，不要碰冻结目录，钱不能用浮点数。然后建立一个简单的 plan 点 md 习惯，任何 Claude 做的非小改动，先有计划，再动代码。接着做一两个 hook，比如阻止提交凭证、阻止编辑受保护路径。最后再考虑 skills、evals、AI review 和 CI 中的非交互 Claude。

还有一个坑要避开，就是不要把所有治理都写进 prompt。prompt 很灵活，但也很脆。必须一致执行的规则，要么进入 skill，让 Claude 更容易应用；要么进入 hook、CI、branch protection，让它不能绕过。另一个坑是把 review 压力全部转嫁给人。AI 生成越多，人类 review 越累，所以你必须同时建设自验证、eval、AI review、清晰的产物链。否则团队很快会从“写代码太慢”变成“没人敢合代码”。

我个人认为，这篇文章最有价值的地方，不是某一个 Claude 功能，而是它给了一个组织级视角。AI 编码工具的竞争，早期看模型能不能写代码；中期看能不能读懂项目、跑通测试；再往后看的是，你的组织流程能不能承载这种速度。谁能把需求、设计、实现、测试、发布和维护都变成机器可读、人类可控、全程可审计的闭环，谁才真正吃到 AI 原生研发的红利。

最后用两三句话总结。代码生成已经被加速，传统 SDLC 的其他环节如果不变，就会成为新的瓶颈。Anthropic 提出的 AI 原生 SDLC，是用 intent 点 md、spec 点 md、plan 点 md、CLAUDE 点 md、skills、hooks、evals 和 CI CD，把研发流程重构成一个可审计的智能体协作循环。我的点评是，这不是一个“买了 Claude Code 就自动拥有”的未来，它更像一套工程管理和平台工程能力的升级清单，值得每个认真引入 AI 编程的团队尽早开始建设。
