## Script

今天我们聊的文章是 Maximizing the value of your Claude Code sessions，中文可以译作《最大化你的 Claude Code 会话价值》。这篇文章发表于二〇二六年八月十四日，离今天二〇二六年八月十六日只有两天，所以这是一篇非常新的文章，讲的是当下软件工程师正在真实遇到的问题：当我们把 Claude Code 这类 agentic coding 工具，也就是能自己读文件、跑命令、改代码的智能编码代理，放进日常工作流之后，怎么让每一次会话花出去的 token 都更有价值。

这篇文章篇幅不长，原文标注大概五分钟阅读，但它背后其实讲了一个很重要的转变。过去我们写代码，用编辑器、IDE、命令行工具，通常是固定费用，甚至免费。你下午修一个测试，还是修五十个测试，工具本身的成本差别不大。但到了 Claude Code 这样的工具里，同样一个任务，可能因为你怎么提问、怎么组织会话、让 Claude 读了哪些文件、跑了哪些命令，最终消耗完全不同。换句话说，代码编辑这个动作第一次变得有了非常细粒度的边际成本。

这不是单纯的省钱话题。对订阅用户来说，你可能看不到每个 token 的价格，但你会感受到额度消耗变快。对 API 用户、企业用户、团队管理员来说，这就是实打实的预算。更关键的是，上下文塞得越多，模型每一轮都要在更大的信息堆里找重点，结果不只是贵，还可能更慢、更容易走偏。所以这篇文章的核心，不是让你少用 Claude Code，而是让你把 token 花在真正有助于解决问题的地方。

我们先从文章开头的例子讲起。假设你要修一个失败的测试。在一个高效的会话里，你告诉 Claude：修 utils.test.ts 里面失败的测试。Claude 读这个测试文件，再读被测试的源文件，改一处代码，跑测试，通过，结束。整个过程可能就几轮对话。但在另一个会话里，你只说：测试挂了，帮我看看。Claude 不知道哪个测试挂了，于是先 grep 一下仓库，再打开一堆可能相关的文件，跑测试，输出很多日志，最后其实还是回到同样那两个文件上，做同样的修改。

两个会话交付的结果一样，但成本不一样。更微妙的是，Claude 在第二个会话里不只是多花了 token 去搜索，它之后每一轮还要带着前面读过的那些文件和命令输出继续工作。就像你让一个同事修一个小 bug，第一种情况你把准确的测试文件和相关背景递给他，第二种情况你把整个项目资料夹、所有日志、今天上午所有讨论记录都扔给他，说你自己找。最后他也能做完，但他每次思考都要绕过大量噪音。

Anthropic 在文中强调，token 效率不是简单地少用 token。真正的目标是确保你用掉的 token 都服务于当前任务。这个说法我个人认为很重要，因为很多团队一谈 AI 成本，就容易走向极端：要么完全不管，反正工具能提效；要么过度抠 token，导致模型拿不到必要上下文，结果改错代码。更合理的做法是，让必要上下文足够充分，让无关上下文尽早离场。

接下来文章解释了 token 为什么会有价格。你账单上看到的是按 token 计费，但你真正付费的是推理，也就是模型在 GPU、TPU 或其他计算硬件上处理这些 token 的时间。影响单个 token 成本的因素主要有三个：你用的是哪个模型，这个 token 是输入还是输出，以及它有没有命中缓存。

模型大小很好理解。更大的模型在输入和输出阶段都要做更多计算，所以更贵。什么时候用大模型，什么时候用小模型，原文说这是另一个主题，他们在另一篇关于选择 Claude 模型和 effort level，也就是努力程度的文章里展开过。这里我们只需要抓住一个原则：如果问题真的难、含糊、需要架构判断，用更强的模型是值得的；如果只是重复性、机械性的改动，用较小模型往往更划算。

输入 token 和输出 token 的差别，是很多人容易忽略的地方。一次请求进入模型，大致有两个阶段。第一个阶段叫 prefill，可以理解为模型先把你发来的所有内容读一遍，包括系统提示词、工具定义、CLAUDE 点 md 文件、你的消息，以及会话里此前追加进去的文件内容和命令输出。这些都是输入 token。第二个阶段叫 decode，也就是模型开始一个 token 一个 token 地生成输出，可能包括它的思考、工具调用，以及你最终看到的文字。

为什么输出 token 通常比输入 token 贵很多？文章里说，decode 是逐 token 生成的。一个两百 token 的回复，本质上就是模型连续运行两百次，每次生成下一个 token。每个输出 token 都让 GPU 忙更久，所以输出价格大约是输入的五倍。这里还有一个现实问题：Claude Code 会话中相当一部分输出 token 不是最终答复，而是 thinking tokens，也就是模型内部用于推理的思考 token。你选择的 effort level，努力程度，控制的就是每一轮模型愿意花多少思考预算。

这就引出文章的第一个操作建议：在新会话一开始，就运行 slash model 和 slash effort，确认你现在到底用的是哪个模型、哪个努力程度。因为 Claude Code 会记住你上一次的选择，这个默认值会带到下一次会话。你以为自己在用便宜配置做杂活，实际可能还停留在昨天解决复杂问题时选的大模型高努力程度。原文还提到，如果你明确知道某个会话只是苦力活，可以用 MAX_THINKING_TOKENS 等于零，让这个会话关闭思考 token。不过文章也特别注明，Fable 五除外。这里我们不用纠结具体环境变量怎么配，重点是：模型和努力程度都应该是有意识的选择，而不是历史遗留状态。

然后是整篇文章最技术、也最有实用价值的部分：prompt caching，也就是提示词缓存。它的原理可以用一个很朴素的方式理解。假设服务器刚刚处理过一个请求，而下一个请求的开头一大段 token 和上一个请求完全一样，那么模型读完这段开头后得到的内部状态也是一样的。既然一样，服务器就可以把这个状态保存下来，下次直接加载，不必重新计算。这就是缓存。

缓存命中之后，读取缓存的成本只有普通输入价格的零点一倍，因为服务器只是在加载状态，不是在重新做完整计算。把 token 写进缓存会比普通输入稍贵，最高到两倍，因为服务器还要把状态保存下来。但写入通常只发生一次，而后续每一轮都能用零点一倍的价格读取，所以长会话里缓存非常关键。Claude Code 会自动管理 prompt cache，不需要你手动开启。但原文反复强调，你虽然不用打开它，却很容易破坏它。

文章用一个修测试的例子，把一轮 Claude Code 会话是怎么计费的讲得很清楚。你输入：修 utils.test.ts 里失败的测试。Claude Code 先组装第一个请求，包括工具定义、系统提示词、CLAUDE 点 md，还有你的消息。因为此时缓存还没有东西，所以这些输入都要完整 prefill，并写入缓存。模型发现自己没看过测试文件，没法修，于是输出一个 Read 工具调用，要求读取 utils.test.ts。

Claude Code 读完文件后，把文件内容追加到会话里，再把整个会话发给模型。注意，是整个会话，不是只发新文件。但由于前一轮的系统提示词和用户消息都已经在缓存里，这部分只按零点一倍读缓存，真正按全价 prefill 的只有新的 Read 调用和文件内容。接着模型可能又要读被测试的源文件，于是再输出一个 Read。Claude Code 读文件，追加，再发送整个会话。这一次，前面两轮都尽量从缓存读，新的源文件按全价输入。

然后模型输出 Edit 调用，Claude Code 应用修改，把结果追加，再发给模型。之后模型运行 npm test，测试输出被追加，再发给模型。最后测试通过，模型给一个简短总结，没有新的工具调用，会话结束。一个小修复可能有五次请求，每一次请求都包含截至当前的完整会话。典型的一轮是输入非常大，可能几万 token，输出只有几百 token。但因为缓存存在，只有这一轮新增的部分按全价输入，历史部分按缓存读价格。

这个模型对理解 Claude Code 成本非常关键。每一轮账单大致由三块组成：历史上下文的缓存读取，新加入内容的完整输入，以及模型这一轮的输出。订阅用户虽然不直接看到这三块价格，但额度消耗背后也是同样的请求。你可以把它想成坐出租车：起步价、里程费、等待费都被打包到最终计价器里，你不一定逐项看见，但它们确实在跑。

那缓存什么时候会失效？原文说，缓存必须从请求的最开头开始完全匹配。Claude Code 发请求的顺序也固定：先是工具定义，然后系统提示词，然后会话内容，其中 CLAUDE 点 md 在会话前面。如果这个前缀的任何东西变了，后面的内容就不能继续复用原来的缓存，需要重新 prefill。最理想的新增内容，是追加在会话末尾的工具结果，因为它后面没有东西，不会影响前面缓存。最糟糕的是改动靠前的东西，或者改动缓存的 key。

具体来说，中途切换 model 会影响缓存。中途切换 effort 也会影响缓存，所以 Claude Code 会在会话中间切换时要求你确认。fast mode，快速模式，也是缓存 key 的一部分。如果你要开，就最好一开始开。文章还说，关闭 fast mode 在缓存角度是免费的。compact，也就是压缩会话，会改写整个会话摘要，所以它一定有成本。时间也会影响缓存。订阅场景下，每一轮都会重置计时，但缓存一小时后过期。API key 默认五分钟后过期，可以通过 ENABLE_PROMPT_CACHING 一小时的环境变量改成一小时。隔很久回来继续老会话，通常也会重新 prefill，因为缓存多半没了，启动时系统提示词也可能被重建。

这里有一个很实用的判断：不是说永远不要切模型、切努力程度、做 compact，而是要在便宜的时机做。便宜时机是新会话一开始，或者 slash clear 之后，因为上下文还短。昂贵时机是一个很长会话的中间，因为前面所有内容可能都要重新走一遍。原文还给了一个小技巧：如果最近几轮走偏了，不想保留，不要立刻 compact，可以用 slash rewind 回到走偏之前。rewind 只是从尾部剪掉几轮，前面的缓存还在，所以几乎没有额外成本。compact 则会重写整个会话，所以一定会花钱。

讲完缓存，文章进入另一个关键概念：上下文不是一次性发送的。凡是进入会话的东西，无论是 Claude 读过的文件，还是它运行命令产生的输出，都会在后续每一轮再次发送。虽然大部分会走缓存，便宜，但便宜不是免费。而且它们还占上下文窗口，让模型每次都要在这些信息旁边思考。文章把整个会话的成本模型总结得很简洁：有多少 token 进入上下文，它们在上下文里停留多少轮，以及你同时跑了多少个上下文。

这句话值得每个工程师记住。我们平时优化程序性能，会关心数据结构里到底塞了多少对象、这些对象生命周期多长、是不是有多个副本。Claude Code 会话其实也是类似的。你把一个巨大的测试日志放进主会话，它就像一个常驻内存的大对象，每一轮都跟着你。即便缓存让它读取便宜，它仍然占内存、占注意力、占上下文空间。工程师很熟悉垃圾回收，但在 AI 会话里，很多人忘了自己也需要做上下文垃圾回收。

会话里有些内容在你还没输入任何东西之前就已经存在，比如工具定义、系统提示词、CLAUDE 点 md，以及启动时加载的其他配置。原文建议，在一个新会话里运行 slash context，看看到底加载了什么。如果 CLAUDE 点 md 里塞了太多泛泛的工作流说明，每个会话都要带着它们。更好的做法是，让 CLAUDE 点 md 保持具体、必要，把特定工作流相关的指令移到 skills，也就是技能里，只有用到时才加载。如果某个 MCP server，本轮任务不需要，也可以用 slash mcp 关掉。MCP 是 Model Context Protocol，模型上下文协议，用来把外部工具和资源接到模型里。接得越多，能力越强，但会话开销也可能越大。

会话进行中，大部分新增上下文来自工具结果。最常见的是文件内容和命令输出。Claude 读多少文件，取决于你给它多少线索。如果你只说测试失败了，Claude 必须先搞清楚哪个测试失败，可能会搜索几次，打开几个文件判断相关性。这些搜索结果和文件内容，之后都会留在会话里。你如果直接说修 utils.test.ts 里的失败测试，它就跳过搜索，至少少跑几步。如果你用 at 提及文件，也就是在 Claude Code 里用 @ 直接引用文件，Claude Code 会在发送请求前把文件附到你的消息里，这样连 Read 调用都省了。

这里有个细节很容易踩坑。文件本身占用的上下文空间，不管是 Claude 自己 Read，还是你 @ 提及，本质上差不多。@ 的好处主要是省掉一次工具调用和一次搜索，让文件从第一轮就进入上下文。但同一个文件在一个会话里只需要提一次，因为它会留在上下文里。你后面又 @ 一次，通常会再附一份副本，反而浪费。实践上，你可以把 @ 文件看成把资料直接递给同事，而不是让同事自己去资料柜找。但资料递过去之后，就不要每隔五分钟再复印一份给他。

另一个容易膨胀上下文的是命令输出。Claude 每次跑测试、跑构建、看 git log，终端打印出来的内容都会像文件一样追加到会话里，并且在后续轮次停留。原文说，特别大的输出反而问题不大，因为超过三万字符之后，Claude Code 会把输出写到文件里，只在会话里放一个短预览和路径。真正麻烦的是低于这个阈值但很啰嗦的输出。比如一个测试运行器把四百个通过的测试一行一行打印出来，总长度没超过三万字符，于是这四百行全进了上下文，并在接下来每一轮都跟着你。

Claude 通常会自己用 quiet flags，也就是安静模式参数，或者 tail 之类的命令，只保留关键输出。但你最好不要完全依赖它。文章建议，把你每天反复运行的两三个命令写进 CLAUDE 点 md，带上安静参数，用你自己平时会敲的方式描述。比如运行单个测试文件时，用 vitest 的 dot reporter，让输出简短。这个小改动很朴素，但每个会话都能省掉一轮解释和几百行没必要的输出。原文还提到，文档里有一个 hook，可以在噪声命令执行前改写它，只让关键行返回。对团队来说，这类 hook 很适合做成统一工程规范。

然后文章谈到长会话。一个长会话通常比同样工作拆成几个短会话更贵，而且贵得可能超出直觉。因为第四十轮也要重新带上前面三十九轮的上下文。你希望会话里的上下文短而相关，所以不要把一个任务的上下文带进下一个任务。开始新任务时用 slash clear。当前任务早期探索已经结束，后面只需要保留结论时，用 slash compact。原文开头的要点里还特别说，离开键盘休息前最好 compact 一下，因为 prompt cache 一小时后过期。趁缓存还在时总结会话，比过一小时回来让整段长会话重新 prefill 更便宜。

这里我个人建议大家把 slash clear 和 git commit 形成类似的肌肉记忆。一个功能点结束，测试通过，提交前后都可以考虑清空会话。不要从上午修登录页样式一路聊到下午改数据库迁移。Claude 不是人类同事，它不需要通过保留全天对话来维持人际连续性。它真正需要的是当前任务的相关上下文。对工程师来说，clear 不是丢历史，而是释放上下文堆内存。

当然，有些会话你之后可能还想回来。原文建议，clear 之前可以先 slash rename，给会话起个名字，方便以后找。如果你要 compact，最好告诉 Claude 要保留什么，或者在 CLAUDE 点 md 里写一个 Compact instructions，也就是压缩指令段，如果你每次需要保留的信息都差不多，就让它自动按这个规则总结。文章还提到，如果你在使用一百万上下文窗口的模型，又希望 auto compact 的安全网回到以前更早触发的位置，可以用 slash autocompact 二十万，把自动压缩阈值设回二十万上下文，这需要 Claude Code 二点一二二一或以上版本。这个细节很工具化，但它说明 Anthropic 在引导用户主动管理超长上下文，而不是默认把一百万窗口当成可以随便塞的仓库。

还有一种隐藏成本来自你没在键盘前输入的轮次。比如 slash loop，会在你设置它的会话里触发完整轮次。每次 loop 都带着整个会话上下文跑。如果距离上一轮超过一小时，还会叠加缓存失效。文章建议，如果你要跑 loop，最好开另一个终端，用一个新会话去跑。这个建议非常现实。很多工程师会让 agent 循环跑测试、修复、再跑测试。如果这个循环挂在一个已经聊了很久的主会话里，每次循环都背着一大包历史，很不划算。把循环隔离到新会话，就像把批处理任务放到一个干净容器里跑。

说到隔离，文章最后重点讲了 subagent，子代理。subagent 的作用，是让某些事情发生在另一个上下文里。它有自己的上下文窗口、自己的系统提示词、工具和 CLAUDE 点 md，但没有你的主会话对话历史。它自己运行若干轮，最后只有它的答案回到主会话。其他中间读过的文件、跑过的命令输出，任务结束就丢掉。

这听起来很美，但原文也提醒了代价。因为 subagent 没有主会话历史，它有时需要重新读取主会话已经读过的东西。它运行自己的轮次，也要花自己的 token。对于很小的任务，这就是额外开销，不一定划算。它真正适合的是会产生大量你不想长期保留输出的工作，比如遍历日志、扫描大量文件、做一次性调查。主会话只需要最后结论，不需要把几千行日志常驻在上下文里。Claude 有时会自动为这类任务使用 subagent，如果没有，你也可以明确说：请在 subagent 里检查这个日志。

这里的取舍可以类比微服务。把所有逻辑放在一个进程里，调用成本低，共享内存方便，但状态容易膨胀。拆成单独服务，通信有开销，也可能重复加载数据，但故障隔离和资源隔离更好。subagent 也是一样。小任务别乱拆，噪声大、输出多、探索性强的任务值得拆。原文还建议，如果你反复把某类噪声任务交给 subagent，可以给它一个专门的 subagent 定义，并指定 model 为 haiku 或 sonnet。否则它会沿用主会话的模型。也就是说，你主会话如果用昂贵模型做架构推理，日志清洗这种苦力活最好不要也用同样配置。

把这些点合起来，我们可以提炼出一套日常工作流。你打开 Claude Code，第一件事不是马上说帮我改代码，而是先确认环境。运行 slash model 和 slash effort，看看模型和努力程度是不是这次任务需要的。如果只是机械修改，别用过强配置。如果是复杂重构，再把配置调高。然后运行 slash context，看看启动时加载了什么。CLAUDE 点 md 是不是太长？不相关的 MCP server 是不是开着？这些都是你还没开始工作就已经背上的成本。

接着，提问时尽量给准确入口。不要只说项目坏了、测试挂了、页面不对。更好的说法是：这个测试文件失败，目标行为是这样；或者这个组件的这个交互有问题，请先看我 @ 的两个文件。用 @ 文件减少搜索和 Read 调用，但同一文件别重复 @。如果你已经知道复现命令，也直接给出来，而且最好是安静输出版本。你可以说：只运行这个测试文件，并使用简洁 reporter。这样 Claude 不用先猜命令，也不会把整套测试输出塞进上下文。

过程中要注意命令输出。看到 Claude 准备跑一个会打印海量日志的命令，你可以打断或提前说明，只保留失败用例、错误栈和最后几十行。对于构建系统、测试框架、lint 工具，每个团队都应该沉淀一份适合 AI 工具调用的低噪声命令。过去我们设计命令行输出，主要给人看；现在还要给 agent 看。给人看的详尽进度条、彩色日志、通过测试列表，对 agent 来说可能只是上下文污染。

当一个任务完成，不要顺手问下一个无关问题。先 slash clear。如果同一任务前面做了大量探索，现在已经知道方向，可以 compact，并明确告诉它保留关键决策、改过的文件、待办、测试结果，丢掉无关搜索过程。如果刚才几轮误入歧途，用 rewind，而不是 compact。这个差别很重要：rewind 像撤销几步编辑，compact 像重写一份会议纪要。撤销尾部便宜，重写全文更贵。

如果你准备去开会、吃饭、通勤，回来还要继续同一个任务，文章建议在离开键盘前 compact。因为缓存一小时后过期，趁热压缩比冷启动后重读整段历史便宜。这个建议非常像数据库里的 checkpoint，趁状态还在内存里，把关键状态固化成更短的表示。回来之后，你不是拖着几十轮原始对话继续，而是带着一份精炼摘要继续。

对于后台循环和长时间任务，最好隔离。slash loop 放到新会话。日志分析、批量扫描、噪声命令交给 subagent。主会话只保留你真正要基于它继续决策的信息。这里有一个简单判断：如果这个输出你五分钟后还需要逐行引用，就留在主会话；如果你只需要结论，就放到 subagent 或让命令输出变短。

我个人认为，这篇文章最值得中国工程团队借鉴的地方，是它把 AI 编码工具从玩具式使用推进到了工程化使用。很多团队现在评估 Claude Code、Cursor、Codex 类工具，还停留在模型聪不聪明、能不能一次写对代码。但真正大规模使用时，工作流纪律会变得同样重要。谁来维护项目级指令，哪些命令默认加 quiet flags，什么时候 clear，什么时候 compact，哪些 MCP 默认开启，哪些任务交给 subagent，这些都会影响团队总体成本和稳定性。

还有一点值得提醒：省 token 不等于把上下文压到极限。你如果不给 Claude 足够文件，它可能会猜接口、猜业务规则，最后制造更贵的返工。文章真正反对的是无关上下文，不是必要上下文。好的上下文应该像一份干净的 bug report：包含复现步骤、相关文件、期望行为、实际行为、最小日志。坏的上下文则像把整个 Slack 频道和全部 CI 日志都贴进去，希望模型自己筛。越是强大的模型，越容易让我们偷懒，但成本模型会逼我们重新学会表达清楚问题。

我们用两三句话收尾。Anthropic 这篇文章讲的核心是：Claude Code 的成本由模型选择、输入输出、prompt cache、上下文长度、会话轮次和并行上下文共同决定；高效使用不是少给信息，而是让信息短、准、相关。实际操作上，你可以从几个动作开始：新会话确认 model 和 effort，用 @ 文件给入口，给命令加安静参数，任务切换时 clear，休息前 compact，噪声任务交给 subagent。我个人认为，这些习惯会成为未来 AI 原生软件工程的基本功，就像今天我们已经默认会写 gitignore、会拆 commit、会看 CI 日志一样。
