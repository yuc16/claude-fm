## Script

今天我们要聊的这篇文章，标题是 Agentic coding is straining CI. Here's how we scaled test impact analysis at Anthropic。翻成中文，大概是「智能体编程正在压垮持续集成：我们如何在 Anthropic 扩展测试影响分析服务」。文章发表在二〇二六年九月十四日，到今天过去还不到一周，是一篇非常新鲜的、来自一线工程团队的实战复盘。

我先说说为什么值得你花二十多分钟听这一期。因为这篇文章表面上讲的是 Anthropic 内部一个叫测试影响分析的服务怎么扩容，但它真正回答的是一个正在逼近所有工程团队的问题：当 AI agent 开始大量写代码、大量提合并请求、大量改测试的时候，我们过去二十年习以为常的那套持续集成体系，到底还撑不撑得住。Anthropic 给的答案是撑不住，而且崩得比你想象得快。

他们 CI 的作业量在六个月里涨了二十五倍。同一个服务被打了三次补丁，第一次撑了七十天，第二次撑了二十九天，第三次撑了不到一天。最后他们不得不把整个服务推倒重来。

这里最有意思的一点，不是他们最后用了什么高深技术。买更大的机器、做进程并行、重启服务，这些都是非常老套的手法。真正扎心的是作者反复强调的一句话：这些老套手法今天能买给你的时间，只有一年前的零头；可是反过来，彻底重构一个服务的成本，也只有一年前的零头。当写代码本身不再是瓶颈，我们对架构的取舍逻辑就必须整体换一遍。

好，我们把背景铺开。

先说说持续集成，也就是 CI，到底是什么。简单讲，就是每次有人提交代码改动，系统自动跑一遍构建和测试，确保这个改动没有把别的地方弄坏。这是现代软件工程的地基。但地基有个前提假设：跑一遍完整测试的成本是可控的。

如果每次改动都把所有测试跑一遍，会发生什么？随着代码库变大、测试变多，这堵墙会越来越慢、越来越贵、越来越不可信。CI 门禁从五分钟变成半小时，再变成一个半小时。工程师开始绕过它，开始说"这个失败跟我没关系，先合了再说"。测试红灯的权威性就被稀释掉了。

所以很多成熟团队会引入一个东西，叫测试影响分析，或者叫测试选择。它的思路很朴素：既然一个改动通常只影响代码库的一小部分，那为什么要把所有测试都跑一遍？我们根据历史数据判断，这次改动动了哪些文件、哪些包，哪些测试在过去对这些改动敏感，只跑这些测试就好了。

Anthropic 也有这么一个服务。文章特别强调了一点，它是确定性的。这不是拿机器学习模型去猜，而是基于历史表现和代码包的相关性，用规则算出来的。这个区别很重要，后面我们会看到为什么。

那为什么 agent 时代这件事突然变得要命了呢？

先看一组数字。Anthropic 的工程师，人均每季度产出的代码量，是二〇二一到二〇二五年那几年的八倍。这八倍里，Claude 撰写了百分之八十的代码。而且 Claude 不只是写，它还深度参与 PR 的审查和批准。什么是 PR？就是代码合并请求，你写完代码，提一个请求，让别人审一遍再合进主干。Claude 在这里也干活。

与此同时，代码库里的测试总量涨了十倍。而工程师人数呢？文章说只"名义上增加了一点"。也就是说，代码产出涨了八倍，测试涨了十倍，人头基本没动。

这三件事叠加起来，结果就是 CI 作业量在六个月内涨了二十五倍。注意，二十五倍不是测试执行量涨了二十五倍，因为不是每个测试都会在每次 PR 上跑，这正是测试选择服务的作用。但即便被过滤过一轮，作业量还是涨了二十五倍。

作者还讲了一个很关键的观察：Claude 偏爱更小、更细粒度的 PR。这跟人类习惯不太一样，人类喜欢攒一个大改动一次提交。Claude 的做法是拆成很多小改动。这本身是好事，审查更容易、回滚更精准。但它带来了一个副作用：一天之内的 PR 数量变多了，CI 作业的触发次数也就变多了。再加上 agent 会在夜里、在周末持续推送代码，整个 CI 的"活动底线"被抬高了，可是它依然是突发性的，因为人类工程师仍然驱动和批准着相当一部分 PR。你可以想象，一条本来就有波峰的曲线，整体被抬高，波峰还变得更密集，这对一个单点服务的压力是灾难性的。

这里还有一个我觉得特别值得所有做 AI 工具链的人记住的点。文章说，人类特别擅长判断某个测试失败跟自己有没有关系。你看到一条红灯，扫一眼报错，心想"这是隔壁团队的缓存测试，跟我改的这个文案没关系"，然后在心里把它忽略掉。但 agent 不擅长这个。agent 需要更多上下文和明确的指示。如果你给它一组具体的、有效的测试，它就能自我验证、快速迭代；如果你给它一坨真假难辨的失败，它就懵了。

所以测试选择服务在 agent 时代不只是性能优化。它是 agent 能不能自主闭环的关键基础设施。这是文章里一个很容易被忽略、但分量很重的判断。

好，现在我们进入正题：这个服务原来的架构长什么样，为什么会崩。

文章说，这个服务依赖两个确定性组件保持同步。第一个叫 listener，监听器，它负责记录每一次 CI 运行产生的测试结果。第二个叫 selector，选择器，它读取测试结果的历史，决定某个 PR 应该跑哪些测试。

这套设计本身是有效的。问题在于，当每秒有大量 CI 作业在跑的时候，listener 会越来越跟不上 PR 队列。这里作者给了一个非常具体的换算：listener 落后二十分钟，就意味着有几万条测试更新没有应用到 selector 上。

你可能会问，落后二十分钟很严重吗？在传统的开发节奏里，二十分钟可能就是喝杯咖啡的事。但在一个 AI 原生的软件生命周期里，小延迟会引发大问题。作者列了三种后果，我一个一个展开讲。

第一种，如果一个坏改动被合并了，那么某个测试会开始对所有人失败，导致多起不必要的排查。你想象一下，一个真正能抓到 bug 的测试，因为没有及时更新，被选择器漏掉了，那个 bug 就溜进了主干。接下来的一两个小时里，五六个工程师分别被同一条红灯卡住，每个人都花二十分钟去查，最后发现是同一个原因。这就是延迟的代价。

第二种，如果某个依赖开始变得不稳定，也就是大家常说的 flaky，那些不稳定的红灯就会开始阻塞合并。flaky 测试是工程团队的慢性病，它时好时坏，你很难判断是真 bug 还是随机失败。如果 listener 没跟上，选择器就不知道这个测试最近已经变得不可靠了，于是继续把它当作阻塞条件，整个团队的合并全被卡死。

第三种，如果一个测试被修复了，或者新增了一个测试，那在 listener 追上之前，它根本不会跑，这就埋下了回归的风险。你刚修好的 bug，下一秒可能又被别人改回去了，因为你新加的那条防护测试还没进入选择器的视野。

这三种后果，本质上都是同一件事：这个服务的状态过期了，而它的每一个决策都建立在这个状态上。

那为什么它这么难扩展呢？文章给了一个非常关键的解释。因为要维护每个测试的运行历史，就必须有一个单一写入者来按顺序应用结果。整个系统是一个单进程。你可以理解为，一个账本只有一个记账员，所有流水都得从他手里过一遍，才能保证顺序正确。这就从根上挡住了水平分片。你没法简单地说，来，我们开四台机器分担一下吧，不行，因为四台机器会写出四个互相矛盾的账本。

到去年十月，这个服务已经明显吃不消了，他们连续两天被叫去处理告警。

好，接下来就是文章最精彩的部分，三次打补丁的过程。我把它当作一个"半吊子方案代价递增"的案例来拆。

第一次修复很简单，把跑这个服务的 CPU 核心数翻倍。买更大的机器。这个办法立竿见影，撑了七十天。而且作者说，他们当时就知道这只是缓兵之计。

这里有一个非常真实的组织问题被点了出来：归属不清。没有人愿意再多拥有一块基础设施。同时 CI 团队手上有更大的事要忙。这句话翻译成大白话就是，这个服务是谁的？没人说得清。于是它就一直带着病往下跑。

为了推动长期修复，作者做了一件很有意思的事。他在内部版本的 Claude Tag 里开了一个长期会话，专门用来监控这个服务。什么叫长期会话？就是它会记住之前的上下文，不用你每次重新交代一遍。每当 listener 落后超过五万个作业，Claude 就会 ping 他，然后接着之前的对话继续讨论下一步怎么办。

这个会话持续了好几个月。作者说，这很有帮助，因为他不用反复提醒它过去的努力和上下文。Claude 经常主张来一次大重构，但大多数时候，他们还是选择了再打一个补丁。

我觉得这段描述特别真实。它其实揭示了一个很微妙的人机协作模式：AI 的建议是对的，人类的执行是保守的，双方都没有错，但结果是问题被拖延了。你如果处在那个位置，大概也会做同样的选择，因为重构听起来很吓人，补丁听起来更安全。

到了二月，指数增长又一次把服务压到极限。这次他们决定并行化。

这里有个技术细节值得讲清楚。listener 不需要一个全局的单一写入者，它真正需要的是，每个代码包有一个单一写入者，来保证这个包内测试结果的顺序正确。文章说，Claude 帮他们生成了代码，把每个包的状态切分到一个分片，每个分片有自己的 worker。

打个比方，原来的账本是一个人记所有部门的所有流水，现在改成每个部门一个记账员，各记各的。只要部门之间的账不需要严格排序，这个方案就成立。

这又是一次"明知短暂"的修复。但他们没料到的是，它只买了二十九天。

到三月，这个进程在工作日下午就会撞到内存上限。这次他们又去找快速修复，但这次运气很差。作者列了几件令人沮丧的事。第一，只找到四个 bug，都不足以解释问题。第二，试着换内存分配器作为权宜之计，完全没用。他们本来想优化的是垃圾回收，结果发现那根本不是症结。第三，他们不敢对这样一个已经处于高负载的单例做内存剖析，怕把它直接压垮。第四，重启服务，只买到不到一天的时间。

请你注意这一步的处境。前面两次，至少有明确的杠杆可以拉，加核心数、做分片。到了第三次，所有的杠杆都失效了，你面对的是一堵你看不见的墙。这是工程实践里最难受的时刻。

更糟的是，他们还发现每日重启导致服务逐渐越落越远。当落后超过一个小时，而且这种情况发生好几次的时候，大量作业结果根本没被 listener 记录下来。

这个后果要澄清一下，因为很容易被误读。它不代表那些 PR 上 CI 没跑，也不代表未经测试的代码被推上了生产。它真正意味着的是，listener 漏掉了一些结果，于是测试选择组件在用过期数据决定哪些测试该跑、哪些不该跑。绝大多数情况下，这会导致他们跑了一些本来就很不稳定、或者大范围失败的测试。也就是说，浪费算力，浪费时间，也浪费信任。

这就是打补丁的终局：你打的每一个补丁，都在给下一个问题埋雷。

好，现在讲最终方案。他们终于采纳了 Claude 的建议，给测试选择服务配了一个数据库，准确地说是一个内存数据存储。

这个改动的本质是什么？是把原来那个单例进程承担的大块内存计算，卸载出去。

具体来说，现在任何一个 listener worker 都可以处理任何一条结果，把它追加到一个 journal 里，也就是一个日志流水，然后就可以走人了，什么都不用留在内存里。这正是"无状态"的含义，而只有无状态，才能水平扩展。然后有一个独立的、很小的 consumer 进程，每隔几秒把 journal 汇总成每个测试的历史，selector 就可以快速查询到相关的历史。

我打一个比方帮你记住这个架构。原来的做法是，一个会计坐在办公室里，手里拿着总账本，每来一笔流水他都要立刻算进总账，所以他必须一个人干，而且必须记得住所有细节。新的做法是，前台只负责把每笔流水写进流水簿，谁来都能写，写完就下班。然后每隔几秒，有个专门的会计把流水簿上的内容规整进总账。前台不需要记住任何东西，所以他可以有一百个。

文章说得很坦率，这个分布式架构运行成本更高，但扩展起来容易得多，做内存剖析也容易得多。整个项目一个工程师花了三周。同样的项目在一年前，大概要花一个季度。

上线之后还有一些微调，比如 journal 的大小、worker 的数量，这些 Claude 基本上自主完成了。从那之后，服务一直保持稳定。

到这儿，核心故事讲完了，但文章真正的精华在后面，作者说，如果把他送回二〇二五年十月，他会用现在知道的东西，做出不同的决策。

第一条建议，也是最重要的：为 AI 的指数增长做规划。CI 作业量会随着每位工程师平均 agent 数量的上升、以及 PR 审批加速的成熟，呈现指数增长。

这句话背后是一个心态转变。过去我们做容量规划，习惯按"现在的量乘以三到五倍"来留余量。但作者的建议是，不管你自建还是采购，都假设你的架构在两个季度内会承受二十五倍的负载。

他接着给了一个很有意思的判断：过度工程这个概念正在慢慢淡出，或者说，门槛被抬得很高了。因为你现在的第零版设计，可以开始考虑十到二十倍的感知规模，只要你的预算允许。

我个人认为，这句话需要谨慎解读。它不是让你无脑地把所有东西都做成分布式。它真正的意思是，过去那种"先写个简单版本，等撞墙了再说"的迭代方式，在指数增长的场景里会失效，因为你根本来不及反应。你会像 Anthropic 那样，七十天、二十九天、不到一天，被追着打。所以成本结构和以前不一样了，预防的性价比变高了。

但"十到二十倍余量"这个数字也不能当成教条。如果你的服务根本不在关键路径上，如果你面对的是线性增长，如果你团队只有三个人，那么提前二十倍扩容就是浪费。你要判断的是，你这个系统有没有可能被 agent 驱动到指数增长。如果是，那就提前设计；如果不是，就别跟风。

第二条建议：给你的服务装上可观测性，让它成为 Claude 的眼睛和耳朵。这样 Claude 就可以爬坡，也就是 hill-climb，一点一点地把问题改进，比我们手动做得好得多、快得多。

这里"爬坡"这个词很关键。它指的是一个反馈闭环：看到指标、做出小改动、观察效果、再调整。这种活人类做起来很痛苦，因为需要一直盯着，而且容易失去耐心。但 agent 最适合干这个。在 Anthropic 的案例里，那个长期会话会在 listener 落后超过五万作业时主动 ping 人，这本身就是把可观测性和 agent 结合起来的产物。

作者特别强调了一个必须保证的指标：进来的 CI 作业数要等于出去的。这句话听起来特别朴素，但它是这套系统最重要的一个守恒律。一旦进出不等，就说明有地方在积压。你应该把这个等式做成你监控面板上的第一行。

第三条建议：从一开始就把状态移出进程。别把状态留在进程内存里，因为你一旦留下状态，你就锁死了水平扩展的能力。我前面讲的那个账本比方，说的就是这件事。

第四条建议：避免把任何关键服务跑成单实例，除非你能测量它，并且能做金丝雀变更。金丝雀变更就是先放一小部分流量到新版本上，确认没问题再全量。

其实这四条建议可以浓缩成一句话：让每一层都无状态、可观测、可替换。因为 CI 演进得太快了，你没有别的路可走。

好，讲完了原文，我来聊聊这对我们实际工作的意义。我会尽量具体，让你的团队明天就能用上。

第一件事，先量测，再决策。文章里有一句话我印象很深，很多同行所在的组织仍然每次变更都跑所有测试。如果你也在这样的团队，我建议你先花一周做一次数据采集，计算三个数：一天之内 CI 作业的总量、过去三个月的环比增长率、以及单次全量测试的中位耗时。如果增长率超过百分之三十，那基本可以确定，你离 Anthropic 那个处境大概还有一到两个季度。这个判断比什么架构讨论都重要。

第二件事，把你所有的"单实例服务"列一个清单。这里说的单实例，不只是 physically 只有一台机器，还包括那种逻辑上只有一个写入者、只有一个队列消费者、只有一个调度器的设计。我敢打赌，你列出来的清单会比你想的长。然后对每一个问一个问题：如果它的负载在两个季度内涨二十五倍，会发生什么？如果答案是"会崩"，那它就值得进你的改造清单。

第三件事，针对测试选择这类服务，做一个进出的守恒监控。具体做法是：在入口埋一个计数器，记录进来了多少作业；在出口埋一个计数器，记录处理完了多少。两者的差值就是积压量。不要让这个差值沉默地增长。Anthropic 的教训就是，等到落后一个小时才被发现，几万条数据就丢了。

第四件事，关于要不要自己做测试影响分析。文章提到，这个领域有一类厂商在做相关产品。所以对大多数团队来说，采购是合理的。但我要提醒的是，不管你是买还是自建，那个二十五倍的容量假设都适用。你在选型的时候，一定要问供应商一个很直白的问题：当我们的 PR 数量在六个月内涨十倍，你的架构怎么扩展？如果对方只能回答"我们会加机器"，那你就要警惕了，因为 Anthropic 的第一招就是加机器，撑了七十天。

第五件事，也是最容易被忽略的：把 agent 当成 CI 的一等消费者来设计。文章里说得很清楚，agent 需要具体的、有效的测试集合，才能自我验证和迭代。这意味着你的 CI 系统输出的不应该只是"红"或者"绿"，而应该是结构化的、能告诉 agent 该修哪儿的信息。如果你的团队正在引入编码 agent，这一条会直接决定 agent 能不能真正闭环，还是每走一步都要人来擦屁股。

第六件事，关于什么时候该重写而不是打补丁。Anthropic 的故事给了一个很实用的判据：如果你第三次为同一个服务做权宜修复，而且这次修复买来的时间比上一次短得多，那就别再打补丁了，开始准备重写。他们第一次买了七十天，第二次二十九天，第三次不到一天。这个递减曲线就是信号。

第七件事，我想讲一个不那么技术、但可能更重要的点。文章提到，这个服务归属不清，没人愿意多拥有一块基础设施。这是极其普遍的团队现象。而 Anthropic 的解法，是在内部 Claude Tag 里开一个长期会话，让 AI 持续盯着它，定期叫人。这其实是一种新的组织手段：当没有人愿意承担这块基础设施的归属时，用一个持续运行的 AI 会话来代替人的注意力，把问题保持在可见状态。我觉得这个做法值得很多团队抄。你不需要 Claude Tag，你需要的只是，让问题不会被组织的注意力盲区吞掉。

再说几个坑，你一定得避开。

第一个坑，把重启当成解决方案。文章显示，每日重启只买到不到一天，而且还导致服务逐渐越落越远。重启之所以看起来有效，是因为它清空了内存，但它不解决任何根本问题，而且会偷偷丢数据。如果你的监控面板上看不出重启造成的丢数，那你就处在一个非常危险的盲区里。

第二个坑，在没有观测的情况下就上 agent。作者说得很清楚，Claude 能爬坡、能增量修复，前提是他把服务仪表化，让 Claude 成为眼睛和耳朵。如果你什么都没埋点，就把 agent 放进去，它只能瞎猜，效果可能还不如人。

第三个坑，盲目追求大重构。文章原话说，他们前两次补丁是明知短暂也照打不误。这不是单纯的错误，这是一种权衡。重构的风险和成本是真实的，问题只在于你有没有在正确的时机止损。所以正确的态度不是"永远重构"，而是"知道自己在拖，并且设好触发条件"。比如，当兼容方案买来的时间少于三十天，就启动重写。

第四个坑，把二十五倍当成精确预测。它是作者基于 Anthropic 自己的数据给出的经验值，你的团队不一定是这个数。你要做的是理解这个数量级的思维，而不是照抄这个数字。

好，我们来收个尾。

这篇文章讲的是一个非常窄的技术问题，Anthropic 内部一个测试选择服务怎么扩容。但它真正在说的事是，当代码的生产和审查都被 AI 加速之后，整条工程流水线上最慢的那一环会被迅速放大成瓶颈。Anthropic 遇到的瓶颈是测试影响分析，你的团队遇到的可能是构建缓存、可能是制品仓库、可能是代码搜索、可能是代码评审本身。位置不同，但结构是一样的。

作者最硬的那句话，我想再复述一遍：这些扩容技巧能买到的时间，只有一年前的零头；而彻底重构一个服务的成本，也只有一年前的零头。这个非对称意味着，拖延的代价变高了，而提前设计的代价变低了。过去我们习惯用"先跑起来，以后再优化"来换取速度，现在这个交易的汇率已经变了。

我个人认为，这篇文章最值得记住的不是那个内存数据存储，也不是 journal 和 consumer 的分工。那些都是具体解法。真正值得带走的是那个提问方式：假设你的系统在两个季度内要承受二十五倍负载，你的架构会长什么样？如果你现在就能回答这个问题，你大概就能避开 Anthropic 花了大半年、被叫醒无数次才学到的那一课。今天就聊到这里，我们下期见。
