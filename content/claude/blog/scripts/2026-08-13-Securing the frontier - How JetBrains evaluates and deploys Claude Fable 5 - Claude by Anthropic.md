这篇文章的形式是一段访谈，Anthropic 采访了 JetBrains 的 CTO，Vladislav Tankov。文章并不是一篇论文，也没有展开非常细的实验协议，所以我们今天不是把它当成模型排行榜来读，而是把它当成一份前沿模型进入大型软件公司的部署手册来看。它真正有价值的地方，是把几个平时容易混在一起的问题拆开了。一个问题是，模型 benchmark 跑分好，不等于在你自己的代码库里好用。第二个问题是，每个 token 价格贵，不等于每个任务成本贵。第三个问题是，模型越强，既能帮你找漏洞，也会让外部攻击者更容易找你的漏洞。第四个问题是，未来 IDE 可能不再只是写代码的窗口，而会变成开发者和 agent 一起工作的驾驶舱。

我们先说背景。JetBrains 的 CTO 在访谈开头说，他在 JetBrains 已经十年，他们是最早的一批大语言模型供应商客户之一。过去一年，他们经历了一个很明显的变化，就是公司内部和客户中的 AI 怀疑者，基本都承认 AI 会长期存在。他用了一个很重的说法，叫这是技术行业里一个巨大而基础的变化，公司里几乎每个怀疑者都改变了看法。

这句话对我们很有意思。因为在二〇二三年到二〇二四年，很多工程团队讨论 AI 编程时，常见观点是，它可以补全样板代码，可以写单元测试，可以问问文档，但真正复杂的工程工作还是不行。到二〇二六年，JetBrains 这样的工具公司给出的反馈已经不是要不要 AI，而是如何评估、如何部署、如何治理。这个语气变化本身就说明，行业焦点从概念验证转向生产化了。以前大家问的是，这东西能不能写代码。现在问的是，在我的私有仓库里能不能修 bug，能不能少走弯路，能不能通过测试，能不能不泄露数据，能不能在合规行业用。

如果你在一个企业研发团队里，这个变化应该很熟悉。最开始团队可能让大家试试 AI 插件，看看补全体验。过一阵子，大家开始问能不能接入代码库，能不能读工单，能不能自动改测试。再往后，问题就会变成预算、审计、权限、数据留存、模型选择、失败兜底。AI 编程从一个个人效率工具，慢慢变成组织级工程系统。JetBrains 这篇访谈正好给了一个大型开发工具公司在这个阶段的思考切面。

接下来我们看第一个核心点，JetBrains 怎么评估新模型。文章里说得很直接，因为 JetBrains 是一家编码公司，所以他们有一条很大的 evaluation pipeline，也就是评测流水线。他们用大型评测集，并且这些评测集来自私有代码仓库，包括他们自己的 monorepo，也就是把很多项目集中在一起管理的大型单体代码仓库。

这里最重要的不是评测这个词，而是私有代码仓库这几个字。我们平时看模型能力，容易看公开 benchmark，比如代码题、算法题、开源项目修复题。但公开 benchmark 有一个天然问题，模型供应商可能会围绕这些题调优，甚至模型在预训练或后训练过程中见过相似材料。JetBrains 的 CTO 说，有些模型被调到在公开 benchmark 上得分很高，但在实际任务上会掉下来。用私有仓库评测，就更容易检查模型是不是真的会干活。

这对工程团队特别关键。想象你在公司里选一个 coding agent，如果只看官网跑分，很像只看一个程序员的简历。简历上写熟悉 Java，熟悉微服务，熟悉 Kubernetes，看起来不错。但你真正要知道的是，他能不能读懂你们公司十年历史的代码，能不能理解那些没人敢动的配置，能不能在一堆历史包袱里改出一个不破坏线上行为的小变更。公开题更像考试，私有仓库任务更像入职后的真实工作。JetBrains 做的就是把模型放到真实工作台上，而不是只看考试成绩。

文章还提到，他们维护不同维度的排行榜，包括最佳质量、每个任务的最佳成本，以及最快模型。这一点非常务实。很多团队选模型会陷入一个单指标思维。比如谁最聪明就用谁，或者谁最便宜就用谁，或者谁响应最快就用谁。但在真实工程里，不同任务对模型的要求不一样。一个简单的补全任务，用户等不了太久，也没有必要用最贵的模型。一个复杂重构任务，可能宁可多等几分钟，也希望它少犯错。一个批量生成文档的任务，成本可能最重要。一个安全审计任务，准确和覆盖可能最重要。

所以 JetBrains 的做法更像是在建立模型路由系统。这个任务要速度，就看最快模型。这个任务要质量，就看最佳质量。这个任务要综合经济性，就看每个任务成本。注意，文章这里特别强调 Claude Fable 五虽然每个 token 更贵，但在一些情况下，尤其是复杂、长时间运行的工作里，每个任务成本反而更低。token 可以理解为模型处理文本的基本单位，也是常见的计费单位。每个 token 贵，不等于最后账单一定贵，因为一个更强的模型可能更快到达答案，需要更少轮尝试，更少上下文消耗，也需要更少人工返工。

我个人认为，这是很多团队最容易算错的一笔账。比如你让一个便宜模型修一个复杂 bug，它试了十轮，每轮都读一大段代码，最后还要人工工程师花半天收拾烂摊子。另一个贵模型三轮修好，并且测试通过。你如果只看模型账单，可能觉得前者便宜。但如果把工程师时间、等待时间、错误回滚、审查成本算进去，后者可能更便宜。JetBrains 文章里的每个任务成本，就是在提醒大家，AI 落地不能只按 token 单价做采购决策。

第二个核心点，是 Claude Fable 五在 JetBrains 评测里的表现。文章给了几个数字。Claude Fable 五在他们的 Python 评测套件里取得了最好的通过率，百分之四十四点三。对比 Opus 四点八的百分之二十八点二，提升了十六个百分点。在头对头比较里，Claude Fable 五解决了十八个 Opus 四点八没有解决的 Python 任务，只输掉了两个。

这组数字听起来就是模型更强，但我们要仔细听后面的解释。JetBrains 特别强调，Claude Fable 五的答案更值得信任。文章说，当它生成的代码能够运行时，它通过测试的频率远高于任意一个 Opus 模型。这很关键，因为能运行但结果错误的代码，是最昂贵的失败类型之一。

为什么这类失败特别贵呢。我们拿一个普通后端服务举例。代码完全跑不起来，编译失败，测试启动不了，这种失败虽然烦，但很显眼。CI 会红，IDE 会报错，工程师一眼知道不能合。真正危险的是，代码能编译，服务能启动，测试覆盖不到的边界条件却错了。比如金额计算少处理了一个舍入规则，权限判断在某个组合条件下放宽了，缓存失效逻辑漏了一个分支。这样的错误会给人一种我已经完成了的错觉，进入代码评审时也更难发现。JetBrains 说代码能跑但给错答案最贵，背后就是这个工程现实。

这对 AI 编程尤其重要。很多模型生成的代码看起来非常像那么回事，命名规范，结构完整，甚至注释写得很好。作为人类审查者，我们很容易被这种流畅性麻痹。模型的自然语言表达越自信，代码风格越像资深工程师，错误就越隐蔽。所以在评测模型时，只看它有没有输出，或者有没有通过语法检查，远远不够。你要看它在可运行情况下通过测试的比例，看它是不是会产生那种表面正常、内里错误的结果。

文章还讲了效率。Claude Fable 五比 Opus 四点八大约少用了百分之二十二的步骤就能到达解法，所以它用更少的试错拿到可工作的代码。这里的步骤可以理解为 agent 在执行任务时的行动次数，比如读文件、修改文件、运行测试、根据错误再修改。少百分之二十二不是一个小差异。对于本地开发者来说，可能意味着等待十分钟和等待八分钟的区别。对于大规模平台来说，可能意味着成千上万次任务的算力、API 调用和排队时间差异。

更有意思的是，JetBrains 说 Claude Fable 五把力气花在了正确的地方。文章举了 Java 任务的例子。Opus 四点八会反复尝试引入外部资源，而在 JetBrains 的环境里，这些外部资源几乎从不有帮助。Claude Fable 五则完全跳过这一步，直接处理眼前代码。JetBrains 认为这体现了更好的工程习惯。

这句话很值得软件工程师咂摸。我们平时说一个工程师成熟，不只是说他懂很多算法，而是说他知道什么时候不该做什么。面对一个代码库里的 bug，新手可能第一反应是搜索全网、升级依赖、引入一个新库、重写一大块。老工程师往往会先看现有上下文，看测试，看调用链，尽量在局部做最小改动。因为他知道工程环境有约束，不能随便拉东西，不能随便动架构，不能把一个简单修复变成一次冒险。JetBrains 对 Claude Fable 五的评价，实际上就是它更像一个知道工程边界的合作者，而不是只会展示能力的答题机器。

第三个核心点，是 JetBrains 什么时候用 Claude Fable 五，而不是其他模型。文章里有一句很形象的话，Opus 被看作 workhorse，也就是干活很稳的主力马。你可以很确定它会把工作做完。而当你真的需要好的推理能力，几乎需要一个伙伴，并且你自己也不确定该怎么做的时候，你会去用 Claude Fable 五。

这个定位非常重要。它不是说 Claude Fable 五替代所有模型，也不是说越强越要全场景使用。它更像团队里那个你遇到难题时会拉过来一起看的人。普通任务可以交给稳定模型，高频任务可以交给更便宜或更快的模型。但当问题模糊、路径不明确、需要探索和判断时，就需要更强推理模型。

文章举了一个例子。JetBrains 的一个技术负责人决定实现一个富文本编辑器组件。这个组件他们过去几年尝试过几次。富文本编辑器不是简单表单，它通常涉及光标、选区、样式嵌套、撤销重做、复制粘贴、输入法、不同平台行为，很多细节会互相影响。文章说，Claude Fable 五几乎 one shot 完成了，也就是接近一次性做出来。当然我们要注意，文章没有给出这个组件的完整复杂度，也没有说完全无需人工审查，所以不能把它理解成模型神奇地独立替代团队。但这个例子说明，JetBrains 看到的是在多年未完成或多次尝试的复杂组件上，模型可以成为真正的突破助手。

另一个重要用例是长时间运行的 agentic coding 实验。agentic coding 可以理解为让 AI 代理不只是回答问题，而是围绕软件开发目标持续行动。JetBrains 会给一个运行 Claude Fable 五的 agent 提供规格说明，规格说明可以是文本，也可以是图片，然后让它实现复杂的、类似 IDE 的应用。更有意思的是，规格说明本身也可以由 agent 根据已有应用生成。把这两个组件连起来，就可以在一种近似黑盒的设置下，把一个应用从一个运行时、框架或语言改写到另一个运行时、框架或语言。

这里我们停一下，因为这段很有未来感。传统迁移项目非常痛苦。比如一个老桌面应用要迁移到新框架，或者一个内部工具要从一种语言迁到另一种语言。你需要先理解旧系统做了什么，再写规格，再实现新系统，再对齐行为。JetBrains 描述的思路是，先让 agent 从现有应用中提取规格，也就是把旧系统的行为和界面尽可能总结出来，再让另一个 agent 或同一个流程根据规格实现新应用。因为输入可以包括文本和图片，所以它不只是读代码，也可能理解界面外观和交互意图。文章说这是一种 nearly black box，也就是近似黑盒的方法。意思是它不一定需要人类把旧系统所有内部逻辑逐行解释清楚，而是通过观察和抽取规格来迁移。

我个人认为，这个方向可能会深刻改变开发工具公司的产品边界。过去 IDE 主要帮助你写当前语言的当前项目，最多做重构、导航、补全。agent 时代的 IDE 可能会帮你做跨技术栈迁移、老系统现代化、原型还原、需求到实现闭环。比如产品经理给一组截图和说明，agent 生成一个可运行原型。再比如团队把一个 Swing 老工具迁到 Web 前端，agent 先识别功能，再生成规格，再实现新版本，再用测试和人工审查对齐行为。这些在今天还不能理解为完全自动化交付，但已经足够让工具形态发生变化。

第四个核心点，是安全和数据留存。这个部分对企业听众尤其重要。JetBrains 的 CTO 说，他们不是一家试图自己创造最安全模型的公司。他们期待 Anthropic 侧完成的 red teaming，也就是红队测试，以及其他安全工作，足以让他们相信模型是安全的。然后 JetBrains 自己采取系统化部署方法，在模型和 harness，也就是调用模型的执行框架周围创建基础设施和安全网，而不是去微调模型本身。

这句话很现实。大多数企业没有能力从底层训练或改造前沿模型，也不应该幻想靠几条 prompt 就解决所有安全问题。更可行的是，承认模型是一个强大的外部智能组件，然后在它周围建立权限、沙箱、审计、监控、回滚、分类器、人工审核等一整套系统。换成工程语言，就是不要只问模型本身安不安全，要问你的部署拓扑安不安全。它能读哪些文件，能不能访问生产密钥，能不能发网络请求，能不能提交代码，谁批准，日志保存多久，异常行为怎么拦截，严重事件谁复盘。

文章还说，安全本身也是 JetBrains 使用 Claude Fable 五的最大场景之一。他们对自己的产品做白盒测试来寻找漏洞。白盒测试就是测试者可以看到内部实现、源代码和结构，不是只从外部黑盒试探。JetBrains 的安全团队也在为一个现实做准备，那就是不只是他们自己会运行 Claude Fable 五，公司外部的人也会运行 Claude Fable 五或类似级别的模型，去探测 JetBrains 所有产品里的漏洞。因为 JetBrains 服务很多受监管行业的大企业客户，所以他们必须提前准备。文章的表述是，Claude Fable 五支持了他们的安全工作，而不是阻碍他们。

这里有一个很微妙的平衡。JetBrains 的 CTO 说，分类器越不激进，就越可能有人在他们的产品里找到漏洞，包括没人知道的漏洞。这里的分类器，可以理解为判断请求是否危险、是否应该拦截的安全过滤系统。对 Anthropic 这样的模型供应商来说，如果分类器太宽松，模型可能帮用户写攻击代码或利用漏洞。如果分类器太严格，企业安全团队做合法防御测试时又会被挡住。JetBrains 的立场很清楚，他们需要模型帮助自己发现真实漏洞，因为攻击者也会用同级别模型。如果防守方因为过滤过严而不能测试，反而是不安全。

这个问题对国内企业也一样。假设你是一家做 SaaS 的公司，你的安全团队想用前沿模型审计自己的 API 权限漏洞。如果模型一看到漏洞利用、请求伪造、越权测试就拒绝，那防守价值会大打折扣。但如果模型完全不管，它又可能帮助恶意用户。正确做法不是简单地喊放开或封死，而是建立身份、场景、权限和审计。企业安全团队在受控环境里做白盒测试，和匿名用户要求生成攻击步骤，不应该被同样处理。文章没有展开这些机制，但它点出了这个张力。

数据留存也讲得很坦诚。JetBrains 的 CTO 说，毫无秘密，他们更希望零数据留存。但是他也说，他看不到还有什么其他办法让模型供应商理解用户问了什么，以及分类器可能在哪里工作不正确。只要审查仅用于调查被标记出的最严重情况，他可以接受。他认为这是一个公平交易，换取前沿智能，让他的团队做出最好的工作。

这段话可能会让很多工程师有共鸣。企业客户理想上当然希望自己的代码、问题、日志都不被保留。但是安全系统要改进，误拒绝要排查，严重滥用要调查，又需要一定的留痕。这里没有完美答案，只有边界和信任。关键是数据留存的范围、时长、用途、访问权限和审查条件要清晰。JetBrains 在文章里的态度不是无条件接受，而是说如果审查只用于最严重标记案例的调查，他认为可以接受。

我个人认为，这里可以给企业团队一个实操提醒。你在采购或接入任何前沿模型时，不要只问一句会不会训练我的数据。还要问数据是否留存，留存多久，哪些内容会被留存，谁能看，什么条件下看，是否有企业级零留存选项，安全事件如何通知，日志如何脱敏，合规团队如何审计。对于代码工具尤其如此，因为开发者的输入里可能包含源代码、错误日志、客户字段、内部路径、配置名称，甚至偶尔包含密钥。前沿模型能带来效率，也会放大数据治理的短板。

最后我们看 JetBrains 对 AI 路线图的判断。文章结尾说，他们预期大语言模型供应商构建的底层模型会继续变强。现在重要的是一种软件开发 cockpit，也就是驾驶舱。这个驾驶舱是一个空间，agent 和人可以在里面协作，人可以管理开发过程。JetBrains 认为这是一次大转型，他们有机会围绕 agentic software development lifecycle，也就是代理式软件开发生命周期，构建下一代产品。开发者会在 agent 的帮助下交付更多、更好的代码，非技术角色会在软件创造中扮演更大角色，组织也会得到所需的治理能力和投资回报清晰度。

驾驶舱这个比喻很好。以前 IDE 像工作台，代码编辑器是中心，工程师亲手敲代码，工具负责提示、导航、编译、调试。后来 Copilot 类工具出现，IDE 变成有副驾驶的工作台，它在你旁边补几行、写个函数。再往后，agent 能自己读代码、改文件、跑测试、根据错误迭代，IDE 就不只是打字界面，而像一个任务调度和监督中心。你可能不是每一行都亲手写，而是在定义目标、分配任务、审查计划、查看差异、批准提交、监控风险。

这对软件工程师意味着什么呢。短期看，你应该开始把 AI 使用从聊天升级为流程。不要只是打开一个窗口问怎么写这个函数，而是想办法把模型接入可验证任务。比如给它一个明确的 bug、相关测试、预期行为，让它改完后跑测试。再比如让它在一个受控分支里做重构，要求每一步解释变更范围。你要把它放进工程反馈回路里，而不是让它在文本世界里自由发挥。JetBrains 的评测思路告诉我们，真实能力要在私有仓库、真实任务、自动测试和人工审查里看。

中期看，团队应该建立自己的模型评测集。这个评测集不一定一开始就很大，但要来自你们自己的代码和任务。可以收集过去真实发生过的 bug 修复、迁移任务、测试补齐、性能优化、文档生成需求。每个任务要有可判断结果，最好有测试，有期望 diff，有人工评分标准。然后你可以比较不同模型的质量、速度、成本和失败类型。文章里 JetBrains 做的是大型专业评测流水线，但普通团队也可以做一个小版本。只要你不再单纯相信公开排行榜，就已经前进了一大步。

再说模型选择。不要把所有任务都交给最强模型，也不要为了省钱把复杂任务都压给便宜模型。你可以把任务分层。简单补全、格式转换、文档初稿，可以用快而便宜的模型。明确的小修小补，可以用稳定的主力模型。需求模糊、跨模块推理、架构迁移、复杂调试、安全审计，就留给推理更强的模型。JetBrains 对 Opus 和 Claude Fable 五的区分，就是一个很好的参考。主力马负责可靠干活，强推理伙伴负责最难、最不确定的问题。

还要特别注意评测失败类型。不要只统计成功率，也要记录失败长什么样。有的模型失败得很明显，代码跑不起来。有的模型失败得很隐蔽，代码能跑但答案错。有的模型会乱引外部依赖，有的模型会过度重构，有的模型会编造不存在的 API，有的模型会在测试失败后反复撞墙。JetBrains 说 Claude Fable 五少走步骤，并且不去拉无用外部资源，这其实就是在评价模型的行为习惯。对团队来说，行为习惯和最终准确率一样重要。因为你要把模型放进长期工作流，不只是做一次演示。

在安全实践上，建议把 agent 当成一个有能力但需要管控的初级同事，而不是一个无害的自动补全。它能读什么、写什么、执行什么命令，都要有权限边界。让它操作代码可以，但最好在隔离分支。让它运行测试可以，但不要默认给生产凭证。让它访问网络要谨慎，尤其是企业内部环境。所有关键变更要有可审计日志，敏感操作要有人批准。文章里 JetBrains 说，他们关注的是围绕模型和执行框架的基础设施与安全网，这就是部署前沿模型最实在的工程方向。

对于安全团队，文章还有一个更积极的信号。不要只把前沿模型视为风险，也要把它作为防守工具。你可以用它做白盒代码审计，生成威胁模型，检查权限路径，辅助写安全测试，复盘历史漏洞，看类似漏洞是否在其他模块重复出现。与此同时，也要假设外部攻击者拥有同级别能力。过去一个低危的复杂漏洞，因为利用链很难构造，可能实际风险有限。现在有了强模型，发现和拼接漏洞的门槛可能下降。你的安全基线也要相应提高。

对产品和管理角色来说，JetBrains 提到非技术角色会在软件创造中扮演更大角色，这一点也值得提前准备。未来产品经理、设计师、运营人员可能不只是写需求给工程师，而是能用 agent 做可运行原型，生成规格，验证交互，再交给工程团队固化和治理。好处是创意到原型更快，坏处是如果没有治理，组织里会出现很多影子软件、影子自动化和不可维护脚本。所以 cockpit 不只是让大家都能生成代码，也要提供权限、版本、审查、成本和投资回报可见性。

我个人认为，JetBrains 这篇访谈最有启发的地方，不是某个具体数字，而是它呈现了一种成熟的 AI 工程观。第一，不迷信公开跑分，用私有真实任务评估。第二，不迷信 token 单价，用每个任务的总成本评估。第三，不把模型安全完全外包，也不试图自己改造底层模型，而是在部署层建立护栏。第四，不把 agent 当成玩具，而是围绕软件开发生命周期重构工具。

如果你今天在通勤路上听到这里，可以带走一个很实际的问题。你们团队现在有没有一套属于自己的 AI 编程评测任务。如果没有，下周就可以从十个真实 bug 开始。再问一个问题，你们现在用模型时，是按聊天窗口体验做判断，还是按通过测试、减少步骤、降低返工来做判断。如果还是前者，那就很容易被模型的流畅表达骗过去。最后再问一个问题，你们有没有把数据留存、权限边界、安全审计写进 AI 工具接入流程。如果没有，越早补越好。

总结一下，这篇文章讲的是 JetBrains 如何把 Claude Fable 五这样的前沿模型放进真实开发工具和企业环境。它看重的不只是聪明，而是真实代码库里的可用性、复杂任务里的成本效率、工程习惯、安全测试能力，以及围绕 agent 协作的新产品形态。我个人的点评是，前沿模型落地到软件工程，真正的竞争已经从谁会写几行代码，转向谁能把模型放进可信、可测、可治理的开发系统里。对于工程团队来说，这可能就是下一阶段最重要的基本功。
