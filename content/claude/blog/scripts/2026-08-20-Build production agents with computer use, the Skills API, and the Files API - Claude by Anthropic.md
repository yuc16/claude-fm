我们先把三个关键词说清楚。Computer use，中文可以理解为计算机使用能力，就是让 Claude 像坐在电脑前的人一样，看截图、点按钮、输入文字、滚动页面。Skills API，中文可以叫技能接口，就是把你们团队的操作说明、脚本、模板，打包成一个技能，需要的时候 Claude 再加载。Files API，中文可以叫文件接口，就是给 agent 一个文件存储层，让它可以读取你上传过的 PDF、表格，也可以把它生成的文件存起来，让你后面下载。文章说，这三项能力现在都在 Claude Platform 上正式可用。同时，computer use 还新增了一个 browser use tool，也就是浏览器使用工具，专门面向网页应用场景。

为什么值得我们这些软件工程师和 AI 从业者听？因为这不是一个单点模型能力的升级，而是在回答一个很实际的问题：如果我要把 agent 放到生产环境里，不是 demo，不是录屏，不是内部小玩具，而是真的跑业务流程，我需要什么基础设施？Anthropic 给出的答案，是三个层面同时补齐。第一层，让 agent 能操作现有软件。第二层，让 agent 能吸收组织自己的经验。第三层，让 agent 能管理输入输出文件。你会发现，这三个东西一合起来，就从一个聊天机器人，变成了一个可以进入业务系统、按流程办事、最后留下可追溯产物的自动化员工。

我们先看背景。传统软件自动化最喜欢什么？最喜欢稳定的 API、清晰的数据结构、可靠的事件流。你要自动处理订单，就调订单 API；你要查库存，就调库存 API；你要生成报表，就跑 SQL 或者调用后台服务。问题是，真实世界没有这么理想。很多企业内部系统是十年前甚至更早搭起来的，界面能用，API 没有，或者有 API 但权限申请很慢，字段文档也不全。还有大量 SaaS 系统、政府网站、保险门户、供应商后台，它们是给人操作的，不是给机器操作的。你想自动化，就只能用 RPA，也就是机器人流程自动化，靠模拟鼠标键盘和固定坐标来点。但传统 RPA 的痛点也很明显：页面稍微改版，按钮位置变了，脚本就坏；流程遇到异常，往往只能停下来等人工处理；如果需要理解文档内容，RPA 自己又不擅长。

大模型 agent 的出现，给这个问题带来了新思路。模型能看、能读、能推理，就有可能像人一样处理界面和文档。但早期的 computer use 也不是银弹。只靠截图和像素定位，就像让一个人隔着模糊摄像头远程操作电脑。他能看到页面大概长什么样，也能猜按钮在哪里，但如果网页布局复杂、弹窗遮挡、滚动区域很多，它就容易点偏。每次模型调用只做一个动作，也会导致流程很长，成本高，延迟大。比如填写一个表单，要点姓名框、输入姓名、点日期框、输入日期、滚动、点上传，每一步都要来回调用模型，那生产系统很难接受。Anthropic 这次正式可用时强调的改进，就是 computer use 更新后，Claude 可以在一个回合里采取多个动作，而不是每次模型调用只做一个动作。原文说，这会让任务用更少调用、更少时间完成。

这里我们可以打个比方。以前你让一个远程同事帮你填网页表单，你每次只能发一句指令：先点这里。等他点完，你再说：输入这个。再等他输入完，你又说：往下滚。现在变成你可以一次告诉他：打开这个页面，填好姓名、电话和地址，然后点下一步。中间如果他看得懂页面，就可以连续完成多个动作。对工程实现来说，这意味着 agent loop 的粒度变粗了。系统不需要每一个微动作都回到调度器，不需要不断等待模型响应，整个链路的时延和调用次数都有机会下降。文章没有给具体性能数字，所以我们不能替它编 benchmark，但方向很明确：多动作回合是把 computer use 从演示推向真实任务的关键一步。

再看 browser use tool。这个工具是今天这篇文章里非常重要的新内容。原文说，它属于 computer use 的一部分，面向网页应用。区别在于，除了截图之外，agent 还可以读取页面结构，并且作用在具体字段或按钮上，而不是只根据屏幕位置行动。这个改动很关键。只看像素，就像你在图片里找一个蓝色按钮；读取页面结构，就像你拿到了网页的骨架，知道这个输入框叫 email，这个按钮的文本是 submit，这个下拉框有几个选项。对网页自动化来说，这比单纯点坐标可靠得多。

如果你做过浏览器自动化，大概会想到 Playwright 或 Selenium。它们最稳的方式通常不是按坐标点，而是找选择器、找文本、找可访问性标签。browser use tool 的思路跟这个方向有相通之处，但它不是让你手写自动化脚本，而是让 Claude 在理解任务的同时，能利用页面结构来行动。比如页面上有两个“继续”按钮，一个在广告弹窗里，一个在主流程里。如果只看截图，模型可能点错；如果能读结构和上下文，就更有可能定位到正确的业务按钮。又比如表单里有“投保人姓名”和“被保险人姓名”两个字段，视觉上都差不多，靠坐标很危险，靠页面结构和标签会更稳。

这里要注意，原文没有说 browser use tool 可以解决所有网页自动化问题。它说的是，增加页面结构以后，agent 比只依赖像素更可靠。作为工程师我们应该把这句话听得很准确。更可靠不等于百分之百可靠。真实网页还有验证码、多因素认证、会话超时、动态组件、权限变化、反爬策略、弹窗和 A B 实验。browser use tool 降低的是“看不懂页面结构导致误操作”的风险，但生产环境里，你仍然需要设计权限边界、重试策略、人工接管和审计日志。我个人认为，这正是以后 agent 工程和传统自动化工程会融合的地方：模型负责理解意图和处理变化，工程系统负责约束动作、记录过程、兜底异常。

接下来我们看 Skills API。原文对 skill 的定义很具体：一个 skill 是一个文件夹，里面包含说明、脚本和模板。Claude 只在任务需要的时候加载它。用 Skills API，你可以上传并版本化自己的技能，然后把这些技能附加到任何请求里。它们运行在 Claude 的代码执行沙箱里，所以你不用自己托管。这几句话信息量很大。

先说“技能是文件夹”。这其实把 prompt 工程往软件工程方向推了一步。过去我们给模型知识，常见方式是把一大段提示词塞进 system prompt，或者在检索增强里把文档片段召回。这样做当然有用，但维护起来很容易混乱。今天财务流程改了，你去改一个长 prompt；明天法务模板更新，你再去改另一个 prompt；后天某个脚本换版本，没人知道线上到底用了哪版。Skills API 的思路是，把一类任务所需的东西打包：有文字说明，告诉 Claude 应该遵循什么流程；有脚本，用来处理结构化数据或生成文件；有模板，用来保证输出格式。这就更像一个可复用组件，而不是一段临时提示词。

再说“只在任务需要时加载”。这对大模型应用很重要。上下文窗口再大，也不应该把所有公司知识一股脑塞进去。你做理赔任务，不需要加载市场营销文案规范；你做销售报价，不需要加载客服退费流程。只在需要时加载技能，可以减少上下文污染，也可以让 Claude 更专注于当前任务。原文没有展开技能选择机制的细节，我们这里不猜具体实现，但从产品设计角度看，这意味着开发者可以把能力模块化，然后在请求里选择要附加的技能。比如一个“发票校验技能”、一个“季度报告生成技能”、一个“保险提交技能”，不同业务流按需组合。

版本化也很关键。生产环境里，最怕的是“昨天还好好的，今天输出变了，但没人知道为什么”。如果 skill 可以上传和版本管理，你就能把流程知识纳入发布管理。一个团队可以先在测试环境验证新版本技能，再切到生产；出了问题可以回滚；审计时可以回答，这个文件是用哪个版本的流程生成的。这听起来不像炫酷 AI，但它是生产级系统最需要的基础能力。对于企业 AI 应用来说，可复现、可回滚、可审计，往往比单次回答多聪明一点更重要。

文章还说，这些技能运行在 Claude 的 code execution sandbox，也就是代码执行沙箱里，所以开发者没有东西需要自己托管。这个点也值得展开。很多 agent 任务不只是语言生成，还需要跑代码。比如读一个 Excel，清洗数据，生成图表，套一个模板输出成文件。如果每个团队都要自己维护执行环境，就会面对依赖安装、权限隔离、资源限制、安全审计这些问题。Anthropic 把 skill 放进自己的代码执行沙箱，等于给开发者提供了一个托管执行层。当然，作为使用方你仍然要关心数据合规和权限范围，但至少从应用开发角度，不必为了一个技能再搭一套微服务。

然后是 Files API。原文说，Files API 是 agent 读写文档的存储。你可以上传一个 PDF 或电子表格一次，之后请求里用文件 ID 引用它，不需要反复重新发送；同时也可以下载 agent 创建的文件。正式可用以后，它还增加了自动文件过期、五倍更高的速率限制，以及每个组织一 TB 存储。这里我们也分开讲。

先说为什么需要文件层。很多 AI 应用早期做法是，每次调用模型时把文件内容重新传进去。小文件还行，大文件就麻烦了。第一，上传慢；第二，token 成本高；第三，调用链里到处复制数据，不好管理；第四，后续任务想复用同一个文件，还要重新传。Files API 的设计像是给 agent 加了一个工作盘。文件上传一次，平台保存起来，后面你只传文件 ID。模型要读的时候读，要写的时候写，最后生成的结果也变成一个可以下载的文件。对工程系统来说，这比“每次请求都夹带一堆附件”干净很多。

自动文件过期也很有现实意义。企业里很多文件有敏感信息，尤其是合同、病历、理赔材料、财务表格。你不希望临时处理文件永远留在平台上。自动过期可以帮助控制数据生命周期。原文没有说明具体过期策略怎么配置，我们不能展开到文档细节，但可以确定的是，正式可用版本把文件生命周期管理放到了能力清单里。五倍更高的速率限制和每组织一 TB 存储，则说明 Anthropic 在把这个 API 从试用型能力推向更高吞吐的生产使用。对真正的业务场景来说，文件数量和并发请求很快会上来，没有足够的 rate limit 和存储空间，agent 流程很容易卡在基础设施上。

现在我们把三个能力合起来看。原文给了一个理赔 agent 的例子。假设你在构建一个 claims agent，也就是理赔智能体。它从 Files API 读取报案或受理文档，按照一个 skill 里的团队申报流程执行，然后用 browser use tool 在保险公司的网页门户完成提交，最后把确认信息保存回一个文件。文章还补了一句，已经正式可用的 code execution 和 web search，也可以放进同一个循环里。

这个例子很典型，因为它覆盖了企业自动化最难的几段路。第一段是读材料。理赔材料可能是 PDF、表格、扫描件整理后的文档，里面有姓名、保单号、事故时间、金额、附件清单。Files API 负责让这些输入成为 agent 可以引用的对象。第二段是按流程判断。比如哪些字段必填，哪些文件要先命名，哪些情况要补充说明，提交前要做哪些校验。这些不是通用世界知识，而是团队经验，放在 skill 里。第三段是进入外部系统提交。保险公司的门户不一定给你 API，也不一定愿意为你定制集成，这时 browser use tool 让 Claude 像人一样操作网页，但又利用页面结构提高可靠性。第四段是产物归档。提交成功后，确认页、确认编号、回执文件，都要保存下来，Files API 又接住输出。这样一圈走完，才叫业务闭环。

你可以想象，如果没有这三件套，你会怎么做这个系统。你可能先写一个服务接收文件，把 PDF 解析出来；再写一堆 prompt 让模型抽字段；再用 RPA 或 Playwright 操作网页；再自己维护模板和脚本；再把输出文件存在 S3 或内部对象存储；还要设计任务状态、错误重试、版本管理。不是不能做，但集成成本高，而且模型、文件、技能、浏览器操作之间没有一个统一抽象。Anthropic 这篇文章的价值就在于，它把这些能力放在 Claude Platform 的同一个开发体验里。原文说，code execution 和 web search 也能放进同一个 loop，这说明它的目标不是某个孤立工具，而是一个 agent 运行时。

当然，我们也要保持清醒。文章说的是这些能力 generally available，正式可用，不代表你可以立刻把所有流程无人值守地交给它。生产级 agent 的关键，不只是模型能不能完成任务，而是出错时怎么处理，权限怎么限制，操作怎么审计，成本怎么控制，数据怎么合规。Anthropic 提到 computer use 现在也有资格用于 HIPAA 监管工作负载，前提是在它们的 BAA 下。这里的 HIPAA 是美国健康保险可携性与责任法案，BAA 是商业伙伴协议。这句话主要对医疗健康相关客户很重要，说明 computer use 的合规覆盖范围在扩大。但对中国听众来说，我们不应该简单把它等同于满足中国本地合规要求。你如果处理医疗、金融、政企数据，仍然要看自己的监管要求、数据出境、权限审计和供应商合同。

说到实践应用，工程师最关心的问题是：这对我明天的工作意味着什么？我觉得可以从三个方向思考。

第一，如果你们公司有大量“有界但繁琐”的网页后台操作，这类能力值得评估。所谓有界，是流程步骤相对明确，输入输出可定义，异常类型可枚举。比如根据客户资料在某个供应商后台创建账号，根据内部审批结果去外部门户提交申请，根据表格批量更新 CRM 字段，根据发票信息在财务系统里生成记录。这些任务过去要么靠人工，要么靠脆弱的 RPA。computer use 和 browser use tool 的组合，可能让 agent 更容易应对页面变化和文本理解。但不要一上来就选最复杂、最敏感、最不可逆的流程。更好的起点，是只读场景、草稿场景，或者操作后需要人工确认的场景。比如让 agent 填好表单但不提交，让人最后点确认；或者让 agent 生成提交包，人工上传。等成功率和审计机制稳定后，再逐步增加自动化程度。

第二，把团队知识做成 skill，而不是把一切都塞进 prompt。很多团队现在做 AI 应用，最大的问题是 prompt 越写越长，里面混着业务规则、输出格式、异常处理、示例、临时补丁。时间一长，没人敢改。Skills API 给了一个更工程化的方向。你可以把一个业务流程拆成技能包：说明文件写清楚步骤和边界，模板文件固定输出格式，脚本文件处理可确定的计算和转换。比如季度经营分析技能里，说明文件定义报告结构，模板规定标题和表格样式，脚本负责读取表格、计算环比同比、生成图表。Claude 负责理解任务、调用这些材料、补齐叙述。这样做的好处是，业务人员和工程人员可以围绕 skill 协作。业务人员审核流程文本和模板，工程人员维护脚本和版本，平台负责加载和执行。

第三，把文件当成一等公民来设计。不要把文件只看成“上传给模型的一坨附件”。在 agent 系统里，文件是输入、状态、证据和输出。输入文件要有来源和权限；中间文件可能是解析结果、临时表格、校验报告；输出文件可能要归档、下载、发送给客户。Files API 的文件 ID 模式，可以让你在任务链路中引用同一个文件，而不是到处复制。自动过期提醒我们，设计时就要考虑生命周期。哪些文件只保留一天，哪些要保留一个月，哪些必须进入公司自己的存档系统。每组织一 TB 存储听起来不少，但生产场景里，如果每天处理大量 PDF 和表格，也需要配额监控和清理策略。

我们再聊聊架构上可以怎么落地。假设你要做一个“供应商入驻审核 agent”。用户上传供应商资料包，包括营业执照 PDF、银行信息表、合规问卷。你的后端先把文件传到 Files API，拿到文件 ID。然后调用 Claude，请求里附加一个供应商审核 skill。这个 skill 里面包含审核步骤、字段校验规则、输出报告模板，也许还有一个脚本用来比对表格字段。Claude 读取文件，提取关键信息，生成一份审核草稿。如果需要去某个外部网站查询公开信息，web search 可以进入循环。如果需要登录内部网页后台录入审核结果，browser use tool 可以执行操作。最后，Claude 生成审核报告和操作回执，保存成文件，你的系统再把文件 ID 记录到自己的业务数据库里。整个过程中，你的应用不是简单地把 prompt 发给模型，而是在编排文件、技能、浏览器操作、代码执行和人工确认。

这里有几个坑需要提前避开。第一个坑是权限过大。既然 computer use 可以点击、输入、滚动，就一定要限制它能访问什么环境、能操作什么账号、能不能执行不可逆动作。不要给 agent 一个管理员账号，然后让它在生产后台自由行动。更合理的是使用最小权限账号，为不同任务准备不同权限范围，关键动作前增加确认。第二个坑是缺少观测。agent 的每一步都应该有日志，至少包括使用了哪些文件、哪个 skill 版本、访问了哪个页面、产生了什么输出、是否需要人工接管。否则出错后你只能看最终结果，很难复盘。第三个坑是把模型判断当成确定性程序。能用脚本确定的事情，就放在脚本里；需要格式稳定的输出，就用模板；需要业务规则一致，就写进 skill。Claude 很强，但生产系统要尽量把不确定性关在合适的位置。

第四个坑是忽视页面变化。browser use tool 因为能读页面结构，会比单纯像素点击可靠，但网页应用仍然会变。你需要对关键流程做持续测试。就像 API 集成要有契约测试，浏览器 agent 也应该有回归测试。比如每天在测试账号上跑一遍提交流程，看是否还能定位字段，是否出现新弹窗。第五个坑是文件安全。上传到 Files API 的文件可能包含敏感信息，所以要明确哪些数据允许进入平台，哪些需要脱敏，哪些必须留在私有环境。文章提到 Skills API 和 Files API 也可以通过 Microsoft Foundry 使用，更新后的 computer use 和 browser use tool 很快会来到 Google Cloud 的 Vertex AI。对很多企业来说，这意味着它们可以在自己已经采购和治理的云平台里接入这些能力。但具体合规边界仍然要看合同和部署方式，不能只看一句“可用”。

还有一个很值得注意的产品信号，是 Anthropic 说现有 beta 集成会继续工作，同时你可以迁移。这对开发者很重要。正式可用往往意味着 API 稳定性、支持承诺、限额和合规范围都进入一个新的阶段，但平台也知道已经有人在 beta 版本上做了集成，所以不会一刀切。对团队来说，如果你已经试过 computer use 或文件能力，现在应该做的不是马上重写，而是对照正式版能力做一次架构评审。哪些地方可以用多动作回合减少调用？哪些网页操作可以从像素定位迁到 browser use tool？哪些 prompt 可以沉淀成 skill？哪些重复上传文件的地方可以改成文件 ID 引用？这些都是很实际的迁移收益。

我个人认为，这篇文章最重要的不是“Claude 又多了几个 API”，而是它在定义生产级 agent 的基本形态。一个真正能上生产的 agent，不应该只是一个大模型加工具列表。它需要眼睛和手，可以操作软件；需要组织记忆，知道团队流程；需要工作空间，能管理文件；需要执行环境，能跑脚本；还需要搜索和外部信息能力，能补充上下文。Anthropic 正在把这些能力拼成一个平台化的 agent 运行时。未来开发者写 agent，可能会越来越像配置一个数字员工的工作台：它能打开哪些文件，掌握哪些技能，能访问哪些网页，能执行哪些代码，操作结果写到哪里，出错时找谁接管。

对中国的软件工程师和 AI 从业者来说，这也有启发。即使你暂时不用 Claude Platform，这套思路也值得借鉴。做企业 agent，不要只卷模型选型和提示词技巧，要把文件管理、技能版本、工具权限、网页自动化、审计日志一起设计。很多失败的 agent 项目，不是因为模型不会说，而是因为它没有稳定的工作流接口，没有可维护的业务知识封装，没有可靠的输入输出管理。你可以用别的平台、私有模型、内部 RPA、对象存储和脚本系统实现类似架构，但问题清单是一样的。

我们最后再回到原文。Anthropic 在二〇二六年八月二十日宣布，computer use、Skills API 和 Files API 在 Claude Platform 上正式可用。computer use 现在支持每个回合多个动作，并且在 BAA 下有资格处理 HIPAA 监管工作负载；新的 browser use tool 结合截图和页面结构，让网页操作更可靠；Skills API 让团队上传、版本化并复用自己的技能；Files API 提供文件读写存储，带来自动过期、更高限额和每组织一 TB 存储。它们合在一起，目标是让开发者构建能操作软件、应用团队经验、交付成品文件的生产级 agent。

我的点评是，这是一篇短公告，但指向的是 agent 工程的长期方向：从会聊天，到会办事；从一次性 prompt，到可版本化技能；从临时附件，到文件生命周期；从像素点击，到理解网页结构。真正的挑战会在生产落地里出现，包括可靠性、安全、合规和成本。但如果你正在做企业 AI 自动化，这篇文章给出的三件套，值得放进你的技术路线图里认真评估。
