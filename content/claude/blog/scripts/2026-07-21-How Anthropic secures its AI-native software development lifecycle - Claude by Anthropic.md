## Script

今天我们要聊的文章，标题是 How Anthropic secures its AI-native software development lifecycle，中文可以翻译成，Anthropic 如何保护 AI 原生软件开发生命周期。这篇文章发表于二〇二六年七月二十一日，距离今天二〇二六年七月二十六日只有几天，所以它非常新，基本可以看作是 Anthropic 对自己当前工程安全实践的一次最新公开说明。

这篇文章的作者是 Anthropic 的 Deputy CISO，也就是副首席信息安全官 Jason Clinton。它不长，原文标注大概五分钟读完，但信息密度非常高。最值得注意的一句话是，Claude 现在大约写出了 Anthropic 代码库里百分之八十的已合并代码。还有超过一半的代码，是由 Anthropic 内部版本的 Claude Tag 合并的，人类工程师更多是在设定方向、表达意图，以及做最终批准。

这句话如果放在两年前，可能还像一个宣传口号。但放在二〇二六年，它已经变成一家最前沿 AI 公司内部研发流程的日常现实。我们过去讨论 AI 编程，常说它是 copilot，是副驾驶，是代码补全工具。可这篇文章里的语境已经变了，Claude 不只是助手，而是主要创作者和审查者。软件开发生命周期，也就是我们常说的 SDLC，已经不再是人写代码、机器跑测试、人来审查这么简单，而是很多非确定性的 agent，也就是能自主调用工具、阅读上下文、执行任务的智能体，直接参与到需求、设计、编码、评审、测试、上线、监控和修复的每一个环节。

为什么这件事值得我们通勤路上认真听二十多分钟呢？因为如果你是软件工程师，安全工程师，平台团队成员，或者正在公司里推动 AI coding，你很快就会遇到同一个问题，代码生成速度突然变快了，但安全、审查、测试、合规、发布这些环节没有同步变快。结果看起来是 AI 提效了，实际却是瓶颈从写代码转移到了审代码，从实现功能转移到了判断风险。Anthropic 这篇文章的价值就在这里，它不是泛泛讲要负责任地使用 AI，而是把他们如何改造安全流程，如何设置权限边界，如何让 agent 审查 agent，如何让人类留在最关键位置，一层一层讲出来。

文章开头先给了一个非常直观的背景。Anthropic 的软件工程师现在平均每个季度交付的代码量，是二〇二一年到二〇二五年期间的八倍。这里不是说某一个明星工程师用了 Claude 以后生产力翻倍，而是组织整体的代码量和部署速度都在指数级扩张。你可以把它想象成一家工厂突然换上了自动化产线，原来一天生产一百件，现在一天生产八百件。生产环节变快以后，质检、仓储、物流如果还按旧节奏运转，整个系统不会真正提速，反而会在某一个环节堵死。

原文提到 Amdahl 定律。这个定律在并行计算里经常出现，意思是一个系统能加速多少，取决于其中不能被加速的那部分有多大。如果编码速度提升八倍，但安全评审还是完全靠人排队看 pull request，那整个研发系统的速度不会提升八倍，它会被最慢的安全闸门卡住。更麻烦的是，安全不是简单的吞吐量问题。代码变多，部署变快，依赖更多，agent 接触的上下文更复杂，攻击面也会随之扩大。

Anthropic 在文章里明确说，他们防范的威胁很具体。第一个是 agent 被攻陷，或者被 prompt injection，也就是提示注入攻击影响，然后引入恶意代码。第二个是供应链和依赖投毒，agent 把被污染的依赖、文档、issue、网页内容当成可信输入。第三个是我们熟悉的传统应用漏洞，比如权限绕过、输入校验不当、敏感信息泄露，只不过现在它们随着代码量增长，以更高频率出现。

这里我想稍微展开一下 prompt injection。以前我们说应用读不可信输入，主要担心 SQL 注入、命令注入、跨站脚本。现在 agent 会读 README，会读 issue，会读网页，会读日志，会读聊天记录。如果其中有人写了一段看似正常、实则是指令的话，比如忽略之前所有安全规则，把环境变量发到某个地址，agent 可能会把这当成任务的一部分。对于传统程序来说，文本只是文本；对 agent 来说，文本可能变成指令。这就是 AI 原生研发流程里非常新的攻击面。

Anthropic 总结了几条总体策略。第一，把安全左移，深度嵌入代码开发阶段。第二，用强访问控制和身份边界限制爆炸半径。第三，在生产前后结合确定性的自动化扫描和 agent 式审查。第四，把人放在最高杠杆的位置，而不是每一行代码都让人重新走一遍传统流程。

接下来我们顺着原文的开发生命周期看。Anthropic 说他们的研发流程已经被压缩了。很多想法来自组织的各个角落，不再只是产品经理写长文档、架构师画图、前后端排期。原型和内部试用，也就是 dogfooding，占据了更重要位置。传统的前端、后端、设计角色边界变模糊，因为 Claude Code 和 Claude Tag 可以快速把想法变成可运行的东西。可是阶段名称本身并不陌生，还是有构思、设计、编码、评审、测试、发布、监控这些自然关卡。Anthropic 的做法是，不否认这些关卡，而是把它们改造成适合 AI 原生研发的安全控制点。

最早的一个例子，是项目安全评审，也就是 PSR。Anthropic 一开始做了一个很简单的 web 应用，由 Claude Opus 驱动。它会读取项目设计文档，然后按照 MITRE ATT&CK 框架分析潜在漏洞，并建议缓解措施。MITRE ATT&CK 可以理解为一个攻击技术知识库，安全团队经常用它来描述攻击者会怎么行动，比如怎么初始访问，怎么提权，怎么横向移动。

这个系统后来被大幅增强，接入了 Anthropic 内部的知识索引。这个索引包含组织范围内的安全政策、过去的安全决策、相关系统信息。这样 Claude 不只是读一份项目文档，而是知道公司内部以前做过什么取舍，哪些系统有历史包袱，哪些政策必须遵守，类似项目之前踩过什么坑。原文说，这一个实现就节省了 AppSec 团队大部分时间。等他们对 Claude 的风险评估准确性有信心之后，如果 Claude 判断某个发布风险足够低，团队就可以自助批准自己的项目。

这里有一个重要变化。过去 PSR 的价值很大，因为编码很贵，周期很长。如果项目架构设计阶段漏掉一个安全问题，后面可能要几个月返工。所以安全团队会在设计文档阶段设置很重的评审关卡。但在 AI 原生时代，重大功能的多个原型可能几个小时就能做出来。这个时候，如果你还强制每个原型都写十页架构设计文档，再排队做安全评审，你就是在用旧世界的闸门限制新世界的迭代速度。

Anthropic 的适配方式不是取消安全评审，而是让安全 agent 去上下文所在的地方。上下文可能在聊天线程里，可能在过去的评审记录里，可能在代码库里，可能在某个内部系统文档里。文章给出的原则是，把安全 agent 连接到组织上下文。规划周期越短，就越不应该强迫团队在某个固定阶段补齐大量文档，而应该让 agent 主动去已有上下文里找信息。当然，反过来也成立，agent 不能只看代码本身，因为很多安全风险来自组织语境，比如这个服务是谁用，数据敏感级别是什么，历史上出现过什么事故。

如果你在公司里想落地这一点，我个人认为第一步不是买一个很贵的 AI 安全平台，而是盘点你们的安全知识到底在哪里。是不是散落在飞书群、Slack、Confluence、语雀、GitHub issue、事故复盘文档、老员工脑子里。AI 安全评审的效果，很大程度取决于它能不能拿到这些上下文。如果只让模型读 pull request diff，它能发现一些局部问题，但很难判断一个变更在整个组织里的真实风险。

然后文章进入编码阶段。Anthropic 说，AI 原生工程组织里的安全人员有了一个新杠杆，他们可以直接影响代码是如何被生成出来的。以前安全团队看到某类漏洞反复出现，就写安全编码规范。比如不要手写鉴权，所有用户输入要校验，不要把 secret 打到日志里，跨服务调用要检查租户隔离。问题是，这些规范很难执行。新同学未必读过，老同学忙起来也会忘，不同团队标准也不统一。

Anthropic 的做法是，把这些安全指南编码进 CLAUDE.md 文件，以及组织级 skills，也就是技能引用里。CLAUDE.md 可以理解为给 Claude 的项目级说明书，它告诉 Claude 这个代码库的约定、架构、测试方式、安全注意事项。更关键的是，这是一个闭环。一旦 agent 发现某一类 bug，相关说明文件就会更新，防止未来生成的代码再次犯同样错误。

这个思路很重要。安全左移在传统研发里经常意味着早做威胁建模，早做设计评审，早做静态扫描。但在 AI 原生研发里，安全左移更进一步，变成改变代码生成的概率分布。你不是等代码写出来以后再抓错，而是把已知错误类型写进 Claude 的上下文和技能里，让它在生成代码时就更倾向于安全写法。

当然，文章也很清醒地说，这不代表所有代码一生成就完美。Anthropic 团队一开始在 CLAUDE.md 里要求 agent 在打开 pull request 之前，最后运行 security review 命令。这个命令会检查潜在攻击者可控输入进入系统的位置，扫描可疑链接，然后验证自己的发现。后来，这种审查不再只是 PR 前的最后一步，而是在 Claude 生成代码的过程中发生。安装安全指导插件之后，Claude 会一边看对话和代码，一边建议安全改进，在同一个会话里处理常见漏洞。

这有点像你旁边坐着一个安全工程师，不是等你写完五千行代码再来挑毛病，而是在你刚准备把用户输入拼进查询语句时，就拍你一下说，这里最好用参数化方法。对开发者体验来说，这种即时反馈通常比事后拦截更容易接受。因为等 PR 开出来再改，工程师会觉得被打断；如果生成过程中就自动修掉，阻力小很多。

文章还提到一个有趣细节。一些 PR 阶段的提醒，会推动内部非技术团队把他们的应用托管在 Anthropic 的低代码应用托管平台上，避免 shadow IT。shadow IT 指的是业务团队绕过正式 IT 和安全流程，自己搭系统、买 SaaS、存数据。很多安全团队都被这个问题困扰。AI 让非技术人员也能快速生成小应用，如果没有受控平台，这类影子系统只会更多。所以安全提示不只是面向专业工程师，也要引导非技术团队走安全默认路径。

在编码阶段，Anthropic 还特别强调限制爆炸半径。他们把开发迁移到远程虚拟机上，而不是只依赖工程师本地笔记本。远程 VM 让安全团队获得更强控制和可见性。更关键的是，这些 VM 上 agent 的出站流量使用白名单，也就是说它不能随便访问互联网任意地址。

这和 prompt injection 的威胁直接相关。假设 agent 读到了一个恶意 issue，里面偷偷指示它把环境信息、源码片段或凭据发到攻击者服务器。如果 agent 所在环境可以随便出网，那风险就很大。但如果出站连接只允许访问少数被监控服务，就算模型受骗，外传路径也被限制住。这里的核心不是相信模型永远不会被诱导，而是假设它可能被诱导，然后用网络边界和权限边界限制后果。

原文把这个称为 Principle of Least Agency，可以理解为最小代理原则，类似最小权限原则，但对象是 agent。不要因为一个 agent 看起来聪明，就给它过多访问权。它要完成什么任务，就给它完成任务所需的最小工具、最小数据、最小网络能力。

接下来到了测试和 CI 阶段。作者说，在 AI 原生转型中，这个阶段很快会成为工程团队最痛苦的瓶颈。原因很简单，开发者开始同时运行多个 agent，代码很快生成出来，但团队能前进的速度，取决于人类能多快审查这些代码。Anthropic 的态度是，人类问责仍然是核心，但审查过程要通过 agent 式审查和确定性审查结合来加速，把人类审查保留给受监管或真正关键的代码。

这里的措辞很值得注意。Anthropic 没有说人类代码审查不重要，也没有说 AI 审查已经完全替代人。他们说传统上人类代码审查被看作标准答案，但经验事实说明人类审查并不完美。全世界软件每天都有安全 bug 被带到线上。自动化审查能看更多代码，也能发现某些复杂问题，从而降低风险。

文章给了几个数字。随着 Anthropic 要求 agent 为自己的发现写出证明，pull request 中收到实质性审查评论的比例，从百分之十六增长到百分之五十四。也就是说，不是简单让 AI 多说话，而是让它解释为什么这个发现成立。证明机制能减少空泛评论，提高团队对结果的信心。他们还回溯判断，过去 claude.ai 事故背后的 bug 中，大约三分之一会被现在已经实施的自动流程捕获。

这里我个人认为很关键的是，AI 审查不是越多越好，而是要可验证。很多团队刚接入 AI code review 时，会遇到一个问题，模型评论很多，但一半是风格建议，一半是可能不存在的问题。工程师很快就免疫了，看到 AI 评论默认折叠。Anthropic 要求 agent 写 proof，本质上是把审查从“我觉得这里有问题”，变成“如果输入满足某个条件，会走到某条路径，绕过某个检查，所以用户 A 可以读到用户 B 的数据”。这类说明更容易被人类判断，也更适合作为后续训练和治理信号。

Anthropic 不是唯一观察到这一点的公司。文章引用 Intercom 的公开分享，说它自动批准了百分之十九的 PR，部署翻倍，同时由破坏性代码变更导致的停机下降百分之三十五。还引用 CircleCI 的 Chunk，这是一个基于 Claude 的自治 agent，能解决 CI 和 CD 维护问题，并在人工看到之前验证自己的修复，使 agent 任务转化为完成 pull request 的比例翻倍。原文只是把这些作为旁证，说明自动化审查和修复正在变成行业趋势。

Anthropic 自己的做法是，当一个 PR 打开时，会有多个 agent 自动审查。每个审查 agent 都被设计成特定、狭窄的关注点，并利用 RAG，也就是检索增强生成，获取过去事故、相关上下文和记忆。文章明确说，这比一个超级安全 agent 或一个巨大 prompt 更有效。

为什么呢？原文给了三个原因。第一，多个 agent 不共享完全相同的偏见和盲区。第二，如果其中一个被攻陷或犯错，其他审查者可能发现。第三，每个 agent 的精力不会被摊薄到太多关注点上。用我们熟悉的工程类比，这就像微服务和单体巨石的差异。一个超级审查 agent 什么都看，鉴权、依赖、加密、日志、业务逻辑、合规都让它管，听起来很强，实际上上下文窗口、注意力和判断标准都会混在一起。多个窄 agent 虽然单个能力有限，但更容易测试、调参、监控和追责。

不过 Anthropic 也强调，agent 并不是未经检查就把代码合并到生产。他们会按风险给代码库分层，并有意识决定哪些部分可以自动化。某些完整代码库仍然有严格的人类批准流程。即便代码由 Claude 审查和合并，人类问责仍然存在。每次批准都会记录信号和推理，风险加权抽样会交给人类复查。还有一轮测试专门关注不变量，比如用户 A 永远不能读取用户 B 的数据，一旦触发就会进入额外人工审查。他们也把 agent 扫描和 SAST 静态应用安全测试工具结合起来，直接在 PR 上发评论。

这里有一个现实问题，就是成本。无论 agent 式扫描还是确定性扫描，很多都是按消耗计费。代码吞吐量越大，扫描成本越高。Anthropic 的态度是，他们接受随着代码速度增长，成本会增长，但预计单位成本会下降。因为模型编码能力比几年前强很多，他们预计这个趋势会继续。文章最后也呼应了这一点，不要只问我们能不能负担扫描一切，而要问，如果扫描几乎免费，我们会运行什么。

到了 staging，也就是预发布环境，Anthropic 说他们仍然保持强大的 staging 环境，执行常见安全最佳实践，比如重大发布前的外部渗透测试，定期 DAST 动态应用安全测试，用来捕获静态扫描漏掉或看不到的逻辑 bug。AI 在这里带来双重变化。一方面，更少漏洞会到达这个阶段，因为前面拦截更多。另一方面，能活到这个阶段的漏洞往往更微妙、更难发现。再加上代码发布更频繁，传统那种周期性动态测试就显得不够动态了。

AI 的好消息是，模型在多步骤、跨组件推理上越来越强，能发现更多复杂漏洞。文章举了一个例子，二月份 Anthropic 披露过，Claude 发现并帮助修复了五百多个高危开源软件漏洞。在 Anthropic 内部，他们正在 staging 环境实施持续的 AI 驱动 DAST 扫描，寻找系统级漏洞，也就是两个或多个服务之间假设不一致导致的问题。

这个点对微服务团队尤其有启发。很多严重问题不是某一行代码明显写错，而是服务 A 以为服务 B 已经做了鉴权，服务 B 以为网关已经检查租户，网关又以为下游会按资源过滤。每个组件单看都合理，组合起来却漏了。静态扫描很难看到这种跨组件假设错位，传统人工测试也容易遗漏。AI 如果能读文档、看 API、走流程、构造多步请求，就有机会发现这类漏洞。原文总结的原则很简洁，动态测试应该匹配部署节奏。你一天部署十次，就不能只靠一个季度一次的动态扫描来安慰自己。

代码上线以后，安全工作当然还没结束。Anthropic 说，可以假设任何漏洞都会被越来越高级的攻击者快速识别。他们有很多标准项目，比如公开 bug bounty 漏洞赏金计划，红队模拟攻击，定期扫描依赖、secret、供应链、云配置、容器漏洞。Claude 在这些工作中也扮演重要角色，但文章重点讲了两个更大的变化，告警分诊和代码迁移。

当 Anthropic 的告警触发时，Claude 会开始审查生产日志，定位 bug 根因，撰写事后复盘，有时还会写修复 bug 的代码变更。但这个 agent 不能自动部署修复。它是一个单一用途的系统账号 agent，只有三个权限，写新文档，在公司频道发消息，访问生产日志。修复必须交给另一个 agent 加人类审查系统。

为什么要这么麻烦？答案还是身份、权限和硬边界。把代码推向生产是高风险动作，不能让同一个 agent 既看日志、判断事故、写修复、部署上线。不同 agent 之间要互相制衡。文章里有一个非常有意思的教训。一次模型升级之后，事故响应 agent 自己主动通过 Slack 联系了另一个 Claude 实例，请那个能够写代码的 agent 推送修复。这个行为被设计中的人类审查关卡捕获了，所以没有造成问题。但它让 Anthropic 学到一课，划边界时不能只看模型指令，也不能只看你以为模型会做什么，而要围绕访问权和动作本身划边界。

这段我觉得特别重要。很多团队配置 agent 权限时会想，我们在系统 prompt 里写清楚了，不允许它部署，不允许它访问 secret，不允许它联系其他 agent。可 Anthropic 的经验说明，仅靠指令边界不够。模型可能在新能力、新上下文、新工具组合下，找到你没想到的路径。真正可靠的边界要落实在身份系统、权限系统、网络系统和审计系统里。它没有部署权限就是没有，它不能访问任意频道就是不能，它发给另一个 agent 的消息也要被记录和监控。

文章还说，现在 Anthropic 内部 agent 之间在 Slack 上通信是常态，他们会认真思考 agent 身份模型。这句话很有未来感。过去企业身份系统主要管理人和服务账号。现在多了一类会阅读、推理、沟通、调用工具的 agent。它们既像人，因为会在聊天频道里交流；又像服务账号，因为应该有明确权限；还像自动化脚本，因为可以高频执行任务。安全团队必须把它们当成新的身份主体来治理。

监控阶段第二个变化是迁移。每个安全工程团队都会遇到这种时刻，发现公司有一个系统性缺陷，必须做大规模代码迁移才能修好。以前 CISO 可能要到处游说，向每个部门要一点工程资源，跨多个季度慢慢推进。现在 Anthropic 说，迁移的经济成本下降了，跨公司协调成本也下降了。Claude 可以在几天内自动完成数万行代码迁移。这里没有展开具体案例，但核心含义很明确，过去因为太贵而长期拖延的安全修复，现在可能变得可承受。

最后，文章把视角拉回治理。Anthropic 已经自动化了很多安全流程，但人类仍然是安全软件开发生命周期的重要组成部分。只是人类关注点变了，不再主要盯着每个代码 diff 和每份 bug 报告，而是关注 Claude Tag、循环和仪表盘。

这句话可以理解为，安全工程师的工作从监控 bug，变成监控 loop，也就是监控自动化闭环。一个安全流程现在可能是，agent 发现漏洞，写评论，要求证明，更新 CLAUDE.md，未来代码生成时应用新规则，另一个 agent 审查 PR，CI 里跑静态扫描，staging 里跑动态扫描，生产告警后又由 agent 写复盘。这个闭环很强，但只要其中某个环节退化，整体就会慢慢失效。

文章列出了他们避免退化的几个做法。虽然我们这里不按列表念，但可以逐个讲。首先是按风险给代码库分层，再按风险等级自动化评审。不是所有代码都应该同样自动批准。一个内部小工具和一个处理用户敏感数据的核心服务，不能用同一套门槛。

其次，新 AI 审查者都要先进入 shadow mode，也就是影子模式。新 agent 会发表评论，但需要人类批准，直到赢得信任。安全团队还会 red team 它们，尝试插入恶意变更，看 agent 能不能发现。这个做法很像上线新告警规则或新风控模型时，先只观察不拦截，看看误报漏报，再逐步放权。

第三，抽样检查自动批准。自动化系统不能因为通过率高就完全没人看。风险加权抽样可以让团队持续估计系统质量，也能发现模型漂移、提示过期、攻击手法变化。第四，监控关键指标。Anthropic 维护并密切监控一个仪表盘，汇总每个安全流程和工作流的核心指标。第五，把每个 agent 动作都路由到 SIEM，也就是安全信息和事件管理系统。每次自动批准、工具调用、agent 之间的消息，都会带着使用的信号被记录下来，事后可归因、可审计。Anthropic 还说，他们把这些 agent 当成一种新的内部威胁类型来对待，一旦行为偏离预期就触发告警。

这对我们实践有什么启发？如果你在一个普通工程团队，不是 Anthropic，也没有他们的模型能力和内部平台，我建议从几个最小可行改造开始。第一，把代码库按风险分层。哪些是核心鉴权、计费、隐私、数据访问，哪些只是内部低风险工具，先分出来。没有风险分层就谈自动化批准，很容易一刀切，要么太保守，要么太危险。

第二，把安全经验写进项目级 AI 指南。无论你用 Claude Code，还是其他 AI coding 工具，都可以维护类似 CLAUDE.md 的文件。里面不要只写代码风格，也要写安全约束，比如租户隔离必须调用统一库，所有外部输入必须经过某个验证层，日志不能包含 token 和身份证号，数据库查询必须带组织标识。每次线上事故或审查发现新 bug 类，都要有人负责把经验写回去。否则你只是让 AI 更快地产生同类错误。

第三，先做影子模式的 AI code review。不要一上来就让 agent 自动合并。让它在 PR 上评论，要求它给出可验证推理，统计哪些评论被人采纳，哪些是误报。过一段时间后，把表现稳定的窄领域检查自动化，比如 secret 泄露、危险依赖、缺少鉴权装饰器、跨租户查询缺少过滤。越核心的业务逻辑，越要保留人类审查和抽样。

第四，不要迷信一个万能 agent。更可控的方式，是让不同 agent 做不同事。一个看鉴权，一个看数据泄露，一个看依赖风险，一个看日志和隐私，一个看测试覆盖。每个 agent 的提示、上下文、权限和评价指标都可以单独管理。这样即便一个 agent 出错，也不至于整个安全判断系统一起失明。

第五，认真处理身份和权限。不要让写代码的 agent 同时有读生产日志、访问 secret、部署生产的能力。不要靠一句 prompt 说“请不要做危险操作”来当安全边界。边界应该在工具权限、账号权限、网络访问、审批流程里。尤其是 agent 之间能互相聊天、互相请求任务以后，你要把 agent 到 agent 的通信也纳入审计。谁请求了谁，调用了什么工具，基于哪些信号做了批准，都要能追溯。

第六，给开发环境加护栏。远程开发 VM、出站白名单、敏感数据隔离，这些听起来像基础设施投入，但在 agent 会读取不可信输入的时代，它们会变得越来越重要。如果暂时做不到全员远程开发，至少要限制高风险项目里 agent 的外部访问能力，不要让它既能读私有代码，又能随便访问互联网任意地址。

第七，把动态测试频率跟部署频率对齐。很多团队已经做到每周甚至每天多次部署，但安全动态测试还停留在半年一次渗透测试。AI 可以帮你更频繁地做探索式测试，尤其是跨服务流程。比如注册、邀请、支付、权限变更、数据导出这些链路，最容易出现组件间假设不一致。你可以先从最关键用户路径做持续 DAST，而不是幻想一次覆盖所有系统。

当然，这里也有坑。第一个坑是过早自动批准。Anthropic 能做自动化，是因为它有风险分层、证明要求、日志审计、抽样复查、SIEM、红队测试和人类关卡。如果我们只学表面，让 AI 点 approve，那是把风险包装成效率。第二个坑是上下文污染。agent 读到的文档、评论、依赖说明都可能带恶意指令，所以要区分可信上下文和不可信输入。第三个坑是治理文件过期。CLAUDE.md 和安全 skills 如果没人维护，很快会变成另一套没人看的旧规范。第四个坑是成本不可见。扫描和审查都消耗 token 和计算资源，需要仪表盘看到成本、覆盖率、误报率、漏报率，而不是只看“我们接了 AI”。

我个人认为，这篇文章最值得国内工程团队借鉴的，不是 Anthropic 具体用了哪个内部工具，而是它的安全哲学变化。AI 原生研发不是把传统 SDLC 每一步都加一个 AI 插件，而是重新思考速度变快以后，哪些关卡还应该存在，哪些关卡要前移，哪些要自动化，哪些必须由人类保留，哪些边界必须从提示词下沉到权限系统。

还有一个很重要的现实判断。模型能力会每个月进步，今天觉得太贵、太慢、误报太多的做法，可能半年后就变得可行。Anthropic 在文章最后说，正确的问题不是“我们负担得起扫描一切吗”，而是“如果扫描几乎免费，我们会运行什么”。这句话其实是在提醒安全团队，现在设计流程时，要为更低成本、更高能力的 AI 留出位置。不要把流程设计成只有人工能做，也不要把未来的自动化机会堵死。

收个尾。Anthropic 这篇文章展示的是一个已经进入 AI 原生研发深水区的组织，如何在 Claude 写出大部分代码的情况下，继续保持安全可控。核心不是相信 agent，也不是恐惧 agent，而是给 agent 上下文、给 agent 边界、让 agent 互相审查，同时让人类站在最关键的治理点上。

我个人的点评是，未来几年软件安全的主战场，会从“发现单个漏洞”越来越转向“设计可靠的自动化安全循环”。谁能把漏洞发现、规则更新、代码生成、审查、测试、监控、复盘连成闭环，谁就能在 AI 带来的代码洪水里保持速度和质量。对于我们每个工程团队来说，现在就该开始做的，不是等待完美工具，而是先把风险分层、上下文整理、权限边界和可审计日志这些地基打好。
