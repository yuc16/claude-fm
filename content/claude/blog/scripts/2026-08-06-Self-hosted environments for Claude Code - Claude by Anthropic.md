先把原文的结论放在最前面。Anthropic 现在允许企业在自己的基础设施上运行 Claude Code sessions。这里的 session，可以理解成一次 Claude Code 的工作会话。你可以从网页端、手机端、桌面端，或者某个 routine，也就是例行流程里启动一个会话。但真正执行代码检出、运行命令、调用内部工具链的地方，不再一定是 Anthropic 托管的基础设施，而可以是在你自己的网络内部，靠近你的内部服务、数据库、软件包仓库、编译工具链和安全控制系统。

这件事听起来像是一个部署选项，但对很多公司来说，它其实改变了 AI agent 的可用范围。以前你可能可以让 Claude 帮你解释一段代码，写一个测试，或者看一个粘贴进去的错误信息。但是一旦进入真实企业环境，问题就来了。你的代码仓库在内网，你的私有 npm registry 或 Maven 仓库不对公网开放，你的 CI 系统、制品库、数据库、feature flag 服务、权限系统都在内网里。一个运行在外部云上的 agent，哪怕模型能力再强，如果碰不到这些东西，就像一个很聪明的外包同学坐在公司大楼外面，只能靠你不断截图、复制粘贴、转述上下文来工作。它能帮忙，但很难真正融入工程流程。

Anthropic 在文章开头也很明确地说，对大多数企业，他们仍然强烈推荐 hosted offering，也就是 Anthropic 托管版。原因很朴素，托管版运维简单，不需要企业自己跑基础设施，不需要维护 runner，不需要考虑扩缩容，也不需要安排平台工程师值守。自托管环境不是给所有人的默认选择，而是给那些网络、工具链或者合规要求确实要求 agent 执行过程留在可控基础设施里的团队。如果你选择这条路，原文非常直白地提醒，你要准备投入工程人力，负责初始搭建和持续维护。

这个提醒很重要。我个人认为，它也是整篇文章里最值得企业决策者听进去的一句话。很多 AI 工具在营销时会说，接入很简单，一键启用，开发者马上增效。但自托管环境不是这样。它更像你把一个新的开发执行层接进了公司基础设施。你不仅是在买一个模型能力，而是在运营一组可以替开发者检出代码、读写文件、执行命令、访问内部服务的自动化 worker。这个东西一旦进入内网，价值很大，责任也很大。

我们先来看 Anthropic 说大家为什么会选择 self-host。原文提了三个原因，网络访问、可定制性、合规。听起来都是企业软件常见词，但放在 AI coding agent 上，每一个都很具体。

先说网络访问。Claude Code 的 session 如果跑在你的网络内部，就可以访问那些没有暴露到公网的内部服务、数据库和 registry。举个最常见的例子，你们公司的后端服务依赖一个内部代码生成工具，这个工具需要从内网的 schema registry 读取接口定义，再生成客户端代码。外部托管的 agent 看不到这个 registry，就只能猜，或者让你把生成结果贴给它。而自托管之后，session 跑在内网，它可以像你公司里的一个构建任务一样访问这些资源。它不需要你把 registry 暴露到公网，也不需要临时打洞，也不需要为了 AI 工具改变网络边界。

再比如企业里常见的私有软件包仓库。很多 Java、Go、Python、Node 项目都依赖内部包。一个 agent 想要真正跑测试，就必须能下载依赖。否则它只能在语义层面分析代码，不能完成构建验证。自托管环境的一个价值就是，让 Claude Code 会话处在和开发者机器、CI runner 类似的网络位置。它能够获取依赖，跑编译，执行测试，调用内部命令行工具。这样它才不只是一个聊天机器人，而更像一个可以在受控沙箱里干活的工程助手。

第二个原因是可定制性。原文说，你可以在环境里预安装 compilers、SDKs 和内部 CLIs，让每一个 session 一启动就已经准备好构建。这个点对做过大型工程的人会特别有感觉。很多项目不是拿到代码就能跑的。你可能需要特定版本的 JDK，特定版本的 Bazel，内部封装的构建命令，某个公司自研的代码扫描工具，甚至还有一套只有在公司镜像里才存在的证书和配置。如果每次 Claude Code 开始工作都要先安装这些东西，那速度慢，失败率高，也很难保证一致性。

自托管环境把这个问题变成了平台工程问题。平台团队可以维护一个 runner image，也就是运行镜像，把常用工具链、编译器、SDK、内部 CLI 都预装进去。这样每次 session 启动时，就像开发者进入一个标准化的远程开发环境，基础工具已经齐了。你可以想象它有点像企业内部的黄金镜像，或者 CI 的基础镜像，只不过它服务的对象不是传统流水线，而是 AI 代码 agent。

第三个原因是合规。原文的表述是 source code and build artifacts stay on infrastructure you control，也就是源代码和构建产物留在你控制的基础设施上。这一点对金融、医疗、政企、半导体、云厂商、大型 SaaS 公司都很关键。很多公司并不是完全不能用外部 AI，而是不能让某些敏感资产离开自己的控制范围。源代码 checkout、构建产物、临时文件、密钥，这些东西如果放在外部托管执行环境里，审计、数据边界、访问控制都会变复杂。

不过这里一定要讲清楚一个非常关键的边界。Anthropic 在文章里专门有一段叫 Data stays on your infrastructure，但它不是说所有数据都不离开你的基础设施。原文说，repository checkouts、build artifacts、secrets，以及 session 创建或修改的任何文件，都会留在你配置的基础设施上。也就是说，代码仓库的检出目录、构建出来的 jar 包、docker 镜像上下文、测试报告、临时文件、配置文件，这些实体文件留在企业自己的环境。

但是，对话本身会发送给 Anthropic 做推理。这里包括 prompts，也就是你给 Claude 的指令，responses，也就是 Claude 的回答，还有 tool results，工具执行结果。而工具执行结果可能包含 Claude 读到的代码。原文明确说，conversation itself，包括 prompts、responses 和 tool results，会发送给 Anthropic for inference，也就是用于模型推理。同时，session transcript，也就是会话记录，会被存储，这样你可以从任何支持的入口继续接上同一个 session。

这段话一定不能被忽略。自托管环境解决的是执行环境在哪里、文件和构建产物在哪里、内网资源怎么访问的问题，但它并不等于模型推理完全在你本地运行。Claude 仍然是 Anthropic 的模型，推理仍然在 Anthropic 侧完成。Claude 要理解代码，就需要看到相关上下文，而这些上下文可能通过工具结果进入对话，再被发送给 Anthropic。所以如果你的组织对代码内容进入模型推理有严格限制，你不能只听到自托管三个字就以为万事大吉。你还要看公司的数据政策，看 Anthropic 的企业条款，看是否允许 prompts 和工具结果出域。

这也解释了文章后面提到的一个限制，自托管环境对 Claude Team 和 Enterprise 计划的组织开放，但默认关闭，并且不适用于使用 ZDR 的组织。ZDR 是 Zero Data Retention，零数据保留。原文没有展开解释，但结合它前面说的 session transcript 要存储，以便从任何入口继续会话，我们可以理解为什么 ZDR 组织不在支持范围里。因为这个功能依赖会话记录的保存和跨端续接，而零数据保留的策略和这种体验之间天然有冲突。这里我个人建议，企业在评估前不要只问能不能自托管，而要先问我们的数据保留策略是什么，我们能接受哪些内容被发送用于推理，哪些内容必须完全不出域。

接下来我们看它的架构。文章用很简洁的方式描述了 self-hosted environments 怎么工作。使用自托管环境时，你要部署一组 runners。runner 可以理解成长期运行的执行进程，或者执行工人。它们会接收排队中的 sessions，然后为每个 session 启动一个 Claude Code process，也就是 Claude Code 进程。

把这个过程类比成打车平台会更容易理解。用户在手机、网页、桌面，或者自动化流程里发起一个需求，就像乘客叫车。Anthropic 的控制面知道有一个 session 要开始，但真正开车的人，也就是 runner，不在 Anthropic 托管环境里，而在你公司的基础设施里。runner 接到任务后，在自己的环境里创建一个工作目录，检出仓库，运行 Claude Code 进程，执行工具调用。Claude 的大脑仍然通过 Anthropic 做推理，但手脚是在你的网络里动。

runner 有两种模式。第一种是 fixed，固定模式。你保持固定数量的 runner 一直运行，sessions 会被分配到它们上面。这个模式的优点是简单、可预测、启动快。比如你知道每天大概有几十个开发者会用 Claude Code，你可以预先准备一批 runner，让它们随时待命。缺点也很明显，低峰期可能空转浪费资源，高峰期如果固定容量不够，就会排队。

第二种是 on demand，按需模式。这里会有一个 orchestrator，也就是编排器，监控排队中的 sessions。当有 session 到来时，它启动 runner；工作完成后，再停止 runner，让容量跟着需求变化。这个模式更像云上的弹性伸缩。高峰期多开，低峰期少开，资源利用率更好。但它也带来更多运维复杂度。你要维护编排器，要处理启动时间，要保证镜像拉取速度，要考虑失败重试，还要监控队列长度和资源上限。原文没有展开这些细节，但它明确说，如果你用 on demand 模式，就需要运行 orchestrator。

文章还提到，runner 可以服务多个 session，但每个 session 都运行在自己的 checkout 里，所以不同开发者和账号之间的工作是隔离的。这个点很关键。因为 Claude Code 做的事情不是只读聊天，它可能修改文件，生成补丁，运行测试，创建中间产物。如果多个用户共享同一个工作目录，结果会非常混乱，也有安全风险。每个 session 独立 checkout，就像每个开发者有自己的工作副本。即使同一个 runner 上同时服务多个 session，代码目录和修改也要隔离开。

这里我个人会提醒一点，原文说的是每个 session 有自己的 checkout，保证工作在开发者和账号之间隔离。但企业自己落地时，不能只把隔离理解成目录不同。你还要想权限、密钥、缓存、日志、网络访问策略是不是也有边界。比如一个 runner 镜像里预置了访问内部 registry 的凭证，这个凭证的权限是不是过大？session 之间共享的构建缓存里会不会残留敏感文件？日志采集系统会不会把工具输出里的代码片段集中到另一个地方？这些不是文章展开的内容，但它们是自托管环境一旦进入生产就必须面对的问题。

另一个很实用的设计点是，来自所有支持入口的 sessions 都会路由到同一个环境。也就是说，你只需要配置一次自托管环境，团队无论从网页、手机、桌面，还是 routine 里启动 session，都会进入同一套企业环境。这对开发者体验很重要。否则每个端都要配一遍，每种入口的网络能力不一致，最后就会变成只有少数高级用户会用。Anthropic 的设计思路是把入口和执行环境解耦。入口可以很多，执行环境由平台团队统一管理。

文章还特别区分了 self-hosted environments 和 Remote Control。Remote Control 可以让开发者从手机或浏览器继续自己机器上正在运行的 session。比如你在办公室电脑上运行了 Claude，出门后想用手机继续看进度，这就是 Remote Control 的场景。但这种 session 和那台机器绑定。那台机器停止运行，session 就结束了，而且它也绑定到运行 claude 的那个用户。

自托管环境不是这样。它运行在平台团队运营的共享基础设施上，可以被任何用户使用。它不是把个人电脑远程投屏到手机上，也不是让手机接管你本地的命令行，而是把 agent 执行搬到企业统一管理的 runner 池里。这个区别对企业很大。个人机器上的 Remote Control 适合个人连续工作，自托管环境适合组织级标准化。前者像你远程连回自己的笔记本，后者像公司提供了一套统一的远程开发和执行平台。

那这篇文章放在二〇二六年的 AI 编程工具背景下，意味着什么？我个人认为，它说明 coding agent 的竞争已经从单纯模型能力，进入了工程执行环境的竞争。过去大家比较哪个模型会写代码，哪个模型通过基准测试更多，哪个模型上下文窗口更大。但在企业真实场景里，agent 的能力上限往往不是模型本身，而是它有没有环境。没有内网访问，它不能跑完整测试；没有正确工具链，它不能构建；没有权限边界，它不能上线；没有审计和合规，它不能被大规模采用。

对中国的软件工程师和 AI 从业者来说，这个趋势也很熟悉。很多公司内部早就有各种研发平台、DevOps 平台、CI 平台、制品库、发布系统、权限系统。AI agent 如果要从 demo 变成生产力，就不能永远停留在浏览器聊天框里。它必须嵌入这些平台，成为研发流程的一部分。而一旦嵌入，问题就不再是 prompt 写得好不好，而是怎么接入内网，怎么隔离权限，怎么管理运行镜像，怎么审计操作，怎么控制成本。

我们可以想象几个具体场景。第一个场景，一个大型后端团队有几百个微服务，服务之间依赖复杂，内部 SDK 和代码生成工具很多。开发者想让 Claude Code 帮忙升级一个框架版本，比如把某个内部 RPC SDK 从旧版迁到新版。Claude 需要检出仓库，理解调用点，修改代码，运行生成器，执行单元测试，还要访问内部依赖仓库。托管环境如果看不到这些内部资源，就只能给出建议。自托管环境如果配好工具链，它就能直接在真实工程里尝试修改，再根据测试失败继续迭代。

第二个场景，移动端团队有一套内部构建系统，依赖私有签名配置、内部插件和公司自己的 CLI。开发者希望 Claude Code 帮忙定位一次构建失败。这个失败可能不是代码语法问题，而是某个内部插件版本和 Gradle 配置冲突。一个外部 agent 如果只能看日志，很难复现。而自托管 session 如果运行在公司网络里，并且镜像里有对应 SDK 和 CLI，就可以更接近开发者本地或 CI 的真实环境。它能跑命令，看到失败，再建议修改。

第三个场景，平台团队想做例行的代码维护，比如升级依赖、补充测试、修复 lint、迁移配置。文章里提到 session 可以从 routine 启动，虽然没有展开 routine 的具体机制，但我们可以理解为某种例行流程或自动化入口。自托管环境让这种 routine 不必在外部环境里摸索，而可以在企业标准环境中运行。这样 agent 做批量维护时，能够使用公司内部工具链，也更容易纳入安全控制。

不过，说到实践应用，我们不能只讲美好的一面。作为工程团队，如果你明天就要评估 Claude Code self-hosted environments，我建议先问四个问题。

第一个问题，我们到底为什么需要自托管？如果只是觉得自托管听起来更安全，但你的代码仓库已经可以通过现有企业集成安全访问，项目没有复杂内网依赖，合规也允许使用托管版，那 Anthropic 自己都建议用 hosted offering。因为托管版省掉大量运维工作。自托管不是免费午餐，它会把平台团队拉进来，让你维护 runner image、更新 runner、监控任务、处理失败、做权限设计。如果收益不明确，很容易变成又一套没人愿意长期负责的平台。

第二个问题，我们需要访问哪些内部资源？这决定 runner 放在哪里，网络策略怎么配，权限开多大。很多团队一开始会想，既然在内网，那就让 runner 能访问所有东西吧。这个想法很危险。Claude Code session 本质上会执行工具，可能读文件、跑命令、访问服务。你应该尽量按项目和团队划定访问范围，至少要知道它能访问哪些仓库、哪些 registry、哪些数据库、哪些密钥。原文强调自托管可以靠近安全控制，这意味着你要真的使用这些安全控制，而不是把它变成内网里的超级用户。

第三个问题，我们如何维护环境的一致性？自托管的价值之一是可定制，但可定制也意味着可能失控。不同团队都想往镜像里塞工具，最后 runner image 越来越大，启动越来越慢，漏洞越来越多，版本冲突越来越频繁。比较稳妥的做法是把它当成正式平台镜像来管理，有版本，有发布流程，有回滚策略，有安全扫描，有变更记录。原文明确说，平台、开发者体验或开发者生产力团队需要负责构建和维护 runner image。这个工作不能临时甩给某个热心开发者。

第四个问题，我们能接受哪些数据发送给 Anthropic？前面讲过，文件和构建产物留在自有基础设施，但对话、回答、工具结果会发送给 Anthropic 做推理，并且会话记录会存储以支持跨入口继续。对于一般企业，这可能在企业协议范围内是可接受的。但对于某些敏感代码、客户数据、密钥输出，就必须谨慎。实践中要避免让工具结果无意中包含密钥、生产数据或过多敏感代码片段。开发者也要知道，自托管不是本地模型，不是所有信息都不出域。

如果你是平台工程团队，落地时可以从一个小范围试点开始。选择一个依赖内网工具链但风险相对可控的项目，准备一个 runner 镜像，里面放好必要的编译器、SDK 和内部 CLI。先用 fixed 模式可能更简单，因为固定 runner 容量容易理解，问题也更少。等使用量上来，再考虑 on demand 模式，通过 orchestrator 做弹性。不要一开始就追求覆盖全公司、支持所有语言、所有工具链、所有网络资源。那样很容易把试点变成平台大工程，最后迟迟无法上线。

在试点过程中，最值得观察的不是 Claude 能写多少代码，而是它能否闭环。所谓闭环，就是它能不能拿到代码，能不能构建，能不能跑测试，能不能根据失败结果继续修改，能不能把结果交给开发者审核。如果一个 agent 只能给建议，开发者还要手工执行大部分步骤，效率提升会有限。如果它能在安全边界内独立完成一轮修改、验证和解释，那么它才真正进入工程工作流。

还要观察开发者怎么从不同入口使用它。文章说自托管环境支持从 web、mobile、desktop 和 routine 启动，并路由到同一环境。这里有一个有趣变化，以后代码 agent 不一定只在 IDE 里工作。你可能在通勤路上用手机发起一个 session，让它先分析一个失败的测试；到公司后在桌面端接着看；下午通过网页让它继续补充测试；晚上某个 routine 又触发它做依赖升级。这种跨端连续性只有在 session transcript 被保存、执行环境统一时才比较顺畅。这也是 Anthropic 为什么强调 session 可以从任何 surface，也就是入口，继续接上。

但这也带来治理问题。入口越多，发起 session 越容易，资源消耗和权限使用也越需要管理。以前跑一次 CI 是明确动作，有提交、有流水线、有日志。现在一个开发者在手机上就能启动一个内网里的 Claude Code session，平台团队就要知道谁启动了，运行了多久，访问了哪些仓库，产生了哪些文件，失败时怎么排查。原文没有讲审计功能细节，所以我们不能说它提供了哪些具体审计能力。但从企业落地角度，这一定是你要向供应商和内部平台确认的问题。

再说固定模式和按需模式的选择。固定模式适合早期试点，也适合使用量稳定的团队。它像办公室里固定放了几台共享工作站，大家来了就用。优点是响应快，故障面小，容量上限清楚。缺点是如果很多人同时启动 session，就会排队；如果没人用，机器也在消耗成本。

按需模式适合使用波动大、成本敏感或者组织规模更大的场景。它像云函数或弹性 CI runner，有任务才起机器，任务结束就释放。优点是容量跟需求走，缺点是冷启动、编排、镜像分发、队列监控都会复杂。尤其是 runner image 如果很大，按需启动的体验可能受影响。这里我个人建议，团队不要只看计算成本，也要看开发者等待时间。如果开发者每次启动 Claude Code 都要等几分钟拉镜像，使用意愿会明显下降。

还有一个容易被低估的点，是内部 CLI 的设计。文章说可以预安装 internal CLIs，让每个 session ready to build。但很多公司内部 CLI 原本是给人类开发者设计的，会有交互式登录，会弹浏览器，会要求输入验证码，会依赖本机配置。AI agent 在 runner 里调用这些工具时，交互方式可能不一样。所以如果你真的想让 Claude Code 在自托管环境里高效工作，可能需要把内部工具做得更自动化、更脚本友好、更适合非交互式运行。换句话说，AI agent 会倒逼企业改善开发者体验。那些对人类已经很别扭的工具，对 agent 只会更别扭。

密钥管理也要特别小心。原文说 secrets 留在你配置的基础设施上，这当然比放到外部执行环境好。但留在内部不等于没有风险。runner 需要什么密钥，session 是否能读取，工具输出会不会把密钥打印到对话里，Claude 是否会看到这些输出，这些都需要策略。一个简单原则是，不要把生产级高权限密钥直接暴露给通用 agent session。尽量使用最小权限、短期凭证、项目级访问控制，并且让内部工具避免在 stdout 里打印敏感信息。这里是我个人的工程建议，不是原文展开的内容。

对于安全团队来说，自托管环境的好消息是，agent 执行发生在企业可控网络里，更容易接入现有安全控制。比如网络分段、访问控制、镜像扫描、日志系统、密钥管理，都可以沿用企业已有体系。坏消息是，你们多了一个新型执行主体。它不是传统 CI，也不是普通员工电脑，而是由模型驱动、能根据上下文动态决定下一步工具调用的 agent。安全审查不能只看机器在哪里，还要看它被允许做什么，用户如何授权，输出如何处理。

对于普通开发者来说，最直接的变化是 Claude Code 可能更像一个真正能跑项目的同事。你不需要把一堆内部错误日志复制到聊天框里，也不需要手工告诉它我们公司构建命令怎么写。平台团队如果配置得好，你启动 session，它已经在正确环境里，有正确工具链，能检出代码，能运行测试。你要做的是描述目标、审查修改、决定是否采纳。开发者的工作会从亲自敲每一个命令，逐渐转向给目标、设边界、看结果、做判断。

但开发者也不能放松警惕。Claude Code 修改代码不等于代码一定正确，自托管运行测试也不等于覆盖所有风险。你仍然需要 code review，需要 CI，需要安全扫描，需要理解它为什么这么改。特别是在自托管环境里，agent 能访问更多内部资源，犯错的影响也可能更大。最好的使用方式不是把它当成自动提交机器，而是当成一个执行力很强的 pair programmer，结对编程伙伴。它可以快速尝试，你负责方向和验收。

这篇文章最后的 getting started 也很简洁。自托管环境现在是 public beta，面向 Claude Team 和 Enterprise plans 的组织开放。它默认关闭，不适用于 ZDR 组织。Anthropic 建议由 platform、developer experience 或 developer productivity team，也就是平台团队、开发者体验团队或开发者生产力团队，负责设置和持续运营，包括构建和维护 runner image、更新 runners，如果使用按需模式，还要运行 orchestrator。反馈可以通过 GitHub 或 Anthropic account team 提交。

注意这里的团队归属很有意思。Anthropic 没说让每个业务团队自己搞，也没说让单个开发者自己装一套。它明确指向平台、开发者体验、开发者生产力团队。这说明 Anthropic 对这个功能的定位是组织级能力，不是个人小工具。它需要标准化，需要运维，需要治理，也需要和企业内部研发流程结合。

我个人认为，未来企业 AI 编程工具会形成两层。一层是模型和产品入口，比如 Claude、网页、桌面、手机、IDE。另一层是企业自己的执行环境，包含代码仓库访问、构建工具链、内部服务、权限和安全控制。模型供应商会努力让第一层体验统一，而企业真正的差异化在第二层。谁能把自己的工程环境整理得更标准、更自动化、更安全，谁就更容易让 AI agent 发挥作用。反过来，如果一个组织的构建流程高度依赖个人电脑上的神秘配置，内部工具不稳定，权限混乱，那么再强的 agent 也会被环境拖住。

回到这篇文章本身，它没有宣布 Claude 在本地推理，也没有说企业代码永远不会进入模型上下文。它宣布的是 Claude Code 的执行会话可以跑在企业自有基础设施上，并且通过 runner 架构支持固定和按需两种运行方式。这是一个很具体的工程能力，解决的是内网访问、环境定制和合规边界的一部分问题。

如果你在公司里负责 AI coding 工具选型，我建议你把这篇文章当成一个评估清单的起点。先确认你的真实痛点是不是内网和工具链。如果是，再评估数据流边界，尤其是对话和工具结果会发送给 Anthropic 这一点。然后让平台团队做小范围试点，先把 runner image、权限、网络、日志和成本跑通。不要一上来承诺全员提效，也不要把自托管误解成完全私有化。

如果你是工程师，这个功能值得关注，因为它意味着未来 Claude Code 可能不再只是你本地终端里的助手，而会成为公司研发平台的一部分。你从手机、网页、桌面发起的同一个任务，背后可能都在公司统一的 runner 池里执行。你需要学会和这种 agent 协作，也需要理解它的边界。知道哪些东西留在公司基础设施里，哪些内容会进入模型推理，这会成为使用 AI 工具的基本素养。

最后用两三句话收个尾。Anthropic 这次发布的 self-hosted environments，把 Claude Code 从外部托管执行推进到了企业可控执行环境，让 agent 更容易接入内网、工具链和安全体系。但它不是零运维，也不是完全本地化推理，企业必须认真处理数据流、权限和平台维护。我个人认为，这类能力会成为企业级 coding agent 的标配，因为真正的生产力不只来自聪明模型，也来自它能不能在正确的工程环境里安全地干活。
