这里先解释一个词，token，你可以把它粗略理解成模型处理文本时使用的计量单位。输入材料要算，输出内容也要算。它不直接等于汉字数量，也不等于英文单词数量。所以，比较每百万 token 的价格，只是在比较单位原料的价格，还没有比较做成一道菜到底消耗多少原料。

假设你让模型写一份技术方案。便宜模型第一遍漏了约束，第二遍补约束时又改坏了结构，第三遍才发现表格数字不一致。每一轮都要重新处理上下文，还要占用你检查和解释的时间。更强的模型如果第一遍就接近交付，单位价格虽然高，总成本却未必更高。

我个人认为，这有点像买服务器。你不能只看单个实例每小时多少钱，还要看完成整批任务需要多少实例、跑多久、失败后重试几次。当然，类比也有边界。人工智能输出的质量不是单纯的吞吐量，所以最后仍然要把人的验收时间算进去。

Haiku 五点五还有一个变化，是这个系列首次提供思考强度控制。也就是说，在换更大模型之前，你可以先让它更认真地做一遍。但文章仍然强调，它更适合短小、边界清楚的任务。需要较长分析的时候，建议转向 Opus 五点五。

Sonnet 五点五的定位，是要求已经讲清楚的快速任务。例如，你已经有完整笔记，只需要整理成正式文档；或者已经有幻灯片模板，只需要按模板制作。它每百万输入 token 是两美元，输出是十美元。速度比 Opus 快，单位价格也低。

Opus 五点五则是输入四美元，输出二十美元，速度定位是中等。它面向需要判断的知识工作。这里的关键词是判断，不只是把内容排整齐，而是要决定哪些证据可靠、哪些结论站得住、哪些信息应该放在前面，以及一份材料还缺什么。

对大多数知识工作，作者不是让大家直接选最贵的 Fable，而是先从 Opus 开始，确实遇到范围和复杂度上的需要，再往上走。套餐也有区别。文章说 Fable 在所有付费方案上可用，但某些套餐在限时首发优惠之外，需要消耗额外的用量额度，不能简单理解成订阅之后就随便使用。

还有一个很容易被忽略的区别。刚才那些美元价格，是按 token 计费的价格。在订阅方案里，价格更高的模型会更快消耗你的使用限额。对个人用户来说，成本可能体现为今天还能不能继续用；对企业来说，则可能体现为预算、额度和实际产出之间的关系。

那遇到结果不好，到底先调强度还是先换模型？文章的建议是，先试更高的思考强度。如果模型已经拿到了上下文，也明显尝试过了，但还是做错，再升级模型。我个人会在这里补一个检查：先确认任务本身是不是说清楚了，否则你可能只是花更多钱，让它认真解决一个错误的问题。

接下来，我们看文章拿什么证明 Opus 适合做日常主力。第一个重点，是文档和研究里的可靠性。作者说，它更严格地遵循指令，比较不容易偏离范围，所以电子表格、幻灯片和文档常常只需要少量编辑。这个说法很吸引人，但真正有信息量的是后面的测试条件。

在一项内部研究测试中，模型要根据保存下来的网页快照，撰写一家公司的季度业绩报告。这个资料环境里，公司的财报新闻稿并不好找。自动评分器会把报告里的每一个数字、每一段引文，都与快照里的页面核对。只要编造一个数字或者一段引文，整份报告就判失败。

结果是在不同思考强度下，十八份报告有十六份通过。请注意，这不是说它所有结论都百分之百正确，也不是说今后任何财报任务都有同样的通过率。它说明的是，在这项具体任务和严格核对条件下，大多数报告没有触发数字与引文编造的失败标准。

为什么我觉得这个测试值得展开？因为很多知识工作的风险，不是整篇文章胡说八道，而是一份看起来很专业的报告里，混进一个没有来源的增长率。你可能不会逐句怀疑它，恰恰因为其他部分都写得很像样。把每个数字和引用都视为需要追溯的对象，比只看报告读起来顺不顺，更接近真实验收。

如果换成你做技术选型报告，道理也一样。比如某个数据库的吞吐量来自哪个测试，是否使用同一硬件，是否包含副本开销，这些都不能因为模型表达流畅就自动成立。我个人建议，把资料来源、结论和待确认事项分开要求，让你能沿着证据链检查，而不是面对一团漂亮的总结。

文章还强调，Opus 五点五的写作比此前更清楚。重要信息放在前面，术语更少，更能遵守你给的写作规范。长任务结束后，它会直接说明做了什么、发现了什么、还需要你提供什么。作者把这种可检查性既视为实用价值，也视为安全收益。

这个观点很适合工程师理解。一个服务报错，如果只说执行失败，你很难定位；如果能说明哪个输入缺失、哪个步骤完成、哪个假设没有验证，你就更容易处理。模型输出也是如此。可读性不只是文风问题，还关系到你能不能及时发现它在什么地方越过了证据边界。

文章引用了 Ramp 一位资深软件工程师的反馈。他说，这个模型写起来像一个好同事，能够遵守他们的写作规则。一份设计规格说明只做很少修改就能使用，模型改写的一段提示，他甚至比自己的版本更喜欢。这里是用户体验反馈，不是普遍保证，但它解释了作者想强调的交付质量。

第二个重点，是分析任务能不能真正做到成品。文章举了一个虚构的并购案例。两家人力资源软件公司计划合并，模型需要在 Excel 里建立财务模型，再做一份给管理层看的演示，判断这个交易价格是否合理。它不是单独回答一道计算题，而是把分析和表达连起来。

这项内部测试里，Opus 五点五用了六十三分钟，Opus 五完成同样任务用了九十三分钟。文章说，新模型成本只有一半，财务模型更全面，演示也更容易阅读。这组结果支持的是，在这个具体任务里，新模型既缩短了时间，也降低了成本，并改善了交付物。

但我们不能顺手推出所有任务都能省一半。文章没有在这里给出完整的样本分布和所有评判细节，也没有说不同公司的材料都会产生同样结果。比较稳妥的理解是，它提供了一个值得你自己复测的方向：不要只测模型答得对不对，也要测从材料到成品，整条链路要多久。

这条链路为什么重要？因为我们在工作中经常面对的不是一个问题，而是一串相互依赖的决定。先读材料，再确定口径，再计算，再画图，再写结论，最后转换成老板能看懂的演示。任何一环漏掉约束，后面都会跟着返工。模型能不能跨步骤保持一致，往往比某一次回答多漂亮更关键。

文章还引用了一位量化研究工程负责人的反馈。在较高思考强度下，Opus 五点五发现他们自己的指令里，分钟索引存在偏移一位的问题，并做了修正。模型还说明，这样做可能会被评分器扣分。反馈者说，它的判断是对的，而且他们此前测试过的模型没有抓住并处理这个问题。

这其实点出了知识工作的一种难度：任务说明本身也可能有错。好的助手不能永远只做机械执行。但我个人认为，发现错误之后，最佳行为还取决于后果。报告里标出疑点，与直接修改生产系统，是两回事。我们可以欢迎模型提出异议，却不应该因此取消高风险操作的确认步骤。

第三个重点，是视觉能力。文章说，Opus 五点五是他们视觉能力最好的 Opus，能够更准确地读取密集文档、图表、截图和示意图。一个很醒目的比较是，即使在最低思考强度下，它读取密集图表数值的准确度，也超过了 Opus 五在最高思考强度下的表现。

这带来的实用变化，是你不一定还要先把图上的数值全部手抄出来，再交给模型分析。直接提供图表、截图或者示意图，可能就够了。过去为了弥补模型能力而加上的人工中转步骤，现在值得重新检查。不是因为这些步骤一定没用，而是它们可能已经不再是必要成本。

不过，直接给图，不等于不做核对。想象你上传一张季度业务图，里面有两条纵轴，左边是金额，右边是增长率。如果模型把百分比当金额，后面的分析仍然可能一路跑偏。我个人建议，金额、单位、时间范围、图例和关键拐点，至少抽查一遍。把省下来的抄写时间，转移到有针对性的验收上。

讲完能力，接下来才是这篇文章最适合明天上班就用的部分。作者说，每一次新模型发布，都是一个重新测试委派范围、清理旧提示习惯的机会。也就是说，不只是换掉模型名称，还要问自己，原来那些一步步牵着它走的操作，今天是否仍然必要。

第一个改变，是直接要求成品。如果你需要电子表格，就让它交付电子表格；需要文档，就要求文档，而不只是先给一个供你照着制作的大纲。文章认为，Opus 五点五很多时候可以从请求直接做到完成文件。这里强调的是把真正目标告诉模型，而不是把中间步骤误当成交付。

比如你要为一次技术评审准备材料。旧习惯可能是先要目录，再让它补背景，再补风险，最后你自己搬进文档。我个人会尝试换成这样说：请根据这些材料，制作一份供评审使用的技术方案，先写建议，再写依据，明确迁移风险和未决问题；资料缺失的地方不要猜，集中列出来。

注意，这不是文章里的原话，而是我根据它的方法给出的工程场景示例。它的价值在于，同时说明目标读者、成品形态、内容优先级和缺失信息的处理方式。模型获得的不只是一个主题，而是判断完成与否的标准。你也就有了可以验收的对象。

第二个改变，是把完整任务放进第一条消息。文章建议，说明目标、最终输出，以及什么时候应该停下来问你。对于长的、多部分工作，作者认为 Opus 五点五比 Opus 五更能一路执行到底。但授权执行和无限自由不是一回事，停止条件恰恰是完整委派的一部分。

假设你让它分析服务成本。可以明确说，如果账单口径和监控口径冲突，先列出冲突，不要自行合并；如果只是缺少不影响主要结论的说明，就完成分析并标注限制。这种指令比每隔一会儿补一句你再看看，更能帮助它区分可以自主处理的细节和必须让人决定的分歧。

第三个改变，是接入工作材料。文章建议通过连接器，把 Claude 连到文件和系统。连接器可以理解为让助手访问相关工作资料的接口。这样它能够主动获取任务需要的内容，而不是只能依赖你粘贴进来的片段。在 Team 和 Enterprise 方案里，需要所有者先开启连接器，成员才能使用。

我个人认为，这一步往往比优化一句提示更重要。因为再强的模型，也无法从没有提供的内部口径里变出正确答案。但接入也意味着权限管理变重要。我的建议是，先用范围有限的文件夹试跑，确认里面的材料确实允许处理，再扩大范围。这是实践补充，不是文章宣称连接后就自动解决了权限和数据治理。

第四个改变，是删掉那些让它努力思考、仔细思考的口号。文章说，Opus 五点五始终开启思考，会根据请求和设定的强度决定投入多少。在他们的测试里，去掉这类句子之后，回答开始得更快，而且没有观察到明确的质量下降。

这里不是说提示词没用了，而是说笼统催促可能没有你想象中有效。与其反复说认真一点，不如告诉它，结论必须能对应来源，不同口径不要混算，证据不足时保留不确定性。前者像催同事加油，后者才是在提供工作标准。这个区别，对人和模型都很实用。

思考强度方面，作者建议从中等开始，这也是 Opus 五点五的默认值。他们说，在编码和知识工作评估里，中等强度的 Opus 五点五已经达到或者超过高强度的 Opus 五。更高强度会思考更久、花费更多，但不总能带来更好的成果。

早期测试者 Factory 的一位技术人员也给出类似反馈。他们测试里，中等强度的 Opus 五点五能够匹配高强度的 Opus 五，同时少用百分之二十到百分之二十五的输出 token。请把这个百分比理解成那组测试的观察结果，而不是你每次请求都能拿到的固定折扣。

具体操作上，文章说，可以点击发送按钮旁边的模型名称，找到思考强度选项。如果中等强度卡住，再提高到高强度。另外，Sonnet 如果已经被你推到特别高或者最高强度，单个任务的成本可能接近 Opus 五点五，这时就应该重新比较，而不是执着于较低的标价。

还有两个写作和设计方面的建议，很容易被忽略。一个是明确说出不喜欢的具体风格。比如不要只说避免模板感，而要说不要奶油色背景、不要胶囊形按钮。文章认为，泛泛地拒绝一种感觉，可能只会让模型换成另一套默认风格。

另一个是给它你们自己的规范。把品牌规则、写作指南放进请求，或者通过连接器提供优秀的历史演示稿，让它照着匹配。文章也没有承诺一次就完全一致，而是提醒你，可能需要几轮调整。我个人觉得，这比反复说更专业一点有效，因为专业不是一种统一的颜色，而是组织自己的表达习惯。

最后，我们把这些建议放进文章那个完整的零售演示里看。一家假想零售公司过去一年收入增长放缓，管理层提出四种解释。分析师手里有一个资料文件夹，里面包括各门店销售表格、管理层会议的文档，以及其他文件。任务是检验四个解释，到底哪些得到数据支持。

这个演示使用 Opus 五点五的中等思考强度。提示大意是，今年增长慢了很多，管理层的几种理论在主管的笔记里，已有材料都在上传的文件夹中，请逐一对照数据检验，并告诉我哪些成立。它没有指定每种理论应该打开哪个文件，也没有加一句你一定要仔细思考。

模型的发现是，数据不支持这四种理论，不过其中一种还不能完全排除。这两个说法的区别很重要。不支持，不一定就是已经证明错误。数据可能缺少必要维度，也可能无法区分多种解释。一个能交付研究结果的助手，应该保留这种差别，而不是为了结论干脆就全部写成否定。

接着，它提出一个管理层没有提到的解释：新门店开得离老门店太近，分走了老门店的销售。按城市排列门店的时候，这个模式不明显；按照与新门店的距离重新筛选后，关系就清楚了。它进一步用销售影响与距离之间的回归分析，为这个发现提供支持。

回归可以简单理解成，观察一个因素变化时，另一个因素通常怎样变化。在这里，就是新老门店距离不同，老店销售受到的影响是否也呈现规律。但我个人必须补一句，回归关系本身不自动等于因果关系。商圈、店面大小、开店时间等因素，也可能同时影响距离和销量。

因此，如果你真的负责这个业务，我会把演示里的发现当作后续调查的重点，而不是立刻据此调整所有开店计划。可以继续检查可比门店，确认观察时间窗口，排查促销和区域需求变化。这些是我的分析建议，原文并没有交代演示已经完成了这些额外验证。

接下来，模型把分析做成一份文档，里面同时有文字、图表和交互元素。比如一个滑块，可以展示新老门店之间距离变化时，销售怎样变化。团队同事还能同时审阅。经理随后要求，把文档转成面向董事会的幻灯片，并且开头就给答案。

这段演示真正想展示的，不只是模型会做回归，而是从资料文件夹，到假设检验，到新解释，再到可讨论的文档和董事会演示，工作链条没有被切成许多彼此脱节的小请求。不使用 Claude 的同事，也可以通过导出后的常见文档和幻灯片格式参与协作。

那么，明天你该怎样试？我个人建议，选一个真实但风险可控的任务，比如把一份已有方案和几张成本表，整合成评审材料。不要挑一个答案你完全无法判断的陌生领域，也不要第一次就交给它不可撤销的生产操作。先让验收能力跟得上委派范围。

把资料一次交齐，说明最后要什么文件，谁来阅读，核心问题是什么，哪些数字必须核对，什么情况下停下来问你。先用中等思考强度，记录第一版用了多久，你改了多久，关键错误有几处，最后文件能不能进入真实流程。然后再与原来的模型和做法比较。

如果失败，先分类。是资料没有给够，是交付标准不清，是工具没有访问权限，还是模型拿到完整材料后仍然判断错误？前面几种问题，不一定靠换模型解决。最后一种，才更值得尝试提高强度或者升级模型。这样你积累的是可复用的工作方法，而不是对某一次惊喜或者翻车的情绪。

这篇文章的核心，是把默认模型的选择，从单价比较转向完整任务的交付效率，再用更明确的目标和更少的无效干预释放能力。我个人认为，最值得升级的未必只是模型，而是我们验收模型工作的方式：把重复搬运交出去，把证据核查、权限边界和最终判断留得更清楚。这里是 Claude FM，我们下期再见。
