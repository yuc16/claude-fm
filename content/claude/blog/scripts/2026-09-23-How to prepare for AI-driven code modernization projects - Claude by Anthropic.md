## Shownotes

Anthropic 一线部署工程师把大型代码现代化的实战经验总结成一套六步法。核心洞察是：agent 让写代码快了十倍，但审查、审批、合规这些组织流程一步没少，于是瓶颈从"写变更"转移到了"让组织消化变更"。这一期我们把"证书"和"晋级策略"这两个关键概念讲透，也聊聊它对普通工程师意味着什么。

- 六步法全貌：定义目标、创建证书、设定晋级策略、落实前置条件、构建 agent 工作流、跑通试点再规模化
- 三种现代化路线 uplift、transform、reimagine 的选择，为什么必须事先吵完
- "证书"是什么：一组必须自动可检的验收条件，以及一份高频使用的条件清单
- 晋级策略：按爆炸半径和 agent 置信度分层评审，以及为什么指令要来自最高层
- 成本真相：在受监管环境里，验证比写代码更烧 token
- 一次现代化的真正产出不是新代码库，而是可复用的工作流和证据链

## Script

你好，这里是 Claude FM。今天我们要聊的这篇文章，英文标题是 How to prepare for AI-driven code modernization projects，中文可以翻译成《如何为 AI 驱动的代码现代化项目做好准备》。文章发表在二〇二六年九月二十三日，距离今天只有四天，非常新鲜。它来自 Anthropic 官方博客的 Notes from the Field 系列，中文可以叫"来自一线的笔记"。写这篇文章的不是做市场的人，而是前向部署工程师，也就是被派到客户现场、跟客户工程团队一起干活的那批人。他们把自己在大型现代化项目里积累的经验拿出来分享。

我先用一句话概括整篇文章的核心洞察，这也是我个人认为最值得你记住的一点：代码现代化这件事，过去要按年规划、全员上阵，现在有了 agent，也就是智能体，几个月甚至几周就能跑完；但围绕这件事的组织工作，也就是改一个关键系统的代码要走多少流程、要谁签字、要留下什么证据，往往一点都没有变少。

换句话说，AI 把写代码这一端加速了十倍，但另一端那些审查、审批、合规的动作还原地不动。结果就是瓶颈换了位置。以前卡在没人写得出这么多变更，现在卡在组织没办法消化这么多变更。这篇文章要讲的，就是在正式开跑之前，企业必须先把哪些事情想清楚、谈妥当、准备到位。

你可能会想，这不就是老生常谈的"流程先行"吗？不完全是。这篇文章给了一套相当具体的六步法，而且每一步都有可操作的细节。更重要的是，它把"证书"和"晋级策略"这两个概念摆到了非常核心的位置，这两个概念是理解全文的钥匙。我们后面会重点讲。

先把背景补完整。为什么传统的代码现代化这么难？

想象一下一家银行的核心系统。这套系统可能已经跑了二三十年，中间经历过无数次补丁、扩展、人员更替。现在要把它迁移到新的技术栈上。每一次改动，哪怕只是改一个字段名，都要走变更管理流程，要有人评审，要有人批准。这不是官僚主义，这是监管机构、审计方和业务本身的要求。正是这些流程，让关键系统变得可信。

问题在于，这套流程是建立在一个人写变更、另一个人看 diff 的假设之上的。diff 就是代码差异对比。过去这个假设成立，因为写代码的速度受限于人的数量和工作时长，评审的人努努力还能跟得上。但现在，agent 写变更的速度远远超过任何人类团队逐个 diff 评审的速度。于是整个系统的瓶颈，从生产变更，转移到了让组织围绕变更运转起来。

这里有个很形象的类比。这就像一家餐厅，后厨突然换了一台超级快的炒菜机器人，出菜速度提升了二十倍。但餐厅门口还是要一个一个核对预约、一个一个安排座位、一个一个上菜介绍菜品。结果前面排队的人不但没减少，反而因为后厨出得太快、服务员手忙脚乱而变得更混乱。这个时候你要做的不是再加一台炒菜机器人，而是重新设计前厅的动线。

代码现代化也是一样。这篇文章明确说，它要讲的是现代化正式开始之前企业必须完成的工作，包括四件事：定义什么叫"做完"；定义每个变更必须携带什么样的证据；定义已经通过认证的变更怎么进入生产环境；以及什么必须先准备好，这样整个流程才跑得起来。它把这四件事拆成了六步。

第一步，定义目标。目标是现代化完成之后，代码应该长成什么样，技术栈是什么，行为是什么。

文章说，目标决定了你到底在做哪一种现代化。它把现代化分成三类。第一类叫 uplift，可以翻译成"升级式现代化"，通常指把系统升级到受支持的运行时或者依赖版本，行为基本不变。第二类叫 transform，可以翻成"转换式现代化"，也就是把技术栈换掉，但行为保持恒定。第三类叫 reimagine，可以翻成"重构式现代化"，这一次不只是换栈，还要顺便把技术债还掉，甚至提出新的业务需求。

这三类的区分不是学术分类，它直接决定了后面所有工作的难度和风险。文章说，组织内部经常为选哪条路争得不可开交。根据 Anthropic 的观察，离生产最近的人，比如运维和站点可靠性工程师，倾向于选择 transform，也就是只换栈、行为不变，把风险圈住。而另一边，长期跟这套代码打交道的工程师，往往希望借这次机会还掉技术债，业务方的利益相关者则希望顺便把新需求塞进去，这就是 reimagine 的路线。

这两种立场都合理。但文章给了一个很重要的提醒：如果这个分歧不解决，它不会消失，它会在项目后期以另一种形式爆发出来，变成一场"这个变更到底算不算正确"的争吵。因为如果目标是模糊的，那正确就没有标准，评审的时候每个人心里的尺子都不一样。

我个人觉得这个观察非常扎心。很多项目失败不是因为技术做不到，而是因为一开始没人愿意花两周时间把"我们到底要什么"谈清楚。大家都觉得这事显而易见，赶紧开工更重要。结果三个月后，评审会上为了一个字段的默认值吵了三个小时，因为没有人知道这个字段在新系统里应该是什么行为。

那怎么定义目标呢？文章给了一个很实用的建议：先去理解现有系统。把老代码实际在做什么提取出来，建立一份当前行为的清单。有了这份清单，你就容易判断哪些部分要保留、哪些要改、哪些干脆丢掉，也就自然回答了这是 transform 还是 reimagine。而且这个过程经常会暴露出那些没人记得的业务逻辑和边缘情况。

你知道最可怕的代码是什么吗？是那种跑了很多年、没人知道为什么这么写、但一删就出事、于是谁也不敢动的代码。这种代码里往往藏着真正的业务规则。它可能是一个看起来毫无意义的取整操作，背后却是某年某月跟监管方谈好的口径。这种知识不在任何文档里，只存在于几个快退休的老工程师脑子里。

文章提到，Claude 可以承担很大一部分这种发现工作，包括画依赖关系图、把没人记得怎么建起来的工作流写成文档。代码现代化插件里有几个命令，叫 assess、map 和 extract-rules，可以挖掘业务规则，并且附上源代码引用，方便工程师复核。这里要强调"源代码引用"这四个字，因为如果 AI 只给你一个结论而不告诉你依据在哪，工程师是不会信的，在关键系统里也不会有人敢签字。

不过文章也很诚实地指出，光靠 Claude 的发现可能不足以完整捕捉遗留系统的全部行为。跟业务用户和开发者的访谈、内部文档，可以填补这些空白。前期花在收集上下文上的时间可能不短，但这份上下文的质量，会决定后面工作流做的每一个决定的质量。

如果是 reimagine 路线，定义目标还要多做一步：写一份详细的行为规格说明，并且跟用户群体达成一致。这一步的难度会显著上升，因为没有现成系统可以对比，正确与否更多依赖判断。

文章还建议，在定义目标的同时，组织应该想清楚这件事到底为什么值得做。这里有一个反直觉的观点：现代化的好处里，降低成本通常不是最主要的驱动力。Anthropic 的经验是，大多数现代化项目的首要收益是降低风险。所以你在争论要不要做的时候，真正该问的问题不是"能省多少钱"，而是"不做的风险是什么"。

比如说，一个系统带着没打补丁的漏洞，可能意味着一次网络入侵，或者一次严重到足以让整个业务停摆的故障。又比如说，一个运行时已经不被支持了，或者懂这套系统的工程师越来越少、招不到也留不住，这些都会让风险不断放大。这些都是"不做"的代价。

文章也承认，agent 类工具确实缩短了现代化的时间线，但预算依然很难估，这会导致组织陷入惯性、迟迟不动手。Anthropic 公开了他们一些大型现代化项目的成本，其他公司也有类似的公开数据，可以作为粗略的基线参考。

而启动这类项目最大的挑战，通常不是技术，而是建立内部共识，让拥有这套系统的团队和依赖这套系统的团队都愿意投入。这时候，把商业论证写清楚、把项目目标定在领导层层面，会让这件事容易很多，也能为后面证书和晋级策略里的取舍提供锚点。当利益相关者对"一个变更能承担多大风险"产生分歧时，不现代化的风险就是那枚压舱的砝码。

好，第一步讲完了。接下来是这篇文章最有价值的部分，第二步，创建证书。

什么是证书？文章的定义是：每一个现代化变更都必须满足的一组条件或测试。注意这里的措辞，不是一个测试，是一组条件。而且选条件的原则是，要挑选那些能够累计提供最强证据、证明这个变更相对目标而言是正确的条件。

我个人觉得"证书"这个比喻非常妙。你可以把它想成给一个外包团队写的验收标准。如果你只说"把代码改好"，那最后交回来一堆你看不懂的东西，你也没法说他没做好。但如果你说清楚，必须满足这十几条，而且每一条都能自动检查，那事情就变得可管理了。

更关键的是下一句：每一条条件都应该可以在没有人类参与的情况下检查。为什么这一点如此重要？因为只有这样，agent 工作流才能自己迭代一个变更，反复改直到满足证书；如果改不出来，就把它标记出来交给人类评审。这是整个自动化循环能够转起来的前提。如果证书里有一条要求"资深工程师凭直觉判断这个设计好不好"，那整个流程就会在这一点上堵死。

文章列了一份常用的条件清单，我尽量完整地念给你听，你可以对照自己团队的实际情况看看缺了哪些。

原有的测试套件要通过。

现代化过程中由 Claude 编写的测试要全部通过。

测试覆盖率要达到事先约定的阈值。

性能基准要保持在约定范围内。

由 Claude 进行的独立对抗性审查，每一次都在全新的上下文窗口里做，没有发现阻塞性问题。

对于用户界面，由 Claude 驱动的计算机操作要发现不了回归问题。

当前版本和目标版本对同样的输入要产生同样的输出，这些输入可以是实时的、录制的，或者由 Claude 生成的。

持久化状态和线上传输格式要能在当前版本和目标版本之间往返一致。

变更要在预发环境里跑够约定的一段时间，错误率、延迟和告警都没有回归。

静态分析和安全扫描不能出现新的问题。

如果目标是编译型语言，构建要干净，类型检查要过。

这份清单我建议你记一下。它不是随便凑的，每一类都对应一种失败模式。原测试保证你没破坏已有行为；新写测试保证新代码本身逻辑自洽；覆盖率防止 agent 绕开难测的部分；性能基准防止功能对但性能崩；对抗性审查防止自说自话；输入输出对比和往返测试防止细微的数据格式差异；预发观察防止只在真实流量下才暴露的问题；静态分析防止引入新的安全隐患；构建和类型检查是最便宜的第一道门。

这里我要特别展开一下"对抗性审查"和"全新上下文窗口"。

假设你让同一个 agent 写完代码之后再自己审查，它会倾向于认为自己的写法是对的，因为它记得自己为什么这么写。这在人类身上也一样，你刚写完一段代码，再让你自己 review，你很容易看不见自己的盲区。所谓对抗性审查，就是换一个角色、换一种立场，专门去找问题。而"全新上下文窗口"的意思是，这个审查者不携带写代码时的任何记忆，它只能看到变更本身和证书，就像一个完全不知情的外部审计员。这种设计的目的，是让审查更接近独立第三方审计的效果，而不是自我确认。

然后是跟谁一起写这份证书。文章的答案很明确：跟那些将来要评审、要把变更推进到生产环境的人一起写。把现在依赖这套代码库的开发者、用户群体和业务负责人拉进来，而且要在证书和 agent 工作流还在设计阶段的时候就拉进来。

为什么？因为他们的专业判断决定了证书该测什么，而他们的早期参与，是他们在变更真正进入评审时愿意买单的原因。文章给了一个很好的自检标准：如果这些人表示，他们仅凭证书提供的证据就愿意合并这个变更，那这份证书就是合格的。更进一步，如果他们能在这份证书里看到自己平时的那把尺子，第三步的晋级策略就可以做得更轻。

这句话背后的逻辑值得琢磨。评审之所以慢，很多时候不是因为评审本身耗时，而是因为评审者不信任上游给的东西，所以他必须从头看一遍。如果证书是他参与设计的，每一条他都认，那当证书全部通过时，他就有理由说"行，这个我可以签"。信任是提前建立起来的，不是在评审现场临时建立的。

接下来，证书的具体形态要看现代化的类型。

对于 uplift 也就是升级式现代化，原文这一段有些简略，但结合上下文理解，升级式的证书主要围绕现有测试和兼容性构建。

对于 transform 也就是转换式现代化，对比的基准仍然是原来的代码库，但问题是，原来的测试套件很少能直接跑在新栈上。所以承担主要验证工作的，是生产流量的回放、新旧系统之间的差分测试，以及一个和生产线并行的部署。所谓差分测试，就是同样的输入同时喂给新旧两套系统，然后比较输出。这是转换式现代化最有力的武器之一。

对于 reimagine 也就是重构式现代化，证书锚定在那份行为规格说明上。文章说这是最难的一种情况，因为规格说明不像一个现成的系统那样客观、可对比，需要更多模型层面的判断，结果的可变性也就更大。在这种情况下，证书更多依赖从规格写出来的测试、Claude 的独立对抗性审查，以及在新系统保留旧行为的地方做差分检查。而且，要做好心理准备，证书会随着规格逐渐清晰而不断修订，因为规格里的空白，往往最先在这里暴露出来。

文章接着说了一个很现实的问题：老系统通常测试覆盖率很低，测试不稳定，遥测数据也少。定义证书的一部分工作，就是识别这些缺口。如果很难支撑一份强证书，那么在这个阶段最有价值的一件事，就是用 Claude 去补齐缺失的证据，无论是搭一个和生产线并行的环境，做一个流量回放装置，还是写更多的测试。

我个人认为这里藏着一个很重要的心态转变。传统上，测试是开发的一部分，是要花时间的成本项。但在这个框架里，测试和证据是证书的原材料，是让 agent 能够自主循环的燃料。你前期在证据上投入的每一分力气，都会在后面的规模化阶段成倍地收回，因为它减少了每一次人工介入的需要。

好，证书有了。接下来第三步，设定晋级策略。

文章一开头就点明现实：agent 生产变更的速度，远远超过任何人类团队逐个 diff 评审的速度。所以晋级策略要解决的问题是：给变更分层，规定每一层需要多深的人工评审，而且这一切要提前写下来、达成一致，这样现代化才能在一个可接受的时间线上完成。

注意"提前写下来"这几个字。这跟传统的做法很不一样。传统做法是，变更来了再讨论这个要不要仔细看。而在一场高速运行的现代化里，如果每一层都要临时讨论，那流程就会彻底堵死。

文章说，跟证书一样，这一步要跟评审者一起做，并且尽可能嵌入组织现有的变更管理流程。具体细节因组织而异，但有几条规则是普遍适用的。我们来逐条讲。

第一条，按爆炸半径和 agent 置信度给变更分层。如果你们组织已经有自己的变更分级或者风险分级标准，就直接用。关键路径上的变更，保留完整的人工评审。所谓爆炸半径，就是这个变更如果出问题，会影响多大范围，是影响一个内部工具，还是影响资金清算。

第二条，反复出现的标记，要回到源头去修。也就是把一段时间内被标记的变更收集起来做分析。如果同一种标记反复出现，那就不要在评审环节一个一个地去处理它，而是回到 agent 工作流或者证书里，把根因修掉。这条规则我特别喜欢，因为它把人工评审从一种被动的、重复的劳动，变成了一种主动的、能产生反馈的信号源。每次人工否决，都应该问一句：我们能不能让工作流下次自动避免这个问题？

第三条，输出格式要跟评审者一起设计。要事先约定，什么样的信息和格式能让评审最快，什么样的信号比其他信号更值得信任。并且让评审者在第五步的时候，提前看一些样本输出。

第四条，高效分配领域专家的时间。文章说得很直白：领域专家不会去读每一个最终 diff，但他们的判断仍然是稀缺的输入。所以要让他们能直接跳到最高风险层级的变更，以及每一层里那些被 agent 标记出来的决策点，而不用在巨大的 diff 里艰难跋涉。这样，少量的专家小时数，就能覆盖住风险最大的那些变更。

这几条规则有一个共同效果，就是把领域专家的时间前置。他们的反馈会在全面现代化开始之前，把证书和工作流调好。而他们对样本的签字认可，也成了在置信度高的地方走更轻评审路径的进一步依据。文章特别指出，这跟传统非 agent 模式是反过来的。传统的模式是，评审发生在最后。

这一点值得再强调一次。传统软件工程里，评审是收尾动作。代码写完了，交给资深工程师看一眼。但在 agent 驱动的现代化里，评审者的角色变成了设计者和校准者，他们在项目最早期就参与进来，参与定义什么是对，然后让机器去执行。他们的价值不再是逐行看代码，而是把判断力编码成证书和工作流。

文章接着说，晋级策略还应该反映现代化在这条谱系上的位置，一端是速度，一端是评审深度。

如果现代化是在冲一个硬性截止日期，比如运行时马上要停止支持了，那就需要一个更快的策略，人工评审更轻，并且明确同意每个变更承担更多的风险。

如果时间线更长，那就可以承担更深的人工评审和更慢的切换节奏。利益相关者会根据自己的风险偏好和约束条件落在谱系上的不同位置，所以在开工之前就把这个位置锁定下来是值得的。

接下来文章讲了一段很现实的话，关于监管环境。在受监管的环境里，哪怕只是对某个变更采取更轻的人工评审路径，也可能引起真实的不适。个体审批人会犹豫要不要签字，因为他个人承担着一个坏变更的责任，而领导层承担的是系统老化的更大风险。这是典型的风险错配。

Anthropic 的经验是，晋级策略的指令最好来自组织最高层。而且最好事先达成一致，这样当一个 bug 真的进入生产环境时，责任是共担的，而不是钉在最后那个签字批准的人身上。

我个人觉得这一段虽然是讲组织政治，但它可能是全文最实用的部分之一。因为技术方案再好，如果没有人愿意签字，项目就是动不了。让指令从上面下来，本质上是把个人风险转化为组织风险，这样个体审批人才敢在合理范围内走轻量路径。

当然，文章也提醒，这一切仍然依赖两个前提：证书足够详细，能够作为真实证据；评审者足够理解 Claude 是怎么得出一个变更的，从而愿意信任它。

好，第四步，把前置条件落实到位。

这一步的大部分工作要通过现代化之外的团队来完成。文章列了几类，包括平台或基础设施团队负责主机环境，质量保证或发布工程团队负责测试容量，安全和合规团队负责审批。这些团队通常都有自己的待办列表和审批流程，所以要尽早开启对话，最好在你识别出需求的时候就开始，往往是在前三步还在进行的时候。

具体的清单分几块。

环境和测试容量方面：一个专用的远程主机，用来跑工作流，并且让 Claude 能够访问代码库和其他相关来源；按证书要求提供的测试容量；以及任何能强化证书的东西，比如生产遥测、和生产线并行的环境，或者用于回放的生产数据。

代码库准备方面：一份代码库依赖关系图，要基于构建和编译日志、导入分析和运行时追踪来建立。文章提醒，插件的 map 命令是个不错的起点，但取决于代码库的规模和年头，可能需要做更多的前期工作。此外还要有对依赖和包的处置计划，作为目标定义的一部分；如果需要，准备好加入持续集成流程的兼容性检查；如果是在原地做现代化，要有一个商定好的代码冻结策略；以及面向活跃开发者的沟通计划，说明代码冻结和新的兼容性要求。

跨团队协作方面：跟依赖这套代码库的其他团队达成一致，明确他们怎么参与，比如签署证书，或者按晋级策略进行评审，并且预留出评审者的时间。

安全和合规方面：一条经过批准、可用于源代码的 Claude Code 模型访问路径；给 agent 工作流配置最小权限，只允许写入现代化分支，不能有生产环境凭证；从现代化分支里清除或遮蔽密钥和个人身份信息；每一个变更都可追溯，每一个拉取请求都关联到 agent 的对话记录和证书证据；以及对新依赖做许可证和漏洞检查。

这份清单信息密度很高，但我觉得有一条特别值得拎出来讲，就是每个拉取请求都关联到 agent 的对话记录。这在传统开发里是没有的东西。过去我们看一个拉取请求，最多看到提交信息、代码 diff 和几条评论。现在我们多了一层证据：这个变更背后的推理过程。谁在什么时候问了 agent 什么，agent 尝试了什么，失败了几次，最后为什么选了这个方案。这在审计和事后复盘的时候，价值巨大。而且它也让信任这件事有了抓手，因为审查者可以去读 agent 的推理链条，判断它是不是走对了路，而不是只看结果。

好，第五步，构建并打磨 agent 工作流。

文章的建议是，从代码现代化插件开始，然后把工作流可能需要的一切都放到文件系统上，或者通过 MCP 也就是模型上下文协议暴露出来，让 Claude 能够访问。这些内容包括目标、证书、晋级策略、代码库、文档，以及证书要求的任何数据源或工具。文章甚至说，你可以把这篇文章本身作为上下文喂给 Claude。

这里的思想很有意思：把项目的全部知识，集中成一个知识库，放在 agent 能触达的地方。这跟传统上靠人来记住和传递项目背景完全不同。当知识是显式的、可被机器读取的，工作流的每一个子任务都能自己去取用正确的上下文，而不是靠某个工程师在提示词里临时补充。

知识库搭好之后，构建现代化工作流本身反而是容易的部分。让领域专家在需要的时候审查 Claude 的工作，包括那些代码库专用的技能或者提取出的规则，而且要确保在下游任何东西依赖它之前就审完。

然后就是打磨。方法是用它去处理代码库里的一小部分，让领域专家审查它产出的变更、agent 的过程，以及证书被满足的证据。文章强调了一条原则：当问题浮出水面时，你要改的是工作流，不是每一个单独的变更。

这句话我认为是整个方法论的一个关键。如果某一个变更做错了，你手动去改它，那下一个类似的错误还会出现。但如果你回头去看工作流为什么会产生这个错误，把根因修掉，那这个类别的错误就整体消失了。目标是要建立起这种信心：一旦规模化，变更几乎在所有地方都能满足证书，而评审者也愿意按晋级策略直接合并。

好，第六步，运行现代化。

方法是，先在代码库的一小部分上端到端地完成一次现代化，包括通过晋级策略完成评审和落地。在还便宜的时候把不work的地方修好，重复这个过程，直到你有信心，然后再扩展到整个代码库。

这里文章特别讲了一个变化：对于 transform 和 reimagine，通常是新目标和旧系统并行构建，等新系统完成之后一次性切换。但对于 uplift，还有第二个选项，就是在活跃的代码库上原地现代化，开发同时继续。

什么时候选这个选项？当系统不能停机，或者代码库变化太快，很难让一个独立的现代化副本保持同步的时候。文章说他们看到有效的做法是：把代码库按照从叶子向内的顺序拆成逻辑分区，一次冻结并现代化一个分区，然后对持续集成流程加门禁，确保一旦某个分区完成现代化，新的提交不能把它改回去。

这个从叶子向内的提法很形象。叶子就是依赖树的末端，那些最底层、被别人依赖但不依赖别人的模块。从叶子开始改，意味着你每次改的东西只被上层依赖，而不会反过来依赖上层。这样做的好处是，可以在不一次性冻结整个代码库的情况下，逐步推进。而那个门禁是关键，否则你刚现代化完一个模块，第二天就有人用旧写法给它提了一个补丁，前功尽弃。

接下来是成本。文章说，他们经常被问到一次这样的现代化要花多少 token。每次现代化都不一样，但主要的成本驱动因素有几个：代码库有多少部分需要被读取，而不是被修改；证书有多复杂，在受监管环境里，验证而不是写变更，通常占更大的份额；证书要求新写和修复多少测试；以及在你运行的过程中，其他团队在周围合并代码带来了多少协调工作。

这里有个很反直觉的点：在受监管环境里，验证的成本通常超过写变更的成本。这跟我们直觉里"AI 写代码很花钱"的印象不一样。其实是那一大堆测试、审查、对比、回放更烧钱。

那怎么估算？文章给的方法是：在小范围试点完成现代化的时候，测量 token 用量，然后用它去推算整个运行。把试点看不到的东西，比如在活跃代码库上的协调工作，当作未知数。这样你至少能得到一个完整现代化的成本下限。

试点数据还能告诉你该往哪里优化。找出最耗 token 的环节，想想怎么让它更高效。把计算密集的验证信号放到更便宜的关卡后面，只有在更容易的检查通过之后才运行它们。这一点其实是一种很实用的工程技巧：先跑便宜的门，再跑贵的门。因为大部分变更会在前期就被筛掉，你不需要为每一个失败品都付一次最贵的验证成本。

模型选择上，文章建议，对于机械的、大批量的、而且证书能完整验证的工作，用像 Sonnet 这样在成本和能力之间取得平衡的模型。把更聪明的模型留给困难的转换，以及那些验证正确性的对抗性审查。你也可以在一个便宜模型没满足证书的时候，升级到一个更贵的模型，但在试点期间要仔细分析重试率，因为好几次便宜的尝试加起来，可能比一次贵的还贵。

最后这一点我觉得特别实用。很多人下意识地觉得用小模型省钱，但如果小模型失败率高，重试三次四次，那总成本反而更高，而且浪费时间。所以重试率是一个必须盯着看的指标。它本质上是一个经济学问题：你要优化的是完成一次变更的总期望成本，不是单次调用的单价。

好，到这里六步讲完了。文章最后有一段总结，我觉得值得完整地讲一遍。

文章说，现代化的代码库只是产出之一。其他的产出包括：产生它的那个工作流；一份写下来的证书，定义了什么叫正确；一个变更管理流程已经接受的晋级策略；以及每一个落地的变更所留下的证据链。要把这套打法固化成一个可复用的资产，这样下一次升级或者重写的时候，这套模式已经就位了。

我个人认为这一段是整篇文章的价值观所在。它其实在说，一次现代化的真正交付物，不是一个新代码库，而是一套可以重复使用的组织能力。代码库会老化，技术栈还会过时，三年后你可能又要现代化一次。但如果你这次把证书、晋级策略、工作流和证据链都沉淀下来，那下一次你面对的就不是一个从零开始的组织变革，而是一个已经跑通的流程。这才是真正的复利。

文章最后提到，Anthropic 的前向部署工程师会跟客户一起，在他们最关键的系统上走完这些步骤。这其实也解释了为什么这篇文章读起来不像市场宣传，而更像一份现场笔记。它讲的是真实项目里的取舍。

好，讲完了文章，接下来我想聊聊，这些内容对正在听节目的你，实际意味着什么。

如果你的公司正在或者即将启动一个遗留系统改造项目，我建议你先做一件事：把"证书"这个概念带进你下一次的会议。不要一上来就讨论用哪个模型、哪个工具，而是先问团队一句话：一个变更要满足哪些条件，我们才认为它是正确的，而且这些条件能不能自动检查？

我几乎可以保证，这个问题会立刻暴露团队里对正确的理解有多不一致。有人觉得测试过了就行，有人觉得必须有性能基准，有人觉得要通过安全扫描，有人觉得必须有人工签字。这些分歧现在暴露出来，成本是几场会议。等到项目跑起来再暴露，成本是几个月。

第二件事，是把领域专家的时间往前挪。我知道在很多团队里，资深工程师的时间是最难抢的资源，大家都觉得让他们参与早期讨论太浪费。但文章的逻辑很清楚：这些人的判断力是稀缺的，稀缺资源应该用在定义标准上，而不是用在事后逐行看代码上。让他们花二十个小时参与设计证书和工作流，可能省下后面两千个小时的评审时间。这笔账其实很好算。

第三件事，是关于你自己的位置。如果你是一名普通工程师，这篇文章传递的信号是：未来你在现代化项目里的价值，可能不在于你写代码有多快，因为 agent 比你快得多。你的价值在于你知道这套老系统里哪一段是不能碰的，你知道那个看起来多余的判断是在防什么业务风险，你知道哪个字段在财务对账的时候有特殊含义。这些知识，正是写证书的时候最需要的东西。所以，趁着这些知识还在你脑子里，把它写下来，把它变成可以被机器使用的规则。这既是给项目做贡献，也是在给自己的职业价值找一个不会被 agent 替代的位置。

第四件事，是关于坑。文章里提到的坑，我挑三个最值得警惕的。

第一个坑，是目标和评审标准没有事先对齐。这会导致项目后期无休止的争论，而且每次争论都在消耗团队的士气。解决方案听起来很土，就是开会、写文档、签字，但它是真的管用。

第二个坑，是在试点阶段发现问题时去手改单个变更，而不是改工作流。这会造成一种假象，以为问题解决了，其实只是把同一个问题推迟到了规模化阶段。等到几万个变更一起涌过来的时候，同一个问题会同时出现在几百个地方，那时候再回头改工作流就晚了。

第三个坑，是低估验证的成本。很多人做预算的时候只算了 agent 写代码的 token，没算测试、回放、差分、对抗性审查的成本。在受监管的环境里，后者往往是大头。如果你拿一个只算了写代码的预算去汇报，很可能在项目中期发现自己严重超支。

最后，还有一点我想补充我自己的观察。这篇文章从头到尾其实在讲一件事：当执行变得便宜时，定义和验证就变成了新的稀缺资源。写变更这件事正在被商品化，但判断什么是正确的、什么是可接受的、什么风险值得承担，这些仍然是人的工作。而且这些工作不但没有减少，反而因为变更数量的爆炸式增长变得更加关键。

所以，与其焦虑 agent 会不会取代工程师，不如想想：你上一次把一个模糊的验收标准写清楚是什么时候？你上一次跟业务方坐下来，一条一条对齐什么是对是什么时候？这些能力，在接下来的几年里会变得越来越值钱。

总结一下今天这一期。这篇文章给了六步法：定义目标、创建证书、设定晋级策略、落实前置条件、构建 agent 工作流、跑通试点再规模化。它的核心主张是，AI 缩短了现代化的技术时间线，但组织时间线不会自动缩短，你必须主动去重新设计它。我最欣赏的一点是，它把一次现代化的真正产出定义为可复用的流程和证据资产，而不只是一个新代码库。
