## Shownotes

Claude Code 团队有大约百分之九十的代码由 Claude 自己编写、自己审查。这篇文章讲的就是他们如何让 agent 用证据证明自己写对了，从而把"一次跑一个"变成"同时跑几十上百个"。我们逐条拆解端到端测试、属性测试、差分测试三种武器，以及 verify skill、提交门禁、可靠性清单这些可以直接抄走的工程实践。

本期要点：

- 验证循环不是锦上添花，而是并行的前提：没有它你只能盯着一两个 Claude，有了它才能开几十上百个
- 如果只能投一种测试，选端到端：单元测试可能通过但功能已经坏了，因为写代码的和写测试的共享同一个误解
- 属性测试用"不可能失败的断言"加海量随机输入来打破你的自信，专攻 agent 最容易漏的边界情况
- 差分测试是新旧系统同输入对拍，迁移和重写场景的第一选择
- 检查不能被它所检查的改动修改，否则这个检查从一开始就是坏的
- 团队维护三十九项可靠性清单，每项带可从 diff 读出的触发条件，Claude 每次只看匹配的三到十项

## Script

今天我们来聊一篇刚出炉的文章，标题是 How the Claude Code team thinks about verification，中文我把它翻成「Claude Code 团队如何思考验证」。这篇文章发表在二〇二六年十一月十六日，距离今天也就是六天时间，所以它是当下最新的工程实践总结，不用担心时效性问题。

那为什么值得专门花二十多分钟讲它？因为这篇文章讲的不是某个新模型、某个新功能，而是一个更底层、更扎心的问题：当你的代码有百分之九十都是 AI 写的，你怎么知道它写对了？这几乎是所有正在用 coding agent 的中国团队现在都会撞上的一堵墙。

你很可能已经体验过那种感觉。Claude 或者别的 agent 帮你写了两三百行代码，看起来很像样，测试也过了，但你就是不敢合进去，因为你手里没有证据。你只能自己一行一行地看，看完之后你会发现，其实你并没有比让它写更快。于是你一次只能跑一个 agent，跑完还得自己当人肉编译器。

这篇文章的核心主张，说白了就一句话：让 agent 用证据验证自己的工作，是把它从「一次跑一个」变成「同时跑一百个」的那个开关。

我们先把背景铺一下。

文章开篇就扔出一个我认为是全文最有冲击力的数字：在 Claude Code 团队内部，大约百分之九十的代码是 Claude 写的，也是 Claude 审的。注意这里有两个动作，写和审。不是人写完让 Claude 帮忙看看，而是 Claude 写完，Claude 审，人只在特定节点介入。

这个比例意味着什么？意味着如果验证这件事做不好，整个团队的吞吐量会直接塌掉。因为人根本读不过来。你想想，一个正常的工程团队一天能产出多少代码，你让一两个资深工程师去读百分之九十，那是物理上不可能的。

所以文章说，在这个规模下，怎么让 agent 用证据来验证自己的工作，变得极其重要。

接下来是这篇文章里我最想让你记住的一个判断：验证循环是让你能委派更多工作的基石。没有它，你实际上一次只能跑一两个 Claude，因为所有东西你都得自己检查。有了它，你可以并行跑几十个、上百个。

这句话其实点破了很多人对 agent 的困惑。为什么你听说别人能同时开好多个 agent 干活，你自己开两个就乱了？不是人家的模型更强，是人家的验证层更厚。你开十个 agent，就相当于给自己开了十个待办事项，每个都得你自己验收；人家开十个 agent，十个 agent 自己互相验收，人只看红灯。

那验证到底能带来多少提升呢？文章给了一个内部测试的数据，我觉得这个数据很值得琢磨。他们在结构化文件生成这个场景里做测试，也就是让 Claude 生成某种有固定结构要求的文件，比如配置文件、schema 之类的东西。结果是：如果引入一个独立的评分者，按照一份评分标准去检查 Claude 的产出，任务成功率比标准的提示循环最高能提升十个点。

十个点听起来不算爆炸，但请注意后面那半句：在最难的问题上收益最大。这才是关键。这说明什么？说明验证不是在模型已经有把握的地方锦上添花，而是在模型自己最没底、最容易飘的地方，把它拽回来。越是复杂任务，模型越容易自信地犯错，这时候一个外部检查器就是救命的。

而且这里有个很重要的成本变化。过去验证是很贵的：写测试贵，搭 benchmark 贵，写规格文档贵，真跑一遍端到端更贵。现在这些都可以让 agent 来干，而且干得还挺快。更妙的是，一旦这些测试和 benchmark 被生成出来，它们就是软件，可以反复运行，几乎不消耗额外的 token。

你可以这么理解：请一个师傅来给你装一条自动化质检流水线，装的时候是要花钱的，但装完之后，每一件产品过一遍检测，成本接近于零。所以这笔投资的性质是资产，不是开销。

文章还讲了怎么把这个闭环真正闭上。光有测试不够，你得用测试结果去改进 agent 的表现。它举了个很具体的例子：如果 agent 反复在同一个测试上失败，这个测试是检查日志里有没有泄漏用户数据的，那你可以针对性地加一个 hook，或者在 CLAUDE.md 里写一条更明确的规则，让它以后别再犯。hook 就是在特定事件触发时自动执行的脚本，CLAUDE.md 就是项目根目录下那份 Claude 每次会话都会读的说明文件。

文章说，这样做基本上能阻止同一个问题再次发生。我很喜欢「基本上」这个词，它很诚实，没有吹成百分之百。

好，铺垫完了，进入正题。既然验证这么重要，那到底该用哪几种测试，又该怎么把它们铺到整条流水线上？

在讲三种测试之前，文章先讲了三个必须避开的失败模式，我觉得这部分特别实用，因为它对应的都是大家踩过的坑。

第一个坑：如果你的测试是不稳定的，也就是那种时好时坏、跑三次过两次的 flaky 测试，那你实际上是在训练 agent 养成一个坏习惯，测试挂了就重跑一次，而不是去修真正失败的代码。这个推演非常精准。你想想，agent 是很擅长从反馈里学模式的，你给它一个随机通过的环境，它学到的最优策略就是反复重试。久而久之，它对你的测试套件彻底失去敬畏。

第二个坑：如果测试很慢，agent 就会倾向于少跑几批，批次少了，出问题的时候你就很难定位到底是哪一块坏的。这就像你调试的时候把日志粒度调粗了，报错还在，但你不知道错在哪一行。

第三个坑跟第二个相关：比较重的测试最好放在你已经准备好提交改动之前跑，而不是每一步都跑。这个顺序安排其实是在替 agent 省时间，也是在替你省钱。

避完坑，我们来看文章推荐的三种测试。它说得很直白：如果只能focus在一种测试上，选端到端。

端到端测试是什么？就是描述真实的用户流程。比如往购物车里加一件商品，结账，跳到确认页面。就这么一条链路，从头走到尾。

为什么端到端这么有效？文章给的理由我觉得是全文最漂亮的一句：它很难被糊弄，要么整个功能能用，要么不能用。它还有明确的完成标准，而且能具体地告诉你哪里坏了。

这句话背后其实藏着一个很深的洞察。单元测试更快、更稳定、更不容易 flaky，这些都是真的。但单元测试有一个致命问题：它可能全部通过，而功能仍然是坏的。为什么？因为写代码的 agent 和写测试的 agent，它们对任务的理解是同一套。如果这个理解本身就有偏差，那么代码会按照偏差写，测试也会按照同一个偏差去验证，两边严丝合缝，绿灯全亮，功能是错的。

这就像什么呢？就像一个学生自己出考卷自己答。他理解错的那个知识点，在他出的卷子上根本不会被考到。所以他能考一百分，但真实考试会挂。

而端到端测试是从用户视角出发的。用户不懂你的实现，他不知道你内部有几个模块、几个状态机，他只知道我点了这个按钮，应该出来那个页面。这个视角和 agent 的内部理解是天然错位的，这种错位恰恰是价值所在。

那怎么让 agent 做端到端？文章说，要给它「手和眼睛」，让它能碰到真实运行的系统。具体做法是写一个 skill，让它能启动应用、驱动应用、检查应用，用的工具可以是 CDP，也就是 Chrome 调试协议，也可以是模拟器，或者 API 测试脚手架。

这里还提到一个我特别喜欢的概念，叫功能地图，英文是 feature map。这个东西既可以当 agent 的指南，也可以当评分标准。因为功能地图通常是从用户视角列出来的功能清单，每一条会写清楚路径、快捷键、选择器、预期结果。你把这个东西交给 agent，它就知道该点哪里、该期待什么。

你可以想象一下，如果你的项目里有一份写得不错的功能地图，那 agent 做端到端测试的时候，就不是在瞎点，而是拿着剧本在验收。

第二种测试，属性测试。文章开头有句话说得很有意思：很多测试是基于「你想到可能出错的地方」来写的。而属性测试关注的是人们容易漏掉的那些边界情况，这恰恰是 agent 经常失败的地方。

属性测试怎么玩？你先写一句话，一句你认为绝对不可能失败的陈述，然后用一个测试库去生成成千上万个输入，试图证明你这句话是错的。

常用的库有这么几个：JavaScript 和 TypeScript 生态里是 fast-check，Python 是 Hypothesis，Rust 是 proptest。思路都一样，就是让机器帮你找反例。

文章列了几种几乎每个项目里都存在的属性，我们一个一个说。

第一种叫往返编码，round-trip。就是「你把 X 编码，再解码回来，应该还是 X」。这个属性在解析和序列化场景里到处都是。你可以类比成把一句中文翻成英文，再翻回中文，语义应该保持一致。如果你的 JSON 序列化再反序列化之后字段丢了、类型变了、精度掉了，这个属性立刻就会报警。

第二种叫不变量，invariant。就是那些必须永远为真的事情，比如账户余额永远不能变成负数。这种断言写起来特别简单，但它能抓住的 bug 类型非常多，尤其是并发和边界条件引发的。

第三种叫幂等性，idempotency。同一个动作做两次和做一次，效果应该一样。数据库迁移、数据规范化、请求重试，这些场景都必须幂等。你想想，一个重试逻辑如果不幂等，那网络抖动一下就可能多扣一次钱。

第四种叫等价性，equivalence。优化后的代码应该和那个朴素但正确的版本产出同样的结果。这个在重构的时候简直是无价之宝。你把一段 O(n²) 的代码优化成 O(n)，性能上去了，但你怎么保证语义没变？拿随机输入同时喂给新旧两个实现，比对输出就行了。

文章特别强调了一点：属性测试库是让 agent 保持诚实的好办法，因为这些边界情况不是由写原始代码的那个 agent 生成的，它的偏见不一样。这是「用不同的偏见对抗偏见」的思路，我觉得非常聪明。你自己想不出来的坑，让一个思路跟你不一样的东西来挖。

还有一点很实用：属性测试在重写场景里特别好用。什么时候？就是当规格文档已经和生产行为漂移了，文档不再可信的时候。这时候你没法靠文档验证，只能靠性质。这个判断很多团队会有共鸣，尤其是那些祖传代码，文档写的和代码跑的根本是两回事。

第三种测试，差分测试。这个在大规模迁移里特别好使，因为迁移的前提假设就是功能不变。

做法很直接：把同样的输入，同时喂给老系统和新系统，看结果一不一样，不一样就说明有 bug 或者有破坏性变更。

关键在于输入怎么来。文章说，要么用随机生成的输入，要么用生产流量的采样。用生产流量采样这个思路非常重要，因为真实流量的分布和你拍脑袋想的完全不一样，长尾部分尤其如此。

然后有两个工程细节必须做。第一，把无关因素规范化，比如空白字符、时间戳、字段顺序这些，不然你会被一堆假阳性淹没。第二，维护一份已批准变更清单，因为有些情况下新环境本来就该和老环境不一样，比如你顺手修了个老 bug，那这个差异是预期的，得记下来。

好，三种测试讲完了。接下来是这篇文章最有分量的一句话，我个人认为也是整篇的题眼：端到端地把应用跑起来，比测试本身更重要。

文章说，你不会在没在模拟器里试过的情况下就发布一个 iOS 改动，对 Claude 也一样。这句话听着朴素，但它划出了一条界线：测试是代码层面的证据，真正跑起来是系统层面的证据，后者更接近真相。

Claude 可以像一个人或者一个 QA 工程师那样去测整个应用。具体怎么做？如果是 Web 改动，让它用 Claude 的 Chrome 扩展；移动端，用 iOS 或者 Android 的 MCP；桌面端，用 computer use，也就是让模型直接操作图形界面；后端，就在本地把服务跑起来。

MCP 这里解释一下，它是 Model Context Protocol，模型上下文协议，可以理解成给 agent 装的各种外设接口。

接下来这段是全文最可操作的部分，我建议你听完就去试。文章说，要把「怎么启动模拟器、怎么跑应用」这件事固化下来，写成一个叫 verify 的 skill，放在仓库里的 .claude/skills/ 目录下，而且尽量放在离相关代码近的地方，需要几个就放几个。Claude 知道在提交改动之前要用这个 verify skill。

然后，重点来了：要投入精力把这个 verify skill 做得又快又可靠。让 Claude 自己去迭代它、去压力测试它。因为它是你的冒烟测试夹具，你必须让它坚如磐石。

这个建议的价值在于它改变了投入的方向。很多人花大量时间去调提示词，希望 agent 一次写对；而正确的做法可能是花时间去建那条验证流水线，让 agent 能自己发现自己写错了。前者是在提高上限，后者是在提高下限，而下限对并行更重要。

文章说，当你给了 Claude 一个端到端冒烟测试自己改动的方式，你会得到好得多的结果。你会看到它像人一样反复迭代，更快地抓到真正的错误。这也是他们在 Anthropic 测试几乎全部改动的方式。

好，到这里我们讲完了「怎么验证」。接下来这部分更有意思，讲的是「怎么用验证结果来决定人的介入」，也就是人机如何分工。

文章说得很坦白：没有人能读每一个改动，所以他们用失败作为一种信号，来决定哪些东西需要人来看。Claude 跑检查，尝试修掉所有失败的东西。如果一个检查在三轮之后仍然失败，Claude 就停下来，把人叫进来。

这个「三轮」的设计我觉得很妙。它同时解决了两个问题：一方面防止 Claude 在一个死胡同里无限打转，烧掉大量 token；另一方面也防止它为了过检查而胡来。三轮是个既给了足够尝试空间、又明确划了止损线的数字。

那检查是谁写的呢？文章说，代码的拥有者写检查，并且不断打磨，直到这个检查能标出拥有者本人会标出的东西。这句话其实定义了「好检查」的标准：不是覆盖率多高，而是它和人的判断有多对齐。

还有一个细节：当一个检查把某个 reviewer 拉进来的时候，它应该说清楚为什么要拉，这样 reviewer 就不用自己从 diff 里去猜。这个体验优化看着小，其实很关键，因为审查者最烦的就是打开一个 diff 不知道要看什么。

接下来是我认为整篇文章最值得抄走的一个具体实践：可靠性清单。

他们维护了一份三十九项的清单，每一项包含三个部分：一个可以从 diff 里读出来的触发条件、一个具体的检查、以及这一项背后的真实事故或者 PR。

文章举了个例子，有一项叫「resume 参数会加载旧会话记录」。当会话存储或者消息类型发生变化的时候，他们就会问：新加的字段能不能安全加载？因为旧的会话记录里根本没有这个字段。

这个例子的通用性很强。任何涉及持久化结构变更的改动，都要问一句老数据怎么办。

而 Claude 怎么用这份清单？它读 diff，只检查那些触发条件匹配的项，通常三十九项里只命中三到十个。所以没有人需要去背历史上发生过的所有故障。这解决了一个很现实的团队问题：事故复盘的经验很难传承，写在文档里没人看，存在脑子里会随着人员流动丢失。把它变成带触发条件的清单，交给 agent 每次自动匹配，这个知识就活了。

然后是审查环节的几个原则，每一条都挺反直觉。

第一条：不要靠堆 reviewer 来改进审查。在主 reviewer 之上再加一个更贵的，往往不如把主 reviewer 调好。这个我深有同感，很多团队一发现漏 bug 的第一反应就是加一道审查，结果流程变长、成本翻倍，漏的 bug 还是漏，因为根本问题在于主审查者的关注点没被定义清楚。

他们的解法是搞一个 REVIEW.md，说明这个代码的 reviewer 应该关注什么。

第二条：审查和验证的轮次应该互相累积。每一轮都指向之前轮次的上下文和过去的失败，而不是每次从头重查一遍。这样更便宜，也能发现更多。这个思路其实和人类工程师做 review 是一样的，你第二轮不会重新看一遍格式，你会直接去看上一轮有疑问的地方。

第三条，也是我认为最重要的一条：如果一个改动能够修改评判它的那个检查，那这个检查就是坏的。他们的 Code Review 永远从 base 分支或者默认分支读 REVIEW.md，绝对不从 pull request 的改动里读。

这条原则必须展开说一下，因为它触及了「谁监督监督者」这个根本问题。你想想，如果 agent 既能改代码，又能改判断代码好不好的规则，那它通过检查这件事就毫无意义了，因为它随时可以把标准调低。这就像一个被告可以修改刑法。所以规则必须放在改动够不着的地方，这个隔离是验证体系可信的前提。

第四条：审查是针对 commit 的。如果有人在审查进行的时候又推了新代码，那这个审查结果就没用了。一个过期的 commit 上通过的审查，一文不值。这个细节很多人会忽略，但它是保证「审查结果真的对应你即将合并的那份代码」的必要条件。

第五条：先跑便宜的检查。如果一个 agent 在本地测试之前就推代码，那它已经浪费了共享的 review 和 CI 时间，而这些 bug 它本来自己就能抓到。在他们的团队里，Claude 在开 pull request 之前会跑测试、构建和 linter。你可以用一个 hook 强制这一点，让它在 Claude 结束的时候自动跑测试；或者用 slash goal 把「测试套件通过」设成目标。

然后是提交盖章和提交门禁这两件事，我觉得这是整套体系里最有工程味的部分。

他们在自己的仓库里，给每一个 commit 打上一个标记，记录这个改动是怎么被验证的。这个标记甚至包含 none 这个值，也就是「没有验证」，这样你就可以直接查询出所有没被验证过的提交。这个设计非常聪明，它不是禁止你提交未验证的代码，而是让未验证变得可见、可查询。可见性本身就是一种约束。

更进一步，他们还做了一个提交门禁，如果一次会话里没有跑过 code-review 或者 verify，就可以阻止这次提交。这个门禁有三种模式：off、observe、enforce。

off 就是关闭。observe 模式只记录「本来会被阻止的提交」，这样你可以先看看有没有误报，确保没有人被误伤。enforce 模式才真正拦截。

这个灰度路径的设计我觉得特别值得学。任何自动化门禁上线时最大的风险就是误报导致大家开始绕过它，一旦绕过成了习惯，这个门禁就废了。先用 observe 模式跑一段时间，收集误报，把规则打磨干净，再开 enforce，这是很成熟的运维思路。

而且他们留了后门：任何提交都可以在 message 里解释为什么它没被验证。另外，如果一次会话里已经被阻止了两次，第三次就会放行，免得 Claude 卡死。文章很坦率地补了一句：Claude Code 并不完美。

我很欣赏这种设计哲学。它不是追求零绕过，而是追求「绕过成本略高于遵守成本」，同时保留一条明确的逃生通道。所有做过平台工程的同学应该都懂，没有逃生通道的门禁，最后一定会被整体关掉。

好，接下来是最后一大块，也是最容易被忽略的一块：怎么审查审查者本身。

文章说，他们会定期审查自己的审查系统效果。追踪三个指标：第一，合并之后又被回滚的改动有多少；第二，维护者在合并前拒掉的改动有多少；第三，一组大小匹配、一直保持干净的改动。

第三个指标是关键，它是用来防止过度标记的对照组。因为如果你只看前两个指标，那让审查系统对什么都报警，指标会很好看，但实际上它变成了噪音。

除了这些运营指标，他们还有一套正式的评估方法，这部分我觉得是整篇文章方法论上最扎实的地方。

做法是这样的：基于过去的事故和回滚构造评估集。对每一个例子，把仓库恢复到当时审查时的那个状态，然后提供一句话的答案键，说明那个 bug 到底是什么。只有正确描述了这个 bug 的发现才能得分。同时用「已合并且稳定」的改动作为对照组，防止过度标记。他们的调优集和固定的测试集是分开的。

这里有几个技术点值得展开。

第一，「把仓库恢复到审查时的状态」这一步非常关键。你不能拿今天的代码去考当时的审查系统，那样答案是泄露的。这需要一定的工具支持，但一旦搭起来，你就有了一套可重复、可对比的评估。

第二，「一句话答案键」这个设计很聪明。它把评估的判定标准降到最低成本，同时避免了「大致说对了」这种模糊地带。你要么说中了那个 bug，要么没有。

第三，分别评估三个阶段的召回率：原始发现、验证之后、最终审查。为什么要分开？因为这样才能看出系统是不是把自己已经找到的 bug 又给丢了。文章说得很直白：任何把这三个阶段合成一个端到端分数的评估，都捕捉不到这个细节。

这个洞察我觉得特别重要。在 agent 系统里，多阶段流水线很常见，每一阶段都可能引入新问题。如果你只看最终结果，你根本不知道瓶颈在哪一段。是发现能力不行，还是验证环节把对的给毙了？分开测才知道。

第四，关于重要性的分级。文章说，除了「有效性」，另一个维度是这个改动有多重要。一个好的 reviewer 能抓住大部分技术上正确的东西，但人真正关心的是：这个 bug 是必须修、应该修，还是只是个小毛病。所以他们的 Code Review 会把问题标成 Important、Nit 或者 Pre-existing 三个等级。

其中 Pre-existing 这个标签特别有意思，意思是「这个问题本来就存在」，所以 reviewer 不应该让这次的作者为它负责。这个标签的价值在于它保护了作者，也保护了审查系统的信噪比。没有这个标签，每个改动都会因为历史遗留问题被反复标记，然后大家就开始无视所有标记。

第五，关于召回率要调到什么程度。文章说，他们一直把召回率往上调，直到下一次提升变成对评估集的过拟合，而不是真的能抓到 bug 为止。这个停手点很难把握，但必须承认它的存在。我个人认为，这是所有做 eval 的团队都该内化的一条纪律：评估分数持续上涨，但线上效果不动，那你就是在刷题。

最后一部分，讲的是怎么把漏掉的案例变成规则。文章给了两种方法。

第一种，从人工代码审查的评论和 PR 回滚里提取模式，找出常见问题。但要成为一条候选规则，必须满足两个条件：至少在两个 PR 里出现过，而且可以从 diff 里识别出来。然后会有三个 agent 尝试去反驳这条规则，最后由人在一个 PR 里审查批准。

这个流程设计得很讲究。「至少在两个 PR 里出现」防止你为了一次偶发就加规则；「可从 diff 识别」保证这条规则真的可执行；「三个 agent 试图反驳」是一种对抗性验证，专门用来杀掉那些似是而非的规则；「人批准」保留了最终的决定权。

第二种方法，用三个找 bug 的 agent 去重放一个关联到已知事故的 PR。如果至少两个找到了那个 bug，那说明这个 bug 是可检测的。反过来，如果一个小 diff 上的 bug 被漏掉了，那就是一个值得写进 REVIEW.md 的缺口。

这里有个细节我觉得很妙：用三个 agent 投票，而不是一个。这其实是在用集成的方式降低单次判断的方差，和前面说的「三个 agent 试图反驳规则」是同一个思路的两个方向。

然后是 flaky 测试的处理，这块特别干脆。文章说，Claude 不能跳过它们，不能加 sleep，也不能重试到通过为止。如果它找不到根因，那就删掉这个测试，并且写下为什么删。

这个规定背后是一种价值观：不稳定的测试比没有测试更有害，因为它会污染整个信号系统。而「写下为什么删」这一步，保证了删除不是一个逃避动作，而是一个有记录的技术决策。

最后一条：规则本身也需要清理。测试套件、验证步骤、各种 md 文件，你不主动管它们，它们只会一直长。所以他们会定期整理。

好，文章的主要内容我们梳理完了。接下来我想聊聊，对于我们这些在国内做工程的人来说，这篇文章能落到什么具体动作上。

第一件事，也是最容易上手的：给你的项目写一个 verify skill。不用等，今天就可以做。具体怎么做？你先自己手动走一遍「怎么把这个服务在本机跑起来、怎么确认它没坏」的流程，把每一步记下来，然后把它写成一个 skill 文件，放到 .claude/skills/ 目录下。里面要说清楚怎么启动、怎么等它 ready、怎么发一个健康检查请求、怎么判断结果是成功的。写完让 Claude 自己跑几遍，让它告诉你哪里不清晰、哪里会卡住。

这件事的投入产出比高得离谱，因为它一次性把你的环境知识固化下来了，之后每一个 agent 会话都在复用。

第二件事，从你的产品里挑一条最核心的用户流程，做成端到端测试。注意，是一条，不是全部。选那条如果坏了你老板会立刻打电话给你的流程。然后让 agent 用浏览器自动化或者 API 调用的方式把它跑通。这条测试的价值不在于覆盖率，而在于它是你唯一一个「很难被糊弄」的信号。

第三件事，如果你的主语言是 Python，装一下 Hypothesis；如果是 TypeScript，装一下 fast-check。然后找三个函数给它写属性：一个序列化和反序列化的，一个涉及金额或者计数的，一个涉及重试逻辑的。就三个，先感受一下它挖出来的反例有多刁钻。我敢说你会被吓到。

第四件事，如果你手上有任何迁移任务，数据库迁移、框架升级、服务重写，那差分测试是你现在就该建立的基建。把生产流量采样下来，同时打进新旧两套系统，比对输出。记得做好规范化，记得维护已批准变更清单。这套东西建起来之后，你对迁移的信心会从「我觉得应该没问题」变成「我跑了三百万条真实请求，差异只有这七条，而且这七条我都知道原因」。

第五件事，建立你自己那份可靠性清单。不要一上来就写三十九条，你写不出那么多。从你印象最深的三个线上故障开始，每一个写清楚：触发条件是什么，怎么从 diff 里看出来，具体的检查是什么。然后每次出事故就加一条。这份清单会随着时间变成你们团队最值钱的资产之一，因为它承载的是血的教训。

第六件事，给你的提交加一个验证标记。哪怕只是简单地在 commit message 里写一行「已验证：单元测试加端到端冒烟」，也比什么都没有强。因为它让「没验证」这件事变得可见。你没法改进你测不到的东西。

第七件事，如果你打算上自动化门禁，务必先跑 observe 模式。先只记录、不拦截，收集一周的误报，把规则调干净，再切到 enforce。同时留一个逃生通道，允许在 commit message 里解释为什么不验证。这是我个人认为这篇文章里最容易被忽略但最影响落地成败的一条。

那要避哪些坑呢？

第一个坑，别纵容 flaky 测试。你团队里那些时好时坏的测试，正在教你的 agent 学会重试而不是修复。要么修根因，要么删掉，没有第三条路。

第二个坑，别让检查能被被检查的东西改掉。这一条我要再强调一次，因为它在实践中太容易违反了。你把审查规则、把测试文件、把 CI 配置和业务代码放在同一个 PR 里，就已经违反了。规则必须在改动够不着的地方。

第三个坑，别用堆 reviewer 的方式解决漏 bug 的问题。先去定义清楚主 reviewer 该关注什么，把 REVIEW.md 写出来，再考虑加人。

第四个坑，别让评估集变成刷题。你的 eval 分数一路涨但线上效果不动，那八成是过拟合了。把调优集和测试集分开，这是底线。

第五个坑，别让规则和测试无限膨胀。定期清理，这个动作听起来无聊，但它决定了你这套体系一年后还能不能用。

最后我想用两三句话总结一下这篇文章。

它真正讲的不是「怎么写测试」，而是「怎么建立一个让 agent 可以被信任的体系」。核心是三件事：让验证层独立于它所评判的改动，用真正重要的 bug 去给它打分，以及在它漏掉东西的时候写下教训、并且定期修剪这些教训。

我很喜欢文章结尾的那个判断：做完这些之后，你的工作会从「读每一个 diff」，变成「定义什么叫完成，然后审查证据」。我个人认为，这句话精确地描述了这个职业正在发生的变化。我们不是在变懒，我们是在把注意力从「检查过程」转移到「定义标准」。而定义标准这件事，恰恰是机器目前还替不了我们的部分。

好，今天就聊到这里。如果你听完想动手，我建议就从那个 verify skill 开始，那是门槛最低、回报最快的一步。我们下期见。
