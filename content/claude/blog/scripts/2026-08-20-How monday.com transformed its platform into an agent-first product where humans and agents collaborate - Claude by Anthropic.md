## Script

今天我们来看一篇 Anthropic 官方博客，英文标题是 How monday.com transformed its platform into an agent-first product where humans and agents collaborate，我把它翻译成中文就是，monday.com 如何把平台改造成一个 agent 优先、人与智能体协作的产品。这篇文章发表于二〇二六年八月二十日。今天是二〇二六年八月二十三日，所以这是一篇非常新的文章，几乎就是刚刚发生的产业案例。它所处的阶段也很明确，AI 产品已经不再停留在聊天框、总结按钮、文本生成小工具，而是进入到一个更难的问题，怎么把 agent，也就是能够接收任务、理解上下文、调用工具并持续推进工作的智能体，真正嵌进企业工作流里。

这期为什么值得听？因为 monday.com 不是一个纯 AI 创业公司，它本来是一个工作管理平台，服务超过二十五万家公司，从中小企业到财富五百强都有。它面对的问题，其实跟很多中国软件公司、企业内部平台团队、SaaS 团队非常像。你已经有一个成熟产品，有用户，有权限体系，有流程，有数据，有业务板块。然后大模型来了，大家都说要上 AI，你第一反应可能也是加几个功能，自动总结、自动分类、自动写周报、自动生成文档。短期看很热闹，Demo 很好看，发布会也能讲，但过一阵子你会发现，用户不是每天都离不开它，功能像撒在旧产品表面的一层亮粉，闪一下，然后就沉下去了。

Anthropic 这篇文章讲的，就是 monday 怎么从这种状态往前跨了一步。它先做了很多 AI 功能，发现有天花板，然后决定不是继续给旧流程加插件，而是把整个平台围绕人和 agent 一起工作重新设计。文章里有一个很关键的说法，采用 AI 功能，不等于变成一家 AI 公司。这个判断非常值得软件工程师和 AI 产品团队反复咀嚼。

先把背景铺一下。monday.com 最早的核心产品，是一个可视化的工作管理界面。你可以把它理解成一个让团队管理项目、自动化流程、跟踪任务的系统。很多团队在里面建 board，也就是看板或者工作板；在 board 里有 item，也就是一条条任务、需求、客户、候选人、合同或者项目记录；再配上状态、负责人、时间、自动化规则、通知和权限。它解决的是组织协作问题，而不是单点办公问题。

过去十多年，这类平台的价值很清楚。它让工作透明，让流程可追踪，让不同角色能在同一个地方对齐。但到了大模型成熟之后，用户会有新的期待。既然这里已经有任务、上下文、历史记录、审批状态、负责人、附件和评论，那 AI 能不能不只是帮我写一句话，而是直接帮我推进工作？比如 IT 工单来了，AI 能不能判断类别、查知识库、给出解决方案、需要人工时再升级？比如招聘流程里，AI 能不能先看简历、筛出匹配候选人、安排面试，同时把 HR、面试官、招聘经理都同步好？比如市场团队要做活动，AI 能不能从 brief 到落地页草稿，再到品牌和法务检查，整个链路都在工作板里跑起来？

这就是 monday 遇到的机会，也是它遇到的挑战。文章说，monday 的重建分了三个阶段。第一个阶段，是随着前沿大语言模型成熟、客户兴奋度提高，团队开始把 AI 能力嵌进原来的平台。这个努力在二零二五年五月达到一个高潮，monday 内部搞了一个 AI month，也就是 AI 月，四周时间里，公司各个团队集中交付 AI 功能或者 AI 产品。

这听起来是不是很熟悉？很多公司过去两年也做过类似事情。某个季度设一个 AI 战役，所有业务线都要报项目。客户支持做自动摘要，销售做邮件生成，研发做需求拆分，产品做调研总结，运营做文案生成。结果通常会有一批东西上线，也会有一段时间的兴奋。monday 也一样，文章说采用情况不错，也激发了很多热情。

但是很快，团队撞到了一个天花板。monday 的 AI Works Platform 产品副总裁 Orly Stern Izhaki 用了一个词，叫 AI dust。直译就是 AI 灰尘，或者我们更口语一点说，撒 AI 粉。意思是，把 AI 自动化像亮粉一样洒在既有工作流上，但没有真正嵌入工作流内部，也没有改变产品根本的价值主张。用户可以用这些功能来总结文本、分类信息，但它们没有形成持续使用模式。

这个判断很重要。一个 AI 功能有没有价值，不能只看它能不能跑，也不能只看第一次使用时用户会不会觉得哇。你要看它有没有变成用户日常工作的一部分。比如自动总结会议纪要，第一次很好玩；但如果总结完之后还要我手动复制到任务系统、手动分配责任人、手动改状态、手动追踪后续，那它就是一个外部辅助。反过来，如果总结直接变成可跟踪任务，关联到项目、负责人、截止日期、审批流程，并且后续还能提醒、更新、升级，那它才可能成为工作流本身。

Izhaki 在文章里说，采用 AI 功能，不等于成为 AI 公司。一旦他们理解了这件事，一切都变了。于是 monday 的目标从给产品加 AI，转向原生地把 AI 建进平台。它要从一个工作管理工具，变成一个人和 agent 一起把事情做完的地方。

这里有一个组织层面的细节也值得注意。文章说，转型命令来自公司高层，但具体怎么把这个北极星转化成产品选择，要靠每个团队、每个员工自己去做，还要构建自己的 agents。也就是说，这不是某个 AI 中台小组做一堆能力，然后别的团队被动接入。它更像是全公司都要改变对产品的想象。你做 IT 流程，就要想 IT agent 怎么成为同事；你做 HR 流程，就要想招聘 agent 怎么接任务；你做市场流程，就要想营销 agent 怎么参与生产线。

经过几个月高强度工作，monday 在二零二六年五月发布了公司历史上最重大的变化，把整个产品体验围绕人和 agent 协同工作重建。这个重建不是凭空做一个新聊天应用，而是利用 monday 已经内置的上下文、工作流、board、权限和治理机制。文章给了一个结果数据，从二零二六年五月上线以来，monday 的客户已经在平台上和 agents 发生了超过五百万次交互。这个数字本身不能证明所有事情都成功了，但至少说明它不是停留在概念发布，而是真有大量用户在实际使用。

接下来我们拆核心内容。第一点，是 monday 把 agent 设计成团队成员，而不是工具按钮。

文章说，每个 monday agent 都有访问权限和限制，也有名字和头像。同事可以通过平台里的触发器和 mention，也就是提及，给 agent 分配工作。这个设计非常有意思。技术上看，好像只是加了名字、头像、权限、触发方式；但产品心智上，它在告诉用户，这不是一个在角落里的 AI 按钮，而是你团队里的一个新角色。

为什么这件事重要？文章说，monday 在客户群里观察到一个模式，很多企业想让 AI 真正干活，但常常停在一个 AI chat，也就是 AI 聊天窗口，而这个聊天窗口和真实工作发生的地方是平行的。你在一个地方聊天，让 AI 生成东西；然后你再把结果搬到另一个地方，进入真实流程。这个平行结构会带来很大摩擦。因为企业工作不是一句问答，它有权限，有状态，有责任，有历史，有异常，有审批，有审计。聊天框很擅长回答问题，但不天然知道这件事现在到了哪一步，谁能看，谁能改，下一步该交给谁。

所以 monday 的做法，是把 agent 直接嵌进工作流里，并且让人像和同事互动一样和它互动。比如你可以在某个任务里提到一个 agent，说请你根据这份需求生成初始项目计划。也可以设置触发器，当新的 IT 工单进入并且类别为空时，让 Intake and Triage Agent 自动分类。这样一来，agentic AI，也就是有行动能力的 AI，就从抽象概念变成一个具体、可操作的团队成员。

你可以类比一下公司里的实习生、项目助理或者运营同学。一个新人如果只是坐在旁边，你每次都要把背景从头说一遍，让他做完再发给你一份文档，你当然会觉得麻烦。但如果这个人就在项目系统里，有自己的权限，能看到相关任务，知道流程状态，能被分配任务，做完以后把结果写回原处，那他就真正进入了团队生产关系。monday 想让 agent 变成后者。

文章给了几个 agent 可以承担的工作范围。IT 场景里，有从工单到解决的流程。Intake and Triage Agent 负责分类工单，自动解决常见请求，在需要升级时带着完整上下文交给人。Knowledge Agent 负责发现知识库缺口，起草新的知识库文章。Incident Agent 负责发现事故，打开 war room，也就是事故应急协作空间，并触发事后复盘。HR 场景里，从职位发布到招聘完成，Resume Screener 可以给申请打分，浮现优秀候选人，发送拒信；Interview Scheduler 处理排期和确认；Hiring Coordinator 让所有相关方持续同步，同时保证始终有人在环。

这里不要把这些例子理解成，AI 已经完全替代 IT、HR 或项目经理。文章强调的其实是分工。agent 接的是高重复、高上下文整理、高流程推进的部分；人在关键判断、例外处理、最终批准和质量把关上仍然在场。尤其 Hiring Coordinator 这个例子里，文章明确说 so there is always a human in the loop，也就是始终有人在环。这是企业场景里非常现实的设计。因为招聘、法务、财务、代码发布这类流程，不只是效率问题，还涉及风险、责任和信任。

第二点，是 Claude 在 monday 平台里的四种运行方式。这个部分对技术同学尤其有价值，因为它不是说我们接了一个模型接口这么简单，而是把不同层级的 agent 入口都考虑到了。

第一种能力叫 monday Agents。团队可以用 prompt，也就是提示词，构建自定义 agents，并选择 Claude 作为模型。平台会给这个 agent 一个名字、一张脸，以及 board 上的一个位置，任何人都可以给它分配工作。你可以把它理解成低代码或者无代码 agent 构建能力，适合业务团队做贴近流程的小助手。比如销售运营团队想要一个竞争情报简报 agent，每周读取相关资料，生成给销售看的要点；不一定要工程师从零写系统，只要在 monday 里定义它的职责和提示词，再连接到对应工作流。

第二种叫 Bring Your Own Agent，缩写是 BYOA，也就是带上你自己的 agent。它让 Claude Managed Agents，也就是由 Claude 托管或管理的 agents，加入 monday 平台。一旦进入 monday，一个人构建的 agent 就可以变成整个团队都能提及、都能分配任务的 teammate，也就是队友。这个思路很符合企业真实情况。公司里不可能所有智能体都由一个平台统一生成。有些团队已经在别处做了 agent，有些 agent 需要特定环境、特定工具、特定安全边界。BYOA 的价值就是让外部或已有 agent 能进入协作平面，而不是继续孤岛化。

第三种是 Pre-built Agents，也就是预构建 agents，它们在 monday Agents Store 里提供。文章说，它可以把 Claude plugins，也就是 Claude 插件，变成专业化队友。比如法律团队可以把法律插件作为 agent 放进自己的工作流，财务团队也可以用自己的专业 agent。这里的关键是专业化。通用大模型能做很多事，但企业流程往往需要领域模板、领域约束和领域工具。预构建 agent 类似应用商店里的垂直应用，只不过它不是一个静态应用，而是一个能被分配任务的工作伙伴。

第四种是 Claude Coding integration，也就是 Claude 编码集成。团队可以在 monday dashboard，也就是仪表盘里连接 Claude，然后规划和分配 agent 任务。Claude Managed Agents 在客户自己的环境里执行，结果和更新会回到 ticket，也就是工单或任务单上，然后再交给下一个 agent，或者交给人来 review，也就是审查。文章用一句话概括得很好，工作从业务需求到可运行代码，再回到业务用户。

这个链路很值得展开。传统软件交付里，业务用户在 monday 或类似系统里提需求，产品经理拆需求，工程师去 Jira 或 GitHub 做开发，代码合并后再回到业务侧确认。中间有很多信息损耗。Claude Coding integration 想做的是，让需求仍然在业务工作板里开始，但 agent 可以接到任务，在客户自己的开发环境里执行，生成代码或变更，然后把结果、状态、需要人判断的地方回写到原始 ticket。这样业务和技术之间不是靠截图、消息和会议串起来，而是靠同一个工作流对象串起来。

当然，原文没有展开它的安全细节和工程实现细节，我们不能替它编。但从产品结构上，你能看出 monday 的野心不是做一个 AI 编码助手的入口，而是把编码 agent 纳入业务流程编排。对于工程团队来说，这个视角比单纯问哪个模型写代码更强更弱更重要。因为真正影响组织效率的，往往不是某一次补全快了十秒，而是需求、实现、验证、交付、反馈能不能被端到端追踪。

第三点，是文章给了一个从 brief 到 landing page 的端到端例子。这个例子很适合拿来理解 agent-first 产品到底长什么样。

场景是一个营销团队在单个 board item 里跑一条 campaign production line，也就是营销活动生产线。市场人员和内容负责人先在这个 item 里一起打磨 brief，也就是活动简报，明确目标、受众、核心信息和渠道。接着，一个用 monday Agents 构建的 Strategist Agent，也就是策略 agent，把这些原始输入转换成结构化 brief，里面包括活动目标、信息支柱、渠道拆解和成功指标。

然后，Landing Page Builder，也就是落地页构建 agent 接手。它运行在公司自己环境里的 Claude Managed Agents 上，拉取已经批准的 brief，然后基于现有落地页生成一个新版本，文案、结构和信息都会根据这次活动做适配。输出会自动回到 monday item 上。页面进入批准之前，一个 Brand Reviewer，也就是品牌审查 agent，会按照品牌指南和法律标准检查，标出需要人注意的地方。最后，营销经理只需要做一个决定，发布，还是继续修改。

你听这个流程，会发现它和普通的“让 AI 写一版落地页文案”差别很大。普通做法是，市场同学打开聊天框，复制背景，生成文案，再贴到文档，找设计，找法务，找经理审批，最后再同步状态。monday 的例子里，AI 不是单点生成，而是多个 agent 沿着同一个工作对象协作。策略 agent 负责结构化，构建 agent 负责产出页面变体，品牌审查 agent 负责把关，人负责关键决策。每一步都回到同一个 item，不需要离开 board。

这也是 agent-first 和 AI feature 的分界线。AI feature 解决一个动作，agent-first 重新组织一串动作。AI feature 通常问的是，我能不能帮用户更快写出一段东西；agent-first 问的是，这个业务结果要经过哪些角色、哪些状态、哪些检查，哪些可以由 agent 承担，哪些必须由人判断，数据在哪里流动，权限怎么控制，结果怎么沉淀。

第四点，是 Cooke 这个客户案例。Cooke 是一家家族海鲜企业，一九八五年创立于加拿大新不伦瑞克省的 Blacks Harbour，最初只有一个养殖场和五千条鲑鱼，现在已经发展成世界上最大的家族所有海鲜公司，在十六个国家运营。这个案例有意思，是因为它不是典型的互联网公司，也不是 AI 原生团队。它更像大量传统企业，业务复杂、项目多、合同多、资源调度难，但又不一定有无限工程资源。

文章说，Cooke 现在把项目交付、资源管理和合同管理放在 Claude 和 monday 一起运行。产品经理使用 Claude，把已批准的项目章程和需求转换成初始项目计划，生成状态报告，并发现风险和问题，这些风险和问题会直接进入 monday 的 RAID logs。RAID 在项目管理里通常指风险、假设、问题和依赖这类日志。文章还提到，这覆盖大约两百个活跃和拟议项目。Claude 自动化了报告和数据准备，帮助一百三十份合同相关的生命周期工作流保持准确，而这些维护工作以前是繁琐且手工的。

Cooke 的战略总监 Patti Stevens 有一句话，Together, monday and Claude help us read team capacity and make smarter allocation calls。意思是，monday 和 Claude 一起帮助他们理解团队产能，并做出更聪明的资源分配判断。她还说，Monday used to be a platform we had to update. Now we operate from it。以前 monday 是一个我们必须更新的平台，现在我们从它里面运营业务。

这句话很关键。很多企业系统最大的问题就是，它是事后记录系统，不是工作发生系统。你干完活，要去系统里更新状态；开完会，要去系统里补纪要；风险已经发生了，要去系统里填日志。员工当然觉得烦，因为系统像一个管理层要求维护的账本。agent 如果用得好，可能把系统从“我必须更新它”，变成“我在里面工作，它帮我推进和记录”。这就是从记录层变成操作层。

第五点，是 monday 总结的五条经验。文章写得比较清楚，我们逐条讲，但不按干巴巴的列表念，而是把它放到产品和组织语境里。

第一条经验是，心智模型比技术更难改变。人们自然想保护质量，并持续改进已经有效的东西。把团队从“我们怎么负责任地改进当前产品”，转向“我们怎么负责任地为一个不同的未来重建它”，花的时间比技术工作更久。

这太真实了。成熟产品团队最擅长的是迭代。这个按钮转化率提升一点，流程少一步，页面加载快一点，权限边界更清楚一点。这些都很重要，也支撑了公司的收入和客户信任。但 agent-first 要求你问一个更激进的问题，如果某些工作不再由人点按钮完成，而是由人给目标、agent 执行、人审查，那界面还应该长什么样？如果用户不是打开功能菜单，而是在 board 里提到一个队友，那导航、权限、通知、日志、计费都要怎么变？这不是小修小补。

对工程师来说，心智模型变化也很难。以前我们习惯把 AI 当一个后端能力，一个模型调用，一个服务接口。现在你要把它当成系统里的 actor，也就是行动者。它有身份，有权限，有任务，有输出，有失败，有审计，有协作关系。这个变化会影响数据模型和架构。比如任务分配表里，assignee 只能是 user 吗？还是也可以是 agent？评论里 mention 的对象只能是人吗？权限系统怎么表达 agent 能看哪些字段、能改哪些状态、能触发哪些外部工具？审计日志里要不要记录 agent 为什么做这个判断？这些都不是 prompt 能解决的。

第二条经验是，当一切都在同时变化时，小团队移动更快。文章说，方向、用户体验、技术、定价、信任模型，以及公司自己对“好产品”的定义，都在同时变化。层层利益相关方会丢失太多细节，但有清晰 ownership，也就是所有权，并且有快速决策权的小团队，能贴近这些细节。

这个经验对大公司尤其重要。AI 转型常常被做成大型治理项目，先成立委员会，再制定统一规范，再开很多评审会。治理当然需要，但如果产品形态还在探索，过多层级会让反馈变慢。monday 的说法不是不要治理，而是当变量很多时，要让小团队拥有足够清晰的目标和快速决策权。比如一个 HR agent 团队，最好能同时理解招聘流程、模型能力、权限边界、用户体验和上线指标，而不是每个决策都拆给五个委员会。

我个人认为，这一点和中国团队很相关。很多公司推 AI，容易出现两种极端。一种是完全中心化，所有 AI 能力都必须走一个平台团队，业务等排期，最后做出来很通用但不贴流程。另一种是完全散养，各团队自己接模型，自己写 prompt，短期快，但安全、成本、复用和治理混乱。monday 这篇文章给的启发是，可以把底层模型、权限、审计、数据基础设施做成平台能力，但具体 agent 怎么嵌入业务，应当让贴近场景的小团队有决策权。

第三条经验是，采用取决于信任，和能力一样重要。产品市场匹配不只取决于 agent 有多能干，还取决于用户是否有信心、是否准备好让 agent 进入真实工作方式。治理、权限、透明度和可靠性，决定了 agent 是停留在 pilot，也就是试点，还是进入 production，也就是生产环境。

这也是很多 AI 项目从 Demo 到生产最常见的坎。Demo 里你可以让 agent 自由发挥，失败了说这是实验。但企业生产里，错发一封拒信、误改一个合同状态、把敏感信息发给不该看的人、在代码里做了不可控变更，代价都很高。所以 monday 强调权限和治理并不意外。它本来就是工作管理平台，知道企业客户关心什么。agent 要成为队友，首先要像员工一样被管理。员工入职有权限，离职要回收权限；不同岗位能看不同信息；关键动作需要审批；做了什么要留下记录。agent 也一样。

透明度也很关键。用户要知道 agent 做了什么、基于什么上下文、下一步会交给谁、哪里需要人确认。如果一个 agent 像黑箱一样突然改了十个字段，用户会紧张。相反，如果它在任务里清楚写出，我已根据这三份输入生成项目计划，发现两个风险，建议分配给某某审查，用户更容易建立信任。

第四条经验是，能力需要匹配的基础设施。文章说，当 agents grounded in live project data，也就是扎根在实时项目数据、团队历史和结构化工作流中时，它们表现会达到不同水平。而在企业规模上，后端必须撑得住。除了 agent 层，monday 投资了 monday DB，让数据基础设施能够支持 agents 在整个组织内运行时带来的容量、速度和复杂性。

这点对工程师最硬核。很多人讨论 agent 时喜欢讨论模型、prompt、工具调用、RAG，也就是检索增强生成。但在企业产品里，数据基础设施可能才是决定天花板的东西。agent 如果拿不到实时数据，就只能生成泛泛建议；如果拿到的数据结构很乱，就会误判；如果权限过滤不严格，就会泄露；如果每次查询都慢，工作流就卡住；如果事件系统不稳定，触发器就丢任务；如果没有良好的状态管理，多个 agent 协作就会互相踩脚。

monday 原文没有详细介绍 monday DB 的技术实现，我们不要展开不存在的架构。但它明确说，monday 投资数据基础设施，是为了支持 agents 跨组织运行时的量、速度和复杂度。这个判断可以推广。agent-first 产品不是在现有系统旁边加一个 AI 服务就完了。你可能要重看数据模型、事件总线、权限服务、审计日志、任务队列、幂等性、观察性和成本控制。尤其当 agent 数量多起来，它们会产生大量读写操作和中间状态。如果后端仍然按人类点击频率设计，就可能扛不住 agent 的自动化频率。

第五条经验是，建立在已经有效的东西上。monday 一直把自己描述为一个让人们组队推动业务结果的地方。agent-first 重建并没有抛弃这个承诺，而是把它扩展到一种新的团队成员。人们仍然来 monday 实现目标，不同的是，现在和他们并肩工作的某些团队成员是 agents。

这条看起来简单，但产品战略上很关键。AI 转型不等于抛弃原来的价值。monday 的核心不是聊天，也不是模型，而是工作协同。Claude 是核心能力，但它服务于 monday 原有的业务承诺。对很多公司来说，最危险的不是不做 AI，而是为了做 AI 把自己做成一个同质化聊天壳。用户为什么已经在用你？你的数据、流程、关系、权限、行业知识在哪里？AI 应该放大这些优势，而不是把你拖进一个所有人都长得一样的输入框竞争。

讲到这里，我们转向实践。假设你是一个中国软件工程师、AI 平台负责人，或者企业 SaaS 产品经理，这篇文章到底能带来什么可操作启发？

第一，你可以先做一个很直接的自查。你们现在的 AI 功能，是撒 AI 粉，还是改变了工作流？判断标准不是用了多强的模型，而是用户是否在真实工作对象上持续使用它。比如一个需求管理系统，如果 AI 只是在一个侧边栏里回答“帮我总结这条需求”，那多半还是辅助功能。如果 AI 能在需求进入后自动识别模块、补充验收标准、发现依赖、建议拆分任务、提交给负责人确认，并把所有输出留在需求对象里，那就开始接近 agent-first。

第二，别急着做万能 agent。monday 的例子里，agent 是有工作的。IT 的 Intake and Triage Agent 做分类和分流，Knowledge Agent 做知识缺口，Incident Agent 做事故流程。HR 的 Resume Screener 看简历，Interview Scheduler 排面试，Hiring Coordinator 同步状态。营销的 Strategist Agent 做结构化 brief，Landing Page Builder 做页面变体，Brand Reviewer 做品牌审查。每个 agent 都有相对清晰的职责边界。你如果一上来做“企业超级助手”，它什么都能答，什么都能做，反而很难进入生产。因为没有人知道该把什么任务交给它，也不知道怎么评估它做得好不好。

第三，把 agent 当成系统角色来设计，而不是当成模型调用来设计。你要问，它叫什么，在哪里出现，谁能提到它，谁能给它分配任务，它能看哪些数据，能改哪些字段，能调用哪些工具，什么情况下必须升级给人，失败时怎么回滚，输出怎么审查，日志怎么留下。这个问题看似产品，实际上会牵动后端。用户表、权限表、审计表、任务状态机、通知系统都可能要改。

第四，优先选择已经有结构化流程和高重复劳动的场景。文章里的 IT、HR、市场、项目报告、合同生命周期，都是比较适合 agent 的地方。因为它们有明确输入，有标准流程，有可审查输出，也有大量重复的信息整理。相反，如果一个场景本身目标很模糊，流程靠人情推动，数据散在十个群里，没有标准状态，直接上 agent 可能会很痛苦。你可能先要把流程和数据结构化，再谈智能化。

第五，人机协作点要设计得具体。不要笼统说 human in the loop。你要明确，人在哪一步介入，介入时看到什么信息，有哪些选项，是批准、驳回、修改，还是重新分配。monday 的营销例子里，营销经理最后做的是 publish or refine，也就是发布或修改。Brand Reviewer 负责标出需要人注意的问题，而不是直接替人承担法律责任。这种边界越清楚，越容易被企业接受。

第六，基础设施要提前规划。你可以先从小范围 agent 做起，但心里要知道，一旦 agent 真进入工作流，系统压力会变。它会更频繁读取数据，更频繁写状态，更依赖事件触发，更需要权限过滤，也更需要可观察性。你至少要能回答几个问题。某个 agent 今天处理了多少任务？失败率是多少？平均耗时是多少？花了多少 token，也就是模型处理文本的基本计量单位？哪些任务被人工驳回？哪些输出被修改最多？有没有越权访问尝试？没有这些指标，你很难从试点走向生产。

第七，别把聊天框当成最终形态。聊天很重要，因为自然语言是低门槛入口。但企业工作不是只有聊天。monday 的重点是 board、item、trigger、mention、permission、workflow。换成你的系统，可能是工单、订单、客户、合同、需求、病例、设备、发票。agent 最好围绕这些业务对象运行，而不是漂在旁边。用户不想在一个孤立窗口里“使用 AI”，用户想把工作做完。

第八，组织上要给小团队足够空间。你可以建立统一的模型接入、安全规范和评估框架，但不要让每个场景都排队等一个中央团队理解业务。最好让懂场景的人直接参与 agent 设计，让工程、产品、业务运营和安全一起坐在小队里快速迭代。因为 agent 的难点常常不是“模型会不会总结”，而是“这个总结在这个流程里应该写到哪里，谁来确认，错了怎么办”。

也要说几个坑。第一个坑，是过度自动化。看到 agent 能做很多事，就想一路自动到底。但企业用户需要逐步建立信任。刚开始可以让 agent 草拟、建议、分类，让人确认；等数据证明稳定，再扩大自动执行范围。第二个坑，是忽略权限。很多 Demo 都用全量数据跑，效果很好，但生产里每个部门、每个角色、每个项目都有边界。第三个坑，是没有评估闭环。agent 不是上线就完事，它的提示词、工具、上下文、流程边界都要根据真实反馈改。第四个坑，是为了 AI 改掉用户已经熟悉的主流程。monday 的策略恰恰是让客户在已经知道的工作流里进入 AI 前沿，而不是强迫他们搬到一个全新 AI 空间。

我个人认为，这篇文章最有价值的地方，不是证明 Claude 有多强，虽然 Claude 显然是 monday 重构的核心；也不是证明 monday 的所有设计就是唯一答案。它真正有价值的是，把 AI 产品转型的问题从“加哪些 AI 功能”，推进到了“谁和谁一起工作，工作对象是什么，流程怎么流转，信任怎么建立，基础设施怎么支撑”。这对任何严肃做企业 AI 的团队，都是必须面对的问题。

最后收一下。monday.com 的故事可以用一句话概括，先撒 AI 粉，发现不够，然后把 agent 当成团队成员，把 Claude 嵌进已有的工作流、权限和数据基础设施里，让人和 agent 在同一个平台上共同完成工作。两个月五百万次交互说明，这种方向至少已经从概念走进了真实使用。我的点评是，下一阶段 AI 产品的竞争，不只是模型能力竞争，而是组织工作流重构能力的竞争。谁能把 agent 放到正确的位置，给它正确的上下文、权限和责任边界，谁才更可能把 AI 从演示变成生产力。
