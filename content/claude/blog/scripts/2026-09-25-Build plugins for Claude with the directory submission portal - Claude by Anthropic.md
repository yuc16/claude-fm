## Shownotes

Anthropic 在二〇二六年九月二十五日上线了 Claude 插件目录的开发者提交门户，开发者可以提交插件、跟踪审核、自主决定发布时间，并在上线后查看安装与发现数据。这篇文章不长，但它把 Claude 生态里长期缺的一块拼图补上了——从"能连"到"有人用"。

本期要点：
- 插件是一个打包容器，把 MCP 连接器和 Agent Skill 装在一起，成为第三方扩展 Claude 的主要形态
- 两条提交路径：单个远程 MCP 连接器，或者托管在 GitHub 上的插件包；Claude Code 里还能带 LSP、命令、钩子和子智能体
- 门户提供自动验证与安全扫描、透明的审核状态和建议修改、以及开发者自己掌握的发布时机
- 上线后能看到按产品入口和版本拆分的安装量，以及列表查看次数和带来访问的搜索词

- 已有的技能、连接器和插件无需改动，未来连接器列表可升级为插件，统一的发现体验即将在 Claude 和 Claude Code 推出

欢迎收听 Claude FM，我是你的主播。今天是二〇二六年九月二十七日，我们要解读的这篇文章，标题是 Build plugins for Claude，直译过来就是为 Claude 构建插件，发表于二〇二六年九月二十五日，也就是两天前，非常新鲜，不存在时效性问题。

这篇文章来自 Anthropic 官方博客，原文标注的阅读时间是五分钟，篇幅确实不长，但它传递的信息量，对一个正在做 AI 工具分发的开发者来说相当关键。它宣布了一件非常具体的事情：Claude 的插件目录，现在有了一个正式的开发者提交门户。你可以提交插件，可以跟踪审核进度，上线之后还能看到使用数据。

如果你手里有一个能用的 MCP 服务器，或者你给 Claude 写过 Agent Skill，又或者你在 Claude Code 里做过一些小工具，那这一期节目就是给你准备的。因为在这个生态里，过去最大的问题往往不是做不出来，而是做出来之后没人知道。这篇文章讨论的，恰恰是从我做好了，到数百万用户真的能用上，中间那段路该怎么走。

我们先说说这件事的背景。文章一开头有一句话，翻译过来是，每天有数百万的人把 Claude 连接到他们的应用、工作工具和数据上。这句话看起来像一句客套的开场白，但它其实是整篇文章的立足点。它说的是需求侧已经成熟了，用户已经习惯让 Claude 去访问外部系统，问题于是转移到了供给侧的效率，也就是第三方开发者能不能方便地把自己的能力接进来。

要理解这个背景，得先理解 MCP。MCP 是 Model Context Protocol 的缩写，中文一般叫模型上下文协议。你可以把它想象成一个通用插座标准。在它出现之前，每接一个外部工具，Claude 这边要写一套适配，工具那边也要写一套适配，两边是一对一的私接，工具数量和客户端数量一乘，工作量就爆炸了。MCP 出现之后，工具方只要实现一个 MCP 服务器，把它挂上去，任何支持 MCP 的客户端都能连。这就把乘法变成了加法。这个协议在二〇二四年底由 Anthropic 提出，之后被大量工具和客户端采纳，逐渐变成了事实标准。

到了文章发表的这个时间点，也就是二〇二六年九月，MCP 规范已经走到了文章里说的 MCP 二点零，核心特征之一是无状态。这个我们后面会详细展开。这里先建立一个印象：协议层已经稳定，生态里已经沉淀了大量的服务器和技能，接下来真正要解决的问题，是分发和发现。你有好东西，怎么让需要的人找到你？怎么让平台信任你？怎么在你上线之后了解真实的使用情况？这篇文章给出的答案，就是目录提交门户。

现在我们进入文章的核心内容。第一个要搞清楚的概念，是 plugin，也就是插件。文章说得很清楚，插件打包 MCP 连接器、Agent Skill，或者两者都打包，它是第三方开发者为 Claude 构建扩展的主要方式。

这句话里有三个层次，值得拆开讲。最底下的一层是 MCP 连接器。它的职责是连接，把 Claude 接到你的远程 MCP 服务器上。你可以把它理解为一条数据管道，或者一个插座。Claude 通过它去读你的数据、调用你的接口。

中间一层是 Agent Skill，智能体技能。技能不负责连接，它负责怎么做事。它更像一本操作手册，或者一套工作流程，告诉 Claude 在某个场景下应该按什么步骤、用什么格式、遵守什么约束去完成任务。比如一份周报该怎么写，一次代码审查该看哪些点，一个客服工单该怎么分类。

最上面一层就是插件。插件本身不是一种全新的能力，它是一个打包容器。它把连接和技能装在一起，作为一个整体交付给用户。这个区别很重要，因为它决定了用户在目录里看到的，不是一个孤零零的接口，也不是一段飘在空中的提示词，而是一个完整的产品。

你可以这样类比。MCP 连接器像是给厨房接好了水电燃气，Agent Skill 像是一本菜谱，而插件是端上桌的一整套套餐。用户点一次单，水电、菜谱、摆盘就全都到位了。对用户来说，最后感知到的是套餐，而不是水电。

我举个更具体的例子。假设你们公司做的是客户关系管理，你可以提供一个 MCP 连接器，让 Claude 能读取客户数据。再写一个 Agent Skill，规定按照你们公司的模板生成客户周报。然后把两者打包成一个插件。用户安装这一个插件，就同时获得了数据访问能力和生成周报的流程规范，不需要自己去拼装。这就是插件存在的意义。

文章还特别强调了一句，技能和 MCP 连接器会继续作为构建块存在，目录也会继续列出它们。这句话是说给已经有资产的开发者听的，你别慌，你原来的东西没有作废。而且文章提到，未来开发者可以把已有的连接器列表直接转成一个插件。换句话说，连接器是入场券，插件是升级路径。这个设计思路非常聪明，它让开发者可以渐进式地投入，而不是被逼着一次性重构。

搞清楚插件是什么之后，第二个关键点是怎么提交。文章给了两条路。

第一条路，单个 MCP 连接器。你有一个远程 MCP 服务器，把地址指过去，就提交完了。这是最轻量的方式，适合那些能力单一、只做一件事的连接器。比如你提供一个天气查询服务，或者一个数据库查询接口，没有复杂的交互流程，那就走这条路。它的好处是快，门槛低，你可以在很短时间内看到自己的东西出现在目录里。

第二条路，插件包。你把 MCP 服务器和技能组合起来，托管在一个 GitHub 仓库里，然后提交这个仓库。这条路适合能力比较完整的产品。用户装一次，就能同时拿到连接和技能，不需要自己去拼。你可以把插件包想象成一个已经组装好的家具，而不是一堆螺丝和木板。

这里有一个细节很有意思。文章说，在 Claude Code 里面，插件还可以包含 LSP、commands、hooks 和 agents。我们一个一个说。LSP 是 Language Server Protocol，语言服务器协议，它给编辑器提供代码补全、跳转定义、类型检查这些能力。插件里带 LSP，意味着 Claude Code 能更准确地理解你的代码结构，而不是靠字符串匹配去猜。commands 是命令，通常表现为斜杠命令，用户敲一下就能触发一个固定动作。hooks 是钩子，在特定事件发生时自动执行，比如每次保存文件之后跑一次代码格式化，或者每次提交之前做一次检查。agents 是智能体，也就是可以被委派任务的子角色，比如一个专门做测试的智能体，一个专门写文档的智能体。

你可以想象这样一个场景。你为某个前端框架做一个 Claude Code 插件，里面打包了一个理解这个框架模板语法的语言服务器，一组一键生成页面骨架的命令，一个在保存时自动整理导入顺序的钩子，再加一个专门帮你升级依赖版本的子智能体。这套东西对用户的黏性，远远高于一个单纯的接口连接。因为它嵌入的是工作流，而不是一个孤立的查询动作。

为什么 Claude Code 的插件能包含这么多东西？因为 Claude Code 本身就是一个开发环境，它的扩展点天然比聊天界面多。你在聊天里能插入的是一个工具，你在开发环境里能插入的是整个工作流。这其实暗示了一个趋势，插件正在从一个接口包装，慢慢变成一个应用形态。

第三个关键点，是这个提交门户本身提供了什么。文章列了三件事，我认为这三件事分别对应了开发者最痛的三个环节。

第一，自动验证。你提交的那一刻，系统就会做检查和安全性扫描，让你尽早发现问题。这个设计的精髓在于早。传统的审核流程是你提交，等两周，然后收到一封邮件说这里不行那里不行，你改完再提交，再等两周。自动验证把反馈周期从周缩短到了分钟。做过发布的同学应该都有体会，最消耗人的往往不是改问题本身，而是不知道要改什么，以及无休止的等待。把检查左移到提交那一刻，开发者就能像跑持续集成一样迭代自己的插件。

第二，审核状态和反馈。你能看到插件在审核流程中的位置，看到安全扫描的结果，看到系统建议的修改。这就把黑盒变成了玻璃盒。这里我要提醒一句，安全扫描对涉及外部数据访问的插件尤其重要，因为 MCP 连接器本质上是让模型代表用户去访问系统，权限边界、凭据管理、数据回传范围，这些都是扫描会重点看的地方。与其被退回，不如在提交之前自己先过一遍。

第三，准备好时发布。批准之后，什么时候上线由你自己决定。这一点经常被低估。发布时机是可以设计的。比如你可以等一个大版本一起发，可以做预热，可以避开节假日，也可以先在小范围用户里验证，再全面放开。把发布按钮交给开发者，实际上是把节奏控制权交还给了产品团队。你不用再担心审核通过的那一刻你还在改别的功能，手忙脚乱地被迫上线。

另外文章说，这个门户对使用付费 Claude 套餐的开发者开放。这是一个门槛，但也说明平台在做质量控制的取舍，先把专业开发者服务好。对认真的团队来说，这个门槛本身不算什么问题。

第四个关键点，是上线之后的数据。文章说得很具体，使用分析会按产品入口和版本展示安装量。

先说按产品入口。Claude 现在已经不只是一个聊天框了，文章后面也提到，发现体验会同时在 Claude 和 Claude Code 上推出。那这两个入口的用户画像是不一样的。如果安装量集中在 Claude Code，说明你的插件偏开发场景；如果集中在聊天端，说明你的插件面向的是通用办公人群。这个信息直接决定你下一版该优化谁、该往哪个方向做功能。你可能会问，知道这个有什么用？用处很大。同样一个功能，开发者和办公用户的期待完全不同。开发者要的是精确、可组合、可脚本化；办公用户要的是简单、少配置、开箱即用。如果数据告诉你是前者，你就该把文档写得更技术；如果告诉你是后者，你就该把引导做得更傻瓜。

再说按版本。这是排查回归问题的利器。假设你这个版本改了鉴权流程，然后版本二点三的安装量突然掉下去，而版本二点二的用户还留在旧版本不升级，那基本可以判断是升级路径出了问题。没有版本维度的数据，你只能看到一个总数，什么都诊断不出来。我个人的经验是，任何时候看到聚合指标，都要问一句能不能拆，能拆到多细。拆得越细，你越可能找到真正的原因。

除了安装，文章还提到发现侧的数据。你会看到自己的列表被查看了多少次，以及哪些搜索带来了这些访问。这个就是应用商店优化，英文里叫 ASO，也就是应用商店优化。它告诉你两件事：你的描述够不够吸引人，以及你的关键词有没有覆盖用户真实使用的说法。举个例子，如果你的插件能连 Notion，但用户在搜索知识库而不是搜索 Notion，那你的描述里就该同时出现这两种表达，甚至三种。再比如，如果某个搜索词带来了很多查看却很少安装，那说明你的首屏介绍和用户预期不匹配，这时候该改的是描述，不是功能。

当然，我要强调一下，这些是我基于文章给出的指标做的推演，文章本身只说了会提供安装数据、查看数据和搜索来源数据。

第五个关键点，是协议层面的进展。文章说 Claude 支持最新的 MCP 规范，通常被称为 MCP 二点零，它包含一个无状态核心。

什么叫无状态核心？简单说，服务端不需要为每一次会话记住上下文状态，每个请求自带完成任务所需的信息。这样做的好处非常实际。第一，水平扩展更容易，你可以随意加机器，不用担心会话粘性问题，用户的请求打到哪台机器上都一样。第二，在云函数、边缘计算这类环境里部署更自然，因为它们本来就是短生命周期、无状态的。第三，容错更简单，一个请求失败了，重试就行，不存在会话状态错乱的风险。第四，测试更容易，因为每个请求是自包含的，你可以很方便地重放和构造用例。

对开发者来说，这意味着你的 MCP 服务器架构可以做得更轻、更便宜、更稳。当然，无状态也有代价。每次请求都要携带足够的上下文，请求体积可能变大，鉴权需要用无状态令牌来实现，这些都是在设计时要想清楚的地方。但总体而言，协议往无状态走，是顺应云原生基础设施的方向。

除了规范本身，文章还点名了两个扩展。第一个是 MCP Apps，用它在聊天里做交互式界面。以前模型和用户之间是纯文本一来一回，你想让用户填个表单、看个图表、点个审批按钮，只能靠文字描述。有了 MCP Apps，你可以在对话里直接渲染界面。这个变化其实很大，它让插件从工具往应用的方向走。

你可以想象一个报销插件的场景。用户对 Claude 说，帮我看看这个月有哪些报销单要审批。Claude 调用了你的连接器，在对话里直接渲染出一个待审批列表。用户点开其中一条，看到明细和发票图片，点一下确认。整个过程用户没有离开聊天窗口，也没有跳转到别的系统。这种体验的顺滑程度，和纯文本描述相比是完全不同的量级。我个人认为，MCP Apps 可能是这一整篇文章里最被低估的一个点，因为它改变的是交互范式，而不只是能力边界。

第二个扩展是 Enterprise Managed Auth，企业托管认证，给企业用户提供零手动操作的 OAuth 授权。OAuth 你可能熟悉，就是那种使用某某账号登录的授权流程。对个人用户来说，点几下就完了。但在企业里，这件事很麻烦，因为涉及管理员审批、权限范围、合规审计。Enterprise Managed Auth 把这些流程交给企业统一管理，用户端几乎无感。这是企业落地的关键一环，没有它，很多公司根本不会允许员工接入外部插件。

我们换个角度理解这件事。企业采购软件的逻辑和个人用户完全不同。个人用户看的是好不好用，企业看的是能不能管、能不能审计、出了问题谁负责。零手动授权听起来像是省了几次点击，但它真正的价值在于让 IT 管理员有了统一的管控入口。这意味着插件的买家和使用者分开了，买的人是管理员，用的人是员工。你设计插件的时候，就得同时讨好这两拨人。这跟消费级产品的思路差别很大。

文章最后还说，未来几周，会有一个统一的发现体验在 Claude 和 Claude Code 上推出，更多 MCP 特性和扩展也在路上。如果你已经有技能、连接器或者插件在目录里，不需要做任何改动。这一句是定心丸，也说明平台在做平滑演进，而不是推倒重来。对开发者来说，向前兼容的承诺非常重要，它意味着你今天投入的工程不会因为平台改版而打水漂。

好，讲完文章的核心内容，我们来聊聊对实际工作的意义。

第一种情况，你手里已经有一个能用的 MCP 服务器。我的建议是，先走最轻的那条路，也就是单连接器提交。原因很简单，先上线，先拿到数据，先验证需求。你不需要一上来就把自己包装成一个完整的插件包。等你在数据面板里看到真实的安装来源、版本分布、搜索词，再决定要不要升级成插件包，把技能编排加进去。这是典型的精益做法，用最小成本换取最大信息量。很多人会掉进一个陷阱，觉得既然平台支持打包，那我就一次性做全套。结果花了三个月，上线第一天发现没人搜你的品类，那三个月就白花了。

第二种情况，你只有一个 Agent Skill，没有连接器。文章说你不需要做任何改动，目录会继续列出技能。而且原文提到，未来开发者可以把连接器列表转成插件，但并没有承诺技能也能一键转换。所以我的判断是，技能作者现在应该把精力放在技能的描述质量和覆盖场景上，同时留意后续的转换路径。如果你真的想上插件形态，那就考虑补一个远程 MCP 服务器，或者找一个已有的服务器合作，把你的技能和别人的连接能力打包在一起。这种组合在目录里会更有竞争力，因为用户想要的是完整解决方案，不是半成品。

第三种情况，你在做 Claude Code 的工具链。那插件包这条路值得重点投入，尤其是语言服务器、钩子和子智能体。这三样东西是聊天端插件做不到的，也是你相对其他提交者的差异化壁垒。我之前举过框架插件的例子，这里再补一个。假设你做一个数据库相关的插件，里面可以打包一个理解 SQL 方言的语言服务器，让 Claude Code 在写查询时能给出准确的字段提示；一个生成迁移脚本的命令；一个在改动模型文件后自动检查索引的钩子；再加一个专门负责分析慢查询的子智能体。这一整套下来，用户基本上离不开你了。这就是工作流级别的锁定，比单纯的接口调用强得多。

第四种情况，你在企业环境里做内部工具。Enterprise Managed Auth 对你是关键。以前企业内部推广一个 AI 插件，最难的往往不是技术，而是安全团队点头。现在有了企业托管的授权机制，你可以把这部分交给 IT 管理员做统一配置，用户侧零操作。我的建议是，提前把合规材料准备好，包括数据流向、权限范围、日志保留策略，这些在安全扫描和审核环节都会被问到。你越主动，推进越顺。

第五种情况，你还没动手，只是在观望。那我想说，从这篇文章的描述来看，现在是一个非常合适的入场时机。基础设施已经就位，门户有了，自动验证有了，数据反馈也有了。你需要的只是一个能解决具体问题的小能力，先把它包成一个连接器提交上去。不要追求大而全，先跑通一遍流程，比什么都重要。

接下来讲几个要避的坑，这些都是从文章的字里行间推出来的，算是我的个人建议。

第一个坑，把提交门户当成营销渠道。它不是。数据面板里那些指标，最终是用来改进产品的，不是用来刷存在感的。如果你的列表被看了很多次但安装转化很低，问题很可能出在描述和首屏体验上，而不是曝光不够。

第二个坑，忽视版本管理。因为分析是按版本拆的，你的版本号策略会直接影响你能否读懂数据。建议使用语义化版本，每次改动明确对应一个可解释的变化。不要一天发五个小版本，那样数据会被切得七零八落，看不出趋势。也不要长期不升版本，那样新旧行为混在一起，出了回归你也定位不到。

第三个坑，一上来就做大而全的插件包。包越大，出问题的面越大，审核周期也可能越长。更稳的做法是先提交一个最小可用版本，跑通流程，拿到反馈，再逐步把技能、命令、钩子加进去。每一次增加都应该是数据驱动的，而不是拍脑袋的。

第四个坑，凭据管理。你的连接器大概率需要访问用户的第三方账号，那 OAuth 令牌怎么存、怎么刷新、怎么撤销，这些细节一旦出错就是安全事故。安全扫描会在这一步卡你，所以最好在提交之前就自己过一遍。我个人建议，把凭据管理当作产品的核心模块来做，而不是顺手写个脚本。

第五个坑，忽略发布时机的价值。文章特意说，批准之后由你决定何时发布。这意味着你可以做节奏管理。比如把发布和新版本功能对齐，或者和企业客户的培训排期对齐，或者避开你们团队休假的时间，确保上线后有人盯着数据。不要看到审核通过就手忙脚乱地按下发布键。

还有一个值得思考的方向。文章说插件正在成为第三方扩展的主要方式，而未来的发现体验会统一到 Claude 和 Claude Code。这其实意味着一个类似应用商店的生态正在成形。在应用商店里，早进入的开发者会享受先发优势，因为目录的位次、用户的心智、搜索词的占有率，都是先到先得的。我个人认为，现在这个时间点，相当于移动应用商店刚开放提交的那个阶段，基础设施已经就位，但供给还远没有饱和。对独立开发者和小团队来说，这是一个值得认真对待的窗口。

当然，也要保持冷静。平台的规则会变，审核标准会收紧，收录策略也可能调整。所以不要把全部身家压在一个渠道上。插件应该是你产品分发的一条腿，而不是唯一的一条腿。健康的做法是，把插件目录当成获取早期用户和反馈的地方，同时继续经营自己的官网、社区和其他分发渠道。

最后总结一下。这篇文章宣布了 Claude 插件目录的开发者提交门户正式开放，开发者可以通过它提交插件、跟踪审核、管理发布，并在上线后查看安装和发现数据。提交有两条路径，单 MCP 连接器和插件包，后者可以组合连接器与技能，在 Claude Code 里还能带上语言服务器、命令、钩子和子智能体。协议侧，Claude 支持带无状态核心的 MCP 二点零，并提供 MCP Apps 和 Enterprise Managed Auth 两个扩展，分别解决聊天内交互界面和企业授权的问题。已有的技能、连接器和插件不需要改动，未来连接器可以升级为插件，统一的发现体验会很快在 Claude 和 Claude Code 上推出。

我个人认为，这篇文章的价值不在于它宣布了多大的功能，而在于它补齐了生态闭环里最后一块拼图。协议有了，运行时有，能力也有人在写，缺的一直是分发和反馈。现在开发者第一次能在 Claude 生态里看到完整链路：写代码、提交、过审、发布、看数据、迭代。对一个平台来说，这意味着它开始从工具走向市场。

而市场的规律是，早到的人拿到位置，位置又带来更多的用户和更好的数据。所以如果你手上正好有一个能帮上别人的 Claude 扩展，我建议这两天就去把文档读一遍，先提交一个最小版本。早提交的收益不只是曝光，更重要的是你会更早拿到真实用户的反馈，而这在 AI 这个变化速度的赛道里，往往比什么都值钱。
