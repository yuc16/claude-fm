先看无状态核心。原文说，MCP 从一个双向有状态协议，转向请求响应模型。服务器现在可以部署在 serverless 和 edge infrastructure，也就是无服务器和边缘基础设施上。这会简化为 Claude 构建 MCP server 的体验，并且在采用规模增长时更容易扩展。

这里的有状态和无状态，很多听众应该不陌生。我们平时写 Web 服务，会区分一个服务是不是依赖某个长期会话状态。无状态服务通常是客户端发一个请求，服务端根据请求里的信息和后端存储处理完，然后返回响应。下一次请求来了，理论上可以打到另一台机器，因为这台机器不用记得上一台机器内存里发生了什么。有状态服务则不一样，它可能维护长连接、会话上下文、订阅状态、双向通信通道。这样做有时很自然，尤其是需要实时交互的时候，但扩容、故障恢复、负载均衡都会复杂不少。

把这个放到 MCP 里看，早期协议采用双向有状态模型，有它的合理性。AI agent 和工具之间的交互可能不是简单的一问一答，可能需要 server 主动发事件，可能有资源订阅，可能有持续会话。对于早期开发者来说，协议表达力强，能快速支持复杂场景。但当 MCP 服务器数量变多、调用量变大、部署环境变复杂的时候，有状态就会变成摩擦。比如你想把 MCP server 部署到 serverless 平台，函数可能短时间启动、处理、结束，不适合长期维持连接。你想把它部署到 edge 节点，让用户离得更近，降低延迟，也希望每个请求都可以独立路由。你想自动扩容，希望流量高峰时多起几个实例，低峰时缩掉，不想处理粘性会话，也不想担心某个实例挂掉之后会话状态丢失。

所以无状态核心的意义，并不只是协议风格变了，而是把 MCP server 从一种更像长驻应用服务器的形态，推向更像现代云原生 API 的形态。对于工程团队来说，这意味着你可以用更熟悉的请求响应思路来构建连接器。比如一个连接器负责查公司知识库，Claude 发来一个请求，说请按这个查询词搜索并返回结果。server 处理请求，校验权限，调用后端搜索服务，返回结构化响应。这一次结束之后，它不需要把和 Claude 的长会话状态留在内存里。下一次用户再问，可能打到另一个实例，也没有关系。

当然，原文没有展开无状态核心的具体迁移细节，也没有说所有扩展能力都只能是简单请求响应。它强调的是核心协议变成无状态，而一些更复杂的能力通过标准化扩展来承载。这里我个人认为，一个很重要的设计取舍是，把基础层做薄、做稳定、做容易扩容，把复杂能力放在可版本化、可选择的扩展里。这样协议不会因为每增加一种能力，就把核心变得越来越重。对于做平台的人来说，这个方向很熟悉：核心越小，兼容性越好；扩展越规范，生态越容易成长。

你可能会问，无状态会不会让开发者失去一些表达能力？比如长时间任务怎么办？用户界面怎么办？这就引出文章里的第二个变化：标准化扩展。原文说，MCP Apps 和 Tasks 现在被放在一个带版本的 extensions framework，也就是扩展框架下面。开发者有了正式路径，可以添加 interactive UIs，也就是交互式用户界面，以及 long-running work，也就是长时间运行的工作，而不需要改变核心协议。

这个点非常关键。很多协议一开始都很优雅，但生态一热起来，大家开始有各种需求。有人想让工具返回一段文本，有人想返回一个按钮，有人想嵌入一个表单，有人想展示一个图表，有人想让任务跑半小时再回来，有人想让用户中途确认。假如没有扩展框架，大家就会各自发明字段，各自定义事件，各自写兼容逻辑。短期看速度快，长期看就会碎片化。一个客户端支持 A 家扩展，不支持 B 家扩展；一个 server 在 Claude 里能用，在另一个环境里就变形；开发者不知道该依赖什么稳定能力，用户体验也不一致。

MCP Apps 的价值，是让 server 可以直接在对话中渲染交互式界面。文章里说，用户可以看到一个 connector 正在做什么，并且直接在对话里和它一起工作，不需要切换标签页。你可以想象一个很常见的企业场景：用户问 Claude，帮我看看本周销售漏斗里高风险的机会。传统聊天机器人可能返回一段文字，说有三个机会风险比较高。更进一步的 connector 可以展示一个小表格，让用户筛选地区、负责人、阶段，点击某个机会查看详情，或者直接在对话里确认是否要创建跟进任务。MCP Apps 的方向就是把这种交互嵌入对话，而不是把用户踢到另一个网页里。

从产品体验看，这件事非常重要。AI 工具最大的优势是把很多操作聚合到一个自然语言入口，但如果每一步都要跳出去登录、打开新页面、复制粘贴，再跳回来，体验就会碎。用户会觉得，我还不如直接去原系统操作。能在对话里展示可理解、可操作的界面，等于让 agent 的行为更透明，也让用户更容易纠错。尤其在企业环境里，用户不可能完全信任一个黑盒自动操作。你让它展示正在查什么、将要改什么、需要用户确认什么，信任感会高很多。

MCP Tasks 则对应另一类问题：长时间运行的工作。我们平时写一个工具调用，最好几秒钟内返回。但现实中很多任务没那么快。比如生成一份月度经营分析，需要跑多个数据仓库查询，汇总报表，调用权限审批，再生成文档。或者让 agent 扫描一个大型代码仓库，找出迁移到新框架的影响范围，这可能需要排队、分批处理、持续反馈。再比如把一批客户记录同步到另一个系统，中间要处理失败重试和人工确认。这些都不是简单的同步请求可以优雅处理的。

如果核心协议强行承担长任务，就会让核心变复杂。要定义进度、取消、恢复、通知、结果领取、错误状态，还要考虑客户端重启、网络中断、权限过期。把 Tasks 作为版本化扩展来推进，逻辑上更干净。支持长任务的客户端和 server 可以按扩展规范协同；不需要长任务的场景，就继续用无状态核心的请求响应。这里我个人认为，Anthropic 在做的是一种分层治理：核心协议保证最低共同能力，扩展框架保证高级能力有路可走，而不是靠私有约定野蛮生长。

第三个大变化是授权强化。原文说，Authorization 现在对齐生产级 OAuth 二点零和 OIDC 部署，所以 MCP servers 可以连接到企业身份系统，比如 Entra 或 Okta，而不需要 workaround，也就是不需要绕路和变通方案。这里对企业开发者来说，含金量很高。

做过企业集成的人都知道，真正拦住上线的往往不是模型能力，而是身份和权限。demo 阶段你可以用一个 API key，或者让每个用户手动粘贴 token。到了生产环境，安全团队会问一串问题：用户是谁？他属于哪个组？他有没有权限访问这个数据？离职之后权限会不会自动失效？管理员能不能统一开关？审计日志在哪里？token 怎么轮换？多租户怎么隔离？如果答案不清楚，哪怕功能再炫，也很难进入公司核心流程。

OAuth 二点零和 OIDC 是现代企业身份体系里非常常见的标准组合。OAuth 更关注授权，也就是一个应用能代表用户访问哪些资源。OIDC 建立在 OAuth 之上，更关注身份认证，也就是确认用户是谁。Entra，也就是微软的企业身份平台，和 Okta 这类身份提供商，是很多公司管理员工账号、组、应用访问权限的核心系统。MCP 授权对齐这些生产部署，意味着连接器不需要用一些临时方案去适配企业身份，而是可以更自然地接入已有 IdP，也就是身份提供方。

文章在后面提到 Claude 今年已经推出了 enterprise-managed auth，也就是企业托管认证。管理员可以通过身份提供方为整个组织配置 MCP connectors。管理员授权一次，用户通过已有 IdP 组继承访问权限，第一次登录时就已经连接好，对终端用户来说是零接触设置。这里的零接触很值得注意。很多企业 AI 工具推广失败，不是因为模型不好，而是因为每个员工都要自己配置一遍连接器，授权流程复杂，遇到错误不知道找谁。管理员统一配置，用户自然继承，才符合大组织的运维方式。

举个例子，一个公司希望在 Claude 里接入内部工单系统。安全团队希望只有研发和运维组能创建工单，销售组只能查询自己的客户相关工单，外包账号不能访问。最理想的方式不是让 connector 自己维护一套用户表，也不是让每个人手动申请一个 token，而是沿用公司已有的身份组。用户在 Entra 或 Okta 里属于哪个组，Claude 里的连接器就按这个组授予能力。这样员工入职、转岗、离职时，权限变化跟随企业身份系统，AI 连接器不用变成新的权限孤岛。

这次规范还和 Claude 产品里的 MCP 能力演进放在一起讲。文章说，Claude 现在在 connectors directory，也就是连接器目录里列出了超过九百五十个 MCP servers，每天有数百万人使用。这个数字说明 Claude 已经不只是一个单独聊天产品，而是在把 MCP 连接器当成一个生态入口。对开发者来说，连接器目录有点像应用商店，用户可以发现、安装、使用你的服务。对企业来说，它也是治理入口：哪些连接器可用，谁能用，如何授权，如何监控，都需要平台能力支撑。

Claude 今年还推出了几个和 MCP 生产化相关的功能。前面讲过 MCP Apps 和企业托管认证，文章还提到 observability for developers，也就是给开发者的可观测性能力。对于发布在 Claude 目录里的连接器，开发者可以看到一个仪表盘，了解它们在 Claude 不同产品界面里的表现。可以追踪采用情况，诊断错误和延迟，并且按产品拆分使用量。

这个功能看似是后台小工具，其实对开发者非常实用。你做了一个 connector，上线之后最怕什么？最怕用户说不好用，但你不知道哪里不好用。是认证失败多？是某个接口延迟高？是 Claude 桌面端用得多，网页端没人用？是某个工具调用经常返回格式错误？没有观测，你只能靠用户反馈猜。AI 连接器还有一个额外复杂点：很多错误不是传统意义上的五百错误，而是模型选择工具不稳定、参数填错、权限提示不清楚、结果太慢导致用户中断。虽然原文没有展开这些细节，但它提到的采用、错误、延迟和产品拆分，至少说明 Anthropic 在把连接器当成需要运营的生产软件，而不是一次性集成。

如果你是做后端的，可以把 MCP connector 当成一组对 AI agent 开放的 API，但它和普通 API 又不完全一样。普通 API 的调用方是程序，参数往往确定，错误处理路径可控。agent 调 API，前面还有一层模型推理，它可能根据用户一句模糊的话选择工具、组织参数、解释结果。你要观测的不只是服务健康，还包括用户是否真的从工具结果里获得价值。文章里没有说 Claude 的仪表盘能做到多细，但它提出这个方向，至少是在补生产闭环。

还有一个很有意思的能力是 MCP tunnels，目前是 research preview，也就是研究预览。原文说，它可以把 Claude 连接到私有网络里的 MCP servers，而不需要把这些 server 暴露到公网。团队可以把内部工具带到 Claude 里，不需要入站防火墙规则，不需要公共端点，也不需要在源站做 IP allowlisting，也就是 IP 白名单。

这点对企业内部系统特别重要。很多公司最有价值的工具都在内网：部署平台、监控系统、数据查询平台、知识库、权限后台、财务审批、工单系统。把它们接给 AI 很有吸引力，但安全团队通常不愿意为了一个连接器开公网入口。传统做法可能是建 VPN，做反向代理，配置白名单，或者把服务暴露到某个中间层。每一步都增加运维成本和攻击面。MCP tunnels 的目标，是让 Claude 能访问私有网络里的 MCP server，同时不要求源站暴露公共端点。原文没有详细说明 tunnel 的实现方式，也没有给出可用性承诺，只明确说是研究预览，所以我们不能把它理解成已经完全成熟的企业网络方案。但方向很清楚：Anthropic 知道企业 adoption 最大障碍之一就是网络边界。

把这些点连起来看，MCP 二零二六年七月二十八日规范和 Claude 产品更新其实是在回答同一个问题：怎么让 AI agent 真正进入生产系统。无状态核心回答部署和扩展问题。标准化扩展回答复杂体验和长任务问题。强化授权回答企业身份和安全问题。观测能力回答上线之后怎么运营的问题。私有网络 tunnel 回答内部工具怎么安全接入的问题。连接器目录回答生态发现和分发的问题。这已经不是单纯给模型加几个工具，而是在搭一整套 agent 应用层基础设施。

那对我们这些软件工程师和 AI 从业者，具体意味着什么？如果你现在正在做 MCP server，或者计划把公司系统接到 Claude，我个人建议先从服务形态入手，重新审视你的 connector 有没有把状态绑在单个进程里。比如你是不是在内存里保存了用户会话、任务状态、临时授权信息、工具调用上下文。如果未来要适配无状态核心，最好把关键状态放到外部存储或后端系统里，让每个请求可以被任意实例处理。不要把 connector 写成必须长期在线、必须某个连接不断、必须某台机器记住上下文的形态。这样不仅更贴合新规范，也更容易部署到 serverless、容器自动扩缩容和边缘环境。

但这并不是说所有状态都消失了。业务当然有状态。订单状态、工单状态、任务进度、用户偏好都还在。无状态说的是协议核心和服务处理方式尽量不依赖连接状态。工程上可以这样理解：请求之间需要共享的东西，放到数据库、队列、缓存、对象存储、任务系统里；单个运行实例只负责处理当下请求。这样一来，实例挂了可以重试，请求量上来可以横向扩容，部署位置可以更灵活。对于很多团队，这也是从 demo 代码走向生产代码的一道分水岭。

如果你的 connector 需要交互式界面，不要急着自己发明一套嵌入 HTML 或自定义 JSON 的私有协议。文章明确说 MCP Apps 已经在版本化扩展框架下发布。更稳妥的路径是研究官方扩展怎么表达 UI，哪些客户端支持，版本兼容策略是什么。比如你想在 Claude 对话里展示一个审批卡片，里面有金额、申请人、理由、同意和拒绝按钮。你要考虑的不只是能不能展示，还要考虑用户点击之后的授权校验、审计记录、重复点击防护、网络失败重试、以及模型是否能正确解释这个 UI 的状态。标准化扩展会让这些问题更有共同语言。

如果你的 connector 涉及长任务，也要避免用一个超长同步请求硬扛。很多工程事故都来自这种设计：用户发起一个操作，后端接口一直挂着，网关超时了，客户端以为失败，服务端其实还在跑，用户又点一次，结果任务重复执行。长任务应该有任务 ID，有状态查询，有取消或超时策略，有最终结果领取，有幂等设计。文章说 MCP Tasks 进入版本化扩展框架，意味着这类场景会越来越有标准做法。你可以把内部任务队列和 MCP Tasks 对接，让 Claude 发起任务后获得可追踪的进度，而不是让用户在聊天框里干等。

身份和授权方面，如果你还在用单个共享 API key 作为 connector 的访问凭据，最好尽早升级设计。共享 key 在 demo 阶段省事，但在企业环境里很难回答谁做了什么。更好的方式是让每个用户通过企业 IdP 授权，connector 能拿到代表用户或代表组织的访问上下文，再根据后端系统权限执行操作。文章强调对齐 OAuth 二点零和 OIDC，以及 Entra、Okta 这些系统，说明未来企业采购和安全评审会越来越期待这种标准集成。你不一定一开始就把所有权限模型做得极其复杂，但至少不要把架构锁死在无法区分用户的模式里。

这里还有一个容易忽略的坑：AI agent 的权限不应该因为它很聪明就自动扩大。Claude 能帮用户操作系统，但它应该继承用户原本拥有的权限，而不是拿一个超级管理员 token 到处跑。管理员授权 connector，也不等于所有用户能做所有事。比较安全的模式是，connector 暴露的工具能力、用户身份组、后端资源权限、操作审计要对齐。比如查询知识库和删除记录是两种完全不同的风险等级。你可以允许广泛查询，但删除、发布、转账、发邮件这类高影响操作，需要更严格的确认和记录。原文没有展开这些安全实践，这是我个人基于企业集成经验的建议。

可观测性方面，如果你准备把 connector 提交到 Claude 的连接器目录，不要等到上线后才想日志怎么打。你需要从一开始就定义关键指标。比如认证成功率、工具调用成功率、平均延迟、尾部延迟、后端依赖错误、用户取消率、长任务完成率。还要注意不要把敏感数据随便打进日志。AI 工具调用里可能包含用户问题、客户名称、代码片段、内部文档标题，这些都可能是敏感信息。文章说 Claude 会给目录里的发布连接器提供仪表盘，帮助追踪采用、错误和延迟。你自己的服务端也应该有对应观测，这样当仪表盘显示某个错误上升时，你能回到自己的链路里定位。

网络部署方面，如果你的目标是接内部系统，可以关注 MCP tunnels，但要记住它目前只是研究预览。研究预览意味着可以探索、可以试点，但不要默认它已经满足所有生产合规要求。你需要和安全团队一起看数据流向、认证方式、密钥管理、审计和故障模式。即使未来 tunnel 方案成熟，也不代表内部工具可以毫无边界地接给模型。最好的做法仍然是最小权限、清晰工具定义、明确用户确认、高风险操作可回滚或可审计。AI 接入内网越方便，治理就越要跟上。

对应用开发团队来说，这次规范还带来一个产品策略上的提醒：连接器不是越多越好，而是越可理解、越可靠越好。Claude 的目录已经有超过九百五十个 MCP servers，每天数百万人使用。生态变大之后，用户会面临选择成本。你的 connector 如果工具名称模糊、描述不清、权限请求吓人、第一次认证就失败、响应经常超时，就很难留下用户。反过来，如果你能把一个核心工作流做顺，比如查数、生成报告、提交工单、审批流程、代码检索，配合清晰的 UI 和稳定授权，它就可能成为用户每天都用的入口。

如果你是平台团队，可能还要考虑公司内部的 MCP 治理。随着 MCP 变成行业标准，业务部门可能自己写 connector，供应商也会提供 connector，安全团队会要求统一审查。你可以提前设计一个内部目录，规定哪些 connector 可用于生产，哪些只能实验，哪些可以访问敏感系统。你也可以制定开发规范，比如必须支持企业身份，必须有审计日志，必须有超时和幂等，必须通过安全扫描，必须明确工具能力边界。MCP 的开放标准降低了集成门槛，但也会让连接数量迅速膨胀。没有治理，最后可能变成新的影子 IT。

对于 AI agent 开发者，这篇文章还有一个更底层的信号：未来 agent 能力的竞争，不只在模型本身，也在模型能接触到的上下文和行动空间。谁能更安全、更标准、更低摩擦地把业务系统接进来，谁就能让模型真正产生生产力。Claude 本身很强，但如果它只能回答公开知识，它对企业价值有限。接上工单、代码库、文档、数据仓库、客户系统之后，它才可能变成员工工作台。MCP 就是这个工作台背后的插座标准，而这次规范是在升级插座的电气规范、安装方式和安全认证。

当然，我们也要保持一点冷静。文章是 Anthropic 自己的发布稿，目标是宣布新规范和 Claude 支持计划，所以它会强调方向和好处，不会展开迁移成本、兼容性细节、不同客户端支持进度、以及现有 server 需要改多少。原文最后说，支持会很快在 Claude 产品中逐步推出。也就是说，如果你今天就要上生产，仍然要查看最新 spec 和 SDK，确认你依赖的功能在哪个产品面已经可用。特别是 Apps、Tasks、tunnels 这类扩展和预览能力，最好逐项验证，不要只根据文章标题做架构承诺。

如果你想上手，原文的建议很简单：去看 spec 和 SDK，开始构建。如果计划把 MCP server 提交到 Claude 的连接器目录，可以参考相关提交流程。结合今天的内容，我建议你上手时可以按一个小闭环来做。先选一个低风险但高频的内部场景，比如查询文档、搜索工单、读取项目状态。用新的无状态思路实现一个最小 connector。接入企业身份或至少设计好未来接入企业身份的接口。加上基础日志和指标。然后让一小组真实用户试用，观察他们在 Claude 里怎么问、工具怎么被调用、哪里容易失败。等这个闭环跑顺，再考虑 Apps 的交互界面、Tasks 的长任务、以及更敏感的写操作。

收尾总结一下。Anthropic 这篇文章表面上是在宣布 MCP 二零二六年七月二十八日规范，但核心信息是 MCP 正在进入生产基础设施阶段。无状态核心让部署和扩展更简单，标准化扩展让 UI 和长任务有正式路径，强化授权让企业身份接入更自然，而 Claude 侧的目录、观测、企业认证和 tunnel，则是在把这个协议变成可用的产品生态。

我个人认为，这次发布对开发者最大的提醒是：不要再把 AI 连接器当成一次性 demo。它正在变成企业软件的一部分，需要协议兼容、云原生部署、身份治理、可观测性和安全边界。如果你所在团队已经在做 agent 平台，MCP 这次规范值得认真跟进；如果还没开始，也可以把它当作观察 AI 应用基础设施走向的一个重要窗口。
