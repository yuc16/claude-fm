## Script

这篇文章的标题是 Claude Cowork and chat are now one Claude，中文可以翻译成《Claude Cowork 和聊天，现在合为一个 Claude》。文章发表于二〇二六年九月十六日，距离今天只有四天，来自 Anthropic 的官方博客，原文标注的阅读时长是五分钟。

虽然这只是一篇很短的公告，但我觉得它值得单独做一期节目。因为它讲的不是某个新功能上线，而是一次产品方向的回调。Anthropic 把原本分开的两个入口，聊天和 Cowork，重新合成一个。对正在做 AI 助手、agent 或者企业内部工具平台的同学来说，这篇文章里藏着一个非常具体、也非常值得抄的设计判断。

我先给你一个三十秒的概览，然后我们再慢慢拆。从今天起，你不需要再决定一个任务该放到哪里去，Claude 自己会判断。你可以在任何一段对话里，得到原本只有 Cowork 和 Design 才具备的能力，而且你已有的上下文、技能和连接器都会跟着一起过来。同时，Anthropic 发布了 Claude Docs 和 Claude Slides，Claude Design 也搬进了对话里。这些会先上 Pro 和 Max 计划，未来几周内推给网页版、桌面版和移动版。

我们先回到问题的起点。

任何一个做过 AI 产品的人都会遇到同一个选择题：到底是做一个万能的对话框，还是做很多个专门的入口。这两种做法各有各的道理。一个对话框的好处是简单，用户不需要学习，打开就能用，也不用理解你的内部结构。坏处是它承载不了复杂任务，聊到第五十轮，上下文开始混乱，你自己都找不到刚才那份草稿放在哪里。

多个专门入口的好处是每个场景都能做得更深。做文档的地方可以给你排版工具，做视觉的地方可以给你一块画布，做长任务的地方可以给你任务队列和后台执行。坏处也很明显，用户得先做一个分类判断，我这件事到底算哪一类。而这个判断，往往是用户最不想做、也最容易做错的一步。

Anthropic 走的就是后一条路。文章里说得很直白，他们把 Cowork 建成了一个独立的地方，用来承接更大的工作，把 Design 建成了一个独立的地方，用来做视觉相关的工作。这两个东西本身都做得不错，用户也确实都在用。

问题出在交界处。

文章里有一句话我觉得是整篇文章的核心，原话大意是，人们两个都在用，然后告诉我们，最让人沮丧的部分，是决定一个任务到底属于哪里。而且，你在其中一个里面开始的东西，也不会带到另一个里面去。

这句话描述的是所有多入口产品共享的通病。你可以想象一下你家里有两张书桌。一张大桌子用来写长报告，另一张小桌子用来做设计和排版。听上去很合理，分工明确。但你每次坐下来之前，都得先在心里做一次分类。更麻烦的是，你在写报告的桌子上摊开了十份资料，写到一半突然想做一个信息图，你得抱着这些资料换到另一张桌子，而且换过去之后，你还得重新解释一遍你手上这些东西是什么、你想干什么、之前已经做到哪一步了。

这种摩擦在用户量小的时候并不明显，因为早期用户通常很懂你的产品，他们心里有一张清晰的映射表，知道什么该放哪里。但当产品走向主流，用户根本没兴趣理解你的内部架构。他们只想知道一件事，我把事情交给你，你能不能办完。

所以 Anthropic 的回应是，我们不让你选了。

文章原话是，我们不再让你做这个选择。Claude 现在可以自己判断一个任务需要什么，于是 Cowork 和 Design 能做的事情，从任何一段对话里都可以调用，并且会带上你已有的上下文、技能和连接器。

这里有几个词需要解释一下，因为它们决定了这次合并到底合并了什么。

上下文，指的是你在这一段对话或者这个项目里已经积累的信息，包括你之前说过的话、你上传的文件、你表达过的偏好。技能，指的是你事先配置好的一些能力或者套路，比如你们团队固定的写作风格、某个标准的分析流程。连接器，指的是把外部系统接进来的通道，通常是让你公司的数据库、文档系统或者代码仓库，能够被 Claude 访问和操作。

这三样东西才是用户真正的资产。一个 AI 产品做久了，用户最舍不得的其实不是你的模型有多强，模型能力半年就会拉平，而是他在你这里积累下来的这些配置和记忆。所以这次合并最大的价值，不是界面上少了一个按钮，而是这些东西终于可以在所有场景里复用了。以前你在聊天里配好的技能，到了 Cowork 里可能得再配一遍；现在不需要了。

文章里给了一个用户的例子，是安德鲁·凯勒，一位高级经济学家。他说，我可以让 Claude 打开我的法律研究数据库，它会把所有的判例拉出来，读一遍，判断我可能还需要哪些别的判例，把它们下载下来，存到一个文件夹里，供我个人审阅。

这个例子很值得琢磨。你把它拆开看，它至少包含六个动作。第一，连接到一个外部的专业数据库。第二，按条件做检索。第三，把检索结果读进来。第四，做一次推理，判断哪些相关的东西还没有拿到。第五，执行下载。第六，归档到一个有结构的地方。而最后一步是人对结果做审阅。

这就是所谓的多步骤自主任务。它的难点不在任何一个单一步骤，检索、下载、存文件，这些技术上都不新鲜。真正的难点在中间那个判断，也就是我还需要什么。这一步要求模型理解你的意图和目标，而不是机械地执行指令。而最后那句话特别重要，存到一个文件夹里供我个人审阅。也就是说，这个循环的出口是人的判断，不是自动对外发布。这解释了后面我们会讲到的控制权设计。

文章里第二个例子更具体，我建议你仔细听，因为它几乎就是一个未来工作日的完整切片。

场景是这样的。你有一份周报，中午要交。你出门之前，问 Claude 上周的管线里有什么变化，然后补上一句，按我们一贯的写法来写，把任何出现滑坡的地方标出来，再把要点做成五页幻灯片，给管理层会议用。

注意这句话的信息密度。它同时包含了几件事。一个内容要求，上周管线里的变化。一个格式要求，按我们一贯的写法。一个判断要求，把滑坡的地方标出来，这其实是在告诉它什么算重要。还有一个衍生产物的要求，把这些要点做成给管理层看的五页幻灯片。

如果有不清楚的地方，Claude 会来问你。这一点很关键，它说明这不是一个只能一次成型的批处理任务，中间是可以有来回的。

然后你出门了。你在去办公室的路上用手机看进度。等你到工位的时候，报告已经在等着你了，是一份文档，上面还有你同事留下的批注，幻灯片也准备好了，你可以打开、调整、下载成 PowerPoint。

这里有一句话，我认为是整篇文章里技术含量最高的一句。原话是，两者出自同一段对话，所以幻灯片和报告天然是对齐的。

为什么这句话重要？因为在现实世界里，报告和演示文稿不一致是一个长期存在的顽疾。通常的流程是，某个人写了一份详细报告，然后另一个人，或者同一人，再从中提炼出一版幻灯片。提炼的过程，就是信息丢失和数字出错的过程。三个月后有人翻出幻灯片，发现上面的增长率和报告正文里的对不上，然后开始一场漫长的排查，最后也不知道到底哪个版本才是对的。

如果文档和幻灯片是从同一段对话、同一份上下文里同时生成的，这种不一致从源头上就不容易发生。你在对话里更新了一个数字，理论上两份产出都知道这个数字变了。这是一个看起来很小、实际上能省掉大量返工的设计。它把一致性问题从流程问题，变成了架构问题。

接着你做最后的收尾。你自己改了一行，在某一页幻灯片上给 Claude 留了一个评论，然后分享出去。你还可以把它设成每周一自动执行，这样 Claude 不需要你催就会开始做报告。

这个设成每周一是一个信号。它意味着这个产品正在从你问它答，走向它按计划自己动。这是 agent 产品最重要的一次跨越。因为一旦任务可以被排期，它就真的更接近一个同事，而不是一个工具。工具需要你伸手，同事会在你没伸手的时候也开始工作。

接下来我们看产品层面的三件套。

文章里说，Claude Docs 和 Claude Slides 是今天新发布的，Claude Design 现在也可以在你的对话里工作。你要一份文档，你和 Claude 一起写。你要一个演示，Claude 起草幻灯片。你可以直接编辑，可以直接从 Claude 里演示，也可以下载成 PowerPoint 或者 PDF。

这里我想强调两点。

第一点是「一起写」这个措辞。它不是说生成一份文档给你，而是说你和 Claude 一起写。这个区别在产品体验上非常大。生成给你，你拿到的是一个要么整体接受、要么整体丢弃的东西，你更像一个审稿人。一起写，意味着文档是一个持续编辑的对象，你可以改一段、留个评论、让它再改一段，你始终是作者之一。

第二点是下载格式。PowerPoint 和 PDF 这两个选项的选择，非常务实。因为无论 AI 多能干，你最终还是要在一个真实的会议室里，用一台真实的电脑，打开一份真实的文件。你的老板、你的客户、你的合规部门，不会因为你说这是 Claude 生成的，就接受一个网页链接。能导出成 PowerPoint，意味着这份产出可以被纳入现有的工作流，被转发、被存档、被审计、被归档到公司的知识库里。这一小步，是 AI 产出从玩具变成正式交付物的分界线。

然后文章提到，你用这三样东西做的任何内容，都存在于一个可分享的链接里，你可以在手机上打开。你可以选中一个元素把它挪走，也可以直接告诉 Claude 你想改什么。这个细节依然围绕同一个思路，让产出脱离某一个设备、某一个应用，跟着你走。

还有一个治理细节，文章说这三个功能在付费计划上是 beta，企业管理员可以自己决定什么时候打开。如果你单独使用 Claude Design，它照旧工作，不会因为这次合并就消失或者改版。

再往下，是我个人认为这次更新里最耐人寻味的一段，就是关于控制权的设计。

文章说，你可以选择 Claude 怎么跟你确认。默认情况下，Claude 在采取行动之前会先问你。如果你更希望让它一直做下去，只在有东西需要更仔细看一眼的时候才来找你，你可以把这个打开。最后一句是，你保留最终的决定权。

这个设计的精髓，在于默认值和可选性的组合。

默认是行动前先问。这是一个保守的默认。为什么必须保守？因为一个会自己动手的助手，一旦动错了，代价可能比不干还大。它可能删掉一个文件、发出一封本该草稿的邮件、改错一个对外数字。所以在用户建立信任之前，默认必须是最小惊讶原则，每一步都让你看得见。

但是如果你每天都用它，每做一步都来问你，那就会变成一种打扰。你人在会上，它在旁边问你要不要继续，这比自己动手还累。所以必须提供一个开关，让你可以说，你放手做，只在关键的地方停下来。

这个模式其实很像带一个新人。第一天，你希望他每一步都来跟你确认，因为你还不知道他会怎么判断。三个月以后，你希望他自己拿主意，只在真正模糊的时候才来敲你的门。产品要能陪着用户走完这条信任曲线，而不是一上线就要求用户全盘信任。

对做 agent 的同学来说，这里有一个很实用的启示。不要只做全自动或者全手动两个极端，要把检查点的粒度做成可配置的。你可以想象几个档位。每一个动作都确认，是一个档。只在写操作之前确认，比如要改文件、发消息的时候才停下来，是一个档。只在涉及外部系统或者对外发布的时候确认，是一个档。只在成本超过某个阈值时提醒，是一个档。完全自主，但事后给你一份完整的操作报告，又是一个档。每一档对应不同阶段的信任，也对应不同的用户群。企业客户可能永远停在第二档，而个人用户几天之后就调到第五档了。

接下来是迁移这块，我觉得它是产品经理最该注意的部分。

文章说，如果你主要用聊天，你不需要做任何不一样的事情。当你想交出去一个更大的东西时，就试试下一份你本来要自己做的报告或者演示文稿。如果你一直在 Cowork 里工作，所有东西都在你离开的地方，包括你的聊天、项目、产出物、连接器和技能。打开应用，从你停下的地方继续。

这里说的产出物，在 Claude 的语境里，通常指的是那些可以独立存在、独立保存和编辑的生成结果，比如一份文档、一段代码、一张图。它们不属于某一段特定的对话，而是你账号里的长期资产。

这一段话为什么值得单独讲？因为对任何做过产品合并的人来说，最怕的就是数据迁移。用户最怕的是，你们改了个版本，我攒了两年的东西没了。所以文章专门用一段来安抚老用户，告诉他们在哪、没变、打开就能继续。这本身就是产品沟通上的正确做法。做减法的时候，安抚成本往往比开发成本还高。

最后我们看上线节奏和治理。

文章说，这个东西先在 Pro 和 Max 计划上推出，会在未来几周内，通过 Claude 的网页版、桌面版和移动版，推给这两个计划的现有用户和新用户。不需要打开任何开关。Team 计划和 Free 计划随后跟上。企业管理员会在任何改动发生之前，至少三十天收到通知。

那个至少三十天，我要多说两句。在企业软件里，这个提前期不是客套，而是刚需。因为企业客户往往要在这三十天里做完一整套事情。要评估这个功能会不会带来数据合规问题，要更新内部的使用规范，要培训员工，要跟法务确认，甚至要调整采购合同。突然给企业用户换一个界面，是一件会被直接投诉到销售那边的事情。

所以这篇文章虽然短，但它在每一个段落里都留了治理的口子。对个人用户是，不需要打开任何开关，直接用。对企业用户是，管理员决定什么时候开。这两种节奏完全不同，同一篇公告里同时照顾到，说明它是在给两拨完全不同的客户说话。这是个值得学的沟通技巧。

好，前面我们把文章的内容拆完了。接下来我想花一点时间，聊聊这些东西对你在实际工作里意味着什么。

第一，如果你在做 AI 产品，这次合并给出的最大启示是，入口的数量应该由用户的认知负担决定，而不是由你的技术架构决定。

很多时候，我们做产品会不自觉地按照内部架构来切分界面。我们有检索模块、有生成模块、有工作流模块、有可视化模块，于是我们就给用户四个入口。但用户的心智里没有这些模块。用户的心智里只有一句话，我要交一份周报。你把你的架构投射到界面上，用户就得为你的架构买单。

这次 Anthropic 的做法，是把分类这件事从用户手里收回到模型手里。这是一个很难、但很正确的方向。说它难，是因为分类做错的代价会比不做分类更高。如果用户自己选错了入口，他会怪自己。如果模型自动判断错了，他会怪你。所以你要有很强的意图识别能力，还要有很好的兜底路径。

如果你要借鉴这个设计，我建议你先想清楚三件事。第一，你怎么判断一个任务需要哪种能力，是靠对话开头一次轻量的意图识别，还是等对话推进到某一步才动态切换。第二，判断错了怎么办，用户有没有一个明确而且低成本的纠正动作。第三，能力切换的时候，上下文能不能无损地跟过去，包括文件、历史、你配好的技能。第三点最容易被忽略，也最容易出问题。因为如果上下文带不过去，那只不过是把两个入口的割裂藏到了一个入口的内部而已。

第二，上下文、技能、连接器这三样东西，才是 AI 产品真正的护城河。

模型能力是会拉平的。今天你领先半代，半年后可能就没有了，甚至开源模型就追上来了。但用户在你这儿积累的项目结构、写作偏好、接好的数据源、调好的工作流，是搬不走的。所以当你在设计产品的时候，要反复问自己一个问题，用户在我这里积累了什么？如果答案是，什么也没有，每次都是从零开始，那你的用户流失率一定会很高，因为你的切换成本对用户来说是零。

反过来，这次合并之所以有价值，正是因为它让这些积累可以在所有场景里复用。你的技能和连接器不再是某一个小入口的附属品，而是整个产品的基础设施。这个思路对所有做 AI 工具的人都适用。

第三，关于异步执行。

即使你关掉笔记本电脑这个表述看起来不起眼，但它背后的工程量不小。它意味着任务要能在服务端持续运行，要能感知进度，要能被中断和恢复，还要能在你不在的时候做出一些安全的判断。你在手机上能看到进度，意味着后台任务要有一个可观测的界面，要能把当前状态、已完成的部分、卡住的地方都呈现出来。

如果你在做类似的内部工具，这是一个可以马上借鉴的点。很多公司内部的 AI 工具都是一个网页，你输入问题，它流式输出，你一关标签页，任务就死了。把任务变成后台作业，并且提供一个进度视图，体验上的差别是巨大的。你的用户会开始把长任务交给它，因为他知道中途可以去开会。

第四，关于交付格式。

PowerPoint 和 PDF 这两个导出选项，是最容易被低估的功能。因为企业内部的信息流转，绝大多数还是在这些文件里发生的。邮件附件、会议材料、归档目录，全是它们。任何 AI 产出的东西，只要不能落地成这些格式，它的可用范围就会被限制在给我看看这个层级。你没法把它发给客户，没法放进季度的存档，没法让它进入正式流程。所以如果你在产品里做文档生成，一定要尽早做导出，而且要保证导出之后布局不崩。这不性感，但它决定了你的产出是玩具还是工具。

第五，说几个我想提醒的坑。

第一个坑，是 beta 阶段的稳定性。文章明说了这三个功能在付费计划上是 beta，beta 意味着接口和体验都可能变。如果你打算把它接进一个重要的流程，比如每周要给管理层出的周报，最好先保留人工复核的环节，跑几周稳定了再考虑减少检查。不要第一周就把复核环节砍掉。

第二个坑，是自主执行的成本。当你把开关调到让它一直做下去，它可能会做比你预期多得多的动作。检索、阅读、下载、生成、再修改，每一步都在消耗资源。如果贵公司是按用量计费的，这个模式一定要设一个上限，或者至少设一个提醒。否则某天早上你会看到一个让你心跳加速的账单。

第三个坑，是企业环境的治理。文章里说得很清楚，企业管理员决定什么时候打开这些功能，而且会在变更之前至少三十天收到通知。如果你在一个大公司里，你想用这个功能但管理员还没开，这不是你能绕过去的。所以更现实的做法是，主动去找你的 IT 或者安全团队，把你看到的价值讲清楚，推动内部评估，而不是私下去找绕过的方法。

第四个坑，也是我认为最需要警惕的一个，就是一致性幻觉。文章里说，文档和幻灯片出自同一段对话，所以是天然对齐的。这是一个很强的承诺，但它成立的前提是，你在对话里给出的假设是对的、信息是完整的。如果你一开始就漏掉了一个区域的数据，那么错误会同时出现在文档和幻灯片里，而且因为它们互相一致，反而更难被发现。人看到两份材料对得上，就会本能地放心。一致不等于正确。所以无论工具多好，关键数字的复核还是不能省。这条建议在任何自动化流程里都成立。

第六，如果你现在就想用起来，我给你几个具体的切入点。

一个是周报和月报。这类东西的特点是有固定结构、有固定数据源、有固定的读者群。这正是最容易被自动化的类型。你可以先手动跑几次，把按我们一贯的写法这个要求，用明确的文字写出来，比如先讲结论、再讲数据、最后讲风险，然后存成一个技能。等你确认输出稳定了，再把它排期成每周一自动执行。

一个是把散落的会议记录整理成结构化文档。这类任务的输入很乱，但输出格式很固定，适合交给一个能同时读多份材料、又能在同一个对话里直接产出文档的能力。你可以先让它整理，然后自己改，改完留评论让它再改，几轮下来你会发现这比你自己从头写快很多。

一个是竞品或者市场资料的收集归档。就像文章里那位经济学家的做法，让 Claude 去检索、阅读、判断相关性、下载、归档，最后你来审阅。这个模式的通用性很强，几乎所有做调研的岗位都能用。你做技术选型调研、做故障复盘资料收集，也是一样的套路。

还要提醒一句，如果你以前一直在 Cowork 里工作，你不需要搬家，你的东西都在原地。你唯一需要改变的习惯是，不再纠结一件事该放在哪个入口，直接在你当时所在的对话里说就行。这个习惯的切换，可能比你想象中需要几天时间。

我们来收个尾。

这篇文章表面上讲的是两个入口的合并，实际上讲的是三件事。第一，用户不应该为产品的内部架构买单，分类这件事应该由模型来做，而不是由人来做。第二，上下文、技能和连接器才是真正的资产，它们必须在所有场景里可复用，而不是被锁在某一个入口里。第三，一个会自己动手的助手，必须把控制权交还给用户，用保守的默认值加上可配置的自主程度，陪着用户走完信任曲线。

我个人的评价是，这是一次很诚实的回调。承认我们当初把它拆成两个地方，是一个让用户更累的设计，这需要一点勇气。在行业普遍喜欢加功能的氛围里，做减法通常更难，因为它看起来不像进展。而且他们把企业治理、老用户数据、单独使用 Design 的兼容性这些边角情况都照顾到了，说明这不是一次仓促的合并，而是想清楚了才动的。

如果说有什么需要继续观察的，那就是自动路由的准确率。合并之后，用户体验好不好，几乎完全取决于 Claude 判断任务归属的那一下准不准。这一块文章没有给出任何数据，只说 Claude 可以判断出来。所以接下来几周，真实用户的反馈会很关键。如果路由经常判断错，用户会重新开始怀念那个需要自己选入口的版本，这也不是没有可能。
