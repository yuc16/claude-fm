How the Claude Code team does code review，中文可以翻译成，Claude Code 团队如何做代码审查。这篇文章发表于二〇二六年十月十六日，今天是二〇二六年十月十八日，是一篇刚刚发表的工程实践分享。欢迎收听 Claude FM，今天我们聊一个越来越现实的问题：当机器写代码的速度远远超过人读代码的速度，软件团队到底应该怎么把住质量关。

Anthropic 在文章里说，Claude 已经编写了 Claude Code 自身大约九成的代码。这句话很容易吸引眼球，但对工程师来说，更值得追问的是后半句：这些代码谁来检查，谁决定可以上线，出了问题又是谁负责？如果只是生成速度提高，检查、交付和恢复能力没有跟上，那么所谓效率提升，很可能只是把工作从开发阶段搬到了事故现场。

这篇文章的价值，就是它没有把答案停留在，让另一个模型再看一遍。它展示的是一整套流程调整：让机器承担大部分阅读，把人留给方向、架构和高风险判断，再用测试、发布和回滚机制兜底。我个人认为，值得学习的不是他们敢让多少代码自动合并，而是他们为什么敢，以及哪些地方至今还不敢。

先看他们承受的规模压力。今年五月，Anthropic 的大型单体仓库每天落地的变更大约是两千五百个，到九月已经超过三万个。这里要分清楚，Claude Code 有自己的独立仓库，并不在这个单体仓库里。文章引用这组数字，是为了说明整个公司的变化速度，而不是说 Claude Code 每天合并三万个变更。

Claude Code 自己也在加速。从六月到九月，它的合并请求数量增长了一倍多，而需要回退的合并请求占比下降了超过四成。合并请求，也就是我们通常说的 PR，可以理解成一次准备进入主干的代码改动。这里降低的是回退比例，不等于事故绝对数量也按同样幅度下降，更不能据此证明某个单独措施有效。

但这个结果至少提出了一种可能：增加产出，不一定必须等比例增加人工逐行审查。关键是不要把质量控制理解成一道门，而要把它理解成一套系统。文章说得很直接，他们没有取消审查，只是把大部分阅读交给机器，并且投入很多精力，让错误能够被快速撤销。

传统代码审查其实承担两份工作。一份是找问题，尽量别让缺陷上线。另一份是共享知识，让同事知道系统变了什么、模块怎么配合。以前这两份工作经常混在一起，因为你读同事的代码，既是在挑错，也是在学习。现在机器接过了阅读，团队就必须分别回答：质量怎么保证，知识又怎么流动。

我们先说质量。文章建议，不要只问，有没有人读过这段代码。应该问，这个改动可能怎么出错，又由哪一种检查负责发现。前一个问题非常容易变成仪式：找个人点一下批准，流程就完整了。后一个问题却会逼你讨论真实风险，比如数据会不会丢、权限会不会放宽、升级失败之后能不能恢复。

我个人认为，这有点像检查一座桥。你当然可以要求工程师把图纸全部看一遍，但看过图纸并不自动等于承重可靠。你仍然要知道哪些地方需要计算，哪些材料需要检测，哪些异常需要传感器发现。人类阅读很重要，但它只是手段之一，不应该被当成安全本身。

因此，他们优化的目标也换了。不再单纯追求更少的审查时间，而是在回退和事故不增加的前提下，尽量减少每次变更消耗的人工时间。这里的人工时间包括两头：上线之前看代码的时间，以及上线之后修坏东西的时间。今天少审半小时，明天抢修三小时，这不叫省时间。

他们跟踪每个合并请求需要多少人工批准，看中位数，也看百分之九十五分位，同时观察人工评论数量，以及请求等待某个人处理的时间。中位数告诉你日常体验，较高分位则让你看到那些特别拖沓的尾部案例。回退率和事故率是护栏，护栏变坏，就不能宣称效率改善。

接下来，整个流程最重要的变化，是审查不再主要发生在提交合并请求之后。过去像交作业，写完了再等老师批。现在更像输入法的拼写检查，你一边写，它一边验证。大部分变更在交给人之前，已经被 Claude 检查并修过至少一轮。

这里首先要解释 agent，也就是能够调用工具、执行任务的智能体。给它一句，帮我把功能做完，和给它一套可以运行的验收办法，是两种完全不同的工作方式。前者容易得到一个听起来很自信的完成报告，后者才有机会得到可检查的证据。

文章里，他们会给 Claude 可以实际运行的东西，比如测试、构建，或者一张能够跟设计稿比较的界面截图。要求不是说一句做完了，而是把运行结果拿出来。你可能会问，模型不是也会误读输出吗？会，所以这不是绝对保证，但它把讨论从口头保证拉回了可核对的事实。

比如你让智能体修一个缓存问题。下面这个例子是我的延伸，不是原文案例。只问它修好了没有，它可能回答，已经补充失效逻辑。更好的要求是，让它展示原先失败的场景，现在如何通过；再检查正常命中是否受到影响。你审核的对象，就从一段解释变成了一条证据链。

Claude Code 的创建者 Boris Cherny 在文中给出一个个人估计：让 Claude 有办法验证自己的工作，可能让最终结果好上两到三倍。注意，这是他的经验估计，不是这篇文章展示的严格对照实验。不同领域的验证也不同，可能是一条命令，一套测试，或者在浏览器、手机模拟器里实际操作。

做完之后，还会让一个拥有全新上下文的子智能体检查代码差异。所谓全新上下文，就是尽量不沿着作者此前那套推理继续往下走。我们自己写代码也有这种体验，你一旦认定原因是某个变量，就很容易把所有现象都解释成它的问题。换一个审查者，至少能减少顺着原思路自我确认的倾向。

提交之前，团队还会运行一些内部技能。这里的技能，可以理解成封装好的任务流程，有的专门找缺陷，有的简化改动，有的检查端到端行为。涉及界面的变更，还要对照设计规范。它们不是同一个万能审查者重复念几遍，而是把不同检查目标拆开。

还有一个非常值得带回团队的习惯：如果自动审查总在说同一件事，就不要让它永远靠评论提醒。应该从源头修，写进技能、静态检查规则，或者项目说明文件。我个人认为，这就是把一次性的审查劳动，变成下一次不必再付的流程资产。

文章提到两类说明文件。一类叫 CLAUDE.md，我把它叫作项目说明文件。它告诉 Claude，这是什么项目，用什么技术栈，遵循什么约定，要实现什么，不打算实现什么。由于每次审查都会加载，大仓库尤其应该保持简短，再通过它指向其他文档，而不是塞进一本百科全书。

另一类叫 REVIEW.md，可以叫审查说明文件，由相应代码的负责人编写。它不是泛泛地要求注意质量，而是告诉审查者，这个区域最怕什么。原文的例子很生动：文档最怕说假话，配置最怕把请求送错地方。不同代码的失败形态不同，审查重点也应该不同。

好的审查说明还会限制吹毛求疵，列出可以跳过的路径，要求提供文件和具体行作为证据，不能仅凭函数名字猜测风险。摘要要先说明发现多少个问题，没有可修的问题就明确说没有。团队还会另外检查，审查者到底有没有遵守这些要求，而不是以为文件放在那里就自然生效。

等合并请求真正创建，每一个请求都会先接受 Claude 审查，然后才轮到人。它不只是盯着几行差异，还会结合整个仓库和这次请求声明的意图，判断改动是否解决问题，是否适合现有系统，以及有没有破坏其他地方。如果是修缺陷，还要追问有没有触及根因。

公开产品 Code Review for Claude Code，在文章发布时已经向团队版和企业版正式开放，本地也有较轻量的代码审查命令。内部在研究预览上线后，收到实质性审查评论的请求比例，从百分之十六升到了百分之五十四。这个数字说明覆盖方式变了，但不能直接理解成缺陷检出率翻了几倍，因为两个指标不是一回事。

他们观察到，大多数超过一千行的请求会有发现，多数小请求则没有问题需要指出。管理员可以选快速、标准、深度三档。深度审查适合漏掉一个缺陷的代价，比多花一点检查时间更高的地方。这背后的重点不是永远开最强档，而是让审查成本和失败成本匹配。

更有意思的是，发现问题的智能体，并不能直接把所有怀疑发给人。多个智能体会并行找缺陷，然后另一组智能体对每条发现进行判断，只有获得足够认可才发布。主要涉及风格、诊断信息或清理的问题，会被过滤。团队在自己的请求上做过对照测试，才保留这些过滤机制。

我个人认为，这相当于把找线索和决定是否立案分开。找线索的时候可以敏感一点，但发到开发者面前，就必须更克制。因为评论不是免费的，它会打断人，也会触发修改。尤其作者本身是智能体时，一句无关紧要的建议，也可能变成新提交、新检查和新一轮等待。

最终发布的评论会按严重程度排列，还会区分重要问题、细枝末节和原本就存在的问题。最后这一项非常关键。你修改登录界面，审查者发现旁边有个几个月前的缺陷，不应该让读者误以为是你这次引入的。发现旧问题有价值，但责任归属和当前变更风险不能混为一谈。

每条发现都必须回应。要么修复，要么给出理由并关闭讨论。安全审查也单独运行，只要缺陷审查或安全审查还有未关闭的问题，请求就不能合并。误报不是不能关，但必须简短说明原因。如果后续提交已经修复，相关发现可以自动清除。

这些机制之外，常规检查一点没少。静态规范检查、类型检查、各个平台的测试和构建，都照常运行。一个典型的命令行工具合并请求，在人看之前可能已经跑过几十项检查。请求模板还要求说明怎么测试，以及怎么撤销。Claude 可以帮忙填写，但发起变更的人要确认。

你可能会问，既然自动检查这么多，最后到底需不需要人？他们的答案不是统一需要，也不是统一不需要，而是按变更风险分层。低风险包括文档、文案、仅供内部使用的功能，以及被功能开关保护的增量改动。在自动审查和安全检查通过后，可以不要求额外人工批准。

中等风险包括普通产品改动，也包括缓存、自动更新器、系统提示词等敏感区域的改动，需要一个人。最高风险代码，以及少量规定必须双人检查的路径，需要两个人。这里容易听错，敏感不等于所有变更自动进入最高档，具体还要看团队定义的路径和规则。

风险等级由变更决定，而不是作者决定。一个分类器读取改动并确定等级，第二个分类器再问，即使这个等级原本不要求额外的人，这次是不是仍然需要。某些路径始终要有人参与，包括负责人标记的敏感位置，以及持续集成的工作流文件。

同时，轻量通道只向仓库信任名单中的作者开放，主要是负责这个仓库的团队成员。其他人仍然需要第二个人批准。也就是说，变更决定风险等级，信任关系决定能不能使用简化通道。这是两道不同的限制，不能因为一个分类器说风险低，就让任何来源的代码直接进去。

而且智能体的批准，永远不能冒充一个人的批准。自动审查可以让低风险变更满足自动合并条件，但如果规则要求人类，它就不能填那个位置。文章最后也澄清，公开的代码审查产品发布的是问题发现，不是批准；他们自己的仓库在此基础上，才由负责人决定哪些低风险改动可以自动进入。

在人类责任上，他们定得很清楚：谁指挥智能体做这次修改，谁就要对修改负责。即使代码不是你敲的，你也算所要求的审查者之一。批准还只针对一个具体提交，如果后面又来了系统无法担保的新提交，比如智能体继续推送，或者有人手动解决合并冲突，就需要重新批准。

下面这个推演是我的解释。假设你看完一个版本，确认只是调整展示文案，随后智能体为了让测试通过，又改了权限判断。如果原来的批准仍然有效，流程表面上有人负责，实际上那个人从未看过最终内容。所以批准绑定提交，不是形式主义，而是在保证批准的对象没有偷换。

不过，单个请求检查通过，也不代表两个请求合到一起不会出问题。因此他们使用合并队列，在变更真正进入主干之前，把它应用到最新主干上，重新跑所有检查。你可以把它理解成，不能只验证每个零件单独合格，还得验证装到当前机器上能一起运转。

发布之后还有层层缓冲。新行为通常先放在功能开关后面，让 Anthropic 员工使用。公开发布先进入最新通道，稳定通道再晚一些跟进。如果出错，功能开关可以不重新部署就关闭。团队还有按周轮换的值班制度，事故复盘会追问，本来应该由哪一层拦住这个问题。

这里有个诚实的边界。文章说，他们还没有建立一种自动熔断机制，在回退或事故数字变差时，自动收紧审批。现在仍然依赖作者、值班工程师和相关看板发现问题。团队里的工程师希望，在更多代码走向零人工合并之前，先把这种机制补上。

所以不要把这篇文章听成，Anthropic 已经解决了所有自动交付问题。恰恰相反，它呈现的是一套还在调整的系统。他们更愿意提高发现和修复问题的速度，而不是单纯通过少做事情来降低错误数量。但这句话能成立，前提是错误影响可控，发现足够快，撤销足够容易。

接着看他们怎么判断自动审查有没有进步。第一件事，把过去造成事故的合并请求收集起来，同时收集修复和回退记录，再让熟悉代码的工程师确认缺陷是什么、位于哪里。这些材料构成评测集，审查者每天都要在上面运行。

评测，就是拿已知答案的案例检验系统。它能回答一个非常实在的问题：上次真的让我们摔过跤的坑，今天这个审查者还能不能认出来？我个人认为，这比拿几个看上去聪明的演示案例更接近工程质量。尤其当模型、提示词或者工具改变时，旧能力有没有丢，必须重新验证。

第二件事，不能只数发现了多少问题，还要观察人怎么处理评论。团队把回应分成修复、认为判断错误、说明行为本来就是如此，以及认为问题不重要。他们还拿已知干净的请求测试，检查审查者会不会提出让人改坏代码的建议。误报不只是浪费时间，极端情况下还会制造缺陷。

第三件事，是让审查收敛。文章有个让人印象很深的案例，一个命令行工具的请求，在一夜之间经历了超过五十轮审查和修改，最后由作者叫停。想象一下，两台机器彼此认真提意见，谁也不下班，看起来特别勤奋，实际上交付被困在原地。

他们追查被反复标记代码的历史，发现大约百分之五十九，在第一轮审查时就已经存在。也就是说，很多后续轮次不是发现刚刚引入的新问题，而是在旧代码里每次再翻出一点。团队自己也承认，过去习惯默认多跑几轮，因为每轮总能找到东西，反而强化了这个循环。

后来他们开始同时追踪检出能力和通过所需轮数。三轮之后，审查者会要求作者停下来重新考虑方案。前几轮之后，只重新检查新增差异；发现一类缺陷，就提示作者一次修全，而不是只修某一行；已经发布过的发现，也不再重复。夜间仍会扫描现有代码，但不必把所有旧债都塞进当前请求。

到这里，我们可以把核心逻辑串起来了：代码生成可以持续，检查也可以持续，但每条问题都要有证据，每轮审查都要有边界，每次放行都要有明确责任。真正的目标不是让机器一直忙，而是让一项合理的改动，在可接受风险下完成交付。

那普通团队明天能怎么用？我个人建议，先别从取消人工审批开始，而是挑一个仓库，把现有流程里最含糊的地方补清楚。比如所谓测试通过，究竟跑了哪条命令，覆盖什么行为，没有覆盖什么；所谓可以回滚，是点一个按钮，还是需要临时找人翻操作记录。

接下来，写一份短的项目说明和审查说明。不要抄几十条放之四海皆准的原则，而是记录这个仓库真实踩过的坑。我举个假设例子，如果你们总在配置默认值上出错，就写清楚缺省、空值和显式关闭分别代表什么，再尽量把能机器判断的部分变成测试。

然后只在一个仓库接入人工智能审查，运行几周，观察哪些评论真让人改了缺陷，哪些评论总被解释掉。文章给出的推广顺序也是先调说明，再扩大范围。不要因为第一次输出很漂亮就全公司铺开，也不要因为一次误报就宣布没有价值，应该看它在真实工作流里的持续表现。

风险分层也应该先严格，再凭证据放宽。认证、计费、持续集成、发布流程和安装器这些位置，可以利用代码负责人规则和分支保护，明确保留人工参与。不要只把规则写在群公告里，因为真正赶进度的时候，能被绕过的约定，往往就是最先被绕过的那一道防线。

试点时还可以做一件很具体的事，这是我的建议：每周挑几条合并请求复盘，从任务发起一直看到上线。不是只问模型找没找到问题，而是问等待发生在哪里，谁反复解释了同一个背景，哪条检查没有提供有效信息，哪次修改其实根本不值得做。这样你优化的是交付链，而不是一个孤立模型的表现。

最后，别忘了开头提到的另一份工作，团队怎么学习代码。Claude Code 团队坦言，他们没有正式解决这个问题，也不认为每个人都需要在脑子里装下整个系统。有人要理解一个模块，就让 Claude 根据当前代码生成针对性的讲解，有时还制作一个小型可视化材料。

我个人认为，这可以替代一部分低价值阅读，但不能自动替代所有共同理解。讲解是不是准确，关键设计取舍有没有讲到，仍然值得核对。原文里他们还依赖开放的工作频道，让大家在别人动手时就看到方向，尽早提出为什么要做，或者有没有更简单的路线。

这一点和机器写代码的低成本有关。既然启动一个任务很容易，有些任务就根本不应该合并。最好早一点在讨论里调整方向，而不是等代码全部写完，再用一个阻塞性评论否定需求。因为写得快，关闭一个不值得的请求，也不必被理解成浪费了巨大投入。

出了问题，通常由最有上下文的作者负责修，但事故复盘看的是系统，不是追着某个人责备。小变更、快速回退、分阶段发布和及时监控，让这种责任有机会成为可执行的责任，而不是一句出了事你负责。开放协作则让其他人也能补位，质量并不只属于某一位代码所有者。

总结一下，这篇文章讲的不是让人类退出代码审查，而是把人从重复阅读里解放出来，去判断方向、架构、证据和风险，再用持续验证与快速恢复支撑交付。我个人认为，值得带回团队的第一步，不是减少一个批准按钮，而是先回答：这个改动最可能怎么失败，我们凭什么能及时发现，又能多快把它撤回来。
