先来看最关键的背景。传统软件当然也需要可观测性。服务出错了，我们看日志；接口变慢了，我们看指标；一次请求跨了好几个服务，我们看链路。但智能体把这个问题放大了，因为它的执行过程通常不再是一条固定路线。同样一句请求，这次可能查两个工具，下次可能查五个，中间还可能重新规划。

你可以把传统业务流程想成一条排好班次的地铁。站点比较固定，换乘路径也能提前画出来。智能体更像一个拿着任务清单的办事员，遇到缺材料就去找材料，发现信息冲突就再问一个系统。最后都说事情办完了，但走过哪些地方、在哪里等了多久、拿了哪份材料，不一定一样。

这也是为什么只保存最后的回答不够。回答相当于办事员交上来的总结，追踪则更像这一路的办事记录。你要分析成本，需要知道调用了多少次模型；你要分析速度，需要知道时间花在哪一步；你要定位错误，需要知道错误是从输入、工具返回，还是后续处理环节开始出现的。

原文给出的一个核心判断是，想让智能体获得更多访问权限，应该先追踪它的模型调用、工具使用，以及 MCP 服务器调用。MCP 可以理解为模型上下文协议，用来连接模型应用和外部工具或数据。先检查执行轨迹，等它证明自己可靠，再逐步扩大访问范围。这是文章里很值得记住的一条原则。

注意这个顺序，不是先把权限全部打开，等出了事故再补监控。我个人认为，这更像对新同事的授权过程。先让他处理低风险任务，观察他是否遵守流程，遇到异常是否上报，再让他接触更敏感的操作。智能体不会因为回答流畅，就天然拥有值得信任的执行记录。

接下来，我们把追踪本身拆开。OpenTelemetry，中文通常叫开放遥测，文章也使用它的简称 OTel。你可以把它理解成一套通用的遥测标准和工具生态。这次公告最重要的地方，不只是 Claude 能产生一些记录，而是这些记录能够通过标准方式，送到不同的观测工具里。

Trace，也就是追踪，通常描述一次操作经过的完整链路。链路里的具体步骤，可以进一步表示成不同的执行片段。对于智能体，我们关心的不只是最外层的用户请求，还包括其中的模型调用、工具调用，以及这些步骤之间的关系。听起来抽象，但把它画成时间线，就非常直观。

假设你做的是一个订单售后助手。用户问，我的退款为什么还没到账。智能体先理解问题，再查询订单，再查询支付状态，发现资料不全，又调用一次模型决定下一步。最后它生成解释。用户看到的是一句话，工程师需要看到的，却是前面这一串步骤，以及每一步的耗时和结果。

文章说，在 Claude Console，也就是 Claude 控制台里添加一个目标地址之后，每个智能体回合、模型调用和工具使用，都可以作为标准的 OpenTelemetry 追踪进入你的观测工具，并带有延迟、token 和标识信息。Token 是模型处理文本时使用的计量单位，不能简单等同于汉字或者英文单词。

这些信息分别回答不同问题。延迟回答时间花在哪里，token 回答模型消耗了多少处理量，标识信息帮助你区分和关联不同执行。它们组合起来，才更接近一次可分析的运行记录。单看总耗时，你只知道任务慢；看见里面的步骤，你才有机会知道到底该优化模型调用，还是该修那个慢查询。

不过，这里要非常谨慎。能看到延迟和 token，不等于已经拿到了完整的业务成本核算；有调用标识，也不等于你所有内部服务就已经自动完成关联。具体有哪些字段，字段记录到什么粒度，如何把应用里的业务请求连起来，都应该去核对文档，并通过实际样本验证。公告不能代替接入验收。

我给你一个假设性的排障过程。售后助手平均响应变慢，团队第一反应是换一个更快的模型。接入追踪以后，发现模型本身并没有明显变慢，真正增加的是支付服务的等待时间。如果只有最终回答，你可能花一周改提示词；如果有执行时间线，你可能很快就知道该去找哪个服务的负责人。

反过来也可能。外部服务都很快，但智能体在相同信息之间来回确认，重复调用模型。那问题可能出在任务说明不清楚，工具返回难理解，或者退出条件不明确。这里的重点不是追踪会自动告诉你正确答案，而是它把一个笼统的感觉，拆成可以检查、可以讨论的证据。

还有一种常见误会，就是把可观测性当成读取模型的内心。它并不是。看到调用顺序、输入输出和时间信息，能够帮助你重建执行过程，但不意味着你获得了模型内部所有决策机制。更不能因为某条轨迹看起来完整，就断言模型给出的业务结论一定正确。

所以，追踪首先解决的是发生了什么，以及问题可能出在哪里。至于这一步是否合法、答案是否可靠、金额是否算对，仍然需要业务规则、测试和人工判断。它像行车记录仪，不像自动授予驾驶资格的证书。这个区别，越是在高风险业务里，越要讲清楚。

文章的第二个重要点，是标准化。它明确说，Claude 的追踪遵循 OpenTelemetry 的 GenAI 语义约定。GenAI 指生成式人工智能。所谓语义约定，你可以理解为大家尽量使用共同的字段含义来描述模型相关操作，而不是每个平台都创造一套只有自己认识的说法。

为什么这件事值得关心？假设你的团队同时使用几个模型供应商。如果每一家都把耗时、调用类型和用量写成完全不同的结构，那么做一张统一看板之前，你得先维护一堆翻译逻辑。共同约定的价值，就是减少这种重复劳动，让不同来源的数据更容易进入同一套分析流程。

但标准化不是魔法。原文说这些数据可以在相同工具和看板里工作，不代表不同供应商的能力、收费方式和所有字段都完全一样。比如你比较两个方案的 token 消耗，还要考虑任务内容和输出质量。不能因为字段可以放在一张表里，就默认这些数字可以不加判断地直接排名。

文章把接入后的用途，分成了几个很实际的方向。首先是跟其他软件系统一起排障。它提到 Grafana Cloud、Honeycomb、Sentry 和 Splunk。在这些工具里，智能体追踪可以和日志、指标放到一起，你更容易判断，一个缓慢或者失败的步骤，来自哪一个服务。

这里的关键是同一个工作现场。以前，模型问题去一个后台看，应用异常去另一个后台看，数据库告警再去第三个地方找。排一次故障，很像几个人拿着不同版本的地图找同一条路。把观测数据汇集起来，至少让大家有机会围绕同一次执行讨论，而不是各讲各的局部现象。

如果你已经把 Claude Code 或者 Cowork 的追踪发送到观测工具，原文说，自己在 Claude 平台构建的智能体也能出现在同一个地方。这对平台团队尤其有意义，因为他们关心的往往不是某一个聊天应用，而是组织里各种人工智能工作流共同的运行状态。

不过我个人认为，同一处查看之后，下一步应该是明确区分。哪些是开发活动，哪些是生产业务，哪些属于内部试验，哪些面向外部客户。如果接进来了却分不清环境和责任人，统一看板也可能只是一张更拥挤的看板。这是团队的数据组织问题，不是标准协议自动替你解决的问题。

第二个方向，是拿生产数据改进智能体。文章提到了 Arize AI、Braintrust、Datadog、Langfuse、LangChain 的 LangSmith、New Relic 和 PostHog。这些工具可以帮助团队把真实追踪转成评测，发现质量问题，并衡量某次修改到底有没有帮助。

这里的 eval，也就是评测，不一定是一次宏大的模型考试。对业务团队来说，它可以很朴素：收集一批真实任务，定义哪些结果算正确，哪些行为不能发生，然后在改动前后重复检查。生产追踪的作用，是让评测不只来自开发者凭想象编的几个例子，而是接近用户真的遇到的问题。

我们继续用售后助手做假设。你发现它在普通退款问题上表现很好，但遇到订单拆分，就经常重复查询。那就可以挑出这类有代表性的执行，整理成测试任务。之后改了工具说明，不能只问大家感觉有没有更聪明，而应该看，这类任务的完成质量、调用次数和耗时有没有变化。

这里有个很容易踩的坑。追踪里出现了一次失败，不代表你把那段记录原封不动塞进测试集，就完成了评测建设。你还得定义预期行为，判断失败原因，处理敏感数据，确认样本有代表性。否则，数据虽然来自生产环境，评测依然可能含糊，甚至把错误行为当成标准答案。

我个人更建议把问题拆开看。一个任务有没有完成，是一件事；用了多少资源，是另一件事；有没有越过权限边界，又是另一件事。你可以让同一批任务接受不同维度的检查，但不要急着把所有指标压成一个总分。总分看起来方便，却经常掩盖你最在意的那个风险。

这也让我们能够正确理解文章里的 Ramp 案例。Ramp 说，Claude 支撑了他们一些很强的内部和面向客户的智能体。他们构建了一个叫 Reflect 的智能体系统，给 Langfuse 里的追踪评分，寻找反复出现的失败，再提出修复建议。这已经是一个围绕轨迹建立的改进闭环。

客户给出的数字是，在部分智能体上，他们已经把 token 使用量降低了百分之十到百分之二十，并让会话快了百分之三十。注意两个限定。第一，这是部分智能体，不是所有任务。第二，这是他们已有改进系统取得的成果，不是这次原生导出功能单独造成的实验结果。

原文接着表达的是，Reflect 只能改进它能观察到的东西，而 Claude 接口的原生 OpenTelemetry 导出，能够把更高保真的运行信息送进这个循环。我个人认为，这个案例最有价值的地方，不是那两个百分比，而是先有观察，再有诊断，再有修改，最后重新验证的工作方式。

如果你来做一个类似系统，也不一定一开始就让另一个智能体自动提出修复方案。先由工程师每周看一批高频失败，整理共同原因，也可以形成闭环。自动化值得追求，但前提是你先知道评什么、怎么判，以及谁对最终修改负责。否则只是把不清楚的判断过程加速了。

文章的第三个用途，是组织范围的使用量追踪。它提到，可以把追踪发送到 Databricks Unity Gateway，让平台和安全团队按团队查看 token 使用量，并标记异常活动。这里的视角，已经从某一次任务为什么慢，转向整个组织的资源和风险分布。

举个假设例子，一支团队平时用量稳定，某天突然升高。它可能是新功能上线，也可能是错误重试，还可能是测试任务没有及时停止。用量异常本身只是线索，不是违规结论。你需要把变化和业务活动放在一起解释，再决定是扩容、修复流程，还是进一步调查。

这也是为什么不能把 token 数直接当成团队效率排名。有些任务本来就复杂，有些团队正在做必要的质量验证。少用不一定做得好，多用也不一定浪费。我个人认为，组织看板应该先帮助大家提出正确问题，再讨论预算和优化，而不是拿一个容易统计的数字替代业务价值。

再来看另外几个客户例子，它们分别展示了不同的观察需求。文章里有一段财务场景的引言，说接触公司账簿的智能体，应该像会计一样展示自己的工作过程。这个客户把 Claude 平台上的智能体追踪，和 Grafana Cloud 里的遥测联系起来，放进对账或者会计分录工作流的同一条时间线。

这段引言具体提到，团队能看到提示词版本、工具调用、延迟和 token 消耗。当审计人员询问智能体做过什么，以及相关原因时，他们可以沿着时间线回答。提示词就是我们经常说的 prompt，也就是交给模型的任务指令。知道当时用的是哪个版本，对复现和解释问题很重要。

不过，客户能在自己的系统里看到这些信息，不代表我们可以直接推断，所有字段在所有入口都默认具备相同记录方式。尤其是审计，不只是有一张图就够了。身份、授权、留存和证据完整性，都需要具体制度支持。这些是我对应用边界的提醒，不是原文宣称已经完成的合规保证。

Foxglove 的场景是机器人调试。他们正在构建帮助机器人团队排查问题的智能体，通过原生导出，把智能体交互放进 PostHog，与产品使用数据一起分析。目标是看清实际表现，发现哪里做得不够好，再决定优先改进什么。

这里有一个很有意思的连接。单看智能体内部，它可能每一步都成功执行了；但和产品使用情况放到一起，你可能发现，用户仍然没有解决问题。当然，原文没有给出这种具体实验结果。我的意思是，系统层面的调用成功，和用户层面的任务成功，是两件值得一起观察的事情。

Sterling Labs 则用了赛车的比喻。他们的智能体全天候分析实时市场，Langfuse 像赛道边的指挥台。原生导出把追踪直接送进去，让团队少做定制埋点，把精力放在自己的核心工作上。这段话强调的是减少接线成本，而不是证明所有市场分析结果因此更准确。

把这几个案例放在一起，你会发现，共同点不是大家使用同一张看板，而是观察数据进入了已有的工作流程。财务团队要解释操作记录，机器人团队要联系产品表现，Ramp 要建立改进循环，实时市场团队要减少接入负担。可观测性的价值，最终取决于谁会拿这些数据做什么。

那么，如果你明天想在自己的项目里试一下，应该怎么落地？先说文章明确给出的状态。这项 OpenTelemetry 追踪能力处于公开测试阶段。Managed Agents 和 Messages API 需要在 Claude 控制台里配置目标地址；Claude SDKs 则会自动导出追踪。原文没有进一步展开所有配置细节。

因此，自动导出不应该被理解成，你完全不需要确认运行环境和目标配置。实际使用哪个版本、支持哪些入口、数据怎样发送，还是要看当时的文档。文章还说，除了列出的工具，其他接受标准 OTLP 端点的 OpenTelemetry 工具也可以使用。OTLP 可以理解为这套遥测数据使用的传输协议。

我个人建议，试点先选一个低风险、流程相对清楚、又确实有痛点的智能体。比如它偶尔响应慢，或者工具调用数量波动明显。不要一开始就接全公司的所有应用。先证明你能稳定收到数据，能解释一次执行，能通过这些记录回答一个原来回答不了的问题。

接入验收也别停留在，控制台上出现了几条漂亮的线。你可以准备一次正常任务，一次工具报错，一次明显较慢的任务，分别检查观测结果。这里说的是测试方法建议，不是平台承诺的专用测试能力。你要确认，重要步骤是否出现，失败是否可识别，时间信息是否足够支持定位。

然后再做一次反向检查。拿观测工具里的一条轨迹，尝试找回对应的业务任务；拿业务系统里的一次用户反馈，尝试定位对应的轨迹。如果两边对不上，真实故障到来时，团队还是得靠猜。至于怎样传递和保存关联信息，要根据你实际使用的框架和平台文档设计。

再往下，就是数据边界。文章没有详细讨论提示内容、工具返回和敏感字段的处理策略，所以千万不要仅凭这篇公告，就假定所有数据都已经自动脱敏。上线前，你需要核对到底发送了什么，谁能访问，保留多久，是否会进入另一个供应商的系统。

这在中国的软件团队里尤其实际。假设工具返回里混有客户联系方式、合同内容或者内部经营数据，观测平台就不再只是技术辅助设施，它也可能成为敏感数据的集中位置。我个人认为，负责业务数据和安全的同事，应该参与这个接入评审，而不是等数据进去了，再讨论该不该留。

接下来才是建立基线。你至少要知道，在一批有代表性的任务上，目前的质量、耗时和用量是什么样。改动之后，尽量用可比较的任务再次检查。否则今天任务简单、明天任务复杂，指标一上一下，很容易把任务差异误认成模型改进或者系统退化。

优化的时候，也别只盯着模型。追踪可能暴露的是工具接口设计不清楚，返回内容太冗长，业务服务不稳定，或者智能体被要求完成一个目标含糊的任务。我个人认为，智能体工程很大一部分工作，就是把原来藏在对话里的问题，重新变成接口、状态和流程的问题。

至于授权，回到文章最初的原则，先观察，再扩大权限。一个值得采用的实践是，先让智能体给建议，再考虑让它执行低风险操作，最后才讨论更高影响的动作。但每一步是否开放，都应该有独立的授权和审批设计。追踪提供证据，并不会替代阻止危险操作的机制。

最后别忘了给观察之后的行动安排负责人。发现重复调用，谁来改工具说明；发现服务超时，谁去排查；发现质量下降，谁决定回滚。如果没有这层责任，遥测数据只会越积越多。真正的闭环，不是把数据成功送出去，而是有人能够基于它做决定，再验证决定的效果。

我们用几句话收回来。这篇文章宣布的核心能力，是让 Claude 平台上的智能体执行轨迹，通过 OpenTelemetry 进入现有观测工具，把排障、评测和组织治理连接起来。它的价值不在于让智能体看起来更神奇，而在于让每一步更容易检查、解释和改进。

我个人认为，当智能体开始接触真实业务，成熟的标志不是我们敢给它多少权限，而是我们能否说明它做了什么，发现问题后又能否及时纠正。先把执行过程看清楚，再谈扩大信任，这可能比再写一条巧妙的提示词，更接近可靠系统的基本功。这里是 Claude FM，我们下期见。
