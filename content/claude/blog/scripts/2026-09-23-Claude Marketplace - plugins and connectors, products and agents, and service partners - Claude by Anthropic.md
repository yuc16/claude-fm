你好，欢迎收听 Claude FM，我是你的主播。今天我们要拆解的这篇文章，标题是 Claude Marketplace: one place to discover plugins, agents, and services from our partners。翻译成中文，大概是"Claude 市场：一个集中发现合作伙伴插件、代理和服务的地方"。这篇文章发表在二〇二六年九月二十三日，来自 Anthropic 的官方博客，原文大概五分钟就能读完，形式上是一篇产品公告。

今天录节目的日期是二〇二六年九月二十七日，文章离我们只有四天，所以时效性完全没有问题，你现在听到的就是刚刚发生的事情。不过我还是想先说明为什么它值得你花这二十多分钟。这不是一次普通的功能更新，而是 Anthropic 第一次正式把"市场"这个概念做成产品。它释放的信号是，Anthropic 想从一家单纯卖模型能力的公司，慢慢变成一家经营生态的平台公司。

如果你只是把 Claude 当成一个写代码、写文档的助手，你可能会想，这跟我有什么关系。关系其实挺大的。因为这篇文章里出现的三组数字和名单，串起来就是一张企业采购的地图。第一组是两千多个连接器和插件，第二组是一份可以拿去付别家软件钱的承诺额度，第三组是埃森哲、波士顿咨询、德勤这些名字。这三样东西放在一起，回答的是每个企业都会问的那个问题：我买了 Claude，接下来到底该怎么用起来，钱从哪里出，活又该谁干。

我们先说说背景。企业用上大模型，其实不是买一个接口密钥就完事了。一般来说，一个企业要真正把 AI 用起来，至少要解决三层问题。第一层是模型本身的能力，这一层 Anthropic、OpenAI、Google 都在做，你只要付钱就能拿到。第二层是模型跟企业内部系统的连接，也就是说，模型得能读到你的 Jira、你的 Confluence、你的 Salesforce、你的数据库，不然它只能靠猜，猜出来的东西没人敢用。第三层是落地服务，也就是有人帮你做流程改造、数据治理、权限设计、员工培训，让这套东西真正在组织里跑起来。

那过去的市场状态是什么样的呢？这三层是割裂的。模型厂商只卖模型和席位；工具厂商各自为政，你要自己去搜、去试、去谈合同；咨询公司自己接项目，跟模型厂商之间没有正式的绑定关系。结果就是企业的技术负责人要同时面对几十个供应商，采购流程拖半年，预算分散在十几个部门手里，最后真正跑起来的东西没几个。

到了二〇二六年，这个矛盾变得特别尖锐。因为大部分企业已经过了做概念验证的阶段，进入了真正的规模部署阶段。做原型的时候，随便找个工具试一下就行；一旦要推给几千个员工用，采购、安全、合规、预算，每一道都是硬门槛。很多 AI 项目不是死在技术上，是死在采购流程和预算归属上。我自己观察到的情况是，技术团队花了三个月做出的东西，可能要在采购环节再卡三个月。

Anthropic 这次的思路，是把这三层收拢到一个入口里。这就是 Claude Marketplace。文章里的定位说得很清楚，对客户来说，它是一个统一的目的地，帮你找到对的工具和服务；对开发者和合作伙伴来说，它是一条更容易触达 Claude 用户的路径。这个双向的表述很关键，它说明 Anthropic 意识到，光有模型不够，平台的价值取决于两边能不能互相找到对方。

我个人认为，这里的参照物非常明显，就是 Salesforce 的 AppExchange 和 AWS 的 Marketplace。这类市场的核心逻辑不是"我帮你卖"，而是"我帮你降低交易成本"。发现成本、信任成本、采购成本、结算成本，四样都降下来，生态才转得起来。你会发现，成功的平台市场卖的不是商品，是摩擦的减少。

那么 Claude Marketplace 具体让客户能做三件事。我们一件一件说。

第一件事，添加连接器和插件。文章说，今天就可以从两千多个连接器和插件里选，包括 Atlassian、Google、Microsoft、Notion、Salesforce 等等。这里有两个概念需要区分一下。连接器，一般指的是让 Claude 能够访问某个外部系统的数据和操作，比如读你的 Confluence 页面，或者在 Jira 里创建工单。插件，更偏向于把一组能力和工作流程打包起来，安装之后 Claude 就多了一项专门的本事，比如按你们公司的规范生成发布说明。

那这两千多个是怎么做出来的呢？靠的是 Model Context Protocol，也就是模型上下文协议，大家通常叫它 MCP。简单说，MCP 是一套让模型和外部工具说同一种话的标准。在 MCP 之前，你想让模型接入一个系统，得为这个模型单独写一套对接代码；换一个模型，代码就得重写。MCP 把这个对接层标准化了，你写一次服务端，理论上所有支持 MCP 的客户端都能用。它是 Anthropic 在两年前开源出去的，现在已经成了行业里被广泛接受的做法。

这里我要多说一句为什么两千这个数字重要。在生态里，第一个一百个集成往往是厂商自己掏钱做的，因为要证明这条路能走通。第一轮到一千个，通常是靠开发者社区的自发热情，大家觉得好玩、觉得有需求就做了。而从一千到两千，说明已经有不少公司把"支持 MCP"当成一件正经的产品工作在排期，有负责人、有预算、有维护承诺。对企业的技术负责人来说，这意味着过去要自己写的那部分对接代码，现在有很大一块可以直接装，或者直接买。

不过我要提醒一句，数量不等于质量。两千多个里面，肯定有做得很扎实的，也有草草了事的。企业真正要看的不是数量，而是这几件事：这个连接器有没有做权限粒度控制，会不会把整个知识库都暴露出去；它支不支持写操作，还是只能读；它的维护者是谁，多久更新一次；出了问题找谁，有没有明确的响应时间。这些问题在 AppExchange 时代就存在，现在只不过是换了个场景重演一遍。

第二件事，买代理和产品。文章说，你可以用你承诺给 Anthropic 的一部分支出去买那些基于 Claude 构建的软件，名单里点了 CrowdStrike、Cursor、Harvey、Legora、Lovable、Snowflake。这一条是整篇文章里我认为最值得琢磨的地方，因为它动的是预算结构，不是功能结构。功能改变的是你能做什么，预算结构改变的是你能不能做成。

我们先解释什么叫"承诺支出"。很多大企业跟模型厂商签的是一年期的承诺合同，比如我今年承诺在你这里花一百万美金，你按这个量给我折扣、给我优先的技术支持、给我更靠前的路线图沟通。问题是，企业实际能消耗掉多少，常常算不准。业务增长快，额度不够用；项目推进慢，额度用不完。用少了，钱浪费掉；用多了，又得临时补预算走审批。

现在 Anthropic 说，这个承诺额度里的一部分，你可以拿去 Marketplace 里买别家公司的产品，而这些产品本身又是基于 Claude 构建的。这句话听起来平淡，但它其实是一次机制创新。

这个设计的巧妙之处在于，它把三笔本来分开的预算合成了一笔。本来企业要买代码补全工具，走一条采购流程；买数据平台，走一条；买安全产品，走一条。三条流程，三个审批人，三份合同。现在只要这些产品在 Marketplace 里，钱就可以从同一个池子里出。对客户来说，采购流程简化了，预算谈判也变简单了。对那些上架的厂商来说，它们获得了一条非常特殊的销售渠道，客户付钱的时候用的不是新预算，而是已经批下来的预算。这两者在企业里的难度完全不是一个量级。

你可以想象一下这个场景。一家公司年初跟 Anthropic 签了承诺合同，到了第三季度发现只用了六成，剩下四成眼看就要浪费。这时候财务会做什么？以前可能就算了，或者硬着头皮多跑点推理任务，反正钱已经花了。现在他们可以打开 Marketplace，把剩下的额度换成团队真正需要的工具。从财务的角度看，这四成预算终于有了去处；从 Anthropic 的角度看，客户的承诺额度被用满的概率提高了，续约时客户也更愿意往上加，因为去年的钱确实花出了价值。

我个人认为这是这一整套设计里最有杠杆的一步。它同时解决了三个问题：厂商的额度消化率、客户的预算浪费焦虑、以及生态伙伴的获客成本。如果它真的跑通，后面其他模型厂商大概率会跟进，因为这是个结构性的优势，不是功能层面的。功能可以被抄，渠道结构一旦形成惯性就很难被撼动。

当然，这里面也有值得担心的部分。当买别家软件的钱是从模型厂商的额度里出的时候，客户跟这些软件厂商之间的直接议价关系就变弱了。价格怎么定，折扣怎么给，退出机制是什么，恐怕都会比以前复杂。这一点我会在后面的实践部分再展开。

第三件事，通过服务伙伴来放大。文章说，你可以联系 Claude Partner Network 里的咨询伙伴或者系统集成商，比如埃森哲、波士顿咨询、德勤，让他们帮你制定 AI 战略，并且把 Claude 推广到整个组织。

为什么咨询公司在这件事里这么重要？因为大部分企业卡住的地方不是模型不会用，而是组织的惯性。一个部门愿意用，另一个部门不愿意共享数据；法务担心合规；安全团队要求审计日志；老板想要一个能讲得通的投入产出故事。这些东西技术团队解决不了，得有人从上往下推。咨询公司卖的其实不是技术，是推动组织变化的合法性和方法论。同样一句话，工程师跟业务部门说三遍没人听，外部顾问说一遍就立项，这种事在企业里天天发生。

而且从 Anthropic 的角度看，这一环是杠杆最大的。一家咨询公司如果把这套方法论标准化，它一年可以带几十个客户进来。这比一个连接器只能影响一家的效率高得多。所以你会看到，市场里三个入口，服务伙伴这一块的战略权重其实是最高的，只是它最不显眼。

好，讲完客户端的三条路，我们翻过来说说构建方的三条路。这篇文章的受众其实很明确，一半是买家，一半是卖家。

如果你是在为使用 Claude 的团队做工具，文章的路径是：用 MCP 和 Agent Skills 来做连接器或者插件。Agent Skills 是 Anthropic 推出的一套开放标准，你可以把它理解成给模型看的说明书加工具箱。一个 Skill 里通常包含一段描述这个能力什么时候该用的说明，加上一些脚本或者参考资料，模型在需要的时候才去读，不需要的时候不占上下文。这一点对企业特别重要，因为企业最怕的就是把所有内部知识一股脑塞进提示词里，又贵又乱还不好维护。Skills 的做法是按需加载，这是一个更聪明的工程折中。

所以对开发者来说，MCP 解决的是"模型怎么连上我的系统"，Agent Skills 解决的是"模型怎么知道在什么场景下用我的能力"。两个合起来，才是完整的接入。只做 MCP，你的工具会在几百个工具里被埋没，模型不知道该在什么时候调用它；只做 Skills，能力描述得很漂亮，但拿不到真实数据，落不了地。

如果你卖的是基于 Claude 构建的代理或者产品，路径是申请上架。上架以后，客户就可以用他们的承诺额度来买。这条路的门槛在于审核，文章没有细说审核标准，但可以合理推断，会涉及安全、数据使用、以及是否真的基于 Claude 构建这些方面。这几项其实都指向同一个问题，就是信任。平台要为客户的采购决策背书，就必须把不合格的东西挡在外面。

如果你是做咨询或者系统集成的，路径是加入 Claude Partner Network，加入之后就会出现在市场里，客户可以找到你、联系你。这条路对中小型的服务商可能反而更有价值，因为过去客户找咨询都是找大牌，现在在一个有明确场景、明确技术栈的市场里，专业细分的小团队更容易被看见。你在某个垂直行业的经验，第一次有了一个能被主动检索到的地方。

接下来我们看文章里给的那个具体案例。这一段其实信息量很大，但原文写得非常短。文章说，CodeRabbit 把它对 Anthropic 承诺额度的一部分用在了 Vercel 上，因为它的编码代理跑在 Vercel 上；Power Digital 和 ThoughtSpot 也做了同样的事，只不过对象是 Snowflake，因为他们的数据在 Snowflake 上。

我们把这个案例放大来看。CodeRabbit 是做代码审查工具的，它的产品本身在 Claude 之上构建。它的基础设施跑在 Vercel 上，所以 Vercel 是它的成本项之一。Anthropic 说，那你就把承诺给我们的一部分钱，直接付给 Vercel 吧。这样一来，CodeRabbit 相当于用本来就要花在模型上的预算，覆盖了一部分基础设施支出，现金流上更从容。Vercel 则拿到了一笔本来可能要走很长销售流程才能拿到的收入，而且客户质量很高，因为对方本来就在用 Claude。而 Anthropic 呢，客户对它的承诺额度被用掉了，续约的数字更好看。

数据侧的例子里，Power Digital 和 ThoughtSpot 的处境类似，它们的数据在 Snowflake 里，Snowflake 是它们的核心依赖。把额度导过去，等于把最贵的两块成本，模型和数仓，变成了一笔可以统筹的预算。对一家正在快速扩张的公司来说，能少签一份合同、少走一轮审批，价值可能比折扣本身更大。

这个模式的本质，我个人认为，是把"承诺额度"变成了一种内部货币。它可以在生态里流转，用来支付生态里其他成员的账。这有点像航空公司的里程，或者是云厂商的抵扣券，但比那些更结构化，因为它绑定了具体的商业关系，不是随便谁都能收。

好，讲到这里，我们进入今天最重要的一部分，这些事对屏幕前的你到底意味着什么。

对于在公司里做 AI 平台的工程师，这篇文章最重要的信息是采购路径的变化。以前你要引入一个新工具，得走安全评估、采购流程、预算审批，每一步都可能卡住。现在如果这个工具在市场里，而且可以走承诺额度，你的推动成本会低很多。我建议你做的第一件事，是去看看你们公司跟 Anthropic 的合同里，承诺额度还剩多少，有没有"可用于第三方产品"这一条。这个信息通常在采购或者财务手里，但它决定了你接下来半年能推动的事情的上限。很多工程师从来没问过这个问题，结果一直在用最费劲的方式推动创新。

第二件事，是把你现在自研的那些对接代码盘一遍。用 MCP 标准写的，可以优先考虑换成官方或者第三方的连接器，把维护成本释放出来。自研的部分留给真正差异化的东西，比如你们内部的业务逻辑、权限模型、审批流。不要什么都自己写。我见过太多团队，把半年时间花在写一个别人已经维护得很好的 Salesforce 连接器上，然后在真正需要他们发力的业务逻辑上草草收场。

第三件事，是重新设计你的接入层。如果你的团队现在是每个工具写一套对接，那趁着 MCP 生态成熟，把这一层收拢成统一的网关。好处有三个：安全策略可以集中管理，不用在十个地方各审一遍；审计日志有统一出口，出了事能追溯；将来换模型或者加模型的时候，不用把对接层重写一遍。第三点在未来这一年尤其重要，因为大多数公司已经不再是"只用一个模型"了，而是根据任务类型、成本、延迟去选不同的模型。接入层如果是统一的，模型切换就只是配置变更；如果是散的，那就是一次重构。

对于独立开发者和小团队，这篇文章给了很明确的信号：生态的入口是开放的，而且有两套标准可以用。MCP 解决连接，Agent Skills 解决场景。如果你手上有一个垂直领域的工具，我建议你想清楚一件事：你到底是在卖一个功能，还是卖一个工作流。功能很容易被模型厂商的原生能力吃掉，你今年做的花哨能力，明年可能就是模型自带的一句话指令。工作流不容易被吃掉，因为它牵扯到数据、权限、以及组织里的固有流程。你的护城河应该在后者。

上架这件事的好处是分发，坏处是你要接受平台的规则，包括审核、定价、以及可能的分成。这里有个很现实的取舍：你愿不愿意用一部分自主权，换一个能直接接触到企业预算的渠道。我个人认为，对于早期团队，这个交换通常是划算的，因为自己一家一家敲企业客户的门，成本高得多，而且周期长到你可能撑不到第一笔收入。但如果你已经有一批稳定的客户，那就要算清楚边际收益，看看新渠道带来的增量，是不是值得让出定价权。

具体到做法上，我建议的顺序是这样：先把最核心的那一个使用场景做扎实，做成一个能被明确描述的能力，然后用 Agent Skills 把它包装出来，再用 MCP 把数据通道打通。不要一上来就想着做一个大而全的套件，因为在市场这种环境下，用户是按具体问题来找工具的，不是按产品线来找的。一个能被一句话说清的能力，比十个模糊的功能更容易被选中。

对于做咨询和交付的团队，Partner Network 值得认真考虑。因为企业的需求已经从"帮我做个原型"变成了"帮我把它推全员"。后者的周期长，单价高，而且极度依赖方法论和信任。加入一个官方名录，至少在信任这件事上帮你省了一段路。而且这类市场有个特点，早期的名录成员会获得更多的曝光红利，等到名单变长、竞争变激烈，后来者的获客成本会明显上升。

接下来我想说几个坑，这些是听这类好消息时最容易被忽略的地方。

第一个坑是供应商锁定，只不过换了一种形式。当你的采购预算、工具链、连接器、甚至服务伙伴都在同一个生态里的时候，迁移成本是整体上升的，不是单项上升的。你今天省下的采购精力，可能是三年后谈判时失去的筹码。所以我的建议是，接口层一定要保持标准化。选 MCP 这种开放协议做接入，哪怕你用的是某一家厂商的市场，至少底层是可替换的。另外，关键业务逻辑不要写进任何一个连接器里，连接器是可以换的，逻辑换了要命。

第二个坑是 MCP 带来的安全面扩大。这是我在过去一年里看到最多问题的部分。MCP 服务端本质上是给模型开了一扇通往你内部系统的门。如果权限没做细，模型可能会读到它不该读的东西，或者执行它不该执行的操作。企业上连接器之前，至少要问清楚四件事：这个服务端用的是什么身份访问我的系统，是服务账号还是用户本人的身份；它的权限粒度到了什么程度，是整库级还是行级；它有没有写权限，写操作有没有二次确认或者审批环节；它的调用日志能不能进到我的审计系统里。这四个问题答不上来的连接器，无论它多好用，都不应该直接进生产环境。

第三个坑是"承诺额度当预算工具"带来的财务被动。听起来很美，用不完的额度可以买东西。但反过来想，如果你的额度用得太快，或者第三方产品的定价随平台调整，你的成本控制就变成了被动。企业需要有人在财务侧盯住这件事，把它当成一项需要管理的资产，而不是一项自动的好事。我建议至少在季度层面做一次对账，看看额度的实际流向，哪些是真正带来价值的，哪些只是"反正钱已经付了"。后者的比例，往往比大家想象的高。

第四个坑是评估和维护的长期成本。装一个连接器很容易，让它持续可用不容易。上游系统的接口变了怎么办，认证方式换了怎么办，供应商停止维护了怎么办。所以在引入任何连接器或者代理之前，除了功能评估，还要看它的维护承诺。有没有服务等级约定，有没有公开的更新日志，有没有明确的弃用政策。这些问题听起来很枯燥，但它们决定了半年以后你是继续正常用，还是被迫临时救火。市场上架的那一刻是兴奋的，第十八个月才是考验。

第五个坑是数据边界。这一点在 Marketplace 这种形态下特别容易模糊，因为一个工作流里可能同时涉及三家的服务。数据从你的系统出来，经过模型，可能还要经过一个第三方代理，再落到另一个平台上。每一跳都是一个潜在的数据暴露面。比较务实的做法，是画一张数据流向图，标出每一跳的数据类型、处理方式和留存策略，然后在采购评审时把它作为必要材料。如果供应商画不出这张图，你就得自己画，然后拿它去问对方。

第五个坑说完了，我们也快接近尾声了。说说我个人的整体判断。

我个人认为，Claude Marketplace 这一类产品的出现，标志着大模型行业的竞争重心在发生位移。二〇二三年到二〇二四年，大家比的是模型能力，谁的分数高、谁的上下文长、谁更便宜。二〇二五年开始，比的是工具调用和代理能力，谁能真正替人把一件事从头做完。到了二〇二六年，比的是生态和采购路径，也就是谁能更低摩擦地把能力送进企业的预算里。这篇文章基本就是第三阶段的宣言书。

对中国的工程师来说，这件事的参考价值不在于你能不能马上用上这个市场，而在于这套结构本身的逻辑。连接器标准化、代理能力按需加载、承诺额度跨厂商流转、服务伙伴名录化，这四件事任何一个有企业客户的平台都会遇到。你可以把它当成一份产品设计参考，看看如果将来你要做一个面向企业开发者的市场，需要解决哪些问题。我个人觉得，最值得抄的不是它的功能清单，而是它把预算流动当成产品设计的一部分这个思路。

最后我想留一个问题给你。如果明天你所在的公司要决定，把明年 AI 预算的一部分放进这样一个市场里，你会投赞成还是反对。赞成的人会说，这降低了采购成本，加快了落地速度。反对的人会说，这加深了锁定，模糊了数据边界。我的看法是，这两件事可以同时成立，关键不在于要不要进，而在于进去之前有没有把接口层标准化和数据治理这两件事做扎实。做扎实了，你是在用别人的生态放大自己的能力；没做扎实，你就是把主动权一点点交出去。

好，今天就聊到这里。总结一下这篇文章：Anthropic 在二〇二六年九月二十三日上线了 Claude Marketplace，把连接器和插件、代理和产品、服务伙伴三样东西收进同一个入口；对客户来说它是统一的发现和采购渠道，对合作伙伴来说它是触达 Claude 用户的新路径；核心机制包括两千多个连接器、可以用承诺额度购买的第三方产品、以及一个咨询伙伴网络。原文只有五分钟的量，但背后的结构性变化值得多想几层。这是我的解读，感谢你听到这里，我们下期再见。
