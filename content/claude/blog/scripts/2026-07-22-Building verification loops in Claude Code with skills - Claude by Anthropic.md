Building verification loops in Claude Code with skills，中文可以翻译成，在 Claude Code 里用 skills 构建验证循环。这篇文章发表于二〇二六年七月二十二日，今天是二〇二六年七月二十六日，所以这是一篇非常新的文章，基本可以看作 Anthropic 对当下 agentic coding，也就是智能体式编程工作流的一次实践总结。

今天这期为什么值得听呢？因为它讲的不是又一个更酷的代码生成 demo，也不是说 Claude 能不能一次写出某个组件、某个接口、某段测试。它讲的是一个更贴近日常工程的痛点：当 AI 帮你写完代码之后，怎么知道它真的写对了？更进一步，能不能让它自己去检查，发现问题，自己修，而不是每次都等你看一遍、指出来、再让它改？如果你已经在用 Claude Code、Cursor、GitHub Copilot，或者任何带 agent 能力的编码工具，这个问题应该非常熟悉。

我们先把原文的核心句子翻译成大白话。大多数 agentic coding session，也就是一次智能体编码会话，都会经历一个循环。你提出一个改动需求，Claude 去收集上下文，然后动手修改代码，接着验证结果。如果验证不通过，它会再回去收集更多上下文，继续改，继续验证。听起来很自然，对吧？但现实里经常卡在验证这一步。模型能看到类型检查器、linter、测试、运行时报错，这些都是确定性的信号。可是它看不到的部分，往往就是你这个项目、你这个团队、你这个业务里最关键的部分。

举个很常见的例子。你让 Claude 改一个后端接口，它把功能写出来了，单元测试也过了。但是你作为老工程师，一看就知道，日志里不能把用户提交的请求体打出来，因为里面可能有敏感信息。或者你让它改一个数据库 migration，它写了 drop column，你马上会问，有没有 backfill 步骤？有没有兼容老版本？这些东西可能不是通用 linter 能检查出来的，也不一定在测试里覆盖到了，但你每次 code review 都会盯。Anthropic 这篇文章的重点就是，这种你反复手动做的小检查，不应该永远靠你的脑子记着，而应该变成 Claude Code 里的 verification loop，中文可以叫验证循环。

所谓验证循环，就是 AI agent 检查自己工作的重复过程。它可以跑测试，跑 linter，跑自定义检查，然后发现失败就回头修，修完再检查。Claude Code 里的一个关键能力，是可以把这种循环打包成 skill，也就是技能。skill 可以理解成一份可复用的操作说明书，里面写清楚什么时候用、允许用哪些工具、具体怎么检查、发现问题怎么处理。这样每次会话就不再依赖人类临时想起来，而是自动套用同一套检查。

这篇文章的背景，其实是整个 AI 编程工具正在从“会写代码”走向“会完成工作”。早期我们用 AI 写代码，更像是一个高级自动补全。你给它一段 prompt，它吐一段代码，你复制进去，然后自己编译、自己测试、自己 review。后来 agent 能力起来以后，它可以读项目、改多个文件、执行命令、观察报错。于是问题就变成了，怎么让它不只是能动手，还能像一个靠谱同事一样，在交付之前先自查一遍。工程师都知道，真正花时间的不是敲代码本身，而是那些边边角角的质量约束。比如类型有没有对齐，测试有没有补，错误处理有没有统一，日志有没有泄漏信息，UI 有没有符合设计规范，接口有没有破坏兼容性。AI 如果只负责写，而人类负责所有验收，那它带来的效率提升会被打折扣。

Anthropic 在文章开头列了 Claude 已经支持的一些验证方式。我们慢慢拆开看。

首先是斜杠 verify skill。它的作用是构建、运行并观察你的应用变化。你可以把它想象成一个默认的“跑起来看看”。这不是玄学判断，而是尽量利用工程系统里已经存在的确定性信号。代码能不能 build，测试能不能过，页面或者服务运行时有没有明显错误，这些都是模型可以通过工具观察到的东西。这里有个很重要的思想，AI 的可靠性不是靠它自己说“我觉得没问题”，而是靠它接上外部反馈。就像人类工程师不会只靠肉眼说没 bug，而会跑测试、看日志、看监控一样。

接着是 toolchain，也就是工具链。文章说，Claude 会尽量捕捉并处理你提供的任何工具的错误码和警告，比如 linter。这里有一个非常实用的小建议，Anthropic 建议你把精确的 build 和 test 命令写进 CLAUDE.md。这个文件可以理解成给 Claude 的项目说明书。为什么这点重要？因为很多项目不是简单一个 npm test 就完事。有的要先生成类型，有的要指定 workspace，有的测试要带环境变量，有的 monorepo 要在某个 package 目录下跑。如果你不告诉 Claude，它只能猜。猜错了，它可能跑了一个不完整的测试，还以为验证通过。把命令明确写下来，相当于给 agent 铺好铁轨。

然后是 Code Review，文章标注它还是 research preview，也就是研究预览能力。它是一个托管的多 agent 服务，可以对你启用的仓库里的 PR 做自动 review。如果发现问题，你可以自己修再 push，也可以在对应 finding 上评论 @claude，让它闭环处理，前提是你已经配置好了 GitHub Actions。这里可以看到 Anthropic 的方向不是把 Claude Code 只当本地工具，而是把它放进整个软件交付链路里。PR 不是终点，而是另一个 agent 可以介入的地方。

再往下是 GitHub Actions。文章说，你可以定义一个 job，让它调用 Claude 和某个 verification skill。这样你本地跑的同一套检查，就能在每次 push 或者 PR 时自动触发。这个点对团队很关键。个人本地习惯再好，也挡不住有人忘记跑。CI 的价值就在于把“你应该做”变成“系统一定会做”。verification skill 接上 GitHub Actions 后，个人工作流就开始有机会变成团队级门禁。

还有 spec validation，也就是规格验证。它是一个 skill，用来对照仓库里的 markdown spec 检查每个变更，并尝试修复违反 spec 的地方。这个能力在 AI 时代很有意思。过去很多团队写需求文档、设计文档，最后它们会慢慢变成历史资料。现在如果 agent 能读取这些 spec，并把它们当作验证依据，那文档就不只是给人看的，也能成为机器执行的约束。你可以想象一个场景，团队有一份 API 设计规范，里面写着错误码格式、分页参数、命名风格。以前这些靠 review 传承，现在可以让 Claude 在每次改接口时对照检查。

最后是 Claude Managed Agents 里的 rubrics，目前文章说是 beta。rubric 可以理解成评分标准或者评估量表。这个托管 agent 服务允许你用一个独立的 grader agent，也就是评分 agent，来对结果进行验证。如果失败，会自动回到返工环节。这个设计特别像人类团队里的分工，一个人写，一个人 review。只不过在这里，写和评是两个 agent。它的价值在于减少同一个 agent 自说自话的风险。因为生成者往往会倾向于认为自己做得不错，而一个独立评估者更适合按照 rubric 去挑问题。

讲完这些内建能力，文章进入最重要的实践部分：什么时候该写自己的自定义验证循环？答案很朴素，当你发现 Claude 每次帮你实现新功能之后，你都要做同样的小修小补，就该把这些步骤写下来。注意，这里不是让你一上来构建一个宏大的自动质量平台，而是从你这一周最常做的手动 follow up 开始。你老是提醒它“这里要加 request ID”，那就写下来。你老是提醒它“不要把请求 body 打日志”，那就写下来。你老是提醒它“改 UI 要对照 DESIGN.md”，那也写下来。

如果是一个新项目，情况也类似。你可能还没有一堆历史问题，但你知道项目应该怎么运行，应该遵守哪些最佳实践。文章建议，把最佳实践版本用普通英文写出来，就像第一天把它交给一个新同事一样。这个比喻很好。我们平时给新人 onboarding，不会只说“代码写好点”。我们会说，这个项目组件放在哪里，测试怎么命名，日志怎么打，错误怎么处理，哪些 API 不能随便改。skill 本质上就是把这种 onboarding 说明交给 Claude。

如果你一下子说不清检查规则，文章还建议可以先问 Claude 最佳实践，然后再修改。这里的关键不是完全相信 Claude 给的通用答案，而是借它帮你起草。你的团队版本很可能在几个点上不一样，而那些不一样的地方，恰恰是最应该捕获的。比如通用建议可能说错误日志要包含上下文，但你的项目进一步规定必须包含 request ID，且不能包含请求体、headers 或用户提交 payload。通用建议可能说 migration 要谨慎，但你的项目规定，任何删除列的 migration 都必须包含 backfill 步骤。这样的规则，就是通用工具很难替你管、但项目内部又非常重要的东西。

文章里有一个 pro tip，我觉得很值得强调。验证检查不一定是“定性”的，也可以是非常确定的规则。比如“拒绝任何没有 backfill 步骤就 drop column 的 migration”。这不是普通 linter 会知道的事，因为它不知道你们的数据迁移策略。但对你们项目来说，它可能是硬规则。所以只要是你反复用手工方式强制执行的检查，都有资格被捕获成 loop。这里的观念转变很重要。很多人一提 AI 验证，就想到复杂的语义理解、模糊评分。其实大量高价值检查并不复杂，只是太项目化、太局部，以至于没有现成工具覆盖。

那怎么把这些重复步骤编码成 verification loop 呢？文章说最常见方式就是写成 skill。最快的办法，是安装 skill-creator plugin，然后让 Claude 采访你。它给了一个例子，大意是，你可以输入“创建一个用于端到端验证前端变更的 skill，采访我了解工作流”。这个交互方式很适合工程团队落地。因为很多流程知识在你脑子里，但不是结构化文档。让 Claude 像访谈一样问你，改前端时看哪些页面，跑哪些命令，如何判断可访问性，哪里容易出错，最后把答案整理成 skill，比你从空白文件开始写要轻松很多。

当然，你也可以手写 skill。文章说，把一个 markdown 文件放到项目里的点 Claude 斜杠 skills 目录下就可以。最简单的 verification skill 包括几行 frontmatter，再加正文。frontmatter 里有 name，也就是技能名；description，也就是什么时候使用；allowed-tools，也就是允许它用哪些工具；正文里写具体检查步骤。文章举的例子叫 verify log hygiene，检查错误日志卫生。它要求读取当前 diff 里的错误处理路径，对每个错误路径上的 log 调用，确认包含 request ID，并且没有传入 request body、headers 或任何用户提供的 payload。发现违规要报告 file line，然后修复。该加 request ID 的加上，该去掉 payload 的去掉。

这个例子特别好，因为它不是一个玩具例子。日志安全真的是很多系统里容易被忽视的问题。AI 写错误处理时，很容易觉得“为了调试方便，多打点上下文”。但真实业务里，多打一点可能就是隐私事故。你如果每次都靠人 review，迟早会漏。把它写成 skill，相当于把“我们团队怎么安全地打错误日志”变成了可执行知识。

这里我个人认为有一个实践原则。写 skill 的时候，不要只写抽象目标，要写可观察动作。比如不要只说“确保日志安全”，这句话太大，模型可能不知道什么叫安全。要写“错误路径上的 log 必须包含 request ID，不得包含 request body、headers 或用户提供 payload”。也不要只说“发现问题要处理”，要写“报告 file line，然后修复”。越接近你会交代给新同事的具体话术，越容易形成稳定 loop。

接下来文章讨论一个非常工程化的问题：验证循环怎么触发？它把模式分成几类。我们不生硬报分类名，而是按使用场景来讲。

有些检查适合你主动调用。也就是说，产物已经存在了，你再告诉 Claude，来，帮我跑这个检查。这类适合跨工作流的检查，不是每次改代码都要做，但在某些节点很重要。文章举了几个例子，比如 pre commit security scan，提交前安全扫描；pre PR accessibility audit，发 PR 前做可访问性审计；repo 范围的 license header 检查。它们的共同点是适用范围广，但不是每个小改动都必须触发。主动调用的好处是灵活，坏处是你还得记得做。文章说得很直白，如果你发现自己每次改完都在运行它，那说明它已经不该继续当主动步骤，而应该嵌入或串起来。

另一种方式，是把验证嵌入到产生代码的 skill 里。也就是说，某个 skill 负责生成东西，生成完自动跑它自己的检查。文章举了一个 scaffold component 的例子。这个 skill 用来在 React 项目的 src components 下面创建一个新组件，包括组件文件、旁边的测试文件和 index export，并参考现有 Button 组件的模式。然后在说明末尾加一句，创建组件文件后，对它运行 eslint，并在报告完成前解决所有错误。这样用户只要说创建组件，skill 不只是生成文件，还会自动 lint 并修。检查和生产动作绑定在一起，不需要你另外提醒。

这类嵌入式验证适合非常具体的工作流。比如“创建组件”之后一定要 lint 新组件，“生成 API handler”之后一定要跑对应测试，“修改 schema”之后一定要跑类型生成。它的优点是无感，缺点是只适合你能编辑的 skill。文章提醒，内建 skill 和插件管理的 skill，尤其是更新时会被覆盖的那种，不适合直接改。如果你不能改原 skill，就不要用嵌入方式，而应该用后面说的链式方式。还有一点，跨多个工作流的检查也不适合塞进某一个 producing skill 里，否则会耦合过重。比如全仓库 license header 检查，就不该藏在创建组件 skill 里。

再往前一步，是 skill 调 skill，也就是把多个环节串成链。文章说，Anthropic 的 Claude Code 团队成员在日常里会用这种模式。比如 code review 先找 bug，simplify 清理 diff，verify 确认端到端行为，如果改动碰到 UI，再用自定义 design skill 对照 DESIGN.md 里的指南检查。这个流程很像一个小型开发流水线。先找问题，再简化，再验证，再检查设计规范。每一步都可以是一个 skill，最后组成一个更完整的开发循环。

链式验证还有一个现实用途，就是给你不能修改的 skill 加验证。文章举了一个 safe refactor 的 wrapper skill，大意是先运行 simplify，结束后再调用 verify no public API changes。也就是说，如果原来的 simplify 你不能改，那就写一个外壳。以后你不再直接运行 simplify，而是运行 safe refactor。以前你的习惯是“我总是在 simplify 后跑 verify”，现在习惯变成契约，“safe refactor 必须先 simplify，再 verify”。这个从习惯到契约的变化，是这篇文章很核心的工程思想。

不过链式并不是越多越好。文章也提醒，如果步骤之间足够独立，你有时候想单独运行其中一个，就不该强行串起来。链式会牺牲灵活性换自动化。而且 chained verification loops 可能增加 token spend，也就是 token 消耗。你让 Claude 连续执行多个 skill，每个都要读上下文、运行工具、解释结果，成本自然会上去。所以文章建议，在大范围部署前先测试这些 loop。对个人来说，先在自己的分支上试，看看有没有误触发、有没有太慢、有没有 token 花得不值。对团队来说，更要谨慎，不要把一个还不稳定的链直接变成所有 PR 的门禁。

当链在你自己的改动里已经稳定之后，就可以考虑把同样流程跑到每个 PR 上。文章说，这时验证就不再是个人基础设施，而是团队基础设施。一个队友的改动也会经过同样的 gates，也就是同样的关卡，不管他有没有记得手动调用。这句话我觉得非常击中工程管理的本质。很多团队规范靠口口相传，靠老员工 review，靠 PR 模板里一个 checklist。问题是 checklist 会被跳过，reviewer 会疲劳，老员工会请假。系统化门禁的价值，就是把“记得做”变成“默认做”。

但文章也提醒，PR 范围的 gate 不要太早上。只要链还在频繁调整，每次调整都会变成团队可见事件。比如今天多加一个检查，明天又改触发条件，后天发现误报太多再撤掉，整个团队都会被打扰。所以比较好的路径是，先个人使用，稳定后小范围试，再放到 PR。这个和传统 CI、lint 规则推广很像。你不会把一个误报很多的 lint rule 直接设成 error，否则大家只会想办法绕过它。

文章最后给了一个 loop engineering，也就是验证循环工程的通用流程。它说，无论你自动化什么、在哪个环境里，过程都是一致的。先挑本周你最常做的手动 follow up。先试试内建的 verify skill，看它是否已经能帮助你的流程。然后用普通英文写下步骤，就像第一天交给新同事一样。再交给 skill creator，或者自己把 markdown 文件放进点 Claude 斜杠 skills。接着在一个新任务上调用它，确认检查真的作为输出的一部分运行起来，不行就迭代。最后再尝试 skill chaining，形成端到端验证流。

注意这里的顺序很务实。不是先设计一个宏伟框架，也不是先讨论 agent evaluation 的哲学，而是从本周最烦人的重复动作开始。你可以问自己一个非常具体的问题：过去几天，我在 Claude 写完代码后，最常输入的那句话是什么？如果答案是“再跑一下测试”，那可能先把测试命令写进 CLAUDE.md，或者用 verify。若答案是“别忘了改文档”，那可以写一个检查 diff 是否触及 API，并验证文档是否更新的 skill。若答案是“这个组件要遵守设计规范”，那就把规范写进 DESIGN.md，再写一个对照检查的 design skill。重复出现的提醒，就是自动化的入口。

对我们这些工程师和 AI 从业者来说，这篇文章最有启发的地方，不只是 Claude Code 多了几个功能，而是它把 AI 编程的关注点往后移了一步。以前大家很关心 prompt 怎么写，怎么让模型生成更好的第一版代码。现在文章说，你能编码给 Claude 遵循的东西越多，Claude 第一次响应就越接近你想要的结果。这里的“编码”不是写传统程序，而是把项目规则、团队习惯、验收步骤写成 skill，写成 loop。换句话说，prompt engineering 正在变成 workflow engineering，甚至可以说是 process engineering。

如果你现在想在团队里实践，我建议从非常小的地方开始。选一个不会引发太多争议、结果相对明确、你又经常手动检查的点。比如日志里不能出现用户 payload，错误响应必须包含统一错误码，新增组件必须带测试，修改公共 API 必须更新 spec。不要一开始就写“检查代码质量是否优秀”这种大而空的 skill。大而空的规则既难验证，也容易让模型自由发挥，最后你反而不信任它。小而硬的规则更容易成功，也更容易让团队看到价值。

写 skill 描述时，要特别注意触发条件。文章里的例子在 description 里写了，当前 diff 触及 error handling 或 logging 时使用。这个细节很重要。如果触发条件太宽，Claude 可能在无关任务里也跑，浪费时间和 token。如果太窄，它又可能该跑时不跑。你可以把 description 当成给调度器看的说明，要写清楚“什么时候应该用”。这和写函数名、写注释有点像，模糊命名会造成误用，模糊 skill 也会造成误触发。

allowed tools 也值得认真对待。文章例子里允许 Read、Edit、Grep。它要读文件、搜索日志调用、修改违规代码，所以这些工具足够。并不是每个 skill 都要给 Bash，也不是每个验证都需要写权限。权限越大，潜在影响越大。尤其是在团队环境和 CI 里，能只读就只读，需要修改再给 Edit，需要跑命令再给 Bash。我个人认为，未来 agent 工作流的治理，很大一部分会落在这种工具权限边界上。让 agent 做事，不等于让它什么都能做。

再说 CLAUDE.md。文章只是提了一句，把准确 build 和 test 命令写进去，但这背后其实很关键。很多 AI 工具失败，不是因为模型能力差，而是因为项目环境没有被机器可读地表达。人类老员工知道“这个测试要在 backend 目录跑”“先启动本地依赖”“这个警告可以忽略，那个不行”。Claude 不一定知道。你把这些写进 CLAUDE.md，就像给它一张地图。verification loop 的效果，很大程度上取决于这些外部信号是否清晰。

还有一个实践点，是让 skill 不只检查，还能报告。文章例子要求报告每个 violation 的 file line，然后修复。这个设计对信任很重要。你不希望 agent 默默改了一堆东西，只告诉你“完成了”。你希望知道它发现了什么，在哪个文件哪一行，为什么改。这样你可以快速抽查，也方便回滚。尤其在安全、隐私、公共 API 这类敏感检查里，报告比修复本身还重要。好的 verification loop 应该留下可审计的痕迹。

当然，我们也要看到边界。verification loop 不是魔法，不能保证所有 bug 都消失。它擅长的是把你已经知道、已经能描述、已经能通过工具或规则观察到的东西自动化。它不一定能替代产品判断，不一定能判断一个交互是否真的让用户满意，也不一定能发现所有复杂并发问题。文章最后也说，那些你不再需要反复 fiddling 的修正，会释放你的注意力，让你去做那些任何 skill 都写不下来的独特工作。这句话其实很清醒。AI 不应该把工程师变成旁观者，而是把低价值重复检查交给系统，让人把精力放在更难表达、更需要判断的地方。

我个人认为，verification loop 还有一个组织层面的价值，就是把隐性知识显性化。很多团队里，资深工程师脑子里有一套规则：哪些地方危险，哪些模式不要用，哪些历史坑不能踩。新人不知道，AI 更不知道。过去这些知识靠 review 传递，成本很高。现在你可以把它写成 skill，让 Claude 每次都执行。久而久之，这些 skill 就像团队的活文档。它们不是静态 wiki，而是能在代码变更时主动介入的文档。

但要避免另一个坑，就是把所有偏好都做成硬门禁。有些东西是规则，比如不能泄漏请求体，不能破坏公共 API。有些只是偏好，比如你更喜欢某种写法，但团队并没有共识。如果把个人偏好过早变成 PR gate，团队会很痛苦。比较好的做法是先区分“必须遵守”和“建议优化”。必须遵守的规则适合自动修复或阻断，建议优化可以先作为报告，不一定阻断。等团队形成共识，再升级。

还有 flaky checks，也就是不稳定检查的问题。传统 CI 里最讨厌的就是 flaky test，AI verification loop 也一样。如果一个 skill 经常误报，或者每次结果不一致，工程师很快会失去信任。失去信任之后，大家要么忽略它，要么绕过它。文章虽然没有展开这一点，但它提到要先测试 loop 再广泛部署，我觉得就是这个意思。自动化的前提是稳定。宁可少一点，但可靠一点。

对安全相关的 loop，更要注意不要让 agent 做危险操作。比如 migration 检查可以读 diff、指出风险，但自动修改数据库迁移可能需要更谨慎。日志脱敏可以自动改代码，但涉及删除字段、改数据结构、修改鉴权逻辑时，也许应该升级给人类确认。verification loop 的目标是闭环，但闭环不等于所有事情都无人值守。哪些失败可以自动修，哪些失败必须 escalate back to you，也就是升级回给你，是每个团队要自己设计的边界。

如果你是平台团队或工具团队，这篇文章还给了一个很好的产品方向。不要只给业务团队一个“AI 会写代码”的入口，而是提供一套可复用的 skill 模板。比如前端项目模板里带可访问性检查、设计规范检查、组件测试检查。后端项目模板里带日志安全检查、migration 检查、API spec 检查。基础设施项目里带配置变更检查、兼容性检查、回滚说明检查。业务团队可以在模板上改自己的规则。这样 AI 编程能力就不只是个人效率工具，而是企业工程体系的一部分。

如果你是个人开发者，也不用觉得这离你很远。你完全可以从一个最小 skill 开始。比如你维护一个开源项目，每次合并 PR 前都要检查 README 有没有更新，或者每个新命令都要出现在帮助文档里。把这个写成 skill。再比如你写前端，每次 Claude 改组件后你都要提醒它跑 eslint 和测试，那就把这一步嵌入 scaffold 或修改组件的 skill。再比如你做 SDK，每次改 public API 都担心 breaking change，那就写一个 wrapper，在重构后调用一个检查 public API 变化的 skill。重点不是一下子全自动，而是把最烦、最常见、最明确的那一步拿出来。

从更大的趋势看，Anthropic 这篇文章反映了一个行业阶段。到二〇二六年，AI coding 已经不只是模型 benchmark 上谁会写 LeetCode，或者谁能补全函数。真正的竞争开始转向工作流、工具权限、验证机制、团队集成。模型生成能力当然仍然重要，但工程团队更关心的是，它能不能安全地接入我的 repo，能不能理解我的规范，能不能在 PR 上给出可靠反馈，能不能在失败后自动修复，能不能不要制造更多 review 负担。verification loop 正是这个阶段的关键词之一。

文章最后一句的意思是，你能编码给 Claude 跟随的内容越多，Claude 的回答就越常在第一次尝试时更接近你想要的结果。那些你不用再手动纠缠的小修正，会把注意力还给你，让你去做那些没有任何 skill 能替你写下来的工作。我觉得这也是今天这期最好的总结。AI agent 的价值，不只是聪明，而是能接入反馈。没有验证的生成，只是一次猜测；有验证循环的生成，才开始像工程。

所以，如果你听完只带走一个行动项，那就是回去看一下你最近几次和 Claude Code 的对话，找出你重复说过最多的一句纠正。把它写成普通语言，放进 skill，先在一个小任务上试起来。不要追求完美，先让 Claude 学会替你检查一个小坑。一个小 loop 稳了，再串成更大的 loop。个人习惯就这样变成契约，契约再变成团队基础设施。对于 AI 编程工具来说，这可能比又多生成几行代码更重要。
