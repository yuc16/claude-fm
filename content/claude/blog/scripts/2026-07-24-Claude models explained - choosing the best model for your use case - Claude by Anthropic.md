今天我们解读的文章标题是 Claude models explained: choosing the best model for your use case，中文可以翻译成，Claude 模型详解，如何为你的使用场景选择最佳模型。这篇文章发表于二〇二六年七月二十四日，也就是两天前。今天是二〇二六年七月二十六日，所以这是一篇非常新的文章，不存在明显的时效性折扣。它反映的是 Anthropic 在当前这个阶段，对 Claude 模型家族、成本、能力、延迟和评测方法的一次官方整理。

为什么这篇文章值得我们在通勤路上花二十多分钟听一遍？因为它回答的是很多工程团队现在每天都会遇到的问题。不是大模型能不能用，而是这个任务到底该用哪个模型。你做一个代码 agent，要不要上最贵的模型。你做客服摘要，Sonnet 够不够。你做批量信息抽取，Haiku 会不会更合适。你做一个企业内部知识工作流，Opus 和 Fable 到底差在哪里。更关键的是，Anthropic 在这篇文章里没有只给一个营销式答案，而是把模型选择拆成了几个非常工程化的问题：任务有多难，延迟要求多高，访问权限有什么限制，单位经济账怎么算，以及怎么用评测来证明选择是对的。

文章一开头就说，他们最常听到的问题之一就是，这个 workload，也就是这类工作负载，我应该选哪个模型。随着模型类别和版本越来越多，答案变得更微妙了。以前我们可能简单地说，复杂任务用大模型，简单任务用小模型。但现在不是这么粗糙了。因为还有 effort level，也就是努力程度或者推理投入程度。你可以把它理解成，在同一个模型上调节它愿意花多少计算和思考时间去解决问题。这样一来，模型选择就不是单轴选择，而是一个二维甚至多维选择。横轴是模型类别，纵轴是 effort level，再加上你的业务约束，比如响应时间、预算、数据访问权限和质量门槛。

Anthropic 给出的默认建议很有意思，他们说，先把复杂的细节放一边，默认建议是，从最聪明的、已经普遍可用的模型开始，然后用 effort level 去调节性能和成本。这个观点乍听上去有点反直觉。很多工程团队一开始会说，先用便宜模型吧，能省就省，顶不住再升级。但 Anthropic 的核心理由是，价格不能只看每个 token 的价格，而要看每个任务的成本。更聪明的模型虽然每 token 更贵，但它可能用更少的轮次、更少的思考时间、更少的返工，直接把任务做对，所以算到每个任务上，反而可能更便宜。

我们用一个日常工程例子来理解。假设你要让模型帮你修一个测试失败的 bug。一个便宜模型每次调用很便宜，但它看了日志之后猜错了原因，改了两个无关文件，测试还是挂。你又让它重新看，它又提出一个不完整修复。最后你花了六轮对话，生成了很多 token，还需要人工 review 半小时。另一个更强模型每 token 价格高一些，但它第一轮就把报错路径、失败断言、相关函数和历史行为串起来，给出一个更小的 patch，测试直接过。你如果只盯着单价，会觉得前者便宜；但如果按完成一个 bugfix 的总成本算，包括模型调用、等待时间、人工介入和失败重试，后者可能更划算。这就是文章里说的 cost-per-task，每个任务的成本，经常比 price-per-token，每 token 价格，更能反映真实经济账。

文章还提醒了一个很工程化的坑：如果一开始就用较小模型，有时候会让你分不清失败到底来自模型能力，还是来自系统配置。比如你刚搭了一个检索增强生成系统，也就是 RAG。你问模型一个公司制度问题，答案不对。原因可能是模型不够强，也可能是检索召回不对，也可能是 chunk 切得太碎，也可能是系统 prompt 写得让模型忽略引用，也可能是权限过滤把关键文档过滤掉了。如果你一开始用一个能力偏弱的模型，排查时就会很痛苦，因为模型失败和工程失败混在一起。Anthropic 的建议是，先用最聪明的普遍可用模型建立一个比较高的上限，证明流程本身能跑通，质量能达到。之后再往下试更便宜、更快的模型，找到刚好够用的点。这个思路和我们做性能优化很像，先写出正确版本，再做 profile 和优化，而不是一开始就在一个错误实现上抠毫秒。

当然，文章也没有说所有团队都必须这么做。它承认，有些组织会选择反过来，从最具成本效益的模型开始，然后逐步向上升级，直到达到质量门槛。也就是说，存在两种方向。一个方向是从高能力往下压成本，另一个方向是从低成本往上补质量。哪种更适合你，取决于你的组织文化、预算压力、任务风险和上线节奏。我个人认为，对于探索期的新工作流，尤其是你还不知道任务可不可做的时候，从强模型开始更合理；对于已经定义清楚、失败代价低、量非常大的生产任务，从便宜模型开始逐步升级，也很合理。

接下来文章介绍 Claude 模型家族。它把模型分成几个类别：Mythos 和 Fable、Opus、Sonnet、Haiku。这里要注意，Anthropic 明确说，这些模型类别不是按行业来划分的。不是说金融用一个模型，科研用另一个模型，代码再用第三个模型。每个 Claude 模型都被训练成在 coding，也就是编程，agentic tasks，也就是能自主规划和执行的代理任务，以及 knowledge work，也就是知识工作上表现良好。真正的差异在于，它们能可靠承载多难的问题，以及这种能力在价格和速度上要付出什么代价。

先说 Mythos 和 Fable。文章说，Mythos 是 Anthropic 最强的模型类别，在多个领域都有前沿能力，尤其擅长 coding、长时间运行的 agent 任务，以及解决那些过去 AI 还不能稳定处理的问题。这里的 long-running agent tasks，可以想象成不是一次问答，而是一个模型要连续规划、调用工具、读写文件、检查结果、修正计划，甚至跨很多步骤完成目标。比如让一个 agent 在一个大型代码库里定位性能瓶颈、改实现、补测试、跑基准、写变更说明，这就不是简单聊天，而是长链条执行。

文章又说，Mythos 这个底层模型会以两种包装形式交付。Claude Mythos 面向可信组织，用来处理 dual-use cybersecurity and biology work，也就是具有双重用途的网络安全和生物相关工作。双重用途的意思是，这些能力可能既能用于防御和研究，也可能被滥用。所以访问会更受限制。Claude Fable 则带有额外的 safeguards，也就是安全保护，使它适合一般公众使用。文章还提到，两者都要求 limited data retention，也就是有限的数据保留，以便安全使用。这里我们不要过度展开，因为原文没有给更多细节，但可以理解为，Anthropic 在最强模型上同时做了能力分层、访问控制和安全包装。

再看 Opus。文章说，Opus 是面向 reasoning-intensive enterprise tasks，也就是推理密集型企业任务的强模型类别。它在一些关键行业 benchmark 上表现很靠前，比如 GDPval-AA 用来衡量知识工作能力，Terminal-Bench 二点一 用来衡量 agentic coding，也就是带代理性质的编码能力。这里的重点不是某个 benchmark 名字本身，而是 Anthropic 对 Opus 的定位：它不是最低价，不是最快，而是企业里需要强推理、强可靠性、强知识工作能力时的主力模型。

有意思的是，文章专门讲了 Opus 和 Fable 的区别。表面上看，它们都擅长 coding、长时间 agent 和知识工作，所以怎么选好像不清楚。Anthropic 给出的观察是，在真实世界里，像 Fable 这种更大的模型，即使在 benchmark 分数上和 Opus 类似，往往还是会表现出更多 wisdom、creativity and writing skills。这里的 wisdom 可以翻译成判断力或者智慧，creativity 是创造力，writing skills 是写作能力。这个说法很重要，因为它承认 benchmark 分数不是全部。两个模型都能把题做对，但在真实任务里，一个模型可能更会判断优先级，更会发现需求里的含混点，更会写出让人信服的解释，更会在没有标准答案的任务里做出高质量取舍。

文章给了一个经验规则。如果你的 evals，也就是评测，或者内部测试显示 Opus 在某些任务上吃力，那么 Fable 就是答案。如果 Opus 已经能通过质量门槛，那么 Opus 的速度和价格画像可能让它成为更好的选择。换句话说，不要为了追求名义上的最强而无脑上 Fable，也不要因为 Opus 已经很强就忽略那些它仍然搞不定的边界任务。真正的判断标准是，你自己的任务和你自己的质量线。

Sonnet 的定位就更接近日常主力。文章说，Sonnet 是 Anthropic 面向 everyday tasks，也就是日常任务的 versatile model class，通用而灵活。它在性能、成本和速度之间取得平衡，适合最广泛的一般用途场景。文章还特别提到，它适合 multi-agent orchestration setups 里的 high-volume sub-agents。翻译成人话就是，在一个多 agent 编排系统里，你可能有很多子 agent 负责不同的小任务，比如一个负责读需求，一个负责检索文档，一个负责生成测试，一个负责格式化输出，一个负责做初步检查。这些子 agent 调用量大，不一定每一步都需要最强模型。Sonnet 往往是这种场景里很自然的选择，因为它够强、够快、成本也相对可控。

Haiku 则是最低成本、最快的模型类别。文章说，Haiku 设计给 high-frequency workloads，也就是高频工作负载，尤其是延迟和成本非常重要的场景。比如你有一个实时输入补全、轻量分类、简单路由、短文本改写、日志标签化、低风险内容筛选，这些任务单次难度不高，但量非常大，用户又不能等太久。这个时候，Haiku 可能是更合适的起点。不过要注意，文章没有说 Haiku 只会做简单任务，也没有说它不适合代码或知识工作。Anthropic 的框架是，所有 Claude 模型都覆盖这些能力，只是能可靠扛住的问题难度不同。

讲完模型家族，文章进入真正的选择方法。它说，选择模型时要问几个问题。第一个问题是，这个任务有多难。如果一个任务通常要花很多时间、涉及多个步骤，或者过去还没有稳定解决方案，那就更适合更强的模型类别。这个标准非常实用。你不用先问这是金融还是教育，也不用先问它是不是代码。你先问，一个合格的人类做这个任务需要多久，需要多少上下文，需要多少判断。如果人类也要花很长时间查资料、拆步骤、反复验证，那么对模型来说也大概率不是轻任务。

举个例子，让模型把一段用户评论分类成正面、中性、负面，这可能不难。让模型读一份三十页的企业合同，找出和标准模板不一致的条款，并评估风险等级，再给出修改建议，这就明显更难。让模型在一个几百万行代码库里理解服务调用链、定位竞态条件、设计修复方案并确保不破坏兼容性，那就更难。任务难度不仅来自输入长度，还来自需要做多少隐含推理、多少跨步骤记忆、多少工具调用，以及失败后能不能自我纠正。

第二个问题是延迟需求。文章说，如果模型参与的是高频的、面向客户的工作负载，Sonnet 往往是最佳选择。这里的关键词是 customer facing，也就是用户直接感知响应时间。比如用户点了一个按钮，期望两秒内看到结果。你不能因为模型更强，就让用户等二十秒。对于面向客户的实时交互，速度和稳定性本身就是产品质量的一部分。即使 Fable 在某些复杂问题上更强，如果你的场景是每个用户每分钟触发多次请求，而且绝大多数请求并不复杂，那么 Sonnet 或更低类别模型可能更实际。

第三个问题是访问限制。文章明确说，Mythos 只对 Project Glasswing 下的组织开放。并且，不是所有组织都会把所有模型类别开放给所有角色。这个点在企业落地里很常见。你作为工程师可能在文档里看到某个模型最强，但你的公司账号不一定能用。或者安全策略规定，某些数据不能发给某些模型。又或者某些高能力模型只允许特定团队、特定项目使用。模型选择从来不是纯技术题，也是治理和权限题。

第四个问题是单位经济账。文章说，更高规模的生产量可能更适合较低类别的模型，尤其是评测显示这些任务可以满意完成时。不同模型的每 token 定价不同，但每任务成本还会受到模型能力和 effort level 影响。这里 again，我们不要只看单价。你要把输入 token、输出 token、重试次数、工具调用次数、人工审核时间、失败造成的业务损失都算进去。一个每天一百次的内部分析任务，和一个每天一千万次的用户请求，对成本敏感度完全不同。前者可能为了质量直接用更强模型，后者必须精细优化每一次调用。

effort level 是文章反复强调的另一个杠杆。更高类别模型配合更高 effort，可以给出最好的性能；而更高类别模型配合较低 effort，有时会比小模型更高效。这个点很值得品味。很多人以为省钱只有一个方向，就是换小模型。但文章提醒你，还有另一个方向，就是用强模型但降低它的推理投入。打个比方，找一个资深工程师快速看一眼，可能比找一个初级工程师研究半天更快更准。强模型低 effort 在一些任务上可能就是这种效果。它的底层能力和判断力更强，不需要花那么多步就能抓住重点。

文章还提到一个很有价值的组合方法，叫 advisor strategy，可以翻译成顾问策略。它的思路是，让更快、更低成本的 worker models，也就是工作模型，来执行大部分任务；只有在需要的时候，调用更聪明的模型来检查计划、评估工作，从而提升整体表现。你可以把它想象成一个团队。不是每一行代码都让首席架构师亲自写，而是由工程师先做，关键节点请资深架构师 review 方案、指出风险、确认结果。这样既保留了高能力模型的判断力，又避免全程使用高成本模型。

原文给了一个具体例子。在 SWE-bench Pro 上，Sonnet 五 搭配 Fable 五 advisor，得分距离全程使用 Fable 五 的得分在百分之十以内，但价格只有全程使用 Fable 五 的百分之六十三。这个数字很关键，因为它说明顾问策略不是一个抽象想法，而是在代码修复类 benchmark 上有显著效果。它的意义不是说永远都该这么搭，而是告诉我们，多模型协作可以改变成本质量曲线。你不一定要在单个模型之间二选一，你可以设计一个系统，让便宜模型做可并行、可验证、可回滚的工作，让强模型在计划、检查和疑难点上介入。

如果你在做 agent 系统，这个策略尤其值得尝试。比如一个代码 agent 可以先让 Sonnet 读 issue、定位相关文件、提出修复计划。然后调用 Fable 作为 advisor，让它检查这个计划有没有遗漏，是否应该先补测试，是否可能破坏 API 兼容。接着 Sonnet 执行修改，再让 Fable 或 Opus 对最终 diff 做审查。注意，这里我是在做工程推演，不是说原文给了这个具体流程。原文只说 worker model 可以在需要时调用更智能模型检查计划和评估工作。但从这个原则出发，我们很容易设计出计划审核、结果审核、失败升级、风险分流这样的模式。

不过顾问策略也有坑。第一个坑是，你要定义什么时候需要 advisor。如果每一步都调用强模型，那就变成全程强模型，省不了多少钱。如果太少调用，质量又上不去。第二个坑是，你要让 advisor 看到足够上下文。只给它一句话，让它判断计划好不好，它也没法判断。第三个坑是，你要决定谁说了算。worker 和 advisor 意见冲突时，是自动采用 advisor 的建议，还是让 worker 解释，还是升级到人类 review。原文没有展开这些工程细节，但对我们落地很重要。我个人认为，advisor strategy 最适合那些有明确阶段边界的任务，比如先计划再执行、先草稿再审阅、先生成再验证，而不是完全开放、没有结构的自由聊天。

文章后半部分讲 evals 和 benchmarks，也就是评测和基准测试。Anthropic 说，判断模型能力是否足够，常见有两种方式：使用标准 benchmark，或者做 custom evaluations，也就是自定义评测。benchmark 是一组预先定义好的任务或场景，通常面向某个领域，并且有已知解。它们可以作为方向性指南，帮助比较不同模型类别和不同提供商的能力。这一点很好理解。没有 benchmark，我们就只剩主观感受。benchmark 至少能给一个公共坐标系，让大家知道模型在代码、数学、知识工作、工具使用等方面大概处于什么水平。

但文章也提醒了一个问题，叫 saturation，饱和。对于 Opus 和 Fable 这样强大的模型，它们可能已经能解决测试集中几乎所有问题。这个时候 benchmark 分数就不再能拉开差距。就像考试太简单，两个学生都考九十八分，你很难根据这张卷子判断谁更能做研究、谁更能解决真实业务问题。标准 benchmark 的题目一旦被强模型打穿，它就更像入门门槛，而不是精细尺子。它能告诉你某个模型大概够不够强，但不一定能告诉你在你的生产场景里谁最好。

所以文章建议，组织应该把模型放到真实工作负载里试，或者用自己的评测来做决定。通常，自定义评测应该来自生产中的问题，尤其包括当前工具做不好的困难任务，并且成功标准由你的团队定义。这个建议非常重要。很多公司做大模型选型时，会拿一些网上公开题目或者随手写十几个问题来测，然后很快得出结论。问题是，这些题可能和你的真实业务没有关系。你的客服系统最难的不是回答百科问题，而是理解你公司复杂的退换货规则。你的代码 agent 最难的不是写一个排序函数，而是在你们代码库的历史包袱和隐式约束里做正确修改。你的法务助手最难的不是总结合同，而是识别你们内部标准条款的细微偏离。

自定义评测要怎么做，文章没有在这篇短文里展开细则，只说 Anthropic 已经写过很多关于自定义 agent 评测最佳实践的内容。但我们可以基于原文原则做一个工程化落地。你可以先从生产日志里抽样，挑出那些高频任务、失败代价高的任务、人工处理耗时长的任务，以及当前模型经常失败的任务。然后让领域专家定义什么叫成功。不是简单地说答案看起来不错，而是要有可检查的标准。比如代码任务要测试通过、diff 小、没有引入安全问题。客服任务要引用正确政策、不能承诺不存在的补偿、语气合规。数据抽取任务要字段完整、格式稳定、不能编造缺失信息。最后，你用不同模型和 effort level 跑同一套评测，记录质量、延迟、成本和失败类型。

这里我个人想强调一点，评测最好不要只记录一个总分。总分容易掩盖结构性问题。一个模型可能在简单样本上全对，在困难样本上全错；另一个模型简单样本也对，困难样本能对一半。总分也许差不多，但实际选择完全不同。你应该把样本按任务类型、难度、输入长度、是否需要工具、是否涉及权限、是否需要长链推理来分层。这样你才能知道，哪些任务可以放心下放给 Haiku，哪些任务 Sonnet 够用，哪些任务必须 Opus，哪些任务一旦 Opus 失败就需要 Fable，甚至需要人类介入。

对软件工程师和 AI 从业者来说，这篇文章最直接的启发，是把模型选择从拍脑袋变成一个持续系统。不是今天开会说我们以后都用某某模型，而是建立一套模型路由和评测机制。比如在一个企业内部 AI 平台里，你可以把任务先分成几类。实时面向用户的轻任务，优先考虑 Sonnet 或 Haiku。复杂但量不大的内部知识工作，优先考虑 Opus。探索性 agent 和特别困难的代码任务，用 Fable 测上限。受访问限制或安全要求特殊的任务，再根据组织权限判断 Mythos 或 Fable 是否可用。然后每隔一段时间用固定评测集重新跑一遍，因为模型版本、价格和业务需求都会变。

还有一个很实用的工作方法，是先定义质量门槛，再谈成本优化。很多团队一开始就问哪个模型最便宜，这会把讨论带偏。更好的问题是，这个任务最低可接受质量是什么。比如法律摘要错误率必须非常低，宁可慢一点贵一点。营销文案草稿可以允许人工改，模型只要给出可用初稿就行。日志分类错一点问题不大，但延迟必须低。不同任务的质量门槛不同，失败代价不同，模型选择自然不同。Anthropic 在文中说，如果 Opus 已经清过质量门槛，它的速度和价格可能更好；如果 Opus 仍然吃力，那就上 Fable。这背后就是质量门槛优先的思路。

再说一个常见误区，很多团队会把模型失败完全归因于模型本身。文章前面提到，从强模型开始可以帮助区分模型失败和 setup failure，也就是设置失败。这个提醒非常值钱。实际项目里，模型表现差，常常不是模型弱，而是 prompt 没说清楚，工具返回格式混乱，检索结果噪声太大，上下文塞了太多无关内容，或者系统没有给模型验证自己答案的机会。强模型不是万能，但它可以帮你先验证系统上限。如果最强模型都做不好，可能任务定义、数据质量、工具链或者评测标准本身有问题。如果最强模型能做好，小模型做不好，那才更像是模型能力差异。

对于多 agent 系统，Sonnet 的定位也值得注意。文章专门提到 Sonnet 适合高容量的 sub-agents，这其实是在暗示一种架构趋势：未来不一定是一个超级模型从头到尾包办所有事情，而是多个模型承担不同角色。一个主控 agent 负责拆解任务，若干 worker 负责执行，advisor 负责审查，某些高风险节点升级到更强模型。这样的架构听起来复杂，但它的好处是成本可控、延迟可控、能力可组合。你可以把它看成软件系统里的微服务思想，只不过服务之间流动的是自然语言、工具调用和中间推理结果。

当然，多模型架构也不是越复杂越好。如果你的任务很简单，一个模型一次调用就能稳定完成，那就不要为了架构优雅搞一堆 agent。每增加一个模型角色，就增加了提示词维护、上下文传递、错误传播和可观测性成本。Anthropic 的文章没有鼓励大家无脑复杂化，它只是给了 advisor strategy 这个在性能和成本之间更优的组合方式。工程上要做的是，用评测证明复杂性是值得的。如果 Sonnet 单独跑已经达标，那就没有必要引入 Fable advisor。如果 Sonnet 单独跑差一点，但加 advisor 后接近 Fable 全程效果，同时成本明显下降，那才是好架构。

落地时还要关注延迟。顾问策略虽然能省钱，但可能增加调用轮次。如果用户在前台等待，worker 先计划、advisor 再审核、worker 再执行、advisor 再评估，体验可能变慢。你可以把它放到后台任务、异步工作流、代码修复、文档生成、批处理分析这些场景里。对于实时对话，可以只在高风险或低置信度时升级。比如模型检测到用户问题涉及退款承诺、医疗法律建议、生产事故操作，才调用更强模型或人工审核。这里同样是我的工程推演，核心仍然来自文章的原则：更强模型在需要时提供指导和评估，而不是每一步都亲自执行。

数据和权限方面也不要忽视。文章提到 Mythos 只在 Project Glasswing 下开放，Mythos 和 Fable 又涉及有限数据保留要求。这提醒我们，模型选型要和安全、合规、采购、平台治理一起看。很多时候，工程师觉得某个模型最合适，但组织未必允许把某类数据发过去。你需要提前和安全团队确认数据分类、日志保留、访问权限、审计要求。否则评测做完了，上线前发现不能用，所有结果都要重来。

如果把这篇文章浓缩成一个实践流程，我会这样做。先用最强的普遍可用模型和合适的 effort level 跑通任务，确认这件事理论上能做好。然后构建来自生产的评测集，里面要包含普通样本和困难样本。接着把候选模型按类别和 effort level 做矩阵实验，记录质量、延迟、每任务成本和失败类型。再根据业务约束选择默认模型，并设计升级策略。简单任务走低成本路径，复杂任务走强模型路径，边界任务让 advisor 检查。上线后继续收集失败样本，把它们回流到评测集里。这样你的模型选择不是一次性决策，而是一个随着业务和模型更新不断进化的系统。

文章最后的结论很朴素：AI 模型选择没有 one-size-fits-all，也就是没有一种适合所有情况的方案。这也是为什么 Anthropic 提供多个模型类别。最终，最好的选择方式，是理解每个模型类别的基础定位，并且深入理解自己的使用场景。这意味着你要构建、维护和部署强评测。注意这里有三个动词，构建、维护、部署。评测不是写一次就完了。业务变了，模型变了，用户行为变了，失败模式也会变。评测集如果不维护，很快就会和真实生产脱节。

我个人认为，这篇文章最有价值的地方，不是告诉你 Sonnet 适合什么、Opus 适合什么、Fable 多强，而是把模型选型的心智从模型排行榜拉回到任务经济学。真正的问题不是哪个模型最强，而是哪个模型在你的任务上，以可接受的延迟和成本，稳定达到你的质量门槛。更进一步，答案也不一定是单个模型，而可能是模型组合，是 worker 加 advisor，是强模型定上限、低成本模型跑规模，是评测驱动的动态路由。

如果你正在公司里推动 AI 应用，我建议你听完这期之后，先不要急着换模型。先问三个问题。你的关键任务有没有真实评测集。你现在看的成本是每 token 价格，还是每任务总成本。你有没有把失败样本分清楚，是模型能力问题，还是检索、工具、prompt、权限和流程问题。把这三个问题搞清楚，再去比较 Mythos、Fable、Opus、Sonnet、Haiku，决策质量会高很多。

总结一下，Anthropic 这篇文章给出的默认建议是，先聪明地开始，从最强的普遍可用模型建立上限，再用 effort level 和较低类别模型优化成本与速度。模型家族的差别主要不在行业，而在能可靠承载的问题难度，以及对应的价格和延迟。真正成熟的团队，会用标准 benchmark 看方向，用生产自定义评测做决策，并在必要时用 advisor strategy 把强模型的判断力和低成本模型的执行效率组合起来。这就是我认为这篇短文背后最值得带走的工程方法。
