- 为什么“一个主智能体加技能”通常比“每领域一个子智能体”更省、更快、效果更好
- 把 UI 组件做成工具调用，而不是让模型输出自定义标签
- 延迟要打两场仗：真延迟靠减少回合，感知延迟靠流式渲染和显示进度

## Script

欢迎回到 Claude FM，我是你的主播。今天要聊的这篇，是 Anthropic 官方博客在二〇二六年九月二日发的，距离今天只隔了四天，可以说还热乎着。文章英文标题是 A guide to the anatomy of effective commerce agents，我把它翻译成《高效商务智能体解剖指南》。这里的 commerce 不只是狭义的电商，还包括旅游、票务、电信套餐，凡是让线上买卖变得更简单的智能体，都算。

这篇文章为什么值得你专门花二十几分钟听？因为它不是那种讲概念、画大饼的文章，而是 Anthropic 团队在过去一年里，跟零售、电商平台、旅行、娱乐、电信这些行业里的工程团队一起，真刀真枪把 agent 推到生产环境之后，总结出来的经验。文章里有一句很朴素的话：这些跑得好的商业智能体，长得都非常像。它们没有复杂的路由分发，没有几十个子机器人，就是一个 Claude 模型跑在一个标准的 agent 循环里，配上一组技能、一堆工具，以及一套足够强的评估体系。如果你正在做 agent 相关的项目，尤其是面向消费者的 agent，这篇文章里说的取舍、踩过的坑，会很直接地影响你怎么设计下一个版本。我们今天的任务，就是把这篇英文技术博客里最要紧的内容，用中文拆开讲透。

先花一两分钟交代背景。过去一年里，Anthropic 和很多大型企业合作，帮他们用 Claude 构建面向电商场景的智能体。这些智能体，一类是服务消费者的，帮用户搜索商品、比价、处理退换货、规划行程、改手机套餐、挑座位；另一类是服务商家的，帮运营人员看销售数据、搞促销、管库存和定价。企业的反馈是，用了这些 agent 之后，购物车金额变大了，商家的运营效率也提高了。这说明 agent 在真实交易里不是玩具，它确实在产生商业价值。

文章开头先纠正了一个常见的思维惯性。你一听就知道，这事很有共鸣。电商是一个覆盖面特别广的场景，品类多、用户意图杂，从“帮我找一双下雨天穿的鞋”到“为什么我这个月话费这么高”，全都有可能。很多团队的第一反应是：我要按领域拆，搞一个售前咨询 agent，一个售后服务 agent，一个订单管理 agent，每个 agent 各管一摊。用术语说，就是前面放一个意图路由器，先把用户的话分成几类，然后再路由给后面一堆不同领域的子智能体。文章说，这种做法听起来合理，但实践证明它非常不划算，甚至是有害的，因为一次电商对话，往往是一个跨了多个意图和多个来回的、强耦合的会话，需要共享大量的上下文。

我给你讲具体一点，你马上就能感受到问题在哪。假设一个用户说，我上周买的那双鞋不合适，想退掉，再帮我看看有没有其他颜色的能换。这短短一句话，同时牵扯到订单历史、当前购物车和商品目录。如果你把每个领域拆成一个子智能体，那么退货流程需要知道订单历史，推荐换货需要看当前购物车，查询替代品又需要查商品目录。那这些数据应该放在哪？要么你想办法在每个子智能体里都塞一份重复的访问权限，要么你就得在任务进行到一半的时候，把上下文从一个子智能体切换到另一个子智能体。但每一次切换背后，都是一次有损的状态交接。

什么叫有损？你想象一下场景：编排器把购物车、用户偏好、五个来回的对话历史都攒在自己手里，然后它把一个子任务丢给了子智能体，传递的方式是重新拼一段提示词，把这个子智能体需要知道的信息尽量写进去。可是语言这个东西永远无法无损压缩。用户在第一轮随口提了一句，我住的地方没有电梯，到了第三轮，你可能就需要这个信息来决定配送方式，但传到子智能体那边的时候，这句话大概率已经被丢掉了。子智能体给出的回答，自然也就没那么准。更现实的是，每次交接都很费钱。文章原话是，一次交接可能消耗数倍的 token，还额外增加好几秒延迟。如果你这个子智能体之间还需要来回协作，那就更糟，因为每多一次交换，对话质量就磨损一次。作者甚至给了一个非常锐利的判断：子智能体架构里，编排器握着全部上下文，而每一次交给子智能体的任务，本质上都是一次状态压缩，压缩就会失真。所以多个电商团队做出来的对比结果出奇一致：一个主 agent 加一组技能，在质量上稳定地超过了两个极端方案，一个极端是把所有指令全塞进一条提示词里，另一个极端就是拆成一大堆子智能体。而且结果往往是单 agent 方案每任务成本还更低、延迟还更短。作者特别提醒说，随着模型越来越强、上下文越来越长，技能和工具越来越多，以前那些逼着你拆分规则的硬限制，每一代模型更新都在松动。也就是说，你今年套着子智能体架构勉强跑通的事，明年直接塞到主上下文里可能反而又快又好。

不过，文章也不是全盘否定子 agent，它给了两个例外场景。第一个例外，是当这个子任务足够独立、足够封闭，适合拥有自己的专属上下文时，子 agent 可以作为工具被主 agent 调用。最典型的就是深度研究型子 agent。你让它去查大量的文档、数据、历史记录，它自己搜、自己碰壁、自己重试，整个过程都在它自己的上下文窗口里完成，最后只需要把一个压缩好的结论交回给主 agent。这种情况下，状态大量集中在子 agent 内部，主 agent 不需要参与每一步，就很划算。第二个例外，更值得关注，是领域交接。比如说你是一个银行应用，金融客服本来就是一个独立的合规部门，有一套自己的 agent，有专门的审计面。那你就不要用子 agent 去委托，而是直接把这个用户、这个任务整体交接给那个领域的 agent，由它接管对话，直接跟用户一起走完后续流程。这背后的本质区别是：到底谁拥有这段对话。如果只是委托，主 agent 仍然是用户的对话对象，领域 agent 在一轮交互里进进出出，每次进出都在磨损质量。如果是交接，领域 agent 变成了用户面对的那个对象，它自己跑自己的循环，直到任务完成，这才是对的模式。作者用了一个很有画面感的说法：判断标准就是看对话的主权归谁。

聊完架构宏观选择之后，我们深入一层，看看指令到底应该放在哪。文章说，系统提示词里放的东西，和技能里放的东西，最核心的区分标准是频率。因为加载一个技能要额外消耗模型一个回合，所以如果一个指令在绝大部分对话里都会用到，你就把它放进系统提示词，让它永远在那里；如果它只在一部分场景里需要，就做成技能，让 agent 在需要的时候再加载。多少算高频？作者给了一个可执行的启动阈值：无论是你预判的，还是你在生产日志里观察到的，只要某个指令跟三分之一的流量相关，就该放进系统提示词。剩下的长尾功能统统做成技能。如果某个技能是你能提前预测到的，比如说用户是从某个特定页面点进来的，那个页面的特征信息已经能告诉你他需要什么技能，那你就干脆在第一次模型调用之前，从外部框架直接把技能内容注入进去，连加载技能那个额外的回合都省掉。这里还有个铁律，任何关键的安全规则、法律限制、品牌红线、用户重要事实，比如用户对坚果过敏，都必须放在系统提示词里，而不是技能里，因为它是跨越所有对话的硬约束，不能赌模型哪次忘了加载。

文章给了两组实际的技能划分例子，我念出来你感受一下它的粒度。面向消费者的购物 agent，系统提示词里只装这几样核心东西：数据的 grounding 原则，也就是怎么把回答锚定在真实数据上、购物车和结账的语义、以及呈现规则。真正的业务能力全部拆成技能，技能包括搜索发现、购买研究、规划目标、客户关怀、记忆与个性化。面向商家的 agent 也是同样的切法，它的技能是业绩洞察、商品上架、库存运营、定价促销、营销活动。每一个技能对应一块运营域。你会注意到，它并没有把“退货”单独拆成一个 agent，而是把退货相关的能力放进了客户关怀这个技能里，因为退货需要跟购物车、订单历史、商品目录协作，它不应该也没办法独立于主 agent。

聊完了指令的存放，下一个话题是工具设计。文章说，工具设计的一般方法论他们另有一篇文章专门讲，但在电商场景里，有两点最重要。第一点，agent 的工具要构建在你现有的核心系统之上，而不是去重造一个副本。这是什么意思？你想想，一个成熟的电商公司，早就有了搜索和排序系统、购物车、用户画像库、库存系统、促销引擎、销售分析后台。这些系统里沉淀了几年的业务逻辑，每天还在接收着模型永远看不到的真实信号。所以当 agent 需要搜索商品的时候，它不应该自己去解析文本然后从数据库里翻东西，它应该调用你们的 search_products 接口，而且结果返回回来的时候，已经是排好序的。模型要做的判断不是怎么排序，而是这批结果里哪些真正符合用户目标，应该展示多少条，以及怎么组合给用户。一句话，工具边界就是业务系统逻辑结束、模型判断开始的地方。你要是让工具替模型做判断，或者让模型替工具做逻辑，都会出事。

第二点，工具结果就是上下文。这句话反过来读就是，你返回给模型的每一个字段，都在占用宝贵的上下文窗口，模型都会不可避免地注意到它，而不是忽略它。所以工具返回结果时，只保留模型做推理真正需要的字段，其他一律扔掉。文章点名了一个最常见的反面典型：搜索结果的每一行，都带着一堆图片 URL。图片 URL 对模型理解商品毫无帮助，却能把上下文撑爆，还干扰注意力。工具内部还要做一件很实用的事：当返回结果本身不足以让模型知道下一步该干嘛的时候，直接在工具结果里补一句建议性的下一步指引。尤其要处理错误场景，给模型读得懂的操作指引，而不是一个冷冰冰的 403 错误码。作者给了一个生动的例子：与其返回一个通用错误代码，不如在工具结果里直接写“查询库存时请带上产品 ID”，模型就知道下一步该怎么改。这种小细节往往就是 agent 显得聪明还是笨的分水岭。

接下来这部分我要重点讲，因为它可能是全文里最给人启发的设计模式：把 UI 组件做成工具。你回想一下，一个电商 agent 的回答，绝大多数时候不是一段散文，而是一块用户界面。它可能是商品轮播卡片、一个行程单、一个座位图、一个对比表格、一个价格趋势图。这意味着，模型的输出格式不是文本，而是一个结构化的 schema。很多团队一开始会怎么做呢？他们会用提示词教模型输出自定义标签，比如尖括号加 product_carousel 之类的，然后在客户端写一个解析器去解析它。这个思路在 demo 阶段感觉没什么问题，但随着界面越来越复杂，它会迅速瓦解。原因有三条。

第一条，模型看过大量工具调用示例，但它没怎么见过你发明的那个自定义标签。你只靠提示词，没法保证模型每次输出都是格式良好、结构正确的内容。嵌套组件一多，可靠性崩得特别快。第二条，标签定义写在系统提示词里，每加一个新组件，系统提示词就膨胀一点，每改一次标签，都要担心影响提示词里别的地方。这等于所有 UI schema 的变更都耦合在同一个提示词文件上。第三条很隐蔽，也最致命。过去对话被存成了只有你的解析器才能读懂的格式，下次要重新加载历史对话，你不得不在客户端做一层反向解析，或者在服务器同时存两份数据，一份给模型 API 读，一份给 UI 解析器用。这太别扭了。

那正确的模式是什么？文章说，把每一个 UI 组件定义成一个工具。模型不再输出文本标签，而是直接调用一个叫 present_products 的工具，或者 present_itinerary，或者 present_plan_comparison。调用的参数是类型化的、有结构的。你的服务端收到这个工具调用后，做校验，做数据补充，发出一个渲染事件，客户端收到事件就把它渲染出来。这个模式有好几个好处。工具调用是模型 API 的原生格式，它们会自然地出现在消息数组里。所以当你重载一个老对话时，所有 UI 组件都还在那里，不用做任何额外的解析。对前端来说，它真正意义上实现了客户端和模型之间的解耦。你甚至可以检查模型最近一次调用了哪个展示工具，它的参数是什么，来知道你屏幕上此刻到底显示了什么。当用户说“我要第一家酒店”，或者“左边数第三个”，模型查一下上一次展示调用的参数，就能立刻知道屏幕上确实有哪几家酒店。当然，这要求展示类工具的参数顺序跟 UI 实际渲染顺序是一一对应的，比如第一行第一列是谁，第二行是谁，不能返回一个无序列表然后让前端客户端自己去重排，否则模型对屏幕的理解就跟用户看到的对不上。

这种展示工具也有一个代价，就是流式传输的颗粒度。因为每个工具的参数在服务端需要做缓冲和校验，所以即使用户开着流式传输，一个复杂页面组件也是分块到位的。要解决这个问题，文章给了一个很具体的配置，给工具定义一个属性叫 eager input streaming，把它设成 true，这样模型产出的内容可以跳过服务端缓冲，直接流向客户端，每一层参数都能以更细的颗粒度逐步到达，看起来响应就快得多。当然它的代价是你放弃了服务端完整 schema 校验的保证。文章说，在现在 Claude Sonnet 这个级别及以上的模型上，schema 违规其实很罕见，但为了保险起见，还是要在外层包一个重试，万一真出现一个格式错误的调用就自动再试一次。

到这里，我相信你已经能感到，这篇文章讲的很多东西都不是模型层的东西，而是工程层的东西。但真正让电商 agent 变得难做的，是延迟和成本。这一节我建议所有做 To C agent 的听众都竖起耳朵。

文章先说了一个反直觉的结论：延迟在电商里当然重要，消费者对延迟的容忍度是最低的，但对于 agent 这种新的交互形态，真正推动用户留存、参与度、购物车金额的，不是延迟降了多少毫秒，而是任务完成的质量。答案是相关的吗？任务真的完成了吗？这两件事对商业指标的影响，远远大于边际的延迟优化。所以作者建议，延迟要打两场仗：第一场，通过好的工程把端到端延迟压下来；第二场，降低用户感知到的延迟，因为用户看着 agent 一步步工作，这个“正在做事”的过程本身就会被他解读为进展。

要做到端到端延迟的最优，先要理解延迟从哪来。一个任务从开始到结束，总延迟等于所有模型回合的延迟之和，每个回合又等于模型输出最后一个 token 的时间，加上工具处理的时间。这么一拆，你就得到了三个可以下手的杠杆：减少回合数，加快工具处理，加快 token 生成。这三个杠杆有时候互相打架，比如一个更聪明的模型单个 token 可能更慢，但它能大幅减少回合数，所以你要最小化的矛是总和，而不是任何单一指标。

怎么减少回合数？文章给了几个经过验证的招。第一招，尽量把可能需要的上下文提前加载进来。如果用户是从某个商品页面点开助手的，或者商家是从某个促销看板点进来的，你就应该提前把那个页面的数据放进会话上下文里，因为接下来的对话大概率会围绕这个页面展开，模型直接从上下文里找答案，就不用再额外发起一轮工具调用去查了。第二招，提高模型智能水平。这个看着像废话，但背后的权衡很关键。在很多复杂任务里，更强的模型因为规划更高效、工具调用更准确，总回合数反而更少。哪怕它单个 token 慢一点，总时间依然可能更短。所以如果你们的请求偏向复杂，或者生产数据里单任务平均超过五个回合，那很可能应该选更聪明的模型，而不是选响应最快的模型。

第三招很实用，让模型并行调用彼此独立的工具。一次典型任务往往需要同时做好几件事，比如一次搜多个商品，或者一次查很多份政策文档，不同销售数据源之间的组合。如果你的 API 支持并行工具调用，一定要用起来，这样多个独立的查询就不用一个接一个地排队消耗回合数。你可以在提示词里明确告诉模型，同一轮里把多个独立工具调用都发出来，工具结果以一个数组的形式返回。第四招，优化工具自己的后端。作者观察到一个很有意思的流行病：很多时候工具边界成了业务逻辑的缝合点。比如一个查库存的工具，返回之前在自己代码里先查了商品目录，拿到 SKU，又跑到库存服务逐店查库存，再查履约服务的截止时间，再把缺货替换规则和门店自提资格全都硬编码在工具里处理一遍，最后才拼出一个答案。这个工具已经超载了，它里面塞满了随时变化的领域知识。正确的做法是，如果一个问题本质上问的是“这个商品在我的门店当前可不可以自提”，那你就应该去后端写一个专门的端点来回答这个问题，agent 的工具只需要瘦瘦地调用它就行。所以当你在工具内部写着写着发现自己开始堆业务规则时，你就该警觉：这些逻辑可能应该回到上游的系统里。第五招，也是比较进阶的招，叫 eager tool dispatch，积极主动地分发工具调用。平常模型生成工具调用的时候，参数是跟着 token 流逐步出来的，你会等整个工具调用都生成完了再去执行。但其实你可以做到每个参数一完整就立刻去执行这个调用，与此同时模型还在继续生成其他内容。文章说他们用这个办法把原本好几秒的间隙压缩到了几百毫秒，而且 Claude 的 Agent SDK 已经默认这么做了。为了最大化效果，你还可以在提示词里建议，如果同时有好几个工具要调用，尽量把最慢的那个放在第一个，因为它能更早被执行。

第二场仗是感知延迟，也就是用户盯着屏幕，要等多久才能看到变化。一个电商回复的 UI 通常要生成五百到七百个输出 token，如果不做流式，用户会对着一个 spinner，也就是转圈图标，等五秒以上。这给人的感受，比实际延迟要糟糕得多。两个改善手段，第一个就是把上面的展示组件流式化，每个参数一生成完就立刻推给客户端，让页面逐渐渲染成形。第二个手段很有意思，叫展示你的工作过程。当 agent 正在后台获取各种上下文的时候，前端可以用通俗的语言把每一步渲染成一行进度提示，比如“正在查找靠近水边的酒店”。这一行字可以直接从工具调用的参数里提取，也可以额外给工具加一个 user_facing_message 参数，专门让模型写一句给用户看的进度说明。这些体验上的小机制，没有增加任何模型智能，却能让用户感觉系统反应快了很多。

成本这块，文章给了一组很具体的数据。提示词缓存，是电商 agent 降低成本的最大机会。读缓存里的内容比读全新的输入便宜十倍，写缓存的成本虽然稍微贵一点，大概一点二五倍，但只要同一个前缀被第二次使用，这笔投资就回本了。在面向消费者的大流量应用里，你有一个独特的机会去达到极高的缓存命中率。Anthropic 说他们见过最好的电商部署，缓存命中率做到了百分之九十到百分之九十九，你要从一开始就按这个水平去设计。除了便宜，缓存还有一个额外好处，在大约十万 token 的上下文规模下，读缓存会比普通读取快一点五到两倍，而且 token 越多，这个优势越明显。

缓存是按前缀匹配的，一个请求只能命中缓存到跟上次请求头一个不同字节出现的位置。所以重要的不只是上下文里有什么，还有它的排列顺序。文章把一次请求想成三个按变化频率排列的段。最前面是全局段，就是系统提示词的大部分和工具定义，它们在所有会话之间都是一样的，这是最热的一段缓存，在足够大的流量下几乎永远不会过期。中间是会话段，包含每个用户自己的上下文和对话历史，不同用户之间不一样，但同一个用户在同一个会话内是稳定的。最后是易变段，任何会在会话内变化的东西，比如当前时间、当前浏览页面，统统放在请求的最末尾，可以放在最新一条用户消息里做一个标记块。这里文章点了一个很多人会踩的大坑。最常见的缓存杀手，就是有人把时间戳或者当前页面放在系统提示词的顶部，这样每次请求的前几个字节都变了，整个缓存每次都静悄悄地被打破。如果你所在的公司已经上了 prompt caching，你现在就可以去检查一下你们的系统提示词开头，如果有动态内容，这就是白花花的银子在流走。

另外，技能应该作为工具结果加载，而不是直接追加到系统提示词里。为什么要这样？因为 append 到系统提示词的内容，等于修改了全局缓存段的前缀，会让缓存失效。但技能作为工具结果返回时，它落在对话历史区，而这个区域本身也是缓存的一部分，于是技能内容也能跟着被缓存。缓存断点还需要每轮向前滚动，因为一个请求允许的断点数量有限。做法是在每一轮新的用户消息后面放最新断点，这样整个累计的对话历史，包括长工具结果，就都能从缓存里被读出来。

模型选择这一节，也给了一个非常清晰的流程。文章说模型大小和努力等级，本质上是同一个权衡，用智力和延迟成本做交换，而且你应该通过测量来决定，不要凭感觉。第一步，定好你的业务指标，那评估得分是你不能跌破的底线，同时明确 p50 和 p99 的延迟预算以及成本预算。第二步，做横扫式对比，把你全部评测集在每一个候选模型和每一个努力等级上都跑一遍。文章建议的起点是，面对商家侧的 task 和 analytical agent 任务更重，可以从 Opus 开始试；面对消费者的 agent，延迟分量更重，可以从 Sonnet 开始试。如果你已经有生产流量，就用真实查询分布给结果加权，然后让数字自己说话。第三步，解读结果时要细心。有两个现象最容易让团队意外。第一个是提示词往往绑定了某个模型风格。你在 Sonnet 上调出来的提示词，直接拿给 Opus 跑，效果不一定好，因为更大的模型可能严格按字面执行你在 Sonnet 上写的那套冗长指令，而这未必是正确的行为。所以不要跑一遍就枪毙某个模型，针对每个模型各自失败的案例做几轮迭代再下结论。第二个现象是，更聪明的配置有时候在延迟上也赢，尤其是 p90 和 p99 这种长尾延迟。虽然它的单 token 更慢，但它能把工具调用规划得更好，在最复杂的请求上需要的回合数更少。最后还要提醒，成本要按每个完成任务的成本来算，而不是每次模型调用的成本。一个更便宜的模型如果需要更多轮次、更多重试，总成本反而更高。当两个配置在指标上非常接近，而成本也在预算范围内的时候，果断选更聪明的那个，因为质量才是驱动用户采用和留存的关键，它也为未来半年模型继续进步留下了空间。

讲完架构、延迟和成本，文章进入第三大部分，讲一个 agent 要真正过生产关需要什么。我们一个个来。

先是记忆。你可能会问，聊天里用户提过的事情，模型不都记得吗？这种记忆只是对话窗口里的短期记忆。文章讨论的是长期记忆，就是要跨会话生存的用户事实。你六月份说过你对坚果过敏，八月份再来的话，这个 agent 不应该让你再说一遍。但你也不能指望模型自己记住这些，因为模型的参数是冻结的。记忆属于你的系统，而不是模型内部。

一个长期记忆系统有三个部分：事实怎么存，怎么写入，怎么读出来。先说存储。当用户画像很小、只有 agent 自己读的时候，一个简单的 markdown 文件就够了。但生产环境的电商 agent 很快会超出这个规模，最实际的答案是使用你本来就在跑的数据库。一条记忆就是一条小的类型化记录，包含一个关键名，比如 shoe_size，default_store，一个短值，一个分类，以及它来自哪个会话。有些关键名是你预先定义好的，所有用户都会有；其余的是抽取器从对话里自己发现的。把记忆放到数据库里而不是思维里，好处是当积累越来越大时，依然可以查询，可以对特定属性做确定性的行为，还能跟你已有的用户数据表做关联。

对商家侧的 agent，记忆还要注意按人来分，而不是按账号分。因为商家的登录账号往往是共用的，一个店的经理和区域经理可能登的是同一个后台账号，如果你把记忆挂在账号上，那么一个人说的话会被另一个人看到。所以每个操作员要有自己的独立记忆，而且读取的时候要尊重这个操作员的权限，区域经理说过的话，店员的 agent 不应该想起来。电商记忆里存放的往往是个人数据，而最值得记住的，往往恰恰是监管最严格的那部分数据。作者提醒，你要像设计一个数据处理系统一样，从写入路径开始就在验证器里强制限定，当前愿意保存哪几种类型的记忆，而不是只在提示词里劝模型不要记。用户要有办法查看、更正、删除已存的内容，删除操作要接入账号删除和数据请求的流程。还要设保留期限，一条几年前的偏好很可能已经过时了。另外，记忆组件应该做成按部署可开关的，这样那些法规上无法承担这些义务的地区，就可以直接跑不带记忆的版本。

写入记忆应该异步进行。每轮对话结束之后，或者在一个长会话里每隔几轮，用一个单独的线程或进程，把整段对话重新读一遍，然后决定创建、更新或删除哪些记忆，这样用户那一轮的延迟完全不受影响。Anthropic 在他们内部的电商记忆评测集上，这个异步方案命中率比对照组高了百分之十三。那为什么不干脆做一个工具，让模型自己保存呢？这也是大多数人的第一反应。但作者认为这是错误方案，理由很清晰。每次保存都是一次工具调用，而在用户可见的回合里，每次额外的工具调用都在增加延迟。更麻烦的是，除非你把整个记忆存储都塞在上下文里，否则模型要保存一条记忆，得先读一遍相关旧记录去判断要不要更新、要不要去重，这又是一整轮工具调用。每个回合都把“要不要保存记忆”这个决策压在模型身上，等于多了一个抢占注意力的任务，而注意力是有限的，它在评测里会表现为记忆丢失。

读取记忆分三层。第一层是显式读取，某些固定事实，比如用户过敏原、名字、默认收货地址，直接放进系统提示词，每次都在那儿。第二层是相关内容检索，只在可能相关时才做语义搜索，所以记忆工具要在执行搜索前先判断相关性。第三层是深层情境化，默认保持折叠状态，但当用户提了一个可能跟很久以前某次互动相关的问题时，它才被展开。这种三层设计，每一层只取当下该有的东西。这样平均每个会话只增加几千 token，远好过把所有个人记忆一次性倒在上下文里。文章用了一个我很喜欢的说法，叫以省略取胜。记忆准则也要在真实数据上和评测上反复调，一层可能给多，一层可能给少。

好，接下来是安全。这大概是全文里最严肃的部分。作者说了一段话我特别认同：提示词是安全行为的起点，但不应该成为安全执行的终点。在电商领域，安全失败是真实的金钱损失，而且经常是不可逆的。一条提示词离被注入攻击绕过，只差一个坏样本的距离。所以下面每一条规则都必须在代码层面强制执行，消费者侧和商家侧共享同一套定义。

第一条也是最核心的原则：没有任何一个模型工具调用可以直接动钱或改变业务。下订单、支付、退款、改价格、发营销活动，这些动作的终点都必须是一个由外层框架控制的行为，而不是模型直接执行的行为。在消费者这边，这个原则是结构性的，结账工具只负责把购物车渲染出来，真正的下单按钮出现在界面上由用户去点。模型所对应的后端接口，根本不存在扣款方法。在商家那边，规则同样是结构性的，但多一步审批。所有写操作工具产生的都是一个暂存变更，带一个由服务器生成的 ID，然后 apply_change 这个最终执行工具，只接受那些已经通过真人操作界面审批过的 ID。比如运营人员在门户里点了一个批准按钮，或者在命令行里进行了确认，或者在 Claude 的托管 agent 平台里通过了工具审批。审查时要用当前最新状态里的限额重新检查，不能采用暂存变更那一刻的旧限额。不管在哪个表面，模式都一样：模型能做的最危险的事是提出变更建议，真正的执行审批权，必须经过你公司里本来就存在的四眼原则流程。对金融行业来说，这个模式你太熟了。

第二条是 ID 白名单，这个设计我在别的 agent 框架里很少看到，它把安全和正确性同时兼顾了。外层框架会为每个会话维护一个记录，记下服务器曾经给这个模型发放过哪些 ID。之后任何写操作或渲染操作，只接受这些记录里存在的 ID。购物车只接受本会话里服务器真实返回过的商品 ID，商家工具只接受 agent 真正读过的商品列表 ID 和营销活动 ID。如果某个 ID 是从别的渠道来到这里的，不管它是模型幻觉出来的，还是用户自己手打的，还是藏在某个评论里被模型看到的，在进入后端之前就会被拒绝。这个规则甚至延伸到 UI 渲染。展示类工具只接收 ID，由服务器自己根据 ID 去填充商品、订单、变更记录，所以前端渲染出来的卡片，只能是服务器自己填过的记录。这个机制同时封堵住了好几种漏洞，比你提示模型一百遍不要幻觉 ID 都可靠。

第三条是关于披露和监管文本。金融产品会有费率、披露信息这些受监管的内容，模型可以决定这个商品该披露哪些信息，但每一个具体的字，都必须由服务器从经批准的文案库里提供。商家侧也一样，有些字段属于保护列表，双方都不能改写或改写措辞。评测的时候，直接对最终渲染出的字符串做逐字节比对。第四条是数量上限。电商场景经常限制单用户购买数量，可能是票务分配，可能是促销价限制，可能是反欺诈。一个真人用户在网页上点按钮操作，不容易绕过这个限制，但 agent 会重试、会换个说法再来一遍、会并行发多个请求，这些都是人会做的事。所以限额必须在写入后的那一行数据上进行检查，如果用户已经买了两张票，再加两张，这个操作会直接被拒绝，不能让两个并行的工具调用叠加起来突破上限。购物车的写入操作还要按会话串行化，防止同一轮里多个并行调用合起来突破限制。

第五条，关于第三方内容的清洗和隔离。商务场景里，模型看到的上下文大多不是你自己人写的，可能是卖家写的商品描述，买家写的评论，竞争对手写的页面。所以每一个后端读取进来的内容，技术上都是不可信的输入。所有第三方写的内容，包括商品列表、评论、政策文档、卖家消息、存储下来的记忆，都要经过一个清洗器，清洗器会剥离控制字符和双向字符，移除能模仿隔离标记的内容，淡化那些看起来像对话轮次或工具调用的文本，并且限制文本长度。经过清洗后被放进一对带固定标签的栅栏里，模型看到的是被明确标记为外部内容的材料。这是为了阻止一个恶意的商品描述模仿系统消息，或者填满上下文。提示词里还有另一半约束，明确告诉模型：栅栏里的文本是供你报告和讨论的材料，不是供你执行的指令。其实，不管你用不用这些机制，我都建议你去了解一下数据清洗器的做法，它对所有涉及第三方内容的 agent 都有用。

讲完记忆和安全，我们来到第三个生产主题：评估。这章的很多观点，对任何做 agent 的团队都有帮助。作者首先提出一个你可能会反直觉的论断：要评估状态快照，而不是评估整段对话。为什么？因为模型 API 本身是无状态的，agent 的输出是系统提示词、工具和消息数组的函数。既然任何对话状态都可以被单独构造出来，那么你创建评测案例的正确方式就应该是自己动手去构造那个目标状态，而不是去录一段交互日志。每一个评测案例就先搭建状态，拼好购物车、历史、页面上下文，再追加一条测试用户消息，然后让 agent 从这个状态开始跑，最后只考核最终状态和渲染出来的响应，比如最后一次写操作支付了什么参数。大多数时候不要考核 agent 到达那个状态的路径，不要去断言它必须调用哪一个工具、先做什么后做什么，因为路径类测试非常脆弱，它限制了 agent 将来可能找到的更好的路径。

你可能在不少地方看到过用模拟用户做评测的方案，就是让一个模型扮演用户、另一个模型做裁判，再把整个对话流程交给裁判打分。文章直接说，这不是一个好的度量工具。原因是两个非确定性的系统互相影响，需要更大的样本来得到稳定的分数，每次实验成本更高，裁判更难公正地评判，而且一旦失败，你很难说清失败到底该归因于被评测 agent 还是模拟用户。那模拟用户还有用吗？有，它适合用来发现覆盖盲区，适合在整体上感受一下 agent 的 vibe，但发现的新场景最终要转写成状态快照类的单次测试，纳入正式评测集。

还有一个很常见的失误也很值得指出：很多团队没有认真构造初始状态。他们写了一个案例，模拟一个需要好几轮复杂历史后才会出现的失败，却从全空的状态开始跑。结果当然是通过，评测变成了一堆漂亮的绿色图标，无法提供任何信息。如果某一种行为只有在第一轮忙乱的多次工具调用之后才会发生，或者只有在对话早期出现矛盾之后才会浮现，那你的测试案例就要把这些前置状态完整编码进去。要确保你的评测集里有一部分是从长的、混乱的、甚至自相矛盾的上下文开始跑的，而不是全从干净状态起步。另外，评估既要测理想行为，也要测非理想行为。每一个应该拒绝的案例，都应该配一个应该服务的正面案例；每一个应该先问用户确认的案例，都应该配一个应该直接执行的案例。作者说缺少这种负面对照，是他们审查合作伙伴评测集时最常见的问题。这两句话值得写在你测试策略文档的第一页。

文章具体列举了电商 agent 应该评测的几类能力。比如说，占流量大头的基础请求，包括简单查询、多约束请求、产品计划问题、混合意图语句。凡是涉及价格、库存、属性的回答，都要能回溯到工具返回的数据，数据缺失时 agent 要说“我不知道”，而不是自己编一个看起来合理的数字。再比如上下文相关请求，也就是指屏幕上的内容、延续前几轮提到的约束、对已存在购物车的操作，这一部分其实也承担了对记忆功能的评测：记忆有没有被提取、能否被检索、是否真的影响了回答。还有安全类和品牌类案例，因为这种失败损失的是钱或者信任，包括被注入攻击、尝试访问其他用户的数据、受监管的措辞，后者要逐字逐句检查。注入测试要分两种，一种是由用户消息发起的注入，另一种是数据面注入，也就是恶意指令藏在商品名、评价或网页摘要里，随着工具返回进入上下文。你一定得把这两种分开测，因为它们走的是完全不同的攻击路径。可视化界面类测试则要检查是否正确渲染了组件、有没有遵守数量上限、用户可见文字里有没有透出内部标识符，超时和空结果也不要放过。

这节里还有一个非常精彩的思维实验，我来转述一下，它充分说明了为什么按能力拆分的评测可能漏掉真正重要的问题。假设一个商家运营人员问：如果我给这个商品降价百分之十五，我的库存够不够应付这波需求？你仔细品一下，这个问题同时跨了定价和库存两个领域。正确的答案应该是一边建立起降价变更暂存，一边附上库存预测；错的答案往往是只处理了其中一半。如果评测集是按能力分开组织的，定价组只测定价部分，库存组只测库存部分，那这个案例就永远不可能被发现有问题，因为每一组只考了自己的那一半。正确的做法是，专门为那些需要两个相邻能力共同协作的请求写交叉案例，并且对输出的两半都要打分。这种问题，我觉得是当前 agent 评测设计里最需要被听到的洞见之一。

评测案例从哪来？文章建议别自己闭门造车，而是跟那些每天亲眼看到故障的产品、法务、商家运营、客服、商品类目管理同事合作，把真实故障变成评测案例。真实世界发生的失败是最有价值的评测数据源。每个用户流程准备五十到一百个评测案例比较合适。生产环境的真实对话记录也是非常好的新案例来源，尤其是那些让 agent 翻车的对话。如果你在做编码 agent，你还可以让代码 agent 根据这些失败来批量生成额外的困难变体。文章提到，他们开放的参考代码仓库里带了一个 Claude Code 插件，内置了用这套方法论构建的评测编写技能，感兴趣的同学可以去看一下。

再往后，文章讨论了一个工程管理层面的问题：在一个大型电商企业里，agent 从来不是一个人或一个团队能独立完成的，搜索团队、结账团队、定价团队、营销技术团队、客服团队、商品平台团队，每个团队都拥有 agent 依赖的系统，各自按自己的节奏发布，而每个团队都会想往 agent 里塞自己关心的工具、技能或规则。这就冲突了。普通服务的模块边界还能保护彼此，而 agent 没有这种边界。价格团队改的一段工具描述，跟结账团队的代码共享同一个上下文窗口，这算谁的回归？

最诱人的解决方案是退回子 agent 架构，一个业务部门一个 agent。但第一部分已经论证过这个方案在质量上不划算。那怎么办？文章给了一套过程上的建议，如果你想引入这种机制，可以按这个思路设计。首先，所有权跟着系统走。每个技能和工具都要有单一的责任团队。价格团队拥有促销工具和定价技能，客服团队拥有订单工具、退货工具和客户关怀技能。共享提示词要有一个平台级负责人来管理公共部分，同时有领域负责人来管理领域专属部分。其次，任何变更必须附带测试用例，CI 里跑一个精选集。比如一个团队要改技能，必须把自己的正反案例以及相邻技能的边界案例一起提交。完整评测集如果每次 pull request 都跑，又慢又贵，基本上跑不下去，所以你要构建一个分层 CI 集。最核心的一层，是流量最高请求对应的用例，外加所有安全用例，这一层每次变动都跑。第二层，凡是你这次改动碰过的东西，把相关用例带上。改技能就加它自己的案例和邻居边界，改工具就加所有会调用它的案例，改共享提示词，那没得商量，跑全量评测集，因为所有请求都会读系统提示词。门禁不要只看单次通过率，要看多次试验中的通过率，同时还要看缓存命中率有没有下降，每轮平均成本有没有飙升。全量评测集每晚跑一次，每次重大发布前也跑一次。跨团队的回归问题，就是在这些每日运行里被逮住的。最后，agent 本身也必须放进发布日历。它是单一部署单元，一次坏变更会同时影响到每一个用户。所以提示词和技能变更要先上金丝雀小流量，要有一个不用发版就能单独关掉某个技能的开关，大促高峰之前要像冻结其他系统一样把 agent 也冻结。这套流程的本质是承认一个事实：agent 就像一个永远在更新的核心系统，它的质量必须被持续监控，而不是发布完就没人管了。

好，我们把这篇长文的内容梳理完了。最后谈一下它对我们的实际工作到底意味着什么。这也是我想花几分钟具体推演一下的部分。

假如你所在团队正在构建一个消费者向的客服或者导购 agent，而且你们现在正好用了某种意图路由加多个子 agent 的架构。文章给的最重要的信息就是：不要急着再加一个子 agent，试试把每个域的能力都变成一个技能，技能主体作为知识放在工具结果里，让主 agent 带着全量上下文自己判断何时加载。你大可以挑一个故障最多的场景做一次对比测试，比如把两个方案都跑在一百个历史困难会话上，你有可能看到子代理架构那一侧的每任务成本高出一大截，而你需要的知识都收缩成若干个按需加载的技能文件，这很值得一试。

再具体到缓存和上下文。如果你重新组织提示词，你可以直接照文章的三段式来。全局段放系统提示词和工具定义，中间放会话历史，最后放当前时间这种易变信息。检查一下技能有没有被错误地直接塞进系统提示词，而当前上下文有没有真的把同一个前缀维持住。如果你们的缓存命中率低于百分之九十，这个检查就可以定位问题。很多团队可能忘了：一个开头就动态生成的时间戳会无声地杀掉缓存，甚至都不报错。这种修复不需要动模型，只是把易变字段挪到最末尾，成本却能立刻降下来。

还有一个重要的建议，虽然聊的是 AI agent，但相当部分的护栏其实跟 AI 无关。你可以把你现在系统的业务规则写下来：谁可以改价、改价要走什么审批、修改后要校验什么总量上限。然后把它们明确地外层代码化，而不是写进提示词。你完全可以设计成所有更改都先生成暂存的变更记录，再经由你的人事审批流去批准，模型本身不掌握 apply 的权力。你的支付系统也可以在设计时就让模型接触不到扣款接口。这些工程措施即便哪一天模型换成了别的模型，也依然在保护你。

评测方面我也有一个印象很深的提醒。不要把所有评测案例都在干净状态上跑，要有意构造那些混乱的、长历史的、自相矛盾的上下文，也别只写正面案例，所有“应该拒绝”“应该先问”“应该直接做”的行为，都要配上对应反例。新增一个能力时，至少带十个案例：五个正例，五个负例，再加两个跨邻接能力的综合案例。每个案例要包含预置状态、用户输入、期望的最终状态。同一类交叉能力缺陷，很有可能经常出现。

最后说一个实践坑，就是延迟不能只盯着 p50。我建议把 p99 拉出来看。如果你们对模型做了一次横扫测试，要把完整 eval 套件在候选模型上都跑一遍，但记得给每个模型几轮迭代提示词。更聪明的配置在复杂请求上可能规划更短路径，p99 反而更低。不要因为首 token 慢就排除它，这是文章反复强调的。

文章最后还有一段关于方向的话让我印象很深。作者说，这套架构能用到比聊天界面更长远的未来。你现在跑起来的评估集和工具，未来可以支撑语音交互，可以让 agent 主动行动，比如说在用户开口之前就处理票价下降。再过几年，一部分逛你店铺的流量将来自替用户代购的其他 agent。到那时候，真正决定你能不能安全向它们开放工具的，正是你现在已经在用的那套溯源、暂存、审批规则。所以，现在把销售流程变成一个 agent 能用的核心系统，长期一定值得。

我个人听完这篇文章，最大的感受可以总结成一句话：做好 agent，本质上是把你的业务系统变成一个可以被人和模型共同操作的操作系统。很多人以为，agent 就是用一个很聪明的模型，把它扔到一个空对话框里就完了。这篇指南却告诉我们：真正的护城河是在模型外面。工具层要调用你们打磨多年的核心系统，技能层要编码你们多年沉淀的业务流程，评估集就是你们把产品需求文档翻译成了可执行测试，而 harness，也就是模型的执行框架，是在替你执行本来就应该由你来执行的策略。模型本身当然会越来越强，但当更强大的模型发布的时刻，这套 shell 依然可以继续服务，只改一个模型配置，跑一遍完整评估集，就能把最新模型接入你的业务。这正是我期望中下一代数据基础架构的形态。

这期节目到这里差不多就该收尾了。今天这篇来自 Anthropic 官方博客的文章，用四个字概括就是：少即是多。一个主智能体带着一组技能，用业务自己的系统做工具，用状态快照加正反例做评测，用暂存审批做安全，用异步抽取加三层检索做记忆，把商业规则的确定性跟模型推理的灵活性尽量解耦。这套组合听起来朴素，却是在大量生产级 commerce agent 中被反复验证过的。希望这一期内容能给你的 agent 架构设计带来新的抓手。你可以在评论区告诉我，你对哪一块体会最深，比如子 agent 和技能之争，还是异步写记忆的三层读取。如果这期对你有帮助，欢迎分享给你身边正在做 agent 的工程师朋友。我们下期再见。
