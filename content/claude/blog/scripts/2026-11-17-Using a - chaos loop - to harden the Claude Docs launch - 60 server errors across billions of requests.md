## Script

今天这期节目，我们聊一篇来自 Anthropic 官方博客的工程文章。英文原标题是 Using a chaos loop to harden the Claude Docs launch: 60 server errors across billions of requests。中文我把它翻译成《用混沌循环加固 Claude Docs 的发布：数十亿次请求里只出现六十个服务器错误》。文章发表于二〇二六年十一月十七日，距离今天十一月二十二日只过去了五天，是非常新鲜的一手工程复盘。

我之所以想第一时间讲这篇，是因为它一口气给出了好几个让人停下来想一想的数字。他们的文档产品 Claude Docs 在九月十六日上线，到九月二十二日，用户创建了四百六十多万份文档。这期间二十亿次请求里只出现了六十个服务器错误。九月份他们往生产环境推了六百二十九次，一次都没有回滚。整套服务只跑在大约五十个内存优化过的 pod 上，pod 你可以理解成 Kubernetes 里的一个运行单元。

还有一个数字更值得琢磨。作者说从八月底到发布日，他大概用掉了价值十二万五千美元的模型推理。同样规模的工作放在几年前，他估计要一个工程师团队干六个月。也就是说这篇文章表面讲的是稳定性，实际上在讲一件更大的事：一个工程师，带着一个能长时间自己跑循环的 AI，能不能把过去一个团队半年的活干完。

如果你在通勤路上听，我建议你把这篇当成一份操作手册来听，而不是一个炫技故事。因为文章后半段作者非常实在地给了一套小团队可以照抄的流程，还把成本从十二万五千美元折算到了三千到一万美元这个量级。好，我们从头讲起。

Claude Docs 是什么？简单说它是一个文档编辑器，但这个文档不是你一个人写，也不是只跟同事协作，而是你、你的队友、还有 Claude，三方在同一个文档里一起干活。最有意思的地方在于，任何一个地方的 Claude 会话，不管是你平时聊天用的窗口，还是在 Claude Code 里写代码的那个会话，都可以打开同一份文档，在你旁边实时地读、写、评论。

你可以想象一个场景：你在写一份技术方案，左边同事在改架构图，右边 Claude 在同一个文档里帮你补上接口说明，而且它引用的是你刚改过的那一版。这种多人加多智能体共享同一份可变状态的产品，工程难度非常高。因为它不是一问一答，它是一条长连接、一个共享的文档状态、一堆并发写入，再加上实时同步。

这里要交代一个关键背景。发布前三周，这个服务还只是一个跑在单节点上的概念验证，Anthropic 内部几千人在用。团队在冲一个很激进的发布日期，而他们自己的估算是，上线头几天就会有数百万份文档。也就是说，从单机几千人到几天几百万文档，中间隔着好几个数量级。问题是跨度这么大，你根本没法用真实流量去验证，因为你没有发布流量可测。几千个内部用户跑在一台机器上，对"这个服务能不能扛住发布"这个问题，什么信息都没提供。这是所有做基础设施的人最熟悉的困境：上线之前你永远不知道你准备好了没有，上线之后你只有一次机会。

传统做法是什么？写压测脚本，造一些流量，看监控，拍脑袋估个容量，然后灰度发布，一边放量一边救火。这套方法的问题在于，压测脚本只能覆盖你想得到的失败模式，而真正打垮你的往往是你没想到的那种组合。另一种做法是混沌工程，也就是主动往系统里注入故障，这是 Netflix 那套思路。但传统混沌工程有个前提，注入什么故障、看到什么指标算异常、怎么修，这些都要人来设计。这篇文章的核心主张其实就一句话：把这几个环节全部交给 Claude，让它自己选场景、自己跑、自己读遥测、自己修、自己验证，然后连续跑两个星期不停。这就是标题里的混沌循环。

作者的做法非常朴素。他没有搭一个复杂平台，而是直接在 Claude Code 里开了一个会话，让这个会话一直挂着跑。循环的内容是：挑一个场景，跑测试夹具，读遥测，提出修复方案，部署到预发环境，然后再来一遍。这个会话扮演协调者的角色，大部分具体工作交给子代理去做。最忙的那一周，通常同时有十一个子代理在跑，峰值到过三十个。

还有一招我觉得特别聪明。这个协调者还通过 Slack 的 MCP 去跟 Anthropic 内部另一个工具沟通，那个工具叫 Claude Tag，当时还是 beta。它干的事是去问其他做过类似规模服务的基础设施团队，你们踩过什么坑，然后那些团队的 agent 会来检查我们的扩展方案，看有没有他们当年撞过的墙。你品一下这个结构：一个 AI 协调者，手下三十个 AI 干活，还能横向去问别的团队的 AI 你们当年怎么翻车的。这已经不是单点自动化了，这是一个有组织记忆的自动化团队。

那它具体挑了哪些场景呢？作者的原话是"我觉得偏执的场景"。我念几个给你听。一天之内创建一千万份新文档。两万两千个活跃连接在同一瞬间重连。一份热点文档前面挂着几百个查看者，同时把一台正在加载这份文档的服务器杀掉，再让数据库卡住。这几个场景的精妙之处在于，它们不是单纯的高并发，而是组合故障。热点文档加服务器被杀加数据库卡住，这三件事单独发生都不致命，但同时发生，就会逼出你架构里最脏的那部分假设。

每次迭代的流程是一样的。测试夹具选中一个功能，比如文档创建，把它压到饱和。然后 Claude 通过 Datadog 的 MCP 去读遥测数据，回来后给你一个很短的选项菜单，外加一个明确的推荐。这里有个细节值得强调。如果这个推荐是容易撤销的，Claude 就自己写代码、自己部署到预发、自己重跑测试，全程不用叫人。

他们给服务的每一个操作都加了遥测。举个具体例子，每一个数据库查询都会上报自己的名字，还有它扫描了多少行、返回了多少行。这样 Claude 就能一眼看出，这个查询扫了一百万行只返回三行，这是个坏查询，然后它自己重写。你看，这就是可读性的第一层含义：不是给人看的仪表盘，而是给模型看的、结构化的、带因果线索的信号。人看仪表盘看的是曲线，模型需要的是这个数字对应哪一行代码。

但作者没有让 Claude 完全放飞。他事先划了一条线，哪些决策必须经过他批准。基本上就是所有难以撤销的事情，比如改数据库的 schema，也就是表结构，比如改 key 的布局，比如改文档的存储和物化方式。Claude 一旦撞上这些就会停下来问他，而且通常带着一个推荐方案。作者说他最后基本都批了。他说 schema 变更是最典型的必须咨询的场景，因为这类问题通常有好几个都合理的答案，而一旦选了方向，掉头非常痛苦。

这条经验我觉得特别值得记下来。不是要不要人类审批，而是审批的边界画在哪。画在不可逆这条线上，而不是画在重要不重要这条线上。重要但可逆的事，让模型自己试错，成本很低。不重要但不可逆的事，也得停下来问一句。这个判断标准是可操作的。

除了审批边界，作者还给 Claude 定了两条不变量。不变量这个词在工程里指的是无论在什么情况下都必须成立的条件。第一条，文档必须几乎瞬间打开，哪怕这份文档有很长的历史。第二条，一旦服务器确认了一次编辑，测试必须证明这次编辑还在。这两条非常关键。因为在一个自动循环里，模型很容易为了修好 A 而悄悄弄坏 B。你把打开要快和确认的编辑不能丢写成硬约束，模型每一轮都得同时满足，它就不能拿正确性去换性能，也不能拿性能去换正确性。

接下来讲这篇文章我觉得最有价值的部分，就是海拔这个概念。作者的同事 Felix Rieseberg 写过一篇教程，讲怎么对模型更贪心一点。核心观点是提高你给 Claude 下指令的海拔，你要的是结果，不是一个个具体任务。举个例子，低海拔的指令是帮我修一下这个崩溃，高海拔的指令是让我的应用不再崩溃。这两句话听起来只是措辞差别，但对 agent 的行为影响是根本性的。前者你每崩一次就要说一遍，你是瓶颈；后者模型自己去找崩溃、自己复现、自己修、自己验证。

但作者提醒了一句很实在的话：想在这个海拔上工作，你得先把代码布置好，让 Claude 能自己去拉崩溃报告，能跑一个夹具去复现每一个崩溃，还能验证修复有没有效。也就是说高海拔不是靠一句咒语实现的，是靠你把可观测性和测试能力提前建好。对他们来说，那个结果就是一个能扛住发布的服务。为了到达这个结果，他们做了两件事，让服务对 Claude 尽可能可读。第一件叫诊断循环，每一轮迭代 Claude 读完遥测之后会自己判断我还缺什么信号，然后把缺的遥测加上。这里有个反差很有意思。作者说手写遥测是很枯燥的活，所以现实里大部分遥测都是等东西坏了以后才补上的。现在 Claude 边干边写，它需要什么就自己加什么。第二件叫可读的技术选型，这一条我们下面展开讲，因为它是整篇文章里最具争议也最值得讨论的工程决策。

先讲内存那个例子，因为它把可读性这三个字讲透了。测试跑起来没多久，他们发现有一份大文档在它的 pod 上占了大约三个 G 的内存。作者的原话是，这不是一个让人看了开心的数字。Claude 的第一次修复尝试是把我们自己的某个缓存缩小，让服务器更早地把文档驱逐出去。听起来很合理对吧？结果下一轮测试显示，内存其实长在某个依赖库内部的另一个缓存里，不在他们自己的缓存里。于是 Claude 撤回了这个改动。

然后它继续用越来越细粒度的内存剖析往下挖。最后发现每一次按键都会把整份文档复制到好几个不同的数据结构里，每次复制加几兆内存。Claude 把这些结构改成了写时复制，也就是 copy-on-write，让它们共享同一份引用，而不是各拿各的副本。大约三天迭代之后，那份文档的内存峰值降到了一百八十兆左右。更重要的连锁反应是对发布所需容量的估算，从五百多个内存优化 pod 直接降到了大约五十个。

你算一下这个账。五百个 pod 降到五十个，这是十倍的容量节省。而且这个修复不是靠人读代码读出来的，是靠遥测给出干净信号，模型顺着信号一路追到根因追出来的。这里我想停一下，说说我自己的看法。这个案例真正值钱的地方不是省了多少钱，而是它展示了一种新的调试范式。传统调试是人在脑子里建模型，模型不准就靠经验猜。这里的调试是模型在数据里建模型，每一轮都用真实的测量结果去证伪。人在这里的角色变成了设定边界和审批不可逆的改动。

好，现在讲那个争议决策，为什么用 Rust。作者说得很直白，他们对服务的运行时和依赖非常挑剔，原因是他们的模型在信号干净的时候爬坡爬得最好。爬坡这个词你可以理解成逐步逼近最优解。他们预期垃圾回收器会引入噪声，因为内存和延迟会随着回收器自己的节奏抖动。你想想看，如果 Claude 看到一个内存尖峰，但这个尖峰其实是垃圾回收器按自己的时间表触发的，那它就会去修一个根本不存在的问题，或者更糟，把好好的代码改坏。所以两个选择帮助最大。

第一个，服务用 Rust 写。Rust 没有垃圾回收器，一份文档占的所有内存都躺在他们自己定义的数据结构里。所以内存涨了，Claude 可以精确指出是哪个结构在涨，改掉它，下一轮看内存有没有降下来。这是一个完美的闭环，假设、改动、测量、确认，四步都在同一套可观测的因果链上。作者也承认，Anthropic 内部有很好的 Go 工具链，他们没有做 Rust 和 Go 的对比评测，所以这只是他们在 Rust 上的经验。作为一个写过多年代码的人，他说从 Go 转过来，最让他舒服的是代码用完之后内存还在不在这件事，几乎不用他操心。

第二点，依赖降到最低。每一个引入的库都会带来一堆你没写过、也没法轻易解释的数据结构。对少数真正需要的库，他们把源码直接内嵌进项目里，也就是 vendoring，这样他们能自己读、自己测。然后是那句我觉得会被人反复引用的话：Rust 对人来说很难写，几年前这一点会严重影响技术选型，但 Claude 写 Rust 和写其他语言一样好，所以这一点现在没那么重要了。

这句话背后其实藏着一个很大的判断转向。过去我们选技术栈，一个很重要的考量是团队好不好上手、招人好不好招、出问题好不好排查。现在这三个问题的答案正在被改写。如果写代码的主要是模型，好不好写这个维度的权重就下降了，而好不好测量这个维度的权重就上升了。这就是这篇文章最反直觉的地方。它不是教你怎么让 AI 适应你的技术栈，而是反过来，为了让 AI 能有效工作，主动去选一个对 AI 更透明的技术栈。

我要提醒一句，这里有个前提别忽略。文章说得很清楚，这套东西能成，是因为他们的前沿模型最近强了很多。作者用的是一个内部研究模型，大致相当于 Claude Fable 五点二。他们的经验是这类模型现在能在一个目标上坚持好几周。这句话是整个案例的地基。如果没有能坚持几周不跑偏这个能力，前面所有的循环设计都是空中楼阁。因为一个循环跑到第十轮就忘了自己在优化什么，那它就是在原地打转。

作者把这个现象起了个名字叫目标漂移，goal drift。他说几个月前这套大概率跑不通。老模型读 MCP 遥测没问题，但长循环跑到十轮二十轮，它们就开始忘记优化目标是什么，作者就得反复重述。而新的前沿模型在跨过很多次上下文压缩之后，还能守住所有不变量，他一次都没重复过。上下文压缩这个词解释一下，就是对话太长超出窗口时，系统会把历史压缩成摘要。压缩是有损的，不变量能不能扛过压缩，是长时 agent 能不能用的关键测试。

现在我们看结果。服务在发布规模下撑住了。第一百万份文档在大约三十小时内出现，到九月二十二日超过四百六十万份，九月份生产发布六百二十九次零回滚。作者说发布那一周有一种奇怪的熟悉感。因为 Claude 非常擅长想象一个服务能怎么挂，发布之前就把大部分失败模式规划过了。他们在预发环境上排练过的十个场景，有七个真的在生产环境发生了。而那时候测试夹具早就让预发把大部分场景跑过一遍，Claude 也早就把修复放在运行时开关后面了。所以当基础设施的某一部分真的开始吃紧，他们通常只是翻一个开关。他还提到不只他们这么干，Vercel 用一套非常类似的、有人监督的 agent 循环，把 Turborepo 提速了最多百分之九十六。

然后是成本，这部分我觉得最有诚意，因为作者把账算得很细，连自己浪费的钱都写了。按 Claude Fable 五点二的 API 标价，也就是二〇二六年十一月的价格，从八月底到发布日，他大概用掉了十二万五千美元的推理。他说同样规模的工作放在几年前估计要一个工程师团队干六个月。这些钱主要花在读遥测、写提案、生成修复、审查代码上。但他主动补了两条。第一，他们这次发布特别大，很大一部分钱花在了只在那个规模下才有意义的基础设施上，而那部分基础设施本身就需要更多推理去理解。Claude 得花很多心思去想一组不断增长的服务怎么互相配合、能怎么失败。第二，他花了很多 token 在摸索流程上。循环在他调试设置的时候是不停跑的。他说以现在知道的，本来可以只花一半。

然后是那个让我眼前一亮的换算。作者说这套方法对规模小得多的服务同样适用，而且应该便宜很多。他做了个粗略估算。先给一个经典的小团队技术栈定价，几个中等大小的 Kubernetes 节点加一个 Postgres 实例。然后他把从八月底到发布日落地的所有变更过了一遍，去掉那套小栈根本用不上的工作，包括跟其他内部服务对接的部分、跟规模工作混在一起的客户端和产品工作、跨很多 pod 运行的部分、细粒度限流的部分。剩下大约三分之一的变更。把花费按三分之一缩放，再扣掉他摸索流程时犯的错，他的估计是同样两周的冲刺，按同样的标价，大概三千到一万美元。

他自己也标明了，这个数他没真跑过，只是个粗略感觉。但我觉得这个数量级是可信的。三千到一万美元，两周，换一个经过混沌测试、知道自己在多少倍流量下会怎么挂的服务。对一个准备大促或者准备发布的中小团队来说，这个投入产出比是很难拒绝的。我个人认为，这个换算比前面那十二万五千美元更有传播价值。因为十二万五千会让人觉得这是大厂游戏，而三千到一万会让一个五人团队认真考虑我们下周是不是也可以试一下。

好，接下来是这篇文章最实操的部分。作者给了一套步骤，前提是一个工程师，加上 Claude Code，加上一个预发环境，加上一个可观测性服务商。他先说了一句很体贴的话：协调者和子代理能加速流程，但如果你发现它们每小时烧的 token 太多，退回单代理也能跑得不错。这句话很重要，它把门槛从你得有三十个 agent 降到了你有一个 agent 就行。

第一步，给 Claude 访问遥测的权限。现在大多数可观测性服务商都有 MCP 服务，Claude 可以直接接上去读。第二步，让 Claude 写一个负载脚本，往预发的副本上打十倍于真实流量的压力，并且故意搞破坏。作者给了三个很好的起点：杀掉一个实例、让数据库卡住、在流量尖峰中间做一次部署。然后就让它不停修那些倒下的东西。第三步，选技术栈的时候倾向于 Claude 最容易测量的那个。对他们来说是 Rust 加尽可能少的依赖。这句话不是让你无脑上 Rust，而是让你在几个候选方案里优先选那个数字能追溯到你自己代码的方案。第四步，开始之前把你最重要的技术不变量写下来交给 Claude。注意是写下来，不是口头说。因为不变量要能扛过几十轮迭代和很多次上下文压缩。第五步，对任何难以撤销的操作，让 Claude 停下来，给你几个选项加一个明确推荐。

这五步我想再展开讲一下，因为直接照抄容易踩坑。关于第一步，很多人会以为给 Claude 一个监控面板的链接就够了。不是的。文章里 Claude 之所以能追到根因，是因为遥测是结构化的、带名字的、能对应到具体代码和具体查询的。如果你的遥测只有一条 CPU 使用率的曲线，那 Claude 看到尖峰也只能猜。所以你在接入之前最好先问自己一句：我现在的指标，能不能回答这个数字是哪一行代码产生的？如果答案是不能，那先补这个，再谈自动化。

关于第二步，十倍流量这个数字我觉得是个很好的默认值。太低测不出问题，太高你会被一堆跟真实场景无关的瓶颈淹没，然后花两周去优化一个上线后一年都碰不到的东西。而故意搞破坏这三个动作也选得很准。杀实例测的是你的故障转移，卡数据库测的是你的超时和降级，尖峰中部署测的是你的滚动更新和状态一致性。这三个基本上是所有线上事故的高频母题。

关于第三步，我要给一个反向的提醒。文章里用 Rust，一个很重要的原因是他们的团队本身就有这个能力，作者自己也写 Rust。如果你团队里没人看得懂 Rust，而 Claude 改出来的代码没人能审，那你其实是在拿可维护性换可测量性，这个交易不一定划算。我的建议是优先选你的团队能审、同时模型能测的交集，而不是盲目追随文章里的具体语言。

关于第四步，不变量这件事我想多讲两句。文章里那两条不变量，一条是文档必须几乎瞬间打开，一条是确认过的编辑不能丢。你注意这两条的共同点，它们都是可以用测试自动验证的。这是写不变量的关键。如果你写系统要稳定，那不是不变量，那是愿望。如果你写任何一次被确认的写入在之后任意时刻读出来都必须存在，那才是不变量，因为它可以被一个测试判真假。所以你在给自己项目写不变量的时候可以套一个句式：无论发生什么，某某条件必须成立，而且我能用一个测试证明它。写不出测试的，说明还没想清楚。

关于第五步，审批边界，我想补充一个文章没明说但很重要的点。作者说他把难以撤销的决策留给人类，比如 schema 变更。但你在实践里会发现，难不难撤销这件事本身，模型和人的判断可能不一样。模型可能觉得改个索引很安全，但你知道在生产库上改索引会锁表。所以审批清单最好由人来列，而且列得具体一点。不要写重大的数据库变更，要写任何会锁表的操作、任何会改变数据保留期的操作。清单越具体，模型越不会误判。

还有一点，文章里有个细节容易被忽略。Claude 每次停下来问的时候，通常带着一个推荐。这个设计很关键。它不是把决策原封不动扔回给人，而是把分析做完了，只把拍板留给人。这样人的负担从想清楚该怎么办降到了同意还是不同意，审阅成本差了一个数量级。你自己搭类似的循环时，一定要在提示里明确要求这一点，否则模型很容易变成一个只会举手说这里有问题请你决定的机器人。

我们再把视角拉高一点，聊聊这套方法对普通工程师意味着什么。我觉得它首先改变的是准备工作的定义。过去我们说一个人要开始做一个项目，准备工作是搭环境、拉分支、写设计文档。现在多了一项，把你系统的可观测性做到模型能自己闭环的程度。这件事平时看起来像是给运维做的，但在 agent 时代，它是给模型铺的路。路铺得好，模型跑得快；路铺得烂，你雇再强的模型也是在泥地里开车。

其次，它改变了对压测的理解。传统压测的目标是我知道我的极限在哪。这套方法的目标是我让系统自己去找到极限，并且自己把极限推高。前者是一次性的动作，后者是一个持续的过程。作者让它连续跑了两周，而且是在发布前两周这个最紧张的时间窗口。这个安排本身就说明，他们不认为这是一次性的验收，而是一个持续加固的过程。

第三，它给了我们一个判断 agent 能不能用的新标准。不是看它会不会写代码，而是看它在长循环里会不会忘记目标。文章里说得很清楚，几个月前这套跑不通，原因是目标漂移。所以如果你现在想复刻，先做一个小实验：让 agent 在一个目标上跑二十轮，每轮都读遥测、提方案、改代码、验证，然后看它第二十轮还记得不记得最初的目标。如果记得，那你可以往上加码；如果不记得，那你需要的是更强的模型，或者更短更密的循环，而不是更复杂的脚手架。

我还想聊聊这套方法的边界，也就是它不擅长什么。第一，它擅长的是有明确可测量目标的加固，不擅长目标本身需要被定义的探索。文章里目标非常清楚，扛住发布，打开要快，确认的编辑不能丢，这三件事都能用数字判真假。但如果你的问题是我们这个产品下一步该做什么，那这套循环帮不上忙，因为模型没法自己判断什么叫更好。第二，它依赖一个真实的、能反映生产的预发环境。文章里预发是镜像生产的，每天超过一百万份合成文档。如果你没有一个像样的预发，那这套方法的第一步就走不通。这是很多团队的真正瓶颈，不是模型不够强，是环境不够真。第三，它默认你能承受让模型改生产路径上的代码。文章里 Claude 能直接部署到预发，还能把修复放在运行时开关后面。这需要你的发布流程足够成熟，能灰度、能回滚、能开关。如果你的发布还是手工传包，那这套流程跑不起来。第四，成本仍然不是零。十二万五千美元对一个大厂是个工程师几个月的工资，但对一个三人创业团队是笔大钱。好在作者给了三千到一万的估算，那才是大多数人该对标的数字。

好，我们差不多要收尾了。我把这篇文章的骨架再给你串一遍。它讲的是一个服务在上线前只有单机几千人的验证，却要面对几天几百万文档的流量。团队没有选择拍脑袋估容量，而是在发布前两周让 Claude 在一个镜像生产的预发上跑了一个混沌循环：自己选场景、自己压、自己读遥测、自己修、自己验证，连续跑了两周。为了让这个循环真的能闭环，他们做了两件事，一是让 Claude 自己补遥测，形成诊断循环，二是选了对模型透明的技术栈，Rust 加极少的依赖，让每一个数字都能追溯到自己的代码。他们还划了审批边界，只把不可逆的决策留给人，并且写了两条硬不变量。结果是二十亿次请求六十个错误，六百二十九次发布零回滚，容量估算从五百多个 pod 降到五十个。

我个人认为，这篇文章真正的贡献不是证明了 AI 能修 bug，而是提出了一个新的工程问题：你的系统，对模型来说可读吗？过去我们优化的是对人可读，代码要清晰、日志要好懂、文档要齐全。现在多了一个维度，对模型可读，指标要结构化、因果链要短、噪声要少。这个维度会慢慢变成技术选型的一部分，就像今天的可维护性一样。如果你这周只能做一件事，我建议你做这个：挑一个你负责的服务，问自己一句，如果我让一个 agent 盯着它的遥测跑二十轮，它能不能自己找到并修掉一个问题？如果答案是能，那你已经准备好了；如果答案是不能，那你知道下一步该补什么了。这期就到这里，我们下期见。
