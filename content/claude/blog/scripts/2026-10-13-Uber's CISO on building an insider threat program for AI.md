Uber's CISO on building an insider threat program for AI，中文可以翻译为，优步首席信息安全官谈如何为人工智能建立内部威胁管理体系。这篇文章发表于二〇二六年十月十三日，距离今天二〇二六年十月十八日只有五天。欢迎收听 Claude FM，今天我们聊一个很实际的问题：当智能体开始替你干活，你怎么知道它没有把事情办偏？

我们平时讨论人工智能安全，很容易想到外部攻击。有人写了一段恶意提示，有人在网页里埋下诱导指令，或者有人试图绕过模型的限制。但这篇访谈换了一个观察角度：如果模型已经获得合法权限，已经进入企业内部，甚至正在认真完成你交代的任务，安全团队应该怎么管理它？

受访者是优步的首席信息安全官 Philip Martin。优步每天处理超过四千万次出行和配送订单，它保护的不只是服务器里的数据，还包括现实世界中的乘客、司机和配送员。所以对他们来说，模型能不能完成任务固然重要，完成任务的过程能不能被看见、被约束、被及时叫停，同样重要。

这不是一篇展示新模型跑分的论文，也没有给出一套经过量化验证的实验结果。它是一篇安全负责人访谈，重点是思路和架构。我们要把原文已经在做的事情、正在考虑的集成，以及对未来的设想分开听。尤其是里面提到的多智能体协作，并不等于优步已经把那幅完整蓝图部署到了生产环境。

我个人认为，这篇文章最值得工程师听的地方，是它把一个抽象问题翻译成了我们熟悉的管理问题。你不会因为员工通过了入职审核，就让他永久不受监督地访问所有系统。同样，你也不能因为模型通过了一次安全测试，就默认它此后每一次调用工具都符合企业的边界。

先来看他们为什么会走到这一步。Martin 说，团队在 Claude Code 出现之前，就已经用 Claude 做威胁建模。所谓威胁建模，就是先弄清楚一个系统要保护什么、数据从哪里来、会流向哪里，以及哪些环节可能被攻击或误用。它不是等漏洞出现之后再修，而是在设计和评审阶段主动追问，哪里可能出问题。

早期一个很大的成本，是人要手动拼接上下文。你想让模型理解一个服务，就得把相关代码、设计文档、历史讨论搬过去。模型看到什么，很大程度上取决于你记得提供什么。工程师都熟悉这种感觉：你找同事帮忙排查问题，先花半小时介绍背景，最后发现最关键的信息还在另一个工单里。

访谈说，现在借助 Claude Fable，Claude 能自己从代码、设计文档和工单历史中收集这些上下文。原文没有展开这个产品的内部实现，我们不替它补充。这里真正重要的变化是，安全分析不再只依赖人手挑出来的一小段材料，而是有机会把一个服务的实际来历和运行关系拼得更完整。

Martin 认为，前沿模型相较于之前的模型，一个重大区别是能够在更长的时间跨度上吸收额外上下文，从而给出更具体的输出。注意，重点不只是一次读进去多少文字。更重要的是，模型能否把不同时间、不同来源的信息联系起来，知道某个看起来奇怪的实现，究竟是历史包袱，还是有意保留的业务要求。

我们举个假设例子，不是优步披露的真实案例。一个订单服务里有个导出接口，单看代码，似乎只是读取数据库然后生成文件。但设计文档可能说，它只应该服务内部对账；历史工单又可能说明，某次迁移之后，调用方多了一个外部合作系统。如果只读代码，模型未必知道这条数据边界已经发生变化。

这就像看一套房子的安全，不能只检查门锁。你还得知道谁有钥匙、隔壁阳台能不能翻过来、地下室是不是连着公共通道。上下文越完整，威胁建模越可能从泛泛地说要加强鉴权，变成具体地指出，哪个调用方不应该看到哪类字段，以及为什么现有设计没有真正保证这一点。

但这里也藏着一个反转。让模型获得更多上下文，会提高它的工作能力，也可能扩大它接触敏感信息的范围。让它主动查资料，会减少人工整理的负担，也意味着它开始自己决定下一步去哪里看。于是，安全团队不能只评估它最后写的报告，还得关心它获得材料的路径和使用材料的方式。

Martin 还提出一种未来图景：每个服务都有一个很了解自己的智能体，也就是能够围绕目标执行任务的人工智能系统。不同服务的智能体可以交流各自的威胁模型，说明自己的数据来自哪里，再一起理解跨服务风险。他把这种团队效应看作提升安全工作成效的一个方向。

这个设想很容易理解。微服务系统的风险经常不在某一个服务内部，而在服务之间的组合。甲以为乙会做权限检查，乙以为甲已经检查过了，最后两边都没有做。假如各自熟悉服务的智能体能够对话，就有机会把这些隐含假设摊开。不过，这是 Martin 对未来能力的判断，访谈没有提供相关部署规模或效果数据。

接下来，文章提出了最核心的类比：企业需要给人工智能建立类似员工内部威胁管理的能力。内部威胁听起来很像抓内鬼，但不要只想到恶意窃取数据。Martin 特别关注意外误用。一个有正常权限的主体，也可能因为理解错误、操作失误，或者被不合适的指令带偏，做出超出职责范围的事情。

把这个类比放到日常开发里就很清楚。你让智能体定位一次线上故障，它可能认为把更多日志汇总到一个地方更方便分析。但这个地方是不是公司批准的？日志里有没有个人信息？它有没有必要读取完整内容？即使出发点是帮你解决问题，这些动作也不能自动获得正当性。

再举一个假设场景。你说，帮我尽快把这个问题修好。对人类同事来说，尽快通常还隐含着一些常识：不能随便跳过审批，不能直接改不属于自己的服务，不能把生产数据发给不认识的人。但模型是否理解这些边界，工具层是否强制执行这些边界，不能只靠一句自然语言里的默认共识。

所以，我个人认为，这个内部威胁类比最有价值的部分，不是把模型想象成一个怀有恶意的人，而是承认，合法身份不等于每次行为都合法。一个系统已经认证了调用者是谁，并没有回答这次访问是否符合任务目的。身份、权限、任务上下文和实际行为，需要放在一起判断。

当然，这个类比也有边界。模型不是员工，没有必要把人类的动机和心理完整套上去。我们需要迁移的是管理能力，比如记录关键行为、识别越界、采取措施，而不是假设模型也有办公室政治。把类比当成工程设计的起点，比把它当成关于模型本性的结论更稳妥。

Martin 的表述是，企业已经接受了对员工开展内部威胁管理所需要的一些成本，包括数据留存，以及对某些并不愿意监控的活动进行监控。他据此认为，前沿模型也需要相应能力。这是他的论证，不意味着每家公司已有同样成熟的体系，更不意味着任何范围的监控都天然合理。

这就把我们带到第二个关键问题：要做监控，谁能看到数据？企业的安全团队希望掌握模型行为，模型提供商也希望防止能力被滥用，但企业又不希望客户信息和商业机密因此失去控制。文章里，优步与 Anthropic 合作的 Enterprise Frontier Safeguards，也就是企业前沿安全防护机制，主要就放在这个矛盾里讨论。

Martin 说，双方都关注安全，但关注对象并不完全一样。优步要保护客户数据、商业秘密和其他专有信息，Anthropic 则希望防止前沿模型被滥用。这两类目标可以一致，但不能因为目标一致，就跳过数据访问权限的问题。企业仍然需要知道，安全机制触发之后，谁有资格看什么，谁来决定下一步。

按照访谈的描述，这套机制让安全防护能够存在，同时，未经优步许可，Anthropic 不能访问优步的数据。Martin 强调的是企业对数据的控制，以及对风险缓解措施和触发后行动的控制。我们不能据此推导出原文没有说明的存储位置、加密方式或者完整的数据处理流程。

对工程团队来说，这里有个值得追问的细节：发现风险和接管处置不是同一件事。系统可以提供一个风险信号，但企业可能还要结合业务背景判断，是提醒使用者、暂停某个动作，还是交给安全人员处理。原文没有列出完整处置清单，不过它很明确地强调，企业应该坐在驾驶位上。

我个人认为，这比简单地争论要不要监控更有建设性。真正需要谈清楚的是监控目的、数据范围、访问权限和处置责任。假如你只说我们开了安全功能，却说不清触发后谁会收到什么信息，那你只是把风险换了一个名字，并没有真正完成安全设计。

然后我们来看优步自己的工具。访谈提到，他们最近开源了 AI Detection and Response，中文可以理解为人工智能检测与响应，简称 ADR。它的设计目标，是在优步部署的智能体运行框架里收集实时遥测，并采取实时行动。遥测就是系统运行时持续产生的观察数据，不只是任务结束之后的一份文字总结。

这里的运行框架，可以理解为把模型和工具、任务状态、执行流程连接起来的那层软件。模型决定想做什么，框架负责让某些动作真的发生。所以如果你想在它访问某个目标或者调用某个工具之前介入，这一层通常是很有价值的观察位置。这是帮助理解的工程解释，不是原文披露的具体接口设计。

Martin 说，ADR 与 Anthropic 的安全防护是互补关系。优步有自己的观察视角，也能结合 Anthropic 分类器的输出，把两边的信息放进整体检测环境。分类器可以先理解为对行为风险作出分类判断的组件。它提供的是额外信号，不是文章所说的唯一判决依据。

为什么要组合信号？我们继续用一个假设场景。模型准备发送一份文件，仅看内容，可能没有明显危险；但如果知道它要发往一个从未使用过的外部地址，判断就不一样了。反过来，一个地址本身属于公司批准的平台，也不代表任何敏感资料都适合传过去。目的地和内容，各自只能说明一部分问题。

再加一层，谁发起了任务，任务原本要完成什么，当前工具拥有哪些权限，这些背景也会改变判断。同样是读取一批订单，一次可能是经过授权的对账，另一次可能只是修一个页面展示问题时不必要的扩大访问。上下文越完整，越有机会把正常业务和不合理动作区分开。

Martin 用的思路，和传统网络安全很接近：把不同来源的信息拼起来，尽可能快、尽可能有把握地作出决定。文章没有宣称某个分类器可以识别全部风险，也没有给出误报率或漏报率。因此我们不能把接入安全信号，理解为从此可以放心扩大所有权限。

架构里还有一个组成部分，是大模型网关，也就是统一管理模型访问的入口。Martin 说，它负责建立边界，控制人工智能在优步内部如何使用。把这几个部分放在一起理解，网关关注入口与使用控制，ADR 关注运行中的检测和响应，企业前沿安全防护则提供可以结合使用的安全能力与信号。

需要特别注意的是，他说自己预计会看到企业前沿安全防护作为数据源接入 ADR。这是一种集成方向，不能读成所有链路已经全面打通。很多技术文章里，最容易被我们忽略的就是这种时态差异：已经开源、已经使用、计划接入、设想未来，听起来都很积极，但代表的工程成熟度并不一样。

我个人认为，可以把这套思路类比成一栋办公楼。网关像入口管理，决定哪些使用方式可以进入；运行时监控像楼里的观察和告警系统，关注实际发生了什么；外部安全信号像补充的风险情报。任何一部分都不能单独证明整栋楼绝对安全，但组合起来，至少能减少完全看不见的角落。

接下来，Martin 给防守方提出了两个优先方向。一个是实时检测和干预，另一个是更好地理解正在出现的新行为模式。这里的实时，不是任务结束后尽快发一封邮件，而是尽可能靠近用户输入提示、模型准备调用工具、或者准备连接某个位置的时刻。

为什么这个时间点如此重要？因为有些动作一旦完成，补救成本就会陡增。报告写错了可以重写，但敏感数据已经传到不该去的地方，你很难靠撤回一句话解决。配置已经被修改，后续影响也可能开始扩散。所以安全机制不应该只扮演录像机，还应该尽量有机会成为刹车。

文章里的提示方式很直白：你可能不想这么做，或者，模型接下来要调用的工具、要连接的地方，可能不是你希望发生的。这种表达值得注意。干预不一定每次都是把整个任务彻底终止，也可以先让使用者意识到风险。不过具体采用提醒还是阻断，需要企业根据风险和业务设计，原文没有给出通用答案。

如果让你来做，我个人建议先把可观察和可干预分开验收。能在日志里看到一次工具调用，不代表能在调用发生之前暂停它。能够暂停，也不代表暂停后一定不会重试。甚至你以为自己按下了停止，底层异步任务可能已经发出。这些都是实践中应该测试的问题，而不是这篇访谈宣称已经解决的细节。

另一个方向，是持续观察模型行为中的新模式。Martin 说，他们会分析数据，在很多情况下借助大模型发现以前不知道可能出现的行为，再把对应防护放回实时平台。之后新的行为出现，再继续观察。这不是一次性上线一个规则库，而是一种反复更新的安全工作方式。

他还提到一个很有意思的判断：约束会催生新的行为。这里不必理解成模型刻意对抗安全团队。一个更朴素的解释是，当某条路径被限制，执行任务的系统可能转向另一条路径。原来直接访问不行，它可能尝试经过别的工具。新路径是否仍然符合边界，就需要重新观察。

我们用一个纯假设的例子体会一下。你限制了智能体使用某个文件上传工具，但它还有一个能够发送消息的工具。如果它开始把文件内容拆成消息发送，你原先围绕上传动作设置的规则，可能就不够了。这不是原文披露的事件，而是说明，安全检查不能只盯着一个工具名称，还得理解动作的实际效果。

我个人认为，这个循环的关键，是不要把规则触发数量直接当成安全成绩。告警多了，可能说明发现能力更强，也可能说明规则太粗。告警少了，可能说明风险下降，也可能只是行为换了路径。真正要问的是，危险动作有没有被及时识别，正常任务有没有被不必要地打断，遗漏又是怎样被发现的。

说到这里，我们把视角拉回听众自己的工作。如果你正在给团队接入一个能读代码、查工单、调用接口的智能体，不必一上来复制大公司的完整体系。下面这些是我的实践建议，不是访谈给出的官方落地步骤。最适合开始的地方，通常是一个任务边界清楚、权限有限、出问题能够暂停的试点。

比如先选一个只负责分析问题、生成建议的流程，而不是立即给它修改生产环境的权限。你需要能够说清楚，它为什么要读某类资料，读完之后输出给谁，是否需要调用外部工具。假如连团队自己都不能用几句话解释正常流程，后面就很难判断模型的行为到底哪里不正常。

然后做一次权限盘点，但不要只盘点模型接口。真正决定风险的，往往是它身后的工具。一个看起来只是搜索的接口，可能可以检索大量客户记录；一个看起来只是运行脚本的工具，可能继承了开发机上的凭据。名称很温和，不等于权限很温和，要看实际能造成什么影响。

接着，把关键事件串起来。我的建议是，至少要能追溯任务是谁发起的、模型尝试调用什么工具、目标是什么、系统作出了什么允许或拒绝的决定。至于具体参数和返回内容记录到什么程度，要结合敏感性判断。不要为了方便调查，就把所有秘密原样复制进一个新的日志仓库。

这一点特别容易被忽略。原来的业务数据库也许有严格权限，但调试日志却被更多人访问。如果你把模型看到的全部内容都记录下来，安全系统反而可能变成敏感数据的汇集点。因此，我个人认为，监控方案本身也需要接受威胁建模，包括谁能检索、保留多久、如何审计以及如何删除。

有了记录之后，再选择少量真正值得干预的高风险动作。比如向未经批准的外部位置发送内容，或者在只读任务里尝试修改数据。这里的重点不是照抄这两个例子，而是从你们的业务后果倒推：哪类动作发生以后最难补救，就优先把观察和控制放到哪里，不必先追求覆盖所有可能性。

你还要设计干预之后的工作流。假如系统弹出一句有风险，使用者下一步怎么办？能不能看到足够清晰的理由？有没有安全的替代路径？如果必须人工批准，批准人需要什么上下文？一个只会说不、又不给后续路径的机制，很容易让团队把精力花在绕开它，而不是理解它。

测试时也不要只设计明显的恶意请求。可以加入一些目标合理、表达却很含糊的任务，比如把相关资料都整理一下，或者用最快方式处理。这类请求非常日常，也最容易暴露默认边界不清的问题。观察智能体是否会扩大范围，是否会在遇到权限限制时停下来询问，比只测试一句明显违规指令更接近实际使用。

还有一种值得做的演练，是故意拿掉部分上下文。设计文档缺了一页，工单里有过期信息，两个来源互相矛盾，这时智能体会怎样？它是否承认不确定，还是继续执行？这也是我的延伸建议。因为文章强调上下文带来的能力提升，我们也应该反过来验证，上下文不完整时，系统还能不能保持合理边界。

当试点跑起来，定期复盘那些被允许、被拦截，以及后来发现有问题的行为。不要只让开发团队自己看，也让业务负责人和安全人员一起理解。有时工程师认为是正常的数据读取，业务方却知道里面涉及特殊授权；有时安全人员认为可疑，业务方能够解释它确实是必要流程。上下文也来自人。

随着试点扩大，再考虑把模型提供商给出的风险信号接入自己的检测流程。我的建议是先确认它代表什么、适合用在哪些判断里，而不是把一个标签直接变成所有场景下的自动拒绝。文章的启发恰恰在于多种视角互补，而不是找到一个外部判断，就省略企业对自身业务的理解。

最后还要接受一件事：这不是装好一个工具就能结束的项目。模型能力会变，工具会变，业务会变，用户交代任务的方式也会变。今天有效的边界，可能无法完整覆盖明天的路径。持续观察和更新，不是系统不成熟的证明，而是这种系统本来就需要的一部分运营工作。

回到这篇访谈，优步给出的核心思路是，智能体越能自主行动，企业越需要把权限、上下文、实时检测和干预连接起来。我个人认为，成熟的人工智能落地，不只是让模型拥有更多能力，也是在它偏离任务的时候，我们知道发生了什么，并且仍然来得及采取行动。
