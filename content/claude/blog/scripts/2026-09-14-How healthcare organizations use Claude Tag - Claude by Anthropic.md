欢迎收听 Claude FM，我是你的主播。今天要解读的这篇文章，标题是 How healthcare organizations use Claude Tag，中文可以翻译成《医疗健康机构如何使用 Claude Tag》，副标题说的是三家医疗科技公司怎么用 Claude Tag 组建人机协作团队。文章发表在二〇二六年九月十四日，距离今天只过去六天，是 Anthropic 官方博客上一篇非常新鲜的实践案例集。

为什么我觉得它值得你在通勤路上花二十几分钟听？因为它不是概念演示，而是三个真实团队跑了一段时间之后的复盘。医疗行业是所有行业里合规要求最严的一类，但同时又是流程最繁琐、文档最多、最容易被人肉瓶颈卡住的一类。当这两个特点撞在一起，反而逼出了一套非常清晰的 agent 落地方法论：怎么划权限边界、怎么把人类专家留在环路里、怎么让非技术同事直接改生产代码。这套方法不只适用于医疗，任何做企业级 agent 的团队都能抄作业。

先说背景。过去两年，AI 编程助手和聊天机器人在开发者群体里已经普及，但真正把 agent 放进日常工作流、让它长期驻留、让它自己动手改生产系统的公司，其实还是少数。大部分团队的现状是：模型能力够用，工程化也做得出来，卡在最后一公里的是信任和边界。你敢不敢让一个 agent 直接开代码合并请求？敢不敢让它查生产数据库？敢不敢让它替你跟招聘候选人沟通？这些问题的答案不是技术问题，是权限和组织问题。

Claude Tag 是 Anthropic 在 Slack 里推出的一个产品形态，目前还在 beta 阶段。它的核心想法很朴素：与其让工程师专门打开一个网页去跟 AI 对话，不如把 AI 变成 Slack 工作区里的一个队友，一个可以被 @ 的账号。你在频道里 @Claude，它会把整个讨论串读完，调用你给它连接的工具，把活干完，然后回到频道里汇报。这件事听起来简单，但它改变了协作的基本单位。

我打个比方。传统的 AI 对话，像你把一位顾问叫进会议室，关起门来问问题，问完他走了，下一次再叫进来，他什么都不知道。Claude Tag 更像是这位顾问直接坐进了你们团队的大办公区，有自己的工位，能听到大家讨论，能看到墙上的任务板，还记着上周你们聊过什么。文章里有一句话我特别想强调：它记得每个频道里发生过什么，所以长期运转的工作不需要反复解释背景。这一条，是所有 agent 产品能不能真正融入日常的分水岭。

还有更进一层的能力：它可以在你没有 @ 它的时候，自己盯着频道，该出手时出手。这里你只要记住，Claude Tag 有三种工作姿态：被点名才动、被点名后自主执行、以及无人点名时主动介入。这三种姿态对应三种信任等级，而文章最有价值的地方，就是教你怎么按频道分配这三种等级。

现在到了这篇文章真正的核心。医疗数据在美国受一套很严的法规保护，叫 HIPAA，里面有一个关键概念叫 PHI，也就是 protected health information，中文一般译作受保护健康信息。判断一份数据是不是 PHI，不只看它有没有姓名，还要看它能不能跟某个具体的人关联起来，比如就诊日期加邮编加出生日期这种组合，都可能算。而 Anthropic 的业务伙伴协议，也就是 BAA，是它跟客户之间关于处理 PHI 的法律约定。文章说得很清楚：Claude Tag 目前还没有被 BAA 覆盖。这句话是整个案例集的起点。

那你可能会问，既然没被覆盖，医疗公司为什么还敢用？答案是，他们用得非常有选择性。他们把 Claude Tag 严格限制在永远不接触 PHI 的频道和连接器里。工程频道里讨论的是代码和报错，招聘频道里讨论的是流程和文案，运营频道里讨论的是付款方规则和政策。这些工作里当然有敏感信息，但没有患者数据。这个划线的动作，比任何提示词技巧都重要。

接下来我们看 Anthropic 给出的三层管控机制，我觉得这是整篇文章里最可以直接抄到自己公司设计里的部分。

第一，Claude Tag 默认是关闭的，管理员必须逐个频道启用它。而且私聊是禁用的，连接器的作用范围也是按频道来限定的。注意这个组合：默认关闭意味着安全默认值，逐个启用意味着每一次扩张都是一次明确的决策，私聊禁用意味着所有交互都留在公开可审计的地方，连接器按频道限定意味着同一个 Slack 工作区里，A 频道的 Claude 能看到代码库，B 频道的 Claude 看不到。这四条合起来，就是一套最小权限原则的完整落地。

第二，Claude Tag 并不会读遍整个 Slack。文章原话是，它只能看到工作区成员能看到的内容。它可以读取工作区的公开频道，也能在公开频道里做关键词搜索，但没有被邀请进去的私有频道，它看不到。这句话看起来朴素，其实在回答一个很尖锐的问题：一个 AI 队友的权限，应该比一个人类员工更大，还是更小？Anthropic 的答案是，一样大，不多不少。它是一个同事，不是一个超级管理员。

第三，是访问捆绑包，access bundles。这个名字有点抽象，我给你翻译成人话：你可以把一组数据源打包成一个访问套餐，然后只在某个频道里挂上这个套餐。Insight Health 和 Tennr 的做法是把代码库和工单系统放进套餐，挂到工程频道；而电子健康记录系统、临床系统、患者沟通渠道，全都在套餐之外，Claude 根本够不着。这就像给 agent 发一张门禁卡，卡上写着三楼研发区和二楼会议室，而不是整栋楼的全通卡。

另外还有一个挺实际的信息：企业和团队版的组织，如果激活了 Claude Tag 并把它连接到 GitHub，可以拿到一笔额度。企业能拿两万五千美元，十个席位以上的团队版能拿两千五百美元。要注意这笔额度在二〇二六年十月一日过期，也就是大概十天之后。如果你所在的公司正好符合条件，这是一个很短的实际补贴窗口，值得顺手去申请。

好，管控讲完了，我们进入第一个案例，Insight Health。这家公司做的是一个叫 MagicDocs 的产品，可以理解成面向专科诊所的 AI 转诊协调员。

它的工作流程值得展开讲一下，因为你会看到为什么这类公司对 agent 的需求特别强烈。它读取进来的患者文件，包括传真、转诊单、预授权申请、化验单、病历，从中抽取临床细节，把每份文件匹配到正确的患者，再把结构化数据写进电子健康记录系统。它服务超过一千一百家诊所，横跨五十六个专科。你可以想象每天进来多少份传真。

公司长得快，麻烦也跟着来了。生产环境的告警处理，开始吞掉这支精简工程团队本来想花在更高价值工作上的时间。于是过去三个月，他们在不含 PHI 的工程和支持频道里跑起了 Claude Tag，让它在里面调查生产告警、创建和去重工单、审查代码合并请求，并且在不同的讨论串之间携带上下文。

真正精彩的是他们的双 agent 架构。在高流量的生产告警频道里，他们让 Claude Tag 跟第二个 agent 配合，那个 agent 叫 Zeus，是基于 Claude Agent SDK 自己搭的。两个 agent 把一次事故从第一条通知，一路推进到一个经过测试的修复。而关键在于，它们的权限被故意设计成不一样的。

Claude Tag 能看到代码库和 Linear，也就是工单系统，所以它熟悉代码模式和工单历史。Zeus 则跑在公司那份被 BAA 覆盖的 Claude API 组织上，因此它可以查询生产数据，并且在数据进入 Slack 之前先把 PHI 掩码处理掉。这个设计非常聪明。我用一个类比来讲：这就像一间手术室，主刀医生能看到病人完整的影像和化验，但站在走廊里做协调的助理医生，只能看到打了码的示意图。两个角色配合完成同一台手术，但谁看得见什么，被写死在流程里。

具体跑起来是这样的。告警一来，两个 agent 分头调查：查询生产数据，对照代码和最近的部署记录，再跟历史工单比对，整个过程都在 Slack 讨论串里实时汇报进度。找到根因之后，它们开一个草稿状态的代码合并请求，盯着测试跑，最后由人类工程师来审查和合并。注意最后这一步：人类没有离场，人类是合并权的持有者。

这里我特别想展开讲频道记忆的价值。文章列举了三种表现。第一，当一条新的用户抱怨进来时，Claude Tag 能认出这其实是某个已知问题，而且已经有了待合并的修复，于是它不会再从头查一遍。第二，它能回忆起几周前的调查，把当时的结论直接调到眼前。第三，它会主动遵循团队之前立下的指令，不需要你每次重新交代。

第三点其实是最容易被忽略、但商业价值最大的一点。你想想看，人类团队里的隐性知识，很大一部分就藏在大家都知道要这么做里，新人要花几个月才能学会。当一个 agent 也能长期积累这种隐性知识，并且不流失、不休假、不跳槽，那么团队的运营连续性就被重新定义了。当然这里有个坑，后面实践部分我会专门讲，频道记忆如果没管好，也可能变成错误记忆的放大器。

Insight Health 的联合创始人兼首席技术官 Saran Siva 有一段话被引用了。他说，频道里的每个人都能看到两个 agent 的推理过程和它们怎么分工，这种透明建立起信任，也教会团队怎么把 agent 的价值榨到最大。这句话点出了一个反直觉的结论：agent 的可信度不是靠它一次都不出错建立的，而是靠它的思考过程可被围观、可被纠正建立的。把 agent 藏在一个黑盒子里只输出结果，反而更难获得信任。

结果是硬指标。自从 Claude Tag 上线，Insight Health 关键告警频道里百分之九十七的告警，在没有工程师介入的情况下就关闭了。只剩百分之三需要人动手，省下来的工程师时间被投到了核心产品上。

而且他们的用法不局限于事故处理。同一个团队还用 Claude Tag 做招聘、供应商谈判准备、合同审查，比如拿合同条款去对照通话记录看有没有出入，以及一般性的业务运营。这说明一旦频道记忆和工具连接这两件事跑通了，agent 的适用范围会自然往外扩，因为对它来说，换一件事只是换一套工具和一套上下文。

我们进入第二个案例，Tennr。这是一家患者编排平台，做的事情是自动化患者入院时那些繁琐流程：接诊登记、文档整理、授权申请、排期安排。这些环节一旦卡住，患者就迟迟进不了正确的诊疗场景。而 Tennr 用 Claude Tag 的方式跟 Insight Health 很不一样，它管的是内部工具。

文章点出了一个在高速成长公司里非常常见的现象：内部工具死得跟生得一样快，因为没有人有余力去维护它们。这个描述我相信很多听众都会心一笑。业务同事提一个需求，工程师花两天做个内部页面，上线之后需求变了、字段改了、接口升级了，没人管，三个月后这个页面就没人用了。这不完全是工程团队的错，是资源配置的必然结果。

二〇二六年七月，Tennr 换了个做法。他们用 Claude Code 搭了一个内部 offer 展示门户，然后让 Claude Tag 通过一个专门的 Slack 频道来当这个工具的主要维护者。注意这个角色的措辞，是主要维护者，不是助手。

使用这个工具的人是谁呢？招聘人员、人力团队的成员、招聘经理、收入运营团队。这些人不是工程师。他们现在用平实的自然语言在频道里 @Claude 提需求，Claude 提交代码变更、部署、然后回来汇报。工具的真正使用者可以直接迭代工具，不需要把工程师从产品工作上抽走。这句话是整篇文章里我最喜欢的一句。

我们来看看大约一个月里他们用这种方式交付了什么，这部分特别有画面感。十五个以上的工单，包括：一个福利深度介绍区块，是从上传的一份 PDF 单页材料做出来的；一个提示在这里签署 offer 的横幅，链接到 Dropbox Sign 电子签名；目标奖金字段；还有自助式的管理员控制项。

还有几个更像救火的例子。有一个对外暴露的复制接口被标记出来，Claude 当天就把它锁死了。招聘系统 Ashby 的一个导入 bug 不断重置有效 offer 里的股权数据，Claude 修掉了 bug 并把正确的值传播回去。还有一个 bug 短暂地把候选人的浮动薪酬显示错了，Claude 在没有被要求的情况下，主动在频道里发了一条公告，说明受影响的窗口和补救措施。

最后这一条我想单独说两句。主动承认错误并通知受影响方，这在人类工程师里都是需要组织文化支撑的行为，因为人天然倾向于先自己悄悄修好再说。Claude 在这里做的是它认为正确的事。它还顺手写了这个工具的入职文档，并且负责权限管理。

文章还讲了一个很有意思的细节：团队在频道里教会了 Claude 自己的运维惯例，包括一套用表情符号表示状态的小图例，以及一种工单格式，要求包含编号、提出人、代码提交链接、截图和一个实时测试链接。Claude 之后就照这个格式走了。招聘人员实际上是在用自然语言提交工程工单，有时候就丢一张截图，然后一小时内拿到一个生产环境的变更。

Tennr 的业务运营与战略副总裁 Abe Griffiths 说了一句话，我觉得可以作为整个案例的标题：Claude Tag 是让内部工具体系真正可行的那块拼图。因为工具由使用者在频道里直接管理，工程师不用被抽离产品工作。这句话背后其实是一个组织设计问题，不是技术问题。

那为什么他们的推展这么快？文章说是因为地基早就打好了。Tennr 只允许 PHI 存在于有限的一组私有频道里，所以大范围加 Claude Tag 并没有引入新的数据问题。这个细节值得所有做合规的团队记住：真正让你能快速采用新工具的前提，是你早就把数据分层做好了，而不是等到用工具的时候才临时去扫一遍数据在哪。

真正让 Tennr 敢于说可以的，是按频道划定范围这个能力。Griffiths 举了一个对比：在 offer 工具那个频道里，他们希望 Claude 是主动的，修问题、改代码、跳过代码合并请求审查、直接上线。但同样的姿态如果放到产品或工程频道，就明显是错的，因为在那类频道里，Claude 的角色更接近信息收集和保持组织有序。能一个频道一个频道地划线，意味着他们可以在低风险的地方给 Claude 真正的自主权，而不是要么全给要么全不给。

这句话我建议你记下来，它是一个非常实用的心智模型：自主权不是 agent 的属性，是 agent 在特定频道里的属性。同一个 agent，在告警频道里可以直接上线，在战略讨论频道里只该记录和整理。把这个问题想清楚，你的权限设计就有了骨架。

第三个案例是 Medallion。这家公司自动化的是医疗机构的医师资质认证、执照办理和付款方注册。这些工作高度依赖一套晦涩又没有文档的规则，比如哪些付款方要求一个医疗团队在注册之前必须已有最低数量的认证医师，比如各州自己的法规差异，还有几十个类似的问题，工程师在把某个流程写进产品之前，必须先得到答案。

历史上这些答案掌握在一小群内部的医疗领域专家手里。这就形成了一个持续存在的人肉瓶颈，而且这个瓶颈正好卡在核心产品开发决策的路径上。你可能会问，这不就是知识管理问题吗？对，但传统知识库的问题在于，写文档的成本高，维护文档的意愿低，而且专家脑子里很多判断是直觉性的，很难提前写下来。只有当你真的提出一个具体问题时，它才会被表达出来。

Claude Tag 现在就坐在这个环路里，做的事情是打破知识孤岛。当工程师在 Slack 里问一个付款方规则的问题，Claude Tag 会根据过去的专家回答、历史数据和公司内部那些非结构化的资料来作答。关键在于，这些专业知识开始在频道里累积，而不是留在某个人的脑子里。

Medallion 的首席技术官 Armaan Sarkar 说了一句话，我认为这是这篇文章里第二个最有价值的设计点。他说，当 Claude 不确定的时候，它会 @ 上正确的专家，而专家的回答会成为未来相关问题的答案基础。你看，这不是简单的问答机器人，它是一个会主动向人类求助、并把人类回答沉淀成组织资产的机制。很多人担心 AI 会让专家失业，但在这个设计里，专家的价值被放大了，因为他们的一次回答会被复用很多次。

那 Medallion 为什么敢推？Sarkar 说了三点：挑对不含 PHI 的工作流、专家审查、自动校验。我展开说一下。Claude Tag 是在政策层面运作的，它回答的问题是关于付款方规则和流程的，不涉及具体的患者或医师个人。它不是单独作答，有专家提供监督和纠正，而且每一次交流都发生在一个公司任何人都能审计的 Slack 频道里。最后，它的输出还有下游检查，因为 Medallion 的系统会拿这些政策去执行动作，而这些动作本身是被审计和验证的。

这几点合起来是一套很完整的护栏设计，我把它总结成一句话：让 AI 的产出永远站在一个还能被上游纠正、下游校验的位置上。上游是专家，下游是业务系统。AI 不需要一次就对，它需要的是错误能被及时发现，并且不造成不可逆后果。

三个团队有一个共同的起点，文章专门点出来了：他们都从工程、产品、运营或者招聘频道开始，都只接一两个连接器，而且都在公开的讨论串里工作，而不是私聊。这样的选择让整个团队都能审查、都能接上上下文。这个从公开讨论串开始的建议看起来很轻，其实很重，因为公开意味着任何人都能纠错，也意味着 agent 的行为会被组织性地观察，而不是只被提问的那一个人看到。

Anthropic 给出的上手路径也很克制：从一两个频道开始。先给告警频道或者支持工程频道打开 Claude Tag，接上 GitHub，让团队跟它一起工作两周，然后再考虑扩大允许列表。我觉得这两周的安排很有讲究，它不是单纯为了评估性能，而是为了让团队建立直觉，知道这个队友擅长什么、在哪里会犯什么错、什么样的指令它执行得好。

好，前面是文章的内容，接下来我想花一点时间，从中国工程师和 AI 从业者的角度，讲讲这件事对你在做的工作意味着什么。

第一件事，如果你在做企业内部工具，或者在做面向业务流程的 agent 产品，Tennr 那个模式非常值得研究。它本质上是把软件维护权从工程师手里，转移给了工具的实际使用者，而 agent 承担了翻译层。在国内，很多公司的内部系统是业务部门提需求、研发排期、然后做出来的，中间隔着很长的反馈链路。如果有一个 agent 常驻在业务同事的群里，能读懂自然语言需求并直接改代码、上线，这个链路会被压缩到小时级。当然前提是你的部署流程足够自动化、回滚足够容易、有测试兜底。否则使用者直接触达生产，风险会指数级放大。

第二件事，权限设计可以直接抄。默认关闭、按频道启用、私聊禁用、连接器按频道绑定，这四条是通用的，不管你用的是 Slack、飞书、钉钉还是企业微信，逻辑完全一样。如果你已经在用某种机器人接入内部系统，可以对照检查一下：你的机器人是不是默认对所有频道可见？它拿的是不是一张全通卡？它能不能被私聊触发？这三个问题如果答案是肯定的，那你现在就跑在一个高风险配置上。

第三件事，双 agent 权限分离这个思路，我认为是整篇文章里最值得借鉴的架构。一个 agent 掌握敏感数据但不进聊天工具，另一个 agent 在聊天工具里但只看得到脱敏后的信息。这个模式可以迁移到很多场景：比如客户数据不进群，但分析结论进群；比如财务明细不进群，但汇总口径进群。它有很强的可复制性，而且不需要你把安全体系推倒重来。

第四件事，关于频道记忆的坑。记忆是双刃剑。好处刚才讲了，坏处是它会把某一次的错误判断固化成惯例。如果某天一个专家在频道里随口给了一个不太准确的口径，Claude 把它当成规范记下来，之后所有相关回答都会被污染。所以我的建议是，给每个启用 Claude Tag 的频道定一个定期回顾机制，比如每月读一遍它在频道里沉淀下来的规则和惯例，把过期的和错误的清理掉。这件事听起来琐碎，但它是长期可靠性的关键。

第五件事，Medallion 那种不自信就 @ 专家的机制，我强烈建议你在自己的 agent 里实现。它解决的是一个很现实的问题：大模型在知识盲区里往往会流畅地胡说，而让它学会说我不知道，比让它答对更难。如果你能把不知道这个动作接到一个真实的人类专家身上，并且把专家的回答存下来复用，你得到的不只是一个更可靠的 agent，而是一个持续自我充实的组织知识库。

最后提醒一下那个额度的事。企业两万五千美元、十个席位以上团队版两千五百美元，二〇二六年十月一日过期。如果你所在的公司符合条件，又正好在考虑试点，这几天就是动手的窗口。

我们来总结一下。这篇文章讲的是三家医疗科技公司怎么把 Claude Tag 放进 Slack，组建人机协作团队。它们的共同做法是：先做数据分层，把 agent 严格限制在不含受保护健康信息的频道里；用默认关闭加逐频道启用的方式控制暴露面；让 agent 的推理过程在公开讨论串里被所有人围观；让人类专家和人类工程师保留最后的审查权；然后从一两个频道开始，跑两周再扩。

我个人认为，这篇文章最值钱的地方不是它证明了 agent 有多能干，而是它展示了一种成年人的态度：承认工具现在还够不着某些地方，所以先把边界画清楚，再在边界之内放手让它跑。很多团队做 agent 落地时喜欢先追求能力上限，把权限开得很大，出了问题再往回收。这三个案例给的是相反的顺序，先收紧，再逐格放开。在受监管行业里，这个顺序可能不是最优解，而是唯一解。哪怕你不做医疗，这个顺序也值得你重新审视一遍自己团队的 agent 部署策略。
