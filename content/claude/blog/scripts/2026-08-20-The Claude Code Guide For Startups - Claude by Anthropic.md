## Script

The Claude Code Guide For Startups，给创业公司的 Claude Code 指南。这篇文章发表于二〇二六年八月二十日，也就是三天前，来自 Anthropic 的官方 blog。今天是二〇二六年八月二十三日，所以这是一篇非常新的文章，讲的不是回顾过去几年 AI 编程工具怎么演进，而是 Anthropic 站在当下，观察一批正在高速增长的创业公司，看看它们到底怎样把 Claude Code 放进真实的产品研发流程里。

这期为什么值得听？因为这篇文章不是单纯介绍 Claude Code 有什么功能，也不是又一篇泛泛而谈的 AI 会改变软件工程。它更像是一份创业公司现场观察报告。Anthropic 采访了十多家快速增长的公司，试图回答一个很实际的问题：如果一个组织从第一天开始，就围绕 Claude Code 这样的 agentic coding 工具，也就是能自己读代码、改代码、跑流程、反馈结果的智能编程代理，来设计产品开发生命周期，那这个组织会长什么样？它的分工会怎么变？它的工程实践会怎么变？它的产品护城河又会怎么变？

我们先把背景铺开。过去几年，AI 编程工具已经从代码补全，走到了更复杂的编程 agent。早期你可以把它理解成一个更聪明的自动补全，工程师敲一半，它帮你补下一行，或者根据注释写一个函数。后来它可以解释报错、生成测试、重构文件。到 Claude Code 这样的工具，重点已经不只是帮你写几行代码，而是让模型进入你的开发环境，理解项目结构，阅读文件，执行命令，根据反馈迭代，甚至串起一个从需求到原型、从 review 到修复的工作流。

这对创业公司特别重要。大公司有完整的职能分工，有平台团队，有数据团队，有安全团队，有 QA，有内部工具团队。创业公司往往没有这些人，或者每个岗位只有一两个人。它们的资源限制非常明显，但它们的机会窗口又很短。一个市场信号来了，可能一周内就要验证。一个客户反馈来了，可能当天就要做出能演示的版本。传统方式下，所有想法都要排进工程队列，产品经理写文档，设计师画稿，工程师评估，排期，然后才有可能开工。这个流程在成熟组织里有它的必要性，但在创业公司里，经常会变成瓶颈。

Anthropic 在文章里观察到，这些创业公司像是十倍于自身规模的组织一样在交付。注意，这句话不是说它们真的不需要工程师了，也不是说所有岗位都变成了程序员。文章反复强调，劳动分工依然存在。营销同事还是主要做营销，开发者还是主要做开发。真正变化的是，从一个想法到一个可运行原型，也就是从零到一的第一步，不再只属于工程团队。这个门槛被 Claude Code 降低了。

这里就进入文章的第一个核心观点：人人都能 ship，但这里的 ship 不是随便把代码合进主干，而是人人都有机会把自己的业务洞察变成可运行的原型。

这句话听起来很容易变成 LinkedIn 上的口号。人人交付，人人创造，人人都是 builder。可现实里你马上会问，难道市场团队要去审批 pull request 吗？法务团队要去定位 flaky test，也就是偶发失败的测试吗？当然不是。文章给出的答案非常务实：不同岗位还是做自己擅长的事情，但是非技术同事可以参与最关键的早期探索。因为他们往往离客户、市场、合规、行业知识更近，他们知道什么问题值得解决，只是过去没有能力把这个问题快速变成一个能试的东西。

举个通勤路上很好理解的例子。假设你在一家做企业软件的创业公司。销售同事每天都听客户抱怨，说线索提交以后没人及时跟进，或者客户不知道自己的表单体验哪里掉链子。过去销售同事最多能写一个需求，说希望有个工具检测线索表单的响应速度。这个需求要排期，要讨论优先级，也许两个月后才有人做。文章里 Clay 的一个 go to market 团队成员，利用 Claude Code 做了一个自主 agent。这个 agent 会访问你的网站，填写线索收集表单，记录多久有人响应，给体验打分，然后生成一份性能报告。这里的关键不是这个功能本身多炫，而是它来自最接近市场的一线同事，并且先以原型形式出现，然后才有机会进入正式路线图。

文章里提到，最有效的创业公司不会把这种贡献留给偶然性，也不会只靠个别特别有好奇心的员工。它们会建立机制，让非技术同事的原型能够被看见、被讨论、被筛选。比如 Clay 会做季度 review，让这些原型有机会进入正式 roadmap，也就是产品路线图。Omni 则有一个专门的 Slack 频道，收集 Claude 生成的原型，参与者不只是非技术同事，也包括资深技术人员。Omni 还实践了另一个相伴随的原则，人人都和客户交流。这个点很重要，因为如果人人都能做原型，却没有客户反馈，最后就容易变成内部自嗨。只有当原型和真实客户问题相连，人人 ship 才有意义。

Crosby 的例子也很典型。文章说，他们不是把律师带到 Claude Code 面前，而是把 Claude Code 带到律师每天熟悉的工具和操作系统里。这句话很值得软件工程师反复琢磨。很多公司推广 AI 工具失败，不是因为模型能力不够，而是因为它要求用户改变太多习惯。你让法务同事打开一个陌生终端，学习 IDE，理解分支和依赖，这不现实。但如果你把 Claude Code 接到他们已经在用的工作流里，让它围绕他们的文档、审批、案例材料来工作， adoption，也就是采用率，就会高很多。

不过，文章也提醒，人人都能做原型和产品变得支离破碎之间，界限很薄。你不能让每个团队都用自己的方式生成一堆小功能，最后拼成一个像拼布一样的产品。这里 Anthropic 提到一个概念，skills，可以理解成可复用的指令文件。它们把团队的标准、上下文、设计系统、产品约束编码进去。这样不同人用 Claude Code 生成东西的时候，不是从空白 prompt 开始，而是站在同一套组织记忆上。Heidi 的联合创始人兼首席执行官 Thomas Kelly 说，团队里任何人都可以参考他们的设计系统，用 Claude Code 起草产品组件、营销材料或者演示文稿材料。但是，只要 AI 触碰到产品本身，就必须通过更高标准，而 Claude Code 帮他们更精确地达到这个标准。

我个人认为，这里对中国团队也很有启发。很多团队现在推广 AI 编程，是发一个账号，发一份工具链接，然后说大家多用。结果会怎样？会用的人效率飞起，不会用的人还是不用，团队标准没有沉淀，prompt 散落在每个人的聊天记录里。文章里的做法是把 AI 使用从个人技巧变成组织资产。比如你可以为前端组件写一份团队级 Claude 指令，里面包括设计 token 怎么用，错误提示怎么写，表单交互怎么做，无障碍要求是什么。你也可以为后端服务写一份指令，说明日志标准、幂等要求、接口风格、测试边界。这样，新人、产品、运营、工程师都在同一套护栏里探索。

第二个核心观点是，AI 不是只拿来写代码，而是要深度嵌入软件开发生命周期。文章里提到，所有公司从工业革命以来都在用技术追求效率，但这些创业公司不一样的地方，是采用 AI 的速度和深度。很多创始人明确认为，AI 是使命的一部分。机械性的百分之八十工作由 agent 承担，工程师把时间留给真正需要判断力的部分。

这句话很容易被误解成，工程师以后只做最后百分之二十。其实它背后的意思更像是，工程师不应该把大量脑力浪费在重复、低创造性、但又不能完全忽视的环节上。比如新员工环境搭建。Emergent 的 Mukund 说，新员工第一天只要把 Claude 指向正确的 markdown 文件，就能启动整个开发环境。如果 Claude 在入职过程中遇到任何损坏或过时的内容，它会更新那个文件。你想想这件事的价值。很多团队的 onboarding 文档都会过期，尤其是创业公司，依赖版本、环境变量、脚本路径经常变。新人踩坑以后在群里问，老同事口头回答，文档继续过期。下一位新人再踩一次。Emergent 的做法是让 Claude 不只是读文档，而是在使用过程中修文档。文档变成了活的系统。

代码审查也是一个重点。Heidi 的 Thomas Kelly 说，他们会基于经过验证的技术和合规框架运行自动代码审查，在任何内容发布前标出关键问题，并把建议修改路由给正确的 reviewer，也就是审查者。注意 Heidi 做的是医疗相关场景，合规要求很强，所以它不可能让 agent 随便改完就上线。这里 Claude Code 的作用是提前筛出风险，按照技术和合规框架做第一轮检查，然后把人类专家的注意力集中到真正关键的地方。

Translucent 的创始人 Jack 提到一个他最喜欢的 agent，叫 Translucent code reviewer。这个 agent 会围绕一个变更，从多个角度展开审查，然后像资深工程师一样综合结果，但速度比任何一个人都快。Clay 也构建了处理 bug triage 的 agent。bug triage 可以理解成 bug 分诊，从第一轮判断到提出修复代码建议。这里的关键不是让 agent 取代 reviewer，而是让 review、测试、CI、分诊这些原本零散的环节形成 loop，也就是反馈循环。agent 发现问题，提出建议，人类确认，结果反过来改进规则和指令，下一次更好。

如果你现在在一个工程团队里，可以想象一下怎么落地。很多团队的 code review 其实存在两个极端。一种是流于形式，大家看一眼有没有明显问题就点通过。另一种是非常依赖少数资深同事，所有复杂 PR 都压到他们身上，结果 review 排队，发布变慢。Claude Code 这样的 agent 如果接入得当，可以先做结构化检查。比如有没有遗漏测试，接口是否破坏兼容，数据库 migration 有没有回滚策略，日志里有没有敏感信息，权限校验是否绕过，前端组件是否符合设计系统。它不需要最终拍板，但它可以让 reviewer 不再从零开始。

第三个核心观点，是这些公司用 Claude Code 加速大量重复而繁琐的业务流程，尤其是数据分析。文章说，另一个反复出现的模式是，创业公司不只用 Claude Code 的 agentic loop 加速开发，也在创建 agent 来加速经常重复、令人厌烦的流程。这样团队可以把注意力放在竞争优势、客户关系和收入增长上。

最常见的例子是自助式数据分析。创业公司非常依赖快速决策，而且决策需要新鲜数据，包括非结构化数据。传统数据分析往往要写 SQL，拉仪表盘，等数据团队排期，或者靠业务同事手工整理。现在这些公司会把 Claude 用在内部分析 agent 上。Clay 做了内部 analytics agent。Heidi 用 Claude Code 把客户和临床医生反馈与使用数据一起分类，从中浮现对产品洞察真正重要的信号。ClickHouse 和 Omni 本身也发布了把这类 AI 数据分析打包进去的产品，而且由 Claude 驱动。

文章还提到一些更行业化的例子。Crosby 用 subagents，也就是子代理，总结数千份法律文件。Commure 扫描理赔数据，标记不同站点的异常。Translucent 持续挖掘医院财务数据，寻找任何分析师团队都来不及捕捉的预警信号。你会发现，这些场景有一个共同特点：信息量很大，格式不完全统一，人工处理很慢，但又需要一定判断力。AI 在这里不是简单跑一个统计脚本，而是把大量文本、表格、反馈、记录揉在一起，先做筛选、归类、解释和提醒。

对软件工程师来说，这意味着内部工具的价值可能被重新估价。过去内部工具常常是工程团队最不愿意碰的事情，因为它们不直接产生收入，需求又碎，维护还麻烦。但在 AI 原生团队里，内部 agent 可能是速度优势的来源。比如客服反馈自动聚类，销售通话自动提取产品需求，线上异常自动关联最近发布，合规文档自动比对政策变化，财务指标自动解释波动原因。这些东西单看都不是核心产品，但它们让团队更快学习、更快转向、更快发现问题。

不过，文章紧接着给出一个非常重要的配套原则：你不能自动化一个过程，除非你有可靠的方法监控和验证结果。也就是说，自动化繁琐工作必须和评估、审计、治理一起出现。

Anthropic 特别强调，这些创业公司不是让 agent 直接 merge 到 main，然后祈祷一切顺利。很多公司处在高度监管行业，需要强治理框架。Cainex 的例子非常详细，也非常值得展开。它们把 agent 和确定性检查结合起来，读取医疗记录，生成指导医院账单的编码。这类任务风险很高，因为医疗编码会影响计费、合规和审计，不能靠感觉。

Cainex 的 Uriah 描述了他们的循环。Claude Code 先帮助处理一批数据，agent 给出输出。审计人员在内部应用里审查结果。他们看到的不只是编码本身，还能看到模型的推理，并且可以对编码和推理都发表评论。所有东西都有版本，可以审计。然后 Claude Code 读取原始预测、每一条修正和评论，这些内容都来自数据库。每个修正会按编码类型打标签，所以 Claude Code 知道这是诊断问题、程序问题，还是其他类别，并且能直接找到管理这类编码的具体指导原则。

接下来，Claude Code 会找到 agent 指令中导致错误的部分并修改它。如果遇到真正的新情况，就写新的指导。每个变更都基于有版本的指令集合，并且会在失败过的记录上测试。Uriah 说他们强制执行一条规则，修原则，不修例子。这个表达非常关键。很多团队做 prompt 迭代时，会看到一个错误就往 prompt 里塞一个特例。下次又错，再塞一个特例。最后 prompt 变成一堆补丁，模型也不是真的更聪明，只是被硬塞了很多局部规则。Cainex 的经验是，必须把专家反馈提升为一般原则。

然后是 back test，也就是回测。医疗记录可能有不止一种可接受编码，所以不能简单做字符串匹配。它们的检查结合语义匹配和一个 judge，也就是评判模型，去判断这是一个真实错误，还是另一条同样有效的路径。Claude Code 还会增加自己的比较。候选变更会跑过黄金数据集和随机样本，在任何东西发布前暴露回归问题。最后返回的是一个短列表，包括建议编辑、无法解决的记录，以及它希望人类回答的问题。工程师的时间就花在真正困难的案例上，而不是机械性的百分之八十。

这里的黄金数据集，英文叫 golden set，可以理解成一组经过验证的问题和答案，用来评估 agent 准确性。文章明确说，每个创业公司都应该为关键用例维护多组 evals，也就是评估集，并定期更新，这样才能防止 drift，也就是模型或系统表现随时间漂移，也能评估未来模型。这个建议非常实用。因为很多团队一开始试 AI agent，只看几个 demo 成不成功。demo 成功不代表系统可上线。真正上线需要知道它在边界场景、坏数据、歧义输入、权限约束、历史遗留逻辑里表现如何。

我个人认为，这一段是全文最有工程含金量的地方。因为它把 AI agent 从玩具推向生产系统。生产系统的核心不是模型回答得漂不漂亮，而是你有没有闭环。有没有版本管理，有没有审计，有没有人类专家反馈，有没有回测，有没有黄金集，有没有回归检测，有没有把错误归因到原则而不是例子。如果没有这些，agent 越自动化，风险越大。尤其在金融、医疗、法律、政企、基础设施这些场景，速度不是唯一指标，可控性同样是竞争力。

第四个核心观点，是 AI 原生创业公司处在持续重建状态。文章说，AI 往往既是它们正在构建的东西，也是它们构建东西的方法。由于模型能力持续演进，曾经很突破的功能、曾经很关键的脚手架，一旦变成沉没成本，就会被丢掉或重写。很多组织把这种不断重建看成竞争优势的一部分。

Clay 的 Kareem 说，他们的做法是，你构建它，然后再构建一遍，然后再构建一遍。到第四次构建时，你知道所有需要的东西，然后就能做对。他还说，他们不一定是把东西扔掉，而是重建，这一次更清楚。这个说法可能会让传统工程管理者有点紧张。因为我们过去一直强调不要重复造轮子，不要频繁重写，重写系统风险很大。但在 AI 快速变化时期，如果你早期为了弥补模型能力不足，搭了大量复杂工作流、RAG 管线、规则补丁和人工兜底，一旦模型能力跃迁，这些脚手架可能反而拖慢你。

Commure 的联合创始人 Tanay 说得更工程化。他说，一次重建不是新路径上线就结束，而是旧路径消失才结束。以前拆除旧代码总是在优先级竞争中失败，因为它繁琐，而且不发布新功能。现在 Commure 的工程师可以调用一个 Claude skill，大意是，对每一个已经发布给所有人的 feature flag，打开一个 PR 移除它以及相关代码，然后工程师审查返回结果。过去会吃掉很多开发周期的迁移，现在变成一个计划加上并行展开，几小时内完成。

这个例子对做过大型代码库维护的人来说很有共鸣。feature flag，也就是功能开关，本来是为了安全发布。但开关如果不清理，就会堆积成技术债。代码里到处是 if else，老路径新路径并存，测试矩阵变复杂，没人敢删。过去清理这类东西很烦，因为没有产品荣誉感，也不容易被排进 sprint。AI agent 的价值在这里不是发明新功能，而是降低清债成本。技术债的危险在于，每次清理都太痛，所以团队选择不清理。如果 Claude Code 能把初稿 PR、影响范围、测试建议都准备好，人类只需要审查，那么维护质量就有机会跟上交付速度。

文章还引用 Kareem 对护城河的看法。他说，任何公司现在的护城河都需要是自我改进的。Clay 是一个自学习的 revenue engine，也就是收入引擎。你用得越多，它越知道谁是你的最佳客户，应该说什么，什么有效，什么无效，而且这些都会随时间变化。他认为竞争真正比的是谁能最快拿到分发，也就是触达更多客户，然后帮助每个客户，从而让系统自我改进。

这里我们可以稍微停一下。传统软件的护城河可能来自功能完整度、品牌、渠道、数据、网络效应。AI 原生产品的护城河，可能越来越像一个学习系统。用户越多，反馈越多，agent 越知道场景，产品越能改进，内部团队也越会用 AI 构建下一代功能。文章里提到，在二〇二六年五月的 Code with Claude 活动上，Harvey 的应用 AI 负责人 Niko Grupen 说，每一波新模型能力，比如涌现推理、agentic 自动化、规划与编排，都要求平台进行完整的重新架构。虽然原文在 Cognition 联合创始人 Walden Yan 的引用处没有展开具体话语，但它把这些公司放在同一个脉络里：模型边界不断外推，产品架构也必须不断调整。

第五个核心观点，是内部用 AI 构建，反过来帮助公司更好地构建 AI 产品，形成飞轮。文章说，很多创业公司的开发过程中心都有一个关键 flywheel，也就是飞轮。用 AI 构建，帮助它们创造带 AI 的颠覆性产品。开发者推进自己的 agentic coding 实践时，会更强地理解模型能力，也会更清楚前沿 harness design，也就是模型外部工具框架和交互编排，正在怎样演化。然后他们把这些洞察用回自己的 agent 和产品里。

Omni 的 Chris 说，他们从 Anthropic 的文件与 embedding 方法中得到启发，更有信心在自己产品里保持简单，避免了很多本来会来自 RAG pipeline 的复杂性。RAG 是检索增强生成，很多团队一做知识库问答就会默认上 embedding、向量库、chunk、召回、重排。Anthropic 的实践让他们看到，有时候保持文件级上下文和简单工具访问，可能比复杂管线更稳。Chris 还说，他们看到 Claude Code 的 harness 如何让用户并行做事，于是把一些概念改造进自己的 UI。

Emergent 的 Mukund 也提到，因为他们的 app builder，也就是应用构建器，背后也使用 Anthropic 模型。如果他们在自己的产品里看到某种行为，就可以通过 Claude Code 在本地快速调试，判断这是模型行为，还是 harness 问题。这极大改善了 triage cycle，也就是问题分诊周期。这个点非常真实。做 AI 产品时，经常会遇到一个困惑：到底是模型本身不行，还是我们给的上下文不对，工具调用设计不好，提示词有歧义，状态管理出错，或者 UI 引导有问题？如果你的团队日常就用 Claude Code 理解这些边界，你排查问题的速度会更快。

文章总结出一个反复出现的模式：先用 Claude Code 构建内部 agent，自己内部使用，也就是 dogfood，吃自己的狗粮。如果反馈好，再把它提升为面向客户的产品，通常会用 Claude API、SDK，或者 Claude Managed Agents。ClickHouse 的 Alexey 说，他们在产品中构建了自己的 AI agents，团队可以直接交互，包括 SQL console 里的 agent 和 AI SRE。SRE 是站点可靠性工程，用在这里就是帮助处理可靠性和运维问题的 AI 角色。他们用 Claude Code 构建和迭代这些 agent。也就是说，驱动客户 AI 体验的工具，在某种程度上也是用 AI 构建出来的。

这个飞轮对工程组织非常重要。过去内部工具和外部产品经常割裂。内部工具只是为了省事，产品是另一套严肃系统。但在 AI 时代，内部工具可能是外部产品的孵化器。因为内部团队最容易高频使用、快速反馈、容忍粗糙版本，也最懂边界。一个内部 SQL agent 如果真能帮助工程师和数据分析师更快定位问题，就有可能变成客户也想要的能力。一个内部代码审查 agent 如果能稳定发现合规风险，也可能成为平台级功能。一个内部客服反馈分析 agent 如果能准确提取产品信号，也可能包装成客户洞察产品。

说到这里，我们把文章内容转成听众能立刻行动的实践建议。第一件事，不要从买工具开始，而要从找瓶颈开始。你可以问团队，哪些事情每周重复发生，但大家都不愿意做？新员工搭环境是不是总踩坑？PR review 是不是卡在少数人手上？客服反馈是不是没人整理？销售通话里的产品信号是不是丢在录音里？feature flag 是不是没人清？数据分析是不是要排队？这些地方比让 AI 随机写一个新功能更适合作为起点。

第二件事，如果你希望非技术同事参与，不要把他们丢进工程环境里。文章里 Crosby 的启发是，把 Claude Code 带到用户熟悉的工作流里。对中国公司来说，可能是飞书、企业微信、钉钉、语雀、Notion、Jira、内部 CRM、客服系统。你要设计的是入口和上下文，而不是只发一个终端命令。比如市场同事可以在一个模板里描述活动页需求，Claude 根据设计系统生成原型；法务同事可以在文档库里让 Claude 总结合同差异；运营同事可以在数据看板旁边让 Claude 解释异常。技术团队负责护栏、权限、版本和评审。

第三件事，要把 skills 或类似机制当成组织标准沉淀。不要让每个人都从零写 prompt。你可以建立不同用途的指令文件，比如前端组件生成、后端接口修改、数据库 migration、客服反馈分析、代码审查、合规检查、发布复盘。每个指令文件都要包含团队上下文、允许做什么、不允许做什么、输出格式、常见坑、参考文件位置。它的作用有点像过去的工程规范加 runbook，也就是操作手册，只是现在它可以被 agent 直接执行。

第四件事，任何接近生产的 agent，都要先设计评估闭环。你至少要有一组黄金数据集，覆盖正常样例、边界样例、坏样例和高风险样例。你要记录每次 agent 的输入、输出、推理摘要、版本、人工修正。你要能回放历史失败案例，检查新指令有没有修好，也有没有引入回归。你还要明确哪些场景必须人类审批，哪些场景可以自动执行，哪些场景只能给建议。文章里的 Cainex 给了一个非常好的原则，修原则，不修例子。每次错误都要问，背后的通用规则是什么，而不是往 prompt 里塞一个孤立补丁。

第五件事，重建和清理要成为正常工作，而不是失败信号。AI 发展太快，今天合理的架构，半年后可能显得笨重。你当然不能为了追新每天重写系统，但也不能把早期 workaround 当成永久资产。可以让 Claude Code 帮你做技术债盘点，找已经全量发布的 feature flag，找废弃接口，找重复逻辑，找过时文档，生成迁移计划和初稿 PR。人的价值在于判断优先级、审查风险、决定架构方向，而不是手工搜全仓库删分支。

最后也提醒几个坑。不要把人人 ship 理解成人人都能绕过工程治理。原型可以开放，生产必须严格。不要把 AI review 当成最终审查，它应该是前置过滤和辅助判断。不要过度迷信复杂 RAG 或多 agent 编排，文章里 Omni 的经验反而说明，简单架构有时更强。不要只追求自动化比例，而忽略可观测性和审计。还有，不要把 AI 采用变成员工个人能力竞赛。真正有复利的是团队级标准、共享指令、评估数据和反馈循环。

收个尾。这篇 The Claude Code Guide For Startups 讲的核心不是 Claude Code 某个具体功能，而是创业公司如何围绕 agentic coding 重新组织产品开发：让更多人参与从零到一，让 AI 承担机械性的重复工作，用评估和审计守住生产边界，再通过持续重建和内部 dogfood 形成产品飞轮。我个人认为，这篇文章最值得中国工程团队借鉴的，不是照搬某家公司用了什么 agent，而是把 AI 从个人提效工具升级成组织操作系统的一部分。谁能更快把经验沉淀成可复用流程，谁就更可能把模型能力真正转化成交付速度和产品优势。
